Automatic Static Optimization자동 Static 최적화

page에 blocking data 요구 사항이 없으면 Next.js는 해당 page가 static(prerender 가능)하다고 자동으로 판단합니다. 이 판단은 page에 getServerSideProps와 getInitialProps가 없는지를 기준으로 합니다.

Next.js automatically determines that a page is static (can be prerendered) if it has no blocking data requirements. This determination is made by the absence of getServerSideProps and getInitialProps in the page.

이 기능 덕분에 Next.js는 server-rendered page와 statically generated page를 모두 포함하는 hybrid 애플리케이션을 만들어 낼 수 있습니다.

This feature allows Next.js to emit hybrid applications that contain both server-rendered and statically generated pages.

Good to know

statically generated page도 여전히 reactive합니다. Next.js는 애플리케이션을 client-side에서 hydrate해 완전한 interactivity를 제공합니다.

Statically generated pages are still reactive. Next.js will hydrate your application client-side to give it full interactivity.

이 기능의 주요 이점 중 하나는 최적화된 page에는 server-side 연산이 필요 없고, 여러 CDN 위치에서 최종 사용자에게 즉시 stream될 수 있다는 것입니다. 그 결과 사용자는 매우 빠른 loading 경험을 얻습니다.

One of the main benefits of this feature is that optimized pages require no server-side computation, and can be instantly streamed to the end-user from multiple CDN locations. The result is an ultra fast loading experience for your users.

How it works동작 방식

page에 getServerSideProps나 getInitialProps가 있으면, Next.js는 page를 request마다 on-demand로 render하는 방식(Server-Side Rendering)으로 전환합니다.

If getServerSideProps or getInitialProps is present in a page, Next.js will switch to render the page on-demand, per-request (meaning Server-Side Rendering).

그렇지 않은 경우 Next.js는 page를 static HTML로 prerender해서 자동으로 static 최적화합니다.

If the above is not the case, Next.js will statically optimize your page automatically by prerendering the page to static HTML.

prerendering 중에는 이 단계에서 제공할 query 정보가 없으므로 router의 query object가 비어 있습니다. hydration 후에 Next.js는 애플리케이션 업데이트를 trigger해 query object에 route parameter를 제공합니다.

During prerendering, the router's query object will be empty since we do not have query information to provide during this phase. After hydration, Next.js will trigger an update to your application to provide the route parameters in the query object.

hydration 후 query가 업데이트되어 또 한 번의 render를 trigger하는 경우는 다음과 같습니다:

The cases where the query will be updated after hydration triggering another render are:

  • page가 dynamic-route인 경우.
  • page의 URL에 query 값이 있는 경우.
  • next.config.js에 Rewrites가 설정된 경우. rewrite에는 parse해서 query에 제공해야 할 수도 있는 parameter가 있을 수 있기 때문입니다.
  • The page is a dynamic-route.
  • The page has query values in the URL.
  • Rewrites are configured in your next.config.js since these can have parameters that may need to be parsed and provided in the query.

query가 완전히 업데이트되어 사용할 준비가 되었는지 구분하려면 next/router의 isReady field를 활용할 수 있습니다.

To be able to distinguish if the query is fully updated and ready for use, you can leverage the isReady field on next/router.

Good to know

getStaticProps를 사용하는 page에 dynamic route로 추가된 parameter는 항상 query object 안에서 사용할 수 있습니다.

Parameters added with dynamic routes to a page that's using getStaticProps will always be available inside the query object.

next build는 static 최적화된 page에 대해 .html 파일을 만들어 냅니다. 예를 들어 pages/about.js page의 결과는 다음과 같습니다:

Caveats주의 사항

  • getInitialProps가 있는 custom App이 있으면, Static Generation을 사용하지 않는 page에서는 이 최적화가 꺼집니다.
  • getInitialProps가 있는 custom Document가 있다면, page가 server-side rendered라고 가정하기 전에 ctx.req가 정의되어 있는지 확인하세요. prerender된 page에서는 ctx.req가 undefined입니다.
  • router의 isReady field가 true가 될 때까지 rendering tree에서 next/router의 asPath 값을 사용하지 마세요. static 최적화된 page는 server가 아닌 client에서만 asPath를 알기 때문에, 이를 prop으로 사용하면 mismatch error가 발생할 수 있습니다. active-class-name 예제는 asPath를 prop으로 사용하는 한 가지 방법을 보여 줍니다.
  • If you have a custom App with getInitialProps then this optimization will be turned off in pages without Static Generation.
  • If you have a custom Document with getInitialProps be sure you check if ctx.req is defined before assuming the page is server-side rendered. ctx.req will be undefined for pages that are prerendered.
  • Avoid using the asPath value on next/router in the rendering tree until the router's isReady field is true. Statically optimized pages only know asPath on the client and not the server, so using it as a prop may lead to mismatch errors. The active-class-name example demonstrates one way to use asPath as a prop.
