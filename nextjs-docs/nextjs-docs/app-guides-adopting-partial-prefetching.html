Adopting Partial PrefetchingPartial Prefetching 도입하기

Partial Prefetching은 Cache Components route에서 <Link>가 다운로드하는 내용을 바꿉니다. Partial Prefetching이 활성화되면 <Link>는 route의 App Shell, 즉 static content와 URL에 의존하지 않는 cached content를 prefetch합니다. Next.js는 예전처럼 link마다 따로 prefetch하는 대신, route마다 App Shell을 하나 build하고 그 route를 가리키는 모든 link에서 이를 재사용합니다.

Partial Prefetching changes what a <Link> downloads for a Cache Components route. With Partial Prefetching enabled, a <Link> prefetches the route's App Shell: its static content and the cached content that doesn't depend on the URL. Next.js builds one App Shell per route and reuses it for every link to that route, rather than prefetching each link separately as it did before.

App Shell보다 더 많이 prefetch하려면 link에서 <Link prefetch={true}>로 per-link prefetching을 opt in할 수 있습니다. 그러면 prefetch가 params, searchParams 또는 전체 URL에 의존하는 cached URL-specific content까지 resolve할 수 있습니다.

To prefetch more than the App Shell, a link can opt into per-link prefetching with <Link prefetch={true}>. The prefetch can then resolve cached URL-specific content that depends on params, searchParams, or the full URL.

그 과정에서 Next.js는 development 중에 instant navigation insight를 보여 주며, 바꿔야 할 link나 route를 알려 줍니다.

Along the way, Next.js surfaces instant navigation insights in development, naming the link or route to change.

Good to know

Partial Prefetching은 cacheComponents가 활성화되어 있을 때만 동작합니다.

Partial Prefetching only works when cacheComponents is enabled.

Or adopt by hand또는 직접 도입하기

기존 앱에 직접 도입하려면:

To adopt an existing app by hand:

  1. 기존 full prefetch를 검토하고 각 destination의 어느 부분을 계속 prefetch할지 정합니다. instant() test로 regression coverage를 추가할 수 있습니다.
  2. partialPrefetching을 활성화합니다. 규모가 큰 migration이라면 global flag를 끈 채로 점진적으로 도입할 수 있습니다. dynamic data during prefetching insight가 아직 legacy full prefetch를 사용하는 destination을 하나하나 찾아 줍니다.
  3. URL data를 Suspense 뒤로 옮겨 URL data outside of Suspense insight를 해결합니다.
  4. 필요하다면 navigation 후에 stream되는 것만으로는 부족한 route에서 URL data를 prefetch합니다.
  1. Review existing full prefetches and choose which part of each destination should continue to be prefetched. You can use instant() tests to add regression coverage.
  2. Enable partialPrefetching. For larger migrations, you can adopt incrementally with the global flag off. The dynamic data during prefetching insight identifies each destination that still uses the legacy full prefetch.
  3. Move URL data behind Suspense, resolving the URL data outside of Suspense insight.
  4. Optionally, prefetch URL data on the routes where streaming in after navigation isn't enough.

두 insight 모두 development 전용이며 build를 막지 않습니다. 이 insight들은 dev overlay에 fix card와 함께 표시되며, 각 fix card는 해당 해결 방법의 문서 페이지로 연결됩니다. 아직 도입할 준비가 안 된 route가 있다면 그 page나 layout에서 instant = false를 export해 해당 route를 instant-navigation 검증에서 제외하고, 나중에 다시 돌아오세요.

Both insights are development-only and never block the build. They appear in the dev overlay with fix cards that link the docs page for each fix. If a route isn't ready to adopt, export instant = false from its page or layout to opt the route out of instant-navigation validation, and return to it later.

Enable Partial PrefetchingPartial Prefetching 활성화하기

Good to know

기존 앱에서는 Partial Prefetching을 활성화하기 전에 <Link prefetch={true}>가 전달하는 UI를 검토하세요. 이 link들은 legacy full prefetch를 사용하며, Partial Prefetching을 활성화하면 동작이 바뀝니다.

In an existing app, review the UI delivered by <Link prefetch={true}> before enabling Partial Prefetching. These links use the legacy full prefetch, and enabling Partial Prefetching changes their behavior.

next.config.ts에서 partialPrefetching을 활성화하세요:

Enable partialPrefetching in next.config.ts:

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
}

export default nextConfig

flag를 활성화하면 기본 동작, prefetch="auto", prefetch={true}를 사용하는 link는 destination의 App Shell을 prefetch합니다. prefetch={true}가 있는 link는 cached URL-specific content도 resolve할 수 있지만, 더 이상 legacy full prefetch에 있던 uncached dynamic content는 포함하지 않습니다. 새 프로젝트는 migrate할 legacy full prefetch가 없으므로 이 검토 없이 flag를 활성화해도 됩니다.

After enabling the flag, links using the default behavior, prefetch="auto", or prefetch={true} prefetch the destination's App Shell. A link with prefetch={true} can also resolve cached URL-specific content, but it no longer includes uncached dynamic content from the legacy full prefetch. New projects can enable the flag without this audit because they have no legacy full prefetches to migrate.

Good to know

partialPrefetching 값 없이 cacheComponents가 활성화되어 있으면, Next.js는 이를 true 또는 false로 설정하라는 경고를 log에 남깁니다. false는 이 가이드를 진행하는 동안 이전 prefetch 동작을 유지하려는 경우에만 설정하세요. 다음 major release에서는 두 기능이 모든 곳에서 활성화되고 이 option들은 제거될 예정입니다.

When cacheComponents is enabled without a partialPrefetching value, Next.js logs a warning asking you to set it to true or false. Set false only to keep the previous prefetch behavior while you work through this guide. Both features will be enabled everywhere in the next major release, and the options will be removed.

App Shell은 dynamic param과 관계없이 특정 route를 가리키는 모든 link가 공유하므로, 같은 destination으로 가는 <Link>를 많이 render해도 작업량이 늘어나지 않습니다.

The App Shell is shared across every link to a given route, regardless of dynamic params, so rendering many <Link>s to the same destination doesn't multiply the work.

Migrate existing full prefetches기존 full prefetch migrate하기

Partial Prefetching 이전에는 실제 적용되는 prefetch 값이 true인 <Link>가 uncached dynamic content를 포함해 destination 전체를 prefetch합니다. 여기에는 prefetch={true}, 값 없는 prefetch prop, 그리고 true로 resolve되는 wrapper prop이나 조건부 prop이 포함됩니다. 기본값, prefetch="auto", prefetch={false}는 legacy full prefetch를 사용하지 않습니다.

Before Partial Prefetching, a <Link> whose effective prefetch value is true prefetches the complete destination, including uncached dynamic content. This includes prefetch={true}, the bare prefetch prop, and wrapper or conditional props that resolve to true. The default value, prefetch="auto", and prefetch={false} don't use the legacy full prefetch.

legacy full prefetch는 navigation에 필요한 것보다 더 많은 UI를 포함할 수 있습니다. 대부분의 경우 destination 상단의 주요 콘텐츠는 navigation 전에 준비되어 있어야 하고, 부차적이거나 자주 바뀌는 콘텐츠는 그 뒤에 stream해도 됩니다.

A legacy full prefetch can include more UI than the navigation needs. In most cases, the primary content at the top of the destination should be available before navigation, while secondary or frequently changing content can stream afterward.

Good to know

cookies()와 headers()는 prefetch를 URL에 묶지 않습니다. 이 값들은 link마다가 아니라 session마다 달라지므로 App Shell에 여전히 session content가 들어갑니다. params와 searchParams만이 URL data이며, 이는 link마다 달라지므로 공유 App Shell에 포함될 수 없습니다.

cookies() and headers() don't tie a prefetch to a URL. They vary per session, not per link, so the App Shell still carries session content. Only params and searchParams are URL data, which varies per link and can't be included in the shared App Shell.

Verify prefetched UI with teststest로 prefetch된 UI 검증하기

migration을 프로그래밍 방식으로 검증하려면 instant() test로 기존 full prefetch에서 계속 제공되어야 할 UI를 기록할 수 있습니다. 같은 destination으로 가는 link라도 prefetch 설정이 다를 수 있으므로 정확히 그 source link를 test하세요:

To verify the migration programmatically, an instant() test can capture the UI that should stay available from an existing full prefetch. Test the exact source link because different links to the same destination can use different prefetch settings:

TSe2e/product-navigation.test.ts
import { expect, test } from '@playwright/test'
import { instant } from '@next/playwright'

test('preserves the prefetched product summary', async ({ page }) => {
  await page.goto('/products')

  await instant(page, async () => {
    const link = page.getByRole('link', { name: 'Baseball Cap' })
    await expect(link).toBeVisible()
    await link.click()
    await page.waitForURL((url) => url.pathname === '/products/baseball-cap')

    await expect(
      page.getByRole('heading', { name: 'Baseball Cap' })
    ).toBeVisible()
    await expect(page.getByTestId('product-summary')).toBeVisible()
  })
})

next dev에서는 자동 prefetching이 실행되지 않으므로, 이 baseline은 partialPrefetching을 비활성화한 production build에서 실행하세요. 그런 다음 destination을 도입한 뒤 같은 test를 다시 실행합니다. test가 실패하면 선택한 UI가 더 이상 prefetch되지 않는다는 뜻입니다. 계속 제공되어야 할 재사용 가능한 data나 subtree를 cache한 다음, 통과한 test는 regression coverage로 남겨 두세요.

Run this baseline against a production build with partialPrefetching disabled because automatic prefetching doesn't run in next dev. Then rerun the same test after adopting the destination. If it fails, the selected UI is no longer prefetched. Cache the reusable data or subtree that should stay available, then keep the passing test as regression coverage.

Static or cached contentStatic 또는 cached content

출력 결과가 이미 App Shell에 들어 있습니다. 이제 불필요해진 prefetch={true}를 제거하세요:

The output is already in the App Shell. Remove the now-redundant prefetch={true}:

TSapp/nav.tsx
// Before
<Link href="/about" prefetch={true}>About</Link>
// After
<Link href="/about">About</Link>

Uncached content

use cache로 cache해서 App Shell에 포함되게 한 다음, link에서 prefetch={true}를 제거하세요:

Cache it with use cache so it gets included in the App Shell, then remove prefetch={true} from the links:

TSJSapp/products/page.tsx
// Before

Good to know

App Shell에는 stale 시간이 최소 5분인 cached content가 들어갑니다. 위에서 사용한 default profile과 seconds를 제외한 모든 preset이 이 조건을 만족합니다. 이보다 수명이 짧은 콘텐츠는 대신 navigation 후에 stream됩니다. Prerendering behavior를 참고하세요.

The App Shell carries cached content whose stale time is at least 5 minutes, which holds for the default profile used above and every preset except seconds. Shorter-lived content streams in after the navigation instead. See Prerendering behavior.

Session content

cookies()나 headers() 뒤에 있는 콘텐츠는 link마다가 아니라 session마다 달라지고, session data는 App Shell 안에서 resolve되므로 cached session content도 여전히 포함됩니다. session 값은 cache된 함수 밖에서 읽어 인자로 넘긴 다음, link에서 prefetch={true}를 제거하세요:

Content behind cookies() or headers() varies per session, not per link, and session data resolves in the App Shell, so cached session content still gets included. Read the session value outside the cached function and pass it in, then remove prefetch={true} from the links:

TSJSapp/dashboard/page.tsx
// Before
import { Suspense } from 'react'
import { cookies } from 'next/headers'

async function TeamTopics() {
  const team = (await cookies()).get('team')?.value
  const topics = await db.topics.forTeam(team)
  return <TopicList topics={topics} />
}

export default function Page() {
  return (
    <Suspense fallback={<Skeleton />}>
      <TeamTopics />
    </Suspense>
  )
}
// Before
import { Suspense } from 'react'
import { cookies } from 'next/headers'

async function TeamTopics() {

URL data

URL data(params, searchParams)는 link마다 달라지므로, 이에 의존하는 콘텐츠는 공유 App Shell에 포함될 수 없고 navigation 후 <Suspense> boundary 뒤에서 stream됩니다. 이런 link는 prefetch={true}를 유지하며, 클릭 전에 콘텐츠를 prefetch하는 방법은 Prefetching URL data에서 다룹니다.

URL data (params, searchParams) varies per link, so content that depends on it can't be included in the shared App Shell and streams in after navigation from behind its <Suspense> boundary. The links keep prefetch={true}, and Prefetching URL data covers prefetching the content ahead of the click.

Real-time content

real-time content를 prefetch해도 클릭할 때쯤이면 이미 stale 상태가 되므로 보존할 것이 없습니다. prefetch={true}를 제거하고 콘텐츠가 <Suspense> boundary 뒤에서 stream되도록 하세요.

A prefetch of real-time content would be stale by the click, so there is nothing to preserve. Remove prefetch={true} and let the content stream in from behind its <Suspense> boundary.

Adopting incrementally점진적으로 도입하기

도입을 한 번의 변경으로 끝낼 필요는 없습니다. prefetch = 'partial'은 하나의 route로 범위를 좁힌 global flag이므로, global flag를 끈 상태에서도 destination별로 따로 도입하고 deploy할 수 있습니다.

Adoption doesn't have to happen in one change. prefetch = 'partial' is the global flag scoped to one route, so with the global flag still off, you can adopt and deploy each destination on its own.

destination이 Partial Prefetching을 opt in하기 전에는 prefetch={true}가 legacy full prefetch를 수행합니다. development 중에 이런 link로 navigation하면 dynamic data during prefetching insight가 나타나 해당 destination을 알려 주고 해결 방법을 안내합니다:

Before a destination opts into Partial Prefetching, prefetch={true} performs the legacy full prefetch. Navigating through one of these links in development surfaces the dynamic data during prefetching insight, naming the destination and pointing at its fixes:

Opt into Partial Prefetching

    If the page or layout already calls prefetch(), import it under another name, for example import { prefetch as prefetchStage } from 'next/cache', so it doesn't collide with the prefetch export.

  2. Deploy the change. Links to the adopted destination load the App Shell, and the insight keeps surfacing for the destinations you haven't reached.
  3. Repeat until every destination in scope is adopted, then enable the flag.

이제 route별 prefetch = 'partial' export는 불필요합니다. 모든 page와 layout에서 export const prefetch = 'partial'을 제거해 주는 remove-partial-prefetch codemod로 한 번에 제거하세요:

The per-route prefetch = 'partial' exports are now redundant. Remove them in one pass with the remove-partial-prefetch codemod, which strips export const prefetch = 'partial' from every page and layout:

>_Terminal
npx @next/codemod@canary remove-partial-prefetch ./app
Good to know

src/ 프로젝트에서는 ./src/app을 넘기세요. 경로가 잘못되면 실패하는 대신 0 ok를 출력하므로 파일 개수를 확인하세요.

Pass ./src/app in a src/ project. A wrong path reports 0 ok instead of failing, so check the file count.

The codemod removes only the 'partial' value and leaves other values such as prefetch = 'force-disabled' in place.

Move URL data behind SuspenseURL data를 Suspense 뒤로 옮기기

flag를 활성화하면 Next.js는 development 중에 navigation할 때마다 각 App Shell을 검증합니다. App Shell은 route를 가리키는 모든 link가 공유하므로 하나의 URL에만 속하는 data를 담을 수 없습니다. <Suspense> boundary 밖에서 params나 searchParams를 읽으면 shell이 link의 URL에 묶이게 되고, URL data outside of Suspense insight가 나타나 해당 route를 알려 주고 해결 방법을 안내합니다:

With the flag enabled, Next.js validates each App Shell as you navigate in development. The App Shell is shared across every link to a route, so it can't contain data that belongs to a single URL. Reading params or searchParams outside a <Suspense> boundary ties the shell to the link's URL and surfaces the URL data outside of Suspense insight, naming the route and pointing at its fixes:

Wrap in or move into Suspense
<Suspense fallback={…}>
Allow blocking route
// page.tsx or layout.tsx
export const instant = false

이 insight는 build를 막지 않으므로, 이 작업은 flag를 켠 뒤 언제든 진행할 수 있습니다. next dev에서 모든 route를 load해 확인하세요.

The insight never blocks the build, so this pass can happen any time after the flag is on. Load every route in next dev to check for it.

해결 방법은 route에서 URL과 무관한 부분은 boundary 밖에 두고, params나 searchParams를 읽는 부분을 <Suspense>로 감싼 child로 옮기는 것입니다:

The fix is to keep the URL-independent parts of the route outside the boundary and move the params or searchParams read into a child wrapped in <Suspense>:

boundary 밖의 모든 것은 공유 App Shell에 남고, URL-specific 영역만 navigation마다 render됩니다. route를 다시 load하거나 navigation해서 insight가 사라졌는지, 그리고 페이지가 여전히 의미 있는 UI를 그리는지 확인하세요.

Everything outside the boundary stays in the shared App Shell, and only the URL-specific region renders per navigation. Load or navigate to the route again to confirm the insight is gone and the page still paints meaningful UI.

Prefetching URL dataURL data prefetch하기

URL data(params, searchParams)에 의존하는 콘텐츠는 공유 App Shell에 포함될 수 없으므로 navigation 후에 stream됩니다. Per-link prefetching은 prefetch={true}가 있는 link에 대해 클릭 전에 이를 resolve하지만, prefetch 가능한 link마다 server invocation이 한 번씩 발생하는 비용이 듭니다. prefetch 시점에 콘텐츠를 resolve할 수 있게 하려면 read 뒤에서 use cache로 cache하세요. searchParams를 읽는 search 페이지라면 다음과 같습니다:

Content that depends on URL data (params, searchParams) can't be included in the shared App Shell, so it streams in after navigation. Per-link prefetching resolves it ahead of the click for links with prefetch={true}, at the cost of a server invocation per prefetchable link. To make the content resolvable at prefetch time, cache it behind the read with use cache. For a search page that reads searchParams:

TSJSapp/search/page.tsx
// Before - the results stream in after navigation
import { Suspense } from 'react'

async function getResults(query: string) {
  const res = await fetch(`https://api.example.com/search?q=${query}`)
  return res.json()
}

async function Results({
  searchParams,
}: Pick<PageProps<'/search'>, 'searchParams'>) {
  const { q } = await searchParams
  return <ResultList results={await getResults(q)} />
}

export default function Page({ searchParams }: PageProps<'/search'>) {
  return (
    <Suspense fallback={<Skeleton />}>
      <Results searchParams={searchParams} />
    </Suspense>
  )
}
