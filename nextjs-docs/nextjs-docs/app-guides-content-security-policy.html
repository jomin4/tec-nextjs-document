How to set a Content Security Policy (CSP) for your Next.js applicationNext.js 애플리케이션에 Content Security Policy(CSP) 설정하기

Content Security Policy(CSP)는 cross-site scripting(XSS), clickjacking, 기타 code injection 공격 같은 다양한 보안 위협으로부터 Next.js 애플리케이션을 보호하는 데 중요합니다.

Content Security Policy (CSP) is important to guard your Next.js application against various security threats such as cross-site scripting (XSS), clickjacking, and other code injection attacks.

CSP를 사용하면 개발자는 content source, script, stylesheet, 이미지, font, object, media(audio, video), iframe 등에 대해 어떤 origin을 허용할지 지정할 수 있습니다.

By using CSP, developers can specify which origins are permissible for content sources, scripts, stylesheets, images, fonts, objects, media (audio, video), iframes, and more.

예시
  • Strict CSP

NoncesNonce

nonce는 한 번만 사용하도록 만든 고유한 무작위 문자열입니다. CSP와 함께 사용해, 엄격한 CSP directive를 우회하여 특정 inline script나 style만 선택적으로 실행되도록 허용합니다.

A nonce is a unique, random string of characters created for a one-time use. It is used in conjunction with CSP to selectively allow certain inline scripts or styles to execute, bypassing strict CSP directives.

Why use a nonce?왜 nonce를 사용할까요?

CSP는 공격을 막기 위해 inline script와 외부 script를 모두 차단할 수 있습니다. nonce를 사용하면 일치하는 nonce 값을 포함한 특정 script만 안전하게 실행되도록 허용할 수 있습니다.

CSP can block both inline and external scripts to prevent attacks. A nonce lets you safely allow specific scripts to run—only if they include the matching nonce value.

공격자가 page에 script를 로드하려면 nonce 값을 추측해야 합니다. 그래서 nonce는 예측할 수 없어야 하고 request마다 고유해야 합니다.

If an attacker wanted to load a script into your page, they'd need to guess the nonce value. That's why the nonce must be unpredictable and unique for every request.

Adding a nonce with ProxyProxy로 nonce 추가하기

Proxy를 사용하면 page가 render되기 전에 header를 추가하고 nonce를 생성할 수 있습니다.

Proxy enables you to add headers and generate nonces before the page renders.

page를 볼 때마다 새 nonce가 생성되어야 합니다. 즉, nonce를 추가하려면 반드시 dynamic rendering을 사용해야 합니다.

Every time a page is viewed, a fresh nonce should be generated. This means that you must use dynamic rendering to add nonces.

Good to know

development 환경에서는 'unsafe-eval'이 필요합니다. React가 browser에서 server-side error stack을 재구성하는 등 향상된 debugging 정보를 제공하기 위해 eval을 사용하기 때문입니다. production에서는 unsafe-eval이 필요하지 않습니다. React와 Next.js 모두 기본적으로 production에서는 eval을 사용하지 않습니다.

In development, 'unsafe-eval' is required because React uses eval to provide enhanced debugging information, such as reconstructing server-side error stacks in the browser. unsafe-eval is not required for production. Neither React nor Next.js use eval in production by default.

TSJSproxy.ts
import { NextRequest, NextResponse } from 'next/server'

export function proxy(request: NextRequest) {
  const nonce = Buffer.from(crypto.randomUUID()).toString('base64')
  const isDev = process.env.NODE_ENV === 'development'
  const cspHeader = `
    default-src 'self';
    script-src 'self' 'nonce-${nonce}' 'strict-dynamic'${isDev ? " 'unsafe-eval'" : ''};
    style-src 'self' 'nonce-${nonce}';
    img-src 'self' blob: data:;
    font-src 'self';
    object-src 'none';
    base-uri 'self';
    form-action 'self';
    frame-ancestors 'none';
    upgrade-insecure-requests;
`
  // Replace newline characters and spaces
  const contentSecurityPolicyHeaderValue = cspHeader
    .replace(/\s{2,}/g, ' ')
    .trim()

  const requestHeaders = new Headers(request.headers)
  requestHeaders.set('x-nonce', nonce)

  requestHeaders.set(
    'Content-Security-Policy',
    contentSecurityPolicyHeaderValue
  )

  const response = NextResponse.next({
    request: {
      headers: requestHeaders,
    },
  })
  response.headers.set(
    'Content-Security-Policy',
    contentSecurityPolicyHeaderValue
  )

  return response
}

By default, Proxy runs on all requests. You can filter Proxy to run on specific paths using a matcher.

(next/link에서 오는) prefetch와 CSP header가 필요 없는 static asset은 match 대상에서 제외하는 것을 권장합니다.

export const config = {
  matcher: [
    /*
     * Match all request paths except for the ones starting with:
     * - api (API routes)
     * - _next/static (static files)
     * - _next/image (image optimization files)
     * - favicon.ico (favicon file)
     */
    {
      source: '/((?!api|_next/static|_next/image|favicon.ico).*)',
      missing: [
        { type: 'header', key: 'next-router-prefetch' },
        { type: 'header', key: 'purpose', value: 'prefetch' },
      ],
    },
  ],
}

How nonces work in Next.jsNext.js에서 nonce가 동작하는 방식

nonce를 사용하려면 page가 dynamic하게 render되어야 합니다. Next.js는 request에 있는 CSP header를 기반으로 server-side rendering 중에 nonce를 적용하기 때문입니다. static page는 request나 response header가 존재하지 않는 build 시점에 생성되므로 nonce를 주입할 수 없습니다.

To use a nonce, your page must be dynamically rendered. This is because Next.js applies nonces during server-side rendering, based on the CSP header present in the request. Static pages are generated at build time, when no request or response headers exist—so no nonce can be injected.

dynamic하게 render되는 page에서 nonce 지원은 다음과 같이 동작합니다:

Here’s how nonce support works in a dynamically rendered page:

  1. Proxy가 nonce를 생성: proxy가 request마다 고유한 nonce를 만들어 Content-Security-Policy header에 추가하고, custom x-nonce header에도 설정합니다.
  2. Next.js가 nonce를 추출: rendering 중에 Next.js는 Content-Security-Policy header를 parse하고 'nonce-{value}' 패턴으로 nonce를 추출합니다.
  3. nonce가 자동으로 적용: Next.js는 다음 항목에 nonce를 붙입니다:
    • Framework script(React, Next.js runtime)
    • page별 JavaScript bundle
    • Next.js가 생성하는 inline style과 script
    • nonce prop을 사용하는 모든 <Script> component
  1. Proxy generates a nonce: Your proxy creates a unique nonce for the request, adds it to your Content-Security-Policy header, and also sets it in a custom x-nonce header.
  2. Next.js extracts the nonce: During rendering, Next.js parses the Content-Security-Policy header and extracts the nonce using the 'nonce-{value}' pattern.
  3. Nonce is applied automatically: Next.js attaches the nonce to:
    • Framework scripts (React, Next.js runtime)
    • Page-specific JavaScript bundles
    • Inline styles and scripts generated by Next.js
    • Any <Script> components using the nonce prop

이런 자동 동작 덕분에 각 tag에 직접 nonce를 추가할 필요가 없습니다.

Because of this automatic behavior, you don’t need to manually add a nonce to each tag.

Static vs Dynamic Rendering with CSPCSP와 Static vs Dynamic Rendering

nonce를 사용하면 Next.js 애플리케이션이 render되는 방식에 중요한 영향을 줍니다:

Using nonces has important implications for how your Next.js application renders:

Dynamic Rendering RequirementDynamic Rendering 요구 사항

CSP에서 nonce를 사용하면 모든 page가 dynamic하게 render되어야 합니다. 즉:

When you use nonces in your CSP, all pages must be dynamically rendered. This means:

  • page는 build에 성공하지만, dynamic rendering에 맞게 제대로 설정되지 않으면 runtime error가 발생할 수 있습니다
  • 각 request마다 새 nonce가 들어간 새 page가 생성됩니다
  • Static optimization과 Incremental Static Regeneration(ISR)이 비활성화됩니다
  • 추가 설정 없이는 CDN이 page를 cache할 수 없습니다
  • static shell script가 nonce에 접근할 수 없으므로 Partial Prerendering(PPR)은 nonce 기반 CSP와 호환되지 않습니다
  • Pages will build successfully but may encounter runtime errors if not properly configured for dynamic rendering
  • Each request generates a fresh page with a new nonce
  • Static optimization and Incremental Static Regeneration (ISR) are disabled
  • Pages cannot be cached by CDNs without additional configuration
  • Partial Prerendering (PPR) is incompatible with nonce-based CSP since static shell scripts won't have access to the nonce

Performance Implications성능에 미치는 영향

static rendering에서 dynamic rendering으로 바뀌면 성능에 영향을 줍니다:

The shift from static to dynamic rendering affects performance:

  • 초기 page 로딩이 느려짐: page가 매 request마다 생성되어야 합니다
  • server 부하 증가: 모든 request에 server-side rendering이 필요합니다
  • CDN caching 불가: dynamic page는 기본적으로 edge에서 cache할 수 없습니다
  • hosting 비용 증가: dynamic rendering에 더 많은 server 자원이 필요합니다
  • Slower initial page loads: Pages must be generated on each request
  • Increased server load: Every request requires server-side rendering
  • No CDN caching: Dynamic pages cannot be cached at the edge by default
  • Higher hosting costs: More server resources needed for dynamic rendering

When to use noncesnonce를 사용해야 할 때

다음과 같은 경우 nonce를 고려하세요:

Consider nonces when:

  • 'unsafe-inline'을 금지하는 엄격한 보안 요구 사항이 있을 때
  • 애플리케이션이 민감한 데이터를 다룰 때
  • 다른 script는 차단하면서 특정 inline script만 허용해야 할 때
  • compliance 요구 사항이 엄격한 CSP를 의무화할 때
  • You have strict security requirements that prohibit 'unsafe-inline'
  • Your application handles sensitive data
  • You need to allow specific inline scripts while blocking others
  • Compliance requirements mandate strict CSP

Subresource Integrity (Experimental)

nonce의 대안으로, Next.js는 Subresource Integrity(SRI)를 사용한 hash 기반 CSP를 experimental로 지원합니다. 이 방식을 사용하면 엄격한 CSP를 유지하면서도 static generation을 계속 사용할 수 있습니다.

As an alternative to nonces, Next.js offers experimental support for hash-based CSP using Subresource Integrity (SRI). This approach allows you to maintain static generation while still having a strict CSP.

Good to know

이 기능은 experimental이며 App Router 애플리케이션에서 사용할 수 있습니다.

This feature is experimental and available in App Router applications.

How SRI worksSRI의 동작 방식

SRI는 nonce를 사용하는 대신 build 시점에 JavaScript 파일의 cryptographic hash를 생성합니다. 이 hash는 script tag에 integrity attribute로 추가되어, 브라우저가 전송 중에 파일이 변경되지 않았는지 검증할 수 있게 합니다.

Instead of using nonces, SRI generates cryptographic hashes of your JavaScript files at build time. These hashes are added as integrity attributes to script tags, allowing browsers to verify that files haven't been modified during transit.

Enabling SRISRI 활성화하기

next.config.js에 experimental SRI configuration을 추가하세요:

Add the experimental SRI configuration to your next.config.js:

JSnext.config.js
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    sri: {
      algorithm: 'sha256', // or 'sha384' or 'sha512'
    },
  },
}

module.exports = nextConfig

Benefits of SRI over noncesnonce 대비 SRI의 장점

  • Static generation: page를 static하게 생성하고 cache할 수 있습니다
  • CDN 호환성: static page가 CDN caching과 함께 동작합니다
  • 더 나은 성능: request마다 server-side rendering이 필요하지 않습니다
  • Build 시점 보안: hash가 build 시점에 생성되어 무결성을 보장합니다
  • Static generation: Pages can be statically generated and cached
  • CDN compatibility: Static pages work with CDN caching
  • Better performance: No server-side rendering required for each request
  • Build-time security: Hashes are generated at build time, ensuring integrity

Limitations of SRISRI의 한계

  • Experimental: 기능이 변경되거나 제거될 수 있습니다
  • App Router 전용: Pages Router에서는 지원되지 않습니다
  • Build 시점 전용: dynamic하게 생성되는 script는 처리할 수 없습니다
  • Experimental: Feature may change or be removed
  • App Router only: Not supported in Pages Router
  • Build-time only: Cannot handle dynamically generated scripts

Production DeploymentProduction 배포

production에서 흔히 발생하는 문제:

Common issues in production:

  • nonce가 적용되지 않음: 필요한 모든 route에서 proxy가 실행되는지 확인하세요

  • Static assets blocked: Verify your CSP allows Next.js static assets
  • Third-party scripts: Add necessary domains to your CSP policy

Common CSP Violations흔한 CSP 위반

  1. Inline style: nonce를 지원하는 CSS-in-JS library를 사용하거나 style을 외부 파일로 옮기세요
  2. Dynamic import: script-src policy에서 dynamic import가 허용되는지 확인하세요
  3. WebAssembly: WebAssembly를 사용한다면 'wasm-unsafe-eval'을 추가하세요
  4. Service worker: service worker script에 맞는 policy를 추가하세요
  1. Inline styles: Use CSS-in-JS libraries that support nonces or move styles to external files
  2. Dynamic imports: Ensure dynamic imports are allowed in your script-src policy
  3. WebAssembly: Add 'wasm-unsafe-eval' if using WebAssembly
  4. Service workers: Add appropriate policies for service worker scripts
