Server Actions and MutationsServer Action과 Mutation

Server Action은 <form action>, <button formAction>, client-side transition 같은 React의 action 메커니즘을 통해 호출되는 React Server Function입니다.

A Server Action is a React Server Function invoked through React's action mechanisms, such as <form action>, <button formAction>, or a client-side transition.

'use server' directive를 추가해 만들고, form에서 호출하거나 startTransition으로 감싼 event handler 또는 useEffect에서 호출합니다. Server Function을 만들고 호출하는 기본 내용은 Mutating data와 Forms 가이드를 참고하세요.

You create one by adding the 'use server' directive, then invoke it from a form, or from an event handler or useEffect wrapped in startTransition. For the basics of creating and invoking Server Functions, see Mutating data and the Forms guide.

이 페이지는 Server Action 중 Next.js에 특화된 부분을 다룹니다: 흔히 mutation에 어떻게 대응되는지, response가 반환 데이터와 다시 render된 UI를 어떻게 함께 전달하는지, client가 action을 어떻게 dispatch하는지, framework가 강제하는 보안 경계, 그리고 사용할 수 있는 configuration입니다.

This page covers the parts of Server Actions that are specific to Next.js: how they commonly map to mutations, how the response carries both returned data and re-rendered UI, how the client dispatches them, the security boundary the framework enforces, and the configuration available.

Sequential dispatch on the clientClient의 순차 dispatch

Next.js는 client마다 Server Action을 한 번에 하나씩 dispatch합니다. 사용자가 action 세 개를 연달아 빠르게 실행하면, 두 번째는 첫 번째가 끝나기를 기다리고, 세 번째는 두 번째를 기다립니다. 이렇게 해서 다시 render된 server tree가 그것을 만들어 낸 action 결과와 일관되게 유지됩니다.

Next.js dispatches Server Actions one at a time per client. If a user triggers three actions in quick succession, the second waits for the first to finish, then the third waits for the second. This keeps the re-rendered server tree consistent with the action result that produced it.

그 결과: client에서 Server Action을 병렬화하기 위해 Promise.all에 의존하지 마세요. 병렬 작업이 필요하다면 하나의 Server Action 안에서 처리하거나, Server Component에서 병렬로 fetch하거나, mutation이 아닌 request라면 Route Handler를 사용하세요.

A consequence: do not rely on Promise.all to parallelize Server Actions from the client. If you need parallel work, do it inside a single Server Action, fetch in parallel from a Server Component, or use a Route Handler for non-mutation requests.

Good to know

이것은 Server Function 일반의 특성이 아니라 client dispatcher의 특성입니다. server는 Server Action을 queue에 넣지 않습니다. 각 action은 도착하는 대로 자체 request에서 실행되며, async 함수가 할 수 있는 일은 무엇이든 할 수 있습니다.

This is a property of the client dispatcher, not of Server Functions in general. The server does not queue Server Actions. Each one runs in its own request as it arrives, and can do anything an async function can do.

A single response carries data and UI하나의 response가 데이터와 UI를 함께 전달

Server Action이 즉시 revalidation을 일으키면, Next.js는 하나의 HTTP request 안에서 작업을 처리합니다: action을 실행한 다음, 현재 route를 server-side에서 다시 render합니다. 돌아오는 response는 같은 Flight stream 안에 두 가지를 모두 담고 있습니다:

When a Server Action triggers an immediate revalidation, Next.js does the work inside one HTTP request: it runs the action, then re-renders the current route server-side. The response that comes back contains both pieces in the same Flight stream:

  • action의 반환 값. client에서 useActionState나 await한 promise가 이 값을 받습니다.
  • 현재 route에 대해 새로 render된 RSC Payload. client는 이를 seeded navigation으로 commit합니다.
  • The action's return value, consumed by useActionState or the awaited promise on the client.
  • A newly rendered RSC Payload for the current route, which the client commits as a seeded navigation.

애플리케이션 코드는 현재 page의 업데이트된 UI를 보기 위해 후속 fetch를 할 필요가 없습니다.

Your application code does not need a follow-up fetch to see the updated UI for the current page.

action이 다음 중 하나라도 수행하면 같은 response에 re-render가 포함됩니다:

A re-render is included in the same response when the action does any of these:

  • updateTag나 revalidatePath를 호출해 cache된 데이터를 즉시 invalidate합니다.
  • refresh를 호출해 현재 route의 RSC Payload를 다시 fetch합니다.
  • cookies()를 통해 cookie를 변경합니다. cookie를 설정하거나 삭제하면 UI에 새 값이 반영되도록 현재 page가 자동으로 다시 render됩니다.
  • redirect를 호출합니다. response가 router를 navigate시키고 목적지의 RSC Payload를 stream합니다.
  • Calls updateTag or revalidatePath to immediately invalidate cached data.
  • Calls refresh to refetch the current route's RSC Payload.
  • Mutates cookies through cookies(). Setting or deleting a cookie automatically re-renders the current page so the UI reflects the new value.
  • Calls redirect. The response navigates the router and streams the destination's RSC Payload.
TSapp/posts/actions.ts
'use server'

import { revalidatePath } from 'next/cache'
import { auth } from '@/lib/auth'
import { db } from '@/lib/db'

export async function createPost(formData: FormData) {
  const session = await auth()
  if (!session?.user) throw new Error('Unauthorized')

  await db.post.create({
    data: {
      title: String(formData.get('title')),
      authorId: session.user.id,
    },
  })

  revalidatePath('/posts')
}

mutation, cache invalidation, page re-render가 모두 한 번의 roundtrip으로 완료됩니다. redirect는 control-flow exception을 throw하므로 그 뒤의 코드는 실행되지 않습니다. 목적지에서 최신 데이터가 필요하다면 revalidation 호출을 redirect 앞에 두세요.

The mutation, the cache invalidation, and the page re-render all complete in a single roundtrip. Because redirect throws a control-flow exception, any code after it does not run. Place revalidation calls before redirect if the destination needs the fresh data.

stale-while-revalidate profile을 사용하는 revalidateTag는 예외입니다: tag를 background refresh 대상으로 표시할 뿐, action response에 re-render를 포함하지 않습니다. page는 이후의 read에서 변경 사항을 반영합니다. 위의 어느 것도 하지 않는 action은 반환 값만 전달하며, 현재 route는 다시 render되지 않습니다.

revalidateTag with a stale-while-revalidate profile is the exception: it marks the tag for background refresh and does not include a re-render in the action response. The page reflects the change on a later read. An action that does none of the above carries only its return value, and the current route is not re-rendered.

Security보안

Server Action은 그것을 호출한 page에 대한 POST request로 실행됩니다. build 시점에 'use server' directive는 compiler에게 client bundle 속 함수 구현을 server로 다시 POST하는 reference(action ID와 dispatcher)로 바꾸라고 알려 줍니다. 구현은 server에 남아 있지만, 같은 POST를 보낼 수 있는 사람이라면 누구나 그 route에 도달할 수 있습니다. 모든 action을 신뢰할 수 없는 진입점으로 취급하세요.

A Server Action runs as a POST request against the page that invokes it. At build time, the 'use server' directive tells the compiler to swap the function's implementation in client bundles for a reference (an action ID plus a dispatcher) that POSTs back to the server. The implementation stays on the server, but the route is reachable to anyone who can send the same POST. Treat every action as an untrusted entry point.

Next.js는 몇 가지 framework 수준의 보호 장치를 강제합니다:

Next.js enforces a few framework-level protections:

  • CSRF 검사. request의 Origin을 Host(또는 X-Forwarded-Host)와 비교합니다. 일치하지 않으면 거부됩니다. proxy나 CDN domain에는 serverActions.allowedOrigins를 설정하세요.
  • Body 크기 제한. action request는 기본적으로 1MB로 제한됩니다. 더 큰 payload를 받아야 한다면 serverActions.bodySizeLimit를 설정하세요.
  • 암호화된 action ID와 dead code elimination. action reference는 build 시점에 암호화되고, 사용되지 않는 Server Function은 client bundle에서 제거되어 public endpoint를 갖지 않습니다. Built-in Server Actions security features를 참고하세요.
  • Closure 변수 암호화. inline action이 capture한 변수는 client로 보내기 전에 암호화됩니다. multi-instance나 self-hosted deployment에서는 NEXT_SERVER_ACTIONS_ENCRYPTION_KEY를 instance 사이에서 공유되는 안정적인 key로 설정하세요. Closures and encryption을 참고하세요.
  • CSRF check. The request's Origin is compared to the Host (or X-Forwarded-Host). Mismatches are rejected. Configure serverActions.allowedOrigins for proxy or CDN domains.
  • Body size limit. Action requests are capped at 1MB by default. Configure serverActions.bodySizeLimit when accepting larger payloads.
  • Encrypted action IDs and dead code elimination. Action references are encrypted at build time, and unused Server Functions are stripped from client bundles so they have no public endpoint. See Built-in Server Actions security features.
  • Closure variable encryption. Variables captured by an inline action are encrypted before being sent to the client. For multi-instance and self-hosted deployments, set NEXT_SERVER_ACTIONS_ENCRYPTION_KEY to a stable key shared across instances. See Closures and encryption.

framework의 보호 장치가 애플리케이션 수준의 검사를 대신하지는 않습니다. 모든 action 안에서:

Framework protections are not a substitute for application-level checks. Inside every action:

  • 인증과 인가를 수행하세요. render 시점의 gating(인증된 page에서만 form을 render하는 것)은 보안 경계가 아닙니다. request는 UI를 거치지 않고도 보낼 수 있기 때문입니다.
  • 입력을 검증하세요. FormData, query parameter, header를 신뢰할 수 없는 것으로 취급하세요.
  • 반환 값을 제한하세요. action의 반환 값은 serialize되어 client로 전달됩니다. 원시 database record가 아니라 UI가 render하는 형태로 가공하세요.
  • Authenticate and authorize. Render-time gating (only rendering a form on an authenticated page) is not a security boundary, because requests can be sent without going through the UI.
  • Validate inputs. Treat FormData, query parameters, and headers as untrusted.
  • Constrain return values. Action returns are serialized to the client. Shape them to what the UI renders, not raw database records.

Data Access Layer, return-value tainting, rate limiting을 포함한 end-to-end 패턴은 Data Security 가이드를 참고하세요.

For end-to-end patterns including a Data Access Layer, return-value tainting, and rate limiting, see the Data Security guide.

삭제처럼 파괴적인 작업에는 강화된 session 검사나 재인증 같은 더 강력한 처리와, 그런 검사를 통과하지 못했을 때 확실하게 실패를 드러내는 처리가 필요할 수 있습니다.

Destructive operations like deletes may warrant stronger handling, such as elevated session checks or re-authentication, and a loud failure when those checks miss.

TSapp/posts/actions.ts
'use server'

import { auth } from '@/lib/auth'

export async function deletePost(postId: string) {
  const session = await auth()
  if (!session?.user) throw new Error('Unauthorized')
  if (!(await canDelete(session.user, postId))) throw new Error('Forbidden')

  await db.post.delete({ where: { id: postId } })
}

experimental authInterrupts flag를 활성화했다면, 대신 next/navigation의 unauthorized()와 forbidden()을 throw할 수 있습니다. 그러면 Next.js가 해당하는 unauthorized.tsx / forbidden.tsx UI segment를 자동으로 render합니다.

If you've enabled the experimental authInterrupts flag, you can throw unauthorized() and forbidden() from next/navigation instead, so Next.js renders the corresponding unauthorized.tsx / forbidden.tsx UI segment automatically.

예를 들어, client가 server에 어떤 item에 대해 작업할지 알려 주는 것은 정당하지만, 그 row의 내용이나 소유권을 제공해서는 안 됩니다. reference(보통 ID)와 사용자의 변경 사항만 보내고, 나머지는 session을 사용해 신뢰할 수 있는 source에서 다시 읽으세요. schema validation(zod 등)은 입력의 _형태_만 검사합니다. 형식이 올바른 Item object라도 호출자가 소유하지 않은 row를 가리킬 수 있습니다.

For example, a client legitimately tells the server which item to act on, but it should not supply the row's contents or ownership. Send a reference (typically an ID) plus the user's change, and re-read the rest from a trusted source using the session. Schema validation (zod or similar) only checks the shape of the input. A well-formed Item object can still refer to a row the caller does not own.

TSapp/items/actions.ts
'use server'

import { auth } from '@/lib/auth'
import { db } from '@/lib/db'

// Unsafe: no auth, no ownership check. The whole item, including its id, comes
// from the client, so anyone who can POST here can mark any item complete.
export async function completeItemUnsafe(item: Item) {
  await db.item.update({ where: { id: item.id }, data: { completed: true } })
}

// Safe: take only the change, derive identity from the session, look up by ownership.
export async function completeItem(itemId: string) {
  const session = await auth()
  if (!session?.user) return

  const item = await db.item.findFirst({
    where: { id: itemId, ownerId: session.user.id },
  })
  if (!item) return

  await db.item.update({ where: { id: item.id }, data: { completed: true } })
}

Choosing a cache updateCache 업데이트 방식 선택

데이터를 변경한 뒤에는 on-demand revalidation이 server cache, client router, 또는 둘 다를 업데이트합니다. 무엇을 바꿔야 하는지에 따라 선택하세요:

After mutating data, on-demand revalidation updates the server cache, the client router, or both. Choose based on what needs to change:

  • updateTag: tag를 즉시 만료시킵니다. 다음 read(action의 response와 함께 전달되는 route re-render 포함)는 최신 데이터를 기다립니다. 사용자가 자신의 변경 사항을 즉시 볼 수 있도록 action에 read-your-own-writes가 필요할 때 사용하세요. Server Action 전용입니다.
  • revalidateTag: cache-life profile로 tag를 stale-while-revalidate 방식으로 refresh합니다. 이후 read는 background에서 새 fetch가 진행되는 동안 stale 값을 받으므로, action 자체의 re-render는 새 데이터를 기다리지 않습니다.
  • revalidatePath: URL 경로로 invalidate합니다. 영향을 받는 route가 하나뿐이고 tagging이 과할 때 사용하세요.
  • refresh: cache된 데이터를 invalidate하지 않고 현재 route의 RSC Payload를 다시 fetch합니다. 화면이 action이 방금 변경한, cache 바깥의 state에 의존할 때 사용하세요.
  • updateTag: immediate expiration of a tag. The next read (including the route re-render that ships with the action's response) waits for fresh data. Use when the action needs read-your-own-writes so the user immediately sees their change. Server Actions only.
  • revalidateTag: stale-while-revalidate refresh of a tag with a cache-life profile. Subsequent reads get the stale value while a fresh fetch happens in the background, so the action's own re-render does not wait for the new data.
  • revalidatePath: invalidate by URL path. Use when one route is affected and tagging is overkill.
  • refresh: refetch the current route's RSC Payload without invalidating cached data. Use when the view depends on state outside the cache that the action just changed.

updateTag, revalidatePath, refresh가 실행되면 Next.js는 현재 route를 server-side에서 다시 render하고 새로 render된 RSC Payload를 action의 response에 포함하므로, page가 같은 roundtrip 안에서 변경 사항을 반영합니다. stale-while-revalidate profile을 사용하는 revalidateTag는 의도적으로 이 즉시 re-render를 건너뜁니다.

When updateTag, revalidatePath, or refresh runs, Next.js re-renders the current route server-side and includes a newly rendered RSC Payload in the action's response, so the page reflects the change in the same roundtrip. revalidateTag with a stale-while-revalidate profile intentionally skips that immediate re-render.

redirect와 달리 이들은 모두 throw하지 않으므로, action에서 호출한 뒤에도 호출자에게 값을 반환할 수 있습니다. 기반 모델은 How revalidation works를 참고하세요.

Unlike redirect, none of these throw, so an action can call them and still return a value to the caller. See How revalidation works for the underlying model.

Configuration

next.config.js의 serverActions option은 framework 수준의 동작을 제어합니다:

The serverActions option in next.config.js controls framework-level behavior:

JSnext.config.js
/** @type {import('next').NextConfig} */
module.exports = {
  experimental: {
    serverActions: {
      allowedOrigins: ['my-proxy.com', '*.my-proxy.com'],
      bodySizeLimit: '2mb',
    },
  },
}

closure encryption key는 deployment environment에 NEXT_SERVER_ACTIONS_ENCRYPTION_KEY를 설정하세요. deployment별 가이드는 Self-hosting: Server Functions encryption key를 참고하세요.

For the closure encryption key, set NEXT_SERVER_ACTIONS_ENCRYPTION_KEY in the deployment environment. See Self-hosting: Server Functions encryption key for deployment-specific guidance.

Deployment considerationsDeployment 시 고려 사항

각 Server Action은 build artifact의 일부인 action ID로 식별됩니다. 새 deployment는 보통 새 ID를 생성하므로(source가 바뀌지 않아도 Next.js는 최대 14일마다 ID를 교체합니다), 이전 build를 아직 실행 중인 client가 더 이상 존재하지 않는 action ID를 호출할 수 있습니다. 이 오류는 "Failed to find Server Action"으로 나타납니다.

Each Server Action is identified by the action ID that is part of its build artifacts. New deployments typically generate new IDs (Next.js rotates them at most every 14 days, even when the source is unchanged), so a client still running the previous build may invoke an action ID that no longer exists. The error surfaces as "Failed to find Server Action".

영향을 최소화하려면:

To minimize disruption:

  • 활성 사용자가 mutation 도중일 가능성이 높다면 급작스러운 전환보다 rolling deployment를 선호하세요.
  • action reference가 어디서나 복호화될 수 있도록 NEXT_SERVER_ACTIONS_ENCRYPTION_KEY를 instance 사이에서 안정적으로 유지하세요.
  • 오류를 hard failure가 아니라 UI의 retry 경로로 노출해서, refresh로 사용자가 복구할 수 있게 하세요.
  • Prefer rolling deployments over abrupt cutovers when active users are likely to be mid-mutation.
  • Keep NEXT_SERVER_ACTIONS_ENCRYPTION_KEY stable across instances so action references remain decryptable everywhere.
  • Surface the error as a retry path in the UI rather than a hard failure, so a refresh recovers the user.
