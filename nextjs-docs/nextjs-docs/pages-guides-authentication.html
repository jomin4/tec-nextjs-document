How to implement authentication in Next.jsNext.js에서 인증 구현하기

authentication을 이해하는 것은 애플리케이션의 데이터를 보호하는 데 매우 중요합니다. 이 페이지에서는 auth를 구현할 때 어떤 React와 Next.js 기능을 사용해야 하는지 안내합니다.

Understanding authentication is crucial for protecting your application's data. This page will guide you through what React and Next.js features to use to implement auth.

시작하기 전에 이 과정을 세 가지 개념으로 나눠 보면 도움이 됩니다:

Before starting, it helps to break down the process into three concepts:

  1. Authentication: 사용자가 자신이 주장하는 그 사람이 맞는지 확인합니다. 사용자는 username과 password처럼 자신이 가진 무언가로 신원을 증명해야 합니다.
  2. Session Management: 여러 request에 걸쳐 사용자의 auth state를 추적합니다.
  3. Authorization: 사용자가 어떤 route와 데이터에 접근할 수 있는지 결정합니다.
  1. Authentication: Verifies if the user is who they say they are. It requires the user to prove their identity with something they have, such as a username and password.
  2. Session Management: Tracks the user's auth state across requests.
  3. Authorization: Decides what routes and data the user can access.

다음 다이어그램은 React와 Next.js 기능을 사용한 authentication 흐름을 보여 줍니다:

This diagram shows the authentication flow using React and Next.js features:

이 페이지의 예제는 학습 목적으로 기본적인 username/password auth를 단계별로 살펴봅니다. 직접 custom auth solution을 구현할 수도 있지만, 보안을 높이고 단순하게 만들기 위해 authentication library 사용을 권장합니다. 이런 library는 authentication, session management, authorization을 위한 기본 solution뿐 아니라 social login, multi-factor authentication, role-based access control 같은 추가 기능도 제공합니다. 목록은 Auth Libraries 섹션에서 확인할 수 있습니다.

The examples on this page walk through basic username and password auth for educational purposes. While you can implement a custom auth solution, for increased security and simplicity, we recommend using an authentication library. These offer built-in solutions for authentication, session management, and authorization, as well as additional features such as social logins, multi-factor authentication, and role-based access control. You can find a list in the Auth Libraries section.

Authentication

회원가입 및/또는 로그인 form을 구현하는 단계는 다음과 같습니다:

Here are the steps to implement a sign-up and/or login form:

  1. 사용자가 form을 통해 credential을 제출합니다.
  2. form이 API route에서 처리되는 request를 보냅니다.
  3. 검증에 성공하면 과정이 완료되어 사용자가 성공적으로 인증되었음을 나타냅니다.
  4. 검증에 실패하면 error message가 표시됩니다.
  1. The user submits their credentials through a form.
  2. The form sends a request that is handled by an API route.
  3. Upon successful verification, the process is completed, indicating the user's successful authentication.
  4. If verification is unsuccessful, an error message is shown.

사용자가 credential을 입력할 수 있는 로그인 form을 생각해 봅시다:

Consider a login form where users can input their credentials:

TSJSpages/login.tsx
import type { SubmitEvent } from 'react'
import { useRouter } from 'next/router'

export default function LoginPage() {
  const router = useRouter()

  async function handleSubmit(event: SubmitEvent<HTMLFormElement>) {
    event.preventDefault()

    const formData = new FormData(event.currentTarget)
    const email = formData.get('email')
    const password = formData.get('password')

    const response = await fetch('/api/auth/login', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ email, password }),
    })

    if (response.ok) {
      router.push('/profile')
    } else {
      // Handle errors
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <input type="email" name="email" placeholder="Email" required />
      <input type="password" name="password" placeholder="Password" required />
      <button type="submit">Login</button>
    </form>
  )
}

그런 다음 API route에서 Authentication Provider의 API를 호출해 authentication을 처리할 수 있습니다:

You can then call your Authentication Provider's API in the API route to handle authentication:

TSJSpages/api/auth/login.ts
import type { NextApiRequest, NextApiResponse } from 'next'
import { signIn } from '@/auth'

export default async function handler(
  req: NextApiRequest,
  res: NextApiResponse
) {
  try {
    const { email, password } = req.body
    await signIn('credentials', { email, password })

    res.status(200).json({ success: true })
  } catch (error) {
    if (error.type === 'CredentialsSignin') {
      res.status(401).json({ error: 'Invalid credentials.' })
    } else {
      res.status(500).json({ error: 'Something went wrong.' })
    }
  }
}

Session Management세션 관리

session management는 사용자의 인증된 state가 여러 request에 걸쳐 유지되도록 보장합니다. 여기에는 session 또는 token의 생성, 저장, 갱신, 삭제가 포함됩니다.

Session management ensures that the user's authenticated state is preserved across requests. It involves creating, storing, refreshing, and deleting sessions or tokens.

session에는 두 가지 유형이 있습니다:

There are two types of sessions:

  1. Stateless: session 데이터(또는 token)가 브라우저의 cookie에 저장됩니다. cookie는 request마다 함께 전송되어 server에서 session을 검증할 수 있습니다. 이 방법은 더 단순하지만, 올바르게 구현하지 않으면 보안이 약해질 수 있습니다.
  2. Database: session 데이터가 database에 저장되고, 사용자의 브라우저는 암호화된 session ID만 받습니다. 이 방법은 더 안전하지만, 복잡할 수 있고 server 리소스를 더 많이 사용합니다.
  1. Stateless: Session data (or a token) is stored in the browser's cookies. The cookie is sent with each request, allowing the session to be verified on the server. This method is simpler, but can be less secure if not implemented correctly.
  2. Database: Session data is stored in a database, with the user's browser only receiving the encrypted session ID. This method is more secure, but can be complex and use more server resources.
Good to know

두 방법 중 하나를 쓰거나 둘 다 쓸 수 있지만, iron-session이나 Jose 같은 session management library 사용을 권장합니다.

While you can use either method, or both, we recommend using a session management library such as iron-session or Jose.

Setting and deleting cookiescookie 설정과 삭제

API Routes를 사용해 server에서 session을 cookie로 설정할 수 있습니다:

You can use API Routes to set the session as a cookie on the server:

TSJSpages/api/login.ts
import { serialize } from 'cookie'
import type { NextApiRequest, NextApiResponse } from 'next'
import { encrypt } from '@/app/lib/session'

export default function handler(req: NextApiRequest, res: NextApiResponse) {
  const sessionData = req.body
  const encryptedSessionData = encrypt(sessionData)

  const cookie = serialize('session', encryptedSessionData, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    maxAge: 60 * 60 * 24 * 7, // One week
    path: '/',
  })
  res.setHeader('Set-Cookie', cookie)
  res.status(200).json({ message: 'Successfully set cookie!' })
}

Database Sessions

database session을 만들고 관리하려면 다음 단계를 따라야 합니다:

To create and manage database sessions, you'll need to follow these steps:

  1. database에 session과 데이터를 저장할 table을 만듭니다(또는 Auth Library가 이를 처리하는지 확인합니다).
  2. session을 insert, update, delete하는 기능을 구현합니다
  3. session ID를 사용자의 브라우저에 저장하기 전에 암호화하고, database와 cookie가 동기화된 상태를 유지하도록 합니다(선택 사항이지만 Proxy에서 optimistic auth check를 하려면 권장됩니다).
  1. Create a table in your database to store session and data (or check if your Auth Library handles this).
  2. Implement functionality to insert, update, and delete sessions
  3. Encrypt the session ID before storing it in the user's browser, and ensure the database and cookie stay in sync (this is optional, but recommended for optimistic auth checks in Proxy).

Authorization

사용자가 인증되고 session이 생성되면, authorization을 구현해 사용자가 애플리케이션 안에서 무엇에 접근하고 무엇을 할 수 있는지 제어할 수 있습니다.

Once a user is authenticated and a session is created, you can implement authorization to control what the user can access and do within your application.

authorization check에는 크게 두 가지 유형이 있습니다:

There are two main types of authorization checks:

  1. Optimistic: cookie에 저장된 session 데이터를 사용해 사용자가 route에 접근하거나 action을 수행할 권한이 있는지 확인합니다. 이런 check는 UI element를 보여 주거나 숨기는 것, 또는 권한이나 role에 따라 사용자를 redirect하는 것 같은 빠른 작업에 유용합니다.
  2. Secure: database에 저장된 session 데이터를 사용해 사용자가 route에 접근하거나 action을 수행할 권한이 있는지 확인합니다. 이런 check는 더 안전하며, 민감한 데이터나 action에 접근해야 하는 작업에 사용합니다.
  1. Optimistic: Checks if the user is authorized to access a route or perform an action using the session data stored in the cookie. These checks are useful for quick operations, such as showing/hiding UI elements or redirecting users based on permissions or roles.
  2. Secure: Checks if the user is authorized to access a route or perform an action using the session data stored in the database. These checks are more secure and are used for operations that require access to sensitive data or actions.

두 경우 모두 다음을 권장합니다:

For both cases, we recommend:

  • authorization 로직을 한곳에 모으기 위해 Data Access Layer 만들기
  • 필요한 데이터만 반환하도록 Data Transfer Objects (DTO) 사용하기
  • 선택적으로 Proxy를 사용해 optimistic check 수행하기.
  • Creating a Data Access Layer to centralize your authorization logic
  • Using Data Transfer Objects (DTO) to only return the necessary data
  • Optionally use Proxy to perform optimistic checks.

Optimistic checks with Proxy (Optional)Proxy로 optimistic check 하기 (선택)

Proxy를 사용해 권한에 따라 사용자를 redirect하고 싶은 경우가 있습니다:

There are some cases where you may want to use Proxy and redirect users based on permissions:

  • optimistic check를 수행하려는 경우. Proxy는 모든 route에서 실행되므로, redirect 로직을 한곳에 모으고 권한이 없는 사용자를 미리 걸러 내기에 좋은 방법입니다.
  • 사용자 간에 데이터를 공유하는 static route(예: paywall 뒤의 콘텐츠)를 보호하려는 경우.
  • To perform optimistic checks. Since Proxy runs on every route, it's a good way to centralize redirect logic and pre-filter unauthorized users.
  • To protect static routes that share data between users (e.g. content behind a paywall).

하지만 Proxy는 prefetch된 route를 포함한 모든 route에서 실행되므로, 성능 문제를 막으려면 cookie에서 session만 읽고(optimistic check) database check는 피하는 것이 중요합니다.

However, since Proxy runs on every route, including prefetched routes, it's important to only read the session from the cookie (optimistic checks), and avoid database checks to prevent performance issues.

예를 들면 다음과 같습니다:

For example:

TSJSproxy.ts
import { NextRequest, NextResponse } from 'next/server'
import { decrypt } from '@/app/lib/session'
import { cookies } from 'next/headers'

// 1. Specify protected and public routes
const protectedRoutes = ['/dashboard']
const publicRoutes = ['/login', '/signup', '/']

export default async function proxy(req: NextRequest) {
  // 2. Check if the current route is protected or public
  const path = req.nextUrl.pathname
  const isProtectedRoute = protectedRoutes.includes(path)
  const isPublicRoute = publicRoutes.includes(path)

  // 3. Decrypt the session from the cookie
  const cookie = (await cookies()).get('session')?.value
  const session = await decrypt(cookie)

  // 4. Redirect to /login if the user is not authenticated
  if (isProtectedRoute && !session?.userId) {
    return NextResponse.redirect(new URL('/login', req.nextUrl))
  }

  // 5. Redirect to /dashboard if the user is authenticated
  if (
    isPublicRoute &&
    session?.userId &&
    !req.nextUrl.pathname.startsWith('/dashboard')
  ) {
    return NextResponse.redirect(new URL('/dashboard', req.nextUrl))
  }

  return NextResponse.next()
}

// Routes Proxy should not run on
export const config = {
  matcher: ['/((?!api|_next/static|_next/image|.*\\.png$).*)'],
}

Proxy는 초기 check에 유용할 수 있지만, 데이터를 보호하는 유일한 방어선이 되어서는 안 됩니다. 대부분의 security check는 데이터 source에 최대한 가까운 곳에서 수행해야 합니다. 자세한 내용은 Data Access Layer를 참고하세요.

While Proxy can be useful for initial checks, it should not be your only line of defense in protecting your data. The majority of security checks should be performed as close as possible to your data source, see Data Access Layer for more information.

Tips
  • Proxy에서는 req.cookies.get('session')?.value로도 cookie를 읽을 수 있습니다.
  • Proxy는 Node.js runtime을 사용하므로, 사용하는 Auth library와 session management library가 호환되는지 확인하세요.
  • Proxy의 matcher property를 사용해 Proxy가 실행될 route를 지정할 수 있습니다. 다만 auth의 경우에는 Proxy가 모든 route에서 실행되도록 하는 것을 권장합니다.
  • In Proxy, you can also read cookies using req.cookies.get('session')?.value.
  • Proxy uses the Node.js runtime, check if your Auth library and session management library are compatible.
  • You can use the matcher property in the Proxy to specify which routes Proxy should run on. Although, for auth, it's recommended Proxy runs on all routes.

Protecting API RoutesAPI Route 보호하기

Next.js의 API Route는 server-side 로직과 데이터 관리를 처리하는 데 필수적입니다. 권한이 있는 사용자만 특정 기능에 접근할 수 있도록 이런 route를 보호하는 것이 매우 중요합니다. 일반적으로 사용자의 authentication 상태와 role-based permission을 검증하는 작업이 포함됩니다.

API Routes in Next.js are essential for handling server-side logic and data management. It's crucial to secure these routes to ensure that only authorized users can access specific functionalities. This typically involves verifying the user's authentication status and their role-based permissions.

다음은 API Route를 보호하는 예제입니다:

Here's an example of securing an API Route:

TSJSpages/api/route.ts
import { NextApiRequest, NextApiResponse } from 'next'

export default async function handler(
  req: NextApiRequest,
  res: NextApiResponse
) {
  const session = await getSession(req)

  // Check if the user is authenticated
  if (!session) {
    res.status(401).json({
      error: 'User is not authenticated',
    })
    return
  }

  // Check if the user has the 'admin' role
  if (session.user.role !== 'admin') {
    res.status(401).json({
      error: 'Unauthorized access: User does not have admin privileges.',
    })
    return
  }

  // Proceed with the route for authorized users
  // ... implementation of the API Route
}
export default async function handler(req, res) {
  const session = await getSession(req)

  // Check if the user is authenticated
  if (!session) {
    res.status(401).json({
      error: 'User is not authenticated',
    })
    return
  }

  // Check if the user has the 'admin' role
  if (session.user.role !== 'admin') {
    res.status(401).json({
      error: 'Unauthorized access: User does not have admin privileges.',
    })
    return
  }

  // Proceed with the route for authorized users
  // ... implementation of the API Route
}

이 예제는 authentication과 authorization을 위한 2단계 security check가 있는 API Route를 보여 줍니다. 먼저 활성 session이 있는지 확인한 다음, 로그인한 사용자가 'admin'인지 검증합니다. 이 방식은 인증되고 권한이 있는 사용자로만 접근을 제한해 안전한 접근을 보장하고, request 처리에 대한 견고한 보안을 유지합니다.

This example demonstrates an API Route with a two-tier security check for authentication and authorization. It first checks for an active session, and then verifies if the logged-in user is an 'admin'. This approach ensures secure access, limited to authenticated and authorized users, maintaining robust security for request processing.
