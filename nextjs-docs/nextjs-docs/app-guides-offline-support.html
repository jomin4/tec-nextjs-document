Handling connectivity dropsexperimental연결 끊김 처리하기

soft navigation, data fetch, mutation 도중에 network 장애가 발생하면 client에서 error가 던져집니다. 명시적으로 처리하지 않으면 UI가 깨지거나, 사용자에게 다시 시도하라고 요청하는 fallback UI를 직접 만들어야 합니다.

Network failures during a soft navigation, a data fetch, or a mutation throw errors in the client. Without explicit handling, the UI either breaks or you have to build a fallback UI that asks the user to retry.

experimental.useOffline을 활성화하면, network가 끊겼을 때 실패한 navigation, RSC data fetch, prefetch, Server Action이 더 이상 error를 던지지 않습니다. Next.js는 이를 pending 상태로 유지하다가 연결이 돌아오면 다시 시도합니다.

With experimental.useOffline enabled, a failed navigation, RSC data fetch, prefetch, or Server Action no longer throws when the network is down. Next.js keeps it pending and retries it once the connection returns.

request가 pending인 동안 UI는 loading state(Suspense fallback, 또는 Server Action의 경우 pending transition)에 머무르는데, 이는 server가 느릴 때와 똑같아 보입니다. 앱이 offline일 때 사용자에게 피드백을 주려면 useOffline hook을 사용하세요.

While the request is pending, the UI sits in its loading state (a Suspense fallback, or a pending transition for a Server Action), which looks the same as a slow server. Use the useOffline hook to give users feedback when the app is offline.

Client Component 안에서 fetch()로 직접 보내거나 React Query, SWR 같은 client-side data library를 통해 보내는 request는 그 library 자체의 retry policy를 따릅니다. framework의 감지 및 polling 동작은 How retry works를 참고하세요.

Requests you issue directly with fetch() inside a Client Component, or through a client-side data library like React Query or SWR, stay under that library's own retry policy. See How retry works for the framework's detection and polling behavior.

Enable offline detection and see the default behaviorOffline 감지 활성화와 기본 동작 확인

experimental.useOffline을 켜세요. 이 가이드에서는 Cache Components와 Partial Prefetching도 활성화합니다. Cache Components를 사용하면 Suspense boundary를 cache되지 않은 데이터에 최대한 가깝게 두고, 그 주변에 App Shell을 render할 수 있습니다. Partial Prefetching은 그 App Shell을 <Link>가 prefetch하는 단위로 만들어, navigation이 offline에서 일어나도 바로 render할 수 있도록 준비해 둡니다.

Turn on experimental.useOffline. This guide also enables Cache Components and Partial Prefetching. Cache Components lets you place the Suspense boundary as close as possible to the uncached data, with the App Shell rendered around it. Partial Prefetching makes that App Shell the unit a <Link> prefetches, so it is ready to render when a navigation happens offline.

Cache Components 없이도 route 수준의 loading.tsx를 사용하면 segment 수준에서 같은 offline 동작을 얻을 수 있습니다. 아래 Without Cache Components를 참고하세요.

Without Cache Components, a route-level loading.tsx gives you the same offline behavior at the segment level. See Without Cache Components below.

import type { NextConfig } from 'next'

  partialPrefetching: true,
  experimental: {

home page를 로드하세요. <Link>가 viewport에 있으면 dashboard의 static shell이 prefetch됩니다. offline으로 전환한 다음(아래 Testing 참고) /dashboard로 클릭해 들어가세요.

Load the home page. With the <Link> in the viewport, the dashboard's static shell is prefetched. Go offline (see Testing below) and click through to /dashboard.

제목과 container는 static shell에서 render됩니다. cache되지 않은 getLiveMetrics() 호출이 완료될 수 없으므로 Loading... fallback이 화면에 계속 남아 있습니다. 사용자는 server가 느릴 때 보게 되는 것과 같은 spinner를 보게 됩니다.

The title and container render from the static shell. The Loading... fallback stays on screen indefinitely because the uncached getLiveMetrics() call cannot complete. The user sees the same spinner they would see for a slow server.

다시 Online으로 전환하세요. metrics 표가 자동으로 stream되어 들어옵니다. Next.js가 스스로 request를 다시 시도했으며, client 코드는 전혀 관여하지 않았습니다.

Toggle back to Online. The metrics table streams in automatically. Next.js retried the request on its own, no client code involved.

Note

이 기능은 prefetch된 route로의 soft navigation과 현재 페이지에서의 Server Action 호출에만 적용됩니다. offline 상태에서 페이지 전체를 새로 고치면 브라우저가 HTML을 받기 위해 network가 필요하므로 여전히 실패합니다. 완전한 offline 로드를 하려면 service worker가 필요합니다(Progressive Web Apps 가이드 참고).

This feature only applies to soft navigations into prefetched routes and Server Action calls from the current page. A full page reload while offline still fails because the browser needs the network to deliver the HTML; full offline loads would need a service worker (see the Progressive Web Apps guide).

다음으로, 일반적인 fallback UI를 연결 상태를 읽는 fallback으로 바꿔 보겠습니다.

Next, replace the generic fallback UI with one that reads the connectivity state.

Report connectivity inside the Suspense fallbackSuspense fallback 안에서 연결 상태 알리기

useOffline은 브라우저가 offline 이벤트를 발생시킬 때, 또는 navigation, prefetch, Server Action fetch가 실패할 때 true를 반환합니다. background 연결 확인이 성공하면 다시 false로 바뀝니다. 이는 navigator.onLine보다 신뢰할 수 있습니다. navigator.onLine은 OS의 network interface만 반영하므로, WiFi에는 연결되어 있지만 upstream internet이 없는 기기에서도 여전히 true를 보고합니다.

useOffline returns true when the browser fires an offline event or when a navigation, prefetch, or Server Action fetch fails. It flips back to false when a background connectivity check succeeds. This is more reliable than navigator.onLine, which only reflects the OS network interface and still reports true for a device on WiFi with no upstream internet.

hook 값에 따라 메시지를 고르는 client component를 만드세요.

Create a client component that picks its message based on the hook.

TSJSapp/dashboard/connectivity-fallback.tsx
'use client'

import { useOffline } from 'next/offline'

export function ConnectivityFallback() {
  const isOffline = useOffline()

  return (
    <p>
      {isOffline
        ? 'Waiting for connection to load this section...'
        : 'Loading...'}
    </p>
  )
}
'use client'

Note

useOffline은 server-side rendering과 초기 hydration 중에는 false를 반환합니다. 처음으로 정확한 값은 앱이 mount된 후 브라우저가 보고하는 값입니다.

useOffline returns false during server-side rendering and initial hydration. The first accurate value is whatever the browser reports after the app mounts.

fallback은 이 페이지에서만, 그리고 Suspense boundary가 기다리는 동안에만 표시됩니다. 이 앱에서는 연결 상태가 어디서나 보이도록 root layout에 banner를 추가합니다.

The fallback only shows on this page, and only while its Suspense boundary is waiting. In this app, we add a banner in the root layout so connectivity state is visible everywhere.

banner는 offline인 동안 모든 route에 표시되고, 연결이 돌아오면 숨겨집니다.

The banner shows on every route while offline, and hides when connectivity returns.

대부분의 앱에서는 pending loading state만으로 충분합니다. 앱 전체에 연결 상태를 알리려면 root layout에 banner를 추가하세요. 콘텐츠가 로딩되는 바로 그 위치에 상태를 보여 주려면, useOffline으로 route의 Suspense fallback 자체가 offline 상태를 인식하도록 만드세요.

For most apps, the pending loading state is enough. Add a banner in the root layout to communicate the connectivity state across the app. To surface that state right where the content is loading, make the route's Suspense fallback itself offline-aware with useOffline.

같은 패턴은 parameter가 있는 route로도 확장됩니다. /chats/[id] 같은 route는 offline 상태에서 /chats/42로 navigate하면 공유되는 App Shell을 render하고, <Suspense> boundary 뒤의 dynamic 메시지들은 연결이 돌아오면 로드됩니다.

The same pattern extends to parameterized routes. A route like /chats/[id] renders its shared App Shell when you navigate to /chats/42 offline, and the dynamic messages behind its <Suspense> boundary load when the connection returns.

route가 클릭 전에 link별 URL 데이터까지 prefetch한다면, /chats/42는 연결이 돌아오기를 기다리지 않고 offline 상태에서도 그 prefetch로부터 메시지를 즉시 render합니다. 자세한 내용은 Optimizing prefetching을 참고하세요.

If the route also prefetches its per-link URL data ahead of the click, /chats/42 renders its messages from that prefetch immediately, even offline, instead of waiting for the connection to return. See Optimizing prefetching to learn more.

Retry Server Actions after the network returnsNetwork가 돌아온 뒤 Server Action 재시도

flag가 없으면 network 없이 호출한 Server Action은 fetch error를 던지고, await하던 promise는 reject됩니다. form에서 그 rejection을 잡아 error를 보여 줄지, 다시 시도할지, 어딘가에 queue에 넣을지 결정해야 합니다.

Without the flag, a Server Action called with no network throws a fetch error and the awaited promise rejects. Your form has to catch the rejection and decide what to do: show an error, retry, or queue it somewhere.

experimental.useOffline을 활성화하면 그 실패는 코드에 전달되지 않습니다. 호출은 연결이 돌아올 때까지 pending 상태로 남고, request가 다시 실행되며, await하던 promise는 server의 response로 resolve됩니다. component에 try/catch도, retry loop도, reconnection handler도 필요 없습니다.

With experimental.useOffline enabled, that failure never reaches your code. The call stays pending until the connection returns, the request runs again, and the awaited promise resolves with the server's response. No try/catch, no retry loop, no reconnection handler in the component.

하지만 button은 여전히 멈춘 것처럼 보이는 상태로 남아 있을 것입니다. useTransition과 useOffline을 함께 사용해 offline 상태를 인식하는 label을 붙이세요.

The button is still going to sit there looking frozen, though. Combine useTransition with useOffline to give it an offline-aware label.

TSJSapp/ping/actions.ts
'use server'

export async function ping(): Promise<string> {
  return new Date().toISOString()
}

export async function ping() {
  return new Date().toISOString()
}
TSJSapp/ping/ping-form.tsx
'use client'

import { useState, useTransition } from 'react'
import { useOffline } from 'next/offline'
import { ping } from './actions'

export function PingForm() {
  const [pongs, setPongs] = useState<string[]>([])
  const [pending, startTransition] = useTransition()
  const isOffline = useOffline()

  function handleSubmit() {
    startTransition(async () => {
      const pong = await ping()
      setPongs((prev) => [pong, ...prev])
    })
  }

  const label = pending
    ? isOffline
      ? 'Pinging (offline, will retry)...'
      : 'Pinging...'
    : 'Ping'

  return (
    <form action={handleSubmit}>
      <button type="submit" disabled={pending}>
        {label}
      </button>
      <ul>
        {pongs.map((t) => (
          <li key={t}>{t}</li>
        ))}
      </ul>
    </form>
  )
}

offline 상태에서 Ping을 클릭하면 button이 비활성화되고 label이 "Pinging (offline, will retry)..."로 바뀝니다. 연결을 복구하면 await하던 ping() 호출이 resolve되어 목록에 timestamp가 추가되고, label은 "Ping"으로 돌아옵니다. 두 번 클릭할 필요도, client-side retry 코드도 없습니다.

Clicking Ping while offline disables the button and changes its label to "Pinging (offline, will retry)...". Restoring connectivity resolves the awaited ping() call, appends the timestamp to the list, and reverts the label to "Ping". No second click, no client-side retry code.

Note

offline 상태에서 Server Action이 pending인 동안 link를 클릭하면 아무 일도 일어나지 않는 것처럼 보일 수 있습니다. link의 navigation도 network가 필요하므로, action과 같은 연결 신호 뒤에 queue로 대기합니다. 둘 다 연결이 돌아오면 resolve됩니다.

While offline, clicking a link during a pending Server Action may appear to do nothing. The link's navigation also needs the network and queues behind the same connectivity signal as the action. Both resolve when the connection returns.

Testing테스트

이 기능은 next build && next start로 테스트하세요. dev mode는 offline 동작을 확인하기에 신뢰할 수 있는 기준이 아닙니다.

Test this feature with next build && next start. Dev mode is not a reliable reference for offline behavior.

Chrome에서는 DevTools > Network > Offline을, Firefox에서는 Network Monitor의 throttling 메뉴를 사용하세요. 실제 환경에서 테스트하려면 노트북이나 휴대폰의 비행기 모드를 켜거나, WiFi 연결을 끊거나, network cable을 뽑으세요.

In Chrome, use DevTools > Network > Offline; in Firefox, use the Network Monitor's throttling menu. For a real-world test, toggle airplane mode on your laptop or phone, disconnect WiFi, or unplug the network cable.

Without Cache ComponentsCache Components 없이

route 수준의 loading.tsx도 같은 역할을 합니다. Next.js에 route의 shell로 prefetch할 boundary를 제공하므로, shell이 offline에서도 render되고 network가 돌아오면 페이지가 재개됩니다. loading.tsx prefetching이 동작하는 방식은 Prefetching을 참고하세요. useOffline hook, banner, Server Action 재시도는 모두 똑같이 동작합니다.

A route-level loading.tsx does the same job. It gives Next.js a boundary to prefetch as the route's shell, so the shell renders offline and the page resumes once the network returns. For how loading.tsx prefetching works, see Prefetching. The useOffline hook, banner, and Server Action retry all behave the same way.
