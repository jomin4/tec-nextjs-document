Building public pagesPublic page 만들기

Public page는 모든 사용자에게 같은 콘텐츠를 보여 줍니다. 흔한 예로 landing page, 마케팅 page, 상품 page가 있습니다.

Public pages show the same content to every user. Common examples include landing pages, marketing pages, and product pages.

data가 공유되므로 이런 page는 미리 prerender해 두고 재사용할 수 있습니다. 그 결과 page load가 빨라지고 server 비용이 줄어듭니다.

Since data is shared, these kind of pages can be prerendered ahead of time and reused. This leads to faster page loads and lower server costs.

이 가이드에서는 사용자 간에 data를 공유하는 public page를 만드는 방법을 보여 줍니다.

This guide will show you how to build public pages that share data across users.

Example예제

예제로 상품 목록 page를 만들어 보겠습니다.

As an example, we'll build a product list page.

static header로 시작해서, async 외부 data를 사용하는 상품 목록을 추가하고, response를 blocking하지 않고 render하는 방법을 배웁니다. 마지막으로 page 전체를 dynamic rendering으로 전환하지 않고 사용자별 promotion banner를 추가합니다.

We'll start with a static header, add a product list with async external data, and learn how to render it without blocking the response. Finally, we'll add a user-specific promotion banner without switching the entire page to dynamic rendering.

Step 1: Add a simple header1단계: 간단한 header 추가하기

간단한 header부터 시작해 봅시다.

Let's start with a simple header.

TSapp/products/page.tsx
// Static component
function Header() {
  return <h1>Shop</h1>
}

export default async function Page() {
  return (
    <>
      <Header />
    </>
  )
}

Static componentsStatic component

<Header /> component는 외부 data, request header, route params, 현재 시각, 무작위 값처럼 request마다 바뀌는 어떤 입력에도 의존하지 않습니다.

The <Header /> component doesn't depend on any inputs that change between requests, such as: external data, request headers, route params, the current time, or random values.

Good to know

깜빡임 없이 locale에 맞는 날짜나 시간을 표시해야 한다면 Preventing flash before hydration을 참고하세요.

If you need to display locale-aware dates or times without a visible flash, see Preventing flash before hydration.

출력이 절대 바뀌지 않고 미리 결정될 수 있으므로, 이런 component를 static component라고 합니다. request를 기다릴 이유가 없으므로 Next.js는 build time에 page를 안전하게 prerender할 수 있습니다.

Since its output never changes and can be determined ahead of time, this kind of component is called a static component. With no reason to wait for a request, Next.js can safely prerender the page at build time.

next build를 실행해 이를 확인할 수 있습니다.

We can confirm this by running next build.

>_Terminal
Route (app)      Revalidate  Expire
┌ ○ /products           15m      1y
└ ○ /_not-found

○  (Static)  prerendered as static content

명시적인 설정을 추가하지 않았는데도 product route가 static으로 표시된 것을 볼 수 있습니다.

Notice that the product route is marked as static, even though we didn't add any explicit configuration.

Step 2: Add the product list2단계: 상품 목록 추가하기

이제 상품 목록을 fetch하고 render해 봅시다.

Now, let's fetch and render our product list.

TSapp/products/page.tsx
import db from '@/db'
import { List } from '@/app/products/ui'

function Header() {}

// Dynamic component
async function ProductList() {
  const products = await db.product.findMany()
  return <List items={products} />
}

export default async function Page() {
  return (
    <>
      <Header />
      <ProductList />
    </>
  )
}

header와 달리 상품 목록은 외부 data에 의존합니다.

Unlike the header, the product list depends on external data.

Dynamic componentsDynamic component

이 data는 시간이 지나면서 바뀔 수 있으므로, render 결과가 더 이상 안정적이라고 보장할 수 없습니다. 그래서 상품 목록은 dynamic component가 됩니다.

Since this data can change over time, the rendered output is no longer guaranteed to be stable. This makes the product list a dynamic component.

별도 지시가 없으면 framework는 사용자 request마다 최신 data를 fetch하길 원한다고 가정합니다. 이 설계는 새 server request가 page를 render하는 표준 웹 동작을 반영한 것입니다.

Without guidance, the framework assumes you want to fetch fresh data on every user request. This design choice reflects standard web behavior where a new server request renders the page.

하지만 이 component가 request time에 render되면, data를 fetch하는 동안 route 전체의 response가 지연됩니다. page를 새로고침하면 이런 일이 일어나는 것을 볼 수 있습니다.

However, if this component is rendered at request time, fetching its data will delay the entire route from responding. If we refresh the page, we can see this happen.

header는 즉시 render되지만, 상품 목록 fetch가 끝날 때까지 브라우저로 보낼 수 없습니다.

Even though the header is rendered instantly, it can't be sent to the browser until the product list has finished fetching.

이런 performance 급락을 막기 위해, uncached data를 처음 await하면 Next.js는 warning을 표시합니다. <Suspense> 바깥에서 uncached data에 접근하면 route가 prerender되지 않는다는 내용입니다.

To protect us from this performance cliff, the first time we await this uncached data Next.js shows a warning: accessing uncached data outside of <Suspense> prevents the route from being prerendered.

이 시점에서 response를 어떻게 unblock할지 결정해야 합니다. 방법은 둘 중 하나입니다:

At this point, we have to decide how to unblock the response. Either:

  • component를 Cache해서 안정적으로 만들어 page의 나머지 부분과 함께 prerender되게 합니다.
  • component를 Stream해서 non-blocking으로 만들어 page의 나머지 부분이 기다리지 않게 합니다.
  • Cache the component, so it becomes stable and can be prerendered with the rest of the page.
  • Stream the component, so it becomes non-blocking and the rest of the page doesn't have to wait for it.

이 경우 상품 카탈로그는 모든 사용자에게 공유되므로 caching이 올바른 선택입니다.

In our case, the product catalog is shared across all users, so caching is the right choice.

Cache componentsCache component

'use cache' directive를 사용해 함수를 cacheable로 표시할 수 있습니다.

We can mark a function as cacheable using the 'use cache' directive.

TSapp/products/page.tsx
import db from '@/db'
import { List } from '@/app/products/ui'

function Header() {}

// Cache component
async function ProductList() {
  'use cache'
  const products = await db.product.findMany()
  return <List items={products} />
}

export default async function Page() {
  return (
    <>
      <Header />
      <ProductList />
    </>
  )
}

이렇게 하면 함수가 cache component가 됩니다. 처음 실행될 때 반환하는 값이 cache되어 재사용됩니다.

This turns it into a cache component. The first time it runs, whatever we return will be cached and reused.

cache component의 입력이 request가 도착하기 전에 사용 가능하다면, static component와 똑같이 prerender될 수 있습니다.

If a cache component's inputs are available before the request arrives, it can be prerendered just like a static component.

다시 새로고침하면 cache component가 response를 blocking하지 않으므로 page가 즉시 load되는 것을 볼 수 있습니다. 그리고 next build를 다시 실행하면 page가 여전히 static인 것을 확인할 수 있습니다:

If we refresh again, we can see the page loads instantly because the cache component doesn't block the response. And, if we run next build again, we can confirm the page is still static:

>_Terminal
Route (app)      Revalidate  Expire
┌ ○ /products           15m      1y
└ ○ /_not-found

○  (Static)  prerendered as static content

하지만 page가 영원히 static으로 남는 경우는 드뭅니다.

But, pages rarely stay static forever.

Step 3: Add a dynamic promotion banner3단계: dynamic promotion banner 추가하기

간단한 page라도 언젠가는 dynamic 콘텐츠가 필요해집니다. 이를 보여 주기 위해 promotion banner를 추가해 봅시다:

Sooner or later, even simple pages need some dynamic content. To demonstrate this, let's add a promotional banner:

TSapp/products/page.tsx
import db from '@/db'
import { List, Promotion } from '@/app/products/ui'
import { getPromotion } from '@/app/products/data'

function Header() {}

async function ProductList() {}

// Dynamic component
async function PromotionContent() {
  const promotion = await getPromotion()
  return <Promotion data={promotion} />
}

export default async function Page() {
  return (
    <>
      <PromotionContent />
      <Header />
      <ProductList />
    </>
  )
}

이번에도 처음에는 dynamic으로 시작합니다. 그리고 이전과 마찬가지로 blocking 동작이 생기면 Next.js warning이 표시됩니다.

Once again, this starts off as dynamic. And as before, introducing blocking behavior triggers a Next.js warning.

지난번에는 data가 공유되었으므로 cache할 수 있었습니다. 이번에는 promotion이 사용자의 위치나 A/B 테스트 같은 request별 입력에 의존하므로, caching으로 blocking 동작을 해결할 수 없습니다.

Last time, the data was shared, so it could be cached. This time, the promotion depends on request specific inputs like the user's location and A/B tests, so we can't cache our way out of the blocking behavior.

Partial prerendering

dynamic 콘텐츠를 추가한다고 해서 완전히 blocking되는 render로 돌아가야 하는 것은 아닙니다. streaming으로 response를 unblock할 수 있습니다.

Adding dynamic content doesn't mean we have to go back to a fully blocking render. We can unblock the response with streaming.

Next.js는 기본으로 streaming을 지원합니다. Suspense boundary를 사용해 stream되는 response를 어디서 _chunk_로 나눌지, 그리고 콘텐츠가 load되는 동안 어떤 fallback UI를 보여 줄지 framework에 알려 줄 수 있습니다.

Next.js supports streaming by default. We can use a Suspense boundary to tell the framework where to slice the streamed response into chunks, and what fallback UI to show while content loads.

TSapp/products/page.tsx
import { Suspense } from 'react'
import db from '@/db'
import { List, Promotion, PromotionSkeleton } from '@/app/products/ui'
import { getPromotion } from '@/app/products/data'

function Header() {}

async function ProductList() {}

// Dynamic component (streamed)
async function PromotionContent() {
  const promotion = await getPromotion()
  return <Promotion data={promotion} />
}

export default async function Page() {
  return (
    <>
      <Suspense fallback={<PromotionSkeleton />}>
        <PromotionContent />
      </Suspense>
      <Header />
      <ProductList />
    </>
  )
}

fallback은 나머지 static 콘텐츠, cache된 콘텐츠와 함께 prerender됩니다. 안쪽 component는 async 작업이 끝난 뒤 나중에 stream되어 들어옵니다.

The fallback is prerendered alongside the rest of our static and cached content. The inner component streams in later, once its async work completes.

이렇게 바꾸면 Next.js가 prerender 가능한 작업과 request time 작업을 분리할 수 있고, route는 partially prerendered 상태가 됩니다.

With this change, Next.js can separate prerenderable work from request-time work and the route becomes partially prerendered.

이번에도 next build를 실행해 확인할 수 있습니다:

Again, we can confirm this by running next build:

>_Terminal
Route (app)      Revalidate  Expire
┌ ◐ /products    15m      1y
└ ◐ /_not-found

◐  (Partial Prerender)  Prerendered as static HTML with dynamic server-streamed content

build time에는 header, 상품 목록, promotion fallback을 포함한 page의 대부분이 render되고, cache되어, content delivery network로 push됩니다.

At build time, most of the page, including the header, product list and promotion fallback, is rendered, cached and pushed to a content delivery network.

request time에는 prerender된 부분이 사용자와 가까운 CDN node에서 즉시 제공됩니다.

At request time, the prerendered part is served instantly from a CDN node close to the user.

동시에 사용자별 promotion은 server에서 render되어 client로 stream되고, fallback 자리에 교체되어 들어갑니다.

In parallel, the user specific promotion is rendered on the server, streamed to the client, and swapped into the fallback slot.

마지막으로 page를 한 번 더 새로고침하면, page 대부분은 즉시 load되고 dynamic 부분은 준비되는 대로 stream되어 들어오는 것을 볼 수 있습니다.

If we refresh the page one last time, we can see most of the page loads instantly, while the dynamic parts stream in as they become available.
