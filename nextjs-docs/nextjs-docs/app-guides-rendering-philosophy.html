Static and Dynamic as a Spectrum스펙트럼으로서의 Static과 Dynamic

대부분의 웹 framework는 route 수준에서 static과 dynamic 사이에 명확한 선을 긋습니다. 하나의 page는 build 시점에 prerender되거나, request 시점에 server-render됩니다. 이 모델은 이해하기 쉽고 deploy하기도 쉽습니다. static 파일은 CDN에 올리고 dynamic route는 server로 연결하면 됩니다.

Most web frameworks draw a hard line between static and dynamic at the route level. A page is either prerendered at build time or server-rendered at request time. This model is simple to understand and simple to deploy: you upload static files to a CDN and point dynamic routes at a server.

Next.js는 다른 접근 방식을 취합니다: static과 dynamic의 경계는 route 수준이 아니라 component 수준에 있습니다. 하나의 page 안에 즉시 로드되는 static shell과, resolve되는 대로 stream되어 들어오는 dynamic 영역이 함께 있을 수 있습니다. cache된 함수가 dynamic route 안에 있을 수 있습니다. static page를 redeploy 없이 업데이트할 수도 있습니다.

Next.js takes a different approach: the boundary between static and dynamic is at the component level, not the route level. A single page can have a static shell that loads instantly and dynamic sections that stream in as they resolve. A cached function can live inside a dynamic route. A static page can be updated without a redeploy.

이것이 바로 Partial Prerendering, Cache Components(use cache), on-demand revalidation이 가능하게 하는 것입니다. 이들은 점진적으로 덧붙인 기능이 아니라, static과 dynamic을 양자택일이 아닌 스펙트럼으로 다루는 rendering 모델을 나타냅니다.

This is what Partial Prerendering, Cache Components (use cache), and on-demand revalidation enable. They are not incremental features: they represent a rendering model that treats static and dynamic as a spectrum rather than a binary choice.

What This Enables이것으로 가능해지는 것

이 모델은 개발자와 사용자에게 구체적인 이점을 줍니다:

This model benefits developers and users in concrete ways:

  • 체감 로딩 시간 단축. dynamic 콘텐츠가 stream되어 들어오는 동안 static shell은 즉시 render됩니다. 사용자는 page 전체가 render될 때까지 기다리지 않고 바로 유용한 콘텐츠를 볼 수 있습니다.
  • 점진적인 caching. 개발자는 build 시점에 route가 static인지 dynamic인지 미리 결정하지 않고도 caching과 revalidation을 점진적으로 추가할 수 있습니다. 어떤 page든 on-demand로 revalidate할 수 있고, 어떤 함수든 use cache로 cache할 수 있습니다.
  • 세분화된 caching. route가 아니라 함수를 use cache로 cache합니다. deployment가 아니라 tag를 revalidate합니다. 즉, 비용이 큰 database query를 page의 나머지 부분과 독립적으로 cache할 수 있습니다.
  • Faster perceived load times. The static shell renders immediately while dynamic content streams in. Users see useful content right away instead of waiting for the entire page to render.
  • Incremental caching. Developers can add caching and revalidation incrementally, without deciding upfront at build time whether a route is static or dynamic. Any page can be revalidated on demand, and any function can be cached with use cache.
  • Granular caching. Cache a function with use cache, not a route. Revalidate a tag, not a deployment. This means an expensive database query can be cached independently of the rest of the page.

The Trade-Off트레이드오프

웹 framework들은 static 콘텐츠와 dynamic 콘텐츠의 경계를 어디에 두느냐가 서로 다릅니다. 각 접근 방식은 개발자의 유연성과 infrastructure 복잡도 사이에서 서로 다른 trade-off를 선택합니다.

Web frameworks differ in where they place the boundary between static and dynamic content. Each approach makes a different trade-off between developer flexibility and infrastructure complexity.

Build-time prerenderingBuild 시점 prerendering

모든 page가 build 시점에 생성됩니다. 결과물은 runtime infrastructure 없이 어떤 CDN이나 파일 server에서도 제공할 수 있는 static 파일입니다. dynamic 콘텐츠가 있다면 page가 로드된 뒤 client-side fetching이 필요합니다. deploy하기 가장 단순한 모델이지만, 콘텐츠가 바뀔 때마다 rebuild와 redeploy가 필요합니다.

Every page is generated at build time. The output is static files that can be served from any CDN or file server with zero runtime infrastructure. Dynamic content, if any, requires client-side fetching after the page loads. This is the simplest model to deploy, but every content change requires a rebuild and redeploy.

Route-level boundariesRoute 수준의 경계

각 route가 static인지 dynamic인지 선택합니다. static route는 build 시점에 prerender되고, dynamic route는 request마다 server-render됩니다. infrastructure도 깔끔하게 나뉩니다: static 파일은 CDN으로, dynamic route는 server로 갑니다. 이해하기는 쉽지만 선택이 route 단위로 전부 아니면 전무(all-or-nothing)입니다. 대부분 static이면서 dynamic 요소가 하나(사용자 인사말, 실시간 가격) 있는 page는 완전히 dynamic이 되거나, 로드 후 client에서 그 요소를 fetch해야 합니다.

Each route chooses whether it is static or dynamic. Static routes are prerendered at build time, dynamic routes are server-rendered per request. The infrastructure splits cleanly: static files go to a CDN, dynamic routes go to a server. This is straightforward to reason about but the choice is all-or-nothing per route. A mostly-static page with one dynamic element (a user greeting, a live price) must either be fully dynamic or fetch that element on the client after load.

Component-level boundariesComponent 수준의 경계

이것이 Next.js가 취하는 접근 방식입니다. static 콘텐츠와 dynamic 콘텐츠가 하나의 streaming response 안에 공존합니다. 하나의 page에 즉시 로드되는 static shell, 독립적으로 revalidate되는 cache된 함수, resolve되는 대로 stream되어 들어오는 dynamic 영역이 함께 있을 수 있으며, 개발자가 무언가를 별도의 route나 client-side fetch로 나눌 필요가 없습니다.

This is the approach Next.js takes. Static and dynamic content coexist within a single streaming response. A page can have a static shell that loads instantly, a cached function that revalidates independently, and a dynamic section that streams in as it resolves, all without the developer splitting anything into separate routes or client-side fetches.

trade-off는 infrastructure 복잡도입니다. rendering 경계가 더 세밀해지면 복잡도가 애플리케이션 코드에서 hosting platform으로 옮겨 갑니다. 아래에서 설명하는 infrastructure 요구 사항은 이 선택 때문에 존재합니다.

The trade-off is infrastructure complexity. A finer-grained rendering boundary transfers complexity from application code into the hosting platform. The infrastructure requirements described below exist because of this choice.

Infrastructure ImplicationsInfrastructure에 미치는 영향

component 수준의 rendering 모델은 Next.js 애플리케이션을 hosting하는 platform에 직접적인 영향을 줍니다:

The component-level rendering model has direct implications for platforms hosting Next.js applications:

  • static 콘텐츠와 dynamic 콘텐츠가 하나의 response로 제공되기 때문에 Streaming이 필요합니다. server는 초기 콘텐츠를 먼저 보내고, 그다음 dynamic 부분이 resolve되는 대로 stream합니다. 자세한 내용은 Streaming을 참고하세요.
  • cache된 콘텐츠는 언제든 revalidateTag()나 revalidatePath()로 on-demand invalidate될 수 있기 때문에, 여러 instance를 실행할 때는 Cache coordination이 필요합니다. 아키텍처는 How Revalidation Works를 참고하세요.
  • revalidation은 HTML response와 RSC payload(client-side navigation에 쓰이는, serialize된 React Server Components 데이터)를 모두 다시 생성하기 때문에 Cache consistency가 중요합니다. 이 둘이 어긋나면 사용자가 navigation 중에 일관되지 않은 데이터를 볼 수 있습니다. consistency 요구 사항은 How Revalidation Works를 참고하세요.
  • CDN latency로 PPR shell 제공하려면 static shell을 따로 저장하고 dynamic rendering을 올바르게 resume하기 위한 추가 platform integration이 필요할 수 있습니다. 구현 세부 사항은 PPR Platform Guide를 참고하세요.
  • Streaming is required because static and dynamic content are served in a single response. The server sends initial content first, then streams dynamic portions as they resolve. See Streaming for details.
  • Cache coordination is required when running multiple instances because any cached content can be invalidated on demand via revalidateTag() or revalidatePath(). See How Revalidation Works for the architecture.
  • Cache consistency matters because revalidation regenerates both the HTML response and the RSC payload (the serialized React Server Components data used for client-side navigation). If these get out of sync, users may see inconsistent data during navigation. See How Revalidation Works for consistency requirements.
  • PPR shell delivery at CDN latency can require additional platform integration to store the static shell separately and resume dynamic rendering correctly. See PPR Platform Guide for implementation details.

이 infrastructure 요구 사항들은 각각 하나의 기능과 직접 대응합니다: streaming은 점진적인 전달을 가능하게 하고, cache coordination은 invalidation을 여러 instance에 전파하며, cache consistency는 HTML과 RSC를 일치시켜 주고, edge에서의 PPR은 대개 추가적인 shell/resume integration이 필요합니다.

Each of these infrastructure requirements maps directly to a capability: streaming enables progressive delivery, cache coordination propagates invalidations across instances, cache consistency keeps HTML and RSC aligned, and PPR-at-edge often requires extra shell/resume integration.

Portability and Fidelity이식성과 Fidelity

Next.js는 Node.js server process로 실행되며, 단일 process가 모든 기능을 올바르게 처리합니다. streaming 지원은 Server Components와 PPR의 점진적인 전달을 가능하게 합니다. streaming이 없으면 response가 buffer되지만 기능은 여전히 동작합니다. 추가적인 infrastructure 투자(CDN caching, edge compute, shared cache)는 성능을 높이고, multi-instance deployment에서는 consistency 격차를 줄여 줍니다.

Next.js runs as a Node.js server process, and a single process handles every feature correctly. Streaming support enables progressive delivery of Server Components and PPR; without it, responses are buffered but features still work. Additional infrastructure investments (CDN caching, edge compute, shared cache) improve performance and, in multi-instance deployments, reduce consistency gaps.

이를 구체적으로 설명하기 위해, platform 지원을 두 가지 유형으로 구분합니다:

To make this concrete, we distinguish between two types of platform support:

Functional fidelity는 모든 Next.js 기능이 해당 platform에서 올바르게 동작한다는 뜻입니다. adapter test suite가 그 계약입니다: platform의 adapter가 test를 통과하면 완전한 functional fidelity를 갖춘 것입니다. 이것은 이분법적입니다: 통과하거나 통과하지 못하거나 둘 중 하나입니다. test suite는 공정하고 완전하도록 platform 파트너의 기여에 열려 있습니다.

Functional fidelity means every Next.js feature works correctly on the platform. The adapter test suite is the contract: if a platform's adapter passes the tests, it has full functional fidelity. This is binary: it passes or it doesn't. The test suite is open to contributions from platform partners to ensure it is fair and complete.

Performance fidelity는 기능이 최적의 성능 특성을 달성한다는 뜻입니다. 예를 들어 PPR의 static shell이 origin latency가 아니라 CDN latency로 제공되거나, ISR이 background에서 1초 미만의 전파로 revalidate하는 동안 stale 콘텐츠를 즉시 제공하는 것입니다. performance fidelity는 스펙트럼입니다: 모든 platform은 각자의 아키텍처에 따라 서로 다른 수준을 달성하며, 시간이 지나면서 개선됩니다.

Performance fidelity means features achieve their optimal performance characteristics. For example, PPR's static shell served at CDN latency rather than origin latency, or ISR serving stale content instantly while revalidating in the background with sub-second propagation. Performance fidelity is a spectrum: every platform will achieve different levels based on their architecture, and platforms will improve over time.

functional fidelity를 달성한 platform은 Next.js의 완전히 지원되는 deployment target입니다. performance fidelity는 platform들이 차별화하는 지점입니다. 전체 기능 호환성 표는 Deploying to Platforms를 참고하세요.

A platform that achieves functional fidelity is a fully supported deployment target for Next.js. Performance fidelity is how platforms differentiate. See Deploying to Platforms for the full feature compatibility matrix.

CDN Feature CompatibilityCDN 기능 호환성

많은 CDN이 더 깊은 Next.js integration에 유용한 primitive(edge compute, key-value storage, blob storage)를 가지고 있지만, end-to-end PPR resume 지원은 아직 자리 잡는 중이며 platform별 맞춤 작업이 필요할 수 있습니다. 현재 대부분의 community adapter는 이런 CDN 고유의 primitive를 활용하지 않고 Next.js를 Node.js server로 deploy합니다. 현재 adapter 목록은 Deploying 페이지를 참고하세요.

Many CDNs have useful primitives for deeper Next.js integration (edge compute, key-value storage, blob storage), but end-to-end PPR resume support is still emerging and may require bespoke platform work. Most community adapters today deploy Next.js as a Node.js server without leveraging these CDN-specific primitives. See the Deploying page for the current list of adapters.

전체 CDN 호환성 표는 Deploying to Platforms를, caching 동작에 대한 자세한 내용은 CDN Caching을 참고하세요.

See Deploying to Platforms for the full CDN compatibility table and CDN Caching for caching behavior details.
