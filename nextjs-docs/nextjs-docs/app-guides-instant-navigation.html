Ensuring instant navigations즉각적인 navigation 보장하기

이 가이드에서는 instant navigation을 이해하고, 즉시 navigate되는 route를 작성하고, initial UI에 무엇이 들어가는지 시각화하고, end-to-end test로 그 동작을 고정하는 과정을 단계별로 살펴봅니다.

This guide walks through understanding instant navigations, writing a route that navigates instantly, visualizing what's in the initial UI, and locking the behavior in with end-to-end tests.

What "instant" means"instant"의 의미

사용자가 클릭하는 순간 브라우저가 새 페이지 rendering을 시작할 수 있고, static·cache된·fallback 콘텐츠가 바로 표시되며, 그동안 server가 나머지 콘텐츠를 fallback 자리로 stream한다면 그 navigation을 instant navigation이라고 합니다.

A navigation is instant when the browser can start rendering the new page the moment the user clicks, with static, cached, and fallback content showing up right away, while the server streams the remaining content into its fallbacks.

Good to know

이 정의는 cache가 warm 상태라고 가정합니다. cache가 cold 상태라면 server가 cache된 결과를 한 번은 계산해야 하므로, route로의 첫 navigation은 여전히 기다려야 할 수 있습니다.

This definition assumes caches are warm. Cold caches still require the server to compute the cached result once, so the first navigation to a route may still wait.

같은 route라도 직접 방문과 client navigation은 서로 다른 initial UI를 만들 수 있습니다. Direct visit 시에는 보통 CDN에서 static shell을 HTML로 받습니다. Client navigation 시에는 현재 route와 목적지 route가 공유하는 layout 아래만 다시 render하므로, 그 지점보다 위에 있는 <Suspense> boundary가 정의한 fallback UI는 전환 중에 사용할 수 없습니다.

A direct visit and a client navigation to the same route can produce different initial UI. Direct visits get the static shell as HTML, typically from a CDN. Client navigations only re-render below the layout the current and destination routes share, so the fallback UI defined by a <Suspense> boundary above that point can't be used during the transition.

새 페이지가 즉시 나타나는지는 공유 layout 아래에 있는 <Suspense> boundary와 caching에 달려 있습니다.

Whether the new page appears instantly depends on the <Suspense> boundaries and caching present below the shared layout.

페이지 로드와 client navigation이 서로 다른 initial UI를 만드는 이유

페이지 로드 시에는 전체 페이지가 document root부터 render됩니다. 모든 component가 server에서 실행되고, suspend되는 것은 무엇이든 전체 tree에서 가장 가까운 <Suspense> boundary가 잡아냅니다.

/store/shoes와 /store/hats 사이의 client navigation에서는 /store layout 아래의 component만 다시 render됩니다. root layout의 <Suspense> boundary는 페이지 로드 시에는 모든 것을 감싸지만, 이 navigation에서는 re-render 범위보다 위에 있으므로 trigger되지 않습니다.

client-side hook이 다르게 동작하는 이유도 이것입니다. useSearchParams()는 build 시점에 search param을 알 수 없으므로 prerender 중에 suspend됩니다. 하지만 client navigation에서는 router가 이미 URL에서 param을 가지고 있으므로 hook이 동기적으로 resolve됩니다. 같은 component라도 client navigation에서는 즉시 render되지만 페이지 로드 시에는 fallback 뒤에 머무를 수 있습니다.

prefetch={true}를 사용하면 link별 prefetching이 navigation 전에 link의 URL 데이터(searchParams와 params)를 resolve합니다. 먼저 App Shell로 route를 instant하게 만드세요. App Shell 없이 block되는 route는 link별 prefetching으로 고칠 수 없습니다. 관련 패턴은 Optimizing prefetching을 참고하세요.

With prefetch={true}, per-link prefetching resolves a link's URL data (searchParams and params) before navigation. First make the route instant with its App Shell. Per-link prefetching cannot fix a route that blocks without it. See Optimizing prefetching for the patterns.

The rest of this guide covers the tools these migrations use, walks a navigation that blocks to instant, inspects what lands in the initial UI, and locks the result in with end-to-end tests.

The tools도구

Build the static shellstatic shell 만들기

Cache Components에서 caching directive("use cache"와 그 변형)는 async 함수의 결과에 lifetime을 지정합니다. 이 덕분에 Next.js가 그 결과를 static shell에 포함할 수 있습니다.

With Cache Components, caching directives ("use cache" and its variants) assign a lifetime to an async function's result, which is what lets Next.js include it in the static shell.

Good to know

"use cache: private"는 cookies(), headers() 같은 runtime API를 읽는 함수를 cache하기 위한 변형입니다. 결과는 server가 아니라 브라우저에만 cache됩니다. static shell의 일부가 될 수는 없습니다. prefetching과 어떻게 함께 쓰이는지는 Optimizing prefetching 가이드의 "use cache: private"를 참고하세요.

"use cache: private" is a variant for caching functions that read runtime APIs like cookies() and headers(). The result is cached in the browser only, not on the server. It can't be part of the static shell. See "use cache: private" in the Optimizing prefetching guide for how it pairs with prefetching.

cache되지 않은 데이터나 cookies(), headers() 같은 runtime API를 읽는 tree 부분에 대한 fallback UI는 <Suspense> boundary로 선언합니다. 콘텐츠가 resolve되면 fallback 자리로 stream됩니다.

<Suspense> declares fallback UI for parts of the tree that read uncached data or runtime APIs like cookies() and headers(); the content streams into the fallback when it resolves.

Good to know

fallback이 cookies(), headers() 또는 전체 URL에 접근할 수도 있습니다. 그러면 build 시점에 fallback 자체가 suspend되므로, tree에서 더 위쪽에 <Suspense> boundary가 필요합니다. prefetch={true}가 있는 link의 경우 per-link prefetching이 navigation 전에 URL 데이터를 사용할 수 있게 해 주므로, fallback이 prefetch된 UI의 일부가 될 수 있습니다. timestamp나 데이터 fetch 같은 cache된 값은 fallback 안에 바로 둘 수 있습니다.

A fallback may access cookies(), headers(), or the full URL. At build time, the fallback itself suspends, and a <Suspense> boundary further up the tree is needed. For a link with prefetch={true}, per-link prefetching makes URL data available before navigation, so the fallback can become part of the prefetched UI. Cached values like timestamps or data fetches can sit directly inside the fallback.

Next.js는 route마다 App Shell을 생성할 수도 있습니다. App Shell은 나머지 콘텐츠가 stream되는 동안 client navigation 중에 render됩니다. Partial Prefetching은 App Shell을 기본 <Link> prefetch로 사용합니다. prefetch={true}가 있는 link는 해당 link의 URL 데이터에 의존하는 cache된 콘텐츠도 resolve할 수 있습니다.

Next.js can also generate an App Shell per route, which renders during client navigations while remaining content streams. Partial Prefetching uses the App Shell as the default <Link> prefetch. A link with prefetch={true} can also resolve cached content that depends on that link's URL data.

Prefetch URL data for a linklink의 URL 데이터 prefetch하기

Partial Prefetching에서는 화면에 보이는 각 <Link>가 기본적으로 목적지의 App Shell을 prefetch합니다. 같은 route로 가는 link들은 link마다 별도의 App Shell request를 보내는 대신 하나의 App Shell을 공유합니다.

Under Partial Prefetching, each visible <Link> prefetches the destination's App Shell by default. Links to the same route share one App Shell instead of triggering a separate App Shell request for each link.

특정 link에 대해 shell과 함께 페이지 콘텐츠까지 prefetch하려면 prefetch={true}를 설정하세요:

To prefetch the page content alongside the shell for a specific link, set prefetch={true}:

<Link href="/checkout" prefetch>
  Checkout
</Link>

Partial Prefetching이 활성화된 상태에서 prefetch={true}는 해당 link를 per-link prefetching에도 참여시킵니다. per-link prefetching은 클릭 전에 link별 URL 데이터(params, searchParams, 전체 URL)를 resolve합니다.

With Partial Prefetching enabled, prefetch={true} also opts the link into per-link prefetching, which resolves the per-link URL data (params, searchParams, the full URL) ahead of the click.

Validate instant navigationinstant navigation 검증하기

default 설정(validationLevel: 'warning')에서 Cache Components 앱은 development 중에 모든 Page와 Default segment를 검증합니다. 검증은 segment로의 navigation이 instant해지지 못하게 막는 요소를 드러냅니다. 즉, 어떤 navigation이 block될지, 어디에 <Suspense> boundary가 빠져 있는지, 어떤 데이터가 cache되지 않은 채 사용자에게 도달하는지를 보여 줍니다.

By default (validationLevel: 'warning'), Cache Components apps validate every Page and Default segment in development. Validation surfaces what would keep navigations into a segment from being instant — which navigations would block, where a <Suspense> boundary is missing, and which data is reaching the user uncached.

자동 검증을 끄고 instant를 명시적으로 export한 segment만 검증하려면 validationLevel을 'manual-warning'으로 설정하세요:

To opt out of automatic validation and only validate segments that explicitly export instant, set validationLevel to 'manual-warning':

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  experimental: {
    instantInsights: {
      validationLevel: 'manual-warning',
    },
  },
}

export default nextConfig
검증이 서로 다른 navigation을 시뮬레이션하는 방법

검증 대상 route마다 Next.js는 initial page load와, route 계층의 여러 지점에서 일어나는 client navigation을 모두 확인합니다.

/shop/[slug] 같은 route의 경우 검증은 다음을 확인합니다:

  • Page load: 전체 tree가 root부터 render됩니다. root layout의 <Suspense>가 모든 것을 잡아냅니다.
  • Client navigation (예: /shop/shoes에서 /shop/hats로): /shop layout은 이미 mount되어 있고 그 아래 page만 다시 render됩니다. root layout의 <Suspense> boundary는 이 navigation을 감싸지 않습니다.

각 경우는 독립적으로 검증됩니다. 어떤 navigation 경로를 감싸는 <Suspense> boundary가 다른 경로는 감싸지 않을 수도 있습니다. 그래서 페이지가 page load 검사는 통과해도 client navigation에서는 실패할 수 있고, route 수가 늘어날수록 이런 문제를 손으로 잡아내기가 어려워집니다.

Test it in CICI에서 테스트하기

@next/playwright package는 instant() helper를 제공합니다. 이 helper는 assertion의 범위를 navigation 시 즉시 사용할 수 있는 UI로 한정하므로, regression이 CI에서 드러납니다. 패턴은 Prevent regressions with e2e tests를 참고하세요.

The @next/playwright package provides an instant() helper that scopes your assertions to the UI that's immediately available on navigation, so regressions surface in CI. See Prevent regressions with e2e tests for the pattern.

A page that navigates instantly즉시 navigate되는 페이지

이 기본 요소들이 실제로 동작하는 모습을 보기 위해 작은 store 앱을 생각해 봅시다. 각 product는 /store/[slug]에 자체 페이지가 있고, 홈페이지와 다른 product 페이지에서 이동할 수 있습니다. 목표는 product로, 그리고 product 사이를 navigate하는 것이 instant하게 이루어지는 것입니다.

To see the primitives in action, consider a small store app. Each product has its own page at /store/[slug], reachable from the homepage and from other product pages. The goal is that navigating to and between products is instant.

product 페이지는 두 가지 데이터를 fetch합니다: product 상세 정보(이름, 가격)와 실시간 재고입니다.

The product page fetches two pieces of data: product details (name, price) and live inventory.

  • generateStaticParams가 없으므로 slug는 request 시점에만 알 수 있습니다
  • 두 component 모두 slug를 얻기 위해 params를 await하며, 이때 suspend됩니다. 각 component는 자체 <Suspense> boundary를 가집니다
  • Product info 데이터는 거의 바뀌지 않으며, cache된 함수를 사용해 db에서 조회합니다
  • Inventory 데이터는 request마다 최신이어야 합니다. db query는 <Suspense> boundary 안에 있습니다
  • There is no generateStaticParams, meaning slug is only known at request time
  • Both components await params to get the slug, which suspends. Each has its own <Suspense> boundary
  • Product info rarely changes and is queried from the db using a cached function
  • Inventory must be fresh on each request. The db query is inside a <Suspense> boundary
TSapp/store/[slug]/page.tsx
import { Suspense } from 'react'
import { db } from '@/lib/db'

export default function ProductPage(props: PageProps<'/store/[slug]'>) {
  return (
    <div>
      <Suspense fallback={<p>Loading product...</p>}>
        <ProductInfo params={props.params} />
      </Suspense>
      <Suspense fallback={<p>Checking availability...</p>}>
        <Inventory params={props.params} />
      </Suspense>
    </div>
  )
}

type Params = PageProps<'/store/[slug]'>['params']

async function ProductInfo({ params }: { params: Params }) {
  const { slug } = await params
  const product = await getProduct(slug)
  return (
    <>
      <h1>{product.name}</h1>
      <p>${product.price}</p>
    </>
  )
}

async function getProduct(slug: string) {
  'use cache'
  return db.products.findBySlug(slug)
}

async function Inventory({ params }: { params: Params }) {
  const { slug } = await params
  const item = await db.inventory.findBySlug(slug)
  return <p>{item.count} in stock</p>
}

Client Component PagesClient Component 페이지

맨 위에 "use client"가 있는 페이지로의 soft navigation은 single-page app 전환처럼 동작합니다. navigation 시점에 server render가 없으므로 instant합니다. dev overlay는 이 방법을 fix card에 포함하지 않는데, 페이지를 server-component model 안에 유지하는 권장 방식들보다 영향이 크기 때문입니다. 페이지가 완전히 interactive해서 반드시 client component여야 할 때 "use client"를 사용하세요.

A soft navigation into a page with "use client" at the top behaves like a single-page app transition, with no server render at navigation time, which makes it instant. The dev overlay doesn't include this in its fix cards because it has bigger implications than the recommended approaches, which keep the page in the server-component model. Reach for "use client" when the page is fully interactive and must be a client component.

Good to know

"use client"를 써도 static shell에 대한 검증을 건너뛰지 않습니다. useSearchParams() 같은 hook에는 여전히 <Suspense> boundary가 필요합니다.

"use client" doesn't skip validation for the static shell. Hooks like useSearchParams() still need a <Suspense> boundary.

Prevent regressions with e2e testse2e test로 regression 방지하기

검증은 development 중에 구조적인 문제를 잡아내지만, codebase가 커지면 구조 검사는 shell이 존재한다는 것만 알려 줄 수 있습니다. 그 안에 올바른 콘텐츠가 들어 있는지는 알려 주지 못합니다. E2E test가 이 빈틈을 메웁니다. navigation이 완료될 때 사용자가 실제로 보는 것을 assert해서, 배포되기 전에 regression을 잡아냅니다.

Validation catches structural problems during development, but as the codebase grows, the structural checks can only tell you that a shell exists. They can't tell you whether the right content is in it. E2E tests close that gap: they assert on what the user actually sees when the navigation completes, catching regressions before they ship.

@next/playwright package에는 이를 위한 instant() helper가 포함되어 있습니다. @playwright/test와 함께 설치하세요:

The @next/playwright package includes an instant() helper for this. Install it alongside @playwright/test:

pnpm add -D @next/playwright @playwright/test
npm install -D @next/playwright @playwright/test
yarn add -D @next/playwright @playwright/test
bun add -D @next/playwright @playwright/test

route에 도달하는 방법은 두 가지이며, <Suspense> boundary가 한쪽은 감싸면서 다른 쪽은 감싸지 않을 수 있습니다:

A route can be reached two ways, and a <Suspense> boundary can cover one without covering the other:

  • Initial page load: page.goto()를 사용해 document response의 static UI를 테스트합니다.
  • Client navigation: <Link>를 클릭해 목적지의 prefetch된 UI를 테스트합니다. Per-link prefetching은 이 UI에 request별 콘텐츠를 추가할 수 있습니다.
  • Initial page load: Use page.goto() to test the static UI from the document response.
  • Client navigation: Click a <Link> to test the destination's prefetched UI. Per-link prefetching can add request-specific content to this UI.
TSe2e/navigation.test.ts
import { test, expect } from '@playwright/test'
import { instant } from '@next/playwright'

test.describe('Product page (/store/[slug])', () => {
  test('is instant on an initial page load', async ({ page, baseURL }) => {
    await instant(
      page,
      async () => {
        await page.goto('/store/hats')
        await expect(page.locator('h1')).toContainText('Baseball Cap')
        await expect(page.getByText('In stock')).toHaveCount(0)
      },
      { baseURL }
    )
    await expect(page.getByText('In stock')).toBeVisible()
  })

  test('is instant on a client navigation', async ({ page }) => {
    await page.goto('/store/shoes')
    await instant(page, async () => {
      await page.click('a[href="/store/hats"]')
      await page.waitForURL((url) => url.pathname === '/store/hats')
      await expect(page.locator('h1')).toContainText('Baseball Cap')
      await expect(page.getByText('In stock')).toHaveCount(0)
    })
    await expect(page.getByText('In stock')).toBeVisible()
  })
})

page.goto()가 첫 navigation이라면 Playwright의 baseURL을 instant()에 전달하세요. helper는 document를 request하기 전에 origin을 알아야 합니다.

Pass Playwright's baseURL to instant() when page.goto() is the first navigation. The helper needs the origin before requesting the document.

callback 안에서 initial page load는 static UI를, client navigation은 목적지의 prefetch된 UI를 보여 줍니다. 그 밖의 dynamic 콘텐츠는 callback이 끝날 때까지 block된 상태로 남습니다.

Inside the callback, an initial page load shows the static UI and a client navigation shows the destination's prefetched UI. Other dynamic content remains blocked until the callback finishes.

Good to know

instant() scope의 시작은 Navigation Inspector에서 Pause on navigations toggle을 켜는 것과 같고, scope의 끝은 Resume 버튼처럼 일시 정지를 해제합니다.

The start of the instant() scope is the same as turning on Pause on navigations in the Navigation Inspector, and the end of the scope releases the pause the way Resume does.

client navigation의 경우 목적지 UI를 assert하기 전에 목적지 URL을 기다리세요. 그렇지 않으면 공통 selector가 목적지가 commit되기 전에 source 페이지와 match될 수 있습니다. prefetch된 목적지가 commit되지 못하면 URL 대기가 timeout되어 test가 실패합니다.

For client navigations, wait for the destination URL before asserting on its UI. Otherwise, a shared selector can match the source page before the destination commits. If the prefetched destination cannot commit, the URL wait times out and the test fails.

Fixing a navigation that blocksblock되는 navigation 고치기

public API에서 product 데이터를 fetch하고 옆에 featured 목록을 보여 주는 다른 route, /products/[slug]를 생각해 봅시다:

Consider a different route, /products/[slug], that fetches product data from a public API and shows a featured list alongside:

TSapp/products/[slug]/page.tsx
export default async function ProductPage(
  props: PageProps<'/products/[slug]'>
) {
  const featured = await getFeatured()
  const { slug } = await props.params
  const res = await fetch(`https://next-recipe-api.vercel.dev/products/${slug}`)
  const product = await res.json()

  return (
    <div>
      <FeaturedSection items={featured} />
      <h1>{product.name}</h1>
      <p>${product.price}</p>
      <p>{product.description}</p>
    </div>
  )
}

async function getFeatured() {
  const res = await fetch('https://next-recipe-api.vercel.dev/products?limit=3')
  return res.json()
}

두 개의 fetch() 호출이 최상위에서 block됩니다: cache되지 않은 featured 목록 fetch와, slug별 product fetch(이 역시 params를 await함)입니다. 둘 다 Instant validation error로 하나씩 차례로 드러납니다.

Two fetch() calls block at the top level: an uncached featured-list fetch and a per-slug product fetch (which also awaits params). Both will surface as Instant validation errors, one at a time.

Step 1: Move the slug-dependent work into Suspense1단계: slug에 의존하는 작업을 Suspense 안으로 옮기기

검증은 먼저 slug별 product fetch를 드러냅니다.

Validation surfaces the per-slug product fetch first.

slug에 의존하는 작업을 하위 component로 추출하고 <Suspense>로 감싸세요:

Extract the slug-dependent work into a sub-component and wrap it with <Suspense>:

TSapp/products/[slug]/page.tsx
import { Suspense } from 'react'

async function ProductInfo({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params
  const res = await fetch(`https://next-recipe-api.vercel.dev/products/${slug}`)
  const product = await res.json()
  return (
    <>
      <h1>{product.name}</h1>
      <p>${product.price}</p>
      <p>{product.description}</p>
    </>
  )
}

export default async function ProductPage(
  props: PageProps<'/products/[slug]'>
) {
  const featured = await getFeatured()
  return (
    <div>
      <FeaturedSection items={featured} />
      <Suspense fallback={<p>Loading product...</p>}>
        <ProductInfo params={props.params} />
      </Suspense>
    </div>
  )
}

이제 await props.params와 product fetch가 함께 suspend됩니다. product fetch error가 사라지고, 검증은 다음 blocker로 넘어갑니다.

Now await props.params and the product fetch suspend together. The product-fetch error clears, and validation moves on to the next blocker.

Step 2: Cache the featured fetch2단계: featured fetch를 cache하기

이제 검증이 getFeatured()에서 발생합니다.

Validation now fires on getFeatured().

fetch하는 함수에 "use cache" directive를 추가하세요:

Add a "use cache" directive to the fetching function:

TSapp/products/[slug]/page.tsx
async function getFeatured() {
  'use cache'
  const res = await fetch('https://next-recipe-api.vercel.dev/products?limit=3')
  return res.json()
}

결과가 fetch 수준에서 cache됩니다. featured 목록은 App Shell과 함께 전달됩니다.

The result is cached at the fetch level. The featured list ships with the App Shell.

Good to know

serverless deploy 환경에서는 "use cache"의 in-memory caching이 instance 간에 유지되지 않습니다. 영구적인 caching을 원한다면 "use cache: remote" 사용을 고려하세요.

In serverless deployments, in-memory caching with "use cache" will not persist across instances. Consider using "use cache: remote" for persistent caching.

Validation passes. Open the DevTools and try a client navigation. The featured section appears immediately, and "Loading product..." shows where the product details will stream in.

Iterate on loading statesloading state 반복 개선하기

검증을 통과했다는 것은 navigation이 instant하다는 뜻입니다. loading state가 좋다는 뜻은 아닙니다. tree의 높은 곳에 둔 <Suspense> boundary(예를 들어 페이지 전체를 감싸는 boundary)는 검증을 통과할 수 있지만, navigation할 때마다 페이지 대부분을 하나의 fallback으로 대체합니다.

Validation passing means the navigation is instant. It does not mean the loading states are good. A <Suspense> boundary placed high in the tree (say, wrapping the whole page) might satisfy validation, but it replaces most of the page with a single fallback on every navigation.

가장 좋은 loading state는 실제 cache된 콘텐츠를 가능한 한 많이 보이게 유지하고, 데이터가 실제로 전송 중인 곳에만 fallback을 보여 줍니다. header, 이미지, 설명은 보이게 두고 가격과 재고만 fallback 뒤에 둔 product 페이지는, 전체 로드 시간이 같더라도 전체 페이지 skeleton보다 더 빠르게 느껴집니다.

The best loading states keep as much real, cached content visible as possible and only show fallbacks where data is actually in flight. A product page that keeps the header, image, and description visible with only the price and availability behind a fallback feels faster than a full-page skeleton, even at the same total load time.

Use the DevTools to see what your users see, or see the AI workflow for automating the loop with an agent.

AI workflow

큰 흐름에서 보면 agent는 하나의 navigation을 다음과 같이 최적화합니다:

At a high level, an agent optimizes a single navigation like this:

  • Observe: 검증 insight를 읽고, 즉시 나타나야 할 정확한 navigation과 UI를 정합니다.
  • Test: 대상 UI가 정상적으로 render되는지 확인한 다음, instant() test를 작성하고 route를 바꾸기 전에 그 test가 실패하는지 검증합니다.
  • Fix: validation error는 특정 component를 지목하고 해결책(use cache 또는 <Suspense>)을 제안합니다. agent가 해결책을 적용하고 검증을 다시 실행합니다.
  • Verify: production과 유사한 build에서 test를 실행하고, 통과한 test를 regression 방지 장치로 유지합니다.
  • Observe: read validation insights and choose the exact navigation and UI that should appear immediately.
  • Test: confirm the target UI renders normally, then write an instant() test and verify that it fails before changing the route.
  • Fix: validation errors name a specific component and suggest a fix (use cache or <Suspense>). The agent applies the fix and re-runs validation.
  • Verify: run the test against a production-like build and keep the passing test as a regression guard.

agent가 전체 caching model을 이해할 필요는 없습니다. insight와 error가 사라질 때까지 따라가기만 하면 됩니다. 다만 앱에 특화된 의도는 알아야 합니다. 무엇이 즉시 나타나야 하는지, 무엇이 stream되어도 되는지, 무엇이 항상 최신이어야 하는지 알려 주세요. caching 결정이 불분명할 때는 cache lifetime을 추측하기보다 데이터를 <Suspense> 뒤에서 최신 상태로 유지하세요.

The agent doesn't need to understand the full caching model, only to follow the insights and errors until they're gone. It does need your app-specific intent, though. Tell it what should appear immediately, what can stream in, and what must stay fresh. When a caching decision is unclear, keep the data fresh behind <Suspense> rather than guessing a cache lifetime.

loading state를 반복 개선할 때는 "콘텐츠를 최대화하고, spinner 뒤에 있어야 하는 부분을 줄여 줘" 같은 prompt가 boundary를 아래로 내리는 데 효과적입니다.

For iterating on loading states, a prompt like "maximize my content, and reduce the amount that needs to be behind a spinner" works well for pushing boundaries down.

Cache Components route를 다루는 agent는 보통 세 가지 수단을 사용합니다:

Agents working on a Cache Components route typically reach for three levers:

  • Push down: I/O를 Suspense로 감싼 하위 component로 추출해 부모는 static하게 유지하고, static한 형제 component들이 shell로 올라가게 합니다.
  • Cache: 'use cache'와 cacheLife를 함께 사용해 freshness profile을 지정합니다.
  • Per-link prefetching (nav 전용): route가 URL 데이터(searchParams 또는 params)를 읽는다면, framework가 link prefetch 시점에 그 데이터를 resolve하도록 per-link prefetching에 참여시킵니다. cookies()나 headers()에서 오는 session 데이터는 이것 없이도 이미 App Shell에 들어갑니다.
  • Push down: extract I/O into a Suspense-wrapped child so the parent stays static and static siblings lift into the shell.
  • Cache: pair 'use cache' with cacheLife to assign a freshness profile.
  • Per-link prefetching (nav-only): when a route reads URL data (searchParams or params), opt it into per-link prefetching so the framework resolves that data at link-prefetch time. Session data from cookies() or headers() already lands in the App Shell without it.

각 refactor는 변경이 실제로 반영되었는지 검증하기 위해 전후 capture와 함께 진행해야 합니다. capture가 똑같아 보인다면 refactor가 효과를 내지 못한 것입니다.

Each refactor should pair with a before/after capture to verify the change actually landed. Identical-looking captures mean the refactor didn't take effect.

agent가 변경 사항이 실제로 무엇을 render하는지 볼 수 있도록 agent-browser와 함께 사용하세요. React DevTools가 활성화되어 있으면 agent-browser는 component tree와 아직 pending 상태인 <Suspense> boundary를 보고하므로, agent가 변경을 하고, shell의 snapshot을 찍고, 무엇이 반영되었는지 확인하고, 조정할 수 있습니다. 설정 방법은 AI agents 가이드의 Runtime visibility를 참고하세요.

For agents to see what their changes actually render, pair this with agent-browser. With React DevTools enabled it reports the component tree and which <Suspense> boundaries are still pending, so an agent can make a change, snapshot the shell, check what landed, and adjust. See Runtime visibility in the AI agents guide for the setup.

It confirms the target UI renders normally, writes an instant() test that fails before the fix, then works it to green against a production-like build and ships it as a regression guard. Use it for the initial load (hard navigation), client-side navigation (soft navigation), or both.

Opting out제외하기

모든 layout이나 page가 instant할 수 있거나 instant해야 하는 것은 아닙니다. 구조적인 수정이 그만한 노력의 가치가 없거나, route가 instant navigation의 우선순위가 아니라면 두 가지 범위 중 하나에서 검증을 조정하세요.

Not every layout or page can or should be instant. When the structural fix isn't worth the work, or when a route isn't a priority for instant navigation, refine validation at one of two scopes.

dev overlay는 모든 insight 옆에 이를 Block fix로 표시합니다:

The dev overlay surfaces this as the Block fix alongside every insight:

Allow blocking route
// page.tsx or layout.tsx
export const instant = false

page 또는 layout 파일에 instant = false를 설정하세요. 이렇게 하면 해당 segment가 검증 피드백에서 제외됩니다. 구조가 뒷받침된다면 segment는 여전히 instant하게 navigate될 수 있으며, framework가 그 segment에 대한 insight를 표시하지 않을 뿐입니다. 그 아래 형제 segment 사이의 navigation은 여전히 검증됩니다.

Set instant = false on the page or layout file. This opts the segment out of validation feedback. The segment may still navigate instantly if its structure supports it; the framework just won't surface insights for it. Navigations between sibling segments below are still validated.

TSapp/dashboard/layout.tsx
export const instant = false

/dashboard/layout.tsx에 false를 설정하면, 검증은 더 이상 외부에서 /dashboard로 들어오는 navigation을 지적하지 않습니다. /dashboard/a와 /dashboard/b 사이의 navigation은 여전히 검사됩니다.

With false on /dashboard/layout.tsx, validation no longer flags navigations into /dashboard from outside; navigations between /dashboard/a and /dashboard/b are still checked.

제외된 segment의 경우 navigation은 server에서 block됩니다. 콘텐츠가 cookie나 header에 의존하지만 cache lifetime을 알 수 있다면, 제외하는 대신 use cache: private로 cache해서 App Shell이 클릭 전에 그 콘텐츠를 실어 나르게 할 수 있습니다. 단, stale 시간이 최소 5분이어야 합니다.

For opted-out segments, the navigation blocks on the server. If the content depends on cookies or headers but has a known cache lifetime, caching it with use cache: private lets the App Shell carry it ahead of the click instead of opting out, as long as its stale time is at least 5 minutes.
