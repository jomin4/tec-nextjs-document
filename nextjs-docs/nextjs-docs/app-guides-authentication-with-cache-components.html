How to implement authentication with Cache ComponentsCache Components로 인증 구현하기

Cache Components가 활성화되어 있으면 session 읽기는 request 시점에 일어나므로, static shell 안에 prerender될 수 없습니다. 대신 인증된 UI는 <Suspense> boundary 뒤에서 stream되어 들어오고, session에서 파생된 데이터는 여전히 cache할 수 있습니다.

With Cache Components enabled, a session read happens at request time, so it can't be prerendered into the static shell. Authenticated UI streams in behind a <Suspense> boundary instead, and data derived from the session can still be cached.

예제에서는 암호화된 cookie session을 위해 iron-session을 사용하지만, 이 패턴은 어떤 session 또는 authentication library에도 적용됩니다. 실행 가능한 전체 버전은 with-iron-session-cache-components 예제를 참고하세요.

The examples use iron-session for encrypted cookie sessions, but the patterns apply to any session or authentication library. For a complete, runnable version, see the with-iron-session-cache-components example.

Prerequisites사전 준비

cacheComponents를 활성화하세요:

Enable cacheComponents:

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
}

export default nextConfig

이 가이드는 Cache Components를 사용한 authentication의 코드 패턴을 다룹니다: request 시점에 session 읽기, 인증된 UI streaming, session에서 파생된 데이터 caching. Cache Components에 익숙하고(그렇지 않다면 먼저 Caching을 읽으세요), 로그인 시 이미 session을 설정하고 있다고 가정합니다.

This guide covers code patterns for authentication with Cache Components: reading the session at request time, streaming authenticated UI, and caching session-derived data. It assumes you're comfortable with Cache Components (if not, read Caching first) and that you already have a session set on login.

Migrating an existing app기존 앱 마이그레이션하기

Cache Components가 활성화되면 instant navigation validation이 session을 읽는 모든 route를 표시합니다. request 읽기는 static shell 안에 prerender될 수 없기 때문입니다. 배포하기 전에 이를 모두 해결할 필요는 없습니다. page나 layout에 export const instant = false를 설정해 server에서 계속 blocking하도록 두고, 아래 패턴을 route 하나씩 도입하세요. 전체 migration 흐름은 Migrating to Cache Components를 참고하세요.

With Cache Components enabled, instant navigation validation flags every route that reads the session, because a request read can't be prerendered into the static shell. You don't have to resolve them all before shipping. Set export const instant = false on the page or layout to let it keep blocking on the server, then adopt the patterns below one route at a time. For the full migration workflow, see Migrating to Cache Components.

Step 1: Read the current user1단계: 현재 사용자 읽기

현재 사용자를 읽는다는 것은 session cookie를 읽은 다음 사용자를 조회하는 것입니다. request 읽기는 static shell의 일부가 될 수 없으므로, 항상 <Suspense> boundary 뒤에 위치하며 navigation마다 stream되어 들어옵니다.

Reading the current user reads the session cookie, then looks the user up. A request read can't be part of the static shell, so it always sits behind a <Suspense> boundary and streams in on every navigation.

사용자 session은 일정 기간 동안 유효하므로, cache lifetime을 추가하면 framework가 해당 콘텐츠를 미리 prefetch할 수 있습니다.

Because a user session is valid for a period of time, adding a cache lifetime lets the framework prefetch that content ahead of time.

하지만 server 쪽 directive로는 그 lifetime을 줄 수 없습니다: 일반 use cache도 use cache: remote도 cookies()를 호출할 수 없고, 값을 꺼내서 전달하는 방법도 쓸 수 없습니다. 그 이유는 다음과 같습니다:

The server-side directives can't give it that lifetime, though: neither a plain use cache nor use cache: remote can call cookies(), and you can't extract the value and pass it in either, because:

  • session helper는 자기 코드 깊숙한 곳에서 cookie를 읽으므로, 밖으로 꺼낼 것이 없습니다.
  • 이를 검증할 때 token의 만료 시각을 현재 시각과 비교하므로(iron-session의 unsealData는 만료된 seal을 거부합니다), 이 읽기는 request와 시간에 의존합니다.
  • A session helper reads the cookie deep inside its own code, so there's nothing to lift out.
  • Validating it compares a token's expiry against the current time (iron-session's unsealData rejects an expired seal), so the read is request- and time-dependent.

바로 이럴 때 use cache: private를 사용합니다: cookies()와 headers()를 직접 읽고, 결과는 server가 아닌 브라우저에만 보관합니다.

That's what use cache: private is for: it reads cookies() and headers() directly, keeping the result in the browser only, never on the server.

private scope는 브라우저에 머무르므로 server에서는 절대 cache되지 않습니다. 대신 server에서 cache하려면 값(예: userId)을 꺼내 일반 use cache나 use cache: remote에 전달하세요. 같은 패턴으로 session에서 파생된 데이터도 cache할 수 있으며, 이는 4단계에서 다룹니다.

A private scope stays in the browser, so it never caches on the server. To cache on the server instead, extract a value (the userId, for example) and pass it into a plain use cache or use cache: remote. The same pattern caches data derived from the session, covered in Step 4.

TSlib/session.ts
import 'server-only'
import { cookies } from 'next/headers'
import { sealData, unsealData } from 'iron-session'

export type SessionData = {
  userId?: string
}

const COOKIE_NAME = 'app_session'
const password = process.env.SESSION_PASSWORD!

export async function getSession(): Promise<SessionData> {
  const cookie = (await cookies()).get(COOKIE_NAME)?.value
  if (!cookie) {
    return {}
  }
  return unsealData<SessionData>(cookie, { password })
}
TSlib/auth.ts
import 'server-only'
import { redirect } from 'next/navigation'
import { getSession } from './session'
import { findUserById } from './data'

export type User = {
  id: string
  name: string
}

export async function getCurrentUser(): Promise<User> {
  'use cache: private'

  const { userId } = await getSession()
  if (!userId) {
    redirect('/login')
  }

  const user = await findUserById(userId)
  if (!user) {
    redirect('/login')
  }

  return { id: user.id, name: user.name }
}

redirect() 호출은 값을 반환하는 대신 throw해서 rendering을 중단하므로 cache되지 않습니다. 확인된(resolved) 사용자만 cache됩니다.

The redirect() calls throw to interrupt rendering rather than return a value, so they aren't cached. Only a resolved user is.

Good to know

use cache: private는 cookies(), headers(), searchParams는 허용하지만 connection()은 허용하지 않습니다. 전체 목록은 use cache: private를 참고하세요.

use cache: private accepts cookies(), headers(), and searchParams, but not connection(). See use cache: private for the full list.

Step 2: Show the user without blocking the page2단계: page를 막지 않고 사용자 보여 주기

session을 읽는 component는 반드시 <Suspense> boundary 뒤에 있어야 합니다. Cache Components에서는 boundary 밖에서 cookies()를 읽으면 build error가 납니다. 또한 boundary는 page의 나머지 부분을 빠르게 유지해 주는 역할도 합니다. boundary 밖의 모든 것은 static이거나 use cache로 감싸져 있고 자체적으로 runtime 데이터를 읽지 않는 한, static shell로 prerender되어 즉시 로드됩니다. boundary 뒤의 영역만 request를 기다립니다.

A component that reads the session must sit behind a <Suspense> boundary. With Cache Components, reading cookies() outside a boundary is a build error. The boundary is also what keeps the rest of the page fast. Anything outside it prerenders into the static shell and loads instantly, as long as it's static or wrapped in use cache and doesn't read runtime data of its own. Only the section behind the boundary waits for the request.

TSapp/page.tsx
import { Suspense } from 'react'
import { getCurrentUser } from '@/lib/auth'
import { getAnnouncements } from '@/lib/data'

export default function Page() {
  return (
    <main>
      {/* Cached, so it prerenders into the static shell */}
      <Announcements />

      {/* Reads the session, so it streams in behind the boundary */}
      <Suspense fallback={<p>Loading your dashboard…</p>}>
        <Dashboard />
      </Suspense>
    </main>
  )
}

async function Announcements() {
  'use cache'
  const announcements = await getAnnouncements()
  return (
    <ul>
      {announcements.map((announcement) => (
        <li key={announcement}>{announcement}</li>
      ))}
    </ul>
  )
}

async function Dashboard() {
  const user = await getCurrentUser()
  return <h1>Welcome, {user.name}</h1>
}

layout의 최상위에서도 session을 읽지 마세요. layout에서 session을 최상위 await로 읽으면 {children}을 포함한 segment 전체가 그 request 뒤에 묶이므로, boundary 안의 component로 내려 보내세요. Push dynamic access down을 참고하세요.

Keep the session read out of a layout's top level, too. A top-level await on the session in a layout holds the whole segment, including {children}, behind that request, so push it into a component inside a boundary. See Push dynamic access down.

Good to know

getCurrentUser는 session을 읽고 검사한 뒤 범위를 좁힌 user를 반환합니다. 이런 읽기를 하나의 함수에 모으는 것이 Data Access Layer 패턴입니다.

getCurrentUser reads the session, checks it, and returns a narrow user. Centralizing those reads in one function is the Data Access Layer pattern.

Step 3: Share the user across components3단계: 여러 component에서 사용자 공유하기

user가 필요한 component마다 session을 다시 읽을 필요는 없습니다. 한 번 읽은 다음, 같은 boundary 안에서 원하는 만큼 많은 Server Component와 Client Component에 넘겨주면 됩니다.

You don't have to read the session again in every component that needs the user. Read it once, then hand it to as many Server and Client Components as you like from inside the same boundary.

Server Component는 getCurrentUser()를 직접 호출할 수 있습니다. prop drilling 없이 Client Component에 전달하려면 promise를 한 번 만들고 context로 넘긴 다음 use()로 풀어내세요. 일반적인 패턴은 Using React's use within a Context Provider를 참고하세요. getCurrentUser는 request를 읽으므로, 그 promise는 layout 최상위가 아니라 Suspense boundary 안에서 만드세요.

Server Components can call getCurrentUser() directly. To reach Client Components without prop drilling, create the promise once, pass it through context, and unwrap it with use(). For the general pattern, see Using React's use within a Context Provider. Because getCurrentUser reads the request, create its promise inside the Suspense boundary, not at the top of a layout.

TSapp/user-provider.tsx
'use client'

import { createContext, use } from 'react'
import type { ReactNode } from 'react'
import type { User } from '@/lib/auth'

const UserContext = createContext<Promise<User> | null>(null)

export function UserProvider({
  userPromise,
  children,
}: {
  userPromise: Promise<User>
  children: ReactNode
}) {
  return <UserContext value={userPromise}>{children}</UserContext>
}

export function useUser() {
  const userPromise = use(UserContext)
  if (!userPromise) {
    throw new Error('useUser must be used within a UserProvider')
  }
  return use(userPromise)
}

boundary 뒤의 Server Component가 promise를 만들고 await하지 않은 채 provider에 넘깁니다. 그러면 각 consumer가 자기 boundary 뒤에서 이를 resolve하므로, 공유 chrome은 session을 기다리지 않고 render됩니다:

The Server Component behind the boundary creates the promise and hands it to the provider without awaiting it. Each consumer then resolves it behind its own boundary, so the shared chrome renders without waiting on the session:

TSapp/page.tsx
function Dashboard() {
  const userPromise = getCurrentUser()

  return (
    <UserProvider userPromise={userPromise}>
      <Suspense fallback={<span>Loading…</span>}>
        <UserBadge />
      </Suspense>
    </UserProvider>
  )
}

Client Component는 useUser()를 호출해 현재 사용자를 가져옵니다. use()는 promise가 resolve될 때까지 suspend하므로, component를 <Suspense> boundary 뒤에 두세요:

Client Components call useUser() to get the current user. Because use() suspends until the promise resolves, keep the component behind a <Suspense> boundary:

TSapp/user-badge.tsx
'use client'

import { useUser } from './user-provider'

export function UserBadge() {
  const user = useUser()
  return <span>Signed in as {user.name}</span>
}
Good to know

client에는 필요한 것만 노출하세요. getCurrentUser helper는 raw session이 아니라 범위를 좁힌 { id, name }을 반환합니다. 민감한 field가 client에 도달하지 않게 하려면 taintUniqueValue를 참고하세요.

Expose only what the client needs. The getCurrentUser helper returns a narrow { id, name } rather than the raw session. To keep sensitive fields from reaching the client, see taintUniqueValue.

Step 4: Cache session-derived data4단계: session에서 파생된 데이터 cache하기

이제 user를 얻었으니, 그 사용자를 위해 fetch한 데이터를 두 가지 방법 중 하나로 cache할 수 있습니다. user id를 일반 use cache 함수에 전달하면 결과는 server에 id를 key로 하여 보관되고(id가 cache key의 일부가 됩니다), 나중에 cacheTag로 무효화할 수 있습니다. use cache: private scope 안에서 읽으면 결과는 server가 아닌 브라우저에만 보관되는데, 이는 요구 사항상 특정 데이터를 일시적으로라도 server 쪽에 저장하는 것이 금지될 때 중요합니다. 예제에서는 id를 전달합니다. 이 노트들은 tag가 붙어 있고 변경될 때 갱신되기 때문입니다.

Now that you have the user, you can cache the data you fetch for them in one of two ways. Passing the user id into a plain use cache function keeps the result on the server, keyed by the id (it becomes part of the cache key), where a cacheTag can invalidate it later. Reading it inside a use cache: private scope keeps it in the browser only, never on the server, which matters when requirements forbid storing certain data server-side, even ephemerally. The example passes the id, since these notes are tagged and refreshed when they change.

일반 use cache scope는 cookies()를 읽을 수 없으므로, export된 함수가 user를 resolve하고 id만 cache된 함수에 전달합니다:

A plain use cache scope can't read cookies(), so the exported function resolves the user and passes just the id to the cached function:

TSlib/data.ts
import 'server-only'
import { cacheLife, cacheTag } from 'next/cache'
import { getCurrentUser } from './auth'

export async function getNotes() {
  const user = await getCurrentUser()
  return getNotesByUserId(user.id)
}

async function getNotesByUserId(userId: string) {
  'use cache'
  cacheTag(`notes:${userId}`)
  cacheLife('minutes')

  return db.query.notes.findMany({
    where: (notes, { eq }) => eq(notes.userId, userId),
  })
}

getNotesByUserId는 export하지 마세요. 그래야 호출하는 쪽에서 다른 id를 넘겨 다른 사용자의 노트를 요청할 수 없습니다. export된 getter 안에서 user를 resolve하는 것이 이를 안전하게 만듭니다. Data Security를 참고하세요.

Keep getNotesByUserId unexported so a caller can't request another user's notes by passing a different id. Resolving the user inside the exported getter is what makes that safe. See Data Security.

노트를 render하는 Server Component에서 이를 호출하세요. 전달할 user id는 없으며, getter 안의 getCurrentUser() 호출은 private cache에 hit하므로 session을 다시 읽지 않습니다:

Call it from a Server Component that renders the notes. There's no user id to pass, and the getCurrentUser() call inside the getter hits the private cache, so the session isn't read again:

TSapp/page.tsx
async function Notes() {
  const notes = await getNotes()
  // ...
}
Good to know: cache key와 tag는 plain text로 저장됩니다.

cache된 함수의 argument와 capture된 변수는 cache key로 serialize되고, cacheTag 값은 작성한 그대로 저장됩니다. 어느 쪽도 hash되지 않습니다: 기본 cache는 이를 plain text map key와 tag 목록으로 보관하고, remote cache도 같은 방식으로 받습니다. user id처럼 안정적인 식별자로 key와 tag를 정하고, secret과 민감한 개인 데이터(token, password, 원본 email)는 argument와 tag에 넣지 마세요.

A cached function's arguments and captured variables are serialized into its cache key, and cacheTag values are stored as written. Neither is hashed: the default cache holds them as plain-text map keys and tag lists, and a remote cache receives them the same way. Key and tag on a stable identifier like the user id, and keep secrets and sensitive personal data (tokens, passwords, raw emails) out of arguments and tags.

server에서 일반 use cache는 entry를 best effort로 메모리에 보관합니다: 메모리 압박이 있으면 evict되고, serverless 환경에서는 instance 간에 유지되지 않습니다. 그 데이터가 instance와 request를 넘어 유지되어야 한다면, 내구성 있는 공유 storage를 위해 use cache: remote를 선택하세요. 이때는 어떤 cache key를 고르느냐가 hit rate를 좌우합니다.

On the server, plain use cache keeps the entry in memory as a best effort: it's evicted under pressure and, in serverless, doesn't persist across instances. If that data must survive across instances and requests, opt into use cache: remote for durable, shared storage, where the cache key you choose drives your hit rate.

Step 5: Update session-derived data5단계: session에서 파생된 데이터 업데이트하기

Server Action이 사용자의 데이터를 변경하면, 같은 tag로 updateTag를 호출해 cache된 entry를 갱신하세요. action 안에서 session을 다시 읽어, client를 신뢰하는 대신 action이 스스로 authorization하도록 하세요. 이것이 왜 중요한지는 authentication with Server Actions를 참고하세요.

When a Server Action changes a user's data, call updateTag with the same tag to refresh the cached entry. Re-read the session inside the action so it authorizes itself rather than trusting the client. See authentication with Server Actions for why this matters.

TSapp/actions.ts
'use server'
import { redirect } from 'next/navigation'
import { updateTag } from 'next/cache'
import { getSession } from '@/lib/session'
import { saveNote } from '@/lib/data'

export async function addNote(formData: FormData) {
  const { userId } = await getSession()
  if (!userId) {
    redirect('/login')
  }

  const note = String(formData.get('note') ?? '').trim()
  if (note) {
    await saveNote(userId, note)
    updateTag(`notes:${userId}`)
  }
}

Step 6: Make authenticated navigations instant6단계: 인증된 navigation을 즉시 처리하기

cache된 읽기에는 이미 lifetime이 있으므로, 이 부분은 대부분 저절로 이루어집니다. use cache: private scope는 따로 지정하지 않으면 default profile(5분 stale)을 사용하고, session을 읽는 route는 인증된 콘텐츠가 담긴 session별 App Shell을 만들어 내며, 이는 session별로 prefetch되고 cache됩니다. 그런 route로의 navigation은 이미 즉시 이루어집니다.

Cached reads already have a lifetime, so this mostly happens on its own. A use cache: private scope uses the default profile (a five-minute stale) unless you set one, and a route that reads the session produces a per-session App Shell with the authenticated content, prefetched and cached per session. Navigations to it are already instant.

이를 유지하는 데 필요한 두 가지는 다음과 같습니다:

Two things keep it that way:

  • cacheLife로 lifetime을 조정한다면 stale을 30초 이상으로 유지하세요. 그보다 짧으면 해당 scope는 prefetching에서 빠집니다. cacheLife client cache behavior를 참고하세요.
  • URL(params 또는 searchParams 값)에 도 의존하는 route는 그 route를 가리키는 link에 <Link prefetch={true}>가 필요합니다. 이렇게 하면 link별 prefetching을 사용하게 되며, 클릭 전에 link별 데이터를 미리 resolve합니다.
  • If you tune the lifetime with cacheLife, keep stale at 30 seconds or more. Below that, the scope drops out of prefetching. See cacheLife client cache behavior.
  • A route that also depends on the URL (a params or searchParams value) needs <Link prefetch={true}> on the links pointing at it. That opts into per-link prefetching, which resolves the per-link data ahead of the click.
TSapp/page.tsx
<Link href={`/notes/${note.id}`} prefetch={true}>
  {note.text}
</Link>

이를 위해 목적지 route에는 Partial Prefetching이 필요하므로, partialPrefetching flag를 활성화하거나 segment에 prefetch = 'partial'을 설정하세요. 기다림을 줄일 가치가 있는 곳에만 이 prop을 추가하세요: 그 prefetch는 link마다 server 호출 한 번의 비용이 들므로, /chat/[id] link가 늘어선 sidebar는 항목마다 그 비용을 치르게 됩니다.

The destination needs Partial Prefetching for this, so enable the partialPrefetching flag or set prefetch = 'partial' on the segment. Add the prop where the wait is worth it: that prefetch costs one server invocation per link, so a sidebar of /chat/[id] links pays that cost per item.

Common pitfalls흔한 실수

  • 일반 use cache 함수 안에서 cookies()나 headers()를 읽는 것. 이렇게 하면 error가 throw됩니다. request는 밖에서 읽고 값을 전달하거나, use cache: private를 사용하세요.
  • cache key나 tag에 secret이나 개인 데이터를 넣는 것. argument와 cacheTag 값은 plain text로 저장됩니다. 민감한 입력이 아니라 안정적인 식별자로 key와 tag를 정하세요.
  • authorization을 client에 맡기는 것. UI 검사는 element를 숨길 뿐 데이터를 보호하지는 않습니다. 모든 Server Action과 Route Handler에서 데이터 가까이에서 session을 다시 검증하세요. Authorization을 참고하세요.
  • Reading cookies() or headers() inside a plain use cache function. This throws. Read the request outside and pass the value in, or use use cache: private.
  • Putting secrets or personal data in cache keys or tags. Arguments and cacheTag values are stored in plain text. Key and tag on a stable identifier, not on sensitive input.
  • Trusting the client for authorization. UI checks hide elements, but they don't protect data. Re-verify the session in every Server Action and Route Handler, close to the data. See Authorization.
