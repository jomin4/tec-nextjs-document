How to fetch client-side data with TanStack QueryTanStack Query로 client-side 데이터 fetch하기

TanStack Query를 사용해 Client Component에서 데이터를 fetch하고, Server Component에서 초기 데이터를 제공하며, browser mutation과 cache된 server 데이터를 조율하세요. 패턴을 고르려면 Client-side data fetching을 참고하세요.

Use TanStack Query to fetch data in Client Components, provide initial data from Server Components, and coordinate browser mutations with cached server data. See Client-side data fetching to choose a pattern.

Set up the providerprovider 설정하기

TanStack Query를 사용하는 route를 QueryClientProvider로 감싸세요. server render마다 새 query client를 만들고, browser에서는 하나의 query client를 재사용합니다:

Wrap the routes that use TanStack Query in a QueryClientProvider. Create a new query client for each server render and reuse one query client in the browser:

TSapp/products/providers.tsx
'use client'

import type { ReactNode } from 'react'
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'

let browserQueryClient: QueryClient | undefined

function getQueryClient() {
  // Keep server requests isolated and preserve the browser cache across renders.
  if (typeof window === 'undefined') return new QueryClient()
  browserQueryClient ??= new QueryClient()
  return browserQueryClient
}

export function Providers({ children }: { children: ReactNode }) {
  return (
    <QueryClientProvider client={getQueryClient()}>
      {children}
    </QueryClientProvider>
  )
}

가장 가까운 공유 layout에서 provider를 render하세요:

Render the provider from the nearest shared layout:

TSapp/products/layout.tsx
import { Providers } from './providers'

export default function Layout({ children }: LayoutProps<'/products'>) {
  return <Providers>{children}</Providers>
}

demo source의 전체 provider 설정을 확인하거나, TanStack Query Advanced SSR 가이드에서 provider option에 대해 알아보세요.

See the complete provider setup in the demo source or learn about provider options in the TanStack Query Advanced SSR guide.

Fetch data on the clientclient에서 데이터 fetch하기

초기 화면이 hydration 이후의 browser request를 기다려도 된다면 TanStack Query는 전적으로 browser에서 fetch할 수 있습니다. loading UI가 나타날 위치에 따라 inline 또는 Suspense loading state를 선택하세요. 이 예시들에서 query는 빈 값으로 시작해 hydration 이후 client state에 따라 업데이트됩니다.

TanStack Query can fetch entirely in the browser when the initial view can wait for a browser request after hydration. Choose an inline or Suspense loading state based on where the loading UI should appear. In these examples, query starts empty and updates from client state after hydration.

component가 자체 loading state와 error state를 render해야 한다면 useQuery를 사용하세요. enabled option은 상호작용으로 입력이 주어질 때까지 request를 지연시킵니다:

Use useQuery when the component should render its own loading and error states. The enabled option delays the request until the interaction provides an input:

TSapp/product-autocomplete.tsx
'use client'

import { useQuery } from '@tanstack/react-query'

type Product = { id: string; name: string }

async function searchProducts(query: string): Promise<Product[]> {
  const response = await fetch(
    `/api/products?query=${encodeURIComponent(query)}`
  )
  if (!response.ok) throw new Error('Failed to fetch products')
  return response.json()
}

export function ProductAutocomplete({ query }: { query: string }) {
  const {
    data = [],
    error,
    isPending,
  } = useQuery({
    queryKey: ['product-search', query],
    queryFn: () => searchProducts(query),
    enabled: query.length > 0,
  })

  if (!query) return null
  if (error) return <p>Failed to load products.</p>
  if (isPending) return <p>Loading products...</p>

  return (
    <ul>
      {data.map((product) => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  )
}

Use Suspense for client dataclient 데이터에 Suspense 사용하기

가장 가까운 Suspense boundary가 loading UI를 정의해야 한다면 useSuspenseQuery를 사용하세요. 결과가 로드되는 동안에도 사용할 수 있도록 interactive shell은 boundary 바깥에 두세요:

Use useSuspenseQuery when the nearest Suspense boundary should define the loading UI. Keep the interactive shell outside the boundary so it remains available while the results load:

TSapp/product-autocomplete.tsx
'use client'

import { useSuspenseQuery } from '@tanstack/react-query'
import { Suspense } from 'react'

type Product = { id: string; name: string }

async function searchProducts(query: string): Promise<Product[]> {
  const response = await fetch(
    `/api/products?query=${encodeURIComponent(query)}`
  )
  if (!response.ok) throw new Error('Failed to fetch products')
  return response.json()
}

export function ProductAutocomplete({ query }: { query: string }) {
  if (!query) return null

  return (
    <Suspense fallback={<p>Loading products...</p>}>
      <ProductResults query={query} />
    </Suspense>
  )
}

function ProductResults({ query }: { query: string }) {
  const { data } = useSuspenseQuery({
    queryKey: ['product-search', query],
    queryFn: () => searchProducts(query),
  })

  return (
    <ul>
      {data.map((product) => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  )
}

초기 request가 실패하면 useSuspenseQuery는 error를 가장 가까운 error boundary로 전파합니다.

If the initial request fails, useSuspenseQuery propagates the error to the nearest error boundary.

query에 데이터가 생긴 뒤에는, 같은 query에 대한 이후의 refetch에서 Suspense fallback을 다시 보여 주지 않고 cache된 데이터를 계속 render합니다. background refresh feedback을 제공하려면 isFetching을 사용하세요.

After a query has data, later refetches for the same query keep the cached data rendered instead of showing the Suspense fallback again. Use isFetching to provide background refresh feedback.

초기 화면에 데이터가 필요하다면 아래에 나온 것처럼 Server Component에서 제공하세요.

If the initial view needs the data, provide it from a Server Component as shown below.

Good to know

한 component 안의 여러 useSuspenseQuery 호출은 순차적으로 실행됩니다. 독립적인 query는 형제 component에 두거나 useSuspenseQueries를 사용하세요. request waterfall에 대해 더 알아보세요.

Multiple useSuspenseQuery calls in one component run sequentially. Put independent queries in sibling components, or use useSuspenseQueries. Learn more about request waterfalls.

Provide initial data from a Server ComponentServer Component에서 초기 데이터 제공하기

initial render에 데이터가 필요하고 TanStack Query가 이후에도 browser에서 계속 관리해야 한다면 server가 제공하는 데이터 패턴을 사용하세요. client가 이어받기 전에 Server Component가 초기 query 데이터를 제공할 수 있습니다.

Use the server-provided data pattern when the initial render needs the data and TanStack Query should continue managing it in the browser. A Server Component can provide initial query data before the client takes over.

TanStack Query 5.40.0 이상은 pending 상태의 query를 dehydrate할 수 있습니다. prefetchQuery를 await하지 않고 시작한 다음, dehydrate된 state를 <HydrationBoundary>에 전달하세요. Route Handler의 상대 URL은 browser에서만 resolve되므로 server에서는 queryFn을 override하세요:

TanStack Query 5.40.0 or later can dehydrate pending queries. Start prefetchQuery without awaiting it, then pass the dehydrated state to <HydrationBoundary>. Override queryFn on the server because the Route Handler's relative URL only resolves in the browser:

TSJSapp/products/[id]/page.tsx
import { Suspense } from 'react'
import {
  defaultShouldDehydrateQuery,
  dehydrate,
  HydrationBoundary,
  QueryClient,
} from '@tanstack/react-query'
import { getProduct } from './data'
import { productCache } from './product-cache'
import { ProductView } from './product-view'

export default function Page({ params }: PageProps<'/products/[id]'>) {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      {params.then(({ id }) => (
        <ProductData id={id} />
      ))}
    </Suspense>
  )
}

function ProductData({ id }: { id: string }) {
  const queryClient = new QueryClient()

  // Not awaited, so rendering is not blocked.
  void queryClient.prefetchQuery({
    ...productCache.options(id),
    queryFn: () => getProduct(id),
  })

  return (
    <HydrationBoundary
      state={dehydrate(queryClient, {
        shouldDehydrateQuery: (query) =>
          defaultShouldDehydrateQuery(query) ||
          query.state.status === 'pending',
      })}
    >
      <ProductView id={id} />
    </HydrationBoundary>
  )
}
import { Suspense } from 'react'
import {
  defaultShouldDehydrateQuery,
  dehydrate,
  HydrationBoundary,
  QueryClient,
} from '@tanstack/react-query'
import { getProduct } from './data'
import { productCache } from './product-cache'
import { ProductView } from './product-view'

export default function Page({ params }) {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      {params.then(({ id }) => (
        <ProductData id={id} />

    </Suspense>

  // Not awaited, so rendering is not blocked.

      <ProductView id={id} />
    </HydrationBoundary>
  )
}

server와 Client Component는 같은 query key를 사용해야 합니다. 두 호출 위치가 같은 identity를 공유하도록 key와 query option을 함께 두세요:

The server and Client Component must use the same query key. Keep the key and query options together so both call sites share the same identity:

TSJSapp/products/[id]/product-cache.ts
import { queryOptions } from '@tanstack/react-query'

export type Product = { id: string; name: string }

export const productCache = {
  key: (id: string) => ['product', id] as const,
  options: (id: string) =>
    queryOptions({
      queryKey: productCache.key(id),
      queryFn: async (): Promise<Product> => {
        const res = await fetch(`/api/products/${id}`)
        if (!res.ok) throw new Error('Failed to fetch product')
        return res.json()
      },
      staleTime: 30_000,
    }),
}

query 함수는 client에서 실행될 수 있도록 Route Handler를 fetch합니다. staleTime은 hydrate된 데이터를 30초 동안 fresh 상태로 유지해 client에서 즉시 refetch되는 것을 막습니다. 데이터가 얼마나 빨리 바뀔 수 있는지에 따라 기간을 정하세요.

The query function fetches a Route Handler so it can run on the client. The staleTime prevents an immediate client refetch by keeping the hydrated data fresh for 30 seconds. Choose a duration based on how quickly the data can change.

규모가 큰 기능에서는 모든 호출자가 같은 cache contract에서 key를 import하기만 한다면 query option을 별도의 client용 module에 둘 수 있습니다. TanStack Query defaults에 대해 더 알아보세요.

Larger features can place query options in a separate client-facing module as long as every caller imports the key from the same cache contract. Learn more about TanStack Query defaults.

SWR과 마찬가지로 params.then()은 <Suspense> 안에서 id를 resolve하고, ProductData는 boundary 아래에서 prefetch합니다.

As with SWR, params.then() resolves the id inside <Suspense>, and ProductData prefetches below the boundary.

Client Component는 useSuspenseQuery(또는 isPending과 error state를 inline으로 render하려면 useQuery)로 같은 query key를 읽습니다:

The Client Component reads the same query key with useSuspenseQuery (or useQuery to render isPending and error states inline):

Cache server-provided data with Cache ComponentsCache Components로 server가 제공하는 데이터 cache하기

이 패턴을 사용하기 전에 next.config.ts에서 cacheComponents를 활성화하세요. 그러면 TanStack Query에 제공되는 server 데이터를 cache할 수 있습니다. use cache를 추가하고, cacheLife profile을 고르고, mutation이 invalidate할 수 있도록 cacheTag를 적용하세요:

Enable cacheComponents in next.config.ts before using this pattern. You can then cache the server data provided to TanStack Query. Add use cache, choose a cacheLife profile, and apply cacheTag so mutations can invalidate it:

TSJSapp/products/[id]/data.ts
import { cacheLife, cacheTag } from 'next/cache'
import type { Product } from './product-cache'

export async function getProduct(id: string): Promise<Product> {
  'use cache'
  cacheLife('max')
  cacheTag(`product:${id}`)

  const product = await db.product.findUnique({ where: { id } })
  if (!product) throw new Error('Product not found')
  return product
}
import { cacheLife, cacheTag } from 'next/cache'

export async function getProduct(id) {
  'use cache'
  cacheLife('max')
  cacheTag(`product:${id}`)

  const product = await db.product.findUnique({ where: { id } })
  if (!product) throw new Error('Product not found')
  return product
}

이 예시는 쓰기 작업이 product tag를 invalidate하므로 cacheLife('max')를 사용합니다. cache profile 안에서 stale은 Next.js client cache가 prefetch된 payload를 얼마나 오래 재사용할 수 있는지를 제어하고, revalidate와 expire는 server cache를 제어합니다. server 값이 시간에 따라 refresh되어야 한다면 더 짧은 profile을 선택하세요.

This example uses cacheLife('max') because writes invalidate the product tag. Within the cache profile, stale controls how long the Next.js client cache can reuse a prefetched payload, while revalidate and expire control the server cache. Choose a shorter profile when the server value should refresh with time.

TanStack Query는 별도의 browser cache를 소유하므로, staleTime을 cacheLife와 맞출 필요는 없습니다.

TanStack Query owns a separate browser cache, so its staleTime does not need to match cacheLife.

Cache Components가 활성화되면 Next.js는 Client Component도 prerender합니다. initial render 중에 필요한 query는 Suspense 뒤에 두세요. TanStack Query는 active query state를 만들 때 현재 시간을 읽을 수 있는데, boundary가 있으면 Next.js가 current-time prerender error를 발생시키는 대신 그 작업을 뒤로 미룰 수 있습니다.

With Cache Components enabled, Next.js also prerenders Client Components. Keep a query needed during the initial render behind Suspense. TanStack Query can read the current time while creating active query state, and the boundary lets Next.js defer that work instead of raising a current-time prerender error.

같은 mutation이 browser cache를 업데이트하면서 cache된 server 데이터도 invalidate한다면, 두 identity를 하나의 공유 contract에 정의할 수 있습니다:

When the same mutation updates the browser cache and invalidates cached server data, you may define both identities in one shared contract:

app/products/[id]/product-cache.ts
 export const productCache = {
   key: (id: string) => ['product', id] as const,
+  tag: (id: string) => `product:${id}`,
   // ...
 }
app/products/[id]/product-cache.js
 export const productCache = {
   key: (id) => ['product', id],
+  tag: (id) => `product:${id}`,
   // ...
 }

그러면 server 함수는 cacheTag(productCache.tag(id))를 호출할 수 있습니다. 두 cache layer가 모두 재사용할 수 있도록 이 contract에는 server 전용 import와 client 전용 import를 넣지 마세요.

The server function can then call cacheTag(productCache.tag(id)). Keep this contract free of server-only and client-only imports so both cache layers can reuse it.

Good to know

TanStack Query의 dehydrate()는 Cache Components prerendering 중에 현재 시간을 읽습니다. cache된 초기 데이터에는 prerender 가능한 hydration helper를 사용하세요.

TanStack Query's dehydrate() reads the current time during Cache Components prerendering. Use the prerenderable hydration helper for cached initial data.

Coordinate server and client caches after mutationsmutation 이후 server와 client cache 조율하기

hydration은 초기 client cache 값을 제공합니다. hydration 이후에는 TanStack Query가 browser 사본과 그 revalidation을 소유합니다. 재사용되는 데이터의 경우 query key와 server tag를 같은 cache contract에 두세요:

Hydration provides the initial client cache value. After hydration, TanStack Query owns the browser copy and its revalidation. For reused data, keep the query key and server tag in the same cache contract:

TSJSapp/activity/activity-cache.ts
export const activityCache = {
  key: ['activity', 'unread'] as const,
  tag: (userId: string) => `activity:${userId}`,
}
export const activityCache = {
  key: ['activity', 'unread'],
  tag: (userId) => `activity:${userId}`,
}

mutation 시에는 useMutation의 onMutate callback으로 cache를 즉시 업데이트하고, 쓰기가 실패하면 onError에서 이전 값을 복원하세요. 이 예시에서는 최종 값을 알고 있으므로 action이 성공한 뒤에도 optimistic 값을 유지합니다:

On mutation, use useMutation's onMutate callback to update the cache immediately and restore the previous value in onError if the write fails. This example keeps the optimistic value after the action succeeds because the final value is known:

TSJSapp/activity/mark-read-button.tsx
'use client'

import { useMutation, useQueryClient } from '@tanstack/react-query'
import { markActivityReadAction } from './actions'
import { activityCache } from './activity-cache'

export function MarkReadButton() {
  const queryClient = useQueryClient()
  const queryKey = activityCache.key

  const markRead = useMutation({
    mutationFn: markActivityReadAction,
    onMutate: async () => {
      await queryClient.cancelQueries({ queryKey })
      const previous = queryClient.getQueryData(queryKey)
      queryClient.setQueryData(queryKey, { count: 0 })
      return { previous }
    },
    onError: (_error, _variables, context) => {
      queryClient.setQueryData(queryKey, context?.previous)
    },
  })

  return <button onClick={() => markRead.mutate()}>Mark read</button>
}

Server Action은 database에 쓰고 updateTag로 tag가 붙은 server 데이터를 만료시킵니다. tag가 일치하도록 cache된 server query에 cacheTag로 tag를 붙이세요:

The Server Action writes to the database and expires the tagged server data with updateTag. Tag the cached server query with cacheTag so the tag matches:

TSJSapp/activity/actions.ts
'use server'

import { updateTag } from 'next/cache'
import {
  getCurrentUserId,
  markActivityRead as markActivityReadInDatabase,
} from './data'
import { activityCache } from './activity-cache'

export async function markActivityReadAction() {
  const userId = await getCurrentUserId()
  await markActivityReadInDatabase(userId)
  updateTag(activityCache.tag(userId))

optimistic query 값은 현재 화면을 업데이트합니다. updateTag는 다음 cache된 server read가 최신 activity를 반환하도록 보장합니다.

The optimistic query value updates the current screen. updateTag ensures the next cached server read returns fresh activity.

Good to know

Server Action이 쓰기 결과를 즉시 반영해야 하는 cache된 read를 변경할 때 updateTag를 호출하세요. cache되지 않은 read에는 업데이트할 server tag가 없습니다. 다른 invalidation 동작은 Client-side data fetching을 참고하세요.

Call updateTag when a Server Action changes a cached read that must reflect the write immediately. An uncached read does not have a server tag to update. See Client-side data fetching for other invalidation behaviors.

Build a prerenderable hydration stateprerender 가능한 hydration state 만들기

위의 TanStack Query 패턴은 dehydrate()로 hydration state를 만듭니다. Cache Components를 사용하면 dehydrate()가 prerendering 중에 현재 시간(Date.now())을 읽어 current-time prerender error를 일으킵니다.

The TanStack Query pattern above uses dehydrate() to create the hydration state. With Cache Components, dehydrate() reads the current time (Date.now()) while prerendering and causes a current-time prerender error.

대신 그 timestamp만 cache하고 dehydrate된 state는 직접 만드세요. 시간을 읽는 부분을 데이터 read와 같은 tag를 가진 use cache로 감싸세요. mutation이 그 tag를 invalidate하면 데이터와 timestamp가 함께 갱신되므로, 다음 navigation에서 <HydrationBoundary>가 client query를 덮어씁니다:

Instead, cache only that timestamp and build the dehydrated state by hand. Wrap the time read in use cache with the same tags as the data reads. When a mutation invalidates those tags, the data and its timestamp advance together, so <HydrationBoundary> overwrites the client query on the next navigation:

TSJSapp/lib/hydrate.ts
import 'server-only'

import { cacheLife, cacheTag } from 'next/cache'
import {
  defaultShouldDehydrateQuery,
  QueryClient,
  type DehydratedState,
  type QueryKey,
} from '@tanstack/react-query'

type HydratedQuery = {
  queryKey: QueryKey
  data: unknown
}

type HydrationOptions = {
  tags: string[]
}

async function getHydrationUpdatedAt(tags: string[]) {
  'use cache'
  cacheTag(...tags)
  cacheLife('max')
  return Date.now()
}

export async function dehydrate(
  queries: HydratedQuery[],
  options: HydrationOptions
): Promise<DehydratedState> {
  const updatedAt = await getHydrationUpdatedAt(options.tags)

  const queryClient = new QueryClient()

  for (const query of queries) {
    queryClient.setQueryData(query.queryKey, query.data, { updatedAt })
  }

  return {
    mutations: [],
    queries: queryClient
      .getQueryCache()
      .getAll()
      .filter((query) => defaultShouldDehydrateQuery(query))
      .map((query) => ({
        dehydratedAt: updatedAt,
        queryHash: query.queryHash,
        queryKey: query.queryKey,
        state: query.state,
        ...(query.meta ? { meta: query.meta } : {}),
      })),
  }
}

데이터를 소유한 segment에서 helper를 await하고, 데이터와 함께 기반이 되는 getProduct read에 사용한 것과 같은 tag를 전달하세요. 결과는 ProductData 안에서 <HydrationBoundary>에 넘깁니다:

Await the helper in the segment that owns the data, passing the data and the same tags used on the underlying getProduct read. Hand the result to <HydrationBoundary> inside ProductData:

import { HydrationBoundary } from '@tanstack/react-query'
import { dehydrate } from '@/app/lib/hydrate'
import { getProduct } from './data'
import { productCache } from './product-cache'
import { ProductView } from './product-view'

async function ProductData({ id }: { id: string }) {
  const product = await getProduct(id)
  const state = await dehydrate(
    [{ queryKey: productCache.key(id), data: product }],
    { tags: [productCache.tag(id)] }
  )

  return (
    <HydrationBoundary state={state}>
      <ProductView id={id} />
    </HydrationBoundary>
  )
}

Good to know

timestamp는 hydrate된 데이터가 바뀔 때마다 갱신되어야 합니다. 이 helper는 같은 tag를 사용하므로 tag 기반 server 데이터에 적합합니다. 시간 기반 server 데이터의 경우, 서로 무관한 시간 window를 따로 유지하지 말고 같은 cache된 snapshot에서 데이터와 hydration timestamp를 함께 도출하세요.

The timestamp must advance whenever the hydrated data changes. The helper suits tag-driven server data because both use the same tags. For time-driven server data, derive the data and hydration timestamp from the same cached snapshot instead of maintaining unrelated time windows.
