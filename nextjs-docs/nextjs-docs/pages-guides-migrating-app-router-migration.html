Upgrading New Features새 기능 업그레이드

Next.js 13은 새로운 기능과 convention을 갖춘 새 App Router를 도입했습니다. 새 Router는 app directory에서 사용할 수 있으며 pages directory와 함께 공존합니다.

Next.js 13 introduced the new App Router with new features and conventions. The new Router is available in the app directory and co-exists with the pages directory.

Next.js 13으로 upgrade한다고 해서 App Router를 반드시 사용해야 하는 것은 아닙니다. 업데이트된 Image component, Link component, Script component, Font optimization처럼 두 directory 모두에서 동작하는 새 기능과 함께 pages를 계속 사용할 수 있습니다.

Upgrading to Next.js 13 does not require using the App Router. You can continue using pages with new features that work in both directories, such as the updated Image component, Link component, Script component, and Font optimization.

<Image/> Component

Next.js 12에서는 임시 import인 next/future/image로 Image Component의 새로운 개선 사항을 도입했습니다. 이 개선 사항에는 더 적은 client-side JavaScript, image를 확장하고 style을 입히는 더 쉬운 방법, 더 나은 accessibility, 브라우저 native lazy loading이 포함되었습니다.

Next.js 12 introduced new improvements to the Image Component with a temporary import: next/future/image. These improvements included less client-side JavaScript, easier ways to extend and style images, better accessibility, and native browser lazy loading.

버전 13에서는 이 새로운 동작이 next/image의 기본값이 되었습니다.

In version 13, this new behavior is now the default for next/image.

새 Image Component로 migrate하는 데 도움이 되는 codemod가 두 가지 있습니다:

There are two codemods to help you migrate to the new Image Component:

  • next-image-to-legacy-image codemod: next/image import를 next/legacy/image로 안전하게 자동으로 이름을 바꿉니다. 기존 component는 동작이 그대로 유지됩니다.
  • next-image-experimental codemod: inline style을 추가하고 사용하지 않는 props를 제거하는 위험한(dangerous) 작업을 합니다. 기존 component의 동작이 새 기본값에 맞게 바뀝니다. 이 codemod를 사용하려면 먼저 next-image-to-legacy-image codemod를 실행해야 합니다.
  • next-image-to-legacy-image codemod: Safely and automatically renames next/image imports to next/legacy/image. Existing components will maintain the same behavior.
  • next-image-experimental codemod: Dangerously adds inline styles and removes unused props. This will change the behavior of existing components to match the new defaults. To use this codemod, you need to run the next-image-to-legacy-image codemod first.

<Link> Component

<Link> Component에는 더 이상 child로 <a> tag를 직접 추가할 필요가 없습니다. 이 동작은 버전 12.2에서 experimental option으로 추가되었고 이제 기본값입니다. Next.js 13에서 <Link>는 항상 <a>를 render하며, props를 하위 tag로 전달(forward)할 수 있습니다.

The <Link> Component no longer requires manually adding an <a> tag as a child. This behavior was added as an experimental option in version 12.2 and is now the default. In Next.js 13, <Link> always renders <a> and allows you to forward props to the underlying tag.

예를 들면 다음과 같습니다:

For example:

import Link from 'next/link'

// Next.js 12: `<a>` has to be nested otherwise it's excluded
<Link href="/about">
  <a>About</a>
</Link>

// Next.js 13: `<Link>` always renders `<a>` under the hood
<Link href="/about">
  About
</Link>

link를 Next.js 13에 맞게 upgrade하려면 new-link codemod를 사용할 수 있습니다.

To upgrade your links to Next.js 13, you can use the new-link codemod.

<Script> Component

next/script의 동작이 pages와 app을 모두 지원하도록 업데이트되었지만, 매끄럽게 migrate하려면 몇 가지를 변경해야 합니다:

The behavior of next/script has been updated to support both pages and app, but some changes need to be made to ensure a smooth migration:

  • 이전에 _document.js에 넣었던 beforeInteractive script는 모두 app/layout.tsx나 app/[locale]/layout.tsx 같은 root layout으로 옮기세요.
  • experimental worker strategy는 아직 app에서 동작하지 않으므로, 이 strategy를 지정한 script는 제거하거나 다른 strategy(예: lazyOnload)를 사용하도록 수정해야 합니다.
  • onLoad, onReady, onError handler는 Server Component에서 동작하지 않으므로 Client Component로 옮기거나 완전히 제거하세요.
  • Move any beforeInteractive scripts you previously included in _document.js to a root layout, such as app/layout.tsx or app/[locale]/layout.tsx.
  • The experimental worker strategy does not yet work in app and scripts denoted with this strategy will either have to be removed or modified to use a different strategy (e.g. lazyOnload).
  • onLoad, onReady, and onError handlers will not work in Server Components so make sure to move them to a Client Component or remove them altogether.

Font OptimizationFont 최적화

이전에는 Next.js가 font CSS를 inline으로 넣어서 font 최적화를 도와주었습니다. 버전 13에서는 새 next/font module이 도입되었습니다. 이 module을 사용하면 뛰어난 performance와 privacy를 보장하면서도 font loading 경험을 customize할 수 있습니다. next/font는 pages와 app directory 모두에서 지원됩니다.

Previously, Next.js helped you optimize fonts by inlining font CSS. Version 13 introduces the new next/font module which gives you the ability to customize your font loading experience while still ensuring great performance and privacy. next/font is supported in both the pages and app directories.

CSS inline 방식은 pages에서는 여전히 동작하지만 app에서는 동작하지 않습니다. 대신 next/font를 사용해야 합니다.

While inlining CSS still works in pages, it does not work in app. You should use next/font instead.

next/font 사용 방법은 Font Optimization 페이지를 참고하세요.

See the Font Optimization page to learn how to use next/font.

Migrating from pages to apppages에서 app으로 migrate하기

🎥 Watch: App Router를 점진적으로 도입하는 방법을 알아보세요 → YouTube (16분).

🎥 Watch: Learn how to incrementally adopt the App Router → YouTube (16 minutes).

App Router로 옮기면서 Server Component, Suspense 등 Next.js가 기반으로 삼는 React 기능을 처음 사용하게 될 수도 있습니다. 여기에 special file과 layout 같은 새로운 Next.js 기능까지 더해지면, migration은 새로운 개념, mental model, 동작 변화를 익혀야 한다는 뜻이 됩니다.

Moving to the App Router may be the first time using React features that Next.js builds on top of such as Server Components, Suspense, and more. When combined with new Next.js features such as special files and layouts, migration means new concepts, mental models, and behavioral changes to learn.

migration을 더 작은 단계로 나누어 이런 업데이트가 겹치면서 생기는 복잡도를 줄이기를 권장합니다. app directory는 page 단위의 점진적 migration이 가능하도록 pages directory와 동시에 동작하게 의도적으로 설계되었습니다.

We recommend reducing the combined complexity of these updates by breaking down your migration into smaller steps. The app directory is intentionally designed to work simultaneously with the pages directory to allow for incremental page-by-page migration.

  • app directory는 nested route 와 layout을 지원합니다. 더 알아보기.
  • nested folder로 route를 정의하고, special page.js 파일로 route segment를 public하게 접근 가능하게 만듭니다. 더 알아보기.
  • Special file convention은 각 route segment의 UI를 만드는 데 사용됩니다. 가장 흔한 special file은 page.js와 layout.js입니다.
    • page.js로 route 고유의 UI를 정의합니다.
    • layout.js로 여러 route에서 공유하는 UI를 정의합니다.
    • special file에는 .js, .jsx, .tsx 파일 확장자를 사용할 수 있습니다.
  • app directory 안에 component, style, test 등 다른 파일을 함께 둘(colocate) 수 있습니다. 더 알아보기.
  • getServerSideProps와 getStaticProps 같은 data fetching 함수는 app 안에서 새 API로 대체되었습니다. getStaticPaths는 generateStaticParams로 대체되었습니다.
  • pages/_app.js와 pages/_document.js는 하나의 app/layout.js root layout으로 대체되었습니다. 더 알아보기.
  • pages/_error.js는 더 세분화된 error.js special file로 대체되었습니다. 더 알아보기.
  • pages/404.js는 not-found.js 파일로 대체되었습니다.
  • pages/api/* API Route는 route.js(Route Handler) special file로 대체되었습니다.
  • The app directory supports nested routes and layouts. Learn more.
  • Use nested folders to define routes and a special page.js file to make a route segment publicly accessible. Learn more.
  • Special file conventions are used to create UI for each route segment. The most common special files are page.js and layout.js.
    • Use page.js to define UI unique to a route.
    • Use layout.js to define UI that is shared across multiple routes.
    • .js, .jsx, or .tsx file extensions can be used for special files.
  • You can colocate other files inside the app directory such as components, styles, tests, and more. Learn more.
  • Data fetching functions like getServerSideProps and getStaticProps have been replaced with a new API inside app. getStaticPaths has been replaced with generateStaticParams.
  • pages/_app.js and pages/_document.js have been replaced with a single app/layout.js root layout. Learn more.
  • pages/_error.js has been replaced with more granular error.js special files. Learn more.
  • pages/404.js has been replaced with the not-found.js file.
  • pages/api/* API Routes have been replaced with the route.js (Route Handler) special file.

Migrating _document.js and _app.js_document.js와 _app.js migrate하기

기존 _app이나 _document 파일이 있다면 그 내용(예: global style)을 root layout(app/layout.tsx)으로 복사할 수 있습니다. app/layout.tsx의 style은 pages/*에는 적용되지 않습니다. migration 중에는 pages/* route가 깨지지 않도록 _app/_document를 유지해야 합니다. migration이 완전히 끝나면 안전하게 삭제할 수 있습니다.

If you have an existing _app or _document file, you can copy the contents (e.g. global styles) to the root layout (app/layout.tsx). Styles in app/layout.tsx will not apply to pages/*. You should keep _app/_document while migrating to prevent your pages/* routes from breaking. Once fully migrated, you can then safely delete them.

React Context provider를 사용하고 있다면 이를 Client Component로 옮겨야 합니다.

If you are using any React Context providers, they will need to be moved to a Client Component.

Migrating the getLayout() pattern to Layouts (Optional)getLayout() pattern을 Layout으로 migrate하기 (선택)

Step 1: Create a new Client Component

Step 1: Create a new Client Component

  • app directory 안에 Client Component를 export하는 별도의 새 파일(예: app/home-page.tsx 또는 비슷한 이름)을 만드세요. Client Component를 정의하려면 파일 맨 위(모든 import보다 앞)에 'use client' directive를 추가하세요.
    • Pages Router와 마찬가지로, 초기 page load 시 Client Component를 static HTML로 prerender하는 최적화 단계가 있습니다.
  • default export된 page component를 pages/index.js에서 app/home-page.tsx로 옮기세요.
  • Create a new separate file inside the app directory (i.e. app/home-page.tsx or similar) that exports a Client Component. To define Client Components, add the 'use client' directive to the top of the file (before any imports).
    • Similar to the Pages Router, there is an optimization step to prerender Client Components to static HTML on the initial page load.
  • Move the default exported page component from pages/index.js to app/home-page.tsx.

// It receives data as props, has access to state and effects, and is
// prerendered on the server during the initial page load.
export default function HomePage({ recentPosts }) {
  return (

  • asPath has been removed because the concept of as has been removed from the new router.

Step 6: Migrating Data Fetching Methods6단계: Data Fetching 메서드 migrate하기

pages directory는 page의 data를 fetch하기 위해 getServerSideProps와 getStaticProps를 사용합니다. app directory 안에서는 이 기존 data fetching 함수들이 fetch()와 async React Server Component 위에 만들어진 더 단순한 API로 대체됩니다.

The pages directory uses getServerSideProps and getStaticProps to fetch data for pages. Inside the app directory, these previous data fetching functions are replaced with a simpler API built on top of fetch() and async React Server Components.

TSJSapp/page.tsx
export default async function Page() {
  // Opt into the Next.js Data Cache for this request.
  // The cached response can be reused across requests and revalidated on demand.
  // Similar to `getStaticProps`.
  const cachedData = await fetch('https://...', { cache: 'force-cache' })

  // Opt out of caching for this request.
  // Next.js fetches this from the data source on every request.
  // This is the default fetch behavior.
  // Similar to `getServerSideProps`.
  const uncachedData = await fetch('https://...', { cache: 'no-store' })

  // Cache this request, but revalidate it at most every 10 seconds.
  // Similar to `getStaticProps` with the `revalidate` option.
  const revalidatedData = await fetch('https://...', {
    next: { revalidate: 10 },
  })

  return <div>...</div>
}

Dynamic paths (getStaticPaths)

pages directory에서 getStaticPaths 함수는 build 시점에 prerender해야 하는 dynamic path를 정의하는 데 사용됩니다.

In the pages directory, the getStaticPaths function is used to define the dynamic paths that should be prerendered at build time.

JSpages/posts/[id].js
// `pages` directory
import PostLayout from '@/components/post-layout'

export async function getStaticPaths() {
  return {
    paths: [{ params: { id: '1' } }, { params: { id: '2' } }],
  }
}

export async function getStaticProps({ params }) {
  const res = await fetch(`https://.../posts/${params.id}`)
  const post = await res.json()

  return { props: { post } }
}

export default function Post({ post }) {
  return <PostLayout post={post} />
}

app directory에서는 getStaticPaths가 generateStaticParams로 대체됩니다.

In the app directory, getStaticPaths is replaced with generateStaticParams.

generateStaticParams는 getStaticPaths와 비슷하게 동작하지만, route parameter를 반환하는 API가 단순해졌고 layout 안에서도 사용할 수 있습니다. generateStaticParams의 반환 형태는 중첩된 param object의 array나 resolve된 path string이 아니라 segment의 array입니다.

generateStaticParams behaves similarly to getStaticPaths, but has a simplified API for returning route parameters and can be used inside layouts. The return shape of generateStaticParams is an array of segments instead of an array of nested param objects or a string of resolved paths.

JSapp/posts/[id]/page.js
// `app` directory
import PostLayout from '@/components/post-layout'

export async function generateStaticParams() {
  return [{ id: '1' }, { id: '2' }]
}

async function getPost(params) {
  const res = await fetch(`https://.../posts/${(await params).id}`)
  const post = await res.json()

  return post
}

export default async function Post({ params }) {
  const post = await getPost(params)

  return <PostLayout post={post} />
}

app directory의 새로운 모델에는 getStaticPaths보다 generateStaticParams라는 이름이 더 적합합니다. get 접두사는 더 설명적인 generate로 바뀌었는데, 이제 getStaticProps와 getServerSideProps가 필요 없으므로 단독으로 쓰기에 더 잘 어울립니다. Paths 접미사는 Params로 바뀌었는데, 여러 dynamic segment가 있는 nested routing에 더 적합합니다.

Using the name generateStaticParams is more appropriate than getStaticPaths for the new model in the app directory. The get prefix is replaced with a more descriptive generate, which sits better alone now that getStaticProps and getServerSideProps are no longer necessary. The Paths suffix is replaced by Params, which is more appropriate for nested routing with multiple dynamic segments.

Replacing fallbackfallback 대체하기

pages directory에서는 getStaticPaths가 반환하는 fallback property로 build 시점에 prerender되지 않은 page의 동작을 정의합니다. 이 property를 true로 설정하면 page가 생성되는 동안 fallback page를 보여 주고, false로 설정하면 404 page를 보여 주며, blocking으로 설정하면 request 시점에 page를 생성합니다.

In the pages directory, the fallback property returned from getStaticPaths is used to define the behavior of a page that isn't prerendered at build time. This property can be set to true to show a fallback page while the page is being generated, false to show a 404 page, or blocking to generate the page at request time.

app directory에서는 config.dynamicParams property가 generateStaticParams 밖의 params를 처리하는 방식을 제어합니다:

In the app directory the config.dynamicParams property controls how params outside of generateStaticParams are handled:

  • true: (기본값) generateStaticParams에 포함되지 않은 dynamic segment는 요청 시(on demand) 생성됩니다.
  • false: generateStaticParams에 포함되지 않은 dynamic segment는 404를 반환합니다.
  • true: (default) Dynamic segments not included in generateStaticParams are generated on demand.
  • false: Dynamic segments not included in generateStaticParams will return a 404.

이는 pages directory에서 getStaticPaths의 fallback: true | false | 'blocking' option을 대체합니다. streaming에서는 'blocking'과 true의 차이가 무시할 만한 수준이므로 fallback: 'blocking' option은 dynamicParams에 포함되지 않았습니다.

This replaces the fallback: true | false | 'blocking' option of getStaticPaths in the pages directory. The fallback: 'blocking' option is not included in dynamicParams because the difference between 'blocking' and true is negligible with streaming.

  ...

With dynamicParams set to true (the default), when a route segment is requested that hasn't been generated, it will be server-rendered and cached.

  return posts.map((post) => <div>{post.name}</div>)
}

API Routes

API Route는 pages/api directory에서 아무 변경 없이 계속 동작합니다. 하지만 app directory에서는 Route Handler로 대체되었습니다.

API Routes continue to work in the pages/api directory without any changes. However, they have been replaced by Route Handlers in the app directory.

Route Handler를 사용하면 Web Request와 Response API로 특정 route에 대한 custom request handler를 만들 수 있습니다.

Route Handlers allow you to create custom request handlers for a given route using the Web Request and Response APIs.

TSJSapp/api/route.ts
export async function GET(request: Request) {}
export async function GET(request) {}
Good to know

이전에 client에서 외부 API를 호출하려고 API route를 사용했다면, 이제는 대신 Server Component로 data를 안전하게 fetch할 수 있습니다. data fetching에 대해 더 알아보세요.

If you previously used API routes to call an external API from the client, you can now use Server Components instead to securely fetch data. Learn more about data fetching.

Step 7: Styling7단계: Styling

pages directory에서는 global stylesheet를 pages/_app.js에서만 쓸 수 있도록 제한되어 있습니다. app directory에서는 이 제한이 없어졌습니다. global style은 어떤 layout, page, component에도 추가할 수 있습니다.

In the pages directory, global stylesheets are restricted to only pages/_app.js. With the app directory, this restriction has been lifted. Global styles can be added to any layout, page, or component.

Tailwind CSS

Tailwind CSS를 사용하고 있다면 tailwind.config.js 파일에 app directory를 추가해야 합니다:

If you're using Tailwind CSS, you'll need to add the app directory to your tailwind.config.js file:

JStailwind.config.js
module.exports = {
  content: [
    './app/**/*.{js,ts,jsx,tsx,mdx}', // <-- Add this line
    './pages/**/*.{js,ts,jsx,tsx,mdx}',
    './components/**/*.{js,ts,jsx,tsx,mdx}',
  ],
}

또한 app/layout.js 파일에서 global style을 import해야 합니다:

You'll also need to import your global styles in your app/layout.js file:

JSapp/layout.js
import '../styles/globals.css'

export default function RootLayout({ children }) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  )
}

Using App Router together with Pages RouterApp Router와 Pages Router 함께 사용하기

서로 다른 Next.js router가 제공하는 route 사이를 이동하면 hard navigation이 발생합니다. next/link의 자동 link prefetching은 router를 넘나들며 prefetch하지 않습니다.

When navigating between routes served by the different Next.js routers, there will be a hard navigation. Automatic link prefetching with next/link will not prefetch across routers.

대신 App Router와 Pages Router 사이의 navigation을 최적화해 prefetch와 빠른 page 전환을 유지할 수 있습니다. 더 알아보기.

Instead, you can optimize navigations between App Router and Pages Router to retain the prefetched and fast page transitions. Learn more.
