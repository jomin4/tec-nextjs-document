How Next.js preserves UI state with ActivityActivity로 UI state 보존하기

Good to know

이 가이드는 Cache Components가 활성화되어 있다고 가정합니다. Next config 파일에서 cacheComponents: true를 설정해 활성화하세요.

This guide assumes Cache Components is enabled. Enable it by setting cacheComponents: true in your Next config file.

Cache Components 이전에는 navigation 간에 page 수준의 state를 보존하려면 state를 공유 layout으로 끌어올리거나 external store를 사용하는 등의 우회 방법이 필요했습니다. Cache Components를 사용하면 Next.js가 기본으로(out of the box) state와 DOM을 보존합니다.

Before Cache Components, preserving page-level state across navigations required workarounds like hoisting state to a shared layout or using an external store. With Cache Components, Next.js preserves state and DOM out of the box.

Next.js는 navigation 시 page를 unmount하는 대신 React의 <Activity> component로 page를 숨깁니다. Activity는 DOM을 document 안에 그대로 두기 때문에(display: none으로 숨김) React state와 DOM state가 모두 보존됩니다. form 작성 중인 내용, scroll 위치, 펼쳐진 <details> element, video 재생 진행 상황 등이 그 예입니다.

Instead of unmounting pages on navigation, Next.js hides them using React's <Activity> component. Activity keeps the DOM in the document (hidden with display: none), so both React state and DOM state are preserved: form drafts, scroll positions, expanded <details> elements, video playback progress, and more.

Next.js는 최대 3개의 route를 보존합니다. 그 이상이 되면 가장 오래된 route가 제거(evict)되고 다음에는 새로 re-render됩니다.

Next.js preserves up to 3 routes. Beyond that, the oldest route is evicted and will re-render fresh.

Good to know

useRouter().bfcacheId를 React key로 사용하세요. <Fragment key={bfcacheId}> 하나로 push 또는 replace navigation(<Link> 클릭과 router.push / router.replace 포함) 시에는 subtree 전체를 reset하면서, 브라우저 뒤로/앞으로 이동 시에는 여전히 state를 복원할 수 있습니다. bfcacheId는 주로 migration 용도의 도구입니다. 새 코드에서는 아래의 pattern별 reset 방법을 권장합니다.

Use useRouter().bfcacheId as a React key: a single <Fragment key={bfcacheId}> resets an entire subtree on push or replace navigations (including <Link> clicks and router.push / router.replace) while still restoring state on browser back/forward. bfcacheId is mainly a migration tool. For new code, prefer the per-pattern resets below.

Choosing what to preserve무엇을 보존할지 선택하기

Activity는 기본적으로 모든 component state와 DOM state를 보존합니다. 각 state마다 그것이 UI에 맞는 동작인지는 직접 판단해야 합니다. 아래 pattern들은 흔한 시나리오와, 보존할 때와 reset할 때 양쪽을 어떻게 처리하는지 보여 줍니다.

Activity preserves all component state and DOM state by default. For each piece of state, you decide whether that's the right behavior for your UI. The patterns below show common scenarios and how to handle both sides.

Expandable UI (dropdowns, accordions, panels)펼침 UI (dropdown, accordion, panel)

사용자가 다른 곳으로 navigate했다가 돌아오면, Activity는 펼침 element의 열림/닫힘 state를 보존합니다.

When a user navigates away and returns, Activity preserves the open/closed state of expandable elements.

When to keep it: 섹션이 펼쳐진 sidebar, FAQ accordion, filter panel 등입니다. 사용자가 의도적으로 화면을 구성해 둔 것이므로, 이를 복원하면 같은 작업을 다시 하지 않아도 됩니다.

When to keep it: A sidebar with expanded sections, a FAQ accordion, or a filters panel. The user set up their view intentionally, and restoring it avoids re-doing that work.

When to reset it: 버튼 클릭으로 열리는 dropdown menu나 popover입니다. 이런 것은 일시적인 interaction이지, 계속 유지되는 화면 state가 아닙니다. page에 돌아왔을 때 dropdown이 이미 열려 있으면 사용자에게 친절하지 않습니다.

When to reset it: A dropdown menu or popover triggered by a button click. These are transient interactions, not persistent view state. Returning to a page with a dropdown already open is not user friendly.

일시적인 열림/닫힘 state를 reset하려면 useLayoutEffect cleanup 함수에서 닫으세요:

To reset transient open/closed state, close it in a useLayoutEffect cleanup function:

'use client'

import { useState, useLayoutEffect } from 'react'

function SettingsDropdown() {
  const [isOpen, setIsOpen] = useState(false)

  // Close dropdown when this component becomes hidden
  useLayoutEffect(() => {
    return () => {
      setIsOpen(false)
    }
  }, [])

  return (
    <div>
      <button onClick={() => setIsOpen((o) => !o)}>Options</button>
      {isOpen && (
        <ul>
          <li>
            <button>Edit Profile</button>
          </li>
          <li>
            <button>Change Password</button>
          </li>
        </ul>
      )}
    </div>
  )
}

Activity가 이 component를 숨기면 cleanup 함수가 실행되어 isOpen을 reset합니다. page가 다시 보이게 되면 dropdown은 닫혀 있습니다. useLayoutEffect를 사용하면 component가 숨겨지기 전에 cleanup이 동기적으로 실행되므로, 오래된(stale) state가 잠깐 깜빡이는 현상을 막을 수 있습니다.

When Activity hides this component, the cleanup function runs and resets isOpen. When the page becomes visible again, the dropdown is closed. Using useLayoutEffect ensures the cleanup runs synchronously before the component is hidden, avoiding any flash of stale state.

Link의 onNavigate callback을 사용해 navigation link가 클릭되는 즉시 dropdown을 닫을 수도 있습니다.

You can also use Link's onNavigate callback to close dropdowns immediately when a navigation link is clicked.

Dialog and initialization logicDialog와 초기화 로직

Activity는 dialog의 열림/닫힘 state를 보존합니다. 이는 그 state를 기반으로 실행되는 Effect에도 영향을 줍니다.

Activity preserves dialog open/closed state. This also affects Effects that run based on that state.

When to keep it: 사용자가 작업 중이던 multi-step wizard나 settings panel입니다. 현재 단계와 입력 state를 보존하면 진행 상황을 잃지 않습니다.

When to keep it: A multi-step wizard or a settings panel that the user was actively working in. Preserving the step and input state avoids losing progress.

When to reset it: 열릴 때마다 초기화 로직(예: input에 focus 주기)을 실행하는 dialog입니다. dialog가 열린 상태에서 사용자가 다른 곳으로 navigate하면, Activity는 isDialogOpen: true를 보존합니다. 다시 열면 이미 true인 값을 true로 설정하므로 state 변화가 일어나지 않고 Effect도 다시 실행되지 않습니다.

When to reset it: A dialog that runs initialization logic (like focusing an input) each time it opens. If the user navigated away while the dialog was open, Activity preserves isDialogOpen: true. Opening it again sets it to true when it's already true, so no state change happens and the Effect doesn't re-run.

다음 예제를 보세요:

Consider this example:

'use client'

import { useState, useRef, useEffect } from 'react'

function ProductTab() {
  const [isDialogOpen, setIsDialogOpen] = useState(false)
  const inputRef = useRef<HTMLInputElement>(null)

  useEffect(() => {
    if (isDialogOpen) {
      inputRef.current?.focus()
    }
  }, [isDialogOpen])

  // ...
}

dialog가 열린 상태에서 사용자가 다른 곳으로 navigate했다면, 돌아와서 dialog를 열어도 isDialogOpen이 이미 true였기 때문에 focus Effect가 실행되지 않습니다.

If the user navigated away while the dialog was open, returning and opening the dialog won't trigger the focus Effect because isDialogOpen was already true.

이를 해결하려면 dialog state를 search param처럼 보존되는 component state 바깥의 무언가로부터 도출(derive)하세요:

To fix this, derive the dialog state from something outside the preserved component state like a search param:

'use client'

import { useSearchParams, useRouter } from 'next/navigation'
import { useEffect, useRef } from 'react'

function ProductTab() {
  const searchParams = useSearchParams()
  const router = useRouter()
  const isDialogOpen = searchParams.get('edit') === 'true'
  const inputRef = useRef<HTMLInputElement>(null)

  useEffect(() => {
    if (isDialogOpen) {
      inputRef.current?.focus()
    }
  }, [isDialogOpen])

  return (
    <div>
      <button onClick={() => router.push('?edit=true')}>Edit Product</button>

      {isDialogOpen && (
        <dialog open>
          <input ref={inputRef} placeholder="Product name" />
          <button onClick={() => router.replace('?', { scroll: false })}>
            Close
          </button>
        </dialog>
      )}
    </div>
  )
}

이 방식에서는 isDialogOpen이 component state가 아니라 URL로부터 도출됩니다. 다른 곳으로 navigate했다가 돌아오면 search param이 비워지므로(URL이 바뀌었기 때문에) isDialogOpen은 false가 됩니다. dialog를 열면 param이 설정되고, 이것이 isDialogOpen을 바꾸어 Effect를 실행시킵니다.

With this approach, isDialogOpen derives from the URL rather than component state. When navigating away and returning, the search param is cleared (the URL changed), so isDialogOpen becomes false. Opening the dialog sets the param, which changes isDialogOpen and triggers the Effect.

Forms, inputs, and stateForm, input, state

Activity는 navigation 간에 form input 값(text field, 선택된 option, checkbox state), 제출 결과, 상태 메시지를 보존합니다.

Activity preserves form input values (text fields, selected options, checkbox states), submission results, and status messages across navigations.

When to keep it: filter가 있는 검색 page, 사용자가 작성 중이던 초안, 저장하지 않은 변경 사항이 있는 settings form입니다. 사용자가 작업을 잃지 않으므로, 입력 state 보존은 가장 큰 UX 이점 중 하나입니다.

When to keep it: A search page with filters, a draft the user was composing, or a settings form with unsaved changes. Preserving input state is one of the biggest UX wins because the user doesn't lose work.

When to reset it: 방문할 때마다 새로 시작해야 하는 "new transaction" flow, 또는 오래된 성공/오류 메시지가 새로운 맥락에서 혼란을 줄 수 있는 form입니다.

When to reset it: A "new transaction" flow where each visit should start fresh, or a form where stale success/error messages would be confusing in a new context.

Resetting form state on submit제출 시 form state reset하기

사용자가 새 항목을 만드는 page를 생각해 보세요. 제출 후 router.push가 새 record로 navigate합니다. Activity가 page를 보존하므로, 뒤로 navigate하면 이전에 입력한 이름이 form에 그대로 남아 있습니다. form을 새 상태로 유지하려면 event handler에서 state를 reset하세요:

Consider a page where the user creates a new item. After submitting, router.push navigates to the new record. Since Activity preserves the page, navigating back shows the previous name still in the form. Reset state in the event handler to keep the form fresh:

TSapp/new/page.tsx
'use client'

import { useState } from 'react'
import { useRouter } from 'next/navigation'

export default function NewItemPage() {
  const [name, setName] = useState('')
  const router = useRouter()

  async function handleSubmit(e: React.SubmitEvent<HTMLFormElement>) {
    e.preventDefault()
    const item = await createItem({ name })
    setName('')
    router.push(`/items/${item.id}`)
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={name} onChange={(e) => setName(e.target.value)} />
      <button type="submit">Create</button>
    </form>
  )
}

Resetting stale status messages오래된 상태 메시지 reset하기

제출 후 feedback 메시지를 render하기 위해 state에 status를 설정했다면, 이를 지울 만한 믿을 수 있는 사용자 주도 event가 없는 경우가 많습니다.

If after submitting you set a status into state to render a feedback message, there's often not a reliable user-initiated event to clear it.

사용자는 직접 제어할 수 없는 next/link element나 브라우저 컨트롤로 navigate할 수도 있습니다.

The user might navigate via next/link elements out of your control, or via browser controls.

form으로 다시 navigate하면 오래된 메시지가 보입니다. 이 경우 useLayoutEffect cleanup을 사용해 form과 state를 reset할 수 있습니다:

Navigating back to the form shows a stale message. In this case, you may use a useLayoutEffect cleanup to reset the form and state:

'use client'

import { useState, useRef, useLayoutEffect } from 'react'

function ContactForm() {
  const [name, setName] = useState('')
  const [status, setStatus] = useState<'idle' | 'success'>('idle')
  const shouldReset = useRef(false)

  async function handleSubmit(e: React.SubmitEvent<HTMLFormElement>) {
    e.preventDefault()
    await sendMessage({ name })
    setStatus('success')
    shouldReset.current = true
  }

  // Reset stale success message when Activity hides this component
  useLayoutEffect(() => {
    return () => {
      if (shouldReset.current) {
        shouldReset.current = false
        setStatus('idle')
        setName('')
      }
    }
  }, [])

  return (
    <form onSubmit={handleSubmit}>
      <input value={name} onChange={(e) => setName(e.target.value)} />
      <button type="submit">Send</button>
      {status === 'success' && <p>Message sent!</p>}
    </form>
  )
}

shouldReset ref는 제출이 성공한 뒤에만 cleanup이 실행되도록 보장합니다. 사용자가 제출하지 않고 작성 도중에 다른 곳으로 navigate하면 입력 내용은 보존됩니다.

The shouldReset ref ensures the cleanup only runs after a successful submission. If the user navigates away mid-draft without submitting, their input is preserved.

useActionState를 사용한다면 같은 방식이 적용됩니다. reducer에 RESET action을 추가하는 방법은 React 문서의 Reset state를 참고하세요. 이 hook들로 반응성 좋은 interaction을 만드는 방법은 Building interactive apps 가이드를 참고하세요.

If you use useActionState, the same approach applies. See Reset state in the React docs for how to add a RESET action to your reducer. For more on building responsive interactions with these hooks, see the Building interactive apps guide.

callback ref로 모든 form field reset하기

callback ref를 사용해 Activity가 component를 숨길 때 form.reset()을 호출할 수 있습니다:

<form
  ref={(form) => {
    return () => form?.reset()
  }}
>
  <input name="email" />
  <input name="message" />
  <button type="submit">Send</button>
</form>

이렇게 하면 사용자가 다른 곳으로 navigate할 때마다 모든 field가 reset됩니다.

State and authenticationState와 인증

Activity는 인증 변경을 포함해 navigation 간에 local component state(useState, DOM input 값)를 보존합니다. 이는 표준 React 동작입니다. props가 바뀌면(예: 새 user를 받는 경우) re-render가 일어나지만 기존 state는 reset되지 않습니다. 한 사용자가 작성한 초안이 다른 사용자에게 보여서는 안 됩니다.

Activity preserves local component state (useState, DOM input values) across navigations, including authentication changes. This is standard React behavior: props changing (such as receiving a new user) triggers a re-render but does not reset existing state. A draft composed by one user shouldn't be visible to another.

logout flow에서는 router.push 대신 window.location.href를 사용하면 전체 page reload가 일어나 모든 client-side state가 지워집니다.

For logout flows, using window.location.href instead of router.push triggers a full page reload, clearing all client-side state.

전체 reload 없이 사용자가 바뀔 때 특정 state를 reset하려면:

To reset specific state when the user changes without a full reload:

'use client'

import { useState, useEffect, useRef } from 'react'

function UserScopedForm({ userId }: { userId: string | null }) {
  const [draft, setDraft] = useState('')
  const lastUserIdRef = useRef<string | null>(null)

  useEffect(() => {
    if (lastUserIdRef.current !== null && lastUserIdRef.current !== userId) {
      setDraft('') // Reset on user change
    }
    lastUserIdRef.current = userId
  }, [userId])

  return <textarea value={draft} onChange={(e) => setDraft(e.target.value)} />
}

또는 user ID를 component의 key로 지정해 React가 reset을 처리하게 할 수 있습니다: <Form key={userId} />.

Alternatively, key components by user ID to let React handle the reset: <Form key={userId} />.

Global stylesGlobal style

page 수준의 style(CSS variable, z-index, global class)은 그 style을 만든 component가 Activity에 의해 숨겨졌을 때도 보이는 page에 영향을 줄 수 있습니다. 숨겨졌을 때는 이를 비활성화하는 것이 좋습니다. 숨겨진 page의 accent color나 z-index override가 보이는 page로 새어 나와서는 안 됩니다.

Page-level styles (CSS variables, z-index, global classes) can affect visible pages when the originating component is hidden by Activity. You likely want to disable them when hidden: a hidden page's accent color or z-index overrides shouldn't leak into the visible page.

callback ref를 사용해 stylesheet의 media attribute를 전환하세요:

Use a callback ref to toggle the stylesheet's media attribute:

<style
  ref={(style) => {
    if (style) style.media = '' // Enable when visible
    return () => {
      if (style) style.media = 'not all' // Disable when hidden
    }
  }}
>
  {`:root { --page-accent: blue; }`}
</style>

또는 여러 style element를 관리하거나 더 복잡한 cleanup이 필요하면 useLayoutEffect를 사용하세요:

Or use useLayoutEffect when managing multiple style elements or more complex cleanup:

'use client'

import { useLayoutEffect, useRef } from 'react'

function PageWithStyles() {
  const styleRef = useRef<HTMLStyleElement>(null)

  useLayoutEffect(() => {
    if (styleRef.current) styleRef.current.media = ''
    return () => {
      if (styleRef.current) styleRef.current.media = 'not all'
    }
  }, [])

  return <style ref={styleRef}>{`:root { --page-accent: blue; }`}</style>
}

Activity가 component를 숨기면 cleanup이 media="not all"을 설정해 stylesheet를 비활성화합니다. 다시 보이게 되면 effect가 다시 실행되어 media를 reset하고 stylesheet를 활성화합니다.

When Activity hides the component, the cleanup sets media="not all", which disables the stylesheet. When visible again, the effect re-runs and resets media to enable it.

The :has selector:has selector

:root:has(...) rule은 selector를 기준으로 style을 적용합니다. 선택된 element도, match된 element도 그 관계를 알지 못합니다. 유효한 CSS이긴 하지만 React의 data flow를 우회하고 서로 관련 없는 component를 결합시킵니다.

A :root:has(...) rule applies styles based on its selector. Neither the selected element nor the matched element knows about the relationship. It's valid CSS, but it bypasses React's data flow and couples unrelated components.

global state에는 React가 소유하는 data-* attribute를 사용하는 것이 좋습니다:

For global state, prefer a data-* attribute that React owns:

<html data-modal-open={modalOpen ? "true" : undefined}>
html[data-modal-open='true'] {
  overflow: hidden;
}

:has()는 component 내부의 local한 parent/child styling에만 사용하세요:

Reserve :has() for local parent/child styling within a component:

.card:has(img) {
  padding-top: 0;
}

이것은 React data flow나 Next.js만의 문제가 아닙니다. 범위가 넓은 :has() selector는 실제 performance 병목이 됩니다. MDN의 Performance considerations를 참고하세요.

This isn't only a React data-flow or Next.js concern. Broad :has() selectors are a real performance bottleneck. See Performance considerations on MDN.

Good to know

숨겨진 component 자체가 global :has rule을 정의한다면, 위 섹션의 전환 방식이 component의 다른 style과 함께 그 rule도 비활성화합니다.

If the hidden component itself defines the global :has rule, the toggle from the section above disables it along with the component's other styles.

Testing테스트

숨겨진 Activity 콘텐츠는 display: none 상태이지만 document 안에 남아 있습니다. 이는 Cache Components가 보존하는 route와 <Activity>로 직접 숨긴 콘텐츠 모두에 해당합니다. 이 점은 Playwright, Cypress, Puppeteer 같은 도구를 사용한 end-to-end 테스트에 영향을 줍니다:

Hidden Activity content has display: none but remains in the document. This applies both to routes preserved by Cache Components and to content you hide with <Activity> directly. It affects end-to-end testing with tools like Playwright, Cypress, or Puppeteer:

  • DOM query가 숨겨진 element를 찾을 수 있습니다. selector는 visibility와 관계없이 element를 match할 수 있습니다.
  • 숨겨진 element와의 interaction은 실패하거나 time out됩니다. 대부분의 도구는 interaction 전에 element가 보이게 될 때까지 기다리지만, 기다린다고 해서 보이는 element와 숨겨진 element를 모두 match하는 query가 좁혀지지는 않습니다. Playwright는 이를 strict mode violation으로 보고합니다.
  • assertion이 숨겨진 콘텐츠를 match할 수 있습니다. element의 존재를 assert할 때는 visibility를 명시적으로 지정하세요.
  • DOM queries can find hidden elements. Selectors may match elements regardless of visibility.
  • Interactions with hidden elements fail or time out. Most tools wait for an element to become visible before interacting, but waiting doesn't narrow a query that matches both a visible and a hidden element. Playwright reports this as a strict mode violation.
  • Assertions may match hidden content. Be explicit about visibility when asserting element presence.

Use visibility-aware selectorsvisibility를 고려하는 selector 사용하기

숨겨진 element를 제외하는 accessibility tree를 query하는 locator를 사용하거나, 동작을 수행하기 전에 visibility로 match 결과를 filter하세요. Playwright에서 getByRole query는 기본적으로 숨겨진 element를 제외합니다:

Prefer locators that query the accessibility tree, which leaves out hidden elements, or filter matches by visibility before acting on them. In Playwright, getByRole queries exclude hidden elements by default:

// Good - getByRole excludes hidden elements by default
await page.getByRole('button', { name: 'Submit' }).click()
await page.getByRole('textbox', { name: 'Email' }).fill('test@example.com')

getByLabel, getByPlaceholder, .locator()를 포함한 다른 locator는 숨겨진 element를 match할 수 있습니다. visibility로 명시적으로 filter하세요:

Other locators, including getByLabel, getByPlaceholder, and .locator(), can match hidden elements. Filter them by visibility explicitly:

// Filter by visibility explicitly
await page
  .getByLabel('Email')
  .filter({ visible: true })
  .fill('test@example.com')
await page.getByPlaceholder('Search...').filter({ visible: true }).fill('query')
await page.locator('.product-card').filter({ visible: true }).first().click()
await page
  .locator('[data-testid="timer"]')
  .filter({ visible: true })
  .textContent()

// Avoid - may match hidden elements in Activity boundaries
await page.getByLabel('Email').fill('test@example.com')
await page.locator('.product-card').first().click()

getByRole은 Activity, tab navigation, accordion 등 숨겨진 콘텐츠를 DOM에 유지하는 모든 pattern에 견고합니다. 숨겨진 element를 제외하는 accessibility tree를 query하기 때문입니다. 어떤 locator가 숨겨진 element를 match하는지는 테스트 도구와 버전마다 다르므로, 사용하는 도구의 문서에서 locator와 test helper를 확인하세요.

getByRole is robust to Activity, tabbed navigation, accordions, and any other pattern that keeps hidden content in the DOM. It queries the accessibility tree, which excludes hidden elements. Which locators match hidden elements varies between testing tools and their versions, so check your tool's documentation for its locators and test helpers to confirm.

Using Activity in your components직접 만든 component에서 Activity 사용하기

Cache Components는 route 수준에서 Activity를 자동으로 사용하지만, 직접 만든 component에서도 <Activity>를 바로 사용할 수 있습니다. tab, 펼침 panel처럼 unmount하지 않고 콘텐츠를 숨기고 싶은 모든 UI에 유용합니다.

Cache Components uses Activity automatically at the route level, but you can also use <Activity> directly in your own components. This is useful for tabs, expandable panels, or any UI where you want to hide content without unmounting it.

Prerendering hidden content숨겨진 콘텐츠 prerender하기

Activity는 사용자가 아직 보지 않은 콘텐츠를 prerender할 수 있습니다. 숨겨진 boundary는 낮은 우선순위로 render됩니다. Suspense와 함께 사용하면, 사용자가 다음에 볼 가능성이 높은 콘텐츠의 data를 prefetch할 수 있습니다.

Activity can prerender content the user hasn't seen yet. Hidden boundaries render at lower priority. Combined with Suspense, this lets you prefetch data for content the user is likely to view next.

Server Component는 즉시 data fetching을 시작하고 promise를 client component에 전달할 수 있습니다. client component는 사용자가 요청할 때까지 Activity로 콘텐츠를 숨기고, render할 때 use()로 promise를 resolve합니다:

A Server Component can start fetching data immediately and pass the promise to a client component. The client component uses Activity to hide the content until the user requests it, and use() to resolve the promise when rendering:

TSapp/page.tsx
import { Suspense } from 'react'
import { ExpandableComments } from './expandable-comments'

async function getCommentsData() {
  return db.comments.findMany()
}

export default function Page() {
  const commentsPromise = getCommentsData()

  return (
    <article>
      <h1>Post Title</h1>
      <p>Main content visible immediately...</p>

      <ExpandableComments commentsPromise={commentsPromise} />
    </article>
  )
}
TSapp/expandable-comments.tsx
'use client'

import { Activity, Suspense, useState, use } from 'react'

type Comment = { id: string; text: string; author: string }

export function ExpandableComments({
  commentsPromise,
}: {
  commentsPromise: Promise<Comment[]>
}) {
  const [expanded, setExpanded] = useState(false)

  return (
    <>
      <button onClick={() => setExpanded((e) => !e)}>
        {expanded ? 'Hide Comments' : 'Show Comments'}
      </button>

      <Activity mode={expanded ? 'visible' : 'hidden'}>
        <Suspense fallback={<CommentsSkeleton />}>
          <Comments commentsPromise={commentsPromise} />
        </Suspense>
      </Activity>
    </>
  )
}

function Comments({
  commentsPromise,
}: {
  commentsPromise: Promise<Comment[]>
}) {
  const comments = use(commentsPromise)
  return (
    <ul>
      {comments.map((c) => (
        <li key={c.id}>{c.text}</li>
      ))}
    </ul>
  )
}

function CommentsSkeleton() {
  return <div>Loading comments...</div>
}

Server Component는 즉시 comment fetching을 시작하고 promise를 아래로 전달합니다. 숨겨져 있는 동안 data는 낮은 우선순위로 stream됩니다. 사용자가 "Show Comments"를 클릭하면 Comments component가 use()로 promise를 resolve하고 콘텐츠가 즉시 나타납니다.

The Server Component starts fetching comments immediately and passes the promise down. While hidden, the data streams at lower priority. When the user clicks "Show Comments", the Comments component resolves the promise with use() and the content appears instantly.

Effect and media cleanupEffect와 media cleanup

Activity가 콘텐츠를 숨기면 React는 unmount할 때와 똑같이 effect cleanup 함수를 실행합니다. 즉, cleanup을 제대로 작성해 두었다면 timer, subscription, media 재생이 자동으로 일시 정지됩니다:

When Activity hides content, React runs effect cleanup functions just like it does on unmount. This means timers, subscriptions, and media playback pause automatically if you have proper cleanup:

'use client'

import { useEffect, useState } from 'react'

function LiveTimer() {
  const [count, setCount] = useState(0)

  useEffect(() => {
    const id = setInterval(() => setCount((c) => c + 1), 1000)
    return () => clearInterval(id) // Pauses when hidden
  }, [])

  return <p>Count: {count}</p>
}

<video>, <audio> 같은 media element는 display: none으로 재생이 멈추지 않습니다. useLayoutEffect로 명시적인 cleanup을 추가하세요:

For media elements like <video> and <audio>, display: none does not stop playback. Add explicit cleanup with useLayoutEffect:

'use client'

import { useLayoutEffect, useRef } from 'react'

function VideoPlayer({ src }: { src: string }) {
  const videoRef = useRef<HTMLVideoElement>(null)

  useLayoutEffect(() => {
    const video = videoRef.current
    return () => {
      video?.pause() // Pauses when hidden, preserves playback position
    }
  }, [])

  return <video ref={videoRef} src={src} controls />
}

component가 다시 보이게 되면 effect가 다시 실행되고, DOM node가 제거된 적이 없으므로 재생 위치도 보존됩니다.

When the component becomes visible again, effects re-run and playback position is preserved since the DOM node was never removed.

Distinguishing first mount from re-show첫 mount와 다시 보이기 구분하기

Effect는 최초 mount뿐 아니라 숨김에서 보임으로 바뀔 때마다 실행됩니다. 첫 mount와 이후의 visibility 변화를 구분해야 한다면 ref를 사용하세요:

Effects run on every hide-to-visible transition, not just the initial mount. If you need to distinguish the first mount from subsequent visibility changes, use a ref:

'use client'

import { useEffect, useRef } from 'react'

function TrackedComponent() {
  const hasMountedRef = useRef(false)

  useEffect(() => {
    if (!hasMountedRef.current) {
      hasMountedRef.current = true
      console.log('First mount')
    } else {
      console.log('Became visible again')
    }
  }, [])

  return <div>...</div>
}

ref는 숨김/보임 사이클을 거쳐도 유지되므로(ref는 cleanup되지 않음) 첫 mount 이후 hasMountedRef.current는 계속 true로 남습니다. Activity가 보이게 될 때마다 Effect가 다시 실행되지만, 이제는 else branch로 갑니다.

The ref persists across hide/show cycles (refs aren't cleaned up), so hasMountedRef.current stays true after the first mount. Each time Activity becomes visible, the Effect runs again, but now it takes the else branch.
