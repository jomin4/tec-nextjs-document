getStaticPropsgetStaticProps

getStaticProps라는 함수를 export하면, 이 함수가 반환한 props를 사용해 build time에 page를 prerender합니다:

Exporting a function called getStaticProps will prerender a page at build time using the props returned from the function:

TSJSpages/index.tsx
import type { InferGetStaticPropsType, GetStaticProps } from 'next'

type Repo = {
  name: string
  stargazers_count: number
}

export const getStaticProps = (async (context) => {
  const res = await fetch('https://api.github.com/repos/vercel/next.js')
  const repo = await res.json()
  return { props: { repo } }
}) satisfies GetStaticProps<{
  repo: Repo
}>

export default function Page({
  repo,
}: InferGetStaticPropsType<typeof getStaticProps>) {
  return repo.stargazers_count
}
export async function getStaticProps() {
  const res = await fetch('https://api.github.com/repos/vercel/next.js')
  const repo = await res.json()
  return { props: { repo } }
}

export default function Page({ repo }) {
  return repo.stargazers_count
}

getStaticProps에서 사용할 module을 top-level scope에서 import할 수 있습니다. 여기서 사용된 import는 client-side용으로 bundle되지 않습니다. 즉, database에서 data를 가져오는 것을 포함해 server-side 코드를 getStaticProps 안에 직접 작성할 수 있습니다.

You can import modules in top-level scope for use in getStaticProps. Imports used will not be bundled for the client-side. This means you can write server-side code directly in getStaticProps, including fetching data from your database.

Context parameter

context parameter는 다음 key를 담고 있는 object입니다:

The context parameter is an object containing the following keys:

preview(draftMode로 대체되어 Deprecated) page가 Preview Mode이면 preview는 true, 그렇지 않으면 false입니다.

getStaticProps return valuesgetStaticProps 반환 값

getStaticProps 함수는 props, redirect, notFound 중 하나와, 그 뒤에 선택 사항인 revalidate property를 담은 object를 반환해야 합니다.

The getStaticProps function should return an object containing either props, redirect, or notFound followed by an optional revalidate property.

props

props object는 key-value 쌍이며, 각 value는 page component가 전달받습니다. 전달되는 모든 props가 JSON.stringify로 serialize될 수 있도록 serializable object여야 합니다.

The props object is a key-value pair, where each value is received by the page component. It should be a serializable object so that any props passed, could be serialized with JSON.stringify.

export async function getStaticProps(context) {
  return {
    props: { message: `Next.js is awesome` }, // will be passed to the page component as props
  }
}

revalidate

revalidate property는 page 재생성(re-generation)이 일어날 수 있기까지의 시간(초)입니다(기본값은 false, 즉 revalidation 없음).

The revalidate property is the amount in seconds after which a page re-generation can occur (defaults to false or no revalidation).

// This function gets called at build time on server-side.
// It may be called again, on a serverless function, if
// revalidation is enabled and a new request comes in
export async function getStaticProps() {
  const res = await fetch('https://.../posts')
  const posts = await res.json()

  return {
    props: {
      posts,
    },
    // Next.js will attempt to re-generate the page:
    // - When a request comes in
    // - At most once every 10 seconds
    revalidate: 10, // In seconds
  }
}

Incremental Static Regeneration에 대해 더 알아보세요.

Learn more about Incremental Static Regeneration.

ISR을 활용하는 page의 cache 상태는 x-nextjs-cache response header 값을 읽어서 확인할 수 있습니다. 가능한 값은 다음과 같습니다:

The cache status of a page leveraging ISR can be determined by reading the value of the x-nextjs-cache response header. The possible values are the following:

  • MISS - path가 cache에 없음 (첫 방문 시 최대 한 번 발생)
  • STALE - path가 cache에 있지만 revalidate 시간을 초과했으므로 background에서 업데이트됨
  • HIT - path가 cache에 있고 revalidate 시간을 초과하지 않음
  • MISS - the path is not in the cache (occurs at most once, on the first visit)
  • STALE - the path is in the cache but exceeded the revalidate time so it will be updated in the background
  • HIT - the path is in the cache and has not exceeded the revalidate time

notFound

notFound boolean을 사용하면 page가 404 status와 404 Page를 반환할 수 있습니다. notFound: true이면 이전에 성공적으로 생성된 page가 있었더라도 page는 404를 반환합니다. 이는 사용자가 생성한 콘텐츠를 작성자가 삭제하는 것과 같은 use case를 지원하기 위한 것입니다. 참고로 notFound는 여기에서 설명한 것과 동일한 revalidate 동작을 따릅니다.

The notFound boolean allows the page to return a 404 status and 404 Page. With notFound: true, the page will return a 404 even if there was a successfully generated page before. This is meant to support use cases like user-generated content getting removed by its author. Note, notFound follows the same revalidate behavior described here.

export async function getStaticProps(context) {
  const res = await fetch(`https://.../data`)
  const data = await res.json()

  if (!data) {
    return {
      notFound: true,
    }
  }

  return {
    props: { data }, // will be passed to the page component as props
  }
}
Good to know

fallback: false mode에서는 getStaticPaths에서 반환된 path만 prerender되므로 notFound가 필요하지 않습니다.

notFound is not needed for fallback: false mode as only paths returned from getStaticPaths will be prerendered.

redirect

redirect object를 사용하면 내부 또는 외부 resource로 redirect할 수 있습니다. { destination: string, permanent: boolean } 형태와 일치해야 합니다.

The redirect object allows redirecting to internal or external resources. It should match the shape of { destination: string, permanent: boolean }.

드물게 오래된 HTTP client가 제대로 redirect하도록 custom status code를 지정해야 할 수도 있습니다. 이런 경우 permanent property 대신 statusCode property를 사용할 수 있지만, 둘을 함께 사용할 수는 없습니다. 또한 next.config.js의 redirects와 마찬가지로 basePath: false를 설정할 수도 있습니다.

In some rare cases, you might need to assign a custom status code for older HTTP clients to properly redirect. In these cases, you can use the statusCode property instead of the permanent property, but not both. You can also set basePath: false similar to redirects in next.config.js.

export async function getStaticProps(context) {
  const res = await fetch(`https://...`)
  const data = await res.json()

  if (!data) {
    return {
      redirect: {
        destination: '/',
        permanent: false,
        // statusCode: 301
      },
    }
  }

  return {
    props: { data }, // will be passed to the page component as props
  }
}

redirect가 build time에 이미 알려져 있다면, 대신 next.config.js에 추가해야 합니다.

If the redirects are known at build-time, they should be added in next.config.js instead.

Reading files: Use process.cwd()파일 읽기: process.cwd() 사용

getStaticProps에서는 filesystem에서 파일을 직접 읽을 수 있습니다.

Files can be read directly from the filesystem in getStaticProps.

그렇게 하려면 파일의 전체 경로를 알아야 합니다.

In order to do so you have to get the full path to a file.

Next.js는 코드를 별도의 directory로 compile하기 때문에, __dirname이 반환하는 경로가 Pages Router와 다르므로 __dirname을 사용할 수 없습니다.

Since Next.js compiles your code into a separate directory you can't use __dirname as the path it returns will be different from the Pages Router.

대신 Next.js가 실행되고 있는 directory를 알려 주는 process.cwd()를 사용할 수 있습니다.

Instead you can use process.cwd() which gives you the directory where Next.js is being executed.

import { promises as fs } from 'fs'
import path from 'path'

// posts will be populated at build time by getStaticProps()
function Blog({ posts }) {
  return (
    <ul>
      {posts.map((post) => (
        <li>
          <h3>{post.filename}</h3>
          <p>{post.content}</p>
        </li>
      ))}
    </ul>
  )
}

// This function gets called at build time on server-side.
// It won't be called on client-side, so you can even do
// direct database queries.
export async function getStaticProps() {
  const postsDirectory = path.join(process.cwd(), 'posts')
  const filenames = await fs.readdir(postsDirectory)

  const posts = filenames.map(async (filename) => {
    const filePath = path.join(postsDirectory, filename)
    const fileContents = await fs.readFile(filePath, 'utf8')

    // Generally you would parse/transform the contents
    // For example you can transform markdown to HTML here

    return {
      filename,
      content: fileContents,
    }
  })
  // By returning { props: { posts } }, the Blog component
  // will receive `posts` as a prop at build time
  return {
    props: {
      posts: await Promise.all(posts),
    },
  }
}

export default Blog
