Incremental Static Regeneration with Cache ComponentsCache Components와 함께 쓰는 ISR

cacheComponents와 Partial Prefetching을 함께 사용하는 Incremental Static Regeneration (ISR)은 build에 포함되지 않은 URL이라도 모든 route에서 즉각적인 첫 방문을 제공합니다.

Incremental Static Regeneration (ISR) with cacheComponents and Partial Prefetching gives every route an instant first visit, even for URLs that weren't included in the build.

build 중에 Partial Prerendering은 각 render를 두 부분으로 나눕니다:

During build, Partial Prerendering splits each render into two parts:

  • App Shell: URL 데이터에 의존하지 않는, 페이지의 범용적이고 재사용 가능한 부분
  • 나머지 정적으로 render할 수 있는 콘텐츠: generateStaticParams에 나열한 URL에 대한 param별 prerender 결과
  • The App Shell: the generic, reusable part of the page that doesn't depend on URL data
  • The rest of the statically renderable content: the param-specific prerenders for the URLs you list in generateStaticParams

generateStaticParams에 param이 포함된 URL에 방문하면 Next.js는 완전히 prerender된 페이지를 cache에서 제공합니다. param이 포함되지 않은 URL에 방문하면 Next.js는 App Shell을 즉시 제공한 다음, 이제 알게 된 param으로 background에서 이를 upgrade합니다. 이후 같은 URL에 방문하면 App Shell을 완전히 건너뛰고 cache에서 upgrade된 결과를 받습니다.

For a visit to a URL whose params were included in generateStaticParams, Next.js serves the fully prerendered page from the cache. For a visit to a URL whose params weren't, Next.js serves the App Shell instantly, then upgrades it in the background with the now-known params. Subsequent visits to that URL get the upgraded result from the cache, skipping the App Shell entirely.

Pages Router에서 ISR이나 fallback: true를 사용해 봤다면, 이것이 그에 해당하는 Cache Components 방식입니다.

If you have used ISR or fallback: true in the Pages Router, this is the Cache Components equivalent.

cacheComponents와 Partial Prefetching을 모두 활성화하세요.

Enable both cacheComponents and Partial Prefetching.

Cache Components는 fallback UI를 포함할 수 있는 static shell을 prerender합니다. generateStaticParams가 반환하지 않은 경로에 대해서는 Next.js가 해당 경로를 on demand로 render하고, 완성된 결과를 ISR cache에 저장할 수 있습니다.

Cache Components prerenders a static shell that can include fallback UI. For paths not returned by generateStaticParams, Next.js can render the path on demand and store the completed result in the ISR cache.

Partial Prefetching은 URL별 render가 완료되기 전에 fallback을 제공할지 여부를 결정합니다:

Partial Prefetching determines whether the fallback is served before the URL-specific render completes:

  • With Partial Prefetching: <Suspense> 안에서 params를 await할 수 있습니다. Next.js는 나열되지 않은 경로에 대해 fallback을 즉시 제공하고, URL별 콘텐츠를 render한 뒤, 완성된 결과를 ISR cache에 저장할 수 있습니다.
  • Without Partial Prefetching: 나열되지 않은 경로에 대한 첫 request는 URL별 render가 완료될 때까지 기다려야 합니다. loading.tsx가 만드는 boundary를 포함해 모든 <Suspense> boundary 바깥에서 params를 await하세요. 그래야 Next.js가 해당 URL에 대한 ISR entry를 만듭니다.
  • With Partial Prefetching: You can await params inside <Suspense>. Next.js can immediately serve the fallback for an unlisted path, render the URL-specific content, and store the completed result in the ISR cache.
  • Without Partial Prefetching: The first request for an unlisted path must wait for the URL-specific render to complete. Await params outside any <Suspense> boundary, including one created by loading.tsx, so Next.js creates an ISR entry for that URL.
Good to know

Partial Prefetching 없이 <Suspense> 안에서 params를 await하면, Next.js는 URL별 ISR entry를 만드는 대신 공유 fallback을 계속 제공합니다. route가 fetch한 데이터는 여전히 독립적으로 cache될 수 있습니다.

Without Partial Prefetching, awaiting params inside <Suspense> causes Next.js to keep serving the shared fallback instead of creating a URL-specific ISR entry. Data fetched by the route can still be cached independently.

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
}

export default nextConfig

Prepare your routesroute 준비하기

generateStaticParams를 사용해 어떤 param 값을 prerender할지 정의하세요. 이 route들을 render할 때는 build 시점에 param 값을 알 수 있습니다. prerender 과정은 Request-time API나 cache되지 않은 데이터에 도달할 때까지 static shell을 만듭니다. 자세한 내용은 Prerendering을 참고하세요.

Use generateStaticParams to define which param values to prerender. When rendering these routes, the param values are known at build time. The prerender process builds a static shell until it reaches a Request-time API or uncached data. See Prerendering for more details.

category layout은 두 개의 category를 prerender합니다:

The category layout prerenders two categories:

TSapp/[category]/layout.tsx
import Link from 'next/link'
import { Suspense } from 'react'
import { getCategory, getTopCategories } from '../lib/data'

export async function generateStaticParams() {
  const categories = await getTopCategories()
  return categories.map((c) => ({ category: c.slug }))
}

async function CategoryHeader({
  params,
}: Pick<LayoutProps<'/[category]'>, 'params'>) {
  const { category } = await params
  const data = await getCategory(category)

  return (
    <div>
      <Link href="/">&larr; All categories</Link>
      <h1>{data?.name ?? 'Category'}</h1>
      {data?.description && <p>{data.description}</p>}
    </div>
  )
}

export default function CategoryLayout(props: LayoutProps<'/[category]'>) {
  return (
    <div>
      <Suspense fallback={<div>Loading...</div>}>
        <CategoryHeader params={props.params} />
      </Suspense>
      {props.children}
    </div>
  )
}

CategoryLayout이 props.params를 직접 await하지 않는다는 점에 주목하세요. 대신 params promise를 <Suspense> 안의 CategoryHeader에 전달합니다. await가 boundary 안에서 일어나므로, 알 수 없는 category에 대해서도 Next.js는 App Shell을 생성할 수 있습니다. generateStaticParams가 다루는 category에 대해서도 읽기는 boundary 안에 두세요. 정적으로 알려진 param이라도 여전히 하나의 URL에 속하므로, Suspense boundary 위에서 await하면 이 layout의 App Shell이 그 URL에 묶이게 됩니다. route를 이런 방식으로 구성하는 방법은 Instant navigation을 참고하세요.

Notice that CategoryLayout does not await props.params itself. Instead, it passes the params promise to CategoryHeader inside <Suspense>. The await happens inside the boundary, so for unknown categories Next.js can still generate the App Shell. Keep the read inside the boundary even for the categories generateStaticParams covers. A statically known param still belongs to one URL, so awaiting it above the Suspense boundary would tie this layout's App Shell to that URL. See Instant navigation for structuring routes this way.

product page는 category마다 product 하나를 prerender합니다. generateStaticParams는 상위 category param을 받습니다:

The product page prerenders one product per category. generateStaticParams receives the parent category param:

TSapp/[category]/[product]/page.tsx
import { Suspense } from 'react'
import Link from 'next/link'
import { getProduct, getPopularProducts } from '../../lib/data'

export async function generateStaticParams({
  params,
}: {
  params: { category: string }
}) {
  const products = await getPopularProducts(params.category)
  return products.map((p) => ({ product: p.slug }))
}

async function ProductDetails(props: PageProps<'/[category]/[product]'>) {
  const { category, product } = await props.params
  const data = await getProduct(category, product)

  if (!data) {
    return <p>Product not found.</p>
  }

  return (
    <>
      <Link href={`/${category}`} prefetch={true}>
        &larr; Back to products
      </Link>
      <h2>{data.name}</h2>
      <p>${data.price}</p>
      <p>{data.description}</p>
    </>
  )
}

export default function ProductPage(props: PageProps<'/[category]/[product]'>) {
  return (
    <div>
      <Suspense fallback={<div>Loading product...</div>}>
        <ProductDetails {...props} />
      </Suspense>
    </div>
  )
}
Good to know

JSX의 <Suspense> 대신 loading.tsx 파일을 사용할 수도 있습니다. loading.tsx는 boundary를 segment 경계에 두고, inline <Suspense>는 tree의 어디에든 boundary를 둘 수 있게 해 줍니다.

You can also use loading.tsx files instead of <Suspense> in JSX. loading.tsx puts the boundary at the segment edge, while inline <Suspense> lets you place it anywhere in the tree.

데이터 helper는 module 수준에서 'use cache'를 사용하므로 export된 모든 함수가 cache됩니다. 덕분에 그 결과를 static shell에 포함할 수 있습니다:

The data helpers use 'use cache' at the module level so all exported functions are cached. This lets their results be included in the static shell:

TSapp/lib/data.ts
'use cache'

const API = 'https://next-recipe-api.vercel.dev'

export async function getCategory(slug: string) {
  const res = await fetch(`${API}/categories/${slug}`)
  if (!res.ok) return null
  return res.json()
}

export async function getProduct(category: string, slug: string) {
  const res = await fetch(`${API}/products/${category}/${slug}`)
  if (!res.ok) return null
  return res.json()
}

export async function getTopCategories() {
  const res = await fetch(`${API}/categories`)
  const categories = await res.json()
  return categories.slice(0, 2)
}

export async function getPopularProducts(category: string) {
  const res = await fetch(`${API}/products?category=${category}`)
  const products = await res.json()
  return products.slice(0, 1)
}

component가 cookies()나 headers() 같은 Request-time API에 접근한다면 <Suspense>로 감싸세요. prerender 중에 Next.js는 가장 가까운 fallback을 static shell에 포함합니다. 해당 component를 <Link prefetch={true}>에서도 제외하려면, request-time 접근 전에 navigation()을 await하세요. Keep the prefetch static을 참고하세요.

If a component accesses a Request-time API such as cookies() or headers(), wrap it in <Suspense>. During prerendering, Next.js includes the nearest fallback in the static shell. To keep the component out of a <Link prefetch={true}> as well, await navigation() before the request-time access. See Keep the prefetch static.

At build timebuild 시점

next build를 실행하면 Next.js는 알려진 각 category(tops, shorts)의 layout을 prerender하고, 여기에 await params가 suspend되는 render를 하나 더 수행해 [category]의 App Shell을 만듭니다.

When you run next build, Next.js prerenders the layout for each known category (tops, shorts), plus one render where await params suspends, producing the App Shell for [category].

또한 각 category 아래의 알려진 product(tops 아래의 tee, shorts 아래의 joggers)에 대한 page를 prerender하고, 여기에 await params가 suspend되는 render를 하나 더 수행해 [product]의 App Shell을 만듭니다.

It also prerenders the page for each known product under each category (tee under tops, joggers under shorts), plus one render where await params suspends, producing the App Shell for [product].

이것들이 다음과 같이 조합됩니다:

These are combined into:

  • /tops/tee, /shorts/joggers: 두 param을 모두 아는, 완전히 static한 페이지
  • /tops/[product], /shorts/[product]: category header는 render되고, product는 fallback을 표시
  • /[category]/[product]: 둘 다 fallback을 표시
  • /tops/tee, /shorts/joggers: fully static pages, both params known
  • /tops/[product], /shorts/[product]: category header rendered, product shows fallback
  • /[category]/[product]: both show fallback

At runtimeruntime 시점

방문자가 /tops/tee로 이동합니다. 두 param 모두 prerender되어 있었습니다. 방문자는 완전히 static한 페이지를 받습니다.

A visitor navigates to /tops/tee. Both params were prerendered. They get a fully static page.

/tops/overshirt에 처음 방문하는 경우입니다. product overshirt는 알려지지 않았지만 category tops는 prerender되어 있었습니다. Next.js는 category header가 이미 render된 /tops/[product]의 App Shell을 제공합니다. product는 stream되어 들어옵니다.

The first visit to /tops/overshirt. The product overshirt is unknown, but the category tops was prerendered. Next.js serves the App Shell for /tops/[product] with the category header already rendered. The product streams in.

/shoes/basketball-shoes에 처음 방문하는 경우입니다. 어느 param도 prerender되지 않았습니다. Next.js는 /[category]/[product]의 범용 App Shell을 제공합니다. category와 product 모두 stream되어 들어옵니다.

The first visit to /shoes/basketball-shoes. Neither param was prerendered. Next.js serves the generic App Shell for /[category]/[product]. Both the category and the product stream in.

첫 방문 이후 Next.js는 이제 알게 된 param으로 이 route들을 background에서 render합니다. 같은 URL의 다음 방문자는 upgrade된 결과를 받습니다.

After the first visit, Next.js renders these routes in the background with the now-known params. The next visitor to the same URLs gets the upgraded result.

나열되지 않은 URL을 가리키는 <Link prefetch={true}>가 viewport에 들어오면, Next.js는 첫 방문 때와 마찬가지로 클릭 전에 background upgrade를 시작하므로 navigation은 upgrade된 결과에 도착합니다.

When a <Link prefetch={true}> to an unlisted URL enters the viewport, Next.js starts the background upgrade before the click, just as a first visit would, so navigation lands on the upgraded result.

이 페이지들로 가는 link에는 prefetch={true}가 필요합니다. 기본 <Link>는 App Shell만 prefetch하며, 같은 route로 가는 link들은 이 App Shell을 공유합니다.

Links to these pages need prefetch={true}. A default <Link> prefetches only the App Shell, which links to the same route share.

Good to know

나열되지 않은 param에 대한 App Shell 제공은 Next.js 16.3부터 지원됩니다. 이전 버전은 response를 보내기 전에 전체 server render를 기다립니다.

The App Shell for unlisted params is served from Next.js 16.3. Earlier versions wait for a full server render before sending the response.

Wait for complete static output완전한 static 출력 기다리기

나열되지 않은 parameter의 경우 ensureStatic = 'navigation'을 사용하면 첫 request가 완전한 static page를 기다리게 됩니다. 이 요구 사항이 없으면 Next.js는 background에서 페이지를 생성하는 동안 prerender된 fallback을 반환할 수 있습니다. Next.js는 완성된 페이지를 이후 request를 위해 저장합니다.

For an unlisted parameter, ensureStatic = 'navigation' makes the first request wait for the complete static page. Without this requirement, Next.js can return a prerendered fallback while it generates the page in the background. Next.js stores the completed page for later requests.

What the upgrade producesupgrade의 결과물

첫 방문 이후 Next.js는 알려진 param으로 background에서 페이지를 render하고, static boundary를 component tree에서 가능한 한 아래쪽까지 밀어 내리려고 합니다:

After the first visit, Next.js renders the page in the background with the known params and tries to push the static boundary as far down the component tree as possible:

  • 모든 데이터 접근이 cache되고 모든 param이 resolve되면, upgrade 결과는 완전히 static한 페이지입니다.
  • 모든 param이 resolve되었지만 render가 여전히 <Suspense> boundary로 감싼 cache되지 않은 데이터나 Request-time API(cookies(), headers())에 도달하면, upgrade 결과는 해당 fallback을 포함한 cache된 페이지입니다. cache되지 않았거나 request에 특화된 부분은 request 시점에 stream되어 들어옵니다.
  • param은 route 순서대로 resolve됩니다. generateStaticParams가 반환하지 않은 param 값은 resolve되지 않은 상태로 남고, 그보다 더 깊은 param의 upgrade도 막습니다.
  • If every data access is cached and all params are resolved, the upgrade produces a fully static page.
  • If all params are resolved but the render still reaches uncached data or Request-time APIs (cookies(), headers()) wrapped in <Suspense> boundaries, the upgrade produces a cached page with those fallbacks. The uncached or request-specific parts stream in at request time.
  • Params are resolved in route order. A param value not returned by generateStaticParams stays unresolved and prevents any deeper params from upgrading.

Choosing what to prerender무엇을 prerender할지 선택하기

모든 route를 prerender할 필요는 없습니다. prerender하는 페이지가 늘어날수록 build 작업이 늘어나고, 저장하고 deploy해야 할 출력물도 생깁니다. 상당수의 route는 다음 deploy 전까지 한 번도 방문되지 않을 수 있으므로, 그 작업은 불필요해집니다.

Not every route needs to be prerendered. Every page you prerender increases build work and produces output that has to be stored and deployed. Many routes may never be visited before your next deployment, making that work unnecessary.

대신 generateStaticParams를 사용해 인기 페이지나 예측 가능한 콘텐츠처럼 미리 준비해 두면 가장 이득이 큰 route를 prerender하세요. 방문 빈도가 낮은 route는 on demand로 생성되고 첫 방문 이후 upgrade되므로, 한 번도 request되지 않을 수 있는 페이지에 build 시간과 저장 공간을 쓰지 않아도 됩니다.

Instead, use generateStaticParams to prerender the routes that benefit most from being ready ahead of time, such as popular pages or predictable content. Less frequently visited routes are generated on demand and upgraded after their first visit, so you don't spend build time and storage on pages that may never be requested.

Coming from the Pages RouterPages Router에서 넘어오는 경우

Pages Router에서 migrate하는 경우:

If you are migrating from the Pages Router:

  • getStaticPaths의 fallback: true는 Partial Prefetching을 사용하는 Cache Components에 해당합니다. 방문자는 <Suspense> fallback을 즉시 받고, Next.js는 완성된 route를 이후 방문을 위해 저장합니다.
  • fallback: 'blocking'은 Partial Prefetching을 사용하지 않는 Cache Components에 해당합니다. <Suspense> 바깥에서 params를 await하면 첫 request가 완성된 route를 기다리고, Next.js는 이를 이후 방문을 위해 저장합니다.
  • router.isFallback은 필요하지 않습니다. prerender 단계에서 static shell이 생성되며, 'use cache'로 이를 더 키울 수 있습니다.
  • revalidate를 사용하는 getStaticProps는 cacheLife와 함께 쓰는 'use cache'에 해당합니다.
  • getStaticPaths는 generateStaticParams에 해당합니다.
  • fallback: true in getStaticPaths maps to Cache Components with Partial Prefetching. Visitors get a <Suspense> fallback instantly, and Next.js stores the completed route for subsequent visits.
  • fallback: 'blocking' maps to Cache Components without Partial Prefetching. Await params outside <Suspense> so the first request waits for the completed route, which Next.js then stores for subsequent visits.
  • router.isFallback is not needed. The prerendering step generates a static shell, and you can grow it further with 'use cache'.
  • getStaticProps with revalidate maps to 'use cache' with cacheLife.
  • getStaticPaths maps to generateStaticParams.
