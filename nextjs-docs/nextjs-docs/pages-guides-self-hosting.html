How to self-host your Next.js applicationNext.js 애플리케이션 self-hosting하기

Next.js 앱을 deploy할 때, 사용하는 infrastructure에 맞춰 여러 기능이 처리되는 방식을 설정하고 싶을 수 있습니다.

When deploying your Next.js app, you may want to configure how different features are handled based on your infrastructure.

Reverse Proxy

self-hosting할 때는 Next.js server를 인터넷에 직접 노출하기보다, 그 앞에 reverse proxy(nginx 등)를 두는 것을 권장합니다. reverse proxy는 잘못된 형식의 request, slow connection 공격, payload 크기 제한, rate limiting 및 기타 보안 문제를 처리해서 이런 작업을 Next.js server에서 덜어 줍니다. 덕분에 server는 request 검증 대신 rendering에 자원을 집중할 수 있습니다.

When self-hosting, it's recommended to use a reverse proxy (like nginx) in front of your Next.js server rather than exposing it directly to the internet. A reverse proxy can handle malformed requests, slow connection attacks, payload size limits, rate limiting, and other security concerns, offloading these tasks from the Next.js server. This allows the server to dedicate its resources to rendering rather than request validation.

Image Optimization

next/image를 통한 Image Optimization은 next start로 deploy할 때 별도 설정 없이(zero configuration) self-hosted 환경에서 동작합니다. 이미지 최적화를 별도 service에 맡기고 싶다면 image loader를 설정할 수 있습니다.

Image Optimization through next/image works self-hosted with zero configuration when deploying using next start. If you would prefer to have a separate service to optimize images, you can configure an image loader.

next.config.js에 custom image loader를 정의하면 static export에서도 Image Optimization을 사용할 수 있습니다. 이미지는 build 중이 아니라 runtime에 최적화된다는 점에 유의하세요.

Image Optimization can be used with a static export by defining a custom image loader in next.config.js. Note that images are optimized at runtime, not during the build.

Good to know
  • glibc 기반 Linux 시스템에서는 과도한 메모리 사용을 막기 위해 Image Optimization에 추가 configuration이 필요할 수 있습니다.
  • 최적화된 이미지의 caching 동작과 TTL 설정 방법에 대해 더 알아보세요.
  • 원한다면 Image Optimization을 비활성화하고도 next/image 사용의 다른 이점은 그대로 누릴 수 있습니다. 예를 들어 이미지를 따로 직접 최적화하는 경우입니다.
  • On glibc-based Linux systems, Image Optimization may require additional configuration to prevent excessive memory usage.
  • Learn more about the caching behavior of optimized images and how to configure the TTL.
  • You can also disable Image Optimization and still retain other benefits of using next/image if you prefer. For example, if you are optimizing images yourself separately.

Proxy

Proxy는 next start로 deploy할 때 별도 설정 없이 self-hosted 환경에서 동작합니다. 들어오는 request에 접근해야 하므로 static export에서는 지원되지 않습니다.

Proxy works self-hosted with zero configuration when deploying using next start. Since it requires access to the incoming request, it is not supported when using a static export.

모든 Node.js API가 필요한 로직을 추가하려 한다면(또는 외부 package를 사용하려 한다면), 이 로직을 Server Component인 layout으로 옮길 수 있을지도 모릅니다. 예를 들어 header를 확인하고 redirect하는 경우입니다. 또한 next.config.js를 통해 header, cookie, query parameter를 사용해 redirect하거나 rewrite할 수도 있습니다. 그래도 안 된다면 custom server를 사용할 수도 있습니다.

If you are looking to add logic (or use an external package) that requires all Node.js APIs, you might be able to move this logic to a layout as a Server Component. For example, checking headers and redirecting. You can also use headers, cookies, or query parameters to redirect or rewrite through next.config.js. If that does not work, you can also use a custom server.

Environment VariablesEnvironment variable

Next.js는 build time environment variable과 runtime environment variable을 모두 지원합니다.

Next.js can support both build time and runtime environment variables.

기본적으로 environment variable은 server에서만 사용할 수 있습니다. environment variable을 브라우저에 노출하려면 이름 앞에 NEXT_PUBLIC_ prefix를 붙여야 합니다. 단, 이런 public environment variable은 next build 중에 JavaScript bundle에 inline됩니다.

By default, environment variables are only available on the server. To expose an environment variable to the browser, it must be prefixed with NEXT_PUBLIC_. However, these public environment variables will be inlined into the JavaScript bundle during next build.

runtime environment variable을 읽으려면 getServerSideProps를 사용하거나 App Router를 점진적으로 도입하는 것을 권장합니다.

To read runtime environment variables, we recommend using getServerSideProps or incrementally adopting the App Router.

이렇게 하면 서로 다른 값을 가진 여러 environment에 걸쳐 promote할 수 있는 단일 Docker image를 사용할 수 있습니다.

This allows you to use a singular Docker image that can be promoted through multiple environments with different values.

Good to know
  • register 함수를 사용하면 server 시작 시 코드를 실행할 수 있습니다.
  • You can run code on server startup using the register function.

Caching and ISRCaching과 ISR

Next.js는 response, 생성된 static page, build output, 그리고 이미지·font·script 같은 기타 static asset을 cache할 수 있습니다.

Next.js can cache responses, generated static pages, build outputs, and other static assets like images, fonts, and scripts.

page caching과 revalidation(Incremental Static Regeneration 사용)은 같은 Next.js server cache를 사용합니다. 기본적으로 이 cache는 각 Next.js server instance의 로컬 filesystem(디스크)에 저장됩니다.

Caching and revalidating pages (with Incremental Static Regeneration) use the same Next.js server cache. By default, this cache is stored on the local filesystem (on disk) of each Next.js server instance.

persistent 로컬 디스크를 가진 단일 self-hosted next start instance에서는 이것이 자동으로 동작합니다. 여러 instance를 실행하거나, ephemeral compute를 사용하거나, Next.js 앞에 CDN/reverse proxy를 둔다면 Configuring Caching, Multi-Instance Cache Coordination, Usage with CDNs도 함께 검토하세요.

This works automatically for a single self-hosted next start instance with persistent local disk. If you run multiple instances, use ephemeral compute, or place a CDN/reverse proxy in front of Next.js, also review Configuring Caching, Multi-Instance Cache Coordination, and Usage with CDNs.

cache된 page와 데이터를 durable storage에 유지하거나, Next.js 애플리케이션의 여러 container 또는 instance 사이에서 cache를 공유하고 싶다면 Next.js cache 위치를 설정할 수 있습니다.

You can configure the Next.js cache location if you want to persist cached pages and data to durable storage, or share the cache across multiple containers or instances of your Next.js application.

Automatic Caching자동 caching

  • Next.js는 진정으로 immutable한 asset에 public, max-age=31536000, immutable 값의 Cache-Control header를 설정합니다. 이 값은 override할 수 없습니다. 이런 immutable 파일은 파일 이름에 SHA-hash가 들어 있어서 무기한 안전하게 cache할 수 있습니다. 예를 들면 Static Image Imports입니다. 이미지의 경우 TTL을 설정할 수 있습니다.
  • Incremental Static Regeneration(ISR)은 s-maxage: <revalidate in getStaticProps>, stale-while-revalidate 값의 Cache-Control header를 설정합니다. 이 revalidation 시간은 getStaticProps 함수에서 초 단위로 정의합니다. revalidate: false로 설정하면 기본 cache 기간은 1년이 됩니다. 이를 CDN 계층에서 활용하려면 CDN/reverse proxy가 이 directive와 cache-key variability를 따라야 합니다(CDN Caching). 그렇지 않으면 response가 CDN caching을 우회하거나, client-side navigation 중에 stale하거나 맞지 않는 variant가 제공될 수 있습니다.
  • dynamic rendering되는 page는 사용자별 데이터가 cache되지 않도록 private, no-cache, no-store, max-age=0, must-revalidate 값의 Cache-Control header를 설정합니다. 이는 App Router와 Pages Router 모두에 적용됩니다. Draft Mode도 여기에 포함됩니다.
  • Next.js sets the Cache-Control header of public, max-age=31536000, immutable to truly immutable assets. It cannot be overridden. These immutable files contain a SHA-hash in the file name, so they can be safely cached indefinitely. For example, Static Image Imports. You can configure the TTL for images.
  • Incremental Static Regeneration (ISR) sets the Cache-Control header of s-maxage: <revalidate in getStaticProps>, stale-while-revalidate. This revalidation time is defined in your getStaticProps function in seconds. If you set revalidate: false, it will default to a one-year cache duration. To leverage this at the CDN layer, your CDN/reverse proxy must respect these directives and cache-key variability (CDN Caching); otherwise, responses may bypass CDN caching or serve stale/mismatched variants during client-side navigation.
  • Dynamically rendered pages set a Cache-Control header of private, no-cache, no-store, max-age=0, must-revalidate to prevent user-specific data from being cached. This applies to both the App Router and Pages Router. This also includes Draft Mode.

Static AssetsStatic asset

static asset을 다른 domain이나 CDN에서 hosting하고 싶다면 next.config.js에서 assetPrefix configuration을 사용할 수 있습니다. Next.js는 JavaScript나 CSS 파일을 가져올 때 이 asset prefix를 사용합니다. asset을 다른 domain으로 분리하면 DNS와 TLS resolution에 추가 시간이 든다는 단점이 있습니다.

If you want to host static assets on a different domain or CDN, you can use the assetPrefix configuration in next.config.js. Next.js will use this asset prefix when retrieving JavaScript or CSS files. Separating your assets to a different domain does come with the downside of extra time spent on DNS and TLS resolution.

Configuring CachingCaching 설정하기

기본적으로 생성된 cache asset은 메모리(기본 50mb)와 디스크에 저장됩니다. ephemeral compute platform(흔한 serverless 구성)에서는 로컬 디스크가 persistent하지 않거나 사용할 수 없는 경우가 많아서, 이 cache는 사실상 수명이 짧고 instance마다 따로 존재합니다. Kubernetes 같은 container orchestration platform으로 Next.js를 hosting한다면 각 pod가 cache의 사본을 하나씩 갖게 됩니다. 기본적으로 cache가 pod 사이에 공유되지 않아 stale 데이터가 표시되는 것을 막으려면, Next.js cache에 cache handler를 제공하고 in-memory caching을 비활성화하도록 설정할 수 있습니다.

By default, generated cache assets will be stored in memory (defaults to 50mb) and on disk. On ephemeral compute platforms (common serverless setups), local disk is often non-persistent or unavailable, so this cache is effectively short-lived and per-instance. If you are hosting Next.js using a container orchestration platform like Kubernetes, each pod will have a copy of the cache. To prevent stale data from being shown since the cache is not shared between pods by default, you can configure the Next.js cache to provide a cache handler and disable in-memory caching.

self-hosting할 때 cache 위치를 설정하려면 next.config.js 파일에 custom handler를 지정하세요:

To configure the cache location when self-hosting, set a custom handler in your next.config.js file:

JSnext.config.js
module.exports = {
  cacheHandler: require.resolve('./cache-handler.js'),
  cacheMaxMemorySize: 0, // disable default in-memory caching
}

handler 파일은 get, set, revalidateTag, resetRequestCache를 구현한 class를 export합니다. 각 method의 signature는 cacheHandler를, 동작하는 구현은 Redis cacheHandler 예제를 참고하세요.

The handler file exports a class that implements get, set, revalidateTag, and resetRequestCache. See cacheHandler for each method's signature, and the Redis cacheHandler example for a working implementation.

production deployment에서 handler는 다음을 충족해야 합니다:

For production deployments, the handler must:

  • 모든 instance가 접근할 수 있는 곳에 entry를 저장합니다. Redis나 AWS S3 같은 곳입니다. Map처럼 process 내부에 있는 store를 쓰면 다시 각 pod가 cache 사본을 따로 갖게 됩니다.
  • store의 크기를 제한합니다. TTL이나 크기 기반 eviction을 사용해 더 이상 request되지 않는 경로와 fetch key의 entry를 제거하세요.
  • entry를 serialize합니다. process 외부의 store라면 모두 이것이 필요합니다. entry에는 JSON.stringify/JSON.parse만으로는 serialize·복원할 수 없는 Buffer(예: rscData)와 Map(예: segmentData) 값이 들어 있을 수 있습니다. 이 serialization을 처리하지 않으면 client-side navigation이나 prefetch(RSC) request에서 segmentData.get is not a function 또는 failed to pipe response 같은 오류가 발생합니다.
  • tag로 entry를 index합니다. APP_PAGE, APP_ROUTE, PAGES entry는 x-next-cache-tags response header(data.headers)에 tag를 담고 있고, fetch entry의 tag는 ctx.tags에 담겨 있습니다. 한 instance에서 revalidateTag를 호출하면 모든 instance의 entry가 invalidate되도록 index를 shared store에 보관하세요.
  • storage 오류를 처리합니다. timeout이나 끊긴 connection 같은 경우입니다.
  • Store entries where every instance can reach them, like Redis or AWS S3. A store inside the process, such as a Map, gives each pod its own copy of the cache again.
  • Bound the store's size. Use a TTL or size-based eviction to remove entries for paths and fetch keys that are no longer requested.
  • Serialize entries. Any store outside the process needs this. An entry can contain Buffer (for example rscData) and Map (for example segmentData) values that JSON.stringify/JSON.parse can't serialize and restore on their own. Not handling this serialization results in errors like segmentData.get is not a function or failed to pipe response on client-side navigation or prefetch (RSC) requests.
  • Index entries by tag. APP_PAGE, APP_ROUTE, and PAGES entries carry their tags in the x-next-cache-tags response header (data.headers), while ctx.tags carries tags for fetch entries. Keep the index in the shared store, so a revalidateTag call on one instance invalidates the entry on every instance.
  • Handle storage errors, such as timeouts and dropped connections.
Good to know
  • revalidatePath는 cache tag 위에 얹힌 편의 계층입니다. revalidatePath를 호출하면 해당 page를 위한 특수 기본 tag로 revalidateTag 함수가 호출됩니다.
  • 'use cache' directive용 backend를 설정한다면 cacheHandlers를 사용하세요.
  • production을 염두에 둔 community Redis handler(GET timeout, in-memory coalescing, multi-instance tag coordination)는 Redis 예제 README에 정리되어 있으며, @trieb.work/nextjs-turbo-redis-cache와 @mrjasonroy/cache-components-cache-handler가 포함됩니다.
  • revalidatePath is a convenience layer on top of cache tags. Calling revalidatePath will call the revalidateTag function with a special default tag for the provided page.
  • If you are configuring backends for 'use cache' directives, use cacheHandlers.
  • Production-oriented community Redis handlers (GET timeouts, in-memory coalescing, multi-instance tag coordination) are listed in the Redis example README, including @trieb.work/nextjs-turbo-redis-cache and @mrjasonroy/cache-components-cache-handler.

Build Cache

Next.js는 next build 중에 어떤 버전의 애플리케이션이 제공되고 있는지 식별하기 위한 ID를 생성합니다. 같은 build를 사용해 여러 container를 띄워야 합니다.

Next.js generates an ID during next build to identify which version of your application is being served. The same build should be used and boot up multiple containers.

environment의 각 단계마다 다시 build한다면, container 사이에서 사용할 일관된 build ID를 생성해야 합니다. next.config.js에서 generateBuildId command를 사용하세요:

If you are rebuilding for each stage of your environment, you will need to generate a consistent build ID to use between containers. Use the generateBuildId command in next.config.js:

JSnext.config.js
module.exports = {
  generateBuildId: async () => {
    // This could be anything, using the latest git hash
    return process.env.GIT_HASH
  },
}
Good to know

deploymentId가 설정되어 있으면, generateBuildId를 명시적으로 설정하지 않는 한 Next.js는 고정된 build ID를 사용합니다. 대신 Version skew는 deployment ID로 감지됩니다.

When deploymentId is set, Next.js uses a constant build ID unless you explicitly configure generateBuildId. Version skew is detected from the deployment ID instead.

Multi-Server DeploymentsMulti-server deployment

Next.js를 여러 server instance에 걸쳐 실행할 때(예: load balancer 뒤의 container들) 일관된 동작을 보장하려면 추가로 고려할 점이 있습니다.

When running Next.js across multiple server instances (for example, containers behind a load balancer), there are additional considerations to ensure consistent behavior.

Server Functions encryption key

Next.js는 Server Function의 closure 변수를 client로 보내기 전에 암호화합니다. 기본적으로 build마다 고유한 encryption key가 생성됩니다.

Next.js encrypts Server Function closure variables before sending them to the client. By default, a unique encryption key is generated for each build.

여러 server instance를 실행할 때는 모든 instance가 같은 encryption key를 사용해야 합니다. 그렇지 않으면 한 instance가 암호화한 Server Function을 다른 instance가 복호화할 수 없어서 "Failed to find Server Action" 오류가 발생합니다.

When running multiple server instances, all instances must use the same encryption key. Otherwise, a Server Function encrypted by one instance cannot be decrypted by another, causing "Failed to find Server Action" errors.

NEXT_SERVER_ACTIONS_ENCRYPTION_KEY environment variable로 일관된 encryption key를 설정하세요. key는 유효한 AES key 길이(16, 24, 32 bytes)를 가진 base64-encoded 값이어야 합니다. Next.js는 기본적으로 32-byte key를 생성합니다.

Set a consistent encryption key using the NEXT_SERVER_ACTIONS_ENCRYPTION_KEY environment variable. The key must be a base64-encoded value with a valid AES key length (16, 24, or 32 bytes). Next.js generates 32-byte keys by default.

NEXT_SERVER_ACTIONS_ENCRYPTION_KEY=your-generated-key next build

key는 build output에 포함되어 runtime에 자동으로 사용됩니다. 자세한 내용은 Data Security 가이드를 참고하세요.

The key is embedded in the build output and used automatically at runtime. Learn more in the Data Security guide.

Deployment identifier

rolling deployment 중 version skew 보호를 활성화하려면 deploymentId를 설정하세요. 이렇게 하면 client가 항상 일관된 deployment 버전의 asset을 받게 됩니다.

Configure a deploymentId to enable version skew protection during rolling deployments. This ensures clients always receive assets from a consistent deployment version.

Shared cache

기본적으로 Next.js는 instance 사이에 공유되지 않는 in-memory cache를 사용합니다. 일관된 caching 동작을 원한다면 외부 storage에 데이터를 저장하는 custom cache handler와 함께 'use cache: remote'를 사용하세요.

By default, Next.js uses an in-memory cache that is not shared across instances. For consistent caching behavior, use 'use cache: remote' with a custom cache handler that stores data in external storage.

Version Skew

여러 instance에 걸쳐 self-hosting하거나 rolling deployment를 할 때, version skew는 다음과 같은 문제를 일으킬 수 있습니다:

When self-hosting across multiple instances or doing rolling deployments, version skew can cause:

  • Missing assets: client가 server에 더 이상 존재하지 않는 JavaScript나 CSS 파일을 request합니다
  • Server Function mismatches: client가 이전 build의 ID로 Server Function을 호출하는데, server는 그 ID를 더 이상 인식하지 못합니다
  • Navigation failures: 이전 deployment에서 prefetch한 page 데이터가 새 server와 호환되지 않습니다
  • Missing assets: The client requests JavaScript or CSS files that no longer exist on the server
  • Server Function mismatches: The client invokes a Server Function using an ID from a previous build that the server no longer recognizes
  • Navigation failures: Prefetched page data from an old deployment is incompatible with the new server

Next.js는 deploymentId를 사용해 version skew를 감지하고 처리합니다. deployment ID가 설정되어 있으면:

Next.js uses the deploymentId to detect and handle version skew. When a deployment ID is configured:

  • static asset에 ?dpl=<deploymentId> query parameter가 붙습니다
  • client-side navigation request에 x-deployment-id header가 포함됩니다
  • server는 client의 deployment ID를 자신의 ID와 비교합니다
  • Static assets include a ?dpl=<deploymentId> query parameter
  • Client-side navigation requests include an x-deployment-id header
  • The server compares the client's deployment ID with its own

불일치가 감지되면 Next.js는 client-side navigation 대신 hard navigation(전체 page reload)을 실행합니다. 이렇게 하면 client가 일관된 deployment 버전의 asset을 가져오게 됩니다.

If a mismatch is detected, Next.js triggers a hard navigation (full page reload) instead of a client-side navigation. This ensures the client fetches assets from a consistent deployment version.

JSnext.config.js
module.exports = {
  deploymentId: process.env.DEPLOYMENT_VERSION,
}
Good to know

애플리케이션이 reload될 때, page navigation 사이에 state를 유지하도록 설계되어 있지 않다면 애플리케이션 state가 사라질 수 있습니다. URL state나 local storage는 유지되지만, useState 같은 component state는 사라집니다.

When the application is reloaded, there may be a loss of application state if it's not designed to persist between page navigations. URL state or local storage would persist, but component state like useState would be lost.

Immutable AssetsImmutable asset

immutable static asset을 사용하면 version skew를 막기가 훨씬 쉬워집니다:

When using immutable static assets, preventing version skew becomes much easier:

asset을 여러 deployment 사이에서 공유할 수 있으므로, 기존 static 파일 폴더(또는 CDN bucket)에 계속 추가하기만 하면 version skew가 생기지 않습니다(reverse proxy에서 deployment id를 추적하거나 green-blue deployment를 할 필요 없이).

Assets can be shared across deployments, so if you just keep adding them to your existing static file folder (or CDN bucket), there will be no version skew (without having to track deployment ids in the reverse proxy/do green-blue deployments).

Manual Graceful Shutdowns수동 graceful shutdown

self-hosting할 때, server가 SIGTERM 또는 SIGINT signal로 종료될 때 코드를 실행하고 싶을 수 있습니다.

When self-hosting, you might want to run code when the server shuts down on SIGTERM or SIGINT signals.

env 변수 NEXT_MANUAL_SIG_HANDLE을 true로 설정한 뒤, _document.js 파일 안에서 해당 signal에 대한 handler를 등록하면 됩니다. 이 environment variable은 .env 파일이 아니라 package.json script에 직접 등록해야 합니다.

You can set the env variable NEXT_MANUAL_SIG_HANDLE to true and then register a handler for that signal inside your _document.js file. You will need to register the environment variable directly in the package.json script, and not in the .env file.

Good to know

수동 signal 처리는 next dev에서는 사용할 수 없습니다.

Manual signal handling is not available in next dev.

package.json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "NEXT_MANUAL_SIG_HANDLE=true next start"
  }
}
JSpages/_document.js
if (process.env.NEXT_MANUAL_SIG_HANDLE) {
  process.on('SIGTERM', () => {
    console.log('Received SIGTERM: cleaning up')
    process.exit(0)
  })
  process.on('SIGINT', () => {
    console.log('Received SIGINT: cleaning up')
    process.exit(0)
  })
}
