How to migrate from Vite to Next.jsVite에서 Next.js로 migrate하기

이 가이드는 기존 Vite 애플리케이션을 Next.js로 migrate하는 과정을 안내합니다.

This guide will help you migrate an existing Vite application to Next.js.

Why Switch?왜 바꿔야 할까?

Vite에서 Next.js로 바꾸고 싶은 이유는 여러 가지가 있습니다:

There are several reasons why you might want to switch from Vite to Next.js:

Slow initial page loading time느린 초기 페이지 로딩 시간

React용 기본 Vite plugin으로 애플리케이션을 만들었다면, 그 애플리케이션은 순수한 client-side 애플리케이션입니다. single-page application(SPA)이라고도 불리는 client-side 전용 애플리케이션은 초기 페이지 로딩 시간이 느린 경우가 많습니다. 그 이유는 몇 가지가 있습니다:

If you have built your application with the default Vite plugin for React, your application is a purely client-side application. Client-side only applications, also known as single-page applications (SPAs), often experience slow initial page loading time. This happens due to a couple of reasons:

  1. 코드가 데이터를 불러오기 위한 request를 보내기 전에, 브라우저는 React 코드와 애플리케이션 bundle 전체가 다운로드되고 실행될 때까지 기다려야 합니다.
  2. 새 기능과 추가 dependency를 넣을 때마다 애플리케이션 코드가 커집니다.
  1. The browser needs to wait for the React code and your entire application bundle to download and run before your code is able to send requests to load some data.
  2. Your application code grows with every new feature and extra dependency you add.

No automatic code splitting자동 code splitting 없음

앞에서 말한 느린 로딩 시간 문제는 code splitting으로 어느 정도 관리할 수 있습니다. 하지만 code splitting을 수동으로 하려고 하면 오히려 performance가 나빠지는 경우가 많습니다. 수동으로 code splitting을 하다 보면 의도치 않게 network waterfall을 만들기 쉽습니다. Next.js는 router에 자동 code splitting이 내장되어 있습니다.

The previous issue of slow loading times can be somewhat managed with code splitting. However, if you try to do code splitting manually, you'll often make performance worse. It's easy to inadvertently introduce network waterfalls when code-splitting manually. Next.js provides automatic code splitting built into its router.

Network waterfallsNetwork waterfall

performance가 나빠지는 흔한 원인 중 하나는 애플리케이션이 데이터를 fetch하기 위해 client-server request를 순차적으로 보내는 경우입니다. SPA에서 흔히 쓰는 data fetching 패턴은 처음에 placeholder를 render하고, component가 mount된 뒤에 데이터를 fetch하는 것입니다. 안타깝게도 이렇게 하면 데이터를 fetch하는 child component는 parent component가 자기 데이터를 다 불러올 때까지 fetch를 시작할 수 없습니다.

A common cause of poor performance occurs when applications make sequential client-server requests to fetch data. One common pattern for data fetching in an SPA is to initially render a placeholder, and then fetch data after the component has mounted. Unfortunately, this means that a child component that fetches data can't start fetching until the parent component has finished loading its own data.

Next.js에서도 client에서 데이터를 fetch하는 것은 지원되지만, data fetching을 server로 옮기는 선택지도 제공하므로 client-server waterfall을 없앨 수 있습니다.

While fetching data on the client is supported with Next.js, it also gives you the option to shift data fetching to the server, which can eliminate client-server waterfalls.

Fast and intentional loading states빠르고 의도적인 loading state

React Suspense를 통한 streaming을 기본으로 지원하므로, network waterfall을 만들지 않고도 UI의 어떤 부분을 먼저, 어떤 순서로 로드할지 더 의도적으로 정할 수 있습니다.

With built-in support for streaming through React Suspense, you can be more intentional about which parts of your UI you want to load first and in what order without introducing network waterfalls.

이를 통해 더 빨리 로드되는 페이지를 만들고 layout shift를 없앨 수 있습니다.

This enables you to build pages that are faster to load and eliminate layout shifts.

Choose the data fetching strategydata fetching 전략 선택

필요에 따라 Next.js에서는 페이지 단위, component 단위로 data fetching 전략을 선택할 수 있습니다. build 시점에 fetch할지, server에서 request 시점에 fetch할지, client에서 fetch할지 정할 수 있습니다. 예를 들어 CMS에서 데이터를 fetch해 build 시점에 블로그 글을 render하고, 이를 CDN에 효율적으로 cache할 수 있습니다.

Depending on your needs, Next.js allows you to choose your data fetching strategy on a page and component basis. You can decide to fetch at build time, at request time on the server, or on the client. For example, you can fetch data from your CMS and render your blog posts at build time, which can then be efficiently cached on a CDN.

Proxy

Next.js Proxy를 사용하면 request가 완료되기 전에 server에서 코드를 실행할 수 있습니다. 이는 특히 사용자가 인증된 사용자 전용 페이지에 방문했을 때 로그인 페이지로 redirect해서, 인증되지 않은 콘텐츠가 잠깐 보이는 현상(flash)을 막는 데 유용합니다. proxy는 실험(experimentation)과 internationalization에도 유용합니다.

Next.js Proxy allows you to run code on the server before a request is completed. This is especially useful to avoid having a flash of unauthenticated content when the user visits an authenticated-only page by redirecting the user to a login page. The proxy is also useful for experimentation and internationalization.

Built-in Optimizations내장 최적화

이미지, font, third-party script는 애플리케이션 performance에 큰 영향을 주는 경우가 많습니다. Next.js에는 이것들을 자동으로 최적화해 주는 내장 component가 있습니다.

Images, fonts, and third-party scripts often have significant impact on an application's performance. Next.js comes with built-in components that automatically optimize those for you.

Migration StepsMigration 단계

이번 migration의 목표는 가능한 한 빨리 동작하는 Next.js 애플리케이션을 만들어, 그 뒤에 Next.js 기능을 점진적으로 도입할 수 있게 하는 것입니다. 우선은 기존 router를 migrate하지 않고 순수한 client-side 애플리케이션(SPA)으로 유지합니다. 이렇게 하면 migration 과정에서 문제가 생길 가능성을 최소화하고 merge conflict도 줄일 수 있습니다.

Our goal with this migration is to get a working Next.js application as quickly as possible, so that you can then adopt Next.js features incrementally. To begin with, we'll keep it as a purely client-side application (SPA) without migrating your existing router. This helps minimize the chances of encountering issues during the migration process and reduces merge conflicts.

Step 1: Install the Next.js Dependency1단계: Next.js dependency 설치

가장 먼저 next를 dependency로 설치해야 합니다:

The first thing you need to do is to install next as a dependency:

pnpm add next@latest
npm install next@latest
yarn add next@latest
bun add next@latest

Step 2: Create the Next.js Configuration File2단계: Next.js configuration 파일 만들기

프로젝트 root에 next.config.mjs를 만드세요. 이 파일에는 Next.js configuration option이 들어갑니다.

Create a next.config.mjs at the root of your project. This file will hold your Next.js configuration options.

JSnext.config.mjs
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'export', // Outputs a Single-Page Application (SPA).
  distDir: './dist', // Changes the build output directory to `./dist/`.
}

export default nextConfig
Good to know

Next.js configuration 파일에는 .js와 .mjs 중 어느 것이든 사용할 수 있습니다.

You can use either .js or .mjs for your Next.js configuration file.

Step 3: Update TypeScript Configuration3단계: TypeScript configuration 업데이트

TypeScript를 사용한다면 Next.js와 호환되도록 tsconfig.json 파일을 다음과 같이 수정해야 합니다. TypeScript를 사용하지 않는다면 이 단계는 건너뛰어도 됩니다.

If you're using TypeScript, you need to update your tsconfig.json file with the following changes to make it compatible with Next.js. If you're not using TypeScript, you can skip this step.

  1. tsconfig.node.json에 대한 project reference를 제거합니다
  2. include array에 ./dist/types/**/*.ts와 ./next-env.d.ts를 추가합니다
  3. exclude array에 ./node_modules를 추가합니다
  4. compilerOptions의 plugins array에 { "name": "next" }를 추가합니다: "plugins": [{ "name": "next" }]
  5. esModuleInterop을 true로 설정합니다: "esModuleInterop": true
  6. jsx를 react-jsx로 설정합니다: "jsx": "react-jsx"
  7. allowJs를 true로 설정합니다: "allowJs": true
  8. forceConsistentCasingInFileNames를 true로 설정합니다: "forceConsistentCasingInFileNames": true
  9. incremental을 true로 설정합니다: "incremental": true
  1. Remove the project reference to tsconfig.node.json
  2. Add ./dist/types/**/*.ts and ./next-env.d.ts to the include array
  3. Add ./node_modules to the exclude array
  4. Add { "name": "next" } to the plugins array in compilerOptions: "plugins": [{ "name": "next" }]
  5. Set esModuleInterop to true: "esModuleInterop": true
  6. Set jsx to react-jsx: "jsx": "react-jsx"

Step 4: Create the Root Layout4단계: Root Layout 만들기

Next.js App Router 애플리케이션에는 반드시 root layout 파일이 있어야 합니다. 이 파일은 애플리케이션의 모든 페이지를 감싸는 React Server Component입니다. 이 파일은 app directory의 최상위에 정의합니다.

A Next.js App Router application must include a root layout file, which is a React Server Component that will wrap all pages in your application. This file is defined at the top level of the app directory.

Vite 애플리케이션에서 root layout 파일에 가장 가까운 것은 <html>, <head>, <body> tag가 들어 있는 index.html 파일입니다.

The closest equivalent to the root layout file in a Vite application is the index.html file, which contains your <html>, <head>, and <body> tags.

이 단계에서는 index.html 파일을 root layout 파일로 바꿉니다:

In this step, you'll convert your index.html file into a root layout file:

  1. src 폴더 안에 새 app directory를 만듭니다.
  2. 그 app directory 안에 새 layout.tsx 파일을 만듭니다:
  1. Create a new app directory in your src folder.
  2. Create a new layout.tsx file inside that app directory:
TSJSapp/layout.tsx
export default function RootLayout({
  children,
}: {
  children: React.ReactNode
}) {
  return '...'
}
export default function RootLayout({ children }) {
  return '...'
}

Step 5: Create the Entrypoint Page5단계: Entrypoint 페이지 만들기

Next.js에서는 page.tsx 파일을 만들어 애플리케이션의 entrypoint를 선언합니다. Vite에서 이 파일에 가장 가까운 것은 main.tsx 파일입니다. 이 단계에서는 애플리케이션의 entrypoint를 설정합니다.

On Next.js you declare an entrypoint for your application by creating a page.tsx file. The closest equivalent of this file on Vite is your main.tsx file. In this step, you’ll set up the entrypoint of your application.

  1. app directory 안에 [[...slug]] directory를 만듭니다.
  1. Create a [[...slug]] directory in your app directory.

이 가이드에서는 먼저 Next.js를 SPA(Single Page Application)로 설정하는 것을 목표로 하므로, page entrypoint가 애플리케이션의 가능한 모든 route를 받아야(catch) 합니다. 이를 위해 app directory 안에 새 [[...slug]] directory를 만드세요.

Since in this guide we're aiming first to set up our Next.js as an SPA (Single Page Application), you need your page entrypoint to catch all possible routes of your application. For that, create a new [[...slug]] directory in your app directory.

이 directory를 optional catch-all route segment라고 부릅니다. Next.js는 폴더로 route를 정의하는 file-system 기반 router를 사용합니다. 이 특별한 directory는 애플리케이션의 모든 route가 그 안에 있는 page.tsx 파일로 향하도록 해 줍니다.

This directory is what is called an optional catch-all route segment. Next.js uses a file-system based router where folders are used to define routes. This special directory will make sure that all routes of your application will be directed to its containing page.tsx file.

  1. app/[[...slug]] directory 안에 다음 내용으로 새 page.tsx 파일을 만듭니다:
  1. Create a new page.tsx file inside the app/[[...slug]] directory with the following content:
TSJSapp/[[...slug]]/page.tsx
import '../../index.css'

export function generateStaticParams() {
  return [{ slug: [''] }]
}

export default function Page() {
  return '...' // We'll update this
}
import '../../index.css'

export function generateStaticParams() {
  return [{ slug: [''] }]
}

export default function Page() {
  return '...' // We'll update this
}
Good to know

Page 파일에는 .js, .jsx, .tsx 확장자를 사용할 수 있습니다.

.js, .jsx, or .tsx extensions can be used for Page files.

이 파일은 Server Component입니다. next build를 실행하면 이 파일은 static asset으로 prerender됩니다. dynamic 코드는 전혀 필요하지 않습니다.

This file is a Server Component. When you run next build, the file is prerendered into a static asset. It does not require any dynamic code.

이 파일은 global CSS를 import하고, generateStaticParams에 /의 index route 하나만 생성할 것이라고 알려 줍니다.

This file imports our global CSS and tells generateStaticParams we are only going to generate one route, the index route at /.

이제 client에서만 실행될 나머지 Vite 애플리케이션을 옮겨 봅시다.

Now, let's move the rest of our Vite application which will run client-only.

TSJSapp/[[...slug]]/client.tsx
'use client'

import React from 'react'
import dynamic from 'next/dynamic'

const App = dynamic(() => import('../../App'), { ssr: false })

export function ClientOnly() {
  return <App />
}

import React from 'react'
import dynamic from 'next/dynamic'

export function ClientOnly() {
  return <App />
}

이 파일은 'use client' directive로 정의된 Client Component입니다. Client Component도 client로 전송되기 전에 server에서 HTML로 prerender됩니다.

This file is a Client Component, defined by the 'use client' directive. Client Components are still prerendered to HTML on the server before being sent to the client.

우선은 client 전용 애플리케이션으로 시작하고 싶으므로, App component부터 그 아래로는 prerendering을 비활성화하도록 Next.js를 설정할 수 있습니다.

Since we want a client-only application to start, we can configure Next.js to disable prerendering from the App component down.

const App = dynamic(() => import('../../App'), { ssr: false })

이제 entrypoint 페이지가 새 component를 사용하도록 수정하세요:

Step 6: Update Static Image Imports6단계: Static image import 업데이트

Next.js는 static image import를 Vite와 약간 다르게 처리합니다. Vite에서는 이미지 파일을 import하면 그 public URL이 string으로 반환됩니다:

Next.js handles static image imports slightly different from Vite. With Vite, importing an image file will return its public URL as a string:

TSApp.tsx
import image from './img.png' // `image` will be '/assets/img.2d8efhg.png' in production

export default function App() {
  return <img src={image} />
}

Next.js에서는 static image import가 object를 반환합니다. 이 object는 Next.js <Image> component에 바로 사용할 수도 있고, object의 src property를 기존 <img> tag에 사용할 수도 있습니다.

With Next.js, static image imports return an object. The object can then be used directly with the Next.js <Image> component, or you can use the object's src property with your existing <img> tag.

<Image> component에는 자동 이미지 최적화라는 추가 이점이 있습니다. <Image> component는 이미지의 크기를 바탕으로 결과 <img>의 width와 height attribute를 자동으로 설정합니다. 이렇게 하면 이미지가 로드될 때 layout shift가 생기지 않습니다. 하지만 앱에 한쪽 크기만 style이 지정되고 다른 쪽은 auto로 지정되지 않은 이미지가 있으면 문제가 생길 수 있습니다. auto로 지정되지 않으면 그 크기는 <img> 크기 attribute의 값을 기본값으로 사용하므로, 이미지가 찌그러져 보일 수 있습니다.

The <Image> component has the added benefits of automatic image optimization. The <Image> component automatically sets the width and height attributes of the resulting <img> based on the image's dimensions. This prevents layout shifts when the image loads. However, this can cause issues if your app contains images with only one of their dimensions being styled without the other styled to auto. When not styled to auto, the dimension will default to the <img> dimension attribute's value, which can cause the image to appear distorted.

<img> tag를 그대로 두면 애플리케이션의 변경량을 줄이고 위 문제를 막을 수 있습니다. 그런 다음 원한다면 나중에 loader를 설정하거나 자동 이미지 최적화를 제공하는 기본 Next.js server로 옮겨서, 이미지 최적화의 이점을 누리기 위해 <Image> component로 migrate할 수 있습니다.

Keeping the <img> tag will reduce the amount of changes in your application and prevent the above issues. You can then optionally later migrate to the <Image> component to take advantage of optimizing images by configuring a loader, or moving to the default Next.js server which has automatic image optimization.

  1. /public에서 import하는 이미지의 absolute import 경로를 relative import로 바꿉니다:
  1. Convert absolute import paths for images imported from /public into relative imports:
// Before
import logo from '/logo.png'

// After
import logo from '../public/logo.png'
  1. <img> tag에 이미지 object 전체 대신 이미지의 src property를 전달합니다:
  1. Pass the image src property instead of the whole image object to your <img> tag:
// Before
<img src={logo} />

// After
<img src={logo.src} />

또는 파일 이름을 기준으로 이미지 asset의 public URL을 참조할 수도 있습니다. 예를 들어 public/logo.png는 애플리케이션에서 /logo.png로 이미지를 제공하므로, 이 값이 src 값이 됩니다.

Alternatively, you can reference the public URL for the image asset based on the filename. For example, public/logo.png will serve the image at /logo.png for your application, which would be the src value.

Warning

TypeScript를 사용한다면 src property에 접근할 때 type error가 발생할 수 있습니다. 지금은 무시해도 괜찮습니다. 이 가이드가 끝날 때쯤 해결됩니다.

If you're using TypeScript, you might encounter type errors when accessing the src property. You can safely ignore those for now. They will be fixed by the end of this guide.

Step 7: Migrate the Environment Variables7단계: Environment variable migrate하기

Next.js는 Vite와 비슷하게 .env environment variable을 지원합니다. 주요 차이점은 client-side에 environment variable을 노출할 때 사용하는 prefix입니다.

Next.js has support for .env environment variables similar to Vite. The main difference is the prefix used to expose environment variables on the client-side.

  • VITE_ prefix가 붙은 모든 environment variable을 NEXT_PUBLIC_으로 바꾸세요.
  • Change all environment variables with the VITE_ prefix to NEXT_PUBLIC_.

Turbopack은 Vite에 내장된 import.meta.env.MODE, DEV, PROD, BASE_URL, SSR property를 별도 변경 없이 지원합니다. BASE_URL은 Next.js basePath configuration을 반영하며, Vite의 형식과 마찬가지로 끝에 slash가 붙습니다.

Turbopack supports Vite's built-in import.meta.env.MODE, DEV, PROD, BASE_URL, and SSR properties with no changes needed. BASE_URL reflects the Next.js basePath configuration and includes a trailing slash, matching Vite's format.

import.meta.glob 은 Turbopack(Next.js 기본 bundler)에서 별도 변경 없이 지원됩니다.

import.meta.glob is supported by Turbopack (the default Next.js bundler) with no changes needed.

Turbopack에는 Vite의 ?raw, ?url query에 대한 내장 처리가 없으므로, as option(Vite 5에서 deprecated)과 이를 대체하는 query를 쓰려면 next.config.ts에 대응하는 rule이 필요합니다:

Turbopack has no built-in handling for Vite's ?raw and ?url queries, so the as option (deprecated in Vite 5) and its query replacement need a matching rule in next.config.ts:

// Before (Vite)
const modules = import.meta.glob('./dir/*.txt', { as: 'raw' })

// After (Next.js / Turbopack)
const modules = import.meta.glob('./dir/*.txt', { query: '?raw' })
TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  turbopack: {
    rules: {
      // Any file imported with `?raw` is loaded as a string
      '*': { condition: { query: '?raw' }, type: 'text' },
    },
  },
}

export default nextConfig

전체 API는 import.meta.glob 문서를 참고하세요.

See the import.meta.glob docs for the full API.

Vite 애플리케이션에서 custom base URL을 설정했다면, next.config.mjs 파일에 그에 해당하는 basePath를 설정하세요:

If your Vite application configured a custom base URL, set the equivalent basePath in your next.config.mjs file:

JSnext.config.mjs
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'export', // Outputs a Single-Page Application (SPA).
  distDir: './dist', // Changes the build output directory to `./dist/`.
  basePath: '/some-base-path',
}

export default nextConfig

Step 8: Update Scripts in package.json8단계: package.json의 script 업데이트

이제 애플리케이션을 실행해 Next.js로 성공적으로 migrate되었는지 테스트할 수 있을 것입니다. 하지만 그 전에 package.json의 scripts를 Next.js 관련 command로 수정하고, .gitignore에 .next와 next-env.d.ts를 추가해야 합니다:

You should now be able to run your application to test if you successfully migrated to Next.js. But before that, you need to update your scripts in your package.json with Next.js related commands, and add .next and next-env.d.ts to your .gitignore:

package.json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start"
  }
}
>_.gitignore
# ...
.next
next-env.d.ts
dist

Now run npm run dev, and open http://localhost:3000. You should see your application now running on Next.js.
