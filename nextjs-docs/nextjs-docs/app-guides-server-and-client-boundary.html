The Server and Client BoundaryServer와 Client 경계

React Server Components(RSC)는 component tree를 server module graph와 client module graph로 나눕니다. 이 경계가 component 코드가 어디서 실행되는지, 그리고 그 코드가 브라우저로 전달되는지를 결정합니다. RSC는 Server Component를 오직 server에만 두고, Client Component는 interactive UI를 위해 유지합니다. 둘은 하나의 tree 안에서 함께 구성되며, server는 이 tree를 RSC Payload로 render합니다. RSC Payload는 UI를 serialize한 설명으로, 그 안의 Client Component에 대한 reference를 담고 있습니다.

React Server Components (RSC) split a component tree between server and client module graphs. This boundary determines where component code runs and whether that code ships to the browser. RSC keeps Server Components exclusively on the server and retains Client Components for interactive UI. Both compose in a single tree, which the server renders into the RSC Payload, a serialized description of the UI that carries references to the Client Components inside it.

RSC 이전의 React component는 지금 RSC가 Client Component 모델이라고 부르는 방식을 따랐습니다. React는 이런 component를 server에서 HTML로 render할 수 있었지만, 같은 코드가 그 HTML을 hydrate하기 위해 브라우저로도 전달되었습니다. hydration은 초기 HTML을 interactive하게 만들었고, component가 server와 브라우저에서 일치하는 output을 만들어야 했습니다. 완전히 client에서 render되는 앱은 대신 빈 shell로 시작해서 브라우저에서 component tree를 mount할 수 있었습니다.

Before RSC, React components followed what RSC now calls the Client Component model. React could render these components to HTML on the server, but the same code also shipped to the browser to hydrate that HTML. Hydration made the initial HTML interactive and required the component to produce matching output on the server and in the browser. Apps rendered entirely on the client could instead begin with an empty shell and mount the component tree in the browser.

├─ Server Component
└─ Client Component
   └─ Client Component

각 component의 module은 server module graph, client module graph, 또는 둘 다에 속합니다. 두 graph 모두에서 사용되는 module은 Next.js가 각 환경용으로 따로 compile합니다.

Each component's module belongs to the server module graph, the client module graph, or both. Next.js compiles a module used by both graphs separately for each environment.

rendering 중에 server graph는 Client Component에 대한 reference를 만들고 그 component에 전달되는 props를 serialize합니다. client graph는 server graph를 import하지 않습니다. client graph는 RSC Payload를 통해 reference와 serialize된 props를 받습니다.

During rendering, the server graph produces references to Client Components and serializes the props passed to them. The client graph does not import the server graph. The client graph receives the references and serialized props through the RSC Payload.

Rendering environmentsRendering 환경

component 이름만 보면 server와 브라우저가 깔끔하게 나뉘는 것 같지만, rendering은 양쪽 모두에서 일어납니다. server에서는 Server Component tree가 RSC Payload를 만듭니다. Next.js는 이 payload와 Client Component를 사용해 build 시점이나 request를 처리하는 동안 HTML을 render합니다.

The component names suggest a clean split between server and browser, but rendering happens in both places. On the server, the Server Component tree produces the RSC Payload. Next.js uses the payload and Client Components to render HTML at build time or while handling a request.

component가 어디서 실행되는지 판단할 때는, server render와 함께 그 코드가 브라우저에서도 실행되는지를 모두 고려하세요:

When deciding where a component runs, consider both its server render and whether its code runs in the browser:

"Client"라는 단어는 Client Component가 server render에 더해 브라우저에서도 실행된다는 뜻입니다.

The word "Client" indicates that a Client Component also runs in the browser, alongside its server render.

직접 방문할 경우, 다음 Client Component는 server에서 render되고 hydration 중에 브라우저에서 다시 render됩니다. 그래서 log가 terminal과 브라우저 console 양쪽에 나타납니다. client-side navigation에서는 server가 RSC Payload를 보내고, component는 server-rendered HTML 없이 브라우저에서 render됩니다.

On a direct visit, the following Client Component renders on the server and again in the browser during hydration. Its log appears in the terminal and the browser console. On a client-side navigation, the server sends the RSC Payload, and the component renders in the browser without server-rendered HTML.

TSJSapp/hello.tsx
'use client'

export default function Hello() {
  console.log('Hello rendered') // on a direct visit: server, then browser
  return <p>Hello</p>
}
'use client'

export default function Hello() {
  console.log('Hello rendered') // on a direct visit: server, then browser
  return <p>Hello</p>
}

Client Component를 server에서 render하면 HTML이 만들어지지만, 그 component는 여전히 Client Component입니다.

Rendering a Client Component on the server produces HTML, but the component remains a Client Component.

Client Component를 HTML로 render하는 것은 RSC보다 먼저 있었습니다. route에 따라 Next.js는 다음 시점에 HTML을 생성하거나 재생성할 수 있습니다:

Rendering Client Components to HTML predates RSC. Depending on the route, Next.js can generate or regenerate HTML:

  • Static Site Generation (SSG)으로 build 시점에.
  • Incremental Static Regeneration (ISR)으로 build 이후에.
  • server-side rendering(SSR)으로 request마다.
  • At build time with Static Site Generation (SSG).
  • After the build with Incremental Static Regeneration (ISR).
  • For each request with server-side rendering (SSR).

RSC는 이와 별개의 과정으로, Server Component 코드를 server에 두고 그 코드를 전달하는 대신 RSC Payload를 내보냅니다. "Server-rendered"는 Next.js가 HTML을 어떻게 만들었는지를 설명합니다. "Server Component"는 component 코드가 어디서 실행되는지, 그리고 그 코드가 브라우저로 전달되는지를 설명합니다.

RSC is a separate process that keeps Server Component code on the server and emits the RSC Payload instead of shipping that code. "Server-rendered" describes how Next.js produced the HTML. "Server Component" describes where the component code runs and whether that code ships to the browser.

Server Components and SEO

HTML만 읽는 crawler는 첫 response만 보며 JavaScript는 전혀 실행하지 않습니다. Server Component와 Client Component 모두 그 response의 HTML에 기여합니다.

SEO는 server render가 콘텐츠까지 도달하느냐에 달려 있습니다. 사용자 상호작용이나 event 뒤에 가려진 콘텐츠는 JavaScript를 실행하지 않는 crawler가 볼 수 있는 HTML에 나타나지 않습니다.

Server Components and SEO

A crawler that reads only HTML sees the first response and runs none of your JavaScript. Both Server and Client Components contribute HTML to that response.

SEO depends on whether the server render reaches the content. Content gated behind user interaction or an event does not appear in the HTML available to a crawler that does not run JavaScript.

component가 build 시점에 render되는지 request마다 render되는지, static인지 dynamic인지에 대한 자세한 내용은 Rendering Philosophy를 참고하세요.

See Rendering Philosophy for details about when a component renders, whether at build time or per request, statically or dynamically.

How data enters the tree데이터가 tree에 들어오는 방식

RSC 이전에 Next.js 애플리케이션은 보통 getStaticProps나 getServerSideProps 같은 함수로 server 데이터를 모은 다음, props로 component tree에 전달했습니다. data fetching은 tree가 render되기 전에 일어났습니다. tree는 render 중에 데이터를 fetch하는 대신 데이터를 전달받았습니다.

Before RSC, Next.js applications typically gathered server data with functions such as getStaticProps or getServerSideProps, then passed it to the component tree as props. Data fetching happened before the tree rendered. The tree received data instead of fetching it during render.

Server Component는 server에서만 실행되므로 database, filesystem, 내부 service, secret 같은 자원에 접근할 수 있습니다. component는 데이터를 먼저 client에 노출하는 API route 없이, 자신의 render 중에 이런 자원을 읽습니다.

Because a Server Component runs only on the server, it can access resources such as a database, the filesystem, an internal service, or a secret. The component reads these resources during its own render, without an API route that exposes the data to the client first.

TSJSapp/page.tsx
import { PostList } from '@/app/ui/post-list'
import { getPosts } from '@/lib/data'

export default async function Page() {
  const posts = await getPosts() // runs on the server, during render
  return <PostList posts={posts} />
}
import { PostList } from '@/app/ui/post-list'
import { getPosts } from '@/lib/data'

export default async function Page() {
  const posts = await getPosts() // runs on the server, during render
  return <PostList posts={posts} />
}

RSC에서는 Server Component가 render하면서 데이터를 fetch할 수 있습니다. 별도의 데이터 로딩 단계가 component tree에 초기 props를 전달할 필요가 없습니다.

With RSC, a Server Component can fetch data while rendering. A separate data-loading step does not need to pass initial props to the component tree.

Good to know

Server Component는 secret과 server 전용 데이터를 직접 읽을 수 있으므로, Client Component에 무엇을 전달할지 신중하게 결정하세요.

props는 serialize되어 브라우저로 전송됩니다. Data Security를 참고하세요.

Because a Server Component can read secrets and server-only data directly, be deliberate about what you pass to Client Components.

Props are serialized and sent to the browser. See Data Security.

Server Component는 UI를 반환하기 전에 모든 데이터를 await할 필요가 없습니다. server에서 fetch한 데이터를 Client Component로 stream하려면, Server Component에서 request를 시작하고 pending 상태의 promise를 prop으로 전달하세요.

Server Components do not have to await all data before returning UI. To stream server-fetched data into a Client Component, start the request in a Server Component and pass the pending promise as a prop.

Client Component는 use로 promise를 resource로서 읽습니다. promise가 pending인 동안에는 가장 가까운 Suspense boundary가 fallback을 보여 줍니다. promise가 resolve되면 Client Component가 render됩니다.

The Client Component reads the promise as a resource with use. While the promise is pending, the nearest Suspense boundary shows its fallback. The Client Component renders when the promise resolves.

request가 client가 실행되기 전에 시작되므로, Client Component는 mount 이후 같은 데이터를 fetch할 필요가 없습니다. 다만 request할 데이터가 client 전용 state나 사용자 상호작용에 의존한다면 여전히 브라우저에서 fetch를 시작해야 할 수 있습니다.

Because the request starts before the client runs, the Client Component does not need to fetch the same data after mount. You may still need to start a fetch in the browser when the requested data depends on client-only state or user interaction.

동일한 fetch request는 server render 중에 memoize됩니다. Cache Components를 사용하면 데이터 함수나 component를 cache하고, 그 entry를 page의 나머지 부분과 독립적으로 revalidate할 수 있습니다. 구현 패턴은 Fetching Data를 참고하세요.

Identical fetch requests are memoized during a server render. With Cache Components, you can cache a data function or component and revalidate that entry independently of the rest of the page. For implementation patterns, see Fetching Data.

State and interactivityState와 interactivity

Server Component의 코드는 절대 브라우저에 도달하지 않습니다. 이 component는 navigation, refresh, revalidation 이후처럼 Next.js가 route를 render할 때 다시 render될 수 있습니다.

A Server Component's code never reaches the browser. The component can render again when Next.js renders the route, such as during a navigation, refresh, or after revalidation.

Client Component의 코드는 브라우저에 도달합니다. React는 초기 로드 때 component를 hydrate하고, client-side 업데이트가 브라우저에서 component를 다시 render할 수 있습니다.

A Client Component's code does reach the browser. React hydrates the component on the initial load, and client-side updates can re-render it in the browser.

Good to know

초기 로드 때 RSC Payload는 HTML과 함께 전달됩니다.

Server Component의 DOM node를 직접 변경하면 DOM이 React의 component tree와 어긋날 수 있습니다.

Server Component output을 업데이트하려면 server에서 component를 다시 render하세요. 브라우저가 새 RSC Payload를 받으면 React가 component tree를 reconcile하고 DOM을 업데이트합니다. Streaming을 참고하세요.

On the initial load, the RSC Payload ships with the HTML.

Mutating Server Component DOM nodes directly can put the DOM out of sync with React's component tree.

To update Server Component output, render the component again on the server. When the browser receives a new RSC Payload, React reconciles the component tree and updates the DOM. See Streaming.

useState, useEffect, event handler에는 브라우저에서 실행되며 업데이트에 반응하는 코드가 필요합니다. Server Component 코드는 절대 브라우저에 도달하지 않으므로 이런 client-side API를 사용할 수 없습니다.

useState, useEffect, and event handlers require code that runs in the browser and responds to updates. Server Component code never reaches the browser, so it cannot use these client-side APIs.

브라우저와 HTML의 내장 동작은 Client Component 없이도 interactivity를 제공할 수 있습니다. 예를 들면:

Built-in browser and HTML behavior can provide interactivity without a Client Component. For example:

  • <details> element는 열리고 닫힙니다.
  • <form>은 action prop에 전달된 Server Function을 통해 submit할 수 있습니다.
  • <video controls> element는 재생하고 일시정지할 수 있습니다.
  • A <details> element opens and closes.
  • A <form> can submit through a Server Function passed to its action prop.
  • A <video controls> element plays and pauses.

controlled input, 실시간 filter, drag handle처럼 시간에 따라 변하는 브라우저 state가 필요한 동작이라면 Client Component를 사용하세요. 필요한 동작을 브라우저가 모두 제공한다면 button이나 form에 Client Component가 필요하지 않습니다.

Use a Client Component when the behavior requires browser state that changes over time, such as a controlled input, live filter, or drag handle. A button or form does not require a Client Component when the browser provides all the required behavior.

각 환경에 무엇이 속하는지에 대한 실용적인 목록은 When to use Server and Client Components를 참고하세요.

For the practical list of what belongs in each environment, see When to use Server and Client Components.

Crossing the boundary경계 넘기

파일 맨 위, 모든 import보다 앞에 'use client' directive를 추가하면 그 module을 client entry point로 표시할 수 있습니다. 이 directive는 module graph에 경계를 그으며, 무엇이 경계를 넘는지는 두 가지 규칙으로 결정됩니다:

You mark a module as a client entry point by adding the 'use client' directive at the top of the file, before any imports. The directive draws a boundary in the module graph, and two rules determine what crosses it:

  • 코드는 import를 통해 넘어갑니다. Client Component가 import하는 것은 무엇이든 client bundle에 포함됩니다.
  • 데이터는 props를 통해 넘어가며, serializable해야 하므로 event handler 같은 함수는 넘어갈 수 없습니다.
  • Code crosses through imports. Whatever a Client Component imports is pulled into the client bundle.
  • Data crosses through props, and it must be serializable, so functions like event handlers cannot cross.
Good to know

Server Component에서 Client Component로 함수를 prop으로 전달하면 오류가 throw됩니다. onClick 같은 event handler는 넘어갈 수 없습니다. 'use server'로 표시된 Server Function은 reference로서 넘어갑니다.

Server Function은 type만으로는 일반 함수와 구별할 수 없습니다. TypeScript plugin은 이름이 action이거나 Action으로 끝나는 경우에 한해 함수 type의 Client Component prop을 허용합니다. 그 외의 함수 props는 plugin이 경고로 표시합니다.

Passing a function as a prop from a Server Component to a Client Component throws. An event handler like onClick cannot cross. A Server Function marked with 'use server' crosses as a reference.

A Server Function is not distinguishable from a plain function by its type. The TypeScript plugin allows a Client Component prop typed as a function when its name is action or ends in Action. The plugin flags other function props.

render된 React element는 serializable한 데이터이므로 경계를 넘을 수 있습니다. render된 output을 children으로 전달하면 Server Component의 코드를 client graph로 import하지 않고도 Server Component를 Client Component 안에 중첩할 수 있습니다.

A rendered React element can cross the boundary because it is serializable data. Passing rendered output as children lets a Server Component nest inside a Client Component without importing the Server Component's code into the client graph.

TSJSapp/page.tsx
import { Cart } from '@/app/ui/cart'
import { Modal } from '@/app/ui/modal'

// Page and Cart are Server Components. Modal is a Client Component
export default function Page() {
  return (
    <Modal title={<div>Your cart</div>}>
      <Cart />
    </Modal>
  )
}
import { Cart } from '@/app/ui/cart'
import { Modal } from '@/app/ui/modal'

// Page and Cart are Server Components. Modal is a Client Component
export default function Page() {
  return (
    <Modal title={<div>Your cart</div>}>
      <Cart />
    </Modal>
  )
}

children prop은 다른 prop과 똑같이 동작합니다. Modal은 title과 children을 serialize된 React element로 받은 다음, 자신의 구현이 정의한 위치에 render합니다.

The children prop behaves like any other prop. Modal receives title and children as serialized React elements, then renders them in the positions defined by its implementation.

TSJSapp/ui/modal.tsx
'use client'

import { useState, type ReactNode } from 'react'

export function Modal({
  title,
  children,
}: {
  title: ReactNode
  children: ReactNode
}) {
  const [open, setOpen] = useState(true)
  if (!open) return null

  return (
    <div role="dialog">
      <header>
        {title}
        <button onClick={() => setOpen(false)}>Close</button>
      </header>
      {children}
    </div>
  )
}
'use client'

import { useState } from 'react'

export function Modal({ title, children }) {
  const [open, setOpen] = useState(true)
  if (!open) return null

  return (
    <div role="dialog">
      <header>
        {title}
        <button onClick={() => setOpen(false)}>Close</button>
      </header>
      {children}
    </div>
  )
}

여기서 Cart는 server에서 실행되고, Modal은 Cart의 코드가 아니라 output만 보게 됩니다.

Here, Cart runs on the server, and Modal only ever sees its output, never its code.

Owner와 parent

이 예제에서 Page는 React가 구분해서 다루는 두 가지 역할을 보여 줍니다:

  • owner는 자식의 JSX를 source에 담고 있는 component입니다. Page는 Modal과 Cart 모두의 owner입니다.
  • parent는 render된 tree에서 자식을 직접 감싸는 component입니다. Modal은 Cart의 parent입니다.

Cart의 owner가 Server Component이므로 Cart는 server에서 render됩니다. Modal은 parent일 뿐이므로, 배치할 Cart의 output은 받지만 실행할 코드는 받지 않습니다. 이 분리 덕분에 Client Component는 import한 적 없는 Server Component를 표시할 수 있습니다.

경계를 넘나드는 compound component

compound component는 Menu.Item이나 Tabs.Panel처럼 하위 component를 static property로 노출할 수 있습니다. 이 패턴은 모든 조각이 Server Component이거나 모든 조각이 Client Component인 하나의 graph 안에서는 잘 동작합니다.

static member가 경계를 넘으면 이 패턴은 깨집니다. Client Component를 import하는 Server Component는 함수 대신 client reference를 받습니다. 그 결과 Menu.Item은 undefined가 되고 React가 "Element type is invalid." 오류를 throw합니다.

compound Client Component는 다른 Client Component에서 사용하세요. Server Component에서 그 조각들을 사용하려면 static property 대신 named export로 노출하세요.

'use client'는 client subtree의 진입점에만 필요하며, 그 안의 모든 파일에 붙일 필요는 없습니다. 그 진입점에서 import되는 모든 module은 client module graph의 일부가 됩니다.

You only need 'use client' at the entry to a client subtree, not on every file inside it. Every module imported from that entry becomes part of the client module graph.

공유 component를 수정하지 않고 두려면, 그것을 import하는 Client Component wrapper를 만들고 directive를 wrapper에 두세요. wrapper는 공유 module을 그대로 유지하면서 경계를 애플리케이션 코드에 더 가깝게 둡니다. 또한 useState나 useEffect를 호출하는 모든 공유 component에 directive를 추가하지 않아도 됩니다.

To leave a shared component unchanged, create a Client Component wrapper that imports it and place the directive on the wrapper. The wrapper keeps the shared module unchanged and puts the boundary closer to your application code. It also avoids adding the directive to every shared component that calls useState or useEffect.

client 코드가 경계 없이 server graph에 들어오면, compiler가 directive가 필요한 위치를 알려 줍니다.

If client code enters the server graph without a boundary, the compiler points to where you need the directive.
