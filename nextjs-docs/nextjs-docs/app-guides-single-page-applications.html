How to build single-page applications with Next.jsNext.js로 Single-Page Application 만들기

client-side navigation과 data fetching으로 Single-Page Application(SPA)을 만들어 보세요. Next.js는 같은 앱 안에서 client 패턴과 server 패턴을 모두 지원하며, 기존 SPA를 전부 다시 작성하지 않고도 migrate할 수 있습니다.

Build Single-Page Applications (SPAs) with client-side navigation and data fetching. Next.js supports client and server patterns in the same app, and existing SPAs can migrate without a full rewrite.

What is a Single-Page Application?Single-Page Application이란?

SPA의 정의는 다양합니다. 여기서는 "strict SPA"를 다음과 같이 정의합니다:

The definition of a SPA varies. We'll define a "strict SPA" as:

  • Client-side rendering (CSR): 앱이 하나의 HTML 파일(예: index.html)로 제공됩니다. 모든 route, page 전환, data fetch를 브라우저의 JavaScript가 처리합니다.
  • 전체 page reload 없음: route마다 새 document를 request하는 대신, client-side JavaScript가 현재 page의 DOM을 조작하고 필요에 따라 데이터를 fetch합니다.
  • Client-side rendering (CSR): The app is served by one HTML file (e.g. index.html). Every route, page transition, and data fetch is handled by JavaScript in the browser.
  • No full-page reloads: Rather than requesting a new document for each route, client-side JavaScript manipulates the current page's DOM and fetches data as needed.

strict SPA는 page가 interactive해지기 전에 많은 양의 JavaScript를 로드해야 하는 경우가 많습니다. 게다가 client 데이터 waterfall은 관리하기 어려울 수 있습니다. Next.js로 SPA를 만들면 이런 문제를 해결할 수 있습니다.

Strict SPAs often require large amounts of JavaScript to load before the page can be interactive. Further, client data waterfalls can be challenging to manage. Building SPAs with Next.js can address these issues.

Why use Next.js for SPAs?SPA에 Next.js를 쓰는 이유

Next.js는 JavaScript bundle을 자동으로 code split하고, 여러 route에 대한 여러 HTML entry point를 생성할 수 있습니다. 이렇게 하면 client-side에서 불필요한 JavaScript 코드를 로드하지 않게 되어 bundle 크기가 줄고 page 로드가 빨라집니다.

Next.js can automatically code split your JavaScript bundles, and generate multiple HTML entry points into different routes. This avoids loading unnecessary JavaScript code on the client-side, reducing the bundle size and enabling faster page loads.

next/link component는 route를 자동으로 prefetch하므로, strict SPA처럼 빠른 page 전환을 제공하면서도 애플리케이션 routing state를 URL에 유지해 링크하고 공유할 수 있다는 이점까지 갖습니다.

The next/link component automatically prefetches routes, giving you the fast page transitions of a strict SPA, but with the advantage of persisting application routing state to the URL for linking and sharing.

Next.js는 static site로, 또는 모든 것을 client-side에서 render하는 strict SPA로도 시작할 수 있습니다. 프로젝트가 커지면 필요에 따라 server 기능(예: React Server Components, Server Actions 등)을 점진적으로 추가할 수 있습니다.

Next.js can start as a static site or even a strict SPA where everything is rendered client-side. If your project grows, you can progressively add more server features (e.g. React Server Components, Server Actions, and more) as needed.

Build common SPA patterns흔한 SPA 패턴 만들기

다음 예제들은 Next.js로 SPA를 만들 때 흔히 쓰는 패턴을 다룹니다. 함께 제공되는 demo(source)에서 각 패턴이 실제로 동작하는 모습을 볼 수 있습니다.

The following examples cover common patterns for building an SPA with Next.js. The companion demo (source) shows each pattern in action.

Using React's use within a Context ProviderContext Provider 안에서 React의 use 사용하기

React의 use API를 사용하면 server에서 Client Component로 데이터를 stream할 수 있습니다. Server Component(parent나 layout)에서 데이터를 fetch하고 Promise를 아래로 전달하세요. Client Component는 render 중에 await할 수 없으므로 use()로 Promise를 unwrap합니다.

You can use React's use API to stream data from the server to a Client Component. Fetch the data in a Server Component (a parent or layout) and pass the Promise down. The Client Component unwraps it with use(), since it cannot await during render.

앱의 나머지 부분이 render되기 전에 server에서 request를 시작하면 response가 즉시 stream되고 client-side request waterfall을 피할 수 있습니다.

Starting the request on the server, before the rest of the app renders, lets the response stream immediately and avoids client-side request waterfalls.

하나의 Promise를 prop으로 전달해 use()로 unwrap할 수도 있고, React context provider와 짝지어 어떤 Client Component든 custom hook으로 값을 읽게 할 수도 있습니다.

You can pass a single Promise as a prop and unwrap it with use(), or pair it with a React context provider so any Client Component can read the value through a custom hook.

Client Component에 focus revalidation, polling, mutation, request deduplication이 필요하다면 SWR이나 TanStack Query 같은 library를 사용하세요. 브라우저에서 직접 fetch하는 방법, Server Component에서 초기 데이터를 제공하는 방법, library cache를 Next.js server cache 및 client cache와 조율하는 방법은 Client-side data fetching을 참고하세요.

When a Client Component needs focus revalidation, polling, mutations, or request deduplication, use a library such as SWR or TanStack Query. See Client-side data fetching for direct browser fetching, providing initial data from a Server Component, and coordinating the library cache with the Next.js server and client caches.

Server Component(여기서는 root layout)에서 await하지 않고 request를 시작한 뒤, Promise를 provider에 전달하세요:

Start the request in a Server Component (here, the root layout) without awaiting it, and pass the Promise to the provider:

TSJSapp/layout.tsx
import { UserProvider } from './user-provider'
import { getUser } from './user' // some server-side function

export default function RootLayout({ children }: LayoutProps<'/'>) {
  let userPromise = getUser() // do NOT await

  return (
    <html lang="en">
      <body>
        <UserProvider userPromise={userPromise}>{children}</UserProvider>
      </body>
    </html>
  )
}

Good to know

tree 상위에서 설정한 Promise를 다시 fetch하면 그것을 설정한 Server Component가 다시 실행됩니다. 따라서 앱의 일부만 필요로 하는 데이터라면 provider를 root layout 대신 해당 subtree에 두세요. React의 context에서 Promise를 읽을 때의 주의 사항을 참고하세요.

Refetching a Promise set high in the tree re-runs the Server Component that set it, so for data only part of the app needs, place the provider on that subtree instead of the root layout. See React's caveat on reading a Promise from context.

여러 component가 한 request 안에서 같은 데이터를 읽는다면, getUser를 React의 cache로 감싸서 한 번의 호출을 공유하게 하세요. 이 패턴에 대한 자세한 내용은 Reusing data with React.cache를 참고하세요.

If several components read the same data in one request, wrap getUser in React's cache so they share a single call. See Reusing data with React.cache for more on this pattern.

provider는 context를 통해 Promise를 전달합니다:

The provider forwards the Promise through context:

TSJSapp/user-provider.tsx
'use client'

import { createContext, useContext } from 'react'

type User = { id: string; name: string }

const UserContext = createContext<Promise<User> | null>(null)

export function useUser() {
  const userPromise = useContext(UserContext)
  if (!userPromise) {
    throw new Error('useUser must be used within a UserProvider')
  }
  return userPromise
}

export function UserProvider({
  children,
  userPromise,
}: {
  children: React.ReactNode
  userPromise: Promise<User>
}) {
  return (
    <UserContext.Provider value={userPromise}>{children}</UserContext.Provider>
  )
}

마지막으로 어떤 Client Component에서든 useUser() hook을 호출하고 use()로 Promise를 unwrap하세요. use()는 데이터가 준비될 때까지 component를 suspend합니다:

Finally, call the useUser() hook in any Client Component and unwrap the Promise with use(), which suspends the component until the data is ready:

'use client'

import { use } from 'react'

export function Profile() {
  const userPromise = useUser()
  const user = use(userPromise)

  return <p>{user.name}</p>
}

Promise가 resolve되는 동안 fallback을 보여 주려면 consumer를 <Suspense> boundary로 감싸세요:

Wrap the consumer in a <Suspense> boundary to show a fallback while the Promise resolves:

TSJSapp/page.tsx
import { Suspense } from 'react'
import { Profile } from './profile'

export default function Page() {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      <Profile />
    </Suspense>
  )
}
import { Suspense } from 'react'
import { Profile } from './profile'

export default function Page() {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      <Profile />
    </Suspense>
  )
}

Promise를 소비하는 component(예: 위의 Profile)는 Promise가 resolve되는 동안 suspend되므로, JavaScript 로딩이 끝나기 전에 stream된 prerender HTML을 볼 수 있습니다.

The component that consumes the Promise (e.g. Profile above) suspends while the Promise resolves, so you see the streamed, prerendered HTML before JavaScript has finished loading.

Rendering components only in the browser브라우저에서만 component render하기

Client component는 next build 중에 prerender됩니다. Client Component의 prerendering을 비활성화하고 브라우저 환경에서만 로드하고 싶다면 next/dynamic을 사용할 수 있습니다:

Client components are prerendered during next build. If you want to disable prerendering for a Client Component and only load it in the browser environment, you can use next/dynamic:

import dynamic from 'next/dynamic'

const ClientOnlyComponent = dynamic(() => import('./component'), {
  ssr: false,
})

이는 window나 document 같은 브라우저 API에 의존하는 third-party library에 유용할 수 있습니다. 또는 이런 API가 존재하는지 확인하는 useEffect를 추가하고, 존재하지 않으면 null이나 prerender될 loading state를 반환하게 할 수도 있습니다.

This can be useful for third-party libraries that rely on browser APIs like window or document. You can also add a useEffect that checks for the existence of these APIs, and if they do not exist, return null or a loading state which would be prerendered.

React 19.3에는 browser API가 포함되어 있습니다. use(browser())는 Client Component의 첫 브라우저 render가 server-rendered HTML과 일치할 수 없는 경우에만 사용하세요.

React 19.3 includes the browser API. Use use(browser()) only when a Client Component's first browser render cannot match server-rendered HTML.

prerendering 중에 use(browser())는 가장 가까운 <Suspense> boundary까지 suspend합니다. fallback이 component의 초기 HTML이 되므로, JavaScript를 실행하지 않는 crawler는 component 대신 fallback을 보게 됩니다. index되어야 하는 콘텐츠는 browser 전용 boundary 바깥에 두세요.

During prerendering, use(browser()) suspends to the closest <Suspense> boundary. The fallback becomes the component's initial HTML, so crawlers that don't execute JavaScript see the fallback instead of the component. Keep content that should be indexed outside the browser-only boundary.

예를 들어, 이 editor는 localStorage에서 저장된 draft를 읽습니다:

For example, this editor reads a saved draft from localStorage:

JSapp/browser-only-editor.jsx
'use client'

import { use, useState } from 'react'
import { browser } from 'react-dom'

export default function BrowserOnlyEditor() {
  use(browser('The saved draft is stored in localStorage.'))

  const [draft, setDraft] = useState(() => localStorage.getItem('draft') ?? '')

  function handleChange(event) {
    const nextDraft = event.target.value
    setDraft(nextDraft)
    localStorage.setItem('draft', nextDraft)
  }

  return <textarea value={draft} onChange={handleChange} />
}

그다음 Suspense boundary로 감싸세요:

Then wrap it in a Suspense boundary:

JSapp/page.jsx
import { Suspense } from 'react'
import BrowserOnlyEditor from './browser-only-editor'

export default function Page() {
  return (
    <Suspense fallback={<p>Loading editor…</p>}>
      <BrowserOnlyEditor />
    </Suspense>
  )
}

브라우저에서는 browser()가 undefined를 반환하고, editor는 저장된 draft와 함께 render됩니다.

In the browser, browser() returns undefined, and the editor renders with the saved draft.

Shallow routing on the clientClient에서의 shallow routing

Create React App이나 Vite 같은 strict SPA에서 migrate하는 중이라면, URL state를 업데이트하기 위해 shallow routing하는 기존 코드가 있을 수 있습니다. 이는 기본 Next.js file-system routing을 사용하지 않고 애플리케이션 안의 view 사이를 수동으로 전환할 때 유용할 수 있습니다.

If you are migrating from a strict SPA like Create React App or Vite, you might have existing code which shallow routes to update the URL state. This can be useful for manual transitions between views in your application without using the default Next.js file-system routing.

Next.js에서는 native window.history.pushState와 window.history.replaceState method를 사용해 page를 reload하지 않고 브라우저의 history stack을 업데이트할 수 있습니다.

Next.js lets you use the native window.history.pushState and window.history.replaceState methods to update the browser's history stack without reloading the page.

pushState와 replaceState 호출은 Next.js Router와 통합되므로 usePathname, useSearchParams와 동기화할 수 있습니다.

The pushState and replaceState calls integrate into the Next.js Router, allowing you to sync with usePathname and useSearchParams.

TSJSapp/ui/sort-products.tsx
'use client'

import { useSearchParams } from 'next/navigation'

export default function SortProducts() {
  const searchParams = useSearchParams()

  function updateSorting(sortOrder: string) {
    const urlSearchParams = new URLSearchParams(searchParams.toString())
    urlSearchParams.set('sort', sortOrder)
    window.history.pushState(null, '', `?${urlSearchParams.toString()}`)
  }

  return (
    <>
      <button onClick={() => updateSorting('asc')}>Sort Ascending</button>
      <button onClick={() => updateSorting('desc')}>Sort Descending</button>
    </>
  )
}

Mutating data with Server ActionsServer Action으로 데이터 변경하기

interactivity에는 흔히 데이터 쓰기가 필요합니다. Client Component는 Server Action을 호출해 server에서 mutation을 실행할 수 있습니다. client-side data fetching 가이드에서 보여 주듯이, client data-fetching library가 같은 Server Action을 중심으로 브라우저의 optimistic 업데이트를 조율할 수도 있습니다. 이 섹션의 나머지 부분에서는 React의 내장 state API로 Server Action을 조율합니다.

Interactivity often requires writing data. A Client Component can call a Server Action to run the mutation on the server. A client data-fetching library can coordinate an optimistic browser update around the same Server Action, as shown in the client-side data fetching guide. The rest of this section coordinates the Server Action with React's built-in state APIs.

Server Action은 시간이 걸리고 실패할 수도 있습니다. React에는 action이 실행되는 동안 UI의 반응성을 유지해 주는 유용한 도구가 있어서, mutation이 client-rendered SPA처럼 즉각적으로 느껴지게 할 수 있습니다: transitions, useOptimistic, useActionState, useFormStatus.

A Server Action takes time and can fail. React has useful tools to keep the UI responsive while it runs, so a mutation can feel as instant as a client-rendered SPA: transitions, useOptimistic, useActionState, and useFormStatus.

가장 단순하게는, Client Component가 transition 안에서 Server Action을 호출하고 pending state로 피드백을 보여 줍니다:

At its simplest, a Client Component calls a Server Action inside a transition and uses the pending state for feedback:

TSJSapp/delete-post.tsx
'use client'

import { useTransition } from 'react'
import { deletePost } from './actions'

export function DeletePost({ id }: { id: string }) {
  const [isPending, startTransition] = useTransition()

  return (
    <button
      disabled={isPending}
      onClick={() => startTransition(() => deletePost(id))}
    >
      {isPending ? 'Deleting…' : 'Delete'}
    </button>
  )
}

변경 사항이 즉시 나타나야 하는 목록 형태의 state라면 useActionState와 useOptimistic을 조합할 수 있습니다. 아래 예제는 to-do 목록입니다: 순수 reducer가 각 action이 목록을 어떻게 바꾸는지 정의하므로, client와 server가 그 로직의 사본 하나를 공유합니다:

For list-like state where each change should appear instantly, you can combine useActionState with useOptimistic. The example below is a to-do list: a pure reducer defines how each action changes the list, so the client and server share one copy of that logic:

TSJSapp/todos-reducer.ts
export type Todo = { id: string; text: string; done: boolean }

export type TodoAction =
  | { type: 'add'; id: string; text: string }
  | { type: 'toggle'; id: string }
  | { type: 'edit'; id: string; text: string }
  | { type: 'delete'; id: string }

export function todosReducer(todos: Todo[], action: TodoAction): Todo[] {
  switch (action.type) {
    case 'add':
      return [...todos, { id: action.id, text: action.text, done: false }]
    case 'toggle':
      return todos.map((todo) =>
        todo.id === action.id ? { ...todo, done: !todo.done } : todo
      )
    case 'edit':
      return todos.map((todo) =>
        todo.id === action.id ? { ...todo, text: action.text } : todo
      )
    case 'delete':
      return todos.filter((todo) => todo.id !== action.id)
    default:
      return todos
  }
}
export function todosReducer(todos, action) {
  switch (action.type) {
    case 'add':

      )
    case 'edit':

        todo.id === action.id ? { ...todo, text: action.text } : todo
      )
    case 'delete':
      return todos.filter((todo) => todo.id !== action.id)

      return todos
  }
}

Server Action은 reducer를 적용하고, 결과를 저장한 뒤, 다음 목록을 반환합니다:

The Server Action applies the reducer, persists the result, and returns the next list:

TSJSapp/actions.ts
'use server'

import { db } from './db'
import { todosReducer, type Todo, type TodoAction } from './todos-reducer'

export async function saveTodos(
  todos: Todo[],
  action: TodoAction
): Promise<Todo[]> {
  const next = todosReducer(todos, action)
  await db.saveTodos(next)
  return next
}

import { db } from './db'
import { todosReducer } from './todos-reducer'

client는 같은 reducer를 useOptimistic에 전달하므로, optimistic 업데이트와 server가 다음 state를 똑같이 계산합니다. runAction helper는 같은 transition 안에서 optimistic 변경을 적용하고 Server Action을 dispatch하므로, 모든 변경 사항이 즉시 표시됩니다:

The client passes the same reducer to useOptimistic, so the optimistic update and the server compute the next state identically. A runAction helper applies the optimistic change and dispatches the Server Action in the same transition, so every change shows immediately:

TSJSapp/todo-list.tsx
'use client'

import { useActionState, useOptimistic, startTransition } from 'react'
import { saveTodos } from './actions'
import { todosReducer, type Todo, type TodoAction } from './todos-reducer'

export function TodoList({ initialTodos }: { initialTodos: Todo[] }) {
  const [todos, dispatch, isPending] = useActionState(saveTodos, initialTodos)
  const [optimisticTodos, addOptimistic] = useOptimistic(todos, todosReducer)

  function runAction(action: TodoAction) {
    startTransition(() => {
      addOptimistic(action)
      dispatch(action)
    })
  }

  return (
    <>
      <form
        action={(formData) =>
          runAction({
            type: 'add',
            id: crypto.randomUUID(),
            text: String(formData.get('text')),
          })
        }
      >
        <input name="text" />

'use client'

import { useActionState, useOptimistic, startTransition } from 'react'
import { saveTodos } from './actions'
import { todosReducer } from './todos-reducer'

export function TodoList({ initialTodos }) {
  const [todos, dispatch, isPending] = useActionState(saveTodos, initialTodos)
  const [optimisticTodos, addOptimistic] = useOptimistic(todos, todosReducer)

  function runAction(action) {
    startTransition(() => {
      addOptimistic(action)
      dispatch(action)
    })
  }

  return (
    <>
      <form
        action={(formData) =>
          runAction({
            type: 'add',
            id: crypto.randomUUID(),
            text: String(formData.get('text')),
          })
        }
      >
        <input name="text" />
        <button>Add</button>
      </form>
      <ul>
        {optimisticTodos.map((todo) => (
          <li key={todo.id}>
            <input
              type="checkbox"
              checked={todo.done}
              onChange={() => runAction({ type: 'toggle', id: todo.id })}
            />
            <span
              style={{ textDecoration: todo.done ? 'line-through' : 'none' }}
            >
              {todo.text}
            </span>
            <button onClick={() => runAction({ type: 'delete', id: todo.id })}>
              Delete
            </button>
          </li>
        ))}
      </ul>
      {isPending && <p>Syncing to server…</p>}
    </>
  )
}

optimistic 업데이트는 즉시 표시되고, useActionState의 pending flag를 사용하면 Server Action이 resolve될 때까지 은은한 indicator(예: Syncing to server…)를 보여 줄 수 있습니다.

The optimistic update shows instantly, while useActionState's pending flag lets you display a subtle indicator (such as Syncing to server…) until the Server Action resolves.

Static export (optional)Static export (선택)

Next.js는 완전한 static site 생성도 지원합니다. 이는 strict SPA에 비해 몇 가지 장점이 있습니다:

Next.js also supports generating a fully static site. This has some advantages over strict SPAs:

  • 자동 code-splitting: 하나의 index.html을 전달하는 대신 Next.js가 route마다 HTML 파일을 생성하므로, 방문자는 client JavaScript bundle을 기다리지 않고 콘텐츠를 더 빨리 받습니다.
  • 향상된 사용자 경험: 모든 route에 최소한의 skeleton을 보여 주는 대신, route마다 완전히 render된 page를 제공합니다. 사용자가 client side에서 navigate할 때도 전환은 여전히 즉각적이고 SPA처럼 동작합니다.
  • Automatic code-splitting: Instead of shipping a single index.html, Next.js will generate an HTML file per route, so your visitors get the content faster without waiting for the client JavaScript bundle.
  • Improved user experience: Instead of a minimal skeleton for all routes, you get fully rendered pages for each route. When users navigate client side, transitions are still instant and SPA-like.

static export를 활성화하려면 configuration을 업데이트하세요:

To enable a static export, update your configuration:

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  output: 'export',
}

export default nextConfig

After running next build, Next.js will create an out folder with the HTML/CSS/JS assets for your application.

Next.js server features are not supported with static exports. Learn more.
