How to optimize your Next.js application for productionproduction을 위한 Next.js 애플리케이션 최적화

Next.js 애플리케이션을 production에 올리기 전에, 최상의 사용자 경험, performance, 보안을 위해 적용을 고려해야 할 몇 가지 최적화와 pattern이 있습니다.

Before taking your Next.js application to production, there are some optimizations and patterns you should consider implementing for the best user experience, performance, and security.

이 페이지에서는 애플리케이션을 만드는 동안과 production에 올리기 전에 참고할 수 있는 best practice와 함께, 알아 두어야 할 Next.js의 자동 최적화를 소개합니다.

This page provides best practices that you can use as a reference when building your application and before going to production, as well as the automatic Next.js optimizations you should be aware of.

Automatic optimizations자동 최적화

다음 Next.js 최적화는 기본으로 활성화되어 있으며 별도 설정이 필요 없습니다:

These Next.js optimizations are enabled by default and require no configuration:

  • Server Components: Next.js는 기본적으로 Server Component를 사용합니다. Server Component는 server에서 실행되며, client에서 render하기 위해 JavaScript가 필요하지 않습니다. 따라서 client-side JavaScript bundle 크기에 영향을 주지 않습니다. interactivity가 필요할 때는 Client Components를 사용하면 됩니다.
  • Code-splitting: Server Component는 route segment 단위의 자동 code-splitting을 가능하게 합니다. 적절한 경우 Client Component와 third-party library의 lazy loading도 고려해 보세요.
  • Prefetching: 새 route로 가는 link가 사용자의 viewport에 들어오면 Next.js는 background에서 그 route를 prefetch합니다. 그래서 새 route로의 navigation이 거의 즉시 이루어집니다. 적절한 경우 prefetching을 opt out할 수 있습니다.
  • Prerendering: Next.js는 build time에 server에서 Server Component와 Client Component를 prerender하고, 애플리케이션 performance를 높이기 위해 render 결과를 cache합니다. 적절한 경우 특정 route에 대해 Dynamic Rendering을 opt in할 수 있습니다. - Caching: Next.js는 server, database, backend service로 가는 network request 수를 줄이기 위해 data request, Server Component와 Client Component의 render 결과, static asset 등을 cache합니다. 적절한 경우 caching을 opt out할 수 있습니다.
  • Server Components: Next.js uses Server Components by default. Server Components run on the server, and don't require JavaScript to render on the client. As such, they have no impact on the size of your client-side JavaScript bundles. You can then use Client Components as needed for interactivity.
  • Code-splitting: Server Components enable automatic code-splitting by route segments. You may also consider lazy loading Client Components and third-party libraries, where appropriate.
  • Prefetching: When a link to a new route enters the user's viewport, Next.js prefetches the route in background. This makes navigation to new routes almost instant. You can opt out of prefetching, where appropriate.
  • Prerendering: Next.js prerenders Server and Client Components on the server at build time and caches the rendered result to improve your application's performance. You can opt into Dynamic Rendering for specific routes, where appropriate. - Caching: Next.js caches data requests, the rendered result of Server and Client Components, static assets, and more, to reduce the number of network requests to your server, database, and backend services. You may opt out of caching, where appropriate.

이 기본값들은 애플리케이션의 performance를 높이고, 각 network request마다 전송되는 data의 양과 비용을 줄이는 것을 목표로 합니다.

These defaults aim to improve your application's performance, and reduce the cost and amount of data transferred on each network request.

During development개발 중

애플리케이션을 만드는 동안 최상의 performance와 사용자 경험을 위해 다음 기능을 사용할 것을 권장합니다:

While building your application, we recommend using the following features to ensure the best performance and user experience:

Routing and renderingRouting과 rendering

  • Layouts: layout을 사용해 여러 page에서 UI를 공유하고 navigation 시 partial rendering을 활성화하세요.
  • <Link> component: client-side navigation과 prefetching을 위해 <Link> component를 사용하세요.
  • Error Handling: custom error page를 만들어 production에서 catch-all error와 404 error를 우아하게 처리하세요.
  • Client and Server Components: Server Component와 Client Component의 권장 composition pattern을 따르고, client-side JavaScript bundle이 불필요하게 커지지 않도록 "use client" boundary의 위치를 확인하세요.
  • Request-time APIs: cookies나 searchParams prop 같은 Request-time API는 route 전체를(또는 Root Layout에서 사용하면 애플리케이션 전체를) Dynamic Rendering으로 전환한다는 점에 유의하세요. Request-time API는 의도적으로 사용하고, 적절한 경우 <Suspense> boundary로 감싸세요.
  • Layouts: Use layouts to share UI across pages and enable partial rendering on navigation.
  • <Link> component: Use the <Link> component for client-side navigation and prefetching.
  • Error Handling: Gracefully handle catch-all errors and 404 errors in production by creating custom error pages.
  • Client and Server Components: Follow the recommended composition patterns for Server and Client Components, and check the placement of your "use client" boundaries to avoid unnecessarily increasing your client-side JavaScript bundle.
  • Request-time APIs: Be aware that Request-time APIs like cookies and the searchParams prop will opt the entire route into Dynamic Rendering (or your whole application if used in the Root Layout). Ensure Request-time API usage is intentional and wrap them in <Suspense> boundaries where appropriate.
Good to know

Partial Prerendering (experimental)을 사용하면 route 전체를 dynamic rendering으로 전환하지 않고도 route의 일부만 dynamic으로 만들 수 있습니다.

Partial Prerendering (experimental) will allow parts of a route to be dynamic without opting the whole route into dynamic rendering.

Data fetching and cachingData fetching과 caching

  • Server Components: Server Component를 사용해 server에서 data를 fetch하는 이점을 활용하세요.
  • Route Handlers: Client Component에서 backend resource에 접근할 때 Route Handler를 사용하세요. 단, 추가 server request를 피하기 위해 Server Component에서는 Route Handler를 호출하지 마세요.
  • Streaming: Loading UI와 React Suspense를 사용해 server에서 client로 UI를 점진적으로 보내고, data를 fetch하는 동안 route 전체가 blocking되지 않도록 하세요.
  • Parallel Data Fetching: 적절한 경우 data를 병렬로 fetch해 network waterfall을 줄이세요.
  • Data Caching: data request가 cache되고 있는지 확인하고, 적절한 경우 caching을 opt in하세요. fetch를 사용하지 않는 request도 cache되도록 하세요.
  • Static Images: public directory를 사용해 이미지 같은 애플리케이션의 static asset을 자동으로 cache하세요.
  • Server Components: Leverage the benefits of fetching data on the server using Server Components.
  • Route Handlers: Use Route Handlers to access your backend resources from Client Components. But do not call Route Handlers from Server Components to avoid an additional server request.
  • Streaming: Use Loading UI and React Suspense to progressively send UI from the server to the client, and prevent the whole route from blocking while data is being fetched.
  • Parallel Data Fetching: Reduce network waterfalls by fetching data in parallel, where appropriate.
  • Data Caching: Verify whether your data requests are being cached or not, and opt into caching, where appropriate. Ensure requests that don't use fetch are cached.
  • Static Images: Use the public directory to automatically cache your application's static assets, e.g. images.

UI and accessibilityUI와 접근성

  • Forms and Validation: Server Action을 사용해 form 제출과 server-side validation, error 처리를 하세요.
  • Global Error UI: app/global-error.tsx를 추가해 앱 전체의 uncaught error에 대해 일관되고 접근성 있는 fallback UI와 복구 방법을 제공하세요.
  • Global 404: app/global-not-found.tsx를 추가해 앱 전체에서 match되지 않는 route에 대해 접근성 있는 404를 제공하세요.
  • Font Module: Font Module을 사용해 font를 최적화하세요. font 파일을 다른 static asset과 함께 자동으로 hosting하고, 외부 network request를 없애며, layout shift를 줄여 줍니다.
  • <Image> Component: Image Component를 사용해 이미지를 최적화하세요. 이미지를 자동으로 최적화하고, layout shift를 방지하며, WebP 같은 최신 format으로 제공합니다.
  • <Script> Component: Script Component를 사용해 third-party script를 최적화하세요. script를 자동으로 defer하여 main thread를 blocking하지 않도록 합니다.
  • ESLint: 내장된 eslint-plugin-jsx-a11y plugin을 사용해 접근성 문제를 일찍 발견하세요.
  • Forms and Validation: Use Server Actions to handle form submissions, server-side validation, and handle errors.
  • Global Error UI: Add app/global-error.tsx to provide consistent, accessible fallback UI and recovery for uncaught errors across your app.
  • Global 404: Add app/global-not-found.tsx to serve an accessible 404 for unmatched routes across your app.
  • Font Module: Optimize fonts by using the Font Module, which automatically hosts your font files with other static assets, removes external network requests, and reduces layout shift.
  • <Image> Component: Optimize images by using the Image Component, which automatically optimizes images, prevents layout shift, and serves them in modern formats like WebP.
  • <Script> Component: Optimize third-party scripts by using the Script Component, which automatically defers scripts and prevents them from blocking the main thread.
  • ESLint: Use the built-in eslint-plugin-jsx-a11y plugin to catch accessibility issues early.

Security보안

  • Tainting: data object 또는 특정 값을 taint하여 민감한 data가 client에 노출되지 않도록 하세요.
  • Server Actions: 각 action 안에서 authentication과 authorization을 검증하세요. Proxy나 layout, page 수준의 검사에만 의존하지 마세요. database 접근은 server-only Data Access Layer로 옮기고, 비용이 큰 작업에는 rate limiting을 고려하세요. 권장 security practice를 검토하세요.
  • Environment Variables: .env.* 파일이 .gitignore에 추가되어 있는지, 그리고 public variable에만 NEXT_PUBLIC_ prefix가 붙어 있는지 확인하세요.
  • Content Security Policy: cross-site scripting, clickjacking, 기타 code injection 공격 같은 다양한 보안 위협으로부터 애플리케이션을 보호하기 위해 Content Security Policy 추가를 고려하세요.
  • Tainting: Prevent sensitive data from being exposed to the client by tainting data objects and/or specific values.
  • Server Actions: Verify authentication and authorization inside each action. Do not rely on Proxy or layout or page level checks alone. Move database access to a server-only Data Access Layer and consider rate limiting for expensive operations. Review the recommended security practices.
  • Environment Variables: Ensure your .env.* files are added to .gitignore and only public variables are prefixed with NEXT_PUBLIC_.
  • Content Security Policy: Consider adding a Content Security Policy to protect your application against various security threats such as cross-site scripting, clickjacking, and other code injection attacks.

Metadata and SEOMetadata와 SEO

  • Metadata API: Metadata API로 page title, description 등을 추가해 애플리케이션의 검색 엔진 최적화(SEO)를 개선하세요.
  • Open Graph (OG) images: OG image를 만들어 애플리케이션을 소셜 공유에 대비하세요.
  • Sitemaps and Robots: sitemap과 robots 파일을 생성해 검색 엔진이 page를 crawl하고 index하도록 도우세요.
  • Metadata API: Use the Metadata API to improve your application's Search Engine Optimization (SEO) by adding page titles, descriptions, and more.
  • Open Graph (OG) images: Create OG images to prepare your application for social sharing.
  • Sitemaps and Robots: Help Search Engines crawl and index your pages by generating sitemaps and robots files.

Type safety

  • TypeScript and TS Plugin: 더 나은 type-safety를 위해, 그리고 error를 일찍 발견하기 위해 TypeScript와 TypeScript plugin을 사용하세요.
  • TypeScript and TS Plugin: Use TypeScript and the TypeScript plugin for better type-safety, and to help you catch errors early.

Before going to productionproduction에 올리기 전

production에 올리기 전에 next build를 실행해 로컬에서 애플리케이션을 build하고 build error를 잡은 다음, next start를 실행해 production과 비슷한 환경에서 애플리케이션의 performance를 측정할 수 있습니다.

Before going to production, you can run next build to build your application locally and catch any build errors, then run next start to measure the performance of your application in a production-like environment.

Core Web Vitals

  • Lighthouse: 시크릿 모드에서 lighthouse를 실행해 사용자가 사이트를 어떻게 경험할지 더 잘 이해하고 개선할 부분을 찾으세요. 이것은 시뮬레이션 테스트이므로 field data(예: Core Web Vitals)도 함께 살펴봐야 합니다.
  • useReportWebVitals hook: 이 hook을 사용해 Core Web Vitals data를 analytics 도구로 보내세요.
  • Lighthouse: Run lighthouse in incognito to gain a better understanding of how your users will experience your site, and to identify areas for improvement. This is a simulated test and should be paired with looking at field data (such as Core Web Vitals).
  • useReportWebVitals hook: Use this hook to send Core Web Vitals data to analytics tools.

Analyzing bundlesBundle 분석하기

@next/bundle-analyzer plugin을 사용해 JavaScript bundle 크기를 분석하고, 애플리케이션 performance에 영향을 줄 수 있는 큰 module과 dependency를 찾아내세요.

Use the @next/bundle-analyzer plugin to analyze the size of your JavaScript bundles and identify large modules and dependencies that might be impacting your application's performance.
