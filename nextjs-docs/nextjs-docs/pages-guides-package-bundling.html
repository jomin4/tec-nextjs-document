How to optimize package bundlingpackage bundling 최적화

Bundling은 애플리케이션 코드와 그 dependency를 client와 server용으로 최적화된 output 파일로 합치는 과정입니다. bundle이 작을수록 더 빨리 load되고, JavaScript 실행 시간이 줄어들고, Core Web Vitals가 개선되며, server cold start 시간이 짧아집니다.

Bundling is the process of combining your application code and its dependencies into optimized output files for the client and server. Smaller bundles load faster, reduce JavaScript execution time, improve Core Web Vitals, and lower server cold start times.

Next.js는 code splitting, tree-shaking 등의 기법으로 bundle을 자동으로 최적화합니다. 하지만 bundle을 직접 최적화해야 하는 경우도 있습니다.

Next.js automatically optimizes bundles by code splitting, tree-shaking, and other techniques. However, there are some cases where you may need to optimize your bundles manually.

애플리케이션의 bundle을 분석하는 도구는 두 가지입니다:

There are two tools for analyzing your application's bundles:

  • Turbopack용 Next.js Bundle Analyzer
  • Webpack용 @next/bundle-analyzer plugin
  • Next.js Bundle Analyzer for Turbopack
  • @next/bundle-analyzer plugin for Webpack

이 가이드에서는 각 도구를 사용하는 방법과 큰 bundle을 최적화하는 방법을 차례로 안내합니다.

This guide will walk you through how to use each tool and how to optimize large bundles.

Next.js Bundle Analyzer

v16.1 이상에서 사용할 수 있습니다. 전용 GitHub discussion에서 feedback을 남길 수 있고, turbopack-bundle-analyzer-demo.vercel.sh에서 demo를 볼 수 있습니다.

Available in v16.1 and later. You can share feedback in the dedicated GitHub discussion and view the demo at turbopack-bundle-analyzer-demo.vercel.sh.

Next.js Bundle Analyzer는 Turbopack의 module graph와 통합되어 있습니다. 정확한 import tracing으로 server module과 client module을 살펴볼 수 있어서 큰 dependency를 더 쉽게 찾을 수 있습니다. interactive Bundle Analyzer demo를 열어 module graph를 탐색해 보세요.

The Next.js Bundle Analyzer is integrated with Turbopack's module graph. You can inspect server and client modules with precise import tracing, making it easier to find large dependencies. Open the interactive Bundle Analyzer demo to explore the module graph.

Step 1: Run the Turbopack Bundle Analyzer1단계: Turbopack Bundle Analyzer 실행하기

시작하려면 다음 command를 실행하고 브라우저에서 interactive view를 여세요.

To get started, run the following command and open up the interactive view in your browser.

>_Terminal
npx next analyze
yarn next analyze
pnpm next analyze
bunx next analyze

Step 2: Filter and inspect modules2단계: module 필터링하고 살펴보기

UI에서는 route, environment(client 또는 server), type(JavaScript, CSS, JSON)으로 필터링하거나 파일로 검색할 수 있습니다:

Within the UI, you can filter by route, environment (client or server), and type (JavaScript, CSS, JSON), or search by file:

Step 3: Trace modules with import chains3단계: import chain으로 module 추적하기

treemap은 각 module을 사각형으로 보여 줍니다. module의 크기는 사각형의 면적으로 표현됩니다.

The treemap shows each module as a rectangle. Where the size of the module is represented by the area of the rectangle.

module을 클릭하면 크기를 확인하고, 전체 import chain을 살펴보고, 애플리케이션의 정확히 어디에서 사용되는지 볼 수 있습니다:

Click a module to see its size, inspect its full import chain and see exactly where it’s used in your application:

Step 4: Write output to disk for sharing or diffing4단계: 공유나 비교를 위해 output을 디스크에 쓰기

분석 결과를 팀원과 공유하거나 최적화 전후의 bundle 크기를 비교하고 싶다면, interactive view를 건너뛰고 --output flag로 분석 결과를 static 파일로 저장할 수 있습니다:

If you want to share the analysis with teammates or compare bundle sizes before/after optimizations, you can skip the interactive view and save the analysis as a static file with the --output flag:

>_Terminal
npx next analyze --output
yarn next analyze --output
pnpm next analyze --output
bunx next analyze --output

이 command는 output을 .next/diagnostics/analyze에 씁니다. 이 directory를 다른 곳에 복사해서 결과를 비교할 수 있습니다:

This command writes the output to .next/diagnostics/analyze. You can copy this directory elsewhere to compare results:

>_Terminal
cp -r .next/diagnostics/analyze ./analyze-before-refactor

Export analysis data분석 data export하기

v16.4 이상에서 사용할 수 있습니다. 전용 GitHub discussion에서 feedback을 남길 수 있고, turbopack-bundle-analyzer-demo.vercel.sh에서 demo를 볼 수 있습니다.

Available in v16.4 and later. You can share feedback in the dedicated GitHub discussion and view the demo at turbopack-bundle-analyzer-demo.vercel.sh.

next analyze export를 사용하면 다시 build하거나 server를 시작하지 않고도, 저장된 snapshot을 script나 AI 도구용 JSON Lines로 stream할 수 있습니다:

Use next analyze export to stream a saved snapshot as JSON Lines for scripts or AI tools, without rebuilding or starting a server:

>_Terminal
npx next analyze --output --snapshot before
npx next analyze export --snapshot before > bundle-graph.jsonl
yarn next analyze --output --snapshot before
yarn next analyze export --snapshot before > bundle-graph.jsonl
pnpm next analyze --output --snapshot before
pnpm next analyze export --snapshot before > bundle-graph.jsonl
bunx next analyze --output --snapshot before
bunx next analyze export --snapshot before > bundle-graph.jsonl

export option은 CLI reference를 참고하세요.

See the CLI reference for export options.

Bundle Analyzer에는 더 많은 option이 있습니다. 전체 목록은 Next.js CLI reference 문서를 참고하세요.

More options are available for the Bundle Analyzer, see Next.js CLI reference docs for the full list.

Give your AI agent access to the bundle analyzerAI agent가 bundle analyzer에 접근하게 하기

next-bundle-optimizer skill은 AI agent가 Turbopack bundle analyzer의 기반 data에 접근할 수 있게 해서, 사이트의 initial load 성능에 영향을 주는 큰 client-side bundle의 원인을 자동으로 찾아내도록 합니다.

The next-bundle-optimizer skill gives your AI agent access to the data powering Turbopack's bundle analyzer to automatically identify sources of large client-side bundles that impact your site's initial load performance.

먼저 skill을 설치하세요:

First, install the skill:

>_Terminal
npx skills add vercel/next.js --skill next-bundle-optimizer

그다음 agent에게 prompt를 보내세요. audit-only mode에서는 아무것도 변경하지 않고 report만 만듭니다:

Then prompt your agent. In audit-only mode, it produces a report without making any changes:

Use the next-bundle-optimizer skill to produce a report of the initial load performance of this site.

agent에게 문제를 고치라고 지시할 수도 있으며, 그러면 찾아낸 내용을 바탕으로 사이트를 최적화합니다. 또는 prompt에 route를 지정해서 특정 route에 집중하게 할 수도 있습니다.

You can also tell your agent to fix any issues, and it will optimize your site based on its findings. Or have it focus on a specific route by providing the route in the prompt.

@next/bundle-analyzer for WebpackWebpack용 @next/bundle-analyzer

@next/bundle-analyzer는 애플리케이션 bundle의 크기를 관리하도록 도와주는 plugin입니다. 각 package와 그 dependency의 크기를 시각적인 report로 생성합니다. 이 정보를 활용해 큰 dependency를 제거하거나, 코드를 분할하거나, lazy-load할 수 있습니다.

The @next/bundle-analyzer is a plugin that helps you manage the size of your application bundles. It generates a visual report of the size of each package and their dependencies. You can use the information to remove large dependencies, split, or lazy-load your code.

Step 1: Installation1단계: 설치

다음 command를 실행해 plugin을 설치하세요:

Install the plugin by running the following command:

pnpm add @next/bundle-analyzer
npm install @next/bundle-analyzer
yarn add @next/bundle-analyzer
bun add @next/bundle-analyzer

그다음 next.config.js에 bundle analyzer 설정을 추가하세요.

Then, add the bundle analyzer's settings to your next.config.js.

JSnext.config.js
/** @type {import('next').NextConfig} */
const nextConfig = {}

const withBundleAnalyzer = require('@next/bundle-analyzer')({
  enabled: process.env.ANALYZE === 'true',
})

module.exports = withBundleAnalyzer(nextConfig)

Step 2: Generating a report2단계: report 생성하기

다음 command를 실행해 bundle을 분석하세요:

Run the following command to analyze your bundles:

ANALYZE=true npm run build
# or
ANALYZE=true yarn build
# or
ANALYZE=true pnpm build

report가 브라우저에 새 tab 세 개를 열며, 이를 살펴볼 수 있습니다.

The report will open three new tabs in your browser, which you can inspect.

Optimizing large bundles큰 bundle 최적화하기

큰 module을 찾아냈다면, 해결 방법은 use case에 따라 다릅니다. 다음은 흔한 원인과 해결 방법입니다:

Once you've identified a large module, the solution will depend on your use case. Below are common causes and how to fix them:

Packages with many exportsexport가 많은 package

수백 개의 module을 export하는 package(icon이나 utility library 등)를 사용한다면, next.config.js 파일의 optimizePackageImports option으로 그 import가 resolve되는 방식을 최적화할 수 있습니다. 이 option은 여러 named export로 import 문을 작성하는 편리함은 그대로 두면서, 실제로 사용하는 module만 load합니다.

If you're using a package that exports hundreds of modules (such as icon and utility libraries), you can optimize how those imports are resolved using the optimizePackageImports option in your next.config.js file. This option will only load the modules you actually use, while still giving you the convenience of writing import statements with many named exports.

JSnext.config.js
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    optimizePackageImports: ['icon-library'],
  },
}

module.exports = nextConfig
Good to know

Next.js는 일부 library를 자동으로 최적화하므로, 그런 library는 optimizePackageImports 목록에 포함할 필요가 없습니다. 지원되는 package의 전체 목록을 참고하세요.

Next.js also optimizes some libraries automatically, thus they do not need to be included in the optimizePackageImports list. See the full list of supported packages.

Heavy client workloads무거운 client 작업

client bundle이 커지는 흔한 원인 중 하나는 Client Component에서 비용이 큰 rendering 작업을 하는 것입니다. syntax highlighting, chart rendering, markdown parsing처럼 data를 UI로 변환하기 위해서만 존재하는 library에서 자주 발생합니다.

A common cause of large client bundles is doing expensive rendering work in Client Components. This often happens with libraries that exist only to transform data into UI, such as syntax highlighting, chart rendering, or markdown parsing.

그 작업에 브라우저 API나 사용자 interaction이 필요하지 않다면, Server Component에서 실행할 수 있습니다.

If that work does not require browser APIs or user interaction, it can be run in a Server Component.

이 예제에서는 prism 기반 highlighter가 Client Component에서 실행됩니다. 최종 output은 <code> block 하나일 뿐인데도, highlighting library 전체가 client JavaScript bundle에 포함됩니다:

In this example, a prism based highlighter runs in a Client Component. Even though the final output is just a <code> block, the entire highlighting library is bundled into the client JavaScript bundle:

TSapp/blog/[slug]/page.tsx
'use client'

import Highlight from 'prism-react-renderer'
import theme from 'prism-react-renderer/themes/github'

export default function Page() {
  const code = `export function hello() {
    console.log("hi")
  }`

  return (
    <article>
      <h1>Blog Post Title</h1>

      {/* The prism package and its tokenization logic are shipped to the client */}
      <Highlight code={code} language="tsx" theme={theme}>
        {({ className, style, tokens, getLineProps, getTokenProps }) => (
          <pre className={className} style={style}>
            <code>
              {tokens.map((line, i) => (
                <div key={i} {...getLineProps({ line })}>
                  {line.map((token, key) => (
                    <span key={key} {...getTokenProps({ token })} />
                  ))}
                </div>
              ))}
            </code>
          </pre>
        )}
      </Highlight>
    </article>
  )
}

결과가 static HTML인데도 client가 highlighting library를 다운로드하고 실행해야 하므로 bundle 크기가 커집니다.

This increases bundle size because the client must download and execute the highlighting library, even though the result is static HTML.

대신 highlighting 로직을 Server Component로 옮기고 최종 HTML을 server에서 render하세요. client는 render된 markup만 받게 됩니다.

Instead, move the highlighting logic to a Server Component and render the final HTML on the server. The client will only receive the rendered markup.

TSapp/blog/[slug]/page.tsx
import { codeToHtml } from 'shiki'

export default async function Page() {
  const code = `export function hello() {
    console.log("hi")
  }`

  // The Shiki package runs on the server and is never bundled for the client.
  const highlightedHtml = await codeToHtml(code, {
    lang: 'tsx',
    theme: 'github-dark',
  })

  return (
    <article>
      <h1>Blog Post Title</h1>

      {/* Client receives plain markup */}
      <pre>
        <code dangerouslySetInnerHTML={{ __html: highlightedHtml }} />
      </pre>
    </article>
  )
}

External packages that aren't pre-bundledpre-bundle되지 않은 external package

기본적으로 애플리케이션에 import한 package는 bundle되지 않습니다. monorepo나 node_modules에서 import한 경우처럼 external package가 pre-bundle되어 있지 않으면 성능에 영향을 줄 수 있습니다.

By default, packages imported into your application are not bundled. This can impact performance if external packages are not pre-bundled, for example, if imported from a monorepo or node_modules.

특정 package를 bundle하려면 next.config.js의 transpilePackages option을 사용할 수 있습니다.

To bundle specific packages, you can use the transpilePackages option in your next.config.js.

JSnext.config.js
/** @type {import('next').NextConfig} */
const nextConfig = {
  transpilePackages: ['package-name'],
}

module.exports = nextConfig

모든 package를 자동으로 bundle하려면 next.config.js의 bundlePagesRouterDependencies option을 사용할 수 있습니다. 이 option의 기본값은 false입니다.

To automatically bundle all packages, you can use the bundlePagesRouterDependencies option in your next.config.js. This option defaults to false.

JSnext.config.js
/** @type {import('next').NextConfig} */
const nextConfig = {
  bundlePagesRouterDependencies: true,
}

module.exports = nextConfig

Opting specific packages out of bundling특정 package를 bundling에서 제외하기

bundle에 들어가면 안 되는 package를 찾았다면, next.config.js의 serverExternalPackages option으로 특정 package를 자동 bundling에서 제외할 수 있습니다:

If you identify packages that shouldn't be in the bundle, you can opt specific packages out of automatic bundling using the serverExternalPackages option in your next.config.js:

JSnext.config.js
/** @type {import('next').NextConfig} */
const nextConfig = {
  // Automatically bundle external packages:
  bundlePagesRouterDependencies: true,
  // Opt specific packages out of bundling:
  serverExternalPackages: ['package-name'],
}

module.exports = nextConfig
