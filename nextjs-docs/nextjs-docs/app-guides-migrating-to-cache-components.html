Migrating to Cache ComponentsCache Components로 migrate하기

Cache Components를 활성화하면 dynamic, revalidate, fetchCache 같은 route segment config는 use cache와 cacheLife로 대체됩니다.

When Cache Components is enabled, route segment configs like dynamic, revalidate, and fetchCache are replaced by use cache and cacheLife.

migration은 instant navigation validation을 따라 진행됩니다. Cache Components를 활성화하면 Next.js는 development 중에 각 route로 navigate할 때 즉시(instant) render되는지 검증하고, 이를 막는 코드를 error나 insight로 보여 줍니다.

The migration is driven by instant navigation validation. With Cache Components enabled, Next.js validates in development whether navigating into each route renders instantly, and surfaces the code that would block it as an error or insight.

Use the adoption skill (recommended)adoption skill 사용하기 (권장)

next-cache-components-adoption skill은 coding agent로 이 migration을 진행하며, 한 번에 기능 하나씩 처리하고 기능 단위가 끝날 때마다 확인을 받습니다. 두 가지 mode를 지원합니다:

The next-cache-components-adoption skill drives this migration with a coding agent, one feature at a time, checking in at every feature boundary. It supports two modes:

  • Incremental. 모든 route를 validation에서 opt out시키는 기계적인 PR 하나를 먼저 열고, 그다음 각 기능을 후속 PR로 내보냅니다. 아래 점진적으로 도입하기 흐름을 자동화한 것입니다.
  • Direct. 하나의 branch에서 모든 route를 그 자리에서 바로 도입합니다.
  • Incremental. Opens a single mechanical PR that opts every route out of validation, then ships each feature as a follow-up PR. This automates the Adopting incrementally flow below.
  • Direct. Adopts every route in place on one branch.

Or migrate by hand또는 직접 migrate하기

기존 앱을 직접 migrate하려면 다음 단계를 순서대로 따릅니다:

Migrating an existing app by hand follows a few steps, in order:

  1. next.config.ts에서 Cache Components를 활성화합니다.
  2. 접근 방식을 정합니다: 지금 모든 route를 변환하거나, 먼저 route를 validation에서 opt out시킨 뒤 하나씩 변환하며 점진적으로 도입합니다.
  3. 표시되는 validation error와 insight를 따라가며, 각 route segment config를 Cache Components의 대응 방식으로 바꾸고, cache되지 않은 데이터는 use cache로 cache하거나 runtime 데이터를 <Suspense>로 감쌉니다. 아래의 key별 섹션에서 각 config와 API를 다룹니다.
  1. Enable Cache Components in next.config.ts.
  2. Decide your approach: convert every route now, or adopt incrementally by opting routes out of validation first and converting one at a time.
  3. Follow the validation errors and insights it surfaces, replacing each route segment config with its Cache Components equivalent and caching uncached data with use cache or wrapping runtime data in <Suspense>. The per-key sections below cover each config and API.

기존의 fetch와 unstable_cache caching은 그대로 동작합니다. unstable_cache migration은 선택 사항이며 나중에 해도 됩니다.

Your existing fetch and unstable_cache caching keeps working. Migrating unstable_cache is optional and can happen later.

일부 영역은 별도 단계가 있습니다:

Some surfaces have their own steps:

  • dynamic param이 있는 route는 generateStaticParams 가이드를 따르세요.
  • metadata는 generateMetadata와 generateViewport 가이드를 따르세요.
  • For routes with dynamic params, follow the generateStaticParams guidance.
  • For metadata, follow the generateMetadata and generateViewport guidance.

아래 섹션에서는 각 config와 API, 그리고 Cache Components에서 그것을 어떻게 처리해야 하는지 다룹니다.

The sections below cover each config and API and what to do with it under Cache Components.

Enable Cache ComponentsCache Components 활성화하기

Cache Components에는 Next.js 16이 필요합니다. Next.js 15 이하를 사용 중이라면 먼저 version 16 upgrade 가이드를 따라 upgrade하세요. 더 오래된 버전에서 오는 경우라면, 계속하기 전에 upgrade 가이드를 차례로 따라 16까지 올리세요.

Cache Components requires Next.js 16. If you're on Next.js 15 or earlier, upgrade first by following the version 16 upgrade guide. Coming from an older version, work through the upgrade guides to reach 16 before continuing.

그다음 next.config.ts에서 cacheComponents flag를 활성화하세요:

Then enable the cacheComponents flag in next.config.ts:

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
}

export default nextConfig
Good to know

experimental.dynamicIO나 experimental.useCache를 사용하고 있었다면 cacheComponents가 이를 대체합니다. version 16 upgrade 가이드를 참고하세요.

If you were using experimental.dynamicIO or experimental.useCache, cacheComponents replaces them. See the version 16 upgrade guide.

flag를 활성화한 뒤에도 여전히 dynamic, revalidate, fetchCache를 export하는 route segment는 error가 납니다. 먼저 이 config들을 교체하는 것부터 시작하세요. 아래 섹션에서 각각에 대해 무엇을 해야 하는지 설명합니다.

After enabling the flag, route segments that still export dynamic, revalidate, or fetchCache will error. Start by replacing those configs. The sections below explain what to do for each one.

Opting out of validationValidation에서 opt out하기

validation insight나 error는 route가 즉시 render되지 않는다는 것을 알려 줍니다. 권장 사항을 따라 해결하세요: use cache로 데이터를 cache하거나 <Suspense>로 감쌉니다. 아직 해결할 준비가 되지 않았다면, 이를 발생시킨 segment(layout, page, parallel slot)에 instant config를 false로 설정하고 나중에 다시 돌아오세요.

A validation insight or error tells you a route won't render instantly. Resolve it by following the recommendation: cache the data with use cache or wrap it in <Suspense>. If you're not ready to address it yet, set the instant config to false on the segment that raised it (a layout, page, or parallel slot), then come back to it later.

TSapp/dashboard/layout.tsx
export const instant = false
Good to know

instant = false는 segment를 _block해도 되는 것_으로 표시합니다. route를 강제로 dynamic으로 만들지 않으므로, 실제로 prerender 가능한 route는 여전히 static shell을 내보냅니다. 또한 synchronous IO build error를 없애 주지도 않습니다: new Date(), Math.random(), crypto.randomUUID() 같은 호출은 여전히 prerender를 실패시킵니다. 점진적으로 도입하기를 참고하세요.

instant = false marks a segment as allowed to block. It does not force the route to be dynamic, so a genuinely prerenderable route still ships a static shell. It also does not clear synchronous IO build errors: calls like new Date(), Math.random(), and crypto.randomUUID() still fail the prerender. See Adopting incrementally.

Adopting incrementally점진적으로 도입하기

모든 route를 한 번에 migrate할 필요는 없습니다. instant = false를 사용하면 먼저 앱 전체가 build되고 실행되도록 만든 다음, route를 하나씩 변환할 수 있습니다:

You don't have to migrate every route at once. instant = false lets you get the whole app building and running first, then convert routes one at a time:

  1. flag를 활성화하고 각 route segment config를 migrate합니다. dynamic = "force-dynamic", dynamic = "force-static", dynamic = "error", revalidate, fetchCache에 대한 아래 관련 섹션을 따르세요. dynamic param이 있는 route는 generateStaticParams 가이드도 따르세요. 여전히 즉시 render되는 route는 추가 작업이 필요 없습니다.

  2. 준비되지 않은 route는 opt out시킵니다. insight나 error가 나타나는 곳에서, 이를 발생시킨 segment에 instant = false를 설정하세요. 앱 전체에 한 번에 적용하려면 cache-components-instant-false codemod를 실행하세요. 이 codemod는 아직 instant를 선언하지 않은 모든 page, layout, default에 opt-out을 추가합니다:

    >_Terminal
    npx @next/codemod@canary cache-components-instant-false ./app
    Good to know

    src/ 프로젝트에서는 ./src/app을 전달하세요. 경로가 잘못되면 실패하지 않고 0 ok를 보고하므로 파일 개수를 확인하세요.

    앱은 계속 build되고 서비스되며, 이제 opt out된 route에 대해서는 validation이 미뤄집니다.

  3. synchronous IO를 고칩니다. 이것은 미룰 수 없습니다. prerender 중 new Date(), Date.now(), Math.random(), crypto.randomUUID() 같은 호출은 instant = false로도 없어지지 않는 build error를 던집니다. 따라서 이를 사용하는 route는 opt-out 여부와 관계없이 해결하기 전까지 build되지 않습니다. 호출을 prerender되는 shell 밖으로 옮겨 request 시점에 실행되게 하세요: 이를 필요로 하는 부분을 <Suspense>로 감싸고 호출 전에 connection()을 호출하거나, Client Component로 옮기세요.
  4. route를 하나씩 변환합니다. route에서 instant = false를 제거한 다음, use cache로 데이터를 cache하거나 runtime 데이터를 <Suspense>로 감싸서 insight를 해결하세요. opt out된 route가 하나도 남지 않을 때까지 반복합니다.
  1. Enable the flag and migrate each route segment config. Follow the relevant sections below for dynamic = "force-dynamic", dynamic = "force-static", dynamic = "error", revalidate, and fetchCache. For routes with dynamic params, also follow the generateStaticParams guidance. Routes that still render instantly need no further work.

  2. Opt out the routes that aren't ready. Where an insight or error appears, set instant = false on the segment that raised it. To do this in one pass across the whole app, run the cache-components-instant-false codemod, which adds the opt-out to every page, layout, and default that doesn't already declare instant:

    >_Terminal
    npx @next/codemod@canary cache-components-instant-false ./app
    Good to know

    Pass ./src/app in a src/ project. A wrong path reports 0 ok instead of failing, so check the file count.

    The app keeps building and serving, now with validation deferred for the opted-out routes.

  3. Fix synchronous IO. It can't be deferred. Calls like new Date(), Date.now(), Math.random(), and crypto.randomUUID() during prerender throw a build error that instant = false does not clear, so a route that uses them won't build until you address it, opt-out or not. Move the call out of the prerendered shell so it runs at request time: wrap the part that needs it in <Suspense> and call connection() before the call, or move it into a Client Component.
  4. Convert one route at a time. Remove instant = false from a route, then resolve its insights by caching data with use cache or wrapping runtime data in <Suspense>. Repeat until no routes opt out.

dynamic = "force-dynamic"

config를 제거하세요. Cache Components가 없을 때 dynamic = 'force-dynamic'은 매 request마다 route 전체를 render하고 그 안의 fetch request를 cache하지 않도록 만들었습니다. Cache Components에서는 cache되지 않은 데이터와 Request-time API가 이미 request 시점에 실행됩니다. Next.js는 그 주변의 static 또는 cache된 UI를 prerender합니다.

Remove the config. Without Cache Components, dynamic = 'force-dynamic' rendered the entire route for every request and made its fetch requests uncached. With Cache Components, uncached data and Request-time APIs already run at request time. Next.js prerenders any static or cached UI around them.

config를 제거한 뒤에는 나타나는 validation error나 insight를 따라가세요.

After removing the config, follow any validation errors or insights that appear.

dynamic = "force-static"

config를 제거한 다음 caching을 명시적으로 만드세요. Cache Components가 없을 때 dynamic = 'force-static'은 route를 강제로 prerender하고, 데이터를 cache하며, cookies(), headers(), useSearchParams()가 빈 값을 반환하게 만들었습니다.

Remove the config, then make its caching explicit. Without Cache Components, dynamic = 'force-static' forced the route to prerender, cached its data, and made cookies(), headers(), and useSearchParams() return empty values.

재사용해야 하는 데이터는 use cache와 적절한 cacheLife로 cache하세요. config를 제거하면 Request-time API는 실제 request 값을 읽습니다. route가 완전히 prerender된 상태로 남아야 한다면 이런 의존성을 제거하세요.

Cache data that should be reused with use cache and a suitable cacheLife. After removing the config, Request-time APIs read actual request values. Remove those dependencies if the route must remain fully prerendered.

완전히 static한 route를 요구하려면, caching을 migrate한 뒤 ensureStatic = 'navigation'을 추가하세요:

dynamic = 'force-static'과 달리 ensureStatic은 Request-time API가 빈 값을 반환하게 만들지 않습니다. request별 server 작업 때문에 route를 prerender할 수 없으면 error를 보고합니다. App Shell이나 link별 prefetch만 static으로 유지되면 되는 경우에는 덜 엄격한 level을 선택하세요. Keeping pages static을 참고하세요.

dynamic = "error"

config를 제거하세요. Cache Components가 없을 때 dynamic = 'error'는 route가 prerender되도록 요구하고 fetch request를 기본적으로 cache된 것으로 취급했습니다. cache되지 않은 데이터나 Request-time API가 prerendering을 막을 때만 error를 발생시켰습니다.

Remove the config. Without Cache Components, dynamic = 'error' required the route to prerender and treated fetch requests as cached by default. It raised an error only when uncached data or a Request-time API prevented prerendering.

config를 제거하면 fetch는 더 이상 그 cache 기본값을 물려받지 않습니다. route의 기존 caching 동작을 유지하려면 해당 request를 use cache로 감싸고 cacheLife로 lifetime을 설정하세요. route가 그 기본값에 의존하지 않았다면 대체할 필요가 없습니다.

After removing the config, fetch no longer inherits that cached default. To preserve the route's existing caching behavior, wrap those requests in use cache and set their lifetime with cacheLife. If the route did not rely on the default, no replacement is needed.

revalidate

0보다 큰 revalidation 시간은 cacheLife로 바꾸세요. Cache Components가 없을 때 revalidate는 route 전체의 기본 revalidation 시간을 설정했습니다. Cache Components에서는 cache해야 하는 데이터나 UI 주변에 use cache를 두고, cacheLife로 lifetime을 설정하세요.

Replace revalidation times greater than zero with cacheLife. Without Cache Components, revalidate set the default revalidation time for an entire route. With Cache Components, place use cache around the data or UI that should be cached, then set its lifetime with cacheLife.

Good to know

revalidate 값이 내장 cacheLife profile('seconds', 'minutes', 'hours', 'days', 'weeks', 'max')과 맞지 않으면, 가장 가까운 것을 고르거나 팀의 convention에 맞는 custom profile을 정의하세요. 내장 profile의 timing이 애플리케이션의 caching 요구에 맞지 않을 때는 default를 포함해 내장 profile을 재정의할 수도 있습니다.

If your revalidate value doesn't match a built-in cacheLife profile ('seconds', 'minutes', 'hours', 'days', 'weeks', 'max'), pick the closest one or define a custom profile to match your conventions. You can also redefine a built-in profile, including default, when its timings don't match your application's caching needs.

revalidate = 0이라면 config를 제거하세요. Cache Components에서는 cache되지 않은 데이터가 이미 request 시점에 실행됩니다. 매 request마다 실행되어야 하는 데이터는 use cache scope 밖에 두세요.

For revalidate = 0, remove the config. Uncached data already runs at request time with Cache Components. Keep data outside a use cache scope when it must run for every request.

fetchCache

config를 제거하고 data source에서 caching을 설정하세요. Cache Components가 없을 때 fetchCache는 route 안의 모든 fetch request에 대한 cache option을 바꾸거나 제한했습니다. Cache Components에서는 fetch가 use cache scope 안에서 실행되지 않는 한 cache되지 않습니다.

Remove the config and set caching at the data source. Without Cache Components, fetchCache changed or restricted the cache option for every fetch request in a route. With Cache Components, fetches are uncached unless they run inside a use cache scope.

React.cache

하지만 각 Cache Function은 격리된 React cache scope를 가집니다. 예를 들어 한 Cache Function이 데이터를 preload하고 다른 Cache Function이 그것을 사용하는 경우처럼, 서로 다른 Cache Function에서의 호출은 React.cache 결과를 공유하지 않습니다.

On-demand revalidation (revalidateTag, revalidatePath, updateTag)On-demand revalidation

on-demand invalidation은 여전히 cache된 데이터에 tag를 붙이고 이벤트가 발생한 뒤 이를 만료시키는 방식으로 동작합니다. fetch의 next.tags option 대신 use cache 함수 안에서 cacheTag로 데이터에 tag를 붙인 다음, 원하는 동작에 따라 invalidation API를 고르세요:

On-demand invalidation still works by tagging cached data and expiring it after an event. Tag data with cacheTag inside a use cache function instead of the fetch next.tags option, then choose the invalidation API by the behavior you want:

  • updateTag: 사용자가 그 결과를 즉시 봐야 하는 mutation용입니다(read-your-own-writes). Server Action에서 호출하면 tag를 만료시켜, 다음 request가 stale 콘텐츠를 제공하는 대신 새 데이터를 기다리게 합니다.
  • revalidateTag: stale-while-revalidate용입니다. 두 번째 argument로 cache profile이 필수입니다. 예를 들어 'max'를 사용하면 background에서 갱신하는 동안 cache된 데이터를 제공합니다. Server Action과 Route Handler에서 동작합니다.
  • revalidatePath: 이전 caching model과 달라진 점이 없습니다.
  • updateTag: for mutations whose result the user must see immediately (read-your-own-writes). Called from a Server Action, it expires the tag so the next request waits for fresh data instead of serving stale content.
  • revalidateTag: for stale-while-revalidate. A cache profile is required as the second argument, for example use 'max' to serve cached data while it refreshes in the background. Works in Server Actions and Route Handlers.
  • revalidatePath: unchanged from the previous caching model.

updateTag는 Cache Components 전용이 아니지만(이전 caching model에서도 동작함), migration은 이를 도입하기 좋은 시점입니다. Server Action에서 mutation을 한 뒤 사용자가 자신의 변경 사항을 바로 봐야 할 때 사용하세요.

updateTag isn't exclusive to Cache Components (it also works with the previous caching model), but migrating is a good time to adopt it. After a mutation in a Server Action, reach for it when the user should see their own change right away.

page는 params와 searchParams를 props로 받으며, 둘 다 promise입니다. 같은 패턴을 적용하세요: page 최상단에서 await하지 말고, promise를 <Suspense>로 감싼 component에 prop으로 그대로 전달해 그 안에서 await하세요. .then()으로 promise를 inline으로 풀어서 일반 값을 아래로 전달할 수도 있습니다. 비슷한 패턴은 Streaming을 참고하세요.

Your page receives params and searchParams as props, and both are promises. Apply the same pattern: pass the promise straight through to the <Suspense>-wrapped component as a prop and await it there, rather than at the top of the page. You can also unwrap the promise inline with .then() and pass a plain value down; see Streaming for a similar pattern.

TSJSapp/page.tsx
import { Suspense } from 'react'

export default function Page({ searchParams }: PageProps<'/'>) {
  return (
    <Suspense fallback={<p>Loading...</p>}>
      <Results searchParams={searchParams} />
    </Suspense>
  )
}

async function Results({ searchParams }: Pick<PageProps<'/'>, 'searchParams'>) {
  const { query } = await searchParams
  // ...
}

Good to know

root layout에서 cookie나 header 값이 <html> element의 attribute(lang, dir, data-theme 등)를 결정할 때, server에서 이를 읽으면 subtree 전체가 request에 묶이므로 <Suspense>로 감쌀 child가 없습니다. paint 전에 attribute를 설정하는 <head> 안의 inline <script>를 쓰면 shell을 static으로 유지할 수 있습니다. 이 패턴은 Preventing flash before hydration을 참고하세요.

When a cookie or header value drives an attribute on the <html> element in the root layout (lang, dir, data-theme, etc.), reading it on the server makes the whole subtree request-bound, so there's no child to wrap in <Suspense>. An inline <script> in <head> that sets the attribute before paint keeps the shell static; see Preventing flash before hydration for the pattern.

Route Handlers (GET)Route Handler (GET)

dynamic = 'force-static'을 use cache로 바꾸세요.

Replace dynamic = 'force-static' with use cache.

Cache Components가 없을 때 GET Route Handler는 export const dynamic = 'force-static'으로 caching에 opt in하지 않는 한 dynamic입니다. Cache Components에서는 GET handler가 page와 같은 model을 따릅니다: cache되지 않은 데이터나 runtime 데이터에 접근하지 않으면 prerender되고, cache되지 않은 데이터는 use cache로 cache합니다. dynamic config를 제거하고, 데이터 접근을 use cache가 표시된 별도 함수로 옮기세요. directive는 GET export 자체에는 적용할 수 없으므로, handler가 cache된 helper를 호출하는 방식이 됩니다.

Without Cache Components, a GET Route Handler is dynamic unless you opt into caching with export const dynamic = 'force-static'. With Cache Components, GET handlers follow the same model as pages: they prerender when they don't access uncached or runtime data, and you cache uncached data with use cache. Remove the dynamic config and move the data access into a separate function marked with use cache. The directive can't be applied to the GET export itself, so the handler calls a cached helper.

TSJSapp/api/products/route.ts
// Before
export const dynamic = 'force-static'

export async function GET() {
  const products = await db.query('SELECT * FROM products')
  return Response.json(products)
}
// Before
export const dynamic = 'force-static'

export async function GET() {
  const products = await db.query('SELECT * FROM products')
  return Response.json(products)
}
TSJSapp/api/products/route.ts
// After
import { cacheLife } from 'next/cache'

export async function GET() {
  const products = await getProducts()
  return Response.json(products)
}

async function getProducts() {
  'use cache'
  cacheLife('hours')
  return db.query('SELECT * FROM products')
}
// After
import { cacheLife } from 'next/cache'

export async function GET() {
  const products = await getProducts()
  return Response.json(products)
}

async function getProducts() {
  'use cache'
  cacheLife('hours')
  return db.query('SELECT * FROM products')
}
Good to know

GET handler에서 cache되지 않은 데이터나 runtime 데이터를 읽으면 throw를 통해 prerendering에서 빠져나옵니다(bail out). 다른 작업을 감싸고 있던 기존 try/catch가 이 bail-out을 잡게 됩니다. catch block에서 error를 log하면 build output에 noise가 추가됩니다. bail-out 이후에 출력되는 log를 숨기려면 experimental.hideLogsAfterAbort: true를 설정하세요.

Reading uncached or runtime data in a GET handler bails out of prerendering by throwing. A try/catch you already have around other operations will catch that bail-out. If the catch block logs the error, it adds noise to the build output. Set experimental.hideLogsAfterAbort: true to hide logs emitted after a bail-out.

generateMetadata and generateViewportgenerateMetadata와 generateViewport

외부 데이터는 use cache로 cache하거나, 의도적으로 dynamic인 page임을 표시하세요. Cache Components에서 generateMetadata와 generateViewport는 component와 같은 규칙을 따릅니다. 페이지의 나머지는 prerender 가능한데 이 함수들이 runtime 데이터(cookies(), headers(), params, searchParams)를 읽거나 cache되지 않은 데이터를 fetch하면, 선택을 명시적으로 하도록 Next.js가 error를 발생시킵니다. metadata가 runtime 데이터가 아닌 외부 데이터에 의존한다면 use cache를 추가하세요.

Cache external data with use cache, or mark intentionally dynamic pages. Under Cache Components, generateMetadata and generateViewport follow the same rules as components. If they read runtime data (cookies(), headers(), params, searchParams) or fetch uncached data while the rest of the page is otherwise prerenderable, Next.js raises an error so the choice is explicit. If the metadata depends on external but not runtime data, add use cache.

TSapp/page.tsx
// Before
export async function generateMetadata() {
  const { title, description } = await db.query('site-metadata')
  return { title, description }
}
TSapp/page.tsx
// After - cache external data
export async function generateMetadata() {
  'use cache'
  const { title, description } = await db.query('site-metadata')
  return { title, description }
}

metadata에 정말로 runtime 데이터가 필요하다면 generateMetadata를 <Suspense>로 감쌀 수는 없습니다. 대신 page에 dynamic marker component를 추가하면, metadata가 stream되는 동안에도 static 콘텐츠는 여전히 prerender됩니다.

If the metadata genuinely needs runtime data, you can't wrap generateMetadata in <Suspense>. Instead, add a dynamic marker component to the page so the static content still prerenders while the metadata streams in.

TSapp/page.tsx
import { Suspense } from 'react'
import { connection } from 'next/server'

export async function generateMetadata() {
  // reads runtime data
  return { title: 'Personalized Title' }
}

async function DynamicMarker() {
  return (
    <Suspense>
      <Connection />
    </Suspense>
  )
}

async function Connection() {
  await connection()
  return null
}

export default function Page() {
  return (
    <>
      <article>Static content</article>
      <DynamicMarker />
    </>
  )
}

runtime = 'edge'

runtime export를 제거하세요. Cache Components에는 기본값인 Node.js runtime이 필요하며, runtime route segment config를 지원하지 않습니다. runtime = 'nodejs'로 설정되어 있더라도 export를 제거하세요. route가 deprecated된 runtime = 'edge' export를 사용하고 있다면, 이를 제거하고 edge 동작이 필요할 때는 Proxy를 사용하세요.

Remove the runtime export. Cache Components requires the Node.js runtime, which is the default, and does not support the runtime route segment config. Remove the export even when it is set to runtime = 'nodejs'. If a route uses the deprecated runtime = 'edge' export, remove it and use Proxy when you need edge behavior.

experimental_ppr

제거되었습니다. 대신 cacheComponents를 활성화하세요. Next.js 16에서는 실험적인 Partial Prerendering flag(experimental.ppr)와 experimental_ppr route segment config가 제거되었습니다. Removed. Enable cacheComponents instead. Next.js 16 removes the experimental Partial Prerendering flag (experimental.ppr) and the experimental_ppr route segment config. Partial Prerendering is now part of Cache Components, so remove experimental.ppr from next.config and experimental_ppr from your segments. A codemod removes the segment config for you.

UI state preservationUI state 보존

이제 component state가 navigation 사이에서 유지됩니다. Cache Components에서 Next.js는 route를 unmount하는 대신 React의 <Activity> component를 "hidden" mode로 사용해 route를 보존합니다. Effect는 정상적으로 cleanup되고 다시 실행되지만, useState 값, form input, scroll 위치는 다른 곳으로 navigate했다가 돌아와도 더 이상 초기화되지 않습니다.

Component state now persists across navigations. With Cache Components, Next.js preserves routes using React's <Activity> component in "hidden" mode instead of unmounting them. Effects clean up and re-run normally, but useState values, form inputs, and scroll position are no longer reset when navigating away and back.

코드가 state를 지우기 위해 unmount에 의존하고 있었다면, 명시적인 reset 로직을 추가해야 할 수 있습니다:

If your code relied on unmounting to clear state, you may need to add explicit reset logic:

  • Dropdown과 popover: 뒤로 navigate하면 열린 상태로 남습니다. useLayoutEffect cleanup 함수에서 닫으세요.
  • 초기화 로직이 있는 dialog: dialog state에 의존하는 Effect(input에 focus 주기 등)는 state가 보존되었다면 다시 실행되지 않습니다. 대신 URL에서 dialog state를 도출하세요.
  • 제출 후의 form: input 값과 useActionState 결과(성공/error 메시지)가 돌아왔을 때도 유지됩니다. 가능하면 submit handler나 사용자 동작에서 reset하고, 그렇지 않으면 cleanup effect를 사용하세요.
  • Dropdowns and popovers: stay open when navigating back. Close them in a useLayoutEffect cleanup function.
  • Dialogs with initialization logic: Effects that depend on dialog state (like focusing an input) won't re-fire if the state was preserved. Derive dialog state from the URL instead.
  • Forms after submission: input values and useActionState results (success/error messages) persist when returning. Reset in the submit handler or user action when possible, otherwise use a cleanup effect.

각 패턴의 자세한 예시는 Preserving UI state across navigations를 참고하세요.

See Preserving UI state across navigations for detailed examples of each pattern.
