How to think about data security in Next.jsNext.js의 데이터 보안을 생각하는 방법

React Server Components는 performance를 높이고 data fetching을 단순하게 만들어 주지만, 데이터에 접근하는 위치와 방식도 바꾸기 때문에 frontend 앱에서 데이터를 다룰 때의 전통적인 보안 가정 일부를 바꿔 놓습니다.

React Server Components improve performance and simplify data fetching, but also shift where and how data is accessed, changing some of the traditional security assumptions for handling data in frontend apps.

이 가이드는 Next.js에서 데이터 보안을 어떻게 생각해야 하는지, 그리고 best practice를 어떻게 구현하는지 이해하는 데 도움을 줍니다.

This guide will help you understand how to think about data security in Next.js and how to implement best practices.

Data fetching approachesData fetching 방식

Next.js에서 데이터를 fetch할 때 권장하는 주요 방식은 프로젝트의 규모와 연식에 따라 세 가지입니다:

There are three main approaches we recommend for fetching data in Next.js, depending on the size and age of your project:

  • HTTP APIs: 기존의 대규모 애플리케이션과 조직용.
  • Data Access Layer: 새 프로젝트용.
  • Component-Level Data Access: prototype과 학습용.
  • HTTP APIs: for existing large applications and organizations.
  • Data Access Layer: for new projects.
  • Component-Level Data Access: for prototypes and learning.

하나의 data fetching 방식을 골라서 섞지 않고 사용하기를 권장합니다. 그래야 code base에서 일하는 개발자와 보안 감사자(security auditor) 모두 무엇을 예상해야 하는지 분명해집니다.

We recommend choosing one data fetching approach and avoiding mixing them. This makes it clear for both developers working in your code base and security auditors what to expect.

External HTTP APIs외부 HTTP API

기존 프로젝트에 Server Component를 도입할 때는 Zero Trust 모델을 따라야 합니다. Client Component에서와 마찬가지로 Server Component에서도 fetch를 사용해 REST나 GraphQL 같은 기존 API endpoint를 계속 호출할 수 있습니다.

You should follow a Zero Trust model when adopting Server Components in an existing project. You can continue calling your existing API endpoints such as REST or GraphQL from Server Components using fetch, just as you would in Client Components.

TSapp/page.tsx
import { cookies } from 'next/headers'

export default async function Page() {
  const cookieStore = await cookies()
  const token = cookieStore.get('AUTH_TOKEN')?.value

  const res = await fetch('https://api.example.com/profile', {
    headers: {
      Cookie: `AUTH_TOKEN=${token}`,
      // Other headers
    },
  })

  // ....
}

이 방식은 다음과 같은 경우에 잘 맞습니다:

This approach works well when:

  • 이미 보안 관행이 자리 잡혀 있는 경우.
  • 별도의 backend 팀이 다른 언어를 사용하거나 API를 독립적으로 관리하는 경우.
  • You already have security practices in place.
  • Separate backend teams use other languages or manage APIs independently.

Data Access Layer

새 프로젝트에는 전용 Data Access Layer (DAL) 만들기를 권장합니다. 이는 데이터를 언제, 어떻게 fetch하고 render context에 무엇을 전달할지 제어하는 내부 library입니다.

For new projects, we recommend creating a dedicated Data Access Layer (DAL). This is an internal library that controls how and when data is fetched, and what gets passed to your render context.

Data Access Layer는 다음을 지켜야 합니다:

A Data Access Layer should:

  • server에서만 실행됩니다.
  • authorization 검사를 수행합니다.
  • 안전하고 최소한의 데이터만 담은 Data Transfer Objects (DTOs) 형태로 반환합니다.
  • Only run on the server.
  • Perform authorization checks.
  • Return safe, minimal Data Transfer Objects (DTOs).

이 방식은 모든 데이터 접근 로직을 한곳에 모으므로, 일관된 데이터 접근을 강제하기 쉬워지고 authorization 버그의 위험이 줄어듭니다. 또한 하나의 request 안에서 여러 부분이 in-memory cache를 공유하는 이점도 얻을 수 있습니다.

This approach centralizes all data access logic, making it easier to enforce consistent data access and reduces the risk of authorization bugs. You also get the benefit of sharing an in-memory cache across different parts of a request.

TSdata/auth.ts
import { cache } from 'react'
import { cookies } from 'next/headers'

// Cached helper methods makes it easy to get the same value in many places
// without manually passing it around. This discourages passing it from Server
// Component to Server Component which minimizes risk of passing it to a Client
// Component.
export const getCurrentUser = cache(async () => {
  const cookieStore = await cookies()
  const token = cookieStore.get('AUTH_TOKEN')
  const decodedToken = await decryptAndValidate(token)
  // Don't include secret tokens or private information as public fields.
  // Use classes to avoid accidentally passing the whole object to the client.
  return new User(decodedToken.id)
})
TSdata/user-dto.tsx
import 'server-only'
import { getCurrentUser } from './auth'

function canSeeUsername(viewer: User) {
  // Public info for now, but can change
  return true
}

function canSeePhoneNumber(viewer: User, team: string) {
  // Privacy rules
  return viewer.isAdmin || team === viewer.team
}

export async function getProfileDTO(slug: string) {
  // Don't pass values, read back cached values, also solves context and easier to make it lazy

  // use a database API that supports safe templating of queries
  const [rows] = await sql`SELECT * FROM user WHERE slug = ${slug}`
  const userData = rows[0]

  const currentUser = await getCurrentUser()

  // only return the data relevant for this query and not everything
  // <https://www.w3.org/2001/tag/doc/APIMinimization>
  return {
    username: canSeeUsername(currentUser) ? userData.username : null,
    phonenumber: canSeePhoneNumber(currentUser, userData.team)
      ? userData.phonenumber
      : null,
  }
}
TSapp/page.tsx
import { getProfileDTO } from '../../data/user-dto'

export default async function Page({ params }) {
  const { slug } = await params
  // This page can now safely pass around this profile knowing
  // that it shouldn't contain anything sensitive.
  const profile = await getProfileDTO(slug)
  ...
}
Good to know

secret key는 environment variable에 저장해야 하지만, process.env에는 Data Access Layer만 접근해야 합니다. 그래야 secret이 애플리케이션의 다른 부분에 노출되지 않습니다.

Secret keys should be stored in environment variables, but only the Data Access Layer should access process.env. This keeps secrets from being exposed to other parts of the application.

Component-level data accessComponent 수준 데이터 접근

빠른 prototype과 반복 작업을 위해서는 database query를 Server Component 안에 직접 둘 수 있습니다.

For quick prototypes and iteration, database queries can be placed directly in Server Components.

하지만 이 방식은 예를 들어 다음과 같이 private 데이터를 실수로 client에 노출하기 쉽습니다:

This approach, however, makes it easier to accidentally expose private data to the client, for example:

TSapp/page.tsx
import Profile from './components/profile.tsx'

export default async function Page({ params }) {
  const { slug } = await params
  const [rows] = await sql`SELECT * FROM user WHERE slug = ${slug}`
  const userData = rows[0]
  // EXPOSED: This exposes all the fields in userData to the client because
  // we are passing the data from the Server Component to the Client.
  return <Profile user={userData} />
}
TSapp/ui/profile.tsx
'use client'

// BAD: This is a bad props interface because it accepts way more data than the
// Client Component needs and it encourages server components to pass all that
// data down. A better solution would be to accept a limited object with just
// the fields necessary for rendering the profile.
export default async function Profile({ user }: { user: User }) {
  return (
    <div>
      <h1>{user.name}</h1>
      ...
    </div>
  )
}

Client Component에 전달하기 전에 데이터를 정제(sanitize)해야 합니다:

You should sanitize the data before passing it to the Client Component:

TSdata/user.ts
import { sql } from './db'

export async function getUser(slug: string) {
  const [rows] = await sql`SELECT * FROM user WHERE slug = ${slug}`
  const user = rows[0]

  // Return only the public fields
  return {
    name: user.name,
  }
}
TSapp/page.tsx
import { getUser } from '../data/user'
import Profile from './ui/profile'

export default async function Page({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params
  const publicProfile = await getUser(slug)
  return <Profile user={publicProfile} />
}

Reading data데이터 읽기

Passing data from server to clientserver에서 client로 데이터 전달하기

초기 load 시에는 Server Component와 Client Component 모두 server에서 실행되어 HTML을 생성합니다. 하지만 둘은 서로 격리된 module system에서 실행됩니다. 덕분에 Server Component는 private 데이터와 API에 접근할 수 있지만 Client Component는 그럴 수 없습니다.

On the initial load, both Server and Client Components run on the server to generate HTML. However, they execute in isolated module systems. This ensures that Server Components can access private data and APIs, while Client Components cannot.

Server Components:

Server Components:

  • server에서만 실행됩니다.
  • environment variable, secret, database, 내부 API에 안전하게 접근할 수 있습니다.
  • Run only on the server.
  • Can safely access environment variables, secrets, databases, and internal APIs.

Client Components:

Client Components:

  • prerendering 중에는 server에서 실행되지만, 브라우저에서 실행되는 코드와 같은 보안 가정을 따라야 합니다.
  • 권한이 필요한(privileged) 데이터나 server 전용 module에 접근해서는 안 됩니다.
  • Run on the server during prerendering, but must follow the same security assumptions as code running in the browser.
  • Must not access privileged data or server-only modules.

이렇게 해서 앱은 기본적으로 안전하지만, 데이터를 fetch하거나 component에 전달하는 방식에 따라 private 데이터가 실수로 노출될 수 있습니다.

This ensures the app is secure by default, but it's possible to accidentally expose private data through how data is fetched or passed to components.

Tainting

private 데이터가 실수로 client에 노출되는 것을 막기 위해 React Taint API를 사용할 수 있습니다:

To prevent accidental exposure of private data to the client, you can use React Taint APIs:

  • 데이터 객체에는 experimental_taintObjectReference.
  • 특정 값에는 experimental_taintUniqueValue.
  • experimental_taintObjectReference for data objects.
  • experimental_taintUniqueValue for specific values.

next.config.js의 experimental.taint option으로 Next.js 앱에서 이 기능을 활성화할 수 있습니다:

You can enable usage in your Next.js app with the experimental.taint option in next.config.js:

JSnext.config.js
module.exports = {
  experimental: {
    taint: true,
  },
}

이렇게 하면 taint된 객체나 값이 client로 전달되지 않습니다. 하지만 이는 추가적인 보호 계층일 뿐이므로, React의 render context에 전달하기 전에 DAL에서 데이터를 필터링하고 정제하는 작업은 여전히 해야 합니다.

This prevents the tainted objects or values from being passed to the client. However, it's an additional layer of protection, you should still filter and sanitize the data in your DAL before passing it to React's render context.

Good to know
  • 기본적으로 environment variable은 Server에서만 사용할 수 있습니다. Next.js는 NEXT_PUBLIC_ 접두사가 붙은 environment variable만 client에 노출합니다. 더 알아보기.
  • 함수와 class는 기본적으로 이미 Client Component에 전달되지 않도록 차단되어 있습니다.
  • By default, environment variables are only available on the Server. Next.js exposes any environment variable prefixed with NEXT_PUBLIC_ to the client. Learn more.
  • Functions and classes are already blocked from being passed to Client Components by default.

Preventing client-side execution of server-only codeserver 전용 코드의 client 실행 막기

server 전용 코드가 client에서 실행되지 않도록 하려면 server-only package로 module을 표시할 수 있습니다:

To prevent server-only code from being executed on the client, you can mark a module with the server-only package:

TSlib/data.ts
import 'server-only'

//...

이렇게 하면 해당 module이 client 환경에서 import될 때 build error가 발생하므로, 독점 코드나 내부 business logic이 server에만 머물게 됩니다.

This ensures that proprietary code or internal business logic stays on the server by causing a build error if the module is imported in the client environment.

Next.js는 server-only import를 내부적으로 처리합니다. NPM에 있는 이 package들의 내용은 사용되지 않습니다. 다만 linting rule이 불필요한(extraneous) dependency를 경고한다면, 문제를 피하기 위해 설치해 둘 수 있습니다.

Next.js handles server-only imports internally. The contents of these packages from NPM are not used. However, if your linting rules flag extraneous dependencies, you may install them to avoid issues.

npm install server-only
yarn add server-only
pnpm add server-only
bun add server-only

server-only에 대한 자세한 내용은 environment poisoning 방지 섹션을 참고하세요.

Read more about server-only in the preventing environment poisoning section.

Mutating Data데이터 변경하기

Next.js는 Server Actions로 mutation을 처리합니다.

Next.js handles mutations with Server Actions.

Built-in Server Actions Security features내장 Server Actions 보안 기능

기본적으로 Server Action을 만들고 export하면, 애플리케이션 UI를 통해서뿐 아니라 직접적인 POST request로도 접근할 수 있습니다. 즉, Server Action이나 utility 함수가 코드의 다른 곳에서 import되지 않더라도 외부에서 호출될 수 있습니다.

By default, when a Server Action is created and exported, it is reachable via a direct POST request, not just through your application's UI. This means, even if a Server Action or utility function is not imported elsewhere in your code, it can still be called externally.

보안을 강화하기 위해 Next.js에는 다음과 같은 기능이 내장되어 있습니다:

To improve security, Next.js has the following built-in features:

  • Secure action IDs: Next.js는 client가 Server Action을 참조하고 호출할 수 있도록 암호화된 비결정적(non-deterministic) ID를 만듭니다. 보안 강화를 위해 이 ID는 build 사이에 주기적으로 다시 계산됩니다.
  • Dead code elimination: 사용되지 않는 Server Action(ID로 참조됨)은 공개 접근을 막기 위해 client bundle에서 제거됩니다.
  • Secure action IDs: Next.js creates encrypted, non-deterministic IDs to allow the client to reference and call the Server Action. These IDs are periodically recalculated between builds for enhanced security.
  • Dead code elimination: Unused Server Actions (referenced by their IDs) are removed from client bundle to avoid public access.
Good to know

ID는 compile 중에 생성되며 최대 14일 동안 cache됩니다. 새 build가 시작되거나 build cache가 무효화되면 다시 생성됩니다. 이 보안 개선은 authentication 계층이 빠져 있는 경우의 위험을 줄여 줍니다. 하지만 Server Action은 여전히 직접적인 POST request로 접근 가능하다고 간주하고, 각 action 안에서 authentication과 authorization을 검증해야 합니다.

The IDs are created during compilation and are cached for a maximum of 14 days. They will be regenerated when a new build is initiated or when the build cache is invalidated. This security improvement reduces the risk in cases where an authentication layer is missing. However, you should still treat Server Actions as reachable via direct POST requests and verify authentication and authorization inside each one.

// app/actions.js
'use server'

// If this action **is** used in our application, Next.js
// will create a secure ID to allow the client to reference
// and call the Server Action.
export async function updateUserAction(formData) {}

// If this action **is not** used in our application, Next.js
// will automatically remove this code during `next build`
// and will not create a public endpoint.
export async function deleteUserAction(formData) {}

Validating client inputclient 입력 검증하기

client에서 오는 입력은 쉽게 조작될 수 있으므로 항상 검증해야 합니다. 예를 들어 form data, URL parameter, header, searchParams 등이 있습니다:

You should always validate input from client, as they can be easily modified. For example, form data, URL parameters, headers, and searchParams:

TSapp/page.tsx
// BAD: Trusting searchParams directly
export default async function Page({ searchParams }) {
  const isAdmin = (await searchParams).isAdmin
  if (isAdmin === 'true') {
    // Vulnerable: relies on untrusted client data
    return <AdminPanel />
  }
}

// GOOD: Re-verify every time
import { cookies } from 'next/headers'
import { verifyAdmin } from './auth'

export default async function Page() {
  const cookieStore = await cookies()
  const token = cookieStore.get('AUTH_TOKEN')
  const isAdmin = await verifyAdmin(token)

  if (isAdmin) {
    return <AdminPanel />
  }
}

Authentication and authorizationAuthentication과 authorization

page 수준의 authentication 검사는 그 안에 정의된 Server Action까지 적용되지 않습니다. action 안에서 항상 다시 검증하세요:

A page-level authentication check does not extend to the Server Actions defined within it. Always re-verify inside the action:

TSapp/admin/page.tsx
import { auth } from '@/lib/auth'
import { redirect } from 'next/navigation'

export default async function AdminPage() {
  const session = await auth()
  if (!session?.user?.isAdmin) {
    redirect('/login')
  }

  return (
    <form
      action={async () => {
        'use server'
        const session = await auth()
        if (!session?.user?.isAdmin) {
          throw new Error('Unauthorized')
        }
        await db.record.deleteMany()
      }}
    >
      <button>Delete Records</button>
    </form>
  )
}

action 안에서 강조 표시된 auth() 검사가 핵심입니다. 6번째 줄의 page 수준 redirect는 어떤 UI를 render할지를 제어하지만, Server Action은 별도의 진입점(entry point)이므로 호출자를 스스로 검증해야 합니다.

The highlighted auth() check inside the action is critical. The page-level redirect on line 6 controls which UI is rendered, but the Server Action is a separate entry point and must verify the caller on its own.

authentication(사용자가 로그인했는가?) 외에도 authorization(이 사용자가 이 특정 리소스에 대해 작업할 권한이 있는가?)을 확인하는 것을 잊지 마세요. 이렇게 하면 Insecure Direct Object Reference (IDOR) 취약점을 막을 수 있습니다:

Beyond authentication (is the user logged in?), remember to check authorization (does this user have permission to act on this specific resource?). This prevents Insecure Direct Object Reference (IDOR) vulnerabilities:

TSapp/actions.ts
'use server'

import { auth } from '@/lib/auth'
import { db } from '@/lib/db'

export async function deletePost(postId: string) {
  const session = await auth()
  if (!session?.user) {
    throw new Error('Unauthorized')
  }

  const post = await db.post.findUnique({ where: { id: postId } })

  // Check that the user owns this resource
  if (post.authorId !== session.user.id) {
    throw new Error('Forbidden')
  }

  await db.post.delete({ where: { id: postId } })
}

Learn more about Authentication in Next.js.

Using a Data Access Layer for mutationsmutation에 Data Access Layer 사용하기

데이터 읽기에 Data Access Layer를 권장하는 것처럼, mutation에도 같은 패턴을 적용할 수 있습니다. 이렇게 하면 authentication, authorization, database 로직은 전용 server-only module에 두고 "use server" action은 얇게 유지할 수 있습니다.

Just as we recommend a Data Access Layer for reading data, you can apply the same pattern to mutations. This keeps authentication, authorization, and database logic in a dedicated server-only module, while "use server" actions stay thin.

TSdata/posts.ts
import 'server-only'

import { auth } from '@/lib/auth'
import { db } from '@/lib/db'

export async function deletePost(postId: string) {
  const session = await auth()
  if (!session?.user) {
    throw new Error('Unauthorized')
  }

  const post = await db.post.findUnique({ where: { id: postId } })

  if (post.authorId !== session.user.id) {
    throw new Error('Forbidden')
  }

  await db.post.delete({ where: { id: postId } })
}

그러면 "use server" action은 DAL에 작업을 위임합니다:

The "use server" action then delegates to the DAL:

TSapp/actions.ts
'use server'

import { deletePost } from '@/data/posts'
import { revalidatePath } from 'next/cache'

export async function deletePostAction(postId: string) {
  await deletePost(postId) // Auth + authz happen inside the DAL
  revalidatePath('/posts')
}
Good to know

import 'server-only'는 Data Access Layer와 "use server" 파일 자체 양쪽에서 모두 사용할 수 있습니다. "use server" module은 server 전용 webpack layer에서 resolve되기 때문에, action을 Client Component에 import하는 경우(예: useActionState에 전달하기 위해)에도 둘 다 동작합니다.

You can use import 'server-only' in both the Data Access Layer and the "use server" file itself. Both work when the action is imported into a Client Component (for example, to pass it to useActionState), because "use server" modules are resolved in a server-only webpack layer.

Controlling return values반환 값 제어하기

Server Action의 반환 값은 직렬화(serialize)되어 client로 전송됩니다. 원시 database record가 아니라 UI에 필요한 것만 반환하세요.

Server Action return values are serialized and sent to the client. Only return what the UI needs, not raw database records.

TSapp/actions.ts
'use server'

import { auth } from '@/lib/auth'
import { db } from '@/lib/db'

// BAD: Returns the full database record, which may include
// internal fields the client should not see.
export async function updateUser(data: FormData) {
  const session = await auth()
  if (!session?.user) {
    throw new Error('Unauthorized')
  }
  return db.user.update({
    where: { id: session.user.id },
    data: { name: data.get('name') as string },
  })
}

// GOOD: Returns only what the client needs.
export async function updateUserSafe(data: FormData) {
  const session = await auth()
  if (!session?.user) {
    throw new Error('Unauthorized')
  }
  await db.user.update({
    where: { id: session.user.id },
    data: { name: data.get('name') as string },
  })
  return { success: true }
}

Rate limiting

For expensive operations (sending emails, writing to a database), consider adding rate limiting to prevent abuse. See the Rate limiting example in the Backend for Frontend guide.

Closures and encryptionClosure와 암호화

component 안에 Server Action을 정의하면 action이 바깥 함수의 scope에 접근할 수 있는 closure가 만들어집니다. 예를 들어 publish action은 publishVersion 변수에 접근할 수 있습니다:

Defining a Server Action inside a component creates a closure where the action has access to the outer function's scope. For example, the publish action has access to the publishVersion variable:

TSJSapp/page.tsx
export default async function Page() {
  const publishVersion = await getLatestVersion();

  async function publish() {
    "use server";
    if (publishVersion !== await getLatestVersion()) {
      throw new Error('The version has changed since pressing publish');
    }
    ...
  }

  return (
    <form>
      <button formAction={publish}>Publish</button>
    </form>
  );
}
export default async function Page() {
  const publishVersion = await getLatestVersion();

  async function publish() {
    "use server";
    if (publishVersion !== await getLatestVersion()) {
      throw new Error('The version has changed since pressing publish');
    }
    ...
  }

  return (
    <form>
      <button formAction={publish}>Publish</button>
    </form>
  );
}

closure는 rendering 시점의 데이터(예: publishVersion)의 *snapshot*을 캡처해 두었다가 나중에 action이 호출될 때 사용해야 할 때 유용합니다.

Closures are useful when you need to capture a snapshot of data (e.g. publishVersion) at the time of rendering so that it can be used later when the action is invoked.

하지만 이를 위해 캡처된 변수는 client로 전송되었다가 action이 호출될 때 다시 server로 돌아옵니다. 민감한 데이터가 client에 노출되지 않도록 Next.js는 closure로 캡처된(closed-over) 변수를 자동으로 암호화합니다. Next.js 애플리케이션을 build할 때마다 각 action에 대해 새로운 private key가 생성됩니다. 즉, action은 특정 build에 대해서만 호출할 수 있습니다.

However, for this to happen, the captured variables are sent to the client and back to the server when the action is invoked. To prevent sensitive data from being exposed to the client, Next.js automatically encrypts the closed-over variables. A new private key is generated for each action every time a Next.js application is built. This means actions can only be invoked for a specific build.

Good to know

민감한 값이 client에 노출되는 것을 막기 위해 암호화에만 의존하는 것은 권장하지 않습니다.

We don't recommend relying on encryption alone to prevent sensitive values from being exposed on the client.

Overwriting encryption keys (advanced)암호화 key 덮어쓰기 (고급)

Next.js 애플리케이션을 여러 server에 걸쳐 self-hosting하면, 각 server instance가 서로 다른 암호화 key를 갖게 되어 불일치가 생길 수 있습니다.

When self-hosting your Next.js application across multiple servers, each server instance may end up with a different encryption key, leading to potential inconsistencies.

이를 완화하려면 process.env.NEXT_SERVER_ACTIONS_ENCRYPTION_KEY environment variable로 암호화 key를 덮어쓸 수 있습니다. 이 변수를 지정하면 암호화 key가 build 간에 유지되고, 모든 server instance가 같은 key를 사용합니다.

To mitigate this, you can overwrite the encryption key using the process.env.NEXT_SERVER_ACTIONS_ENCRYPTION_KEY environment variable. Specifying this variable ensures that your encryption keys are persistent across builds, and all server instances use the same key.

key는 decode한 길이가 유효한 AES key 크기(16, 24, 32 byte)와 일치하는 base64 인코딩 값이어야 합니다. Next.js는 기본적으로 32 byte key를 생성합니다. 플랫폼의 암호화 도구로 호환되는 key를 생성할 수 있습니다. 예를 들면 다음과 같습니다:

The key must be a base64-encoded value whose decoded length matches a valid AES key size (16, 24, or 32 bytes). Next.js generates 32-byte keys by default. You can generate a compatible key using your platform’s cryptographic tools, for example:

openssl rand -base64 32

이는 여러 deployment에 걸쳐 일관된 암호화 동작이 애플리케이션에 중요한 고급 사용 사례입니다. key rotation과 서명(signing) 같은 표준 보안 관행을 따르세요. deployment별 고려 사항은 Self-Hosting 가이드를 참고하세요.

This is an advanced use case where consistent encryption behavior across multiple deployments is critical for your application. Follow standard security practices such as key rotation and signing. See the Self-Hosting guide for deployment-specific considerations.

Allowed origins (advanced)허용된 origin (고급)

Server Action은 <form> element에서 호출될 수 있으므로 CSRF 공격에 노출될 수 있습니다.

Since Server Actions can be invoked in a <form> element, this opens them up to CSRF attacks.

내부적으로 Server Action은 POST method를 사용하며, 이 HTTP method로만 호출할 수 있습니다. 특히 SameSite cookie가 기본값인 최신 브라우저에서는 이것만으로도 대부분의 CSRF 취약점을 막을 수 있습니다.

Behind the scenes, Server Actions use the POST method, and only this HTTP method is allowed to invoke them. This prevents most CSRF vulnerabilities in modern browsers, particularly with SameSite cookies being the default.

추가 보호 장치로, Next.js의 Server Action은 Origin header를 Host header(또는 X-Forwarded-Host)와 비교합니다. 둘이 일치하지 않으면 request가 중단됩니다. 다시 말해, Server Action은 그것을 호스팅하는 page와 같은 host에서만 호출할 수 있습니다.

As an additional protection, Server Actions in Next.js also compare the Origin header to the Host header (or X-Forwarded-Host). If these don't match, the request will be aborted. In other words, Server Actions can only be invoked on the same host as the page that hosts it.

reverse proxy나 다층 backend 아키텍처(server API가 production domain과 다른 경우)를 사용하는 대규모 애플리케이션에서는 configuration option인 serverActions.allowedOrigins를 사용해 안전한 origin 목록을 지정하는 것을 권장합니다. 이 option은 문자열 배열을 받습니다.

For large applications that use reverse proxies or multi-layered backend architectures (where the server API differs from the production domain), it's recommended to use the configuration option serverActions.allowedOrigins option to specify a list of safe origins. The option accepts an array of strings.

JSnext.config.js
/** @type {import('next').NextConfig} */
module.exports = {
  experimental: {
    serverActions: {
      allowedOrigins: ['my-proxy.com', '*.my-proxy.com'],
    },
  },
}

Avoiding side-effects during renderingrendering 중 side-effect 피하기

mutation(예: 사용자 로그아웃, database 업데이트, cache 무효화)은 Server Component든 Client Component든 절대 side-effect가 되어서는 안 됩니다. Next.js는 의도치 않은 side effect를 막기 위해 render method 안에서 cookie를 설정하거나 cache revalidation을 트리거하는 것을 명시적으로 막습니다.

Mutations (e.g. logging out users, updating databases, invalidating caches) should never be a side-effect, either in Server or Client Components. Next.js explicitly prevents setting cookies or triggering cache revalidation within render methods to avoid unintended side effects.

TSapp/page.tsx
// BAD: Triggering a mutation during rendering
export default async function Page({ searchParams }) {
  if ((await searchParams).logout) {
    const cookieStore = await cookies()
    cookieStore.delete('AUTH_TOKEN')
  }

  return <UserProfile />
}

대신 Server Action을 사용해 mutation을 처리해야 합니다.

Instead, you should use Server Actions to handle mutations.

TSapp/page.tsx
// GOOD: Using Server Actions to handle mutations
import { logout } from './actions'

export default function Page() {
  return (
    <>
      <UserProfile />
      <form action={logout}>
        <button type="submit">Logout</button>
      </form>
    </>
  )
}
Good to know

Next.js는 mutation을 처리할 때 POST request를 사용합니다. 이렇게 하면 GET request로 인한 의도치 않은 side-effect를 막아 Cross-Site Request Forgery (CSRF) 위험을 줄일 수 있습니다.

Next.js uses POST requests to handle mutations. This prevents accidental side-effects from GET requests, reducing Cross-Site Request Forgery (CSRF) risks.

Auditing감사(Auditing)

Next.js 프로젝트를 감사(audit)하고 있다면, 특히 더 살펴보기를 권장하는 몇 가지 항목은 다음과 같습니다:

If you're doing an audit of a Next.js project, here are a few things we recommend looking extra at:

  • Data Access Layer: 격리된 Data Access Layer에 대한 확립된 관행이 있나요? database package와 environment variable이 Data Access Layer 밖에서 import되지 않는지 확인하세요.
  • "use client" files: Component props가 private 데이터를 기대하고 있나요? type signature가 지나치게 넓지는 않나요?
  • "use server" files: Action 인수가 action 안이나 Data Access Layer 안에서 검증되나요? action 안에서 사용자가 다시 authorize되나요? action이 리소스의 소유권을 확인하나요(authentication만이 아니라 authorization까지)? 반환 값이 client에 필요한 것만 남도록 필터링되나요? database 접근이 server-only Data Access Layer에 위임되어 있나요?
  • /[param]/. 대괄호가 있는 폴더는 사용자 입력입니다. params가 검증되나요?
  • proxy.ts and route.ts: 강력한 권한을 가집니다. 전통적인 기법으로 이 파일들을 감사하는 데 시간을 더 들이세요. Penetration Testing이나 Vulnerability Scanning을 정기적으로, 또는 팀의 소프트웨어 개발 lifecycle에 맞춰 수행하세요.
  • Data Access Layer: Is there an established practice for an isolated Data Access Layer? Verify that database packages and environment variables are not imported outside the Data Access Layer.
  • "use client" files: Are the Component props expecting private data? Are the type signatures overly broad?
  • "use server" files: Are the Action arguments validated in the action or inside the Data Access Layer? Is the user re-authorized inside the action? Does the action check ownership of the resource (authorization, not just authentication)? Are return values filtered to only what the client needs? Is database access delegated to a server-only Data Access Layer?
  • /[param]/. Folders with brackets are user input. Are params validated?
  • proxy.ts and route.ts: Have a lot of power. Spend extra time auditing these using traditional techniques. Perform Penetration Testing or Vulnerability Scanning regularly or in alignment with your team's software development lifecycle.
