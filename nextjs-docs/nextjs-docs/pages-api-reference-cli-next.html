next CLInext CLI

Next.js CLI를 사용하면 애플리케이션을 개발(develop), build, start하는 등 다양한 작업을 할 수 있습니다.

The Next.js CLI allows you to develop, build, start your application, and more.

기본 사용법:

Basic usage:

pnpm next [command] [options]
npx next [command] [options]
yarn next [command] [options]
bunx next [command] [options]
Good to know

npm run을 사용할 때는 CLI flag 앞에 --를 붙여야 npm이 flag를 next로 전달합니다. pnpm, yarn, bun에서는 필요하지 않습니다.

With npm run, use -- before CLI flags so npm forwards them to next. This is not required for pnpm, yarn, or bun.

next dev optionsnext dev 옵션

next dev는 Hot Module Reloading(HMR), error reporting 등을 갖춘 development mode로 애플리케이션을 시작합니다.

next dev starts the application in development mode with Hot Module Reloading (HMR), error reporting, and more.

Good to know

development build는 .next 대신 .next/dev에 출력됩니다. 덕분에 next dev와 next build를 충돌 없이 동시에 실행할 수 있습니다.

Development builds output to .next/dev instead of .next. This allows you to run next dev and next build concurrently without conflicts.

next typegen optionsnext typegen 옵션

next typegen은 전체 build를 수행하지 않고 애플리케이션의 route에 대한 TypeScript 정의를 생성합니다. IDE autocomplete와 route 사용에 대한 CI type-checking에 유용합니다.

next typegen generates TypeScript definitions for your application's routes without performing a full build. This is useful for IDE autocomplete and CI type-checking of route usage.

이전에는 route type이 next dev나 next build 중에만 생성되었기 때문에, tsc --noEmit을 직접 실행하면 route type이 검증되지 않았습니다. 이제는 type을 독립적으로 생성하고 외부에서 검증할 수 있습니다:

Previously, route types were only generated during next dev or next build, which meant running tsc --noEmit directly wouldn't validate your route types. Now you can generate types independently and validate them externally:

>_Terminal
# Generate route types first, then validate with TypeScript
next typegen && tsc --noEmit

# Or in CI workflows for type checking without building
next typegen && npm run type-check

>_Terminal

또한 next typegen은 next-env.d.ts 파일을 생성합니다. next-env.d.ts는 .gitignore 파일에 추가하는 것을 권장합니다.

Additionally, next typegen generates a next-env.d.ts file. We recommend adding next-env.d.ts to your .gitignore file.

next-env.d.ts 파일은 tsconfig.json 파일에 포함되어, 프로젝트에서 Next.js type을 사용할 수 있게 해 줍니다.

The next-env.d.ts file is included into your tsconfig.json file, to make Next.js types available to your project.

type-checking 전에 next-env.d.ts가 존재하도록 하려면 next typegen을 실행하세요. next dev와 next build command도 next-env.d.ts 파일을 생성하지만, CI/CD 환경처럼 type-check만을 위해 이 command들을 실행하는 것은 바람직하지 않은 경우가 많습니다.

To ensure next-env.d.ts is present before type-checking run next typegen. The commands next dev and next build also generate the next-env.d.ts file, but it is often undesirable to run these just to type-check, for example in CI/CD environments.

Good to know

next typegen은 production build phase를 사용해 Next.js config(next.config.js, next.config.mjs, 또는 next.config.ts)를 load합니다. config가 올바르게 load될 수 있도록 필요한 environment variable과 dependency가 모두 준비되어 있는지 확인하세요.

next typegen loads your Next.js config (next.config.js, next.config.mjs, or next.config.ts) using the production build phase. Ensure any required environment variables and dependencies are available so the config can load correctly.

next analyze optionsnext analyze 옵션

next analyze는 Turbopack을 사용해 애플리케이션의 bundle output을 분석합니다. 이 command는 JavaScript, CSS 및 기타 asset을 포함해 bundle의 크기와 구성을 이해하는 데 도움이 됩니다. 이 command는 애플리케이션 build를 생성하지 않습니다.

next analyze analyzes your application's bundle output using Turbopack. This command helps you understand the size and composition of your bundles, including JavaScript, CSS, and other assets. This command doesn't produce an application build.

pnpm next analyze
npx next analyze
yarn next analyze
bunx next analyze

기본적으로 이 command는 분석이 끝나면 로컬 server를 시작해, 브라우저에서 bundle 구성을 살펴볼 수 있게 해 줍니다. analyzer로 다음을 할 수 있습니다:

By default, the command starts a local server after analysis completes, allowing you to explore your bundle composition in the browser. The analyzer lets you:

  • route별로 bundle을 filter하고 client view와 server view 사이를 전환
  • module이 왜 포함되었는지 보여주는 전체 import chain 확인
  • server-to-client component 경계와 dynamic import를 가로지르는 import 추적
  • Filter bundles by route and switch between client and server views
  • View the full import chain showing why a module is included
  • Trace imports across server-to-client component boundaries and dynamic imports

최적화 전략은 Package Bundling을 참고하세요.

See Package Bundling for optimization strategies.

server를 시작하지 않고 분석 output을 디스크에 쓰려면 --output을 사용하세요. snapshot과 interactive UI 파일은 <distDir>/diagnostics/analyze(보통 .next/diagnostics/analyze)에 작성됩니다.

To write the analysis output to disk without starting the server, use --output. Snapshot and interactive UI files are written to <distDir>/diagnostics/analyze (normally .next/diagnostics/analyze).

>_Terminal
# Build and save a snapshot without starting the UI server
npx next analyze --output --snapshot audit-1

# Stream that saved graph as one JSON object per line, without rebuilding
npx next analyze export --snapshot audit-1 > graph.jsonl

next analyze export optionsnext analyze export 옵션

export subcommand는 기존 snapshot을 일련의 JSON Lines로 stream합니다. 자체적으로 분석을 실행하거나 web UI를 시작하지는 않습니다.

The export subcommand streams an existing snapshot as a series of JSON Lines. It does not run analysis itself or start the web UI.

Debugging prerender errorsprerender error 디버깅

next build 중에 prerendering error가 발생하면 --debug-prerender flag를 전달해 더 자세한 output을 얻을 수 있습니다:

If you encounter prerendering errors during next build, you can pass the --debug-prerender flag to get more detailed output:

>_Terminal
next build --debug-prerender

이 flag는 debugging을 쉽게 하기 위해 여러 experimental option을 활성화합니다:

This enables several experimental options to make debugging easier:

  • server 코드 minification을 비활성화합니다:
    • experimental.serverMinification = false
    • experimental.turbopackMinify = false
  • server bundle에 대한 source map을 생성합니다:
    • experimental.serverSourceMaps = true
  • 첫 번째 prerender error가 발생한 뒤에도 build를 계속 진행해, 모든 문제를 한 번에 볼 수 있게 합니다:
    • experimental.prerenderEarlyExit = false
  • Disables server code minification:
    • experimental.serverMinification = false
    • experimental.turbopackMinify = false
  • Generates source maps for server bundles:
    • experimental.serverSourceMaps = true
  • Continues building even after the first prerender error, so you can see all issues at once:
    • experimental.prerenderEarlyExit = false

이렇게 하면 build output에서 더 읽기 쉬운 stack trace와 code frame을 확인할 수 있습니다.

This helps surface more readable stack traces and code frames in the build output.

Warning

--debug-prerender는 development에서 debugging할 때만 사용하세요. --debug-prerender로 생성한 build는 performance에 영향을 줄 수 있으므로 production에 deploy하지 마세요.

--debug-prerender is for debugging in development only. Do not deploy builds generated with --debug-prerender to production, as it may impact performance.

Building specific routes특정 route만 build하기

--debug-build-paths option을 사용하면 App Router와 Pages Router에서 특정 route만 build할 수 있습니다. 대규모 애플리케이션에서 작업할 때 더 빠르게 debugging하는 데 유용합니다. --debug-build-paths option은 쉼표로 구분된 파일 경로를 받으며, glob pattern을 지원하고, !로 시작하는 경로는 제외합니다:

You can build only specific routes in the App and Pages Routers using the --debug-build-paths option. This is useful for faster debugging when working with large applications. The --debug-build-paths option accepts comma-separated file paths, supports glob patterns, and excludes any path prefixed with !:

>_Terminal
# Build a specific route
next build --debug-build-paths="app/page.tsx"

# Build more than one route
next build --debug-build-paths="app/page.tsx,pages/index.tsx"

# Include route group folders in the path
next build --debug-build-paths="app/(marketing)/about/page.tsx"

# Use glob patterns
next build --debug-build-paths="app/**/page.tsx"
next build --debug-build-paths="pages/*.tsx"

# Exclude routes with a ! prefix
next build --debug-build-paths="app/**/page.tsx,!app/admin/**"

더 자세한 prerender 진단을 위해 --debug-build-paths를 --debug-prerender와 함께 사용할 수 있습니다.

You can combine --debug-build-paths with --debug-prerender for more detailed prerender diagnostics.

route를 src/ 아래에 두는 프로젝트에서는 src/ prefix가 있든 없든 경로가 resolve되므로, app/page.tsx와 src/app/page.tsx는 모두 같은 route와 일치합니다.

In projects that keep routes under src/, paths resolve with or without the src/ prefix, so both app/page.tsx and src/app/page.tsx match the same route.

일치하는 route만 route table에 나타납니다. App Router route를 선택하면 Next.js는 내장 /_not-found route도 함께 포함합니다.

Only matching routes appear in the route table. When you select an App Router route, Next.js also includes the built-in /_not-found route.

Changing the default port기본 port 변경하기

기본적으로 Next.js는 development 중과 next start에서 http://localhost:3000을 사용합니다. 기본 port는 다음과 같이 -p option으로 변경할 수 있습니다:

By default, Next.js uses http://localhost:3000 during development and with next start. The default port can be changed with the -p option, like so:

>_Terminal
next dev -p 4000

또는 PORT environment variable을 사용할 수 있습니다:

Or using the PORT environment variable:

>_Terminal
PORT=4000 next dev
Good to know

HTTP server 부팅은 다른 어떤 코드보다 먼저 초기화되므로 PORT는 .env에서 설정할 수 없습니다.

PORT cannot be set in .env as booting up the HTTP server happens before any other code is initialized.

Using HTTPS during developmentdevelopment 중에 HTTPS 사용하기

webhook이나 authentication 같은 특정 use case에서는 HTTPS를 사용해 localhost에서 안전한 환경을 만들 수 있습니다. Next.js는 --experimental-https flag를 사용해 next dev로 self-signed certificate를 생성할 수 있습니다:

For certain use cases like webhooks or authentication, you can use HTTPS to have a secure environment on localhost. Next.js can generate a self-signed certificate with next dev using the --experimental-https flag:

>_Terminal
next dev --experimental-https

생성된 certificate를 사용하면 Next.js development server는 https://localhost:3000에서 실행됩니다. -p, --port, 또는 PORT로 port를 지정하지 않으면 기본 port 3000이 사용됩니다.

With the generated certificate, the Next.js development server will exist at https://localhost:3000. The default port 3000 is used unless a port is specified with -p, --port, or PORT.

--experimental-https-key와 --experimental-https-cert로 custom certificate와 key를 제공할 수도 있습니다. 선택적으로 --experimental-https-ca로 custom CA certificate도 제공할 수 있습니다.

You can also provide a custom certificate and key with --experimental-https-key and --experimental-https-cert. Optionally, you can provide a custom CA certificate with --experimental-https-ca as well.

>_Terminal
next dev --experimental-https --experimental-https-key ./certificates/localhost-key.pem --experimental-https-cert ./certificates/localhost.pem

next dev --experimental-https는 development 용도로만 만들어졌으며, mkcert로 로컬에서 신뢰되는 certificate를 생성합니다. production에서는 신뢰할 수 있는 기관에서 정식으로 발급한 certificate를 사용하세요.

next dev --experimental-https is only intended for development and creates a locally trusted certificate with mkcert. In production, use properly issued certificates from trusted authorities.

Configuring a timeout for downstream proxiesdownstream proxy를 위한 timeout 설정하기

downstream proxy(예: AWS ELB/ALB 같은 load-balancer) 뒤에 Next.js를 deploy할 때는, Next의 내부 HTTP server에 downstream proxy의 timeout보다 더 큰 keep-alive timeout을 설정하는 것이 중요합니다. 그렇지 않으면 특정 TCP connection에서 keep-alive timeout에 도달했을 때 Node.js가 downstream proxy에 알리지 않고 즉시 그 connection을 종료합니다. 그 결과 proxy가 Node.js에서 이미 종료한 connection을 재사용하려고 할 때마다 proxy error가 발생합니다.

When deploying Next.js behind a downstream proxy (e.g. a load-balancer like AWS ELB/ALB), it's important to configure Next's underlying HTTP server with keep-alive timeouts that are larger than the downstream proxy's timeouts. Otherwise, once a keep-alive timeout is reached for a given TCP connection, Node.js will immediately terminate that connection without notifying the downstream proxy. This results in a proxy error whenever it attempts to reuse a connection that Node.js has already terminated.

production Next.js server의 timeout 값을 설정하려면 다음과 같이 next start에 --keepAliveTimeout(millisecond 단위)을 전달하세요:

To configure the timeout values for the production Next.js server, pass --keepAliveTimeout (in milliseconds) to next start, like so:

>_Terminal
next start --keepAliveTimeout 70000

CPU profiling

CPU profile을 capture해 Next.js 애플리케이션의 performance bottleneck을 분석할 수 있습니다. --experimental-cpu-prof flag는 V8에 내장된 CPU profiler를 활성화하고, process가 종료될 때 profile을 .next-profiles/에 저장합니다:

You can capture CPU profiles to analyze performance bottlenecks in your Next.js application. The --experimental-cpu-prof flag enables V8's built-in CPU profiler and saves profiles to .next-profiles/ when the process exits:

>_Terminal
# Profile the build process
next build --experimental-cpu-prof

# Profile the dev server (profile saved on Ctrl+C or SIGTERM)
next dev --experimental-cpu-prof

# Profile the production server
next start --experimental-cpu-prof

생성된 .cpuprofile 파일은 Chrome DevTools(Performance tab → Load profile)나 다른 V8 호환 profiling 도구에서 열 수 있습니다.

The generated .cpuprofile files can be opened in Chrome DevTools (Performance tab → Load profile) or other V8-compatible profiling tools.

Good to know

profile 파일 이름에는 설명적인 prefix와 timestamp가 붙습니다. 생성되는 profile은 command에 따라 다릅니다:

next dev:

  • dev-main-* - 부모 process (dev server orchestration)
  • dev-server-* - 자식 server process (request 처리와 rendering) - 보통 분석하고 싶은 것은 이것입니다

next build (Turbopack):

  • build-main-* - 메인 build orchestration process
  • build-turbopack-* - Turbopack compilation worker

next build (Webpack):

  • build-main-* - 메인 build orchestration process
  • build-webpack-client-* - Client bundle compilation worker
  • build-webpack-server-* - Server bundle compilation worker
  • build-webpack-edge-server-* - Edge runtime compilation worker

next start:

  • start-main-* - Production server process

Profile files are named with a descriptive prefix and timestamp. The profiles generated depend on the command:

next dev:

  • dev-main-* - Parent process (dev server orchestration)
  • dev-server-* - Child server process (request handling and rendering) - this is typically what you want to analyze

next build (Turbopack):

  • build-main-* - Main build orchestration process
  • build-turbopack-* - Turbopack compilation worker

next build (Webpack):

  • build-main-* - Main build orchestration process
  • build-webpack-client-* - Client bundle compilation worker
  • build-webpack-server-* - Server bundle compilation worker
  • build-webpack-edge-server-* - Edge runtime compilation worker

next start:

  • start-main-* - Production server process
