Implementing Partial Prerendering on your platform플랫폼에서 Partial Prerendering 구현하기

Partial Prerendering(PPR)은 하나의 route에서 static rendering과 dynamic rendering을 결합합니다. build 시점에 Next.js는 PPR이 활성화된 각 route에 대해 static HTML shell과 postponedState blob을 생성합니다. request 시점에는 shell이 즉시 제공되고, dynamic 부분이 render되어 client로 stream됩니다.

Partial Prerendering (PPR) combines static and dynamic rendering in a single route. At build time, Next.js generates a static HTML shell and a postponedState blob for each PPR-enabled route. At request time, the shell is served immediately and dynamic portions are rendered and streamed to the client.

이 페이지에서는 플랫폼이 다양한 수준의 정교함으로 PPR 지원을 구현하는 방법을 설명합니다.

This page explains how platforms can implement PPR support at different levels of sophistication.

How PPR WorksPPR의 동작 방식

Build timebuild 시점

각 PPR route에 대해 Next.js는 다음을 만들어 냅니다:

For each PPR route, Next.js produces:

  • prerender할 수 있는 모든 콘텐츠를 담고, dynamic 콘텐츠가 나타날 자리에는 Suspense fallback을 둔 static HTML shell.
  • postponedState 값: serialize된 문자열입니다. 이 값은 불투명한(opaque) 값으로 취급하세요. 즉, parse하거나 수정하지 말고 그대로 전달해야 합니다. postponedState를 변경하면 잘못된 dynamic rendering output이 만들어집니다.
  • page의 static 부분에 대한 RSC payload.
  • A static HTML shell containing all the content that can be prerendered, with Suspense fallbacks where dynamic content will appear.
  • A postponedState value: a serialized string. Treat it as opaque: pass it through without parsing or modifying it. Altering postponedState produces incorrect dynamic rendering output.
  • An RSC payload for the static portions of the page.

Request timerequest 시점

PPR route로 request가 도착하면:

When a request arrives for a PPR route:

  1. server가 static HTML shell을 client에 즉시 보냅니다.
  2. server가 postponed state를 사용해 dynamic 부분의 rendering을 재개(resume)합니다.
  3. dynamic 콘텐츠가 client로 stream되어, React가 미뤄 두었던 Suspense boundary를 hydrate할 수 있게 됩니다.
  1. The server sends the static HTML shell to the client immediately.
  2. The server resumes rendering the dynamic portions using the postponed state.
  3. Dynamic content is streamed to the client, allowing React to hydrate the deferred Suspense boundaries.

client는 static shell을 즉시 보게 되고, 이후 dynamic 콘텐츠가 resolve되는 대로 나타납니다.

The client sees the static shell instantly, then dynamic content appears as it resolves.

Storing PPR ArtifactsPPR artifact 저장하기

각 PPR route에는 함께 저장해야 하는 artifact 두 개가 필요합니다:

Each PPR route requires two artifacts to be stored together:

  1. static HTML shell.
  2. postponedState blob.
  1. The static HTML shell.
  2. The postponedState blob.

이 둘은 atomic하게 저장되고 업데이트되어야 합니다. PPR route가 revalidate되면(time-based 또는 on-demand revalidation을 통해), Next.js는 shell과 postponed state를 함께 다시 생성합니다. 새 shell을 예전 postponed state와 함께 제공하거나 그 반대로 하면 잘못된 dynamic 콘텐츠가 만들어집니다.

These must be stored and updated atomically. When a PPR route is revalidated (via time-based or on-demand revalidation), Next.js regenerates both the shell and the postponed state together. Serving a new shell with an old postponed state, or vice versa, will produce incorrect dynamic content.

adapter에서 requestMeta.onCacheEntryV2를 사용해 cache 업데이트를 관찰하고 storage backend에 전파하세요.

Use requestMeta.onCacheEntryV2 in your adapter to observe cache updates and propagate them to your storage backend.

Origin-Only ImplementationOrigin 전용 구현

가장 단순한 방식이며, streaming HTTP response를 지원하는 모든 플랫폼에서 동작합니다.

This is the simplest approach and works on every platform that supports streaming HTTP responses.

모든 request가 Next.js server로 직접 갑니다. server는 local cache에서 shell을 읽어 보낸 다음, dynamic 콘텐츠를 render해서 stream합니다. next start가 기본적으로 하는 일이 바로 이것입니다.

All requests go directly to the Next.js server. The server reads the shell from its local cache, sends it, then renders and streams the dynamic content. This is what next start does by default.

추가 인프라는 필요하지 않습니다. 플랫폼이 streaming HTTP response를 지원한다면 PPR도 지원하는 것입니다.

No additional infrastructure is needed. If your platform supports streaming HTTP responses, it supports PPR.

CDN Shell + Origin Compute

더 나은 TTFB를 위해 static HTML shell을 CDN edge에 cache할 수 있습니다. request가 도착하면:

For better TTFB, the static HTML shell can be cached at the CDN edge. When a request arrives:

  1. CDN이 cache된 shell을 즉시 제공합니다(edge latency).
  2. CDN이 origin server에 resume request를 보냅니다(가능하면 shell streaming과 병렬로).
  3. origin server는 dynamic 부분만 render해서 stream으로 돌려보냅니다.
  4. CDN이 shell과 dynamic 콘텐츠를 이어 붙여 client에 하나의 streaming response로 보냅니다.
  1. The CDN serves the cached shell immediately (edge latency).
  2. The CDN sends a resume request to the origin server (ideally in parallel with streaming the shell).
  3. The origin server renders only the dynamic portions and streams them back.
  4. The CDN concatenates the shell and dynamic content into a single streaming response to the client.

이를 위해서는 CDN이 cache된 콘텐츠와 dynamic 콘텐츠를 하나의 streaming response로 합치는 메커니즘을 지원해야 합니다. static shell의 TTFB는 edge latency 수준으로 줄어들고, dynamic 콘텐츠는 여전히 origin에서 stream됩니다.

This requires the CDN to support a mechanism for combining cached and dynamic content in a single streaming response. The static shell TTFB drops to edge latency while dynamic content still streams from origin.

latency를 최대한 낮추려면, CDN cache 대신 edge storage(예: onBuildComplete 중에 채워 둔 KV store)에서 shell을 제공할 수 있습니다. 이는 플랫폼 아키텍처 차원의 결정이며 Next.js 애플리케이션을 변경할 필요는 없습니다.

For the lowest possible latency, the shell can be served from edge storage (for example, a KV store populated during onBuildComplete) rather than from a CDN cache. This is a platform architecture decision and does not require any changes to the Next.js application.

The Resume ProtocolResume Protocol

resume protocol은 Next.js handler에게 shell은 건너뛰고 dynamic 부분만 render하라고 알려 줍니다. CDN-to-origin 아키텍처와 shell을 별도로 제공하는 adapter 기반 deployment에서 사용됩니다.

The resume protocol tells the Next.js handler to skip the shell and render only the dynamic portions. It is used by CDN-to-origin architectures and adapter-based deployments that serve the shell separately.

표준 next start에서는 server가 shell과 dynamic render를 한 번에 자동으로 처리합니다.

In standard next start, the server handles both the shell and dynamic render in a single pass automatically.

CDN-to-origin

CDN이 별도의 Next.js origin에 HTTP request를 보낼 때:

When the CDN makes an HTTP request to a separate Next.js origin:

  • next-resume: 1 header와 함께 route에 POST request를 보냅니다.
  • postponedState blob을 request body로 포함합니다.
  • server는 미뤄 두었던 Suspense boundary만 render하고 그 결과를 stream합니다.
  • Send a POST request to the route with the header next-resume: 1.
  • Include the postponedState blob as the request body.
  • The server will render only the deferred Suspense boundaries and stream the result.
Good to know

POST request가 Server Action과 PPR resume을 결합하는 경우, request body에는 postponed state 뒤에 action body가 이어서 들어갑니다. x-next-resume-state-length header가 postponed state prefix의 byte 길이를 담고 있어서 handler가 둘을 분리할 수 있습니다. 순수한 PPR resume(일반적인 경우)에서는 request body 전체가 postponed state이므로 이 header가 필요하지 않습니다.

When a POST request combines a Server Action with a PPR resume, the request body contains the postponed state followed by the action body. The x-next-resume-state-length header carries the byte length of the postponed state prefix so the handler can separate the two. For a pure PPR resume (the common case), the entire request body is the postponed state and this header is not needed.

Adapter-basedAdapter 기반

플랫폼이 handler 함수를 직접 호출할 때:

When the platform invokes the handler function directly:

  • req.method를 'POST'로 설정하고, request에 next-resume: 1 header를 넣고, postponedState를 request body로 하여 entrypoint handler를 호출합니다. (handler 호출의 세 번째 argument로 requestMeta: { postponed: postponedState }를 전달할 수도 있는데, 이는 동일하게 동작하지만 HTTP layer를 완전히 우회합니다.)
  • handler는 미뤄 두었던 Suspense boundary만 render하고 그 결과를 res로 stream합니다.
  • HTTP round-trip이 필요하지 않습니다. handler가 in-process로 호출되기 때문입니다.
  • Call the entrypoint handler with req.method set to 'POST', the next-resume: 1 header on the request, and the postponedState as the request body. (You can also pass requestMeta: { postponed: postponedState } as the third argument to the handler invocation, which is equivalent but bypasses the HTTP layer entirely.)
  • The handler renders only the deferred Suspense boundaries and streams the result to res.
  • No HTTP round-trip is needed: the handler is invoked in-process.

Finding PPR routes in build outputbuild output에서 PPR route 찾기

adapter output에서 PPR route는 prerenders 배열 안의 renderingMode: 'PARTIALLY_STATIC'으로 식별됩니다. outputs.prerenders를 순회하며 이런 entry를 찾고 fallback.postponedState를 읽으세요.

In the adapter output, PPR routes are identified by renderingMode: 'PARTIALLY_STATIC' in the prerenders array. Iterate outputs.prerenders to find these entries and read fallback.postponedState.

pprChain.headers에는 resume protocol에 필요한 header인 { 'next-resume': '1' }가 들어 있습니다.

pprChain.headers contains the headers needed for the resume protocol: { 'next-resume': '1' }.

코드 예제가 포함된 자세한 구현은 Implementing PPR in an Adapter를 참고하세요.

For detailed implementation with code examples, see Implementing PPR in an Adapter.

Implementation Checklist구현 체크리스트

  1. build 시점에 PPR output을 읽으세요. adapter의 onBuildComplete에서 renderingMode: 'PARTIALLY_STATIC'인 prerender를 식별합니다. shell HTML과 postponedState를 cache에 저장합니다.
  2. request 시점에 shell을 제공하세요. PPR route로 들어오는 request에 대해 cache된 shell을 즉시 제공하고 streaming을 시작합니다.
  3. dynamic rendering을 재개하세요. CDN-to-origin의 경우: next-resume: 1 header와 postponed state를 body로 하여 Next.js handler에 POST request를 보냅니다. adapter 기반의 경우: POST method와 request body의 postponed state로 handler를 직접 호출합니다(또는 handler에 requestMeta: { postponed: postponedState }를 전달합니다). response를 client로 stream합니다.
  4. cache 업데이트를 처리하세요. requestMeta.onCacheEntryV2를 사용해 revalidation 이후의 새 shell + postponed state 쌍을 포착하고, cache를 atomic하게 업데이트합니다.
  5. graceful degradation을 지원하세요. postponed state를 사용할 수 없거나 stale하다면 전체 server render로 fallback합니다. 사용자는 shell-first 최적화 없이 완전한 page를 받게 됩니다.
  1. Read PPR outputs at build time. In your adapter's onBuildComplete, identify prerenders with renderingMode: 'PARTIALLY_STATIC'. Store the shell HTML and postponedState in your cache.
  2. Serve the shell at request time. For incoming requests to PPR routes, serve the cached shell immediately and begin streaming.
  3. Resume dynamic rendering. For CDN-to-origin: send a POST request to the Next.js handler with the next-resume: 1 header and the postponed state as the body. For adapter-based: call the handler directly with POST method and the postponed state in the request body (or pass requestMeta: { postponed: postponedState } to the handler). Stream the response back to the client.
  4. Handle cache updates. Use requestMeta.onCacheEntryV2 to capture new shell + postponed state pairs after revalidation, and update your cache atomically.
  5. Support graceful degradation. If the postponed state is unavailable or stale, fall back to a full server render. The user gets a complete page without the shell-first optimization.

전체 adapter API reference와 구현 예제는 Deployment Adapter API를 참고하세요.

For the complete adapter API reference and implementation examples, see the Deployment Adapter API.
