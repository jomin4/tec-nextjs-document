Streaming스트리밍

What is streaming?streaming이란?

전통적인 server-side rendering에서는 server가 아무것도 보내기 전에 전체 HTML 문서를 만들어 냅니다. 느린 database query나 API 호출 하나가 페이지 전체를 막을 수 있습니다. Streaming은 chunked transfer encoding을 사용해 response의 각 부분을 준비되는 대로 보내는 방식으로 이를 바꿉니다. server가 나머지를 아직 생성하는 동안에도 브라우저는 HTML rendering을 시작합니다.

In traditional server-side rendering, the server produces the full HTML document before sending anything. A single slow database query or API call can block the entire page. Streaming changes this by using chunked transfer encoding to send parts of the response as they become ready. The browser starts rendering HTML while the server is still generating the rest.

이는 빠른 static 콘텐츠(header, navigation, layout)와 느린 dynamic 콘텐츠(개인화된 데이터, analytics, 추천)를 함께 담은 페이지에서 특히 효과가 큽니다. static 부분은 prerender되어 CDN에서 제공되므로 즉시 화면에 그려지고, dynamic 부분은 준비되는 대로 server에서 stream되어 들어옵니다.

This is especially impactful for pages that combine fast static content (headers, navigation, layout) with slower dynamic content (personalized data, analytics, recommendations). The static parts can be prerendered and served from a CDN, painting instantly, while the dynamic parts stream in from the server as they become ready.

React의 server renderer는 <Suspense> boundary에 맞춰 HTML을 chunk 단위로 만들어 냅니다. Next.js는 이를 App Router에 통합해 두었기 때문에 추가 설정 없이 streaming이 동작합니다.

React's server renderer produces HTML in chunks aligned with <Suspense> boundaries. Next.js integrates this into the App Router so streaming works without additional configuration.

How the App Router delivers a pageApp Router가 페이지를 전달하는 방식

브라우저가 페이지를 request하면, 초기 페이지 로드 중에 두 개의 stream이 함께 동작합니다:

When a browser requests a page, two streams work together during the initial page load:

The HTML streamHTML stream

React의 server renderer는 점진적인 HTML chunk를 만들어 냅니다. 페이지의 static 부분(layout, navigation, Suspense fallback)이 먼저 render되어 즉시 전송됩니다. <Suspense> boundary의 콘텐츠가 준비되면, 예를 들어 async Server Component가 resolve되면, React는 완성된 HTML을 inline <script> tag와 함께 stream합니다. 하나는 fallback DOM node를 새 콘텐츠로 교체하는 script이고, 다른 하나는 React가 나중에 hydrate할 수 있도록 component payload를 담은 script입니다. 브라우저는 페이지의 JavaScript bundle이 로드되거나 hydration이 끝나기를 기다리지 않고 교체를 즉시 실행합니다. 이것이 사용자가 보는 것, 즉 섹션별로 점진적으로 그려지는 페이지입니다.

React's server renderer produces progressive HTML chunks. The static parts of your page (layouts, navigation, Suspense fallbacks) render first and are sent immediately. When a <Suspense> boundary's content is ready, for example when an async Server Component resolves, React streams its completed HTML along with inline <script> tags: one that swaps the fallback DOM node with the new content, and another carrying the component payload so React can later hydrate it. The browser executes the swap instantly, without waiting for the page's JavaScript bundle to load or hydration to complete. This is what the user sees: the page painting progressively, section by section.

The component payloadcomponent payload

component payload는 React가 페이지를 hydrate하고 client-side 업데이트를 처리하는 데 사용하는, component tree의 직렬화된 표현입니다. 초기 로드 때는 (위에서 설명한 것처럼) HTML stream 안에 포함되어 도착합니다. client-side navigation 때는 component payload만 (rsc: 1 request header와 함께) fetch되고 HTML은 전혀 전송되지 않습니다. React는 이를 사용해 component tree를 그 자리에서 업데이트합니다.

The component payload is a serialized representation of the component tree that React uses to hydrate the page and handle client-side updates. On initial load, it arrives embedded in the HTML stream (as described above). On client-side navigation, only the component payload is fetched (with an rsc: 1 request header) and no HTML is transferred at all. React uses it to update the component tree in place.

The static shellstatic shell

async 작업이 resolve되기 전에 render되는 모든 것을 static shell이라고 합니다. layout, navigation, 그리고 <Suspense> boundary에 정의한 fallback UI가 여기에 해당합니다. static shell은 즉시 전송되어, dynamic 콘텐츠가 stream되는 동안 사용자가 보고 상호작용할 수 있는 것을 제공합니다. Cache Components를 사용하면 static shell은 build time에 prerender되어 edge에서 즉시 제공됩니다.

Everything that renders before any async work resolves is called the static shell: your layouts, navigation, and the fallback UI defined by your <Suspense> boundaries. It is sent immediately, giving the user something to see and interact with while dynamic content streams in. With Cache Components, the static shell is prerendered at build time and served instantly from the edge.

각 <Suspense> boundary는 독립적인 streaming 지점입니다. 서로 다른 boundary 안의 component는 각자 독립적으로 resolve되고 stream됩니다. 서로를 막지 않습니다.

Each <Suspense> boundary is an independent streaming point. Components inside different boundaries resolve and stream in independently. They don't block each other.

Page-level streaming with loading.jsloading.js로 page 단위 streaming

streaming을 추가하는 가장 간단한 방법은 loading.js 파일을 사용하는 것입니다. 이 파일을 page.js 옆에 두면 Next.js가 자동으로 page 콘텐츠를 <Suspense> boundary로 감싸고, loading component를 fallback으로 사용합니다.

The simplest way to add streaming is with a loading.js file. Place it alongside your page.js and Next.js automatically wraps the page content in a <Suspense> boundary, using your loading component as the fallback.

TSJSapp/dashboard/loading.tsx
export default function Loading() {
  return (
    <div className="animate-pulse">
      <div className="h-8 w-48 bg-gray-200 rounded mb-4" />
      <div className="h-4 w-full bg-gray-200 rounded mb-2" />
      <div className="h-4 w-full bg-gray-200 rounded mb-2" />
      <div className="h-4 w-2/3 bg-gray-200 rounded" />
    </div>
  )
}

This means:

  • layout은 static shell의 일부로 즉시 render됩니다.
  • loading skeleton은 Suspense fallback으로 즉시 표시됩니다.
  • page component가 로딩을 마치면 그 HTML이 skeleton을 대체합니다.
  • The layout renders immediately as part of the static shell.
  • The loading skeleton is shown instantly as the Suspense fallback.
  • When the page component finishes loading, its HTML replaces the skeleton.

loading.js는 page의 데이터가 resolve되기 전까지 의미 있게 보여 줄 것이 없을 때 유용합니다. page가 무언가를 render하기 전에 데이터를 await해야 한다면, 전체 페이지 skeleton은 합리적인 fallback입니다.

loading.js is useful when there's nothing meaningful to show until the page's data resolves. If the page needs to await data before it can render anything, a full-page skeleton is a reasonable fallback.

Granular streaming with <Suspense><Suspense>로 세분화된 streaming

<Suspense>를 사용하면 페이지의 어떤 부분을 독립적으로 stream할지 정확히 제어할 수 있습니다. 전체 페이지 skeleton 대신 fallback을 특정 섹션으로 내려보내서, static shell에 실제 콘텐츠가 더 많이 포함되게 할 수 있습니다.

<Suspense> lets you control exactly which parts of the page stream independently. Instead of a full-page skeleton, you can push fallbacks down into specific sections so the static shell includes more real content.

Parallel streaming with sibling boundaries형제 boundary로 병렬 streaming

여러 component가 async 작업(데이터 fetch, database 읽기)을 수행한다면 각각을 별도의 <Suspense> boundary로 감싸세요. 각 boundary는 async 작업이 끝나는 대로, 어떤 순서로 끝나든, 서로를 막지 않고 독립적으로 stream됩니다:

When multiple components perform async work (fetching data, reading from a database), wrap each one in its own <Suspense> boundary. Each boundary streams independently as its async work completes, in whatever order that happens, without blocking each other:

TSJSapp/dashboard/page.tsx
import { Suspense } from 'react'
import { Revenue } from './revenue'
import { RecentOrders } from './recent-orders'
import { Recommendations } from './recommendations'

export default function Dashboard() {
  return (
    <div>
      <h1>Dashboard</h1>
      <div className="grid grid-cols-2 gap-4">
        <Suspense fallback={<p>Loading revenue...</p>}>
          <Revenue />
        </Suspense>
        <Suspense fallback={<p>Loading orders...</p>}>
          <RecentOrders />
        </Suspense>
      </div>
      <Suspense fallback={<p>Loading recommendations...</p>}>
        <Recommendations />
      </Suspense>
    </div>
  )
}
import { Suspense } from 'react'
import { Revenue } from './revenue'
import { RecentOrders } from './recent-orders'
import { Recommendations } from './recommendations'

export default function Dashboard() {
  return (

}

이 예제에서 Revenue가 200ms, RecentOrders가 1s, Recommendations가 3s에 resolve된다면, 사용자는 각 섹션의 데이터가 준비되는 즉시 그 섹션이 나타나는 것을 보게 됩니다.

In this example, if Revenue resolves in 200ms, RecentOrders in 1s, and Recommendations in 3s, the user sees each section appear as soon as its data is ready.

Nested boundaries for progressive detail점진적 디테일을 위한 중첩 boundary

<Suspense> boundary를 중첩해 단계적인 로딩 경험을 만들 수 있습니다. 예를 들어 상품 페이지는 header를 즉시, 그다음 상품 상세 정보를, 마지막으로 리뷰를 stream할 수 있습니다:

You can nest <Suspense> boundaries to create a layered loading experience. For example, a product page might stream the header immediately, the product details next, and the reviews last:

TSJSapp/product/[id]/page.tsx
import { Suspense } from 'react'
import { ProductDetails } from './product-details'
import { Reviews } from './reviews'

export async function generateStaticParams() {
  const products = await getTopProducts()
  return products.map((product) => ({ id: product.id }))
}

export default async function ProductPage({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params

  return (
    <div>
      <h1>Product</h1>
      <Suspense fallback={<p>Loading product details...</p>}>
        <ProductDetails id={id} />
        <Suspense fallback={<p>Loading reviews...</p>}>
          <Reviews productId={id} />
        </Suspense>
      </Suspense>
    </div>
  )
}
import { Suspense } from 'react'
import { ProductDetails } from './product-details'
import { Reviews } from './reviews'

export async function generateStaticParams() {
  const products = await getTopProducts()
  return products.map((product) => ({ id: product.id }))
}

export default async function ProductPage({ params }) {
  const { id } = await params

  return (
    <div>
      <h1>Product</h1>
      <Suspense fallback={<p>Loading product details...</p>}>
        <ProductDetails id={id} />
        <Suspense fallback={<p>Loading reviews...</p>}>
          <Reviews productId={id} />
        </Suspense>
      </Suspense>
    </div>
  )
}

바깥 boundary는 ProductDetails가 resolve될 때까지 "Loading product details..."를 보여 줍니다. resolve되면 안쪽 boundary가 보이게 되어, Reviews가 resolve될 때까지 "Loading reviews..."를 보여 줍니다. 이렇게 점진적으로 드러나는 화면이 만들어집니다.

The outer boundary shows "Loading product details..." until ProductDetails resolves. Once it does, the inner boundary becomes visible, showing "Loading reviews..." until Reviews resolves. This creates a progressive reveal.

Push dynamic access downdynamic 접근을 아래로 내리기

즉시 stream되는 부분을 최대화하는 핵심은 dynamic 데이터 접근을 실제로 그것이 필요한 component까지 미루는 것입니다. 이는 params, searchParams, cookies(), headers(), 그리고 데이터 fetch에 적용됩니다. layout이나 page 맨 위에서 이들 중 하나라도 await하면, 그 지점 아래의 모든 것이 dynamic이 되어 static shell의 일부로 prerender될 수 없습니다.

The key to maximizing what streams instantly is to defer dynamic data access to the component that actually needs it. This applies to params, searchParams, cookies(), headers(), and data fetches. If you await any of these at the top of a layout or page, everything below that point becomes dynamic and cannot be prerendered as part of the static shell.

대신 promise를 아래로 전달하고, 이를 사용하는 component가 <Suspense> boundary 안에서 resolve하도록 하세요:

Instead, pass the promise down and let the consuming component resolve it inside a <Suspense> boundary:

TSJSapp/dashboard/layout.tsx
import { Suspense } from 'react'
import { Nav } from './nav'
import { UserMenu } from './user-menu'
import { cookies } from 'next/headers'

export default function DashboardLayout({
  children,
}: {
  children: React.ReactNode
}) {
  const cookieStore = cookies() // Start the work, but don't await

  return (
    <div>
      <Nav>
        <Suspense fallback={<p>Loading user...</p>}>
          <UserMenu cookiePromise={cookieStore} />
        </Suspense>
      </Nav>
      {children}
    </div>
  )
}
import { Suspense } from 'react'
import { Nav } from './nav'
import { UserMenu } from './user-menu'
import { cookies } from 'next/headers'

export default function DashboardLayout({ children }) {
  const cookieStore = cookies() // Start the work, but don't await

  return (
    <div>
      <Nav>
        <Suspense fallback={<p>Loading user...</p>}>
          <UserMenu cookiePromise={cookieStore} />
        </Suspense>
      </Nav>
      {children}
    </div>
  )
}

이 예제에서 <Nav>와 {children}은 layout에서 아무것도 await하지 않으므로 static shell의 일부로 render됩니다. cookie promise를 resolve할 때 <UserMenu>만 suspend됩니다. 만약 layout 맨 위에서 await cookies()를 호출했다면, layout 전체와 그 모든 children이 prerender되지 못하고 막혔을 것입니다.

In this example, <Nav> and {children} render as part of the static shell because nothing in the layout awaits. Only <UserMenu> suspends when it resolves the cookie promise. If the layout had called await cookies() at the top instead, the entire layout and all its children would be blocked from prerendering.

같은 원칙이 params와 searchParams에도 적용됩니다. page 수준에서 destructuring하는 대신, 값이 필요한 component에 promise를 전달하세요:

The same principle applies to params and searchParams. Rather than destructuring them at the page level, pass the promise to the component that needs the value:

TSJSapp/shop/[category]/page.tsx
import { Suspense } from 'react'
import { Hero } from './hero'
import { ProductGrid } from './product-grid'

export async function generateStaticParams() {
  const categories = await getCategories()
  return categories.map((c) => ({ category: c.slug }))
}

export default function ShopPage({
  params,
}: {
  params: Promise<{ category: string }>
}) {
  return (
    <div>
      <Hero />
      <Suspense fallback={<p>Loading products...</p>}>
        <ProductGrid paramsPromise={params} />
      </Suspense>
    </div>
  )
}

import { Hero } from './hero'
import { ProductGrid } from './product-grid'

  return categories.map((c) => ({ category: c.slug }))

<Hero />는 static shell의 일부로 그려집니다. <ProductGrid>는 category가 필요할 때 params를 resolve하며, 자신의 boundary 안에서만 suspend됩니다.

<Hero /> paints as part of the static shell. <ProductGrid> resolves params when it needs the category, suspending only within its boundary.

.then()으로 promise를 inline으로 풀어서, child component가 promise 대신 일반 값을 받게 할 수도 있습니다:

You can also unwrap the promise inline with .then(), so the child component receives a plain value instead of a promise:

TSJSapp/shop/[category]/page.tsx
<Suspense fallback={<p>Loading products...</p>}>
  {params.then(({ category }) => (
    <ProductGrid category={category} />
  ))}
</Suspense>
<Suspense fallback={<p>Loading products...</p>}>
  {params.then(({ category }) => (
    <ProductGrid category={category} />
  ))}
</Suspense>

이렇게 하면 ProductGrid를 단순하게 유지하면서(Promise가 아니라 string을 받음) params 접근은 여전히 Suspense boundary 안으로 미룰 수 있습니다.

This keeps ProductGrid simple (it takes a string, not a Promise) while still deferring the params access to inside the Suspense boundary.

dynamic 접근 가까이에 명시적인 <Suspense> boundary를 두는 것을 선호하세요. prerenderer는 dynamic 작업을 만나면 tree를 거슬러 올라가며 가장 가까운 Suspense boundary를 찾습니다. 아무것도 찾지 못하면 build가 blocking route error로 실패합니다. tree 위쪽에 있는 loading.js도 유효한 boundary이므로 framework는 그것을 찾고 멈추지만, 그러면 페이지 전체가 세분화된 streaming 대신 전체 페이지 skeleton으로 fallback됩니다.

Prefer explicit <Suspense> boundaries close to the dynamic access. When the prerenderer encounters dynamic work, it walks up the tree looking for the nearest Suspense boundary. If none is found, the build fails with a blocking route error. A loading.js high in the tree is a valid boundary, so the framework finds it and stops, but now the entire page falls back to a full-page skeleton instead of streaming granularly.

Error handling mid-streamstream 도중 error 처리

streaming이 시작된 뒤 component가 error를 throw하면, 가장 가까운 error.js boundary가 이를 잡아서 실패한 component 자리에 error UI를 render합니다. 페이지의 나머지는 그대로 유지되고, error가 난 섹션만 교체됩니다.

If a component throws an error after streaming has started, the nearest error.js boundary catches it and renders the error UI in place of the failed component. The rest of the page remains intact, only the section that errored is replaced.

HTTP status code(200 OK)는 첫 chunk와 함께 이미 전송되었으므로 4xx나 5xx로 바꿀 수 없습니다. error는 전적으로 stream된 HTML 안에서 처리됩니다. 이 제약에 대한 자세한 내용은 The HTTP contract를 참고하세요.

Because the HTTP status code (200 OK) has already been sent with the first chunk, it cannot be changed to a 4xx or 5xx. The error is handled entirely within the streamed HTML. See The HTTP contract for more on this constraint.

Streaming data to the clientclient로 데이터 streaming하기

Server Component에서 fetch를 시작하고, 아직 resolve되지 않은 promise를 Client Component에 prop으로 전달할 수 있습니다. promise는 필요한 만큼 여러 계층을 거쳐 전달할 수 있습니다. React의 use API를 호출해 값을 읽는 component만 <Suspense> boundary로 감싸면 됩니다:

You can start a fetch in a Server Component and pass the unresolved promise as a prop to a Client Component. The promise can be passed through as many layers as needed. Only the component that calls React's use API to read the value needs a <Suspense> boundary around it:

    </Suspense>
  )
}

Streaming in Route HandlersRoute Handler에서 streaming

위의 pattern들은 UI를 stream하기 위해 React와 Suspense에 의존합니다. React rendering 밖에서는 Route Handler가 Web Streams API를 사용해 raw response를 stream할 수 있습니다. 이는 Server-Sent Events, 대용량 파일 생성, 또는 데이터가 점진적으로 도착하길 원하는 모든 response에 유용합니다:

The patterns above rely on React and Suspense to stream UI. Outside of React rendering, Route Handlers can stream raw responses using the Web Streams API. This is useful for Server-Sent Events, large file generation, or any response where you want data to arrive progressively:

TSJSapp/api/stream/route.ts
export async function GET() {
  const encoder = new TextEncoder()

  const stream = new ReadableStream({
    async start(controller) {
      for (let i = 0; i < 10; i++) {
        controller.enqueue(encoder.encode(`Chunk ${i + 1}\n`))
        await new Promise((resolve) => setTimeout(resolve, 200))
      }
      controller.close()
    },
  })

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/plain; charset=utf-8',
      'X-Content-Type-Options': 'nosniff',
    },
  })
}

Streaming and Web VitalsStreaming과 Web Vitals

Web Vitals는 Google이 사용자 경험을 측정하는 데 사용하는 지표입니다. Streaming은 그중 여러 지표에 직접적인 영향을 줍니다.

Web Vitals are the metrics Google uses to measure user experience. Streaming directly affects several of them.

TTFB and FCPTTFB와 FCP

streaming이 없으면 server는 HTML을 보내기 전에 모든 데이터를 기다리므로, TTFB는 가장 느린 query와 같아집니다. streaming을 사용하면 server는 static shell이 준비되자마자 보냅니다. TTFB는 layout과 fallback을 render하는 데 걸리는 시간으로 줄어듭니다. 브라우저는 static shell을 즉시 그리므로, FCP는 데이터 fetching 시간과 분리됩니다.

Without streaming, the server waits for all data before sending any HTML, so TTFB equals the slowest query. With streaming, the server sends the static shell as soon as it's ready. TTFB drops to the time it takes to render your layouts and fallbacks. The browser paints the static shell immediately, so FCP is decoupled from your data fetching time.

LCP (Largest Contentful Paint)

LCP element(hero 이미지, 메인 제목, 상품 사진)가 Suspense boundary 안에 있다면, 그 boundary의 콘텐츠가 교체되어 들어오기 전까지는 그려질 수 없습니다. 그러면 그 element는 초기 server response 시간이 아니라 server가 그것을 render하기 위해 하는 작업에 의존하게 됩니다. 이를 드러내는 데에는 client 쪽 비용도 듭니다. React가 boundary의 HTML과 함께 작은 inline script를 stream하고, 콘텐츠는 그 script가 실행된 뒤에야 나타나기 때문입니다.

If your LCP element (a hero image, a main heading, a product photo) is inside a Suspense boundary, it can't paint until that boundary's content is swapped in. The element then depends on the work the server does to render it, not on your initial server response time. Revealing it costs something on the client too, because React streams a small inline script alongside the boundary's HTML and the content only appears once that script runs.

boundary가 LCP element를 지연시키는 이유는 데이터 fetching만이 아닙니다. React는 큰 boundary도 잠시 보류하는데, 그 HTML을 보내는 데 시간이 걸리기 때문입니다. Suspense boundary를 활성화하는 요인을 참고하세요.

Data fetching is not the only reason a boundary delays your LCP element. React also holds back a large boundary, because sending its HTML takes time. See what activates a Suspense boundary.

Good to know

경험상, Suspense boundary가 있다면 React는 그것을 사용할 수 있습니다. 네트워크가 느리거나 CPU가 바쁘면 concurrent rendering이 예상하지 못한 상황에서도 그 boundary로 fallback할 수 있습니다. boundary를 추가한다는 것은 이를 받아들인다는 뜻이므로, 필요하지 않은 boundary는 추가하지 마세요.

As a rule of thumb, if there's a Suspense boundary, React might use it. Under a slow network or a busy CPU, concurrent rendering can fall back to it even when you didn't expect it. Adding a boundary means accepting that, so don't add one you don't need.

LCP를 빠르게 유지하려면:

To keep LCP fast:

  • LCP element를 Suspense boundary 바깥 또는 위쪽에 두어 static shell의 일부로 render되게 하세요.
  • LCP 이미지에는 next/image의 preload prop을 사용하세요. 이 prop은 <head>에 <link rel="preload">를 넣어 주므로, <img> tag가 HTML에 나타나기도 전에 브라우저가 맨 첫 chunk부터 이미지를 가져오기 시작합니다. 이는 이미지를 언제 가져오는지를 제어할 뿐, 언제 그려지는지를 제어하지는 않습니다. boundary 안의 이미지는 여전히 교체를 기다립니다.
  • 이미지가 아닌 LCP element(텍스트, 제목)는 Suspense boundary 바깥에서 render하세요.
  • Keep LCP elements outside or above Suspense boundaries so they render as part of the static shell.
  • Use the preload prop on next/image for LCP images. This injects a <link rel="preload"> into the <head>, so the browser starts fetching the image from the very first chunk, before the <img> tag even appears in the HTML. It controls when the image is fetched, not when it paints. An image inside a boundary still waits for the swap.
  • For non-image LCP elements (text, headings), render them outside Suspense boundaries.

CLS (Cumulative Layout Shift)

Suspense fallback이 resolve된 콘텐츠로 교체되면 브라우저는 페이지를 reflow합니다. fallback과 resolve된 콘텐츠의 크기가 다르면 주변 layout이 밀려납니다. CLS를 최소화하려면:

When a Suspense fallback is replaced by the resolved content, the browser reflows the page. If the fallback and the resolved content are different sizes, the surrounding layout shifts. To minimize CLS:

  • 표현하려는 콘텐츠의 크기와 일치하는 skeleton fallback을 디자인하세요. 최종 card grid와 같은 높이와 너비를 가진 skeleton은 layout shift를 막아 줍니다.
  • Suspense boundary 주변에 고정 높이나 min-height container를 사용해, 콘텐츠가 도착하기 전에 공간을 확보해 두세요.
  • Design skeleton fallbacks that match the dimensions of the content they represent. A skeleton with the same height and width as the final card grid prevents shifts.
  • Use fixed or min-height containers around Suspense boundaries so the space is reserved before content arrives.

INP (Interaction to Next Paint)

Streaming은 selective hydration을 가능하게 합니다. React는 component가 stream되어 들어오는 대로 각각 독립적으로 hydrate하고, 사용자가 상호작용하고 있는 부분을 우선적으로 hydrate합니다. 각 <Suspense> boundary는 하나의 hydration 단위입니다. boundary가 없으면 React는 페이지 전체를 한 번의 blocking pass로 hydrate합니다. boundary가 있으면 hydration이 브라우저에 제어권을 양보하는 작은 task들로 나뉘어 main thread가 반응성을 유지합니다. 함께 제공되는 demo에서 한 번의 blocking hydration pass와 Suspense boundary를 사용한 split hydration을 비교해 볼 수 있습니다.

Streaming enables selective hydration: React hydrates components independently as they stream in, and prioritizes hydrating whatever the user is interacting with. Each <Suspense> boundary is a hydration unit. Without them, React hydrates the entire page in one blocking pass. With them, hydration is broken into smaller tasks that yield to the browser, keeping the main thread responsive. The companion demo lets you compare a single blocking hydration pass with split hydration using Suspense boundaries.

Early resource discovery이른 resource 발견

static shell은 맨 첫 HTML chunk에 <link>와 <script> tag를 포함합니다. 브라우저는 server가 아직 콘텐츠를 생성하는 동안 CSS, JavaScript, font를 즉시 발견하고 가져오기 시작합니다. resource는 server가 작업하는 시간(think time) 이후가 아니라 그 동안에 fetch됩니다.

The static shell includes <link> and <script> tags in the very first HTML chunk. The browser discovers and starts fetching CSS, JavaScript, and fonts immediately, while the server is still generating content. Resources are fetched during server think time rather than after it.

위의 dashboard 예제에서 <h1>은 shell 안에서 render되고(LCP에 좋음), 각 데이터 섹션은 자신의 Suspense boundary 뒤에서 독립적으로 stream되며(hydration이 나뉘므로 INP에 좋음), skeleton fallback이 공간을 확보합니다(CLS에 좋음).

In the dashboard example above, the <h1> renders in the shell (good for LCP), each data section streams independently behind its own Suspense boundary (good for INP since hydration is split), and the skeleton fallbacks reserve space (good for CLS).

The HTTP contractHTTP 계약

streaming이 시작되면 HTTP response header(status code 포함)는 이미 client로 전송된 상태입니다. streaming이 시작된 뒤에는 status code나 header를 변경할 수 없습니다. 이 섹션의 모든 내용은 이 근본적인 제약에서 비롯됩니다.

Once streaming begins, the HTTP response headers (including the status code) have already been sent to the client. You cannot change the status code or headers after streaming starts. Everything in this section flows from this fundamental constraint.

Status codesStatus code

<Suspense> fallback이 render되거나 component가 suspend되면, server는 HTML stream 전송을 시작하기 위해 200 OK로 확정해야 합니다. stream 도중에 notFound()가 호출되면 Next.js는 되돌아가서 status를 404로 바꿀 수 없습니다. 대신 stream되는 HTML에 <meta name="robots" content="noindex">를 넣어 검색 엔진이 페이지를 index하지 않도록 합니다. 마찬가지로 stream 도중의 redirect()는 HTTP redirect header가 아니라 client-side redirect가 됩니다.

When a <Suspense> fallback renders or a component suspends, the server must commit to 200 OK in order to start sending the HTML stream. If a notFound() fires mid-stream, Next.js cannot go back and change the status to 404. Instead, it injects <meta name="robots" content="noindex"> into the streamed HTML so that search engines don't index the page. Similarly, a redirect() mid-stream becomes a client-side redirect rather than an HTTP redirect header.

When does streaming start?streaming은 언제 시작될까?

response body는 Suspense fallback이 render될 때(예: loading.tsx) 또는 component가 <Suspense> boundary 아래에서 suspend될 때 streaming을 시작합니다. error에 대해 실제 HTTP status code를 얻으려면 notFound()를 어떤 await나 <Suspense> boundary보다도 앞에 두세요:

The response body begins streaming when a Suspense fallback renders (for example, a loading.tsx) or when a component suspends under a <Suspense> boundary. To get a real HTTP status code for errors, place notFound() before any await or <Suspense> boundary:

TSJSapp/post/[slug]/page.tsx
import { Suspense } from 'react'
import { notFound } from 'next/navigation'
import { PostContent } from './post-content'

export async function generateStaticParams() {
  const posts = await getPublishedPosts()
  return posts.map((post) => ({ slug: post.slug }))
}

export default async function PostPage({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params
  const exists = await checkSlugExists(slug) // Fast existence check
  if (!exists) notFound() // Real 404, before any Suspense boundary

  return (
    <Suspense fallback={<p>Loading post...</p>}>
      <PostContent slug={slug} />

  )
}

Good to know

proxy(redirect, rewrite, 또는 response 반환용)나 next.config.js redirects를 사용해 request를 일찍 거부할 수도 있습니다. 둘 다 페이지가 render되기 전에 실행되므로 HTTP status code를 여전히 사용할 수 있습니다.

You can also reject requests early using proxy (for redirects, rewrites, or returning a response) or next.config.js redirects. Both run before the page renders, so HTTP status codes are still available.

Bots and crawlersBot과 crawler

HTML만 처리할 수 있는(HTML-limited) bot과 crawler는 초기 HTML의 <head>에 metadata가 있어야 합니다. Next.js는 user agent로 이들을 감지하고, 페이지 콘텐츠를 stream하기 전에 generateMetadata가 resolve되기를 기다립니다. 완전한 브라우저와 DOM을 처리할 수 있는 crawler는 대신 페이지 콘텐츠와 함께 streaming metadata를 받을 수 있습니다.

HTML-limited bots and crawlers need metadata to be available in the <head> of the initial HTML. Next.js detects them by their user agent and waits for generateMetadata to resolve before streaming the page content. Full browsers and DOM-capable crawlers can instead receive streaming metadata alongside the page content.

어떤 bot이 blocking metadata를 받을지는 htmlLimitedBots configuration option으로 customize할 수 있습니다. 자세한 내용은 loading.js SEO 섹션을 참고하세요.

You can customize which bots receive blocking metadata with the htmlLimitedBots configuration option. See the loading.js SEO section for more details.

Cache Components

Cache Components를 사용하면 방문자와 DOM을 처리할 수 있는 crawler는 prerender된 shell을 즉시 받고, dynamic 콘텐츠는 resolve되는 대로 stream되어 들어옵니다. HTML-limited bot은 prerender된 shell을 건너뛰고 페이지를 dynamic하게 render하므로 metadata를 <head>에 넣을 수 있습니다. metadata가 resolve되면 나머지 페이지 콘텐츠는 여전히 stream될 수 있습니다.

With Cache Components, visitors and DOM-capable crawlers receive the prerendered shell immediately, and dynamic content streams in as it resolves. HTML-limited bots skip the prerendered shell and render the page dynamically so metadata can be placed in the <head>. Once the metadata resolves, the remaining page content can still stream.

prerender된 shell이 build-time 데이터나 request-time 환경에서 접근할 수 없는 값처럼 prerender 중에만 존재하는 입력에 의존한다면 이 점을 염두에 두세요. 방문자와 DOM을 처리할 수 있는 crawler는 그 코드를 다시 실행하지 않고 shell을 받지만, HTML-limited bot은 이를 dynamic하게 다시 render합니다. 그래서 사람에게는 잘 로드되는 페이지가 crawler에게는 render에 실패할 수 있습니다. shell이 의존하는 모든 데이터가 request time에도 사용 가능한지 확인하세요.

Keep this in mind when your prerendered shell depends on inputs that only exist while prerendering, such as build-time data or values that are not reachable in the request-time environment. Visitors and DOM-capable crawlers receive the shell without re-running that code, but an HTML-limited bot re-renders it dynamically, so a page that loads for a person can fail to render for a crawler. Make sure any data the shell relies on is also available at request time.

What can affect streamingstreaming에 영향을 줄 수 있는 것

server와 client 사이에서 response를 buffering하는 계층이 있다면 어떤 것이든 streaming의 이점을 줄일 수 있습니다. server에서는 HTML이 점진적으로 모두 생성되더라도, proxy, CDN, 또는 client 자신이 render하기 전에 모든 chunk를 모아 버리면, 사용자는 점진적인 rendering 대신 지연된 response 하나를 보게 됩니다.

Any layer between your server and the client that buffers the response can diminish the benefits of streaming. The HTML may be fully generated progressively on the server, but if a proxy, CDN, or even the client itself collects all the chunks before rendering them, the user sees a single delayed response instead of progressive rendering.

Reverse proxiesReverse proxy

Nginx와 같은 reverse proxy는 기본적으로 response를 buffering합니다. X-Accel-Buffering header를 no로 설정해 buffering을 비활성화하세요:

Nginx and similar reverse proxies buffer responses by default. Disable buffering by setting the X-Accel-Buffering header to no:

JSnext.config.js
module.exports = {
  async headers() {
    return [
      {
        source: '/:path*{/}?',
        headers: [
          {
            key: 'X-Accel-Buffering',
            value: 'no',
          },
        ],
      },
    ]
  },
}

CDNsCDN

Content Delivery Network는 response 전체를 buffering한 뒤 client로 전달할 수 있습니다. 사용하는 CDN 제공자의 문서에서 streaming 지원 여부를 확인하세요. 일부는 chunked response를 그대로 통과시키려면 특정 설정이나 요금제(plan tier)가 필요합니다.

Content Delivery Networks may buffer entire responses before forwarding them to the client. Check your CDN provider's documentation for streaming support. Some require specific configuration or plan tiers to pass through chunked responses.

Serverless platformsServerless 플랫폼

모든 serverless 환경이 streaming을 지원하는 것은 아닙니다. 예를 들어 AWS Lambda는 response streaming mode를 명시적으로 활성화해야 합니다(기본값이 아님). Vercel은 streaming을 기본적으로 지원합니다.

Not all serverless environments support streaming. AWS Lambda, for example, requires response streaming mode to be explicitly enabled (it is not the default). Vercel supports streaming natively.

Compression압축

Gzip과 Brotli 압축은 효율적으로 압축하려면 충분한 데이터가 필요하기 때문에, flush하기 전에 내부적으로 chunk를 buffering할 수 있습니다. 이로 인해 처음 보이는 chunk에 지연이 생길 수 있습니다. streaming 지연이 보인다면 압축 계층이 충분히 적극적으로 flush하고 있는지 확인하세요.

Gzip and Brotli compression can buffer chunks internally before flushing, as the compression algorithm needs enough data to compress efficiently. This can add latency to the first visible chunk. If you notice streaming delays, check whether your compression layer is flushing aggressively enough.

ClientsClient

buffering은 client에서도 일어납니다. Safari/WebKit은 1024 bytes를 받을 때까지 streaming response를 buffering하므로, 아주 작은 response는 점진적으로가 아니라 한 번에 그려집니다. 실제 애플리케이션은 이 기준을 쉽게 넘기 때문에(layout, style, script) 최소한의 demo나 아주 작은 Route Handler response에만 영향을 줍니다.

Buffering also happens at the client. Safari/WebKit buffers streaming responses until 1024 bytes have been received, so very small responses paint all at once instead of progressively. Real applications easily exceed this threshold (layouts, styles, scripts), so it only affects minimal demos or tiny Route Handler responses.

curl 같은 command-line 도구도 기본적으로 buffering합니다. -N flag는 출력 buffering을 비활성화하지만, curl은 여전히 줄바꿈 문자에 의존해 terminal에 줄을 flush합니다. 줄바꿈 없이 chunk를 보내는 stream은 -N을 써도 멈춘 것처럼 보일 수 있습니다.

Command-line tools like curl also buffer by default. The -N flag disables output buffering, but curl still relies on newline characters to flush lines to the terminal. A stream that sends chunks without newlines may appear to stall even with -N.

Verifying that streaming worksstreaming 동작 확인하기

이 섹션은 HTTP response가 인프라를 거쳐 실제로 chunk 단위로 도착하는지 확인하는 방법에 관한 것입니다. 의미 있는 loading state를 설계하고 Suspense boundary를 효과적으로 배치하는 방법은 Granular streaming with <Suspense>와 Cache Components 가이드를 참고하세요.

This section is about confirming the HTTP response is actually arriving in chunks through your infrastructure. For guidance on designing meaningful loading states and placing Suspense boundaries effectively, see Granular streaming with <Suspense> and the Cache Components guide.

Network tab을 확인하세요. Chrome DevTools에서 document request를 선택하고 "Timing" 세부 항목을 보세요. "Time to First Byte"가 빠르고 "Content Download" 단계가 길다면 response가 한 번에 도착하는 것이 아니라 stream되고 있다는 뜻입니다.

Check the Network tab. In Chrome DevTools, select the document request and look at the "Timing" breakdown. A long "Content Download" phase with an early "Time to First Byte" confirms the response is streaming rather than arriving all at once.

raw chunk를 관찰하세요. server가 정확히 무엇을 언제 보내는지 보려면 response를 stream으로 읽는 작은 script를 사용하세요. curl은 자체 buffering 동작이 있으므로, 시간별 chunk를 관찰하는 데에는 이 방법이 더 신뢰할 만합니다:

Observe raw chunks. To see exactly what the server sends and when, use a small script that reads the response as a stream. This is more reliable than curl for observing timed chunks, since curl has its own buffering behavior:

JSstream-observer.mjs
const res = await fetch(
  'https://streaming-demo.labs.vercel.dev/suspense-demo',
  {
    headers: { 'Accept-Encoding': 'identity' },
  }
)

const reader = res.body.getReader()
const decoder = new TextDecoder()
let i = 0
const start = Date.now()

while (true) {
  const { done, value } = await reader.read()
  if (done) break
  console.log(`\nchunk ${i++} (+${Date.now() - start}ms)\n`)
  console.log(decoder.decode(value))
}

node stream-observer.mjs로 실행하세요. 형제 Suspense boundary가 두 개 있는 페이지(함께 제공되는 demo의 Suspense 페이지처럼)라면 다음과 비슷한 출력을 보게 됩니다:

Run with node stream-observer.mjs. For a page with two sibling Suspense boundaries (like the companion demo's Suspense page), you will see output similar to:

>_Terminal
chunk 0 (+0ms)    # Static shell: <head>, CSS, nav, fallback skeletons,
                  # <template id="B:0"> and <template id="B:1"> placeholders,
                  # bootstrap scripts
chunk 1 (+170ms)  # Component payload (self.__next_f.push) for hydration
chunk 2 (+1000ms) # Weather widget: payload + <div hidden id="S:0"> (swaps B:0)
chunk 3 (+3000ms) # Analytics dashboard: payload + <div hidden id="S:1"> (swaps B:1)

<template id="B:0"> marker는 Suspense fallback placeholder입니다. boundary가 resolve되면 React는 완성된 HTML을 담은 <div hidden id="S:0">와 이를 페이지에 교체해 넣는 script를 stream합니다. timestamp를 보면 각 boundary가 독립적으로 resolve되는 것을 알 수 있습니다.

The <template id="B:0"> markers are the Suspense fallback placeholders. When a boundary resolves, React streams a <div hidden id="S:0"> containing the completed HTML and a script that swaps it into the page. The timestamps show each boundary resolving independently.

Good to know

Accept-Encoding: identity header는 압축을 비활성화하므로 chunk가 압축 계층에서 buffering되지 않습니다.

The Accept-Encoding: identity header disables compression so chunks are not buffered by the compression layer.

bot request와 비교해 보세요. 같은 script에 headers: { 'User-Agent': 'Twitterbot/1.0', 'Accept-Encoding': 'identity' }로 bot user agent를 추가하세요. 이제 await fetch() 자체가 전체 render가 끝날 때까지(이 페이지에서는 약 3초) 막힙니다. server가 완성된 문서를 얻을 때까지 response를 붙잡고 있기 때문입니다. 그런 다음 body가 한 번에 도착하며, +1000ms / +3000ms처럼 시차를 둔 timestamp는 전혀 없습니다:

Compare a bot request. Add a bot user agent to the same script with headers: { 'User-Agent': 'Twitterbot/1.0', 'Accept-Encoding': 'identity' }. Now await fetch() itself blocks until the full render completes (around 3 seconds for this page), because the server holds the response until it has the finished document. The body then arrives all at once, with none of the staggered +1000ms / +3000ms timestamps:

>_Terminal
chunk 0 (+0ms) # Entire document in a single burst, after fetch() already waited

이것이 bots and crawlers 동작입니다. server는 전체 render를 기다렸다가 streaming 대신 완전히 구성된 HTML 문서 하나를 보냅니다.

This is the bots and crawlers behavior: the server waits for the full render and sends one fully formed HTML document instead of streaming.

Summary요약

trigger는 여러분의 코드입니다. async 작업, 비결정적(non-deterministic) 출력, 또는 runtime 데이터가 그렇습니다. framework는 이들을 만나면 tree를 거슬러 올라가며 fallback으로 사용할 <Suspense> boundary를 찾습니다. 그 boundary들 위의 모든 것이 static shell을 이루며, 이는 즉시 전송됩니다. 각 boundary가 resolve될 때마다 React가 그 결과를 페이지에 stream합니다.

The trigger is your code: async work, non-deterministic output, or runtime data. When the framework encounters these, it walks up the tree looking for a <Suspense> boundary to use as a fallback. Everything above those boundaries forms the static shell, which is sent immediately. As each boundary resolves, React streams the result into the page.

핵심 결정은 무엇을 cache할지와 Suspense boundary를 어디에 둘지입니다. "use cache"로 cache할 수 있는 것은 cache해서 static shell을 키우세요. dynamic 접근은 그것이 필요한 component로 내리고, 그 component를 <Suspense>로 감싸세요. 나머지는 모두 shell의 일부가 됩니다.

The key decisions are what to cache and where to place Suspense boundaries. Cache what you can with "use cache" to grow the static shell. Push dynamic access down to the components that need it, and wrap those in <Suspense>. Everything else becomes part of the shell.

이 pattern들을 기존 route에 적용하는 단계별 workflow는 Optimizing the static shell을 참고하세요.

For a step-by-step workflow that applies these patterns to an existing route, see Optimizing the static shell.
