How to use Next.js as a backend for your frontendNext.js를 frontend용 backend로 사용하기

Next.js는 "Backend for Frontend" 패턴을 지원합니다. 이를 통해 HTTP request를 처리하고 HTML뿐 아니라 어떤 content type이든 반환하는 public endpoint를 만들 수 있습니다. 또한 데이터 source에 접근하고 원격 데이터를 업데이트하는 것 같은 side effect를 수행할 수도 있습니다.

Next.js supports the "Backend for Frontend" pattern. This lets you create public endpoints to handle HTTP requests and return any content type—not just HTML. You can also access data sources and perform side effects like updating remote data.

새 프로젝트를 시작한다면 create-next-app에 --api flag를 사용하세요. 그러면 새 프로젝트의 app/ 폴더에 API endpoint를 만드는 방법을 보여 주는 예제 route.ts가 자동으로 포함됩니다.

If you are starting a new project, using create-next-app with the --api flag automatically includes an example route.ts in your new project's app/ folder, demonstrating how to create an API endpoint.

pnpm create next-app --api
npx create-next-app@latest --api
yarn create next-app --api
bun create next-app --api
Good to know

Next.js의 backend 기능은 완전한 backend를 대체하지 않습니다. 이는 다음과 같은 API layer 역할을 합니다:

  • 외부에서 공개적으로 접근 가능하고
  • 모든 HTTP request를 처리하며
  • 어떤 content type이든 반환할 수 있습니다

Next.js backend capabilities are not a full backend replacement. They serve as an API layer that:

  • is publicly reachable
  • handles any HTTP request
  • can return any content type

이 패턴을 구현하려면 다음을 사용하세요:

To implement this pattern, use:

  • Route Handlers
  • proxy
  • Pages Router에서는 API Routes

Public EndpointsPublic endpoint

Route Handler는 public HTTP endpoint입니다. 어떤 client든 접근할 수 있습니다.

Route Handlers are public HTTP endpoints. Any client can access them.

route.ts 또는 route.js file convention을 사용해 Route Handler를 만드세요:

Create a Route Handler using the route.ts or route.js file convention:

TSJS/app/api/route.ts
export function GET(request: Request) {}

이는 /api로 보낸 GET request를 처리합니다.

This handles GET requests sent to /api.

export async function POST(request: Request) {
  try {
    await submit(request)
    return new Response(null, { status: 204 })
  } catch (reason) {
    const message =
      reason instanceof Error ? reason.message : 'Unexpected error'

    return new Response(message, { status: 500 })
  }
}

Content negotiation

header matching과 함께 rewrites를 사용하면 request의 Accept header에 따라 같은 URL에서 서로 다른 content type을 제공할 수 있습니다. 이를 content negotiation이라고 합니다.

You can use rewrites with header matching to serve different content types from the same URL based on the request's Accept header. This is known as content negotiation.

예를 들어 문서 사이트는 같은 /docs/… URL에서 브라우저에는 HTML 페이지를, AI agent에는 raw Markdown을 제공할 수 있습니다.

For example, a documentation site might serve HTML pages to browsers and raw Markdown to AI agents from the same /docs/… URLs.

1. Accept header와 match되는 rewrite 설정하기:

1. Configure a rewrite that matches the Accept header:

JSnext.config.js
module.exports = {
  async rewrites() {
    return [
      {
        source: '/docs/:slug*',
        destination: '/docs/md/:slug*',
        has: [
          {
            type: 'header',
            key: 'accept',
            value: '(.*)text/markdown(.*)',
          },
        ],
      },
    ]
  },
}

/docs/getting-started로 가는 request에 Accept: text/markdown이 포함되어 있으면, rewrite가 이를 /docs/md/getting-started로 route합니다. 해당 경로의 Route Handler가 Markdown response를 반환합니다. Accept header에 text/markdown을 보내지 않는 client는 계속 일반 HTML 페이지를 받습니다.

When a request to /docs/getting-started includes Accept: text/markdown, the rewrite routes it to /docs/md/getting-started. A Route Handler at that path returns the Markdown response. Clients that do not send text/markdown in their Accept header continue to receive the normal HTML page.

2. Markdown response를 위한 Route Handler 만들기:

2. Create a Route Handler for the Markdown response:

TSJSapp/docs/md/[...slug]/route.ts
import { getDocsMd, generateDocsStaticParams } from '@/lib/docs'

export async function generateStaticParams() {
  return generateDocsStaticParams()
}

export async function GET(_: Request, ctx: RouteContext<'/docs/md/[...slug]'>) {
  const { slug } = await ctx.params
  const mdDoc = await getDocsMd({ slug })

  if (mdDoc == null) {
    return new Response(null, { status: 404 })
  }

  return new Response(mdDoc, {
    headers: {
      'Content-Type': 'text/markdown; charset=utf-8',
      Vary: 'Accept',
    },
  })
}

}

      Vary: 'Accept',
    },

Vary: Accept response header는 response body가 Accept request header에 따라 달라진다는 것을 cache에 알려 줍니다. 이 header가 없으면 공유 cache가 cache된 Markdown response를 브라우저에 제공할 수 있습니다(반대의 경우도 마찬가지입니다). 대부분의 hosting provider는 이미 Accept header를 cache key에 포함하지만, Vary를 명시적으로 설정하면 모든 CDN과 proxy cache에서 올바르게 동작하도록 보장할 수 있습니다.

The Vary: Accept response header tells caches that the response body depends on the Accept request header. Without it, a shared cache could serve a cached Markdown response to a browser (or vice versa). Most hosting providers already include the Accept header in their cache key, but setting Vary explicitly ensures correct behavior across all CDNs and proxy caches.

generateStaticParams를 사용하면 build 시점에 Markdown 버전을 pre-render할 수 있어서, request마다 origin server에 가지 않고 edge에서 제공할 수 있습니다.

generateStaticParams lets you pre-render the Markdown variants at build time so they can be served from the edge without hitting the origin server on every request.

Good to know
  • /docs/md/... route는 rewrite 없이도 여전히 직접 접근할 수 있습니다. rewrite를 통해서만 제공되도록 제한하려면 proxy를 사용해 예상한 Accept header가 없는 직접 request를 차단하세요.
  • 더 고급 negotiation 로직이 필요하다면, 더 유연하게 rewrites 대신 proxy를 사용할 수 있습니다.
  • The /docs/md/... route is still directly accessible without the rewrite. If you want to restrict it to only serve via the rewrite, use proxy to block direct requests that don't include the expected Accept header.
  • For more advanced negotiation logic, you can use proxy instead of rewrites for more flexibility.

Manipulating data데이터 가공하기

Route Handler는 하나 이상의 source에서 가져온 데이터를 변환, 필터링, 집계할 수 있습니다. 이렇게 하면 로직을 frontend 밖에 두고 내부 시스템이 노출되는 것을 피할 수 있습니다.

Route Handlers can transform, filter, and aggregate data from one or more sources. This keeps logic out of the frontend and avoids exposing internal systems.

무거운 연산을 server로 넘겨 client의 배터리와 데이터 사용량을 줄일 수도 있습니다.

You can also offload heavy computations to the server and reduce client battery and data usage.

Proxying to a backendbackend로 proxy하기

Route Handler를 다른 backend에 대한 proxy로 사용할 수 있습니다. request를 전달하기 전에 validation 로직을 추가하세요.

You can use a Route Handler as a proxy to another backend. Add validation logic before forwarding the request.

TSJS/app/api/[...slug]/route.ts
import { isValidRequest } from '@/lib/utils'

export async function POST(request: Request, { params }) {
  const clonedRequest = request.clone()
  const isValid = await isValidRequest(clonedRequest)

  if (!isValid) {
    return new Response(null, { status: 400, statusText: 'Bad Request' })
  }

  const { slug } = await params
  const pathname = slug.join('/')
  const proxyURL = new URL(pathname, 'https://nextjs.org')
  const proxyRequest = new Request(proxyURL, request)

  try {
    return fetch(proxyRequest)
  } catch (reason) {
    const message =
      reason instanceof Error ? reason.message : 'Unexpected exception'

    return new Response(message, { status: 500 })
  }
}

NextRequest and NextResponseNextRequest와 NextResponse

Next.js는 Request와 Response Web API를 확장해 흔한 작업을 단순화하는 method를 제공합니다. 이 확장 기능은 Route Handler와 Proxy 모두에서 사용할 수 있습니다.

Next.js extends the Request and Response Web APIs with methods that simplify common operations. These extensions are available in both Route Handlers and Proxy.

둘 다 cookie를 읽고 조작하는 method를 제공합니다.

Both provide methods for reading and manipulating cookies.

NextRequest에는 nextUrl property가 있어 들어오는 request에서 parse된 값을 노출합니다. 예를 들어 request pathname과 search params에 더 쉽게 접근할 수 있습니다.

NextRequest includes the nextUrl property, which exposes parsed values from the incoming request, for example, it makes it easier to access request pathname and search params.

NextResponse는 next(), json(), redirect(), rewrite() 같은 helper를 제공합니다.

NextResponse provides helpers like next(), json(), redirect(), and rewrite().

Request를 기대하는 어떤 함수에든 NextRequest를 전달할 수 있습니다. 마찬가지로 Response가 기대되는 곳에서 NextResponse를 반환할 수 있습니다.

You can pass NextRequest to any function expecting Request. Likewise, you can return NextResponse where a Response is expected.

TSJS/app/echo-pathname/route.ts
import { type NextRequest, NextResponse } from 'next/server'

export async function GET(request: NextRequest) {
  const nextUrl = request.nextUrl

  if (nextUrl.searchParams.get('redirect')) {
    return NextResponse.redirect(new URL('/', request.url))
  }

  if (nextUrl.searchParams.get('rewrite')) {
    return NextResponse.rewrite(new URL('/', request.url))
  }

  return NextResponse.json({ pathname: nextUrl.pathname })
}

Webhooks and callback URLsWebhook과 callback URL

Route Handler를 사용해 third-party 애플리케이션으로부터 event 알림을 받으세요.

Use Route Handlers to receive event notifications from third-party applications.

예를 들어 CMS에서 콘텐츠가 바뀌면 route를 revalidate할 수 있습니다. 변경이 있을 때 특정 endpoint를 호출하도록 CMS를 설정하세요.

For example, revalidate a route when content changes in a CMS. Configure the CMS to call a specific endpoint on changes.

TSJS/app/webhook/route.ts
import { type NextRequest, NextResponse } from 'next/server'

export async function GET(request: NextRequest) {
  const token = request.nextUrl.searchParams.get('token')

  if (token !== process.env.REVALIDATE_SECRET_TOKEN) {
    return NextResponse.json({ success: false }, { status: 401 })
  }

  const tag = request.nextUrl.searchParams.get('tag')

  if (!tag) {
    return NextResponse.json({ success: false }, { status: 400 })
  }

  revalidateTag(tag, 'max')

  return NextResponse.json({ success: true })
}

callback URL도 또 다른 use case입니다. 사용자가 third-party 흐름을 완료하면, third party는 사용자를 callback URL로 보냅니다. Route Handler를 사용해 response를 검증하고 사용자를 어디로 redirect할지 결정하세요.

Callback URLs are another use case. When a user completes a third-party flow, the third party sends them to a callback URL. Use a Route Handler to verify the response and decide where to redirect the user.

TSJS/app/auth/callback/route.ts
import { type NextRequest, NextResponse } from 'next/server'

export async function GET(request: NextRequest) {
  const token = request.nextUrl.searchParams.get('session_token')
  const redirectUrl = request.nextUrl.searchParams.get('redirect_url')

  const destination = new URL(redirectUrl ?? '/', request.url)
  // Prevent open redirects: only allow same-origin destinations
  if (destination.origin !== request.nextUrl.origin) {
    return new Response('Invalid redirect', { status: 400 })
  }

  const response = NextResponse.redirect(destination)

  response.cookies.set({
    value: token,
    name: '_token',
    path: '/',
    secure: true,
    httpOnly: true,
    expires: undefined, // session cookie
  })

  return response
}

  }

  const response = NextResponse.redirect(destination)

  response.cookies.set({
    value: token,
    name: '_token',
    path: '/',
    secure: true,
    httpOnly: true,
    expires: undefined, // session cookie
  })

  return response
}

Proxy

프로젝트당 proxy 파일은 하나만 허용됩니다. 특정 경로를 대상으로 하려면 config.matcher를 사용하세요. proxy에 대해 더 알아보세요.

Only one proxy file is allowed per project. Use config.matcher to target specific paths. Learn more about proxy.

request가 route 경로에 도달하기 전에 response를 생성하려면 proxy를 사용하세요.

Use proxy to generate a response before the request reaches a route path.

TSJSproxy.ts
import { isAuthenticated } from '@lib/auth'

export const config = {
  matcher: '/api/:function*',
}

export function proxy(request: Request) {
  if (!isAuthenticated(request)) {
    return Response.json(
      { success: false, message: 'authentication failed' },
      { status: 401 }
    )
  }
}

proxy를 사용해 request를 proxy할 수도 있습니다. 이 예제는 request.nextUrl을 읽으므로 request의 type은 NextRequest입니다:

You can also proxy requests using proxy. This example reads request.nextUrl, so request is typed as NextRequest:

  if (request.nextUrl.pathname === '/proxy-this-path') {

    return NextResponse.rewrite(rewriteUrl)
  }
}

Security보안

Working with headersheader 다루기

header가 어디로 가는지 신중하게 다루고, 들어오는 request header를 나가는 response에 그대로 전달하지 마세요.

Be deliberate about where headers go, and avoid directly passing incoming request headers to the outgoing response.

  • Upstream request headers: Proxy에서 NextResponse.next({ request: { headers } })는 server가 받는 header를 수정하며, 이를 client에 노출하지 않습니다.
  • Response headers: new Response(..., { headers }), NextResponse.json(..., { headers }), NextResponse.next({ headers }), response.headers.set(...)은 header를 client로 돌려보냅니다. 이런 header에 민감한 값이 추가되었다면 client에게 보이게 됩니다.
  • Upstream request headers: In Proxy, NextResponse.next({ request: { headers } }) modifies the headers your server receives and does not expose them to the client.
  • Response headers: new Response(..., { headers }), NextResponse.json(..., { headers }), NextResponse.next({ headers }), or response.headers.set(...) send headers back to the client. If sensitive values were appended to these headers, they will be visible to clients.

자세한 내용은 NextResponse headers in Proxy를 참고하세요.

Learn more in NextResponse headers in Proxy.

Rate limiting

Next.js backend에서 rate limiting을 구현할 수 있습니다. 코드 기반 check 외에도, host가 제공하는 rate limiting 기능이 있다면 활성화하세요.

You can implement rate limiting in your Next.js backend. In addition to code-based checks, enable any rate limiting features provided by your host.

TSJS/app/resource/route.ts
import { NextResponse } from 'next/server'
import { checkRateLimit } from '@/lib/rate-limit'

export async function POST(request: Request) {
  const { rateLimited } = await checkRateLimit(request)

  if (rateLimited) {
    return NextResponse.json({ error: 'Rate limit exceeded' }, { status: 429 })
  }

  return new Response(null, { status: 204 })
}
import { NextResponse } from 'next/server'
import { checkRateLimit } from '@/lib/rate-limit'

export async function POST(request) {
  const { rateLimited } = await checkRateLimit(request)

  if (rateLimited) {
    return NextResponse.json({ error: 'Rate limit exceeded' }, { status: 429 })
  }

  return new Response(null, { status: 204 })
}

Verify payloadspayload 검증하기

들어오는 request 데이터는 절대 신뢰하지 마세요. 사용하기 전에 content type과 크기를 검증하고, XSS에 대비해 sanitize하세요.

Never trust incoming request data. Validate content type and size, and sanitize against XSS before use.

timeout을 사용해 남용을 막고 server 리소스를 보호하세요.

Use timeouts to prevent abuse and protect server resources.

사용자가 생성한 static asset은 전용 service에 저장하세요. 가능하다면 브라우저에서 바로 upload하고, 반환된 URI를 database에 저장해 request 크기를 줄이세요.

Store user-generated static assets in dedicated services. When possible, upload them from the browser and store the returned URI in your database to reduce request size.

Access to protected resources보호된 리소스에 대한 접근

접근을 허용하기 전에 항상 credential을 검증하세요. authentication과 authorization을 proxy에만 의존하지 마세요.

Always verify credentials before granting access. Do not rely on proxy alone for authentication and authorization.

response와 backend log에서 민감하거나 불필요한 데이터를 제거하세요.

Remove sensitive or unnecessary data from responses and backend logs.

credential과 API key는 정기적으로 교체(rotate)하세요.

Rotate credentials and API keys regularly.

Preflight RequestsPreflight request

preflight request는 OPTIONS method를 사용해 origin, method, header를 기준으로 request가 허용되는지 server에 묻습니다.

Preflight requests use the OPTIONS method to ask the server if a request is allowed based on origin, method, and headers.

OPTIONS가 정의되어 있지 않으면 Next.js가 자동으로 추가하고, 정의된 다른 method를 바탕으로 Allow header를 설정합니다.

If OPTIONS is not defined, Next.js adds it automatically and sets the Allow header based on the other defined methods.

Caveats주의 사항

Server Components

Server Component에서는 Route Handler를 거치지 말고 source에서 직접 데이터를 fetch하세요.

Fetch data in Server Components directly from its source, not via Route Handlers.

build 시점에 prerender되는 Server Component에서 Route Handler를 사용하면 build 단계가 실패합니다. build 중에는 이런 request를 받을 server가 떠 있지 않기 때문입니다.

For Server Components prerendered at build time, using Route Handlers will fail the build step. This is because, while building there is no server listening for these requests.

on demand로 render되는 Server Component에서는 handler와 render process 사이에 추가 HTTP 왕복이 생기므로 Route Handler에서 fetch하는 것이 더 느립니다.

For Server Components rendered on demand, fetching from Route Handlers is slower due to the extra HTTP round trip between the handler and the render process.

server side fetch request는 absolute URL을 사용합니다. 이는 외부 server로의 HTTP 왕복을 의미합니다. development 중에는 자신의 development server가 외부 server 역할을 합니다. build 시점에는 server가 없고, runtime에는 외부에 공개된 domain을 통해 server에 접근할 수 있습니다.

A server side fetch request uses absolute URLs. This implies an HTTP round trip, to an external server. During development, your own development server acts as the external server. At build time there is no server, and at runtime, the server is available through your public facing domain.

Server Component는 대부분의 data-fetching 요구를 충족합니다. 하지만 다음과 같은 경우에는 client side에서 데이터를 fetch해야 할 수도 있습니다:

Server Components cover most data-fetching needs. However, fetching data client side might be necessary for:

  • client 전용 Web API에 의존하는 데이터:
    • Geo-location API
    • Storage API
    • Audio API
    • File API
  • 자주 polling하는 데이터
  • Data that depends on client-only Web APIs:
    • Geo-location API
    • Storage API
    • Audio API
    • File API
  • Frequently polled data

이런 경우에는 swr이나 react-query 같은 community library를 사용하세요.

For these, use community libraries like swr or react-query.

Server Actions

Server Action을 사용하면 client에서 server-side 코드를 실행할 수 있습니다. 주된 목적은 frontend client에서 데이터를 변경(mutate)하는 것입니다.

Server Actions let you run server-side code from the client. Their primary purpose is to mutate data from your frontend client.

Server Action은 queue에 쌓여 처리됩니다. data fetching에 사용하면 순차 실행이 발생합니다.

Server Actions are queued. Using them for data fetching introduces sequential execution.

export mode

export mode는 runtime server 없이 static site를 출력합니다. 이 mode는 static site만 만들고 runtime server가 없기 때문에, Next.js runtime이 필요한 기능은 지원되지 않습니다.

export mode outputs a static site without a runtime server. Features that require the Next.js runtime are not supported, because this mode produces a static site, and no runtime server.

export mode에서는 dynamic route segment config를 'force-static'으로 설정한 GET Route Handler만 지원됩니다.

In export mode, only GET Route Handlers are supported, in combination with the dynamic route segment config, set to 'force-static'.

이를 사용해 static HTML, JSON, TXT 등의 파일을 생성할 수 있습니다.

This can be used to generate static HTML, JSON, TXT, or other files.

JSapp/hello-world/route.ts
export const dynamic = 'force-static'

export function GET() {
  return new Response('Hello World', { status: 200 })
}

Deployment environment배포 환경

일부 host는 Route Handler를 lambda function으로 deploy합니다. 이는 다음을 의미합니다:

Some hosts deploy Route Handlers as lambda functions. This means:

  • Route Handler는 request 간에 데이터를 공유할 수 없습니다.
  • 환경에 따라 File System 쓰기를 지원하지 않을 수 있습니다.
  • 오래 실행되는 handler는 timeout으로 종료될 수 있습니다.
  • WebSocket은 timeout 시점이나 response가 생성된 후 connection이 닫히므로 동작하지 않습니다.
  • Route Handlers cannot share data between requests.
  • The environment may not support writing to File System.
  • Long-running handlers may be terminated due to timeouts.
  • WebSockets won’t work because the connection closes on timeout, or after the response is generated.
