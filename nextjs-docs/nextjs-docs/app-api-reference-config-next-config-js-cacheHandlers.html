cacheHandlerscacheHandlers

cacheHandlers configuration을 사용하면 'use cache'와 'use cache: remote'를 위한 custom cache storage 구현을 정의할 수 있습니다. 이를 통해 cache된 component와 function을 외부 service에 저장하거나 caching 동작을 customize할 수 있습니다. 'use cache: private'는 설정할 수 없습니다.

The cacheHandlers configuration allows you to define custom cache storage implementations for 'use cache' and 'use cache: remote'. This enables you to store cached components and functions in external services or customize the caching behavior. 'use cache: private' is not configurable.

When to use custom cache handlerscustom cache handler를 사용해야 할 때

대부분의 애플리케이션에는 custom cache handler가 필요하지 않습니다. 일반적인 사용 사례에서는 기본 in-memory cache로 충분합니다.

Most applications don't need custom cache handlers. The default in-memory cache works well in the typical use case.

custom cache handler는 여러 instance 간에 cache를 공유해야 하거나 cache가 저장되는 위치를 바꿔야 하는 고급 시나리오를 위한 것입니다. 예를 들어 외부 storage(key-value store 등)를 위한 custom remote handler를 설정한 뒤, 코드에서 in-memory caching에는 'use cache'를, 외부 storage에는 'use cache: remote'를 사용하여 같은 애플리케이션 안에서 서로 다른 caching 전략을 사용할 수 있습니다.

Custom cache handlers are for advanced scenarios where you need to either share cache across multiple instances or change where the cache is stored. For example, you can configure a custom remote handler for external storage (like a key-value store), then use 'use cache' in your code for in-memory caching and 'use cache: remote' for the external storage, allowing different caching strategies within the same application.

instance 간 cache 공유

Sharing cache across instances

기본 in-memory cache는 각 Next.js process에 격리되어 있습니다. 여러 server나 container를 실행하는 경우, 각 instance는 다른 instance와 공유되지 않는 자체 cache를 가지며 이 cache는 재시작 시 사라집니다.

The default in-memory cache is isolated to each Next.js process. If you're running multiple servers or containers, each instance will have its own cache that isn't shared with others and is lost on restart.

custom handler를 사용하면 모든 Next.js instance가 접근할 수 있는 공유 storage system(Redis, Memcached, DynamoDB 등)과 통합할 수 있습니다.

Custom handlers let you integrate with shared storage systems (like Redis, Memcached, or DynamoDB) that all your Next.js instances can access.

storage 유형 변경

Changing storage type

기본 in-memory 방식과 다르게 cache를 저장하고 싶을 수도 있습니다. custom handler를 구현하여 cache를 disk, database, 또는 외부 caching service에 저장할 수 있습니다. 재시작 후에도 유지되는 persistence, memory 사용량 감소, 기존 infrastructure와의 통합 등이 그 이유가 될 수 있습니다.

You might want to store cache differently than the default in-memory approach. You can implement a custom handler to store cache on disk, in a database, or in an external caching service. Reasons include: persistence across restarts, reducing memory usage, or integrating with existing infrastructure.

Handler typesHandler 유형

  • default: 'use cache' directive에서 사용됩니다
  • remote: 'use cache: remote' directive에서 사용됩니다
  • default: Used by the 'use cache' directive
  • remote: Used by the 'use cache: remote' directive

cacheHandlers를 설정하지 않으면 Next.js는 default와 remote 모두에 in-memory LRU(Least Recently Used) cache를 사용합니다. 참고용으로 기본 구현을 볼 수 있습니다.

If you don't configure cacheHandlers, Next.js uses an in-memory LRU (Least Recently Used) cache for both default and remote. You can view the default implementation as a reference.

추가로 이름이 있는 handler(예: sessions, analytics)를 정의하고 'use cache: <name>'으로 참조할 수도 있습니다.

You can also define additional named handlers (e.g., sessions, analytics) and reference them with 'use cache: <name>'.

'use cache: private'는 cache handler를 사용하지 않으며 customize할 수 없다는 점에 유의하세요.

Note that 'use cache: private' does not use cache handlers and cannot be customized.

The entry value streamEntry value stream

모든 handler는 set()을 통해 entry를 기록하고 get()을 통해 제공합니다. 두 method 모두 entry의 serialize된 value를 다루며, 이 value는 ReadableStream<Uint8Array>로 전달됩니다. 이 stream의 두 가지 특성이 모든 구현을 제약합니다:

Every handler writes entries through set() and serves them through get(). Both methods work with the entry's serialized value, which arrives as a ReadableStream<Uint8Array>. Two properties of that stream constrain every implementation:

  • 한 번만 읽을 수 있습니다. set()에서 stream을 소비하고, 매 get()마다 저장된 data를 기반으로 새 stream을 만드세요. 이미 읽은 stream은 두 번째 reader에게 제공할 수 없습니다. data를 전달하지 않거나, 첫 번째 reader가 아직 lock을 갖고 있으면 error를 throw합니다.
  • entry를 생성한 request에 속합니다. set()이 resolve된 뒤에는 stream을 보관하지 마세요. stream은 해당 request에 대한 reference를 갖고 있으므로, 이를 보관하면 entry가 evict될 때까지 request의 memory가 유지됩니다. pendingEntry promise에도 같은 내용이 적용됩니다. Next.js는 render를 위해 value의 자체 복사본을 유지하므로, handler는 전달받은 stream을 자유롭게 소비해도 됩니다.
  • It can be read only once. Consume it in set(), and build a new stream over your stored data in every get(). A stream that was already read cannot serve a second reader: it delivers no data, or throws if the first reader still holds its lock.
  • It belongs to the request that produced the entry. Do not keep it once set() resolves. The stream holds a reference to that request, so keeping it holds the request's memory until your entry is evicted. The same applies to the pendingEntry promise. Next.js keeps its own copy of the value for the render, so your handler is free to consume the stream it receives.

data를 어떻게 persist할지는 직접 결정하면 됩니다. stream을 buffering하는 방식과 chunk가 도착하는 대로 store에 pipe하는 방식 모두 괜찮으며, 정확히 한 번만 소비하기만 하면 됩니다. 큰 entry는 pipe하는 것이 좋습니다. page는 많은 byte로 serialize될 수 있으며, S3 같은 backend는 handler가 두 번째 복사본을 들고 있지 않아도 이를 받아들일 수 있습니다.

How you persist the data is up to you. Buffering the stream and piping it to your store as chunks arrive are both fine, as long as you consume it exactly once. Large entries are worth piping: a page can serialize to a lot of bytes, and an S3-like backend can accept them without your handler holding a second copy.

대비해야 할 경우가 두 가지 더 있습니다:

Two more cases to plan for:

  • Fan-out. 하나의 entry가 local store와 remote store처럼 두 곳에 전달되어야 한다면, .tee()를 사용하고 set()이 resolve되기 전에 두 branch를 모두 소비하세요. tee는 value를 보관해 두기 위한 방법이 아닙니다. 저장해 둔 branch가 다음 read를 처리할 수는 있지만, source stream, buffer된 chunk, 그리고 이를 생성한 request를 붙잡고 있으며, 이 중 어느 것도 store가 계산하는 크기에 나타나지 않습니다.
  • 중단된 value. stream은 rendering 도중에 error가 날 수 있으며, 그러면 불완전한 value가 남습니다. 이를 보관할지 버릴지 결정하세요. 불완전한 value는 불완전한 page를 만들기 때문에 버리는 것이 더 안전합니다. 이는 부분적으로 기록된 storage entry와는 별개의 문제로, 후자는 Error Handling에서 다룹니다.
  • Fan-out. If a single entry has to reach two destinations, such as a local store and a remote one, use .tee() and consume both branches before set() resolves. Teeing is not a way to keep the value around. A stored branch does serve the next read, but it holds the source stream, its buffered chunks, and the request that produced them, and none of that appears in the size your store accounts for.
  • Interrupted values. The stream can error partway through rendering, which leaves you holding an incomplete value. Decide whether to keep it or discard it. Discarding is safer, because an incomplete value produces an incomplete page. This is separate from a partially written storage entry, which Error Handling covers.

API Reference

cache handler는 다음 다섯 가지 method를 가진 CacheHandler interface를 구현해야 합니다.

A cache handler must implement the CacheHandler interface with the following five methods.

set()

주어진 cache key에 대한 cache entry를 저장합니다.

Store a cache entry for the given cache key.

set(cacheKey: string, pendingEntry: Promise<CacheEntry>): Promise<void>
ParameterTypeDescription
cacheKeystringentry를 저장할 고유 key.
pendingEntryPromise<CacheEntry>cache entry로 resolve되는 promise.
ParameterTypeDescription
cacheKeystringThe unique key to store the entry under.
pendingEntryPromise<CacheEntry>A promise that resolves to the cache entry.

Promise<void>를 반환합니다.

Returns Promise<void>.

set()이 호출될 때 entry가 아직 생성 중일 수 있으므로 먼저 pendingEntry를 await하세요. 그런 다음 The entry value stream에서 설명한 대로 value stream을 소비하고 전달된 내용을 persist하세요.

The entry may still be generating when set() is called, so await pendingEntry first. Then consume the value stream and persist what it delivers, as described in The entry value stream.

아래 예제는 buffering 방식을 사용하는데, 이는 더 간단한 방법이며 in-memory store에 적합한 방법입니다. remote handler라면 대신 entry.value를 upload로 pipe할 수 있습니다.

The example below buffers, which is the simpler option and the right one for an in-memory store. A remote handler can pipe entry.value into an upload instead.

const cacheHandler = {
  async set(cacheKey, pendingEntry) {
    // Wait for the entry to be ready
    const entry = await pendingEntry

    // Consume the stream, then keep the data rather than the stream
    const value = new Uint8Array(await new Response(entry.value).arrayBuffer())

    // Store in your cache system
    cache.set(cacheKey, { ...entry, value })
  },
}

get()

주어진 cache key에 대한 cache entry를 가져옵니다.

Retrieve a cache entry for the given cache key.

get(cacheKey: string, softTags: string[]): Promise<CacheEntry | undefined>
ParameterTypeDescription
cacheKeystringcache entry의 고유 key.
softTagsstring[]route path에서 파생된 암묵적 tag. 사용 방법은 Soft Tags를 참고하세요.
ParameterTypeDescription
cacheKeystringThe unique key for the cache entry.
softTagsstring[]Implicit tags derived from the route path. See Soft Tags for how to use them.

저장된 것이 있으면 CacheEntry object를, 없으면 undefined를 반환합니다.

Returns a CacheEntry object if one is stored, or undefined if not.

get method는 storage에서 cache entry를 가져와야 하며, 저장된 것이 없으면 undefined를 반환해야 합니다.

Your get method should retrieve the cache entry from storage and return undefined when there is nothing stored.

entry가 얼마나 오래되었는지 확인할 필요는 없습니다. Next.js는 매 read마다 timestamp를 entry 자체의 expire와 비교하고, 너무 오래된 entry는 miss로 처리합니다. 결과가 다른 server cache에 기록되려는 경우에는 revalidate에도 같은 검사를 적용하며, dev server에서는 reload가 빠르게 유지되도록 entry를 조금 더 오래 보관합니다. 직접 age 검사를 추가하면 이 중 첫 번째 검사를 중복할 뿐입니다.

You do not need to check how old the entry is. Next.js compares timestamp against the entry's own expire on every read and treats a too-old entry as a miss. It applies the same check to revalidate when the result is about to be written into another server cache, and it keeps entries a little longer on the dev server so reloads stay fast. Your own age check only duplicates the first of those.

두 timing이 의미하는 바는 반환한 entry를 Next.js가 어떻게 처리하는지에 달려 있습니다:

What the two timings mean for you is what Next.js does with the entry you return:

  • expire 시점이 지나면 entry는 폐기되고 value가 다시 생성됩니다.
  • revalidate 시점은 지났지만 expire 이내라면, entry가 제공되고 background에서 새 entry가 생성됩니다.
  • Past expire, the entry is discarded and the value is regenerated.
  • Past revalidate but within expire, the entry is served and a fresh one is generated in the background.

entry를 더 일찍 삭제하는 것은 필수 사항이 아니라 policy 선택입니다. built-in handler는 revalidate 시점에 entry를 삭제하는데, in-memory entry는 누군가 읽기 전에 evict될 가능성이 높아 대체 entry를 미리 준비(warming)하는 것이 낭비되기 때문입니다. 공유 store에는 그런 문제가 없으므로 expire까지 제공할 수 있습니다.

Dropping entries earlier is a policy choice rather than a requirement. The built-in handler drops at revalidate because warming a replacement is wasted work when an in-memory entry is likely to be evicted before anything reads it. A shared store has no such problem and can serve until expire.

다만 eviction은 직접 처리해야 합니다. Next.js는 store에서 아무것도 삭제하지 않으므로, 다시 읽히지 않는 entry를 회수하는 메커니즘을 사용하세요. expire에서 파생한 TTL이나, built-in handler에 있는 것과 같은 크기 제한 LRU가 그 예입니다. entry를 제공할 때 age를 확인하는 것은 eviction이 아닙니다. 그 방식은 여전히 읽히고 있는 key에만 도달하기 때문입니다.

Eviction is yours, though. Next.js never deletes from your store, so use a mechanism that reclaims entries nobody reads again: a TTL derived from expire, or a size-bounded LRU like the one in the built-in handler. Checking the age of an entry as you serve it is not eviction, because it only ever reaches the keys that are still being read.

invalidation은 두 timing과 별개입니다. tag를 통해 entry가 오래되었음을 알게 되면 두 가지 선택지가 있습니다:

Invalidation is separate from both timings. When a tag tells you an entry is out of date, you have two options:

  • undefined를 반환합니다. entry는 없는 것으로 간주되고, Next.js가 지금 다시 생성합니다.
  • revalidate: -1로 entry를 반환합니다. 음수 revalidate는 항상 과거에 해당하므로, Next.js는 entry를 제공하고 background에서 다시 생성합니다.
  • Return undefined. The entry counts as missing, and Next.js regenerates it now.
  • Return the entry with revalidate: -1. Next.js serves it and regenerates in the background, because a negative revalidate always lies in the past.

이런 invalidation이 어디서 오는지는 Soft Tags와 Distributed Tag Coordination을 참고하세요.

See Soft Tags and Distributed Tag Coordination for where those invalidations come from.

hit될 때마다 저장된 data를 새 stream으로 감싸서 반환하세요. set()에서 받은 stream을 반환하면 안 됩니다.

Wrap your stored data in a new stream on every hit, never the stream you received in set().

const cacheHandler = {
  async get(cacheKey, softTags) {
    const entry = cache.get(cacheKey)
    if (!entry) return undefined

    // No age check: Next.js compares `timestamp` against `expire` itself.
    // `entry.value` holds the stored bytes, so wrap them in a fresh stream
    return {
      ...entry,
      value: new ReadableStream({
        start(controller) {
          controller.enqueue(entry.value)
          controller.close()
        },
      }),
    }
  },
}

refreshTags()

request마다 한 번, 이 handler 종류에 대한 첫 cache read 전에 호출되어 handler가 외부 service에서 tag state를 동기화할 수 있게 합니다.

Called once per request, before the first cache read for this handler's kind, so the handler can sync tag state from an external service.

refreshTags(): Promise<void>

Promise<void>를 반환합니다.

Returns Promise<void>.

in-memory cache에서는 아무 작업도 하지 않아도(no-op) 됩니다. distributed cache에서는 이를 사용해 외부 service나 database에서 tag state를 읽어, 이 instance가 자체 store에서 무언가를 제공하기 전에 다른 instance가 수행한 invalidation을 알 수 있게 하세요. 이 handler에서 아무것도 읽지 않는 request는 이 method를 호출하지 않습니다.

For in-memory caches, this can be a no-op. For distributed caches, use it to read tag state from an external service or database, so this instance learns about invalidations made by the others before it serves anything from its own store. A request that reads nothing from this handler never calls it.

const cacheHandler = {
  async refreshTags() {
    // For in-memory cache, no action needed
    // For distributed cache, sync tag state from external service
  },
}

getExpiration()

tag 집합에 대한 최대 revalidation timestamp를 가져옵니다.

Get the maximum revalidation timestamp for a set of tags.

getExpiration(tags: string[]): Promise<number>
ParameterTypeDescription
tagsstring[]expiration을 확인할 tag 배열.
ParameterTypeDescription
tagsstring[]Array of tags to check expiration for.

반환값:

Returns:

  • tag가 한 번도 revalidate되지 않았다면 0
  • 가장 최근 revalidation을 나타내는 timestamp(millisecond 단위)
  • soft tag를 대신 get method에서 확인해야 함을 나타내는 Infinity

tag revalidation timestamp를 추적하지 않는다면 0을 반환하세요. 그렇지 않다면 제공된 모든 tag 중 가장 최근의 revalidation timestamp를 찾으세요. soft tag 확인을 get method에서 처리하고 싶다면 Infinity를 반환하세요.

If you're not tracking tag revalidation timestamps, return 0. Otherwise, find the most recent revalidation timestamp across all the provided tags. Return Infinity if you prefer to handle soft tag checking in the get method.

const cacheHandler = {
  async getExpiration(tags) {
    // Return 0 if not tracking tag revalidation
    return 0

    // Or return the most recent revalidation timestamp
    // return Math.max(...tags.map(tag => tagTimestamps.get(tag) || 0));
  },
}

durations의 존재 여부로 어떤 종류의 invalidation인지 알 수 있습니다:

Whether durations is present tells you which kind of invalidation this is:

  • Absent: 즉시 invalidate합니다. 이 tag를 가진 entry는 다시 제공되면 안 됩니다. updateTag()와 인자가 하나인 revalidateTag()가 이 경로를 따르며, 호출한 쪽은 자신의 다음 read가 miss되기를 기대합니다.
  • Present: tag는 지금 stale 상태가 되지만, 이 tag를 가진 entry는 durations.expire초가 지날 때까지 background에서 refresh되는 동안 계속 제공될 수 있습니다. revalidateTag(tag, 'max')가 이 경로를 따릅니다.
  • Absent: invalidate immediately. Entries carrying these tags should not be served again. updateTag() and a single-argument revalidateTag() take this path, and the caller expects its own next read to miss.
  • Present: the tags go stale now, but entries carrying them may still be served while they refresh in the background, until durations.expire seconds have passed. revalidateTag(tag, 'max') takes this path.

Promise<void>를 반환합니다.

Returns Promise<void>.

handler는 각 tag가 언제 invalidate되었는지 기록해야 합니다. get()은 이 시간을 entry의 timestamp와 비교하고, getExpiration()은 soft tags에 대해 같은 작업을 합니다. soft tag는 entry의 tags에 저장되지 않으므로, tag를 가진 entry를 삭제하는 것만으로는 revalidatePath()를 처리할 수 없습니다.

Your handler should record when each tag was invalidated. get() compares those times against an entry's timestamp, and getExpiration() does the same for soft tags. Soft tags are not stored in an entry's tags, so deleting the entries that carry a tag does not cover revalidatePath().

const cacheHandler = {
  async updateTags(tags, durations) {
    const now = Date.now()
    for (const tag of tags) {
      const timestamps = tagTimestamps.get(tag) ?? {}
      if (durations) {
        // Serve while refreshing, and expire after `durations.expire` seconds
        timestamps.stale = now
        if (durations.expire !== undefined) {
          timestamps.expired = now + durations.expire * 1000
        }
      } else {
        // Expire immediately
        timestamps.expired = now
      }
      tagTimestamps.set(tag, timestamps)
    }
  },
}

Soft Tags

soft tag는 Next.js가 route path를 기반으로 자동 생성하는 암묵적 tag입니다. path의 모든 segment는 layout tag를 받고, leaf route 자체도 tag를 받습니다. 예를 들어 /blog/hello route는 /layout, /blog/layout, /blog/hello/layout, /blog/hello에 대한 soft tag를 생성합니다. 이 tag들은 내부적으로 _N_T_ prefix가 붙습니다.

Soft tags are implicit tags that Next.js automatically generates based on the route path. Every segment in the path gets a layout tag, plus the leaf route itself. For example, the route /blog/hello generates soft tags for /layout, /blog/layout, /blog/hello/layout, and /blog/hello. These tags are prefixed internally with _N_T_.

soft tag 덕분에 revalidatePath()가 동일한 tag 기반 cache system을 통해 동작할 수 있습니다. revalidatePath('/blog/hello')가 호출되면, 해당 path의 soft tag와 연결된 모든 cache entry가 invalidate됩니다.

Soft tags enable revalidatePath() to work through the same tag-based cache system. When revalidatePath('/blog/hello') is called, it invalidates all cache entries associated with that path's soft tags.

cache handler API에서 soft tag는 softTags parameter로 get() method에 전달됩니다. handler는 cache entry의 timestamp 이후에 soft tag 중 하나라도 invalidate되었는지(getExpiration() 또는 직접 timestamp 비교를 통해) 확인해야 합니다.

In the cache handler API, soft tags are passed to the get() method as the softTags parameter. Your handler should check whether any soft tag has been invalidated (via getExpiration() or direct timestamp comparison) after the cache entry's timestamp.

invalidation이 entry보다 최근이라면, get()에서 설명한 선택지 중 하나를 사용해 entry가 오래되었음을 알리세요. built-in handler는 두 가지를 모두 사용합니다. expire된 tag에는 undefined를, stale된 tag에는 revalidate: -1을 반환합니다.

If an invalidation is more recent than the entry, report the entry as out of date using either option described in get(). The built-in handler uses both: it returns undefined for an expired tag, and revalidate: -1 for a stale one.

Distributed Tag Coordination분산 tag 조정

여러 Next.js instance를 실행할 때는 instance 간에 tag invalidation을 조정해야 합니다. 기본 in-memory handler는 tag를 local에서만 추적하므로, 한 instance에서 revalidateTag()를 호출해도 다른 instance에는 영향을 주지 않습니다.

When running multiple Next.js instances, tag invalidation must be coordinated across instances. The default in-memory handler only tracks tags locally, so calling revalidateTag() on one instance does not affect others.

instance 간에 tag를 조정하려면:

To coordinate tags across instances:

  1. updateTags(): revalidateTag()가 호출될 때 실행됩니다. handler는 invalidation timestamp를 공유 storage에 기록해야 합니다.
  2. refreshTags(): request마다 한 번, 이 handler에서 처음 read하기 전에 실행됩니다. handler는 공유 storage에서 최근 invalidation event를 읽고 local tag state를 업데이트해야 합니다.
  3. getExpiration(): 제공된 모든 tag 중 가장 최근의 revalidation timestamp를 반환합니다. 기본 구현은 Math.max(...timestamps, 0)을 반환합니다.
  1. updateTags() is called when revalidateTag() is invoked. Your handler should write the invalidation timestamp to shared storage.
  2. refreshTags() runs once per request, before the first read from this handler. Your handler should read recent invalidation events from shared storage and update its local tag state.
  3. getExpiration() returns the most recent revalidation timestamp across all provided tags. The default implementation returns Math.max(...timestamps, 0).

다음은 Redis를 사용한 distributed tag coordination 예제입니다:

Here's an example using Redis for distributed tag coordination:

JScache-handlers/distributed-tags.js
const { createClient } = require('redis')

const client = createClient({ url: process.env.REDIS_URL })
client.connect()

// Local cache of tag timestamps, synced via refreshTags
const localTagTimestamps = new Map()

module.exports = {
  // ... get() and set() methods ...

  async refreshTags() {
    // Sync tag invalidation timestamps from Redis
    // Using a dedicated set to track tag keys avoids scanning the keyspace
    const tagKeys = await client.sMembers('revalidated-tags')
    if (tagKeys.length > 0) {
      const values = await client.mGet(tagKeys.map((k) => `tag:${k}`))
      for (let i = 0; i < tagKeys.length; i++) {
        localTagTimestamps.set(tagKeys[i], Number(values[i]))
      }
    }
  },

  async getExpiration(tags) {
    const timestamps = tags.map((tag) => localTagTimestamps.get(tag) || 0)
    return Math.max(...timestamps, 0)
  },

  async updateTags(tags, durations) {
    const now = Date.now()
    const pipeline = client.multi()
    for (const tag of tags) {
      pipeline.set(`tag:${tag}`, String(now))
      pipeline.sAdd('revalidated-tags', tag)
      localTagTimestamps.set(tag, now)
    }
    await pipeline.exec()
  },
}

Error HandlingError 처리

cache 작업은 방어적으로 구현해야 합니다:

Cache operations should be implemented defensively:

  • set() failure: set()은 response stream이 이미 흐르기 시작한 뒤 비동기로 호출되므로, response는 여전히 사용자에게 제공됩니다. cache entry는 손실되고, 다음 request에서 새로 render됩니다. 그래도 error는 직접 catch하세요. reject된 set()은 request의 pending revalidation 작업에 합류하며, render error가 아니라 실패한 background task로 드러납니다.
  • get() failure: handler는 내부 error를 catch하고 undefined("cache miss" 신호)를 반환해야 합니다. framework는 get()을 try/catch로 감싸지 않으므로, get()에서 처리되지 않은 exception은 render error로 전파됩니다.
  • Partial writes: cache entry가 부분적으로 기록된 뒤 읽히면 동작이 정의되지 않습니다. 부분 entry를 제공하지 않도록 atomic write나 write-then-rename pattern을 사용하세요.
  • set() failure: the response is still served to the user because set() is called asynchronously after the response stream is already flowing. The cache entry is lost, and the next request triggers a fresh render. Catch your own errors even so: a rejected set() joins the request's pending revalidation work, where it surfaces as a failed background task instead of a render error.
  • get() failure: your handler should catch internal errors and return undefined (the "cache miss" signal). The framework does not wrap get() in a try/catch, so an unhandled exception from get() will propagate as a render error.
  • Partial writes: if a cache entry is partially written and then read, the behavior is undefined. Use atomic writes or a write-then-rename pattern to avoid serving partial entries.

In-memory handler for learning and debugging학습 및 debugging용 in-memory handler

이 handler는 entry를 Map에 보관하므로, Next.js가 무엇을 저장하고 tag가 이를 어떻게 invalidate하는지 log로 남기거나 살펴보기에 좋습니다. process마다 실행되며 eviction이 없습니다. built-in handler도 in-memory 방식이며, 크기 제한 LRU와 error 처리가 추가되어 있습니다.

This handler keeps entries in a Map, which makes it a place to log or inspect what Next.js stores and how tags invalidate it. It runs per process and has no eviction. The built-in handler is also in memory, and adds a size-bounded LRU and error handling.

JScache-handlers/memory-handler.js
// Entries hold the serialized bytes, never the stream they arrived on
const cache = new Map()
const pendingSets = new Map()
// Tag invalidation times in milliseconds: { stale, expired }
const tagTimestamps = new Map()

function streamFromBytes(bytes) {
  return new ReadableStream({
    start(controller) {
      controller.enqueue(bytes)
      controller.close()
    },
  })
}

module.exports = {
  async get(cacheKey, softTags) {
    // Wait for any pending set operation to complete
    const pendingPromise = pendingSets.get(cacheKey)
    if (pendingPromise) {
      await pendingPromise
    }

    const entry = cache.get(cacheKey)
    if (!entry) {
      return undefined
    }

    // No age check: Next.js compares `timestamp` against `expire` itself.
    // Soft tags are checked by Next.js through `getExpiration()`.
    // This `Map` also has no eviction, which a real handler needs.
    let revalidate = entry.revalidate
    for (const tag of entry.tags) {
      const { stale = 0, expired = 0 } = tagTimestamps.get(tag) ?? {}
      if (expired > entry.timestamp && expired <= Date.now()) {
        return undefined
      }
      if (stale > entry.timestamp) {
        revalidate = -1
      }
    }

    // Every hit gets its own stream over the stored bytes
    return { ...entry, revalidate, value: streamFromBytes(entry.value) }
  },

  async set(cacheKey, pendingEntry) {
    // Create a promise to track this set operation
    let resolvePending
    const pendingPromise = new Promise((resolve) => {
      resolvePending = resolve
    })
    pendingSets.set(cacheKey, pendingPromise)

    try {
      // Wait for the entry to be ready
      const entry = await pendingEntry

      // An in-memory store buffers the stream. Storing the stream itself, or
      // a branch of it, keeps the request that produced the entry alive.
      const value = new Uint8Array(
        await new Response(entry.value).arrayBuffer()
      )

      cache.set(cacheKey, { ...entry, value })
    } finally {
      resolvePending()
      pendingSets.delete(cacheKey)
    }
  },

  async refreshTags() {
    // Tag state lives in this process, so there is nothing to sync
  },

  async getExpiration(tags) {
    return Math.max(
      ...tags.map((tag) => tagTimestamps.get(tag)?.expired ?? 0),
      0
    )
  },

  async updateTags(tags, durations) {
    const now = Date.now()
    for (const tag of tags) {
      const timestamps = tagTimestamps.get(tag) ?? {}
      if (durations) {
        // Serve while refreshing, and expire after `durations.expire` seconds
        timestamps.stale = now
        if (durations.expire !== undefined) {
          timestamps.expired = now + durations.expire * 1000
        }
      } else {
        // Expire immediately
        timestamps.expired = now
      }
      tagTimestamps.set(tag, timestamps)
    }
  },
}

External storage pattern외부 storage pattern

Redis나 database 기반 handler는 각 entry를 serialize해야 합니다. set()에서 stream을 모두 읽어 들이고(drain), get()에서 저장된 byte로 stream을 다시 만드세요:

A handler backed by Redis or a database must serialize each entry. Drain the stream in set(), and rebuild one from the stored bytes in get():

JScache-handlers/redis-handler.js
const { createClient } = require('redis')

const client = createClient({ url: process.env.REDIS_URL })
client.connect()

module.exports = {
  async get(cacheKey, softTags) {
    // Retrieve from Redis
    const stored = await client.get(cacheKey)
    if (!stored) return undefined

    // Deserialize the entry
    const data = JSON.parse(stored)

    // Reconstruct the ReadableStream from stored data
    return {
      value: new ReadableStream({
        start(controller) {
          controller.enqueue(Buffer.from(data.value, 'base64'))
          controller.close()
        },
      }),
      tags: data.tags,
      stale: data.stale,
      timestamp: data.timestamp,
      expire: data.expire,
      revalidate: data.revalidate,
    }
  },

  async set(cacheKey, pendingEntry) {
    const entry = await pendingEntry

    // Read the stream to get the data
    const reader = entry.value.getReader()
    const chunks = []

    try {
      while (true) {
        const { done, value } = await reader.read()
        if (done) break
        chunks.push(value)
      }
    } finally {
      reader.releaseLock()
    }

    // Combine chunks and serialize for Redis storage
    const data = Buffer.concat(chunks.map((chunk) => Buffer.from(chunk)))

    await client.set(
      cacheKey,
      JSON.stringify({
        value: data.toString('base64'),
        tags: entry.tags,
        stale: entry.stale,
        timestamp: entry.timestamp,
        expire: entry.expire,
        revalidate: entry.revalidate,
      }),
      // `EX` needs a positive integer.
      // By definition `expire: Infinity` ("never expire")
      // maps to no TTL at all, so omit `EX` and let Redis persist the key.
      Number.isFinite(entry.expire)
        ? { EX: Math.max(1, Math.ceil(entry.expire)) }
        : {}
    )
  },

  // refreshTags(), getExpiration(), and updateTags() also need shared state.
  // See Distributed Tag Coordination for that half of the handler.
}
