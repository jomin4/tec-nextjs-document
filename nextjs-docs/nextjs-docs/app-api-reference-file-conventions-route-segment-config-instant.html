instantinstant

instant route segment config는 이 segment로의 navigation이 즉시(instant) UI를 만들어 내는지를 Next.js가 어떻게 검증할지 제어합니다.

The instant route segment config controls how Next.js validates whether a navigation into this segment would produce an instant UI.

Next.js는 prefetching을 사용해 현재 page에 있는 모든 앱 내부 link의 navigation을 미리 load합니다. 하지만 client-side data fetching이나 server에서 부분적으로 prerender된 결과 때문에 navigation이 UI를 즉시 업데이트하지 못할 수 있습니다. 빠르게 느껴지는 navigation을 만들 수 있도록, instant를 사용하면 설정한 segment를 거치는 navigation에서 무엇을 기대하는지 Next.js에 알려 줄 수 있습니다. 예를 들어 이 segment로의 navigation은 외부에서 load되는 데이터를 기다리지 않고 즉시 rendering되는 UI를 만들어야 한다고 표시할 수 있습니다. navigation이 즉시 이루어질 필요가 없다고 표시할 수도 있습니다.

Next.js uses prefetching to preload navigations for all in-app links on the current page. However, client-side data fetching or partially prerendered results from the server can lead to navigations that don't update the UI immediately. To help you build fast-feeling navigations, instant lets you tell Next.js what to expect from navigations through the configured segment. For instance, you can indicate that navigations into this segment should produce a UI that renders instantly without waiting on any externally loaded data. You can also indicate that navigations aren't expected to be instant.

segment가 instant UI를 기대하도록 설정되면, Next.js는 navigation이 UI를 즉시 업데이트하지 못하게 막는 애플리케이션 코드를 찾아서 보여 줍니다. 처음부터 끝까지 따라 하는 설명은 Instant Navigation guide를 참고하세요.

When a segment is configured to expect an instant UI, Next.js surfaces any code in your application that would block the navigation from updating the UI immediately. See the Instant Navigation guide for an end-to-end walkthrough.

Good to know
  • instant export는 cacheComponents가 활성화되어 있을 때만 동작합니다.
  • instant는 Client Component에서 사용할 수 없습니다. 사용하면 error가 발생합니다.
  • Next.js는 development에서 prefetch를 수행하지 않으므로, navigation이 production만큼 즉각적으로 느껴지지 않을 수 있습니다. validation은 prefetching이 활성화된 next start에서 일어날 동작을 반영합니다.
  • The instant export only works when cacheComponents is enabled.
  • instant cannot be used in Client Components. It will throw an error.
  • Next.js does not perform prefetches in development, so navigations may not feel as instant as they will in production. Validation reflects what will happen during next start, where prefetching is enabled.

Reference

이 export는 다음 값을 받습니다:

The export accepts:

  • true: 전역으로 설정된 수준으로 segment의 validation을 활성화합니다(Configuring validation defaults 참고). framework default에서는 validation이 development에서만 실행되며 dev overlay에 error를 표시합니다.
  • false: segment를 validation에서 제외합니다(Disabling instant 참고).
  • 객체: 추가 option과 함께 활성화합니다. level을 참고하세요.
  • true: Opts the segment into validation at whatever level is configured globally (see Configuring validation defaults). With the framework defaults, validation runs in development only and surfaces errors in the dev overlay.
  • false: Opts the segment out (see Disabling instant).
  • An object: Opts in with additional options. See level.

level

이 segment에서 validation이 실행되는 심각도(severity)를 설정합니다.

Sets the severity at which validation runs for this segment.

TSpage.tsx
export const instant = {
  level: 'warning',
}
  • 'warning': development에서만 검증합니다. error는 dev overlay에 표시되며 build에는 영향을 주지 않습니다.
  • 'warning': Validates in development only. Errors appear in the dev overlay; the build is unaffected.

앞으로 build 중 validation을 지원하는 validation level이 추가될 예정입니다. experimental validation mode를 활성화하는 경우가 아니라면, 사용할 수 있는 level이 "warning" 하나뿐이므로 level을 지정할 필요가 없습니다.

In the future a validation level that supports validation during build will be supported. Unless you are enabling experimental validation modes there is no need to specify level since the only level available is "warning".

level을 생략하거나 instant = true를 사용하면, segment는 전역으로 설정된 수준으로 검증됩니다. Configuring validation defaults를 참고하세요.

When level is omitted (or instant = true is used), the segment is validated at whatever level is configured globally — see Configuring validation defaults.

Disabling instantinstant 비활성화하기

layout이나 page에 false를 설정하면 이 segment로 navigation할 때 block되어도 괜찮다는 것을 나타냅니다.

Set false on a layout or page to indicate that this segment is allowed to block when navigating to it.

더 깊은 page는 instant여야 하지만 상위 segment는 그럴 수 없을 때 유용합니다. 예를 들어 공유 layout은 즉시 load될 수 없지만 이 layout 아래의 page들로는 즉시 navigation할 수 있다고 보장하고 싶다면, page에는 instant = true를, 공유 layout에는 instant = false를 설정하면 됩니다.

This is useful when a deeper page should be instant but an ancestor can't be. For instance, if a shared layout cannot load instantly but you still want to assert that pages beneath this layout can be navigated to instantly, you can ensure that the pages have instant = true while the shared layout has instant = false.

TSapp/tabs/layout.tsx
export const instant = false
TSapp/tabs/[tab]/page.tsx
export const instant = true

외부에서 tab으로 들어오는 navigation은 layout에서 block되어도 허용됩니다. tab 사이의 navigation은 instant UI인지 검증됩니다.

Navigations from outside into a tab are allowed to block at the layout. Navigations between tabs are validated for instant UI.

상위 segment가 blocking 작업을 한다는 이유만으로 instant page의 상위 segment에 false를 추가할 필요는 없습니다. 상위의 instant = true가 하위 segment를 강제로 검증하지는 않으며, 상위 segment를 설정하지 않은 채로 두어도 괜찮습니다. 더 깊은 page를 instant로 설정했고, blocking 상위 segment를 거치는 navigation을 예외로 두어야 할 때만 false를 사용하세요.

You don't need to add false to ancestors of an instant page just because they do something blocking — a higher-up instant = true doesn't force its descendants to validate, and leaving an ancestor unconfigured is fine. Reach for false only when you've configured a deeper page as instant and need to exempt navigations that pass through a blocking ancestor.

Disabling static shell validationstatic shell validation 비활성화하기

Cache Components는 앱의 각 page가 prerender 시점에 비어 있지 않은 static shell을 만들어 내는지도 검증합니다. route를 이 validation에서 제외하려면 route tree에서 가장 위에 있는 instant config가 false가 되도록 하세요. static shell 검사에서는 tree 위쪽의 false가 더 깊은 곳의 어떤 true보다 우선합니다.

Cache Components also validates that each page in your app produces a non-empty static shell at prerender time. To opt a route out of this validation, ensure the highest instant config in the route's tree is false — a false higher in the tree takes precedence over any deeper true for the static-shell check.

root layout에 false를 설정하면 앱 전체의 static shell validation이 비활성화됩니다. 앱의 나머지 부분이 계속 검증되도록, false는 가능한 한 낮은 곳에, 즉 제외하려는 route를 덮을 만큼만 높은 곳에 두세요.

Setting false on the root layout disables static shell validation for the entire app. Place the false as low as possible — only as high as needed to cover the routes you want to opt out — so the rest of the app keeps validating.

How validation worksvalidation 동작 방식

instant는 route의 모든 공유 layout 경계에서 validation을 실행합니다. validation은 development 중(page load와 HMR 업데이트 시)에 실행되며 dev error overlay에 error를 표시합니다.

instant triggers validation at every shared layout boundary in the route. Validation runs during development (on page loads and HMR updates) and surfaces errors in the dev error overlay.

각 error는 navigation을 block할 component를 알려 줍니다. 보통 use cache로 데이터를 cache하거나 <Suspense> boundary로 감싸면 해결됩니다.

Each error identifies the component that would block navigation. The fix is usually to cache the data with use cache or wrap it in a <Suspense> boundary.

How instant differs from ensureStaticinstant와 ensureStatic의 차이

instant는 navigation이 UI를 즉시 보여 주는지를 검증합니다. ensureStatic은 선택한 server rendering output이 request마다 rendering되지 않고 static이도록 요구합니다. route가 완전히 static이어도 navigation을 block할 수 있습니다. 예를 들어 Client Component가 브라우저에서 데이터를 load하는 경우입니다.

instant validates whether a navigation shows UI immediately. ensureStatic requires selected server-rendered output to be static instead of rendered for each request. A route can be fully static and still block a navigation, for example when a Client Component loads data in the browser.

Configuring validation defaultsvalidation default 설정하기

기본적으로(validationLevel: 'warning') Cache Components 앱은 development에서 모든 Page와 Default segment를 검증합니다. experimental.instantInsights.validationLevel config로 이 동작을 조정할 수 있습니다. 예를 들어 instant로 명시적으로 opt-in한 segment만 검증하도록 제한할 수 있습니다.

By default (validationLevel: 'warning'), Cache Components apps validate every Page and Default segment in development. The experimental.instantInsights.validationLevel config tunes this behavior — for example, to limit validation to segments that opt in explicitly via instant.

JSnext.config.js
module.exports = {
  experimental: {
    instantInsights: {
      validationLevel: 'warning',
    },
  },
}

지원되는 level은 다음과 같습니다:

The supported levels are:

  • 'warning' (framework default): 모든 Page와 Default segment가 암묵적으로 warning level에서 검증됩니다(dev 전용).
  • 'manual-warning': 명시적인 instant가 있는 segment만 warning level에서 검증됩니다(dev 전용).
  • 'warning' (framework default): Every Page and Default segment is implicitly validated at warning level (dev only).
  • 'manual-warning': Only segments with an explicit instant are validated, at warning level (dev only).

segment에 instant = false를 설정하면 그 segment는 validation에서 완전히 제외됩니다.

Setting instant = false on a segment opts it out of validation entirely.

Good to know
  • 앞으로 framework default가 더 높은 validation level을 적용하도록 바뀔 수 있습니다. 이 기능은 experimental이므로 그런 변경은 breaking change로 간주되지 않습니다. 특정 동작을 고정하려면 validationLevel을 명시적으로 설정하세요.
  • framework가 합성한 error route(/_global-error, /_not-found)는 암묵적 validation에서 제외됩니다. 이 route들을 검증하려면 instant로 명시적으로 opt-in하세요.
  • The framework default may change in future versions to opt users into higher levels of validation. Because this feature is experimental, that change is not considered a breaking change. To pin a specific behavior, set validationLevel explicitly.
  • Framework-synthesized error routes (/_global-error, /_not-found) are excluded from implicit validation. To validate them, opt in explicitly with instant.

Inspecting loading statesloading state 살펴보기

Cache Components가 활성화되어 있으면 Navigation Inspector를 사용할 수 있습니다:

The Navigation Inspector is available when Cache Components is enabled:

JSnext.config.js
module.exports = {
  cacheComponents: true,
}

Next.js DevTools를 열고 Navigation Inspector를 선택한 다음 Pause on navigations를 켜세요. toggle이 켜져 있는 동안에는:

Open the Next.js DevTools and select Navigation Inspector, then turn on Pause on navigations. While the toggle is on:

  • page를 새로고침하면 dynamic 데이터가 stream되기 전, route용으로 생성된 초기 static UI가 고정됩니다.
  • link를 클릭하면 목적지 route의 prefetch된 UI가 고정됩니다.
  • Refresh the page to freeze the initial static UI generated for the route, before any dynamic data streams in.
  • Click a link to freeze the prefetched UI for the destination route.

UI가 고정되면 Resume을 클릭해 현재 navigation을 마무리하세요. toggle은 켜진 상태로 유지되므로 다음 새로고침이나 link 클릭도 일시 정지됩니다. 작업이 끝나면 toggle을 끄세요. page 새로고침과 link 클릭을 모두 사용해, 첫 방문과 navigation 모두에서 loading state가 제대로 보이는지 확인하세요.

When the UI is frozen, click Resume to let the current navigation finish. The toggle stays on, so the next refresh or link click pauses too. Turn it off when you are done. Use both page refreshes and link clicks to check that your loading states look right on first visit and on navigation.

Testing instant navigationinstant navigation 테스트하기

@next/playwright package는 callback이 instant UI를 대상으로 실행되는 동안 dynamic 콘텐츠를 보류하는 instant() helper를 export합니다. testing API는 development에서 자동으로 사용할 수 있습니다. production build에서는 test build에서 experimental.exposeTestingApiInProductionBuild를 활성화하세요. 전체 예시는 guide를 참고하세요.

The @next/playwright package exports an instant() helper that holds back dynamic content while the callback runs against the instant UI. The testing API is available automatically in development. For a production build, enable experimental.exposeTestingApiInProductionBuild in the test build. See the guide for a full example.

import { instant } from '@next/playwright'

Known issue: shared cookie across projects알려진 문제: 프로젝트 간 cookie 공유

DevTools는 dynamic 콘텐츠를 보류하고 page를 instant UI 상태로 고정하기 위해 next-instant-navigation-testing cookie를 사용합니다. cookie는 port가 아니라 domain 단위로 적용되므로, 같은 domain(보통 localhost)에서 여러 프로젝트를 실행하면 cookie가 프로젝트 간에 공유되어 예상치 못한 동작이 생길 수 있습니다. 문제를 피하려면 프로젝트를 전환할 때 cookie를 지우거나 Navigation Inspector panel을 닫으세요.

The DevTools use a next-instant-navigation-testing cookie to hold back dynamic content and freeze the page at the instant UI. Because cookies are scoped to the domain and not the port, running multiple projects on the same domain (typically localhost) means the cookie is shared across them and can cause unexpected behavior. Clear the cookie or close the Navigation Inspector panel when switching between projects to avoid issues.

Good to know

이 문제는 기능을 stable로 만드는 과정에서 수정될 예정입니다.

This will be fixed as part of stabilizing the feature.
