cacheLifecacheLife

cacheLife 함수는 함수나 component의 cache 수명(lifetime)을 설정하는 데 사용합니다. use cache directive와 함께, 해당 함수나 component의 scope 안에서 사용해야 합니다.

The cacheLife function is used to set the cache lifetime of a function or component. It should be used alongside the use cache directive, and within the scope of the function or component.

Usage사용법

Basic setup기본 설정

cacheLife를 사용하려면 먼저 next.config.js 파일에서 cacheComponents flag를 활성화하세요:

To use cacheLife, first enable the cacheComponents flag in your next.config.js file:

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
}

export default nextConfig
const nextConfig = {
  cacheComponents: true,
}

module.exports = nextConfig

cacheLife는 cache directive scope 안에서만 사용할 수 있습니다.

cacheLife can only be used within a cache directive scope.

파일 레벨 또는 async 함수나 component의 맨 위에 cache directive(예: use cache)를 추가하세요.

Add a cache directive (for example, use cache) at the file level or at the top of an async function or component.

cacheLife는 module scope에서 사용할 수 없습니다. 파일의 최상위 레벨에서 호출하면 error가 발생합니다.

cacheLife cannot be used at module scope. Calling it at the top level of a file will throw an error.

Good to know
  • 호출 위치에서 동작이 명확하도록 모든 use cache scope에 cacheLife를 설정하는 것을 권장합니다. 생략하면 수명이 암묵적으로 정해지며(default profile 적용), 예를 들어 nested cached scopes에서처럼 동작을 파악하기 어려워집니다.
  • caching이 정의된 같은 함수나 component 안에서 cacheLife를 호출하세요. cache 동작이 명시적이고 파악하기 쉽도록 공유 유틸리티로 추상화하지 마세요.
  • cacheLife를 호출한다면 함수 호출당 한 번만 실행되도록 하세요. 서로 다른 control flow 분기에서 호출할 수는 있지만, request당 하나만 실행되어야 합니다. conditional cache lifetimes 예시를 참고하세요.
  • We recommend setting a cacheLife in every use cache scope so its behavior is clear at the call site. Omitting it leaves the lifetime implicit (the default profile applies), which makes it harder to reason about, for example in nested cached scopes.
  • Call cacheLife in the same function or component where caching is defined. Avoid abstracting it into shared utilities so the cache behavior remains explicit and easy to reason about.
  • If you call cacheLife, ensure only one call executes per function invocation. You can call it in different control flow branches, but only one should run per request. See the conditional cache lifetimes example.

Using preset profilesPreset profile 사용하기

Next.js는 일반적인 caching 요구를 충족하는 preset cache profile을 제공합니다. 각 profile은 세 가지 요소의 균형을 맞춥니다:

Next.js provides preset cache profiles that cover common caching needs. Each profile balances three factors:

  • 사용자가 업데이트 확인 없이 cache된 콘텐츠를 보는 기간 (client-side)
  • 서버에서 새 콘텐츠가 생성되는 빈도
  • 오래된 콘텐츠가 완전히 만료되는 시점
  • How long users see cached content without checking for updates (client-side)
  • How often fresh content is generated on the server
  • When old content expires completely

콘텐츠가 얼마나 자주 바뀌는지에 따라 profile을 선택하세요:

Choose a profile based on how frequently your content changes:

  • seconds - 실시간 데이터 (주가, 실시간 경기 점수)
  • minutes - 자주 업데이트됨 (소셜 피드, 뉴스)
  • hours - 하루에 여러 번 업데이트 (상품 재고, 날씨)
  • days - 매일 업데이트 (블로그 글, 기사)
  • weeks - 매주 업데이트 (팟캐스트, 뉴스레터)
  • max - 거의 바뀌지 않음 (법률 페이지, 보관된 콘텐츠)
  • seconds - Real-time data (stock prices, live scores)
  • minutes - Frequently updated (social feeds, news)
  • hours - Multiple daily updates (product inventory, weather)
  • days - Daily updates (blog posts, articles)
  • weeks - Weekly updates (podcasts, newsletters)
  • max - Rarely changes (legal pages, archived content)

cacheLife를 import하고 profile 이름을 전달하세요:

Import cacheLife and pass a profile name:

TSapp/blog/page.tsx
'use cache'
import { cacheLife } from 'next/cache'

export default async function BlogPage() {
  cacheLife('days') // Blog content updated daily

  const posts = await getBlogPosts()
  return <div>{/* render posts */}</div>
}

profile 이름은 Next.js에게 함수 전체 출력을 어떻게 cache할지 알려 줍니다. cacheLife를 호출하지 않으면 default profile이 사용됩니다. 시간 관련 자세한 내용은 preset cache profiles를 참고하세요.

The profile name tells Next.js how to cache the entire function's output. If you don't call cacheLife, the default profile is used. See preset cache profiles for timing details.

Reference

Cache profile propertiesCache profile 속성

Cache profile은 세 가지 시간 속성으로 caching 동작을 제어합니다:

Cache profiles control caching behavior through three timing properties:

  • stale: client가 서버 확인 없이 cache된 데이터를 사용할 수 있는 기간
  • revalidate: 이 시간이 지나면 다음 request가 background refresh를 trigger함
  • expire: 이 시간 동안 request가 없으면 다음 request는 새 콘텐츠를 기다림
  • stale: How long the client can use cached data without checking the server
  • revalidate: After this time, the next request will trigger a background refresh
  • expire: After this time with no requests, the next one waits for fresh content

stale

Client-side: client가 서버 확인 없이 cache된 데이터를 사용할 수 있는 기간입니다.

Client-side: How long the client can use cached data without checking the server.

이 기간 동안 client-side router는 network request 없이 cache된 콘텐츠를 즉시 표시합니다. 이 기간이 만료되면 router는 다음 navigation이나 request 때 서버에 확인해야 합니다. client cache 덕분에 페이지가 즉시 로드되지만, 데이터가 오래되었을 수 있습니다.

During this time, the client-side router displays cached content immediately without any network request. After this period expires, the router must check with the server on the next navigation or request. This provides instant page loads from the client cache, but data may be outdated.

  • 생략하면 default profile의 stale 값(5분, staleTimes 참고)이 기본값이 됩니다
  • 콘텐츠가 route의 App Shell에 포함될 수 있는지도 결정합니다. Prerendering behavior를 참고하세요.
  • If omitted, defaults to the default profile's stale value (5 minutes, see staleTimes)
  • Also determines whether the content can be part of the route's App Shell. See Prerendering behavior.
cacheLife({ stale: 300 }) // 5 minutes

revalidate

서버가 background에서 cache된 콘텐츠를 다시 생성하는 빈도입니다.

How often the server regenerates cached content in the background.

  • 이 기간 이후 request가 도착하면 서버는:
    1. cache된 버전을 즉시 제공합니다 (있는 경우)
    2. background에서 콘텐츠를 다시 생성합니다
    3. 새 콘텐츠로 cache를 업데이트합니다
  • Incremental Static Regeneration (ISR)과 비슷합니다
  • 생략하면 default profile의 revalidate 값(15분)이 기본값이 됩니다
  • When a request arrives after this period, the server:
    1. Serves the cached version immediately (if available)
    2. Regenerates content in the background
    3. Updates the cache with fresh content
  • Similar to Incremental Static Regeneration (ISR)
  • If omitted, defaults to the default profile's revalidate value (15 minutes)
cacheLife({ revalidate: 900 }) // 15 minutes

expire

서버가 cache된 콘텐츠를 반드시 다시 생성해야 하기까지의 최대 시간입니다.

Maximum time before the server must regenerate cached content.

  • 이 기간 동안 traffic이 없으면 서버는 다음 request 때 콘텐츠를 동기적으로 다시 생성합니다
  • revalidate와 expire를 모두 설정할 때 expire는 revalidate보다 길어야 합니다. Next.js는 이를 검증하고 잘못된 설정에 대해 error를 발생시킵니다.
  • 생략하면 default profile의 expire 값(만료되지 않음)이 기본값이 됩니다
  • After this period with no traffic, the server regenerates content synchronously on the next request
  • When you set both revalidate and expire, expire must be longer than revalidate. Next.js validates this and raises an error for invalid configurations.
  • If omitted, defaults to the default profile's expire value (never expires)
cacheLife({ expire: 3600 }) // 1 hour

Overriding the default cache profiles기본 cache profile 재정의하기

preset profile은 익숙한 시간 단위(seconds, minutes, hours, days, weeks)와 default, max로 구성됩니다. 이들을 그대로 사용하거나, default와 max를 포함해 어떤 것이든 next.config.ts에서 재정의할 수 있습니다. 기본 제공 이름은 editor 자동 완성과 함께 계속 동작합니다.

The preset profiles map to familiar time periods (seconds, minutes, hours, days, weeks), alongside default and max. You can use these as they are, or redefine any of them, including default and max, in next.config.ts. The built-in names keep working with editor autocomplete.

기본 제공 profile을 재정의하는 것은 지원되는 패턴이지만, cacheLife('hours') 같은 호출이 preset이 아니라 직접 설정한 값을 반영한다는 사실을 프로젝트에 문서화해 두세요. 시간 이름이 붙은 profile은 직관적인 기대를 동반하므로(days는 대략 24시간으로 읽힘), 특정 기간을 암시하지 않는 default나 max를 재정의하는 것보다 코드를 읽는 사람을 놀라게 할 가능성이 큽니다. 기본 제공 이름을 덮어쓰는 대신 직접 custom profile을 정의하는 것도 똑같이 유효한 방법입니다.

Redefining a built-in is a supported pattern, but document it in your project so a call like cacheLife('hours') reflects the values you set, not the presets. The time-named profiles carry an intuitive expectation (days reads as roughly 24 hours), so redefining them is more likely to surprise a reader than redefining default or max, which don't imply a specific duration. An equally valid approach is to define your own custom profile rather than overloading a built-in name.

default를 재정의하면 use cache scope에서 cacheLife를 호출하지 않을 때 적용되는 수명도 바뀝니다. 아래 예시는 default의 revalidate를 1시간으로 설정합니다:

Redefining default also changes the lifetime applied when a use cache scope calls no cacheLife. The example below sets default to a one hour revalidate:

TSnext.config.ts
const nextConfig = {
  cacheComponents: true,
  cacheLife: {
    // Redefine the 'default' profile
    default: {
      stale: 300, // 5 minutes
      revalidate: 3600, // 1 hour
      expire: 86400, // 1 day
    },
  },
}

export default nextConfig
Good to know

cacheLife 함수의 type signature는 next dev, next build 또는 next typegen 실행 중에 next.config.ts로부터 생성되므로, 재정의한 profile의 editor 자동 완성과 JSDoc hint는 preset이 아니라 직접 설정한 값을 반영합니다.

The cacheLife function's type signature is generated from next.config.ts during next dev, next build, or next typegen, so an overridden profile's editor autocomplete and JSDoc hint reflect the values you set, not the presets.

Custom cache profiles

next.config.ts에서 직접 정한 이름으로 재사용 가능한 cache profile을 정의하세요:

Define reusable cache profiles with your own names in next.config.ts:

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  cacheLife: {
    biweekly: {
      stale: 60 * 60 * 24 * 14, // 14 days
      revalidate: 60 * 60 * 24, // 1 day
      expire: 60 * 60 * 24 * 14, // 14 days
    },
  },
}

export default nextConfig

custom profile에서 생략된 속성은 default profile에서 상속됩니다. 이는 cacheLife()에 직접 전달하는 inline profile 객체에도 적용됩니다.

Inline cache profiles

일회성인 경우에는 profile 객체를 cacheLife에 직접 전달하세요:

For one-off cases, pass a profile object directly to cacheLife:

TSapp/page.tsx
'use cache'
import { cacheLife } from 'next/cache'

  cacheLife({
    stale: 3600,
    revalidate: 900,
    expire: 86400,

}

Inline profile은 해당 함수나 component에만 적용됩니다. 재사용 가능한 설정이 필요하면 next.config.ts에 custom profile을 정의하세요.

Inline profiles apply only to the specific function or component. For reusable configurations, define custom profiles in next.config.ts.

빈 객체로 cacheLife({})를 사용하면 default profile 값이 적용됩니다.

Using cacheLife({}) with an empty object applies the default profile values.

Client cache behaviorClient cache 동작

stale 속성은 Cache-Control header가 아니라 Client Cache를 제어합니다:

The stale property controls the Client Cache, not the Cache-Control header:

  • 서버는 x-nextjs-stale-time response header를 통해 stale time을 전송합니다
  • client router는 이 값을 사용해 언제 revalidate할지 결정합니다
  • prefetch된 link가 계속 사용 가능하도록 최소 30초가 강제됩니다
  • The server sends the stale time via the x-nextjs-stale-time response header
  • The client router uses this value to determine when to revalidate
  • Minimum of 30 seconds is enforced to ensure prefetched links remain usable

이 30초 최소값은 사용자가 link를 클릭하기 전에 prefetch된 데이터가 만료되는 것을 방지합니다. 시간 기반 만료에만 적용됩니다.

This 30-second minimum prevents prefetched data from expiring before users can click on links. It only applies to time-based expiration.

Server Action에서 revalidation 함수(revalidateTag, revalidatePath, updateTag, refresh)를 호출하면 stale time과 상관없이 client cache 전체가 즉시 비워집니다.

When you call revalidation functions from a Server Action (revalidateTag, revalidatePath, updateTag, or refresh), the entire client cache is immediately cleared, bypassing the stale time.

Good to know

cacheLife의 stale 속성은 staleTimes와 다릅니다. staleTimes는 모든 route에 영향을 주는 전역 설정인 반면, cacheLife는 함수별 또는 route별 설정을 가능하게 합니다. staleTimes.static을 업데이트하면 default cache profile의 stale 값도 업데이트됩니다.

The stale property in cacheLife differs from staleTimes. While staleTimes is a global setting affecting all routes, cacheLife allows per-function or per-route configuration. Updating staleTimes.static also updates the stale value of the default cache profile.

Prerendering behaviorPrerendering 동작

cache 수명이 짧으면 cache된 콘텐츠가 제공될 수 있는 위치가 달라집니다:

A short cache lifetime changes where the cached content can be delivered from:

  • revalidate가 0이거나 expire가 5분 미만: prerender에서 제외되어 request 시점에 resolve되는 "dynamic hole"이 됩니다.
  • stale이 30초 미만: 사용자가 클릭하기 전에 prefetch가 만료되므로 prerender에서 제외됩니다.
  • stale이 30초 이상 5분 미만: prerender에는 포함되지만 route의 App Shell에서는 제외됩니다.
  • revalidate of 0, or expire under 5 minutes: excluded from prerenders, becoming a "dynamic hole" resolved at request time.
  • stale under 30 seconds: excluded from prerenders, because a prefetch would expire before the user could click.
  • stale of at least 30 seconds but under 5 minutes: included in prerenders, but excluded from the route's App Shell.

preset 중에서는 seconds만 이 기준에 해당합니다: expire가 1분이므로 prerender에서 제외됩니다.

Of the presets, only seconds falls under any of these thresholds: its expire of 1 minute excludes it from prerenders.

이 동작 덕분에 같은 페이지 안에서 static 콘텐츠와 dynamic 콘텐츠를 섞을 수 있습니다. static 부분은 prerender되고, 수명이 짧은 cache는 build 시점이 아니라 request 시점에 데이터를 fetch하는 경계를 만듭니다. 콘텐츠가 로드되는 동안 fallback을 제공하려면 dynamic cache를 <Suspense> boundary로 감싸세요.

This behavior allows you to mix static and dynamic content within the same page. Static parts are prerendered, while short-lived caches create boundaries where data is fetched at request time rather than build time. Use a <Suspense> boundary around dynamic caches to provide a fallback while content loads.

Using preset profilesPreset profile 사용하기

caching을 설정하는 가장 간단한 방법은 preset profile을 사용하는 것입니다. 콘텐츠의 업데이트 패턴에 맞는 것을 선택하세요:

The simplest way to configure caching is using preset profiles. Choose one that matches your content's update pattern:

TSapp/blog/[slug]/page.tsx
import { cacheLife } from 'next/cache'

export default async function BlogPost() {
  'use cache'
  cacheLife('days') // Blog posts updated daily

  const post = await fetchBlogPost()
  return <article>{post.content}</article>
}
TSapp/products/[id]/page.tsx
import { cacheLife } from 'next/cache'

export default async function ProductPage() {
  'use cache'
  cacheLife('hours') // Product data updated multiple times per day

  const product = await fetchProduct()
  return <div>{product.name}</div>
}

Inline profiles for unique cases특수한 경우를 위한 inline profile

특정 함수에 일회성 caching 동작이 필요할 때 inline profile을 사용하세요:

Use inline profiles when a specific function needs one-off caching behavior:

TSapp/api/limited-offer/route.ts
import { cacheLife } from 'next/cache'
import { getDb } from '@lib/db'

async function getLimitedOffer() {
  'use cache'

  cacheLife({
    stale: 60, // 1 minute
    revalidate: 300, // 5 minutes
    expire: 3600, // 1 hour
  })

  const offer = await getDb().offer.findFirst({
    where: { type: 'limited' },
    orderBy: { created_at: 'desc' },
  })

  return offer
}

export async function GET() {
  const offer = await getLimitedOffer()

  return Response.json(offer)
}

Caching individual functions개별 함수 caching

세밀하게 제어하려면 유틸리티 함수에 caching을 적용하세요:

Apply caching to utility functions for granular control:

TSlib/api.ts
import { cacheLife } from 'next/cache'

export async function getSettings() {
  'use cache'
  cacheLife('max') // Settings rarely change

  return await fetchSettings()
}
TSlib/stats.ts
import { cacheLife } from 'next/cache'

export async function getRealtimeStats() {
  'use cache'
  cacheLife('seconds') // Stats update constantly

  return await fetchStats()
}

Nested caching behavior중첩 caching 동작

use cache directive를 중첩하면(cache된 함수나 component가 다른 cache된 함수나 component를 사용하는 경우), 바깥 cache의 동작은 명시적인 cacheLife가 있는지에 따라 달라집니다.

When you nest use cache directives (a cached function or component using another cached function or component), the outer cache's behavior depends on whether it has an explicit cacheLife.

With explicit outer cacheLife바깥에 명시적 cacheLife가 있는 경우

바깥 cache는 안쪽 cache의 수명과 관계없이 자신의 수명을 사용합니다. 바깥 cache가 hit되면 모든 중첩 데이터를 포함한 전체 출력을 반환합니다. 명시적 cacheLife는 안쪽 수명보다 길든 짧든 항상 우선합니다.

The outer cache uses its own lifetime, regardless of inner cache lifetimes. When the outer cache hits, it returns the complete output including all nested data. An explicit cacheLife always takes precedence, whether it's longer or shorter than inner lifetimes.

TSapp/dashboard/page.tsx
import { cacheLife } from 'next/cache'
import { Widget } from './widget'

export default async function Dashboard() {
  'use cache'
  cacheLife('hours') // Outer scope sets its own lifetime

  return (
    <div>
      <h1>Dashboard</h1>
      <Widget /> {/* Inner scope has 'minutes' lifetime */}
    </div>
  )
}

Without explicit outer cacheLife바깥에 명시적 cacheLife가 없는 경우

바깥 cache에서 cacheLife를 호출하지 않으면 default profile(15분 revalidate)을 사용합니다. 수명이 더 짧은 안쪽 cache는 바깥 cache의 default 수명을 줄일 수 있습니다. 수명이 더 긴 안쪽 cache는 이를 default 이상으로 늘릴 수 없습니다.

If you don't call cacheLife in the outer cache, it uses the default profile (15 min revalidate). Inner caches with shorter lifetimes can reduce the outer cache's default lifetime. Inner caches with longer lifetimes cannot extend it beyond the default.

TSapp/dashboard/page.tsx
import { Widget } from './widget'

export default async function Dashboard() {
  'use cache'
  // No cacheLife call - uses default (15 min)
  // If Widget has 5 min → Dashboard becomes 5 min
  // If Widget has 1 hour → Dashboard stays 15 min

  return (
    <div>
      <h1>Dashboard</h1>
      <Widget />
    </div>
  )
}

명시적인 cacheLife를 지정하는 것을 권장합니다. 명시적 수명 값이 있으면 중첩된 cache를 추적하지 않고도 cache된 함수나 component를 보고 동작을 바로 알 수 있습니다. 명시적 수명 값이 없으면 동작이 안쪽 cache 수명에 의존하게 되어 파악하기 어려워집니다.

It is recommended to specify an explicit cacheLife. With explicit lifetime values, you can inspect a cached function or component and immediately know its behavior without tracing through nested caches. Without explicit lifetime values, the behavior becomes dependent on inner cache lifetimes, making it harder to reason about.

Nested short-lived caches중첩된 단기 cache

Prerendering behavior에서 설명했듯이, 수명이 짧은 cache(revalidate가 0이거나 expire가 5분 미만)는 prerender에서 제외되는 dynamic hole이 됩니다.

As described in Prerendering behavior, short-lived caches (zero revalidate or expire under 5 minutes) become dynamic holes excluded from prerenders.

수명이 짧은 cache가 명시적 cacheLife 없는 다른 use cache 안에 중첩되면, 전파(propagation)에 의해 바깥 cache의 수명도 조용히 짧아지게 됩니다. 이런 실수로 인한 잘못된 설정을 방지하기 위해 Next.js는 prerendering 중에 error를 throw합니다.

When a short-lived cache is nested inside another use cache without an explicit cacheLife, the outer cache's lifetime would silently become short too via propagation. To prevent this accidental misconfiguration, Next.js throws an error during prerendering.

중첩된 cache는 명확히 드러나지 않을 수 있다는 점에 유의하세요. import한 module이나 심지어 third-party dependency 안에 있을 수도 있습니다:

Note that the nested cache may not be obvious — it could be in an imported module or even a third-party dependency:

TScomponents/short-lived-widget.tsx
import { cacheLife } from 'next/cache'

export async function ShortLivedWidget() {
  'use cache'
  cacheLife('seconds')
  const data = await fetchRealtimeData()
  return <div>{data}</div>
}

명시적 cacheLife 없이 다른 use cache에서 이 component를 사용하면 prerendering 중에 error가 발생합니다:

Using this component from another use cache without an explicit cacheLife will error during prerendering:

TSapp/page.tsx
import { ShortLivedWidget } from '@/components/short-lived-widget'

export default async function Page() {
  'use cache'
  // Error: no explicit cacheLife on outer cache
  return (
    <div>
      <h1>Dashboard</h1>
      <p>Last updated: {new Date().toISOString()}</p>
      <ShortLivedWidget />
    </div>
  )
}

error를 해결하려면 바깥 use cache에 명시적 cacheLife()를 추가하세요:

To fix the error, add an explicit cacheLife() to the outer use cache:

바깥 cache를 static(prerender됨)으로 유지하고 싶다면 더 긴 cache 수명을 설정하세요:

If you want the outer cache to remain static (prerendered), set a longer cache lifetime:

TSapp/page.tsx
import { cacheLife } from 'next/cache'
import { ShortLivedWidget } from '@/components/short-lived-widget'

export default async function Page() {
  'use cache'
  cacheLife('default') // Explicit cacheLife prevents the error
  return (
    <div>
      <h1>Dashboard</h1>
      <p>Last updated: {new Date().toISOString()}</p>
      <ShortLivedWidget />
    </div>
  )
}

바깥 cache도 단기 cache로 만들고 싶다면 의도한 것임을 확인하기 위해 짧은 cache 수명을 명시적으로 설정하세요. 콘텐츠가 로드되는 동안 fallback을 제공하려면 component를 <Suspense> boundary로 감싸세요:

If you want the outer cache to also be short-lived, explicitly set a short cache lifetime to confirm this is intentional. Wrap the component in a <Suspense> boundary to provide a fallback while content loads:

TSapp/page.tsx
import { Suspense } from 'react'
import { cacheLife } from 'next/cache'
import { ShortLivedWidget } from '@/components/short-lived-widget'

async function Content() {
  'use cache: remote'
  cacheLife('seconds') // Explicit cacheLife confirms this is intentionally short-lived
  return (
    <>
      <p>Last updated: {new Date().toISOString()}</p>
      <ShortLivedWidget />
    </>
  )
}

export default function Page() {
  return (
    <div>
      <h1>Dashboard</h1>
      <Suspense fallback={<p>Loading...</p>}>
        <Content />
      </Suspense>
    </div>
  )
}
Note

serverless 배포에서는 기본 in-memory cache를 사용한 runtime caching이 request 간에 유지되지 않으므로 이 예시는 "use cache: remote"를 사용합니다. self-hosted 환경에서는 "use cache"로 충분할 수 있습니다. 자세한 내용은 Runtime caching considerations를 참고하세요.

This example uses "use cache: remote" because runtime caching in serverless deployments doesn't persist across requests with the default in-memory cache. For self-hosted environments, "use cache" may be sufficient. See Runtime caching considerations for more details.

Conditional cache lifetimes조건부 cache 수명

애플리케이션 로직에 따라 서로 다른 cache 기간을 설정하도록 여러 코드 경로에서 조건부로 cacheLife를 호출할 수 있습니다:

You can call cacheLife conditionally in different code paths to set different cache durations based on your application logic:

TSlib/posts.ts
import { cacheLife, cacheTag } from 'next/cache'

async function getPostContent(slug: string) {
  'use cache'

  const post = await fetchPost(slug)

  // Tag the cache entry for targeted revalidation
  cacheTag(`post-${slug}`)

  if (!post) {
    // Content may not be published yet or could be in draft
    // Cache briefly to reduce database load
    cacheLife('minutes')
    return null
  }

  // Published content can be cached longer
  cacheLife('days')

  // Return only the necessary data to keep cache size minimal
  return post.data
}

이 패턴은 결과에 따라 다른 cache 기간이 필요할 때 유용합니다. 예를 들어 항목이 없지만 나중에 생길 가능성이 높은 경우입니다.

This pattern is useful when different outcomes need different cache durations, for example, when an item is missing but is likely to be available later.

Using dynamic cache lifetimes from data데이터에서 동적 cache 수명 사용하기

runtime에 cache 수명을 계산하고 싶다면(예: fetch한 데이터에서 읽어 오는 경우) inline cache profile 객체를 사용하세요:

If you want to calculate cache lifetime at runtime, for example by reading it from the fetched data, use an inline cache profile object:

TSlib/posts.ts
import { cacheLife, cacheTag } from 'next/cache'

async function getPostContent(slug: string) {
  'use cache'

  const post = await fetchPost(slug)
  cacheTag(`post-${slug}`)

  if (!post) {
    cacheLife('minutes')
    return null
  }

  // Use cache timing from CMS data directly as an object
  cacheLife({
    // Ensure post.revalidateSeconds is a number in seconds
    // stale and expire inherit from 'default' profile
    revalidate: post.revalidateSeconds ?? 3600,
  })

  return post.data
}
