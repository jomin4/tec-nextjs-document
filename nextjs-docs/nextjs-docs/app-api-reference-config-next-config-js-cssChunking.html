cssChunkingexperimentalcssChunking

CSS Chunking은 CSS 파일을 chunk로 나누고 순서를 재배치하여 웹 애플리케이션의 성능을 개선하는 전략입니다. 이를 통해 route는 애플리케이션의 모든 CSS를 한 번에 불러오는 대신, 필요한 CSS에 가까운 양만 불러올 수 있습니다.

CSS Chunking is a strategy used to improve the performance of your web application by splitting and re-ordering CSS files into chunks. This lets a route load close to only the CSS it needs, instead of loading all the application's CSS at once.

next.config.js 파일의 experimental.cssChunking option을 사용해 CSS 파일이 chunk로 나뉘는 방식을 제어할 수 있습니다:

You can control how CSS files are chunked using the experimental.cssChunking option in your next.config.js file:

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig = {
  experimental: {
    cssChunking: true, // default
  },
} satisfies NextConfig

export default nextConfig
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    cssChunking: true, // default
  },
}

module.exports = nextConfig

Options

  • true (default) (webpack 및 Turbopack): Next.js는 가능할 때마다 CSS 파일을 merge하려고 시도하며, import 순서로부터 파일 간의 명시적·암묵적 dependency를 판단하여 chunk 수, 즉 request 수를 줄입니다.
  • false (webpack 전용): Next.js는 CSS 파일을 merge하거나 순서를 재배치하지 않습니다.
  • 'strict' (webpack 전용): Next.js는 CSS 파일을 파일에 import된 정확한 순서대로 불러오며, 이로 인해 chunk와 request가 더 많아질 수 있습니다.
  • 'graph' (Turbopack 전용): Next.js는 비용 기반 graph algorithm을 사용해 여러 route에 걸쳐 CSS를 group으로 묶고, 각 route가 download하는 byte와 보내는 request 사이의 균형을 맞춥니다.
  • true (default) (webpack and Turbopack): Next.js will try to merge CSS files whenever possible, determining explicit and implicit dependencies between files from import order to reduce the number of chunks and therefore the number of requests.
  • false (webpack only): Next.js will not attempt to merge or re-order your CSS files.
  • 'strict' (webpack only): Next.js will load CSS files in the correct order they are imported into your files, which can lead to more chunks and requests.
  • 'graph' (Turbopack only): Next.js uses a cost-based graph algorithm to group CSS across your routes, balancing the bytes each route downloads and the requests it makes.

Choosing a strategy전략 선택하기

대부분의 애플리케이션에서는 어느 bundler를 사용하든 기본값(true)이 올바른 선택입니다. CSS를 merge하여 request를 줄여 줍니다. 다른 전략은 특별한 이유가 있을 때만 사용하세요.

For most applications, the default (true) is the right choice in either bundler: it merges CSS to make fewer requests. Reach for another strategy only for a specific reason.

Turbopack에서 그 이유는 보통 성능입니다. route 간에 CSS가 공유되는 방식을 조정하려면 graph로 전환하세요. request가 늘어나는 대신 route가 download하는 사용되지 않는 CSS를 줄일 수 있습니다(Balancing requests and grouping 참고).

In Turbopack, that reason is usually performance. Switch to graph to tune how CSS is shared across routes, cutting the unused CSS a route downloads at the cost of more requests (see Balancing requests and grouping).

webpack에서 그 이유는 보통 정확성입니다. 예상치 못한 CSS 동작을 겪는다면 'strict'로 전환하세요. 예를 들어 서로 다른 파일에서 a.css와 b.css를 다른 import 순서(a 다음 b, 또는 b 다음 a)로 import하면, true는 둘 사이에 dependency가 없다고 가정하고 임의의 순서로 merge합니다. b.css가 a.css에 의존한다면, 'strict'는 chunk와 request가 늘어나는 대신 merge를 막고 import 순서대로 불러옵니다. merge를 완전히 비활성화하려면 false를 사용하세요.

In webpack, that reason is usually correctness. Switch to 'strict' if you run into unexpected CSS behavior. For example, if you import a.css and b.css in different files using a different import order (a before b, or b before a), true merges them in any order and assumes there are no dependencies between them; if b.css depends on a.css, 'strict' prevents the merge and loads them in import order, at the cost of more chunks and requests. Use false to disable merging entirely.

Debugging what a route actually usesroute가 실제로 사용하는 CSS debugging

사용되지 않는 CSS가 어느 정도 있는 것은 괜찮고 대부분의 앱은 아무것도 바꿀 필요가 없지만, render-blocking CSS는 관리해 두는 것이 좋습니다. Lighthouse는 이를 예상 절감량과 함께 Reduce unused CSS 항목(opportunity)으로 표시하며, Chrome DevTools는 Coverage panel에서 stylesheet별로 보여 줍니다. 이 panel의 usage bar는 각 stylesheet에서 적용된 CSS를 초록색으로, 사용되지 않은 CSS를 회색으로 표시합니다.

While some unused CSS is acceptable, and most apps do not need to change anything, it is worth keeping render-blocking CSS in check. Lighthouse flags this as a Reduce unused CSS opportunity with an estimated saving, and Chrome DevTools shows it per stylesheet in its Coverage panel, where a usage bar shows each stylesheet's applied CSS in green and unused CSS in gray.

report를 볼 때는 :hover, :focus, 또는 menu와 modal을 위해 JavaScript로 toggle되는 class처럼 상호작용 시에만 적용되는 style에 주의하세요. Coverage는 이런 style을 실제로 trigger하기 전까지 사용되지 않은 것으로 계산합니다.

When reading the report, watch out for styles that only apply on interaction, such as :hover, :focus, or classes toggled by JavaScript for menus and modals, since Coverage counts them as unused until you trigger them.

사용되지 않는 CSS의 원인은 둘 중 하나입니다. 하나는 route가 import하는 stylesheet 안의 dead CSS로, source에서 사용되지 않는 rule을 제거하거나 이를 사용하는 route만 import하는 stylesheet로 옮겨서 해결합니다(CSS Modules는 style을 import하는 component로 scope를 한정하므로 이를 자연스럽게 해 줍니다).

The source of this unused CSS is one of two things. Either it is dead CSS in a stylesheet your route imports, which you fix in your source by removing the unused rules or moving them into a stylesheet only the routes that use them import (CSS Modules make this natural by scoping styles to the component that imports them).

다른 하나는 bundler가 다른 stylesheet를 route가 불러오는 shared chunk에 merge한 경우입니다. 이는 chunking strategy에 의해 결정됩니다. Turbopack에서는 graph mode를 사용해 CSS를 얼마나 적극적으로 merge할지 세밀하게 조정할 수 있습니다.

Or the bundler merged another stylesheet into a shared chunk that your route loads. That is governed by your chunking strategy. In Turbopack, graph mode lets you fine-tune how aggressively CSS merges.

Balancing requests and groupingRequest와 grouping의 균형 맞추기

graph 전략은 request를 줄이기 위해 CSS를 shared chunk로 묶습니다. 기본 tuning을 사용하는 문자열 형태로 활성화하세요:

The graph strategy groups CSS into shared chunks to cut requests. Turn it on with the string form, which uses the default tuning:

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig = {
  experimental: {
    cssChunking: 'graph',
  },
} satisfies NextConfig

export default nextConfig
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    cssChunking: 'graph',
  },
}

module.exports = nextConfig

균형을 조정하려면 대신 object를 전달하세요. requestCost와 weightDistribution은 모두 선택 사항이므로, 바꾸고 싶은 것만 포함하면 됩니다:

To shift that balance, pass an object instead. Both requestCost and weightDistribution are optional, so include only the one you want to change:

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig = {
  experimental: {
    cssChunking: {
      type: 'graph',
      requestCost: 100000,
      weightDistribution: 0.1,
    },
  },
} satisfies NextConfig

export default nextConfig
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    cssChunking: {
      type: 'graph',
      requestCost: 100000,
      weightDistribution: 0.1,
    },
  },
}

module.exports = nextConfig
  • requestCost (기본값 20000): 추가 CSS request 하나의 예상 비용(byte 단위)입니다. 값이 클수록 더 적고 큰 shared chunk, 그리고 전체적으로 더 적은 request 쪽으로 기웁니다.
  • weightDistribution (기본값 0.1): shared chunk의 비용이 이를 불러오는 route들에 어떻게 분배되는지를 각 route가 import하는 CSS 양을 가중치로 하여 제어합니다. 0은 모든 route에 동일한 가중치를 줍니다. 값이 높을수록 CSS를 적게 import하는 route에 더 큰 가중치를 주므로, 큰 route에서는 추가 CSS가 덜 눈에 띈다는 가정하에 algorithm이 CSS가 적은 route를 우선시합니다.
  • requestCost (default 20000): the estimated cost, in bytes, of each additional CSS request. Larger values bias toward fewer, larger shared chunks, and fewer requests overall.
  • weightDistribution (default 0.1): controls how a shared chunk's cost is distributed across the routes that load it, weighted by how much CSS each route imports. 0 weights every route equally; higher values give more weight to routes that import less CSS, so the algorithm prioritizes routes with less CSS, assuming extra CSS is less noticeable on large routes.

How graph decides what to mergegraph가 merge 대상을 결정하는 방식

CSS를 shared chunk로 merge하는 것은 기본값(true)이 이미 하는 일입니다. graph는 merge와 split 사이의 경계를 어디에 둘지 제어할 수 있게 해 줄 뿐입니다.

Merging CSS into shared chunks is what the default (true) already does; graph just lets you control where it draws the line between merging and splitting.

stylesheet를 공유하는 두 route를 예로 들어 보겠습니다:

Take two routes that share a stylesheet:

/a → [shared.css, only-a.css]
/b → [shared.css]

여기서 /b는 only-a.css를 import하지 않으므로, 내려야 할 결정은 하나입니다. only-a.css를 shared chunk에 남겨 둘지, 별도의 chunk로 분리할지입니다.

Here, /b never imports only-a.css, so there is one decision to make: keep only-a.css in the shared chunk, or give it its own.

merge된 상태로 두면 /a는 모든 CSS를 한 번의 request로 불러올 수 있습니다. 대신 그 shared chunk를 함께 불러오는 /b는 only-a.css를 import하지 않았는데도 이를 download하게 됩니다.

Keeping it merged lets /a load all its CSS in a single request. The cost is that /b, which also loads that shared chunk, now downloads only-a.css even though it never imported it.

분리하면 /b는 그만큼의 byte를 아낄 수 있지만, 이제 /a는 request를 두 번 보내야 합니다. 기본값은 고정된 heuristic으로 둘 중 하나를 선택합니다.

Splitting it out spares /b those bytes, but now /a has to make two requests. The default picks between these with a fixed heuristic.

requestCost option은 graph가 이 trade-off에 가격을 매기는 방법으로, request 하나와 맞먹는 import되지 않은 CSS의 양을 뜻합니다. only-a.css가 requestCost보다 충분히 작은 동안에는 merge된 상태로 두고, request 비용을 넘어설 만큼 커지면 분리합니다.

The requestCost option is how graph prices that trade: the amount of un-imported CSS worth one extra request. It keeps only-a.css merged while only-a.css stays well under requestCost, and splits it out once it grows large enough to outweigh the request.

결정을 좌우하는 것은 merge가 route에 떠넘기게 될 import되지 않은 CSS의 크기이며, 합류하는 shared chunk의 크기는 그보다 훨씬 덜 중요합니다. 기본 requestCost가 약 20 KB이므로, only-a.css는 대략 그 크기를 넘어야 자체 chunk를 갖게 되며, 작은 stylesheet는 merge된 상태로 남습니다.

What drives the decision is the size of the un-imported CSS a merge would push onto a route, much more than the size of the shared chunk it joins. With the default requestCost of about 20 KB, only-a.css would have to exceed roughly that size before it earns its own chunk, so small stylesheets stay merged.

Graph algorithm 개요

큰 틀에서 보면 algorithm은 개별 CSS 파일 단위로 동작합니다. 각 route가 import하는 CSS의 순서 있는 목록에서 시작합니다:

/dashboard  → [reset.css, theme.css, layout.css, dashboard.css]
/settings   → [reset.css, theme.css, layout.css, settings.css]
/login      → [reset.css, login.css]

이로부터 weighted graph를 만드는데, 두 CSS 파일을 같은 순서로 함께 import하는 route가 많을수록 두 파일 사이의 edge가 무거워집니다. 그런 다음 자주 짝지어지는 파일이 인접하도록 graph를 한 줄로 펼치고, 그 줄을 chunk로 나누는 cut(구분점)을 배치합니다. 예를 들면 다음과 같습니다:

reset theme layout │ dashboard │ settings │ login
└──── chunk 1 ────┘   chunk 2     chunk 3    chunk 4

route는 자신이 import하는 파일이 들어 있는 모든 chunk를 불러오므로, /dashboard는 chunk 1과 2를, /login은 chunk 1과 4를 불러옵니다.

algorithm은 byte와 request의 균형을 맞추면서 모든 route에 걸친 총 download 비용이 최소가 되도록 chunk를 나눌 위치를 선택합니다. 각 route를 개별로 최적화하는 것이 아니라 총합을 최적화하므로, 전체 비용을 낮출 수 있다면 route가 import하지 않은 CSS를 일부 떠안게 될 수도 있습니다. 두 option은 이 가중치를 제어합니다:

  • requestCost: reset.css, theme.css, layout.css가 하나의 chunk를 공유하므로, 이들이 필요한 route는 세 번이 아니라 한 번의 request만 보냅니다. requestCost는 request 하나의 가격을 byte로 나타낸 것입니다. 값을 높이면 algorithm은 이런 식으로 더 많이 merge하여 download가 커지는 대신 request를 줄이고, 0에 가깝게 낮추면 chunk를 쪼개서 route가 import하는 것에 가까운 양만 download하는 대신 request가 늘어납니다.
  • weightDistribution: /login은 chunk 1에서 reset.css만 필요하지만, theme.css와 layout.css가 같은 chunk를 공유하므로 이들도 download합니다. 이 option은 algorithm이 이 점을 얼마나 신경 쓸지 결정합니다. 0이면 /login과 /dashboard가 동일하게 계산되므로 추가 CSS가 함께 따라가도록 허용합니다. 값을 높이면 /login처럼 CSS를 적게 import하는 route가 더 중요하게 계산되므로, algorithm은 전체 request가 늘어나는 대가를 치르더라도 이런 route가 import하지 않은 CSS를 떠안지 않도록 합니다.
