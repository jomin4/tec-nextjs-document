Building interactive apps인터랙티브 앱 만들기

사용자 interaction에 server-side 작업이 필요하면 결과를 즉시 얻을 수 없습니다. network request는 완료되기까지 얼마나 걸릴지 알 수 없고, 성공할 수도 실패할 수도 있습니다. 기다리는 동안 client는 feedback을 제공하고 이런 state에 대응해야 합니다. 그렇지 않으면 사용자는 오래된(stale) 데이터를 바라보며 무언가 진행되고 있는지 궁금해하게 됩니다.

When a user interaction requires server-side work, the result is not available immediately. Network requests take an unknown amount of time to complete and may succeed or fail. While waiting, the client should provide feedback and respond to those states. Otherwise, users are left looking at stale data and may wonder whether anything is happening.

이 가이드는 *Taskboard*라는 task 관리 앱에 반응성 있는 feedback을 추가합니다. 각 단계는 느린 read를 streaming하는 것부터 server가 응답하기 전에 mutation을 확정된 것처럼 보여 주는 것까지, 서로 다른 종류의 pending 작업을 다룹니다.

This guide adds responsive feedback to a task management app called Taskboard. Each step handles a different kind of pending work, from streaming slow reads to confirming mutations before the server responds.

Good to know

이 가이드의 패턴은 Core Web Vitals도 개선합니다. <Suspense>를 사용한 streaming은 느린 read가 끝나는 동안 shell을 먼저 그리게 해서 FCP와 LCP를 낮춥니다. Optimistic UI와 transition은 click frame을 빠르게 유지해 INP를 낮춥니다. 다음 route를 prefetch하면 목적지 페이지의 FCP, LCP, INP가 거의 즉각적이 됩니다. 이 패턴들이 도움이 되긴 하지만, 일반적인 INP 개선 작업, 즉 client JavaScript를 덜 보내고 interaction 중 blocking roundtrip을 피하는 일을 대체하지는 않습니다.

The patterns in this guide also improve Core Web Vitals. Streaming with <Suspense> lowers FCP and LCP by letting the shell paint while slow reads finish. Optimistic UI and transitions lower INP by keeping the click frame fast. Prefetching the next route makes FCP, LCP, and INP on the destination page near-instant. These patterns help, but they don't replace the usual INP work: shipping less client JavaScript and avoiding blocking roundtrips during interactions.

Example예제

패턴은 순서대로 쌓여 갑니다: loading boundary 뒤에서 느린 데이터를 streaming하고, 즉시 반응하는 priority toggle을 추가하고, callback prop을 받는 재사용 가능한 filter를 만들고, 확정되기 전에 comment를 보여 주고, drop 시 card를 column 사이로 옮기고, create dialog에서 form lifecycle을 관리하고, pending 중인 삭제를 parent에 알립니다. 마지막 단계에서는 재사용 가능한 read를 cache해서 navigation이 즉각적으로 유지되게 합니다.

The patterns build in order: stream slow data behind loading boundaries, add an instant priority toggle, build a reusable filter with a callback prop, show comments before they're confirmed, move cards between columns on drop, manage form lifecycle in a create dialog, and signal pending deletion to a parent. The final step caches the reusable reads so navigations stay instant.

함께 제공되는 Taskboard 데모(source)에서 이 가이드의 각 패턴이 실제로 동작하는 모습을 볼 수 있습니다.

The companion Taskboard demo (source) lets you see each pattern from this guide in action.

앱은 feature 단위로 구성되어 있습니다. task 도메인에 관한 모든 것(query, Server Function, component)은 features/task/ 아래에 있습니다. 공유 UI primitive는 components/ui/에 있고, app/의 page들이 feature component를 조합합니다. 이 가이드 전체의 파일 경로는 이 구조를 따릅니다.

The app is organized by feature. Everything for the task domain (queries, Server Functions, and components) lives under features/task/. Shared UI primitives live in components/ui/, and pages in app/ compose feature components. The file paths throughout this guide follow that structure.

출발점은 database에서 task와 comment를 읽는 Server Component 앱이며, <Suspense> boundary도 caching도 없습니다. Client Component는 Server Function을 호출해 데이터를 mutate합니다. 각 mutation이 끝나면 Server Function이 refresh()를 호출해 server가 최신 데이터로 다시 render하게 합니다:

The starting point is a Server Component app that reads tasks and comments from a database, with no <Suspense> boundaries and no caching. Client Components call Server Functions to mutate that data. After each mutation, the Server Function calls refresh() so the server re-renders with fresh data:

TSfeatures/task/task-actions.ts
'use server'

import { refresh } from 'next/cache'
import { PRIORITY_CYCLE } from '@/lib/data'
import { getTaskById, updateTaskPriority } from '@/lib/db'

export async function cyclePriority(taskId: string) {
  const task = await getTaskById(taskId)
  if (!task) return null
  const newPriority = PRIORITY_CYCLE[task.priority]
  await updateTaskPriority(taskId, newPriority)
  refresh()
  return newPriority
}

Step 1: Stream slow data with Suspense1단계: Suspense로 느린 데이터 streaming하기

task 상세 페이지는 task와 그 comment를 읽습니다. 두 read를 page component 맨 위에서 모두 await하면, 가장 느린 read가 resolve될 때까지 페이지 전체가 block됩니다.

The task detail page reads the task and its comments. When both are awaited at the top of the page component, the whole page blocks until the slowest read resolves.

TSapp/task/[id]/page.tsx
import { getTask } from '@/features/task/task-queries'
import { TaskDetail } from '@/features/task/components/task-detail'
import { CommentSection } from '@/features/task/components/comment-section'

export default async function TaskPage({ params }) {
  const { id } = await params
  const task = await getTask(id)

  return (
    <div>
      <TaskDetail task={task} />
      <CommentSection taskId={id} />
    </div>
  )
}

이 버전에서는 getTask가 resolve될 때까지 아무것도 render되지 않고, comment read는 그 이후에야 시작됩니다.

With this version, nothing renders until getTask resolves, and the comments read starts only after that.

read를 별도의 component로 나누고, 각각에 promise를 넘기고, <Suspense>로 감싸세요. 페이지는 동기(synchronous)가 되어 shell을 즉시 반환하고, server는 각 section의 데이터가 resolve되는 대로 streaming합니다:

Split the reads into separate components, pass each one a promise, and wrap them in <Suspense>. The page becomes synchronous, returns the shell immediately, and the server streams each section in as its data resolves:

TSapp/task/[id]/page.tsx
import { Suspense } from 'react'
import {
  TaskDetail,
  TaskDetailSkeleton,
} from '@/features/task/components/task-detail'
import {
  CommentSection,
  CommentSectionSkeleton,
} from '@/features/task/components/comment-section'

export default function TaskPage({ params }) {
  return (
    <div>
      <Suspense fallback={<TaskDetailSkeleton />}>
        {params.then(({ id }) => (
          <>
            <TaskDetail id={id} />
            <Suspense fallback={<CommentSectionSkeleton />}>
              <CommentSection taskId={id} />
            </Suspense>
          </>
        ))}
      </Suspense>
    </div>
  )
}

각 section component는 자기 데이터를 await합니다:

Each section component awaits its own data:

TSfeatures/task/components/task-detail.tsx
export async function TaskDetail({ id }) {
  const task = await getTask(id)
  return <TaskHeader task={task} />
}

JSX 안에서 params.then()을 inline으로 호출하면 페이지가 동기로 유지됩니다. 바깥쪽 <Suspense>는 params resolve와 task 상세 read를 감쌉니다. TaskDetail이 resolve되면 React는 task header와 중첩된 <Suspense> boundary를 보여 주고, 이 boundary는 comment가 load되는 동안 CommentSectionSkeleton을 표시합니다.

Calling params.then() inline in JSX keeps the page synchronous. The outer <Suspense> covers the params resolution and the task detail read. Once TaskDetail resolves, React reveals the task header and the nested <Suspense> boundary, which shows CommentSectionSkeleton while comments load.

이제 page shell은 즉시 그려지고, task header는 getTask가 resolve되면 streaming되어 들어오며, comment section은 getComments가 resolve되면 뒤따라 들어옵니다.

The page shell now paints immediately, the task header streams in when getTask resolves, and the comments section follows when getComments resolves.

streaming 패턴에 대한 자세한 내용은 Streaming 가이드를 참고하세요.

For more on streaming patterns, see the Streaming guide.

Step 2: Respond instantly to a toggle2단계: toggle에 즉시 반응하기

각 task card에는 click할 때마다 low, medium, high를 순환하는 priority 표시가 있습니다.

Each task card has a priority indicator that cycles through low, medium, and high on click.

button은 server에서 받은 priority prop을 render합니다. Server Function을 호출하면 mutation이 시작되지만, 현재 render의 그 prop은 바뀌지 않습니다.

The button renders the priority prop from the server. Calling a Server Function starts the mutation, but it doesn't change that prop in the current render.

여기서는 Server Function을 직접 호출합니다:

Here the Server Function is called directly:

TSfeatures/task/components/task-card.tsx
'use client'

import { cyclePriority } from '@/features/task/task-actions'

export function TaskCard({ id, priority }) {
  return (
    <button onClick={() => cyclePriority(id)} className={priorityDot[priority]}>
      {priority}
    </button>
  )
}

점을 click하면 Server Function이 실행되지만, 다음 server render가 도착할 때까지 button은 예전 priority prop을 계속 render합니다.

If you click the dot, the Server Function runs, but the button keeps rendering the old priority prop until the next server render arrives.

직접 호출을 useOptimistic과 useTransition으로 바꾸세요. useOptimistic은 stale prop 대신 render할 값을 제공하고, useTransition은 Server Function을 transition의 일부로 실행합니다. optimistic 값은 그 transition이 pending인 동안 적용됩니다:

Replace the direct call with useOptimistic and useTransition. useOptimistic provides a value to render in place of the stale prop, and useTransition runs the Server Function as part of a transition. The optimistic value applies for as long as that transition is pending:

TSfeatures/task/components/task-card.tsx
'use client'

import { useOptimistic, useTransition } from 'react'
import { cyclePriority } from '@/features/task/task-actions'
import { PRIORITY_CYCLE } from '@/lib/data'

export function TaskCard({ id, priority }) {
  const [optimisticPriority, setOptimisticPriority] = useOptimistic(priority)
  const [, startTransition] = useTransition()

  function handlePriority() {
    startTransition(async () => {
      setOptimisticPriority(PRIORITY_CYCLE[optimisticPriority])
      await cyclePriority(id)
    })
  }

  return (
    <button
      onClick={handlePriority}
      className={priorityDot[optimisticPriority]}
    >
      {optimisticPriority}
    </button>
  )
}

setOptimisticPriority 호출은 순환 순서상 다음 값으로 현재 frame에서 UI를 업데이트합니다. prop 대신 optimisticPriority에서 값을 읽기 때문에, 빠르게 double-click해도 stale closure 값을 읽지 않고 올바르게 순환합니다.

The setOptimisticPriority call updates the UI on the current frame with the next value in the cycle. Reading from optimisticPriority instead of the prop means rapid double-clicks cycle correctly rather than reading a stale closure value.

transition이 끝나고 최신 데이터가 도착하면 optimistic 값은 server가 새로 render한 prop으로 되돌아갑니다. useTransition 안의 Server Function이 throw하면, 수동 try/catch 없이도 error가 가장 가까운 error boundary로 전달됩니다.

When the transition ends and fresh data arrives, the optimistic value reverts to the new server-rendered prop. If the Server Function inside useTransition throws, the error is forwarded to the nearest error boundary without a manual try/catch.

이제 마우스 버튼을 떼는 순간 색이 바뀝니다. 다시 click하면 첫 mutation이 끝나기를 기다리지 않고 다음 값으로 순환합니다.

The color now changes the moment the mouse lifts. Clicking again cycles to the next value without waiting for the first mutation to finish.

Step 3: Filter with pending feedback3단계: pending feedback이 있는 filter

board에는 label filter chip(Design, Frontend, Backend)이 있습니다. chip을 click하면 query param이 업데이트되어 task 목록을 filter합니다.

The board has label filter chips (Design, Frontend, Backend). Clicking a chip updates a query param to filter the task list.

선택된 filter는 URL에서 옵니다. router.push()를 호출하면 client navigation이 시작되고, server는 새 search params로 board를 다시 render합니다. 그 navigation이 완료될 때까지 페이지는 예전 URL state를 계속 render합니다.

The selected filter comes from the URL. Calling router.push() starts a client navigation, and the server re-renders the board with the new search params. Until that navigation completes, the page keeps rendering the old URL state.

여기서는 router.push()를 직접 호출합니다:

Here router.push() is called directly:

TSfeatures/task/components/label-filter.tsx
'use client'

import { useRouter, useSearchParams } from 'next/navigation'

export function LabelFilter() {
  const router = useRouter()
  const searchParams = useSearchParams()

  function handleFilter(value: string | null) {
    const params = new URLSearchParams(searchParams.toString())
    if (value) params.set('label', value)
    else params.delete('label')
    router.push(`/?${params.toString()}`)
  }

  // ...render chips with onClick={handleFilter}
}

이 버전에서는 router.push()가 navigation을 시작하지만 local pending state가 없습니다. chip은 예전 URL 값을 계속 render하고, board는 새 server render가 load 중이라는 신호를 전혀 주지 않습니다.

With this version, router.push() starts the navigation, but there's no local pending state. The chip keeps rendering the old URL value, and the board gives no sign that a new server render is loading.

filter를 두 component로 나누세요. LabelFilter는 query string 업데이트를 담당하고, navigation callback을 재사용 가능한 ChipGroup에 넘깁니다. ChipGroup이 모든 pending feedback을 처리합니다:

Separate the filter into two components. LabelFilter owns the query string update and passes the navigation callback to a reusable ChipGroup, which handles all the pending feedback:

TSfeatures/task/components/label-filter.tsx
'use client'

import { useRouter, useSearchParams } from 'next/navigation'
import { ChipGroup } from '@/components/ui/chip-group'

const labels = [
  { label: 'Design', value: 'design' },
  { label: 'Frontend', value: 'frontend' },
  { label: 'Backend', value: 'backend' },
]

export function LabelFilter() {
  const router = useRouter()
  const searchParams = useSearchParams()
  const current = searchParams.get('label') ?? null

  function filterAction(value: string | null) {
    const params = new URLSearchParams(searchParams.toString())
    if (value) {
      params.set('label', value)
    } else {
      params.delete('label')
    }
    router.push(`/?${params.toString()}`)
  }

  return (
    <ChipGroup items={labels} value={current} changeAction={filterAction} />
  )
}

LabelFilter는 앱이 어디로 navigate할지를 결정하며, 자체 pending state는 갖지 않습니다.

LabelFilter decides where the app navigates and holds no pending state of its own.

Handle pending feedback internallypending feedback을 내부에서 처리하기

ChipGroup은 changeAction prop을 받아 자신의 startTransition 안에서 호출합니다. useOptimistic hook을 두 개 사용하는데, 하나는 선택된 chip용이고, 다른 하나는 ancestor component가 style 기준으로 삼을 수 있는 data-pending attribute용입니다:

ChipGroup accepts a changeAction prop and calls it inside its own startTransition. It uses two useOptimistic hooks: one for the selected chip, and one for the data-pending attribute that ancestor components can style against:

TScomponents/ui/chip-group.tsx
'use client'

import { startTransition, useOptimistic } from 'react'

export function ChipGroup({ items, value, changeAction }) {
  const [optimisticValue, setOptimisticValue] = useOptimistic(value)
  const [isPending, setIsPending] = useOptimistic(false)

  function handleClick(newValue) {
    startTransition(async () => {
      setOptimisticValue(newValue)
      setIsPending(true)
      await changeAction(newValue)
    })
  }

  return (
    <div className="flex gap-1.5" data-pending={isPending ? '' : undefined}>
      {items.map((item) => (
        <button
          key={item.value}
          onClick={() =>
            handleClick(item.value === optimisticValue ? null : item.value)
          }
          className={item.value === optimisticValue ? 'active' : ''}
        >
          {item.label}
        </button>
      ))}
    </div>
  )
}

consumer는 callback(changeAction)을 넘기고, design component가 그것을 transition 안에서 실행합니다. 관례상 action이라는 이름이거나 Action으로 끝나는 prop은 이런 동작을 나타냅니다. 이 패턴은 React 문서의 Exposing action props from components를 참고하세요.

The consumer passes a callback (changeAction), and the design component runs it inside a transition. By convention, props named action or suffixed with Action signal this behavior. See Exposing action props from components in the React docs for this pattern.

ChipGroup root element의 data-pending attribute 덕분에 ancestor component는 별도의 조율 없이 CSS로 반응할 수 있습니다. home page의 board는 group-has-data-pending:opacity-50을 사용해 transition이 실행되는 동안 board를 skeleton으로 바꾸지 않고 흐리게 표시합니다. ChipGroup이 group element 안에서 render되므로, 어떤 ancestor든 이 attribute를 styling에 사용할 수 있습니다.

The data-pending attribute on the ChipGroup root element lets ancestor components react through CSS without any coordination. The board on the home page uses group-has-data-pending:opacity-50 to dim while the transition runs, without replacing the board with a skeleton. Because ChipGroup renders inside the group element, the attribute is available to any ancestor for styling.

Good to know

group-has-data-pending:과 has-data-pending:은 CSS :has() selector로 compile되며, 브라우저는 data-pending이 toggle될 때마다 기준이 되는 subtree 전체를 다시 평가합니다. 여기서는 board가 filter 한 번당 두 번만 toggle하고 dragging(5단계)은 의도적으로 이를 건너뛰기 때문에 비용이 적습니다. 범위가 넓은 :has() anchor가 dragging이나 scrolling처럼 빈번한 interaction에서 toggle된다면 큰 subtree에 대한 반복 재계산이 누적되므로, 그럴 때는 대신 client state를 사용하세요.

group-has-data-pending: and has-data-pending: compile to the CSS :has() selector, which the browser re-evaluates over the anchored subtree whenever data-pending toggles. That stays cheap here because the board toggles it only twice per filter, and dragging (Step 5) deliberately skips it. Reach for client state instead when a broad :has() anchor toggles on a high-frequency interaction like dragging or scrolling, where repeated recalculation over a large subtree adds up.

이제 "Frontend" chip이 현재 frame에서 바로 강조 표시됩니다. filter된 데이터가 load되는 동안 board가 흐려졌다가, filter된 task로 업데이트됩니다.

The "Frontend" chip now highlights on the current frame. The board dims while the filtered data loads, then updates with the filtered tasks.

Step 4: Add comments with instant feedback4단계: 즉각적인 feedback과 함께 comment 추가하기

task 상세 페이지에는 comment section이 있습니다. comment를 제출하면 server에 새 데이터가 기록되지만, 저장된 목록은 server component가 render하므로 다음 server render가 도착하기 전까지는 새 comment를 포함할 수 없습니다.

The task detail page has a comment section. Submitting a comment writes new data on the server, but a server component renders the persisted list, so it can't include the new comment until the next server render arrives.

여기서 comment form은 input에 controlled state를 사용하고 Server Function을 직접 호출합니다:

Here a comment form uses controlled state for the input and calls the Server Function directly:

TSfeatures/task/components/comment-form.tsx
'use client'

import { useState } from 'react'
import { addComment } from '@/features/task/task-actions'

export function CommentForm({ taskId }) {
  const [content, setContent] = useState('')

  async function handleSubmit() {
    if (!content.trim()) return
    await addComment(taskId, content)
    setContent('')
  }

  return (
    <div>
      <input
        value={content}
        onChange={(e) => setContent(e.target.value)}
        placeholder="Write a comment..."
      />
      <button onClick={handleSubmit}>Send</button>
    </div>
  )
}

이 버전에서는 submit 시 Server Function이 실행되지만, server가 응답할 때까지 input은 채워진 채로 남아 있고 목록도 바뀌지 않습니다.

With this version, the Server Function runs on submit, but the input stays filled and the list doesn't change until the server responds.

comment 목록을 두 부분으로 나누세요. server component는 저장된 comment를 render하고, client component는 빈 초기 배열을 넣은 useOptimistic([])로 pending 상태인 comment만 추적합니다. transition이 완료되고 최신 데이터와 함께 새 render가 도착하면 pending 목록은 빈 상태로 초기화되고, 실제 comment가 server가 render한 목록에 나타납니다:

Split the comment list into two parts. A server component renders the persisted comments, and a client component tracks only the pending comments using useOptimistic([]) with an empty initial array. When the transition completes and a new render arrives with fresh data, the pending list resets to empty and the real comment appears in the server-rendered list:

TSfeatures/task/components/optimistic-comments.tsx
'use client'

import { useOptimistic, useRef } from 'react'
import { addComment } from '@/features/task/task-actions'
import { CommentCard } from './comment-card'

export function OptimisticComments({ taskId }) {
  const [pendingComments, setPendingComments] = useOptimistic([])
  const formRef = useRef(null)

  return (
    <>
      <form
        ref={formRef}
        action={async (formData) => {
          const content = formData.get('content')?.trim()
          if (!content) return
          formRef.current?.reset()

          const id = crypto.randomUUID()
          setPendingComments((current) => [
            {
              id,
              content,
              userName: 'You',
              createdAt: new Date().toISOString(),
            },
            ...current,
          ])

          await addComment(taskId, content)
        }}
      >
        <input name="content" placeholder="Write a comment..." required />
        <button type="submit">Send</button>
      </form>
      {pendingComments.map((comment) => (
        <CommentCard key={comment.id} comment={comment} pending />
      ))}
    </>
  )
}

submit 시 세 가지 일이 일어납니다:

Three things happen on submit:

  1. formRef.current?.reset()이 DOM을 직접 조작해 input을 비웁니다. transition 안에서 useState setter는 transition이 완료될 때까지 지연되지만, useOptimistic setter와 formRef.reset() 같은 직접 DOM 호출은 현재 frame에 적용됩니다.
  2. setPendingComments가 client에서 생성한 UUID와 함께 새 comment를 pending 목록에 추가합니다.
  3. form action이 transition 안에서 handler를 실행합니다.
  1. formRef.current?.reset() clears the input through direct DOM manipulation. Inside a transition, useState setters are deferred until the transition completes, but useOptimistic setters and direct DOM calls like formRef.reset() apply on the current frame.
  2. setPendingComments adds the new comment to the pending list with a client-generated UUID.
  3. The form action runs the handler inside a transition.

server component는 그 옆에 실제 목록을 render합니다:

The server component renders the real list alongside it:

import { getComments } from '@/features/task/task-queries'

  return (
    <div>
      <OptimisticComments taskId={taskId} />

이제 submit하면 input이 비워지고 목록 맨 위에 흐릿한 comment card가 나타납니다. server가 확인하면 흐릿한 card는 사라지고 server가 render한 목록에 실제 comment가 그 자리를 대신합니다.

The input now clears on submit and a faded comment card appears at the top of the list. When the server confirms, the faded card disappears and the real comment takes its place in the server-rendered list.

Step 5: Move cards between columns5단계: column 사이로 card 옮기기

board에는 Todo, In Progress, Done 세 개의 column이 있습니다. 각 column은 server가 제공한 tasks prop의 task를 render합니다.

The board has three columns: Todo, In Progress, and Done. Each column renders tasks from the server-provided tasks prop.

card를 drop하면 새 status를 기록하는 Server Function이 시작됩니다. 다음 server render가 도착할 때까지 tasks prop은 바뀌지 않으므로, client에는 pending 중인 이동을 위한 임시 task 목록이 필요합니다.

Dropping a card starts a Server Function that writes the new status. The tasks prop doesn't change until the next server render arrives, so the client needs a temporary task list for the pending move.

여기서는 drop 시 Server Function을 호출합니다:

Here the Server Function is called on drop:

TSfeatures/task/components/board.tsx
'use client'

import { use } from 'react'
import { updateStatus } from '@/features/task/task-actions'

export function Board({ tasksPromise }) {
  const tasks = use(tasksPromise)

  function handleDrop(targetStatus, taskId) {
    updateStatus(taskId, targetStatus)
  }

  // ...render columns from tasks
}

component는 parent server component에서 promise를 받아(1단계의 <Suspense> boundary 참고) use로 unwrap합니다. 이 버전에서는 "Todo"에서 "In Progress"로 drag한 card가 server가 업데이트를 처리하는 동안 예전 column에 머물러 있다가, response가 도착한 뒤에야 새 column으로 점프합니다.

The component receives a promise from the parent server component (see Step 1's <Suspense> boundary) and unwraps it with use. With this version, a card dragged from "Todo" to "In Progress" stays in the old column while the server processes the update, then jumps to the new column after the response arrives.

reducer와 함께 useOptimistic을 추가해 현재 frame에서 card의 status를 다시 매핑하세요. reducer는 전체 task 목록과, 어떤 card가 어디로 이동했는지 설명하는 action을 받습니다:

Add useOptimistic with a reducer to remap the card's status on the current frame. The reducer receives the full task list and an action describing which card moved where:

TSfeatures/task/components/board.tsx
'use client'

import { startTransition, use, useOptimistic } from 'react'
import { toast } from 'sonner'
import { updateStatus } from '@/features/task/task-actions'

export function Board({ tasksPromise }) {
  const tasks = use(tasksPromise)
  const [optimisticTasks, moveTask] = useOptimistic(
    tasks,
    (currentTasks, action: { taskId: string; status: Status }) =>
      currentTasks.map((t) =>
        t.id === action.taskId ? { ...t, status: action.status } : t
      )
  )

  function handleDrop(targetStatus, taskId) {
    startTransition(async () => {
      moveTask({ taskId, status: targetStatus })
      const result = await updateStatus(taskId, targetStatus)
      if (!result.success) toast.error(result.error)
    })
  }

  return (
    <div className="grid grid-cols-3 gap-4">
      {columns.map((col) => (
        <Column
          key={col.status}
          tasks={optimisticTasks.filter((t) => t.status === col.status)}
          onDrop={(taskId) => handleDrop(col.status, taskId)}
        />
      ))}
    </div>
  )
}

reducer는 task 목록을 map하면서 drag된 card의 status만 업데이트하고 나머지는 그대로 둡니다. drag 도중에 polling이나 다른 사용자의 mutation 등으로 background refresh가 도착하면, React는 업데이트된 base 데이터로 reducer를 다시 실행하므로 optimistic 이동이 최신 데이터 위에 얹혀집니다. task가 더 이상 존재하지 않으면 Server Function은 error 결과를 반환하고, client는 이를 toast로 표시합니다.

The reducer maps over the task list and updates the status of the dragged card, leaving the rest unchanged. If a background refresh arrives mid-drag, for example from polling or another user's mutation, React re-runs the reducer with the updated base data so the optimistic move sits on top of fresh data. The Server Function returns an error result when the task no longer exists, which the client displays in a toast.

이 단계에서는 useTransition 대신 독립형 startTransition을 사용합니다. hook의 isPending이 3단계의 board fade를 trigger하기 때문입니다. optimistic 이동이 이미 시각적 feedback을 제공하므로 pending 표시는 필요 없습니다. Server Function이 예상된 error를 반환하면 card는 원래 위치로 되돌아갑니다. 예상치 못한 error는 가장 가까운 error boundary로 전달됩니다.

This step uses the standalone startTransition instead of useTransition because the hook's isPending would trigger the board fade from Step 3. The optimistic move already covers the visual feedback, so no pending indicator is needed. If the Server Function returns an expected error, the card reverts. Unexpected errors are forwarded to the nearest error boundary.

이제 "Todo"에서 "In Progress"로 drag한 card는 손을 떼는 순간 대상 column에 놓입니다.

A card dragged from "Todo" to "In Progress" now lands in the target column the moment you release.

Step 6: Manage form lifecycle6단계: form lifecycle 관리하기

board에는 create dialog를 여는 "New Task" button이 있습니다. form action은 server에서 task를 만든 다음 board를 refresh합니다.

The board has a "New Task" button that opens a create dialog. The form action creates the task on the server, then refreshes the board.

dialog는 action이 pending인 동안 세 가지 client state를 조율합니다: submit button, field 값, 그리고 dialog가 열려 있는지 여부입니다. useActionState가 이 세 가지를 모두 처리합니다.

The dialog coordinates three pieces of client state while the action is pending: the submit button, the field values, and whether the dialog is open. useActionState handles all three.

여기서는 form이 submission state를 수동으로 관리하고 onSubmit handler에서 Server Function을 호출합니다:

Here a form manages submission state manually and calls the Server Function in an onSubmit handler:

TSfeatures/task/components/create-task-modal.tsx
'use client'

import { useState } from 'react'
import { createTask } from '@/features/task/task-actions'

export function CreateTaskModal() {
  const [isOpen, setIsOpen] = useState(false)
  const [isSubmitting, setIsSubmitting] = useState(false)

  async function handleSubmit(e) {
    e.preventDefault()
    const formData = new FormData(e.currentTarget)
    const title = formData.get('title')
    if (!title.trim()) return

    setIsSubmitting(true)
    await createTask({ title /* ... */ })
    setIsSubmitting(false)
    setIsOpen(false)
  }

  return (
    <Dialog open={isOpen} onOpenChange={setIsOpen}>
      <form onSubmit={handleSubmit}>
        <input name="title" placeholder="Task title..." required />
        <button type="submit" disabled={isSubmitting}>
          {isSubmitting ? 'Creating...' : 'Create Task'}
        </button>
      </form>
    </Dialog>
  )
}

이 버전에서는 submit handler가 실행되지만, 두 개의 별도 useState 호출이 pending state를 관리합니다. setIsOpen(false)가 transition 밖에서 실행되기 때문에, board에 새 task가 보이기 전에 dialog가 닫힙니다. 또한 reset key를 직접 추적하지 않으면 form field는 submission이 끝난 뒤에도 값을 그대로 유지합니다.

With this version, the submit handler runs, but two separate useState calls manage the pending state. The dialog closes before the board shows the new task, because setIsOpen(false) fires outside of a transition. The form fields also keep their values across submissions unless you track a reset key yourself.

useActionState는 세 가지 관심사를 모두 처리합니다: button을 위한 isPending, field를 위한 key 기반 reset, 그리고 dialog 닫기를 감싸는 처리입니다:

useActionState handles all three concerns: isPending for the button, key-based reset for the fields, and a wrap around the dialog close:

TSfeatures/task/components/create-task-modal.tsx
'use client'

import { useActionState, startTransition, useState } from 'react'
import { createTask } from '@/features/task/task-actions'

export function CreateTaskModal() {
  const [isOpen, setIsOpen] = useState(false)

  const [{ key }, formAction, isPending] = useActionState(
    async (prev, formData) => {
      const title = String(formData.get('title'))
      if (!title.trim()) return prev

      await createTask({
        title,
        description: String(formData.get('description')),
        status: 'todo',
        priority: 'medium',
      })

      startTransition(() => setIsOpen(false))
      return { key: prev.key + 1 }
    },
    { key: 0 }
  )

  return (
    <Dialog open={isOpen} onOpenChange={setIsOpen}>
      <form action={formAction}>
        <div key={key}>
          <input name="title" placeholder="Task title..." required />
          <input name="description" placeholder="Describe the task..." />
        </div>
        <button type="submit" disabled={isPending}>
          {isPending ? 'Creating...' : 'Create Task'}
        </button>
      </form>
    </Dialog>
  )
}

반환된 state의 key가 form reset을 제어합니다. 성공하면 key가 증가하고, 이에 따라 <div key={key}>가 다시 mount되면서 그 안의 모든 input이 초기화됩니다.

The key in the returned state controls form reset. On success, key increments, which remounts the <div key={key}> and resets every input inside it.

useActionState는 action을 transition으로 실행하므로, createTask가 실행되는 동안 dialog는 열린 채로 있고 isPending은 true로 유지됩니다. await 이후의 state 업데이트는 자동으로 그 transition에 포함되지 않으므로, setIsOpen(false)를 startTransition으로 감싸야 닫기 동작이 transition의 일부로 실행됩니다.

useActionState runs the action as a transition, so the dialog stays open and isPending stays true while createTask runs. State updates after the await aren't automatically part of that transition, so wrapping setIsOpen(false) in startTransition runs the close as part of the transition.

이렇게 감싸 두면 React는 dialog 닫기와 createTask 안의 refresh()가 trigger하는 board 업데이트를 batch 처리하므로, dialog가 닫히는 순간 새 task가 나타납니다. 감싸지 않으면 dialog가 먼저 닫히고 board는 한 frame 뒤에 업데이트됩니다.

With that wrap in place, React batches the dialog close with the board update that refresh() triggers inside createTask, so the new task appears at the moment the dialog closes. Without it, the dialog closes first and the board updates a frame later.

Good to know

이 한계는 React 문서의 React doesn't treat my state update after await as a transition에 설명되어 있습니다. 이 문제가 고쳐지기 전까지는 await 이후의 state 업데이트를 startTransition으로 감싸는 것이 권장 workaround입니다.

This limitation is documented in React under React doesn't treat my state update after await as a transition. Until it's fixed, wrapping post-await state updates in startTransition is the recommended workaround.

toast 같은 side effect도 바로 이 await 이후 구간에 두어야 합니다:

The same post-await window is where side effects like toasts belong:

await createTask({
  /* … */
})

startTransition(() => setIsOpen(false))
toast.success('Task created')

analytics, toast, focus 변경처럼 render되는 state에 영향을 주지 않는 side effect는 await가 resolve된 뒤에 실행됩니다. 이들은 React state를 업데이트하지 않으므로 transition이 필요 없습니다.

Side effects that don't affect rendered state, such as analytics, toasts, and focus changes, run after the await resolves. They don't need a transition because they don't update React state.

이제 submit하면 button 텍스트가 "Creating..."으로 바뀌고 흐려집니다. server가 응답하면 field가 비워지고, dialog가 닫히고, board에 새 task가 나타나며, toast가 action을 확인해 줍니다.

The button text now changes to "Creating..." and dims on submit. When the server responds, the fields clear, the dialog closes, the new task appears on the board, and a toast confirms the action.

Good to know

함께 제공되는 앱은 modal에 status, priority, assignee, label picker를 추가합니다. 패턴은 같습니다: hidden input이 각 picker의 state를 추적하고, 성공하면 key가 이들을 모두 초기화합니다.

Step 7: Signal pending deletion to a parent7단계: pending 중인 삭제를 parent에 알리기

각 comment card에는 server에서 comment를 삭제하는 delete button이 있으며, comment는 다음 render 이후 목록에서 사라집니다.

Each comment card has a delete button that removes the comment on the server, and the comment disappears from the list after the next render.

click과 그 render 사이에도 card는 여전히 예전 데이터를 보여 줍니다. 목록 자체는 pending 중인 삭제를 표시할 수 없으므로, 신호는 button에서 나와야 합니다.

Between the click and that render, the card still shows the old data. The list itself can't show the pending removal, so the signal has to come from the button.

이 단계는 3단계의 data-pending CSS hook을 재사용하지만, useTransition의 isPending 대신 useOptimistic(false)로 이를 구동합니다.

This step reuses the data-pending CSS hook from Step 3, but drives it from useOptimistic(false) instead of the isPending from useTransition.

여기서는 Server Function을 직접 호출합니다:

action을 <form>으로 감싸고, useOptimistic(false)로 pending state를 추적하고, 이를 data-pending attribute로 노출하세요. action을 deleteAction prop으로 받아서 parent comment card가 CSS로 반응할 수 있게 합니다:

Wrap the action in a <form>, track pending state with useOptimistic(false), and expose it through a data-pending attribute. Accept the action as a deleteAction prop so the parent comment card can react with CSS:

TSfeatures/task/components/delete-button.tsx
'use client'

import { useOptimistic } from 'react'
import { Trash2 } from 'lucide-react'

export function DeleteButton({
  deleteAction,
}: {
  deleteAction: () => void | Promise<void>
}) {
  const [isPending, setIsPending] = useOptimistic(false)

  return (
    <form
      action={async () => {
        setIsPending(true)
        await deleteAction()
      }}
    >
      <button
        type="submit"
        disabled={isPending}
        data-pending={isPending ? '' : undefined}
        aria-label="Delete comment"
      >
        <Trash2 className="size-3" />
      </button>
    </form>
  )
}

The parent comment card uses Tailwind's has-data-pending: variant to fade itself when any descendant sets the data-pending attribute. Step 8: Make repeat navigation instant8단계: 반복 navigation을 즉각적으로 만들기

지금까지의 모든 패턴은 단일 interaction을 매끄럽게 만듭니다. navigation을 오가면 같은 read가 다시 실행되고 같은 fallback이 다시 그려집니다. 재사용 가능한 read를 caching하고 실제 request와 함께 prefetching하면, 데이터 모델을 브라우저로 옮기지 않고도 그 간극을 메울 수 있습니다.

Every pattern so far smooths a single interaction. Across navigations, the same reads rerun and the same fallbacks paint again. Caching the reusable reads and prefetching them with the real request closes that gap without moving the data model into the browser.

이 단계는 Next.js 16에 도입된 Cache Components를 사용합니다. 1단계부터 7단계까지는 이것 없이도 동작합니다. Cache Components를 사용하지 않는다면 Caching without Cache Components를 참고하세요.

This step uses Cache Components, introduced in Next.js 16. Steps 1 through 7 work without it. If you aren't using Cache Components, see Caching without Cache Components.

next.config.ts에서 활성화하세요:

Enable it in next.config.ts:

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
}

export default nextConfig

Cache Components를 활성화하면 이 단계의 route뿐 아니라 모든 route에 prerender 검증이 적용됩니다. <Suspense> 밖에서 cookies(), headers(), searchParams 같은 request 데이터를 읽는 route는 이제 prerendering을 block하므로 1단계와 같은 처리가 필요합니다. 기존 앱에서 이를 켜려면 Migrating to Cache Components를 참고하세요.

Enabling Cache Components applies prerender validation across every route, not just the ones in this step. A route that reads request data such as cookies(), headers(), or searchParams outside <Suspense> now blocks prerendering and needs the Step 1 treatment. To turn it on in an existing app, see Migrating to Cache Components.

Cache reusable reads재사용 가능한 read cache하기

각 server read마다 여러 request에 걸쳐 재사용해야 하는지, 그리고 각 write가 그것을 정확하게 invalidate할 수 있는지 따져 보세요. task는 cache하기에 충분히 안정적이고 id별로 명확한 tag를 가집니다:

For each server read, ask whether it should be reused across requests and whether each write can invalidate it precisely. A task is stable enough to cache and has a clear per-id tag:

TSfeatures/task/task-queries.ts
import { cacheLife, cacheTag } from 'next/cache'
import { getTaskById } from '@/lib/db'

export async function getTask(id: string) {
  'use cache'
  cacheLife('hours')
  cacheTag('tasks', `task-${id}`)

  return getTaskById(id)
}

id별 tag task-${id}는 개별 task에 고유한 handle을 부여합니다. 더 넓은 범위의 tasks tag는 목록을 담당합니다. cache scoping('use cache: private', 'use cache: remote'), cache lifetime, tag 패턴은 Caching 가이드를 참고하세요.

The per-id tag task-${id} gives a single task its own handle. The broader tasks tag covers the list. See the Caching guide for cache scoping ('use cache: private', 'use cache: remote'), cache lifetimes, and tag patterns.

Invalidate from mutationsmutation에서 invalidate하기

refresh()는 dynamic 작업을 다시 실행하지만 cache된 entry는 그대로 둡니다. 각 write가 건드린 tag에 대해서는 이를 updateTag로 바꾸세요:

refresh() reruns dynamic work but leaves cached entries in place. Replace it with updateTag for the tags each write touched:

TSfeatures/task/task-actions.ts
'use server'

import { updateTag } from 'next/cache'
import { updateTaskStatus } from '@/lib/db'

export async function updateStatus(taskId: string, newStatus: Status) {
  const updated = await updateTaskStatus(taskId, newStatus)
  if (!updated) {
    return { success: false as const, error: 'Task no longer exists' }
  }

  updateTag('tasks')
  updateTag(`task-${taskId}`)
  return { success: true as const, status: newStatus }
}

모든 Server Function은 같은 형태를 따릅니다: write를 실행한 다음, 바뀐 cache된 read에 대해 updateTag를 호출합니다. dynamic read에는 invalidate할 tag가 없으므로, 그런 mutation에는 refresh()를 사용하세요.

Every Server Function follows the same shape: run the write, then call updateTag for the cached reads that changed. Dynamic reads do not have tags to invalidate, so use refresh() for those mutations.

이 데모에서 comment thread는 dynamic으로 유지됩니다. 사용자는 열려 있는 task 페이지에서 현재 토론이 즉시 업데이트되기를 기대하기 때문입니다. comment를 추가하거나 삭제하면 refresh()가 호출되어, task cache는 그대로 둔 채 현재 route의 dynamic comment read를 다시 실행합니다. tag 패턴, 시간 기반 revalidation, route handler에서의 on-demand invalidation은 Revalidating 가이드를 참고하세요.

In this demo, the comment thread stays dynamic because readers expect the current discussion to update immediately on the open task page. Adding or deleting a comment calls refresh(), which reruns the dynamic comment read for the current route while leaving the task caches in place. See the Revalidating guide for tag patterns, time-based revalidation, and on-demand invalidation from route handlers.

Prefetch the destination with the real request실제 request로 목적지 prefetch하기

Partial Prefetching(Next.js 16.3 이상)에서 <Link>는 목적지의 App Shell, 즉 현재 사용자에 대해 여러 link가 공유하는 route 출력을 prefetch합니다. params와 searchParams는 link마다 다르기 때문에 shell에는 URL data가 포함되지 않습니다. prefetch={true}로 link를 per-link prefetching에 opt in하면 click 전에 그 URL data를 resolve할 수 있습니다:

Under Partial Prefetching (Next.js 16.3 and later), <Link> prefetches the destination's App Shell: the route output that is shared across links for the current user. The shell does not include URL data, because params and searchParams are link-specific. Opt the link into per-link prefetching with prefetch={true} to resolve that URL data ahead of the click:

TSfeatures/task/components/task-card.tsx
<Link href={`/task/${id}`} prefetch={true}>
  {/* … */}
</Link>

per-link prefetching은 사용자가 다음에 필요로 할 가능성이 높은 URL별 작업이 목적지에 있을 때 가장 유용합니다. cache된 read는 prefetch된 출력을 Client Cache에서 재사용하고 tag로 invalidate할 수 있게 해 줍니다. dynamic read도 click 전에 resolve될 수 있지만, prefetch할 때마다 실제 server 작업이 일어날 수 있습니다. 함께 제공되는 앱에서는 task card가 화면에 scroll되어 들어올 때 상세 페이지를 prefetch하므로, 사용자가 click할 즈음에는 즉시 그려집니다.

Per-link prefetching is most valuable when the destination has URL-specific work that users are likely to need next. Cached reads make the prefetched output reusable and tag-invalidatable in the Client Cache; dynamic reads can still resolve before the click, but each prefetch can do real server work. In the companion app, the task cards prefetch the detail page as they scroll into view, so it paints instantly by the time the user clicks.

The patterns in this guide combine a handful of primitives:

상황사용할 것
느린 데이터를 페이지를 block하지 않고 streaming해야 할 때<Suspense>
async 작업이 실행되는 동안 값을 업데이트해야 할 때useOptimistic
async 작업에 pending state, error 처리, 조율된 UI 업데이트가 필요할 때useTransition
form에 pending, reset, 결과 state가 필요할 때useActionState
다른 곳에서 일어나는 작업의 pending state를 ancestor가 표시해야 할 때CSS로 style한 data-pending attribute
재사용 가능한 read가 여러 request에 걸쳐 유지되고 write 후에도 최신 상태여야 할 때cacheTag와 함께 쓰는 'use cache', updateTag 또는 revalidateTag로 revalidate
인터랙티브 앱의 페이지 간 navigation이 즉각적으로 느껴져야 할 때Partial Prefetching을 사용한 <Link> prefetching, 그리고 URL data에 의존하는 콘텐츠에는 prefetch={true}를 통한 per-link prefetching
SituationUse
Slow data should stream in without blocking the page<Suspense>
A value should update while async work runsuseOptimistic
Async work needs pending state, error handling, or coordinated UI updatesuseTransition
A form needs pending, reset, and result stateuseActionState
An ancestor should show pending state for work happening elsewheredata-pending attribute styled with CSS
Reusable reads should survive across requests and stay fresh after writes'use cache' with cacheTag, revalidated by updateTag or revalidateTag
Navigation between pages of an interactive app should feel instant<Link> prefetching with Partial Prefetching, and per-link prefetching via prefetch={true} for content that depends on URL data

Most patterns mix two or more of these. Reach for whichever primitive fits the constraint you're solving.
