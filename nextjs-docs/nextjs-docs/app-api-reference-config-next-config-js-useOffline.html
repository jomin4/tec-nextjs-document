useOfflineexperimentaluseOffline

useOffline configuration option은 offline 연결 상태 감지와, 실패한 navigation, prefetch, Server Action request의 자동 retry를 활성화합니다. 활성화하면 Client Component에서 현재 offline 상태를 읽을 수 있는 useOffline hook도 제공됩니다.

The useOffline configuration option enables offline connectivity detection and automatic retry of failed navigation, prefetch, and Server Action requests. When enabled, it also exposes the useOffline hook for reading the current offline state from Client Components.

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    useOffline: true,
  },
}

export default nextConfig
module.exports = {
  experimental: {
    useOffline: true,
  },
}

활성화하면 Next.js는 다음을 수행합니다:

When enabled, Next.js will:

  • 브라우저의 offline과 online event를 listen해 연결 상태를 추적합니다.
  • navigation, prefetch, Server Action request에서 network 실패를 감지합니다.
  • offline인 동안 backoff를 적용하며 HEAD request로 연결 상태를 polling합니다.
  • 연결이 복구되면 막혀 있던 request를 자동으로 retry합니다.
  • next/offline에서 useOffline hook을 사용할 수 있게 합니다.
  • Listen for the browser's offline and online events to track connectivity.
  • Detect network failures on navigation, prefetch, and Server Action requests.
  • Poll for connectivity using HEAD requests with backoff while offline.
  • Automatically retry blocked requests once connectivity is restored.
  • Make the useOffline hook available from next/offline.

How retry worksretry 동작 방식

offline 상태에는 두 가지 경로 중 하나로 진입합니다:

The offline state is entered through one of two paths:

  • 브라우저 event. Next.js는 window.addEventListener('offline', ...) listener를 등록합니다. OS가 network interface가 끊겼다고 보고하면 즉시 offline 상태로 전환됩니다.
  • 실패한 fetch. navigation, prefetch, Server Action request의 fetch()가 abort나 timeout이 아닌 error로 reject되면 offline module이 호출됩니다. 이를 통해 브라우저는 여전히 navigator.onLine === true로 보고하지만 실제 request는 origin에 도달하지 못하는 경우(captive portal, 고장 난 DNS, 죽은 upstream)를 잡아냅니다.
  • Browser event. Next.js registers a window.addEventListener('offline', ...) listener. When the OS reports the network interface as down, the offline state flips on immediately.
  • Failed fetch. Any navigation, prefetch, or Server Action request whose fetch() rejects with a non-abort, non-timeout error calls into the offline module. This catches the case where the browser still reports navigator.onLine === true but the actual request cannot reach the origin (captive portal, broken DNS, dead upstream).

offline 상태가 되면 polling loop가 연결이 돌아왔는지 확인을 시도합니다.

Once in the offline state, a polling loop tries to confirm that connectivity has returned.

The connectivity check연결 확인

각 확인은 navigation이 사용하는 것과 같은 endpoint인 현재 페이지 URL로, RSC header를 설정한 HEAD request를 한 번 보냅니다. 이 request는 200 ms 후에 abort됩니다.

Each check issues a single HEAD request to the current page's URL with the RSC header set, the same endpoint navigations use. The request is aborted after 200 ms.

다음 두 결과는 "online"으로 간주됩니다:

Two outcomes count as "online":

  1. fetch가 정상적으로 resolve됩니다.
  2. 200 ms timeout으로 request가 abort됩니다. 실제로 offline인 request는 거의 즉시(DNS 또는 TCP error) 실패하므로, 200 ms 시점까지 아직 pending 상태라면 TCP handshake가 성공했고 server에 도달할 수 있다는 뜻입니다.
  1. The fetch resolves normally.
  2. The 200 ms timeout aborts the request. A truly offline request fails almost instantly (DNS or TCP error), so if it's still pending at 200 ms the TCP handshake succeeded and the server is reachable.

그 밖의 reject는 다음 확인을 예약합니다. offline 기간 중 framework fetch(navigation, prefetch, Server Action)가 성공해도 상태가 다시 online으로 전환됩니다.

Any other rejection schedules the next check. A successful framework fetch (navigation, prefetch, Server Action) during the offline period also flips the state back to online.

Backoff

확인 사이의 지연 시간은 exponential이 아니라 단계적으로 늘어나며, 최대 3초로 제한됩니다:

Delays between checks are stepped, not exponential, and capped at 3 seconds:

브라우저의 online event는 현재 대기를 건너뛰고 즉시 연결 확인을 실행합니다. 다음 예약된 tick을 기다리지 않고 재연결을 감지합니다.

The browser's online event short-circuits the current wait and runs a connectivity check immediately. Reconnection is detected without waiting for the next scheduled tick.

Giving up포기 조건

polling loop는 스스로 포기하지 않습니다. 확인이 성공하거나 페이지가 unload될 때까지 3초 간격(상한)으로 계속됩니다. 몇 시간 동안 offline이었다가 연결이 돌아온 기기도 polling loop가 다시 이어져 정상적으로 resolve됩니다.

The polling loop never gives up on its own. It continues at the 3-second cap until a check succeeds or the page unloads. A device that goes offline for hours and then regains connectivity will have its polling loop resume and resolve normally.

Retry of framework requestsframework request의 retry

offline 상태가 활성화된 동안 navigation, prefetch, Server Action은 새로 발생한 것이든 연결이 끊길 때 이미 진행 중이던 것이든 다음 연결 확인이 성공할 때까지 기다립니다. 확인이 성공하면 request는 한 번 실행되며, 추가 backoff는 적용되지 않습니다.

While the offline state is active, any navigation, prefetch, or Server Action waits for the next connectivity check to succeed, whether it was newly issued or already in flight when the connection dropped. When the check succeeds, the request runs once; no extra backoff applies.

network error로 실패하면 앱은 다시 offline 상태로 들어가고 polling loop가 다시 시작됩니다.

If it fails with a network error, the app re-enters the offline state and the polling loop starts again.

Traffic at reconnection재연결 시 traffic

하나의 client가 origin에 폭주하는 traffic을 만들어 내지는 않습니다:

A single client does not produce a runaway burst of traffic against its origin:

  • client가 offline인 동안 실패한 fetch()는 브라우저의 network layer에서 로컬로 reject됩니다. request는 origin에 전혀 도달하지 않습니다.
  • polling loop는 한 번에 하나의 HEAD request만 보내며, 지연 시간은 최대 3초로 제한됩니다. offline 기간 동안 다른 framework request는 origin으로 보내지지 않습니다.
  • 연결이 돌아오면 pending 상태였던 각 navigation과 Server Action이 한 번씩 실행됩니다. 마지막 navigation 시도만 pending 상태로 유지되며, 일반적인 form button은 action이 pending인 동안 비활성화됩니다.
  • prefetch는 한꺼번에 실행되지 않고 기존 prefetch queue를 통해 실행됩니다.
  • While the client is offline, a failed fetch() rejects locally at the browser's network layer. The request never reaches the origin.
  • The polling loop issues one HEAD request at a time, with delays capped at 3 seconds. No other framework requests are sent to the origin during the offline period.
  • When connectivity returns, each pending navigation and Server Action fires once. Only the last navigation attempt is kept pending, and a typical form button is disabled while its action is pending.
  • Prefetches run through the existing prefetch queue, not all at once.

실제로 이 기능이 server를 과부하시킬 가능성은 낮습니다. offline 사용자 한 명당 추가로 발생하는 traffic은 HEAD polling뿐이며, 이것도 연결이 돌아오는 즉시 멈춥니다. prefetch, Server Action, navigation은 장애가 없었을 때와 같은 횟수만큼, 다만 늦게 실행됩니다.

In practice, this feature is unlikely to flood your server. The only extra traffic it generates per offline user is the HEAD polling, which stops as soon as connectivity returns. Prefetches, Server Actions, and navigations fire the same number of times they would have without an outage, just delayed.
