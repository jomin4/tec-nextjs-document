serverActionsserverActions

Next.js 애플리케이션에서 Server Action의 동작을 설정하는 option입니다. 이 option들이 조정하는 security boundary를 포함해 Server Action이 어떻게 동작하는지는 Server Actions 가이드를 참고하세요.

Options for configuring Server Actions behavior in your Next.js application. For how Server Actions work, including the security boundary these options tune, see the Server Actions guide.

allowedOrigins

Server Action을 호출할 수 있는 추가 안전 host 목록입니다. CSRF 공격을 막기 위해 Next.js는 request의 Origin header에 있는 host를 x-forwarded-host 또는 host에서 가져온 앱 자체의 host와 비교하고, 둘이 다르면 action을 거부합니다. 지정하지 않으면 같은 origin만 허용됩니다. Origin header가 아예 없는 request는 거부되지 않고 warning과 함께 통과됩니다.

A list of extra safe hosts from which Server Actions can be invoked. To prevent CSRF attacks, Next.js compares the host in a request's Origin header against the app's own host, taken from x-forwarded-host or host, and rejects the action when the two differ. If not provided, only the same origin is allowed. A request that carries no Origin header at all is allowed through with a warning rather than rejected.

JSnext.config.js
/** @type {import('next').NextConfig} */

module.exports = {
  experimental: {
    serverActions: {
      allowedOrigins: ['my-proxy.com', '*.my-proxy.com'],
    },
  },
}

request의 Origin header 중 host만 항목과 match됩니다. host는 hostname이며, URL에 port가 있으면 port까지 포함합니다. https://my-proxy.com/checkout에서 온 request라면 my-proxy.com이고, https://my-proxy.com:8443/checkout에서 온 request라면 my-proxy.com:8443입니다. 항목도 같은 방식으로 작성하세요.

Only the host of the request's Origin header is matched against your entries, which is the hostname plus the port when the URL carries one. For a request from https://my-proxy.com/checkout, that is my-proxy.com. For one from https://my-proxy.com:8443/checkout, my-proxy.com:8443. Write your entries the same way.

항목은 두 가지 wildcard로 범위를 넓힐 수도 있습니다. *는 host의 label 정확히 하나를, **는 하나 이상의 label을 대신합니다. 그래서 위 예시에는 bare host용 항목과 그 subdomain용 항목, 두 개가 들어 있습니다.

Entries can also expand, through two wildcards: a * stands in for exactly one label of the host, and ** for one or more. That is why the example above lists two entries, one for the bare host and one for its subdomains.

부분 치환은 지원되지 않습니다. app-*.my-proxy.com 대신 *.my-proxy.com으로 작성하세요. **는 pattern의 시작 부분에서만 사용할 수 있습니다. port에는 wildcard를 쓸 수 없으므로 my-proxy.com:8443처럼, subdomain이라면 *.my-proxy.com:8443처럼 전부 적어야 합니다.

Partial replacement is not supported. Write *.my-proxy.com, rather than app-*.my-proxy.com. Using ** is only supported at the start of the pattern. A port cannot be wildcarded, so write it out in full: my-proxy.com:8443, or *.my-proxy.com:8443 for its subdomains.

reverse proxy 뒤에 있을 때, proxy가 x-forwarded-host로 public host를 전달하기만 하면 별도 항목은 필요 없습니다. proxy가 대신 자기 자신의 host를 전달하면 브라우저는 my-proxy.com을 보내는데 server는 localhost:3000 같은 값을 보고하게 되고, 바로 이런 불일치를 위해 이 목록이 있습니다. 추가해야 할 host는 server가 보고하는 내부 host가 아니라 브라우저 주소창에 보이는 host입니다.

Behind a reverse proxy, no entry is needed as long as the proxy forwards the public host in x-forwarded-host. When it forwards its own host instead, the browser sends my-proxy.com while the server reports something like localhost:3000, and that mismatch is what this list is for: the host visible in the browser's address bar is the one to add, not the internal one the server reports.

이 검사는 development뿐 아니라 production에서도 실행되므로, 이 목록은 로컬 작업뿐 아니라 deploy된 앱에도 적용됩니다.

The check runs in production as well as in development, so the list applies to your deployed app and not only to local work.

예를 들어 tunnel을 통한 remote development에서는 tunnel hostname을 두 곳에 넣어야 합니다. dev server가 자체 asset과 endpoint를 제공하도록 allowedDevOrigins에, 그리고 그곳에서 오는 action이 허용되도록 여기에 넣습니다:

For example, remote development through a tunnel needs the tunnel hostname in two places: in allowedDevOrigins, so the dev server serves its own assets and endpoints, and here, so actions from it are accepted:

JSnext.config.js
/** @type {import('next').NextConfig} */

module.exports = {
  allowedDevOrigins: ['*.tunnel.example.com'],
  experimental: {
    serverActions: {
      allowedOrigins: ['*.tunnel.example.com'],
    },
  },
}

bodySizeLimit

기본적으로 Server Action으로 보내는 request body의 최대 크기는 1MB입니다. 이는 대량의 데이터를 parse하느라 server 리소스를 과도하게 소비하는 것과 잠재적인 DDoS 공격을 막기 위한 것입니다.

By default, the maximum size of the request body sent to a Server Action is 1MB, to prevent the consumption of excessive server resources in parsing large amounts of data, as well as potential DDoS attacks.

하지만 serverActions.bodySizeLimit option으로 이 제한을 설정할 수 있습니다. byte 수 또는 bytes가 지원하는 문자열 형식을 사용할 수 있습니다. 예: 1000, '500kb', '3mb'.

However, you can configure this limit using the serverActions.bodySizeLimit option. It can take the number of bytes or any string format supported by bytes, for example 1000, '500kb' or '3mb'.

JSnext.config.js
/** @type {import('next').NextConfig} */

module.exports = {
  experimental: {
    serverActions: {
      bodySizeLimit: '2mb',
    },
  },
}

이 제한은 raw HTTP request body에 적용되며, multipart/form-data가 boundary, part header, field metadata를 위해 추가하는 byte도 포함됩니다. 설정한 값에 가까운 크기의 upload가 예상된다면 이 overhead를 위한 여유를 두세요. 일반적인 multipart upload라면 10–20 KB 정도를 추가로 잡는 것이 무난한 기준입니다.

The limit applies to the raw HTTP request body, including the bytes that multipart/form-data adds for boundaries, part headers, and field metadata. If you expect uploads close to the configured value, leave some room for this overhead. For typical multipart uploads, an additional 10–20 KB is a reasonable rule of thumb.

Enabling Server Actions (v13)Server Action 활성화하기 (v13)

Server Action은 Next.js 14에서 stable 기능이 되었고 기본으로 활성화되어 있습니다. 하지만 이전 버전의 Next.js를 사용한다면 experimental.serverActions를 true로 설정해 활성화할 수 있습니다.

Server Actions became a stable feature in Next.js 14, and are enabled by default. However, if you are using an earlier version of Next.js, you can enable them by setting experimental.serverActions to true.

JSnext.config.js
/** @type {import('next').NextConfig} */
const config = {
  experimental: {
    serverActions: true,
  },
}

module.exports = config
