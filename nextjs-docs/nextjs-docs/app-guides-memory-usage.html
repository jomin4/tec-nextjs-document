How to optimize memory usagememory 사용량 최적화하기

애플리케이션이 커지고 기능이 많아질수록 로컬에서 개발하거나 production build를 만들 때 더 많은 리소스가 필요할 수 있습니다.

As applications grow and become more feature rich, they can demand more resources when developing locally or creating production builds.

Next.js에서 memory를 최적화하고 흔히 발생하는 memory 문제를 해결하는 몇 가지 전략과 기법을 살펴보겠습니다.

Let's explore some strategies and techniques to optimize memory and address common memory issues in Next.js.

Reduce number of dependenciesdependency 개수 줄이기

dependency가 많은 애플리케이션일수록 memory를 더 많이 사용합니다.

Applications with a large amount of dependencies will use more memory.

Bundle Analyzer를 사용하면 애플리케이션에서 제거해 performance와 memory 사용량을 개선할 수 있는 큰 dependency를 조사할 수 있습니다.

The Bundle Analyzer can help you investigate large dependencies in your application that may be able to be removed to improve performance and memory usage.

Try experimental.webpackMemoryOptimizationsexperimental.webpackMemoryOptimizations 사용해 보기

v15.0.0부터 next.config.js 파일에 experimental.webpackMemoryOptimizations: true를 추가해 Webpack의 동작을 바꿀 수 있습니다. 이렇게 하면 최대 memory 사용량이 줄어들지만 compile 시간이 약간 늘어날 수 있습니다.

Starting in v15.0.0, you can add experimental.webpackMemoryOptimizations: true to your next.config.js file to change behavior in Webpack that reduces max memory usage but may increase compilation times by a slight amount.

Good to know

이 기능은 먼저 더 많은 프로젝트에서 테스트하기 위해 현재 experimental 상태이지만, 위험도는 낮은 것으로 간주됩니다.

This feature is currently experimental to test on more projects first, but it is considered to be low-risk.

Run next build with --experimental-debug-memory-usage--experimental-debug-memory-usage로 next build 실행하기

14.2.0부터 next build --experimental-debug-memory-usage를 실행하면, build 내내 heap 사용량과 garbage collection 통계 같은 memory 사용 정보를 Next.js가 계속 출력하는 모드로 build를 실행할 수 있습니다. memory 사용량이 설정된 한도에 가까워지면 heap snapshot도 자동으로 생성됩니다.

Starting in 14.2.0, you can run next build --experimental-debug-memory-usage to run the build in a mode where Next.js will print out information about memory usage continuously throughout the build, such as heap usage and garbage collection statistics. Heap snapshots will also be taken automatically when memory usage gets close to the configured limit.

Good to know

이 기능은 Webpack build worker option과 호환되지 않습니다. 이 option은 custom webpack config가 없으면 자동으로 활성화됩니다.

This feature is not compatible with the Webpack build worker option which is auto-enabled unless you have custom webpack config.

Record a heap profileheap profile 기록하기

memory 문제를 찾으려면 Node.js에서 heap profile을 기록하고 Chrome DevTools에서 불러와 memory leak의 잠재적인 원인을 파악할 수 있습니다.

To look for memory issues, you can record a heap profile from Node.js and load it in Chrome DevTools to identify potential sources of memory leaks.

터미널에서 Next.js build를 시작할 때 Node.js에 --heap-prof flag를 전달하세요:

In your terminal, pass the --heap-prof flag to Node.js when starting your Next.js build:

node --heap-prof node_modules/next/dist/bin/next build

build가 끝나면 Node.js가 .heapprofile 파일을 생성합니다.

At the end of the build, a .heapprofile file will be created by Node.js.

Chrome DevTools에서 Memory tab을 열고 "Load Profile" 버튼을 클릭하면 이 파일을 시각화할 수 있습니다.

In Chrome DevTools, you can open the Memory tab and click on the "Load Profile" button to visualize the file.

Analyze a snapshot of the heapheap snapshot 분석하기

inspector 도구를 사용해 애플리케이션의 memory 사용량을 분석할 수 있습니다.

You can use an inspector tool to analyze the memory usage of the application.

next build 또는 next dev command를 실행할 때 command 앞에 NODE_OPTIONS=--inspect를 붙이세요. 그러면 기본 port에서 inspector agent가 노출됩니다. 사용자 코드가 시작되기 전에 멈추고 싶다면 대신 --inspect-brk를 전달할 수 있습니다. process가 실행되는 동안 Chrome DevTools 같은 도구로 debugging port에 연결해 heap snapshot을 기록하고 분석하면 어떤 memory가 유지되고 있는지 확인할 수 있습니다.

When running the next build or next dev command, add NODE_OPTIONS=--inspect to the beginning of the command. This will expose the inspector agent on the default port. If you wish to break before any user code starts, you can pass --inspect-brk instead. While the process is running, you can use a tool such as Chrome DevTools to connect to the debugging port to record and analyze a snapshot of the heap to see what memory is being retained.

14.2.0부터는 --experimental-debug-memory-usage flag와 함께 next build를 실행해 heap snapshot을 더 쉽게 생성할 수도 있습니다.

Starting in 14.2.0, you can also run next build with the --experimental-debug-memory-usage flag to make it easier to take heap snapshots.

이 모드로 실행하는 동안에는 언제든 process에 SIGUSR2 signal을 보내면 process가 heap snapshot을 생성합니다.

While running in this mode, you can send a SIGUSR2 signal to the process at any point, and the process will take a heap snapshot.

heap snapshot은 Next.js 애플리케이션의 프로젝트 root에 저장되며, Chrome DevTools 같은 아무 heap analyzer에서나 불러와 어떤 memory가 유지되고 있는지 확인할 수 있습니다. 이 모드는 아직 Webpack build worker와 호환되지 않습니다.

The heap snapshot will be saved to the project root of the Next.js application and can be loaded in any heap analyzer, such as Chrome DevTools, to see what memory is retained. This mode is not yet compatible with Webpack build workers.

자세한 내용은 heap snapshot을 기록하고 분석하는 방법을 참고하세요.

See how to record and analyze heap snapshots for more information.

Webpack build worker

Webpack build worker를 사용하면 Webpack compile을 별도의 Node.js worker 안에서 실행할 수 있어, build 중 애플리케이션의 memory 사용량이 줄어듭니다.

The Webpack build worker allows you to run Webpack compilations inside a separate Node.js worker which will decrease memory usage of your application during builds.

v14.1.0부터는 애플리케이션에 custom Webpack configuration이 없으면 이 option이 기본으로 활성화됩니다.

This option is enabled by default if your application does not have a custom Webpack configuration starting in v14.1.0.

이전 버전의 Next.js를 사용하거나 custom Webpack configuration이 있다면 next.config.js에서 experimental.webpackBuildWorker: true를 설정해 이 option을 활성화할 수 있습니다.

If you are using an older version of Next.js or you have a custom Webpack configuration, you can enable this option by setting experimental.webpackBuildWorker: true inside your next.config.js.

Good to know

이 기능은 일부 custom Webpack plugin과 호환되지 않을 수 있습니다.

This feature may not be compatible with all custom Webpack plugins.

Disable Webpack cacheWebpack cache 비활성화하기

Webpack cache는 build 속도를 높이기 위해 생성된 Webpack module을 memory 및/또는 디스크에 저장합니다. 이는 performance에 도움이 되지만, cache된 데이터를 저장하느라 애플리케이션의 memory 사용량도 늘어납니다.

The Webpack cache saves generated Webpack modules in memory and/or to disk to improve the speed of builds. This can help with performance, but it will also increase the memory usage of your application to store the cached data.

애플리케이션에 custom Webpack configuration을 추가해 이 동작을 비활성화할 수 있습니다:

You can disable this behavior by adding a custom Webpack configuration to your application:

JSnext.config.mjs
/** @type {import('next').NextConfig} */
const nextConfig = {
  webpack: (
    config,
    { buildId, dev, isServer, defaultLoaders, nextRuntime, webpack }
  ) => {
    if (config.cache && !dev) {
      config.cache = Object.freeze({
        type: 'memory',
      })
    }
    // Important: return the modified config
    return config
  },
}

export default nextConfig

Disable static analysisstatic analysis 비활성화하기

type checking은 특히 큰 프로젝트에서 memory를 많이 필요로 할 수 있습니다. 하지만 대부분의 프로젝트에는 이런 작업을 이미 처리하는 전용 CI runner가 있습니다. build의 "Running TypeScript" 단계에서 out-of-memory 문제가 발생하면 build 중에 이 작업을 비활성화할 수 있습니다:

Typechecking may require a lot of memory, especially in large projects. However, most projects have a dedicated CI runner that already handles these tasks. When the build produces out-of-memory issues during the "Running TypeScript" step, you can disable this task during builds:

JSnext.config.mjs
/** @type {import('next').NextConfig} */
const nextConfig = {
  typescript: {
    // !! WARN !!
    // Dangerously allow production builds to successfully complete even if
    // your project has type errors.
    // !! WARN !!
    ignoreBuildErrors: true,
  },
}

export default nextConfig
  • TypeScript Error 무시하기
  • Ignoring TypeScript Errors

이렇게 하면 type error 때문에 잘못된 deploy가 만들어질 수 있다는 점을 기억하세요. static analysis가 완료된 뒤에만 build를 production으로 promote하기를 강력히 권장합니다. Vercel에 deploy한다면 staging deployment 가이드를 참고해 custom 작업이 성공한 뒤 build를 production으로 promote하는 방법을 알아보세요.

Keep in mind that this may produce faulty deploys due to type errors. We strongly recommend only promoting builds to production after static analysis has completed. If you deploy to Vercel, you can check out the guide for staging deployments to learn how to promote builds to production after custom tasks have succeeded.

Disable source mapssource map 비활성화하기

source map을 생성하면 build 과정에서 추가 memory가 소모됩니다.

Generating source maps consumes extra memory during the build process.

Next.js configuration에 productionBrowserSourceMaps: false와 experimental.serverSourceMaps: false를 추가해 source map 생성을 비활성화할 수 있습니다.

You can disable source map generation by adding productionBrowserSourceMaps: false and experimental.serverSourceMaps: false to your Next.js configuration.

Next.js는 next build의 prerender 단계에서 기본적으로 source map을 사용합니다. 그 단계("Generating static pages" 이후)에서 계속 memory 문제가 발생한다면, Next.js configuration에 enablePrerenderSourceMaps: false를 추가해 그 단계의 source map을 비활성화해 볼 수 있습니다.

Next.js will use source maps by default during the prerender phase of next build. If you consistently encounter memory issues during that phase (after "Generating static pages"), you can try disabling source maps in that phase by adding enablePrerenderSourceMaps: false to your Next.js configuration.

Good to know

일부 plugin은 source map을 켤 수 있으며, 이를 비활성화하려면 custom configuration이 필요할 수 있습니다.

Some plugins may turn on source maps and may require custom configuration to disable.

Edge memory issuesEdge memory 문제

Next.js v14.1.3에서 Edge runtime 사용 시의 memory 문제가 수정되었습니다. 이 버전(또는 그 이후 버전)으로 업데이트해 문제가 해결되는지 확인해 보세요.

Next.js v14.1.3 fixed a memory issue when using the Edge runtime. Please update to this version (or later) to see if it addresses your issue.

Preloading Entriesentry preload

Next.js server는 시작될 때 각 page의 JavaScript module을 request 시점이 아니라 미리 memory에 preload합니다.

When the Next.js server starts, it preloads each page's JavaScript modules into memory, rather than at request time.

이 최적화 덕분에 response 시간이 빨라지는 대신, 초기 memory footprint가 커집니다.

This optimization allows for faster response times, in exchange for a larger initial memory footprint.

이 최적화를 비활성화하려면 experimental.preloadEntriesOnStart flag를 false로 설정하세요.

To disable this optimization, set the experimental.preloadEntriesOnStart flag to false.

TSJSnext.config.ts
import type { NextConfig } from 'next'

const config: NextConfig = {
  experimental: {
    preloadEntriesOnStart: false,
  },
}

export default config
/** @type {import('next').NextConfig} */
const config = {
  experimental: {
    preloadEntriesOnStart: false,
  },
}

export default config

Next.js는 이 JavaScript module들을 unload하지 않습니다. 즉, 이 최적화를 비활성화하더라도 결국 모든 page가 request되면 Next.js server의 memory footprint는 결국 같아집니다.

Next.js doesn't unload these JavaScript modules, meaning that even with this optimization disabled, the memory footprint of your Next.js server will eventually be the same if all pages are eventually requested.
