redirectsredirects

redirect를 사용하면 들어오는 request path를 다른 destination path로 redirect할 수 있습니다.

Redirects allow you to redirect an incoming request path to a different destination path.

redirect를 사용하려면 next.config.js에서 redirects key를 사용하면 됩니다:

To use redirects you can use the redirects key in next.config.js:

JSnext.config.js
module.exports = {
  redirects() {
    return [
      {
        source: '/about',
        destination: '/',
        permanent: true,
      },
    ]
  },
}

redirects는 동기 함수 또는 async 함수로 정의할 수 있습니다. 이 함수는 source, destination, permanent property를 가진 object의 배열을 반환하거나, 그 배열로 resolve되어야 합니다:

redirects can be defined as a synchronous or async function. It should return, or resolve to, an array of objects with source, destination, and permanent properties:

  • source는 들어오는 request path pattern입니다.
  • destination은 route하려는 path입니다.
  • permanent true 또는 false - true이면 client/검색 엔진에게 redirect를 영구적으로 cache하라고 지시하는 308 status code를 사용하고, false이면 임시이며 cache되지 않는 307 status code를 사용합니다.
  • source is the incoming request path pattern.
  • destination is the path you want to route to.
  • permanent true or false - if true will use the 308 status code which instructs clients/search engines to cache the redirect forever, if false will use the 307 status code which is temporary and is not cached.

Why does Next.js use 307 and 308? 전통적으로 임시 redirect에는 302, 영구 redirect에는 301이 사용되었지만, 많은 브라우저가 원래 method와 관계없이 redirect의 request method를 GET으로 바꿨습니다. 예를 들어 브라우저가 POST /v1/users로 request를 보냈는데 location /v2/users와 함께 status code 302가 반환되면, 이어지는 request는 기대한 POST /v2/users가 아니라 GET /v2/users가 될 수 있습니다. Next.js는 사용된 request method를 명시적으로 유지하기 위해 307 임시 redirect와 308 영구 redirect status code를 사용합니다.

Why does Next.js use 307 and 308? Traditionally a 302 was used for a temporary redirect, and a 301 for a permanent redirect, but many browsers changed the request method of the redirect to GET, regardless of the original method. For example, if the browser made a request to POST /v1/users which returned status code 302 with location /v2/users, the subsequent request might be GET /v2/users instead of the expected POST /v2/users. Next.js uses the 307 temporary redirect, and 308 permanent redirect status codes to explicitly preserve the request method used.

  • basePath: false 또는 undefined - false이면 matching할 때 basePath가 포함되지 않습니다. external redirect에만 사용할 수 있습니다.
  • locale: false 또는 undefined - matching할 때 locale을 포함하지 않을지 여부입니다.
  • has는 type, key, value property를 가진 has object의 배열입니다.
  • missing은 type, key, value property를 가진 missing object의 배열입니다.
  • basePath: false or undefined - if false the basePath won't be included when matching, can be used for external redirects only.
  • locale: false or undefined - whether the locale should not be included when matching.
  • has is an array of has objects with the type, key and value properties.
  • missing is an array of missing objects with the type, key and value properties.

redirect는 page와 /public 파일을 포함하는 filesystem보다 먼저 검사됩니다.

Redirects are checked before the filesystem which includes pages and /public files.

Pages Router를 사용할 때 redirect는 client-side routing(Link, router.push)에 적용되지 않습니다. 단, Proxy가 있고 해당 path에 match되는 경우는 예외입니다.

When using the Pages Router, redirects are not applied to client-side routing (Link, router.push) unless Proxy is present and matches the path.

redirect가 적용되면 request에 제공된 query 값이 redirect destination으로 그대로 전달됩니다. 예를 들어 다음 redirect configuration을 보세요:

When a redirect is applied, any query values provided in the request will be passed through to the redirect destination. For example, see the following redirect configuration:

{
  source: '/old-blog/:path*',
  destination: '/blog/:path*',
  permanent: false
}
Good to know

source와 destination path의 path parameter에서 colon : 앞에 forward slash /를 꼭 넣으세요. 그렇지 않으면 path가 literal 문자열로 처리되어 무한 redirect가 발생할 위험이 있습니다.

Remember to include the forward slash / before the colon : in path parameters of the source and destination paths, otherwise the path will be treated as a literal string and you run the risk of causing infinite redirects.

/old-blog/post-1?hello=world가 request되면 client는 /blog/post-1?hello=world로 redirect됩니다.

When /old-blog/post-1?hello=world is requested, the client will be redirected to /blog/post-1?hello=world.

Path Matching

path match를 사용할 수 있습니다. 예를 들어 /old-blog/:slug는 /old-blog/first-post에 match됩니다(nested path는 제외):

Path matches are allowed, for example /old-blog/:slug will match /old-blog/first-post (no nested paths):

JSnext.config.js
module.exports = {
  redirects() {
    return [
      {
        source: '/old-blog/:slug',
        destination: '/news/:slug', // Matched parameters can be used in the destination
        permanent: true,
      },
    ]
  },
}

pattern /old-blog/:slug는 /old-blog/first-post와 /old-blog/post-1에는 match되지만 /old-blog/a/b에는 match되지 않습니다(nested path는 제외). pattern은 시작 부분에 고정(anchored)됩니다: /old-blog/:slug는 /archive/old-blog/first-post에 match되지 않습니다.

The pattern /old-blog/:slug matches /old-blog/first-post and /old-blog/post-1 but not /old-blog/a/b (no nested paths). Patterns are anchored to the start: /old-blog/:slug will not match /archive/old-blog/first-post.

parameter에 modifier를 사용할 수 있습니다: *(0개 이상), +(1개 이상), ?(0개 또는 1개). 예를 들어 /blog/:slug*는 /blog, /blog/a, /blog/a/b/c에 match됩니다.

You can use modifiers on parameters: * (zero or more), + (one or more), ? (zero or one). For example, /blog/:slug* matches /blog, /blog/a, and /blog/a/b/c.

자세한 내용은 path-to-regexp 문서를 참고하세요.

Read more details on path-to-regexp documentation.

Wildcard Path Matching

wildcard path를 match하려면 parameter 뒤에 *를 사용하면 됩니다. 예를 들어 /blog/:slug*는 /blog/a/b/c/d/hello-world에 match됩니다:

To match a wildcard path you can use * after a parameter, for example /blog/:slug* will match /blog/a/b/c/d/hello-world:

JSnext.config.js
module.exports = {
  redirects() {
    return [
      {
        source: '/blog/:slug*',
        destination: '/news/:slug*', // Matched parameters can be used in the destination
        permanent: true,
      },
    ]
  },
}

Regex Path Matching

regex path를 match하려면 parameter 뒤에 regex를 괄호로 감싸면 됩니다. 예를 들어 /post/:slug(\\d{1,})는 /post/123에는 match되지만 /post/abc에는 match되지 않습니다:

To match a regex path you can wrap the regex in parentheses after a parameter, for example /post/:slug(\\d{1,}) will match /post/123 but not /post/abc:

JSnext.config.js
module.exports = {
  redirects() {
    return [
      {
        source: '/post/:slug(\\d{1,})',
        destination: '/news/:slug', // Matched parameters can be used in the destination
        permanent: false,
      },
    ]
  },
}

다음 문자 (, ), {, }, :, *, +, ?는 regex path matching에 사용되므로, source에서 특수 의미가 아닌 값으로 쓸 때는 앞에 \\를 붙여 escape해야 합니다:

The following characters (, ), {, }, :, *, +, ? are used for regex path matching, so when used in the source as non-special values they must be escaped by adding \\ before them:

JSnext.config.js
module.exports = {
  redirects() {
    return [
      {
        // this will match `/english(default)/something` being requested
        source: '/english\\(default\\)/:slug',
        destination: '/en-us/:slug',
        permanent: false,
      },
    ]
  },
}

Header, Cookie, and Query Matchingheader, cookie, query matching

header, cookie, query 값이 has 필드와 match되거나 missing 필드와 match되지 않을 때만 redirect를 match하려면 이 필드들을 사용할 수 있습니다. redirect가 적용되려면 source와 모든 has 항목이 match되어야 하고, 모든 missing 항목은 match되지 않아야 합니다.

To only match a redirect when header, cookie, or query values also match the has field or don't match the missing field can be used. Both the source and all has items must match and all missing items must not match for the redirect to be applied.

has와 missing 항목은 다음 필드를 가질 수 있습니다:

has and missing items can have the following fields:

  • type: String - header, cookie, host, query 중 하나여야 합니다.
  • key: String - 선택한 type에서 match할 key입니다.
  • value: String 또는 undefined - 확인할 값입니다. undefined이면 어떤 값이든 match됩니다. regex 형태의 문자열을 사용해 값의 특정 부분을 capture할 수 있습니다. 예를 들어 first-second에 대해 값 first-(?<paramName>.*)를 사용하면 destination에서 :paramName으로 second를 사용할 수 있습니다.
  • type: String - must be either header, cookie, host, or query.
  • key: String - the key from the selected type to match against.
  • value: String or undefined - the value to check for, if undefined any value will match. A regex like string can be used to capture a specific part of the value, e.g. if the value first-(?<paramName>.*) is used for first-second then second will be usable in the destination with :paramName.
JSnext.config.js
module.exports = {
  redirects() {
    return [
      // if the header `x-redirect-me` is present,
      // this redirect will be applied
      {
        source: '/:path((?!another-page$).*)',
        has: [
          {
            type: 'header',
            key: 'x-redirect-me',
          },
        ],
        permanent: false,
        destination: '/another-page',
      },
      // if the header `x-do-not-redirect` is present,
      // this redirect will NOT be applied
      {
        source: '/:path((?!another-page$).*)',
        missing: [
          {
            type: 'header',
            key: 'x-do-not-redirect',
          },
        ],
        permanent: false,
        destination: '/another-page',
      },
      // if the source, query, and cookie are matched,
      // this redirect will be applied
      {
        source: '/specific/:path*',
        has: [
          {
            type: 'query',
            key: 'page',
            // the page value will not be available in the
            // destination since value is provided and doesn't
            // use a named capture group e.g. (?<page>home)
            value: 'home',
          },
          {
            type: 'cookie',
            key: 'authorized',
            value: 'true',
          },
        ],
        permanent: false,
        destination: '/another/:path*',
      },
      // if the header `x-authorized` is present and
      // contains a matching value, this redirect will be applied
      {
        source: '/',
        has: [
          {
            type: 'header',
            key: 'x-authorized',
            value: '(?<authorized>yes|true)',
          },
        ],
        permanent: false,
        destination: '/home?authorized=:authorized',
      },
      // if the host is `example.com`,
      // this redirect will be applied
      {
        source: '/:path((?!another-page$).*)',
        has: [
          {
            type: 'host',
            value: 'example.com',
          },
        ],
        permanent: false,
        destination: '/another-page',
      },
    ]
  },
}

Redirects with basePath supportbasePath 지원과 redirect

redirect와 함께 basePath 지원을 활용하면, redirect에 basePath: false를 추가하지 않는 한 각 source와 destination 앞에 basePath가 자동으로 붙습니다:

When leveraging basePath support with redirects each source and destination is automatically prefixed with the basePath unless you add basePath: false to the redirect:

JSnext.config.js
module.exports = {
  basePath: '/docs',

  redirects() {
    return [
      {
        source: '/with-basePath', // automatically becomes /docs/with-basePath
        destination: '/another', // automatically becomes /docs/another
        permanent: false,
      },
      {
        // does not add /docs since basePath: false is set
        source: '/without-basePath',
        destination: 'https://example.com',
        basePath: false,
        permanent: false,
      },
    ]
  },
}

Redirects with i18n supporti18n 지원과 redirect

App Router에서 internationalization과 함께 redirect를 구현할 때, next.config.js의 redirect에 locale을 포함할 수 있지만 hardcode된 path로만 가능합니다.

When implementing redirects with internationalization in the App Router, you can include locales in next.config.js redirects, but only as hardcoded paths.

dynamic하게 또는 request별로 locale을 처리하려면 dynamic route segment와 proxy를 사용하세요. 이를 통해 사용자의 선호 언어에 따라 redirect할 수 있습니다.

For dynamic or per-request locale handling, use dynamic route segments and proxy, which can redirect based on the user's preferred language.

JSnext.config.js
module.exports = {
  redirects() {
    return [
      {
        // Manually handle locale prefixes for App Router
        source: '/en/old-path',
        destination: '/en/new-path',
        permanent: false,
      },
      {
        // Redirect for all locales using a parameter
        source: '/:locale/old-path',
        destination: '/:locale/new-path',
        permanent: false,
      },
      {
        // Redirect from one locale to another
        source: '/de/old-path',
        destination: '/en/new-path',
        permanent: false,
      },
      {
        // Catch-all redirect for multiple locales
        source: '/:locale(en|fr|de)/:path*',
        destination: '/:locale/new-section/:path*',
        permanent: false,
      },
    ]
  },
}

드물게 오래된 HTTP Client가 올바르게 redirect하도록 custom status code를 지정해야 할 수도 있습니다. 이런 경우 permanent property 대신 statusCode property를 사용할 수 있지만, 둘을 함께 사용할 수는 없습니다. IE11 호환성을 위해 308 status code에는 Refresh header가 자동으로 추가됩니다.

In some rare cases, you might need to assign a custom status code for older HTTP Clients to properly redirect. In these cases, you can use the statusCode property instead of the permanent property, but not both. To ensure IE11 compatibility, a Refresh header is automatically added for the 308 status code.

Other Redirects그 밖의 redirect

  • API Routes와 Route Handlers 안에서는 들어오는 request를 기준으로 redirect할 수 있습니다.
  • getStaticProps와 getServerSideProps 안에서는 request 시점에 특정 page를 redirect할 수 있습니다.
  • Inside API Routes and Route Handlers, you can redirect based on the incoming request.
  • Inside getStaticProps and getServerSideProps, you can redirect specific pages at request-time.
