Next.js CompilerNext.js Compiler

SWC를 사용해 Rust로 작성된 Next.js Compiler는 Next.js가 production용으로 JavaScript 코드를 transform하고 minify할 수 있게 해 줍니다. 이는 개별 파일 처리에서는 Babel을, 출력 bundle minify에서는 Terser를 대체합니다.

The Next.js Compiler, written in Rust using SWC, allows Next.js to transform and minify your JavaScript code for production. This replaces Babel for individual files and Terser for minifying output bundles.

Next.js Compiler를 사용한 compilation은 Babel보다 17배 빠르며, Next.js 버전 12부터 기본으로 활성화되어 있습니다. 기존 Babel configuration이 있거나 지원되지 않는 기능을 사용하고 있다면, 애플리케이션은 Next.js Compiler를 사용하지 않고(opt-out) 계속 Babel을 사용합니다.

Compilation using the Next.js Compiler is 17x faster than Babel and enabled by default since Next.js version 12. If you have an existing Babel configuration or are using unsupported features, your application will opt-out of the Next.js Compiler and continue using Babel.

Why SWC?왜 SWC인가?

SWC는 차세대 빠른 개발자 도구를 위한, 확장 가능한 Rust 기반 platform입니다.

SWC is an extensible Rust-based platform for the next generation of fast developer tools.

SWC는 compilation, minification, bundling 등에 사용할 수 있으며, 확장할 수 있도록 설계되었습니다. (built-in 또는 custom) code transformation을 수행하기 위해 호출할 수 있는 도구입니다. 이러한 transformation은 Next.js 같은 상위 수준 도구를 통해 실행됩니다.

SWC can be used for compilation, minification, bundling, and more – and is designed to be extended. It's something you can call to perform code transformations (either built-in or custom). Running those transformations happens through higher-level tools like Next.js.

저희는 몇 가지 이유로 SWC 위에 구축하기로 했습니다:

We chose to build on SWC for a few reasons:

  • Extensibility: SWC는 library를 fork하거나 설계상 제약을 우회할 필요 없이 Next.js 안에서 Crate로 사용할 수 있습니다.
  • Performance: SWC로 전환하면서 Next.js에서 Fast Refresh는 약 3배, build는 약 5배 빨라졌으며, 아직 진행 중인 최적화 여지도 남아 있습니다.
  • WebAssembly: Rust의 WASM 지원은 가능한 모든 platform을 지원하고 Next.js 개발을 어디서든 가능하게 하는 데 필수적입니다.
  • Community: Rust community와 ecosystem은 훌륭하며 계속 성장하고 있습니다.
  • Extensibility: SWC can be used as a Crate inside Next.js, without having to fork the library or workaround design constraints.
  • Performance: We were able to achieve ~3x faster Fast Refresh and ~5x faster builds in Next.js by switching to SWC, with more room for optimization still in progress.
  • WebAssembly: Rust's support for WASM is essential for supporting all possible platforms and taking Next.js development everywhere.
  • Community: The Rust community and ecosystem are amazing and still growing.

Supported Features지원되는 기능

Styled Components

babel-plugin-styled-components를 Next.js Compiler로 이식(port)하는 작업을 진행하고 있습니다.

We're working to port babel-plugin-styled-components to the Next.js Compiler.

먼저 Next.js를 최신 버전으로 업데이트하세요: npm install next@latest. 그다음 next.config.js 파일을 업데이트하세요:

First, update to the latest version of Next.js: npm install next@latest. Then, update your next.config.js file:

JSnext.config.js
module.exports = {
  compiler: {
    styledComponents: true,
  },
}

고급 use case를 위해 styled-components compilation의 개별 property를 설정할 수 있습니다.

For advanced use cases, you can configure individual properties for styled-components compilation.

Note: Next.js에서 styled-components를 사용하기 위한 핵심 요구 사항은 ssr과 displayName transform입니다.

Note: ssr and displayName transforms are the main requirement for using styled-components in Next.js.

JSnext.config.js
module.exports = {
  compiler: {
    // see https://styled-components.com/docs/tooling#babel-plugin for more info on the options.
    styledComponents: {
      // Enabled by default in development, disabled in production to reduce file size,
      // setting this will override the default for all environments.
      displayName?: boolean,
      // Enabled by default.
      ssr?: boolean,
      // Enabled by default.
      fileName?: boolean,
      // Empty by default.
      topLevelImportPaths?: string[],
      // Defaults to ["index"].
      meaninglessFileNames?: string[],
      // Enabled by default.
      minify?: boolean,
      // Enabled by default.
      transpileTemplateLiterals?: boolean,
      // Empty by default.
      namespace?: string,
      // Disabled by default.
      pure?: boolean,
      // Enabled by default.
      cssProp?: boolean,
    },
  },
}

Jest

Next.js Compiler는 테스트 코드를 transpile하고, Next.js와 함께 Jest를 설정하는 일을 다음과 같이 단순화합니다:

The Next.js Compiler transpiles your tests and simplifies configuring Jest together with Next.js including:

  • .css, .module.css(및 각각의 .scss 변형), 이미지 import 자동 mocking
  • SWC를 사용하는 transform 자동 설정
  • .env(및 모든 변형)를 process.env로 load
  • test resolving과 transform에서 node_modules 무시
  • test resolving에서 .next 무시
  • experimental SWC transform을 활성화하는 flag를 위해 next.config.js load
  • Auto mocking of .css, .module.css (and their .scss variants), and image imports
  • Automatically sets up transform using SWC
  • Loading .env (and all variants) into process.env
  • Ignores node_modules from test resolving and transforms
  • Ignoring .next from test resolving
  • Loads next.config.js for flags that enable experimental SWC transforms

먼저 Next.js를 최신 버전으로 업데이트하세요: npm install next@latest. 그다음 jest.config.js 파일을 업데이트하세요:

First, update to the latest version of Next.js: npm install next@latest. Then, update your jest.config.js file:

JSjest.config.js
const nextJest = require('next/jest')

// Providing the path to your Next.js app which will enable loading next.config.js and .env files
const createJestConfig = nextJest({ dir: './' })

// Any custom config you want to pass to Jest
const customJestConfig = {
  setupFilesAfterEnv: ['<rootDir>/jest.setup.js'],
}

// createJestConfig is exported in this way to ensure that next/jest can load the Next.js configuration, which is async
module.exports = createJestConfig(customJestConfig)

Relay

Relay 지원을 활성화하려면:

To enable Relay support:

JSnext.config.js
module.exports = {
  compiler: {
    relay: {
      // This should match relay.config.js
      src: './',
      artifactDirectory: './__generated__',
      language: 'typescript',
      eagerEsModules: false,
    },
  },
}
Good to know

Next.js에서는 pages directory의 모든 JavaScript 파일이 route로 간주됩니다. 따라서 relay-compiler의 artifactDirectory configuration 설정을 pages 밖으로 지정해야 합니다. 그렇지 않으면 relay-compiler가 source 파일 옆의 __generated__ directory에 파일을 생성하고, 이 파일이 route로 간주되어 production build가 깨집니다.

In Next.js, all JavaScript files in pages directory are considered routes. So, for relay-compiler you'll need to specify artifactDirectory configuration settings outside of the pages, otherwise relay-compiler will generate files next to the source file in the __generated__ directory, and this file will be considered a route, which will break production builds.

Remove React PropertiesReact property 제거

JSX property를 제거할 수 있습니다. 주로 테스트에 사용됩니다. babel-plugin-react-remove-properties와 비슷합니다.

Allows to remove JSX properties. This is often used for testing. Similar to babel-plugin-react-remove-properties.

기본 regex ^data-test와 일치하는 property를 제거하려면:

To remove properties matching the default regex ^data-test:

JSnext.config.js
module.exports = {
  compiler: {
    reactRemoveProperties: true,
  },
}

custom property를 제거하려면:

To remove custom properties:

JSnext.config.js
module.exports = {
  compiler: {
    // The regexes defined here are processed in Rust so the syntax is different from
    // JavaScript `RegExp`s. See https://docs.rs/regex.
    reactRemoveProperties: { properties: ['^data-custom$'] },
  },
}

Remove ConsoleConsole 제거

이 transform을 사용하면 애플리케이션 코드(node_modules 제외)의 모든 console.* 호출을 제거할 수 있습니다. babel-plugin-transform-remove-console과 비슷합니다.

This transform allows for removing all console.* calls in application code (not node_modules). Similar to babel-plugin-transform-remove-console.

모든 console.* 호출 제거:

Remove all console.* calls:

JSnext.config.js
module.exports = {
  compiler: {
    removeConsole: true,
  },
}

console.error를 제외한 console.* 출력 제거:

Remove console.* output except console.error:

JSnext.config.js
module.exports = {
  compiler: {
    removeConsole: {
      exclude: ['error'],
    },
  },
}

Legacy Decorators

Next.js는 jsconfig.json 또는 tsconfig.json의 experimentalDecorators를 자동으로 감지합니다. legacy decorator는 mobx 같은 library의 오래된 버전에서 흔히 사용됩니다.

Next.js will automatically detect experimentalDecorators in jsconfig.json or tsconfig.json. Legacy decorators are commonly used with older versions of libraries like mobx.

이 flag는 기존 애플리케이션과의 호환성을 위해서만 지원됩니다. 새 애플리케이션에서는 legacy decorator 사용을 권장하지 않습니다.

This flag is only supported for compatibility with existing applications. We do not recommend using legacy decorators in new applications.

먼저 Next.js를 최신 버전으로 업데이트하세요: npm install next@latest. 그다음 jsconfig.json 또는 tsconfig.json 파일을 업데이트하세요:

First, update to the latest version of Next.js: npm install next@latest. Then, update your jsconfig.json or tsconfig.json file:

{
  "compilerOptions": {
    "experimentalDecorators": true
  }
}

importSource

Next.js는 jsconfig.json 또는 tsconfig.json의 jsxImportSource를 자동으로 감지해 적용합니다. 이는 Theme UI 같은 library와 함께 흔히 사용됩니다.

Next.js will automatically detect jsxImportSource in jsconfig.json or tsconfig.json and apply that. This is commonly used with libraries like Theme UI.

먼저 Next.js를 최신 버전으로 업데이트하세요: npm install next@latest. 그다음 jsconfig.json 또는 tsconfig.json 파일을 업데이트하세요:

First, update to the latest version of Next.js: npm install next@latest. Then, update your jsconfig.json or tsconfig.json file:

{
  "compilerOptions": {
    "jsxImportSource": "theme-ui"
  }
}

Emotion

@emotion/babel-plugin을 Next.js Compiler로 이식(port)하는 작업을 진행하고 있습니다.

We're working to port @emotion/babel-plugin to the Next.js Compiler.

먼저 Next.js를 최신 버전으로 업데이트하세요: npm install next@latest. 그다음 next.config.js 파일을 업데이트하세요:

First, update to the latest version of Next.js: npm install next@latest. Then, update your next.config.js file:

JSnext.config.js
module.exports = {
  compiler: {
    emotion: boolean | {
      // default is true. It will be disabled when build type is production.
      sourceMap?: boolean,
      // default is 'dev-only'.
      autoLabel?: 'never' | 'dev-only' | 'always',
      // default is '[local]'.
      // Allowed values: `[local]` `[filename]` and `[dirname]`
      // This option only works when autoLabel is set to 'dev-only' or 'always'.
      // It allows you to define the format of the resulting label.
      // The format is defined via string where variable parts are enclosed in square brackets [].
      // For example labelFormat: "my-classname--[local]", where [local] will be replaced with the name of the variable the result is assigned to.
      labelFormat?: string,
      // default is undefined.
      // This option allows you to tell the compiler what imports it should
      // look at to determine what it should transform so if you re-export
      // Emotion's exports, you can still use transforms.
      importMap?: {
        [packageName: string]: {
          [exportName: string]: {
            canonicalImport?: [string, string],
            styledBaseImport?: [string, string],
          }
        }
      },
    },
  },
}

Minification

v13부터 Next.js의 swc compiler가 기본으로 minification에 사용됩니다. 이는 Terser보다 7배 빠릅니다.

Next.js' swc compiler is used for minification by default since v13. This is 7x faster than Terser.

Good to know

v15부터는 next.config.js로 minification을 customize할 수 없습니다. swcMinify flag 지원이 제거되었습니다.

Starting with v15, minification cannot be customized using next.config.js. Support for the swcMinify flag has been removed.

Module Transpilation

Next.js는 local package(monorepo 등)나 외부 dependency(node_modules)의 dependency를 자동으로 transpile하고 bundle할 수 있습니다. 이는 next-transpile-modules package를 대체합니다.

Next.js can automatically transpile and bundle dependencies from local packages (like monorepos) or from external dependencies (node_modules). This replaces the next-transpile-modules package.

JSnext.config.js
module.exports = {
  transpilePackages: ['@acme/ui', 'lodash-es'],
}

Modularize Imports

이 option은 Next.js 13.5에서 optimizePackageImports로 대체되었습니다. import 경로를 수동으로 설정할 필요가 없는 새 option을 사용하도록 upgrade하는 것을 권장합니다.

This option has been superseded by optimizePackageImports in Next.js 13.5. We recommend upgrading to use the new option that does not require manual configuration of import paths.

Define (Replacing variables during build)Define (build 중 변수 치환)

define option을 사용하면 build time에 코드의 변수를 정적으로 치환할 수 있습니다. 이 option은 key-value 쌍으로 된 object를 받으며, key는 대응하는 value로 치환될 변수입니다.

The define option allows you to statically replace variables in your code at build-time. The option takes an object as key-value pairs, where the keys are the variables that should be replaced with the corresponding values.

모든 environment(server, edge, client)에 대해 변수를 정의하려면 next.config.js의 compiler.define field를 사용하세요. 또는 server-side(server와 edge) 코드에만 변수를 정의하려면 compiler.defineServer를 사용하세요:

Use the compiler.define field in next.config.js to define variables for all environments (server, edge, and client). Or, use compiler.defineServer to define variables only for server-side (server and edge) code:

JSnext.config.js
module.exports = {
  compiler: {
    define: {
      MY_VARIABLE: 'my-string',
      'process.env.MY_ENV_VAR': 'my-env-var',
    },
    defineServer: {
      MY_SERVER_VARIABLE: 'my-server-var',
    },
  },
}

Build Lifecycle Hooks

Next.js Compiler는 build 과정의 특정 시점에 custom 코드를 실행할 수 있는 lifecycle hook을 지원합니다. 현재 지원되는 hook은 다음과 같습니다:

The Next.js Compiler supports lifecycle hooks that allow you to run custom code at specific points during the build process. Currently, the following hook is supported:

runAfterProductionCompile

production build compilation이 끝난 후, type checking이나 static page 생성 같은 compilation 이후 작업을 실행하기 전에 실행되는 hook 함수입니다. 이 hook은 project directory와 build output directory를 포함한 프로젝트 metadata에 접근할 수 있게 해 주므로, third-party 도구가 sourcemap 같은 build 결과물을 수집하는 데 유용합니다.

A hook function that executes after production build compilation finishes, but before running post-compilation tasks such as type checking and static page generation. This hook provides access to project metadata including the project directory and build output directory, making it useful for third-party tools to collect build outputs like sourcemaps.

JSnext.config.js
module.exports = {
  compiler: {
    runAfterProductionCompile: async ({ distDir, projectDir }) => {
      // Your custom code here
    },
  },
}

이 hook은 다음 property를 가진 object를 전달받습니다:

The hook receives an object with the following properties:

  • distDir: build output directory입니다(기본값은 .next)
  • projectDir: 프로젝트의 root directory입니다
  • distDir: The build output directory (defaults to .next)
  • projectDir: The root directory of the project

Experimental FeaturesExperimental 기능

SWC Trace profiling

SWC의 내부 transform trace를 chromium의 trace event format으로 생성할 수 있습니다.

You can generate SWC's internal transform traces as chromium's trace event format.

JSnext.config.js
module.exports = {
  experimental: {
    swcTraceProfiling: true,
  },
}

활성화하면 swc가 .next/ 아래에 swc-trace-profile-${timestamp}.json이라는 이름으로 trace를 생성합니다. Chromium의 trace viewer(chrome://tracing/, https://ui.perfetto.dev/)나 호환되는 flamegraph viewer(https://www.speedscope.app/)로 생성된 trace를 load하고 시각화할 수 있습니다.

Once enabled, swc will generate trace named as swc-trace-profile-${timestamp}.json under .next/. Chromium's trace viewer (chrome://tracing/, https://ui.perfetto.dev/), or compatible flamegraph viewer (https://www.speedscope.app/) can load & visualize generated traces.

SWC Plugins (experimental)

wasm으로 작성된 SWC의 experimental plugin 지원을 사용하도록 swc의 transform을 설정해 transformation 동작을 customize할 수 있습니다.

You can configure swc's transform to use SWC's experimental plugin support written in wasm to customize transformation behavior.

JSnext.config.js
module.exports = {
  experimental: {
    swcPlugins: [
      [
        'plugin',
        {
          ...pluginOptions,
        },
      ],
    ],
  },
}

swcPlugins는 plugin 설정을 위한 tuple 배열을 받습니다. plugin tuple에는 plugin 경로와 plugin configuration object가 들어 있습니다. plugin 경로는 npm module package 이름이거나 .wasm binary 자체의 절대 경로일 수 있습니다.

swcPlugins accepts an array of tuples for configuring plugins. A tuple for the plugin contains the path to the plugin and an object for plugin configuration. The path to the plugin can be an npm module package name or an absolute path to the .wasm binary itself.

Unsupported Features지원되지 않는 기능

애플리케이션에 .babelrc 파일이 있으면 Next.js는 개별 파일을 transform할 때 자동으로 Babel을 사용하도록 fallback합니다. 이를 통해 custom Babel plugin을 활용하는 기존 애플리케이션과의 하위 호환성을 보장합니다.

When your application has a .babelrc file, Next.js will automatically fall back to using Babel for transforming individual files. This ensures backwards compatibility with existing applications that leverage custom Babel plugins.

custom Babel setup을 사용하고 있다면 configuration을 공유해 주세요. 자주 사용되는 Babel transformation을 최대한 많이 이식하고, 앞으로 plugin도 지원하기 위해 작업하고 있습니다.

If you're using a custom Babel setup, please share your configuration. We're working to port as many commonly used Babel transformations as possible, as well as supporting plugins in the future.
