loading.jsloading.js

special file인 loading.js는 React Suspense로 의미 있는 Loading UI를 만들 수 있게 도와줍니다. 이 convention을 사용하면 route segment의 content가 stream되어 들어오는 동안 server에서 즉각적인 loading state를 보여 줄 수 있습니다. content가 완료되면 새 content로 자동 교체됩니다.

The special file loading.js helps you create meaningful Loading UI with React Suspense. With this convention, you can show an instant loading state from the server while the content of a route segment streams in. The new content is automatically swapped in once complete.

TSJSapp/feed/loading.tsx
export default function Loading() {
  // Or a custom loading skeleton component
  return <p>Loading...</p>
}
export default function Loading() {
  // Or a custom loading skeleton component
  return <p>Loading...</p>
}

loading.js 파일 안에는 가벼운 loading UI라면 무엇이든 추가할 수 있습니다. React Developer Tools를 사용해 Suspense boundary를 수동으로 toggle해 보면 도움이 될 수 있습니다.

Inside the loading.js file, you can add any light-weight loading UI. You may find it helpful to use the React Developer Tools to manually toggle Suspense boundaries.

기본적으로 이 파일은 Server Component이지만, "use client" directive를 통해 Client Component로도 사용할 수 있습니다.

By default, this file is a Server Component - but can also be used as a Client Component through the "use client" directive.

Reference레퍼런스

Parameters

Loading UI component는 어떤 parameter도 받지 않습니다.

Loading UI components do not accept any parameters.

Behavior동작

Navigation

  • Fallback UI는 prefetch되므로, prefetching이 끝나지 않은 경우가 아니라면 navigation이 즉시 이루어집니다.
  • Navigation은 중단 가능(interruptible)합니다. 즉, route를 바꿀 때 해당 route의 content가 완전히 load될 때까지 기다리지 않고 다른 route로 이동할 수 있습니다.
  • 새 route segment가 load되는 동안에도 공유 layout은 interactive 상태를 유지합니다.
  • The Fallback UI is prefetched, making navigation immediate unless prefetching hasn't completed.
  • Navigation is interruptible, meaning changing routes does not need to wait for the content of the route to fully load before navigating to another route.
  • Shared layouts remain interactive while new route segments load.

Instant Loading States즉각적인 Loading State

즉각적인 loading state는 navigation 직후 바로 표시되는 fallback UI입니다. skeleton이나 spinner 같은 loading indicator, 또는 cover photo, 제목 등 앞으로 보일 화면의 작지만 의미 있는 부분을 prerender할 수 있습니다. 이는 사용자가 앱이 반응하고 있다는 것을 이해하도록 돕고 더 나은 사용자 경험을 제공합니다.

An instant loading state is fallback UI that is shown immediately upon navigation. You can prerender loading indicators such as skeletons and spinners, or a small but meaningful part of future screens such as a cover photo, title, etc. This helps users understand the app is responding and provides a better user experience.

폴더 안에 loading.js 파일을 추가해 loading state를 만드세요.

Create a loading state by adding a loading.js file inside a folder.

TSJSapp/dashboard/loading.tsx
export default function Loading() {
  // You can add any UI inside Loading, including a Skeleton.
  return <LoadingSkeleton />
}
export default function Loading() {
  // You can add any UI inside Loading, including a Skeleton.
  return <LoadingSkeleton />
}

같은 폴더에서 loading.js는 layout.js 안에 중첩됩니다. page.js 파일과 그 아래의 모든 children을 자동으로 <Suspense> boundary로 감쌉니다.

In the same folder, loading.js will be nested inside layout.js. It will automatically wrap the page.js file and any children below in a <Suspense> boundary.

component hierarchy에서 loading.js는 not-found.js, page.js, 그리고 중첩된 layout.js 파일을 <Suspense> boundary로 감쌉니다. 같은 segment의 layout.js, template.js, error.js는 감싸지 않습니다.

In the component hierarchy, loading.js wraps not-found.js, page.js, and nested layout.js files in a <Suspense> boundary. It does not wrap the layout.js, template.js, or error.js in the same segment.

Good to know

layout이 uncached 또는 runtime data(예: cookies(), headers(), uncached fetch)에 접근하면, loading.js는 이에 대한 fallback을 보여 주지 않습니다.

  • Cache Components 없이: layout의 rendering이 끝날 때까지 navigation이 block됩니다.
  • Cache Components와 함께: layout의 uncached 또는 runtime data 접근은 반드시 <Suspense>로 명시적으로 감싸야 하며, 그렇지 않으면 Next.js가 build-time error로 안내합니다. static shell이 먼저 stream되고, uncached content가 그 뒤에 채워집니다.

즉각적인 navigation을 보장하려면 uncached data fetching을 layout.js에서 page.js로 옮기거나, layout의 runtime data 접근을 자체 <Suspense> boundary로 감싸세요. 자세한 내용과 예시는 layout.js Caveats를 참고하세요.

If the layout accesses uncached or runtime data (e.g. cookies(), headers(), or uncached fetches), loading.js will not show a fallback for it.

  • Without Cache Components: Navigation blocks until the layout finishes rendering.
  • With Cache Components: Uncached or runtime data access in the layout must be explicitly wrapped in <Suspense>, otherwise Next.js guides you with a build-time error. The static shell streams first, and the uncached content fills in.

To ensure instant navigation, move uncached data fetching from layout.js into page.js, or wrap the runtime data access in your layout in its own <Suspense> boundary. See layout.js Caveats for details and examples.

SEO

  • Twitterbot처럼 static HTML만 scrape하고 일반 브라우저처럼 JavaScript를 실행할 수 없는 bot의 경우, Next.js는 UI를 streaming하기 전에 generateMetadata를 resolve하며, metadata는 초기 HTML의 <head>에 들어갑니다.
  • 그 밖의 경우에는 streaming metadata가 사용될 수 있습니다. Next.js는 user agent를 자동으로 감지해 blocking 방식과 streaming 방식 중 하나를 선택합니다.
  • streaming은 server에서 render되므로 SEO에 영향을 주지 않습니다. Google의 Rich Results Test 도구를 사용하면 Google의 web crawler에게 page가 어떻게 보이는지 확인하고 serialize된 HTML을 볼 수 있습니다(출처).
  • For bots that only scrape static HTML, and cannot execute JavaScript like a full browser, such as Twitterbot, Next.js resolves generateMetadata before streaming UI, and metadata is placed in the <head> of the initial HTML.
  • Otherwise, streaming metadata may be used. Next.js automatically detects user agents to choose between blocking and streaming behavior.
  • Since streaming is server-rendered, it does not impact SEO. You can use the Rich Results Test tool from Google to see how your page appears to Google's web crawlers and view the serialized HTML (source).

Status codes

Streaming page response는 200 status code로 시작합니다.

Streaming page responses begin with a 200 status code.

초기 response header가 나머지 response의 status를 정합니다. 그 이후 Next.js는 redirect, notFound, forbidden, unauthorized로 redirect와 HTTP access fallback을 stream할 수 있습니다.

The initial response headers set the status for the rest of the response. Next.js can then stream redirects and HTTP access fallbacks with redirect, notFound, forbidden, or unauthorized.

예를 들어 404 page가 client로 stream될 때, Next.js는 stream되는 HTML에 <meta name="robots" content="noindex"> tag를 포함합니다. 이렇게 하면 HTTP status가 200이더라도 검색 엔진이 그 URL을 index하지 않습니다. robots meta tag에 대한 Google의 가이드를 참고하세요.

For example, when a 404 page is streamed to the client, Next.js includes a <meta name="robots" content="noindex"> tag in the streamed HTML. This prevents search engines from indexing that URL even if the HTTP status is 200. See Google’s guidance on the robots meta tag.

일부 crawler는 이런 response를 “soft 404”로 분류할 수 있습니다. noindex tag가 이런 response를 검색 결과에서 제외해 줍니다.

Some crawlers may label these responses as “soft 404s”. The noindex tag keeps them out of search results.

규정 준수나 analytics를 위해 404, 403, 401 status를 반환하려면, response body가 stream되기 전에 해당 검사를 실행하세요.

Run the corresponding check before the response body streams to return a 404, 403, or 401 status for compliance or analytics.

404의 경우 Proxy에서 slug를 검사한 뒤 not-found route로 rewrite하거나 404 response를 반환할 수 있습니다. Proxy 검사는 빠르게 유지하고, 그곳에서 전체 content를 fetch하는 것은 피하세요.

For a 404, you can check the slug in Proxy, then rewrite it to a not-found route or return a 404 response. Keep Proxy checks fast, and avoid fetching full content there.

response body는 언제 stream되나요?

response body는 Suspense fallback이 render될 때(예: loading.tsx) 또는 Server Component가 <Suspense> boundary 아래에서 suspend될 때 streaming을 시작합니다. 이 시점 전에 notFound(), forbidden(), unauthorized()를 호출하면 해당 404, 403, 401 status가 유지됩니다.

stream이 시작되면 response header가 전송되고 status code가 고정됩니다.

Browser limits브라우저 제약

일부 브라우저는 streaming response를 buffer합니다. response가 1024 byte를 넘을 때까지 stream된 response가 보이지 않을 수 있습니다. 이는 보통 “hello world” 수준의 애플리케이션에만 영향을 주며, 실제 애플리케이션에는 해당하지 않습니다.

Some browsers buffer a streaming response. You may not see the streamed response until the response exceeds 1024 bytes. This typically only affects “hello world” applications, but not real applications.

Examples예시

Streaming with SuspenseSuspense로 Streaming하기

loading.js 외에도 직접 만든 UI component에 대해 Suspense Boundary를 수동으로 만들 수 있습니다. App Router는 Suspense를 이용한 streaming을 지원합니다. 세분화된 Suspense pattern, Route Handler streaming, 인프라 고려 사항 등 streaming이 어떻게 동작하는지 더 알아보려면 Streaming 가이드를 참고하세요.

In addition to loading.js, you can also manually create Suspense Boundaries for your own UI components. The App Router supports streaming with Suspense. See the Streaming guide for more on how streaming works, including granular Suspense patterns, Route Handler streaming, and infrastructure considerations.

<Suspense>는 asynchronous 작업(예: data fetch)을 수행하는 component를 감싸고, 작업이 진행되는 동안 fallback UI(예: skeleton, spinner)를 보여 준 뒤, 작업이 완료되면 component로 교체하는 방식으로 동작합니다.

<Suspense> works by wrapping a component that performs an asynchronous action (e.g. fetch data), showing fallback UI (e.g. skeleton, spinner) while it's happening, and then swapping in your component once the action completes.

TSJSapp/dashboard/page.tsx
import { Suspense } from 'react'
import { PostFeed, Weather } from './Components'

export default function Posts() {
  return (
    <section>
      <Suspense fallback={<p>Loading feed...</p>}>
        <PostFeed />
      </Suspense>
      <Suspense fallback={<p>Loading weather...</p>}>
        <Weather />
      </Suspense>
    </section>
  )
}
import { Suspense } from 'react'
import { PostFeed, Weather } from './Components'

export default function Posts() {
  return (
    <section>
      <Suspense fallback={<p>Loading feed...</p>}>
        <PostFeed />
      </Suspense>
      <Suspense fallback={<p>Loading weather...</p>}>
        <Weather />
      </Suspense>
    </section>
  )
}

Suspense를 사용하면 다음과 같은 이점을 얻을 수 있습니다:

By using Suspense, you get the benefits of:

  1. Streaming Server Rendering - server에서 client로 HTML을 점진적으로 render합니다.
  2. Selective Hydration - React가 사용자 interaction을 기반으로 어떤 component를 먼저 interactive하게 만들지 우선순위를 정합니다.
  1. Streaming Server Rendering - Progressively rendering HTML from the server to the client.
  2. Selective Hydration - React prioritizes what components to make interactive first based on user interaction.
