Caching and Revalidating (Previous Model)Caching과 Revalidating (이전 모델)

이 가이드는 버전 16에서 cacheComponents flag로 도입된 Cache Components를 사용하지 않는 경우를 전제로 합니다.

This guide assumes you are not using Cache Components which was introduced in version 16 under the cacheComponents flag.

Caching fetch requestsfetch request caching

기본적으로 fetch request는 cache되지 않습니다. cache option을 'force-cache'로 설정하면 개별 request를 cache할 수 있습니다.

By default, fetch requests are not cached. You can cache individual requests by setting the cache option to 'force-cache'.

TSJSapp/page.tsx
export default async function Page() {
  const data = await fetch('https://...', { cache: 'force-cache' })
}
export default async function Page() {
  const data = await fetch('https://...', { cache: 'force-cache' })
}

자세한 내용은 fetch API reference를 참고하세요.

See the fetch API reference to learn more.

unstable_cache for non-fetch functionsfetch가 아닌 함수를 위한 unstable_cache

unstable_cache를 사용하면 database query나 fetch를 사용하지 않는 다른 async 함수의 결과를 cache할 수 있습니다. 함수를 unstable_cache로 감싸세요:

unstable_cache allows you to cache the result of database queries and other async functions that don't use fetch. Wrap unstable_cache around the function:

TSJSapp/lib/data.ts
import { unstable_cache } from 'next/cache'
import { db } from '@/lib/db'

export const getCachedUser = unstable_cache(
  async (id: string) => {
    return db
      .select()
      .from(users)
      .where(eq(users.id, id))
      .then((res) => res[0])
  },
  ['user'], // cache key prefix
  {
    tags: ['user'],
    revalidate: 3600,
  }
)
import { unstable_cache } from 'next/cache'
import { db } from '@/lib/db'

export const getCachedUser = unstable_cache(
  async (id) => {
    return db
      .select()
      .from(users)
      .where(eq(users.id, id))
      .then((res) => res[0])
  },
  ['user'], // cache key prefix
  {
    tags: ['user'],
    revalidate: 3600,
  }
)

세 번째 인자는 다음을 받습니다:

The third argument accepts:

  • tags: revalidateTag로 on-demand revalidation을 하기 위한 tag 배열.
  • revalidate: cache가 revalidate되기까지의 시간(초).
  • tags: an array of tags for on-demand revalidation with revalidateTag.
  • revalidate: the number of seconds before the cache is revalidated.

자세한 내용은 unstable_cache API reference를 참고하세요.

See the unstable_cache API reference to learn more.

Route segment config

Page, Layout, Route Handler에서 config option을 export하면 route 수준에서 caching 동작을 설정할 수 있습니다.

You can configure caching behavior at the route level by exporting config options from a Page, Layout, or Route Handler.

dynamic

layout이나 page의 dynamic 동작을 완전한 static 또는 완전한 dynamic으로 바꿉니다.

Change the dynamic behavior of a layout or page to fully static or fully dynamic.

TSJSlayout.tsx | page.tsx | route.ts
export const dynamic = 'auto'
// 'auto' | 'force-dynamic' | 'error' | 'force-static'
export const dynamic = 'auto'
// 'auto' | 'force-dynamic' | 'error' | 'force-static'
  • 'auto' (default): 어떤 component도 dynamic 동작을 opt-in하지 못하게 막지 않으면서 가능한 한 많이 cache하는 기본 option입니다.
  • 'force-dynamic': dynamic rendering을 강제하며, 그 결과 route가 request 시점에 사용자마다 render됩니다. 이 option은 다음과 동일합니다:
    • layout이나 page 안의 모든 fetch() request option을 { cache: 'no-store', next: { revalidate: 0 } }로 설정하기.
    • segment config를 export const fetchCache = 'force-no-store'로 설정하기
  • 'error': component 중 하나라도 Request-time API나 cache되지 않은 데이터를 사용하면 error를 발생시켜, layout이나 page의 prerendering과 데이터 caching을 강제합니다. 이 option은 다음과 동일합니다:
    • pages directory의 getStaticProps().
    • layout이나 page 안의 모든 fetch() request option을 { cache: 'force-cache' }로 설정하기.
    • segment config를 fetchCache = 'only-cache'로 설정하기.
  • 'force-static': cookies, headers(), useSearchParams()가 빈 값을 반환하도록 강제해, layout이나 page의 prerendering과 데이터 caching을 강제합니다. force-static으로 render되는 page나 layout에서도 revalidate, revalidatePath, revalidateTag를 사용할 수 있습니다.
  • 'auto' (default): The default option to cache as much as possible without preventing any components from opting into dynamic behavior.
  • 'force-dynamic': Force dynamic rendering, which will result in routes being rendered for each user at request time. This option is equivalent to:
    • Setting the option of every fetch() request in a layout or page to { cache: 'no-store', next: { revalidate: 0 } }.
    • Setting the segment config to export const fetchCache = 'force-no-store'
  • 'error': Force prerendering and cache the data of a layout or page by causing an error if any components use Request-time APIs or uncached data. This option is equivalent to:
    • getStaticProps() in the pages directory.
    • Setting the option of every fetch() request in a layout or page to { cache: 'force-cache' }.
    • Setting the segment config to fetchCache = 'only-cache'.
  • 'force-static': Force prerendering and cache the data of a layout or page by forcing cookies, headers() and useSearchParams() to return empty values. It is possible to revalidate, revalidatePath, or revalidateTag, in pages or layouts rendered with force-static.

fetchCache

기본 동작을 꼭 override해야 하는 경우에만 사용해야 하는 고급 option입니다.

cache option을 설정하지 않은 fetch request는 Request-time API가 사용되기 전에 도달할 수 있다면 next build 중에 한 번 fetch됩니다. route가 그 지점까지 prerender되기 때문입니다. Request-time API 이후에 발견된 request는 매 request마다 실행됩니다.

fetchCache를 사용하면 layout이나 page 안의 모든 fetch request의 기본 cache option을 override할 수 있습니다.

TSJSlayout.tsx | page.tsx | route.ts
export const fetchCache = 'auto'
// 'auto' | 'default-cache' | 'only-cache'
// 'force-cache' | 'force-no-store' | 'default-no-store' | 'only-no-store'
export const fetchCache = 'auto'
// 'auto' | 'default-cache' | 'only-cache'
// 'force-cache' | 'force-no-store' | 'default-no-store' | 'only-no-store'
  • 'auto' (default): Request-time API 이전의 fetch request는 각자 지정한 cache option으로 cache하고, Request-time API 이후의 fetch request는 cache하지 않는 기본 option입니다.
  • 'default-cache': fetch에 어떤 cache option이든 전달할 수 있게 허용하되, option이 없으면 cache option을 'force-cache'로 설정합니다. 즉, Request-time API 이후의 fetch request도 static으로 간주됩니다.
  • 'only-cache': option이 없으면 기본값을 cache: 'force-cache'로 바꾸고, cache: 'no-store'를 사용하는 fetch request가 있으면 error를 발생시켜 모든 fetch request가 caching을 opt-in하도록 보장합니다.
  • 'force-cache': 모든 fetch request의 cache option을 'force-cache'로 설정해 모든 fetch request가 caching을 opt-in하도록 보장합니다.
  • 'default-no-store': fetch에 어떤 cache option이든 전달할 수 있게 허용하되, option이 없으면 cache option을 'no-store'로 설정합니다. 즉, Request-time API 이전의 fetch request도 dynamic으로 간주됩니다.
  • 'only-no-store': option이 없으면 기본값을 cache: 'no-store'로 바꾸고, cache: 'force-cache'를 사용하는 fetch request가 있으면 error를 발생시켜 모든 fetch request가 caching을 opt-out하도록 보장합니다
  • 'force-no-store': 모든 fetch request의 cache option을 'no-store'로 설정해 모든 fetch request가 caching을 opt-out하도록 보장합니다. 이렇게 하면 'force-cache' option을 지정한 경우에도 모든 fetch request가 매 request마다 다시 fetch됩니다.

Cross-route segment behavior

  • 하나의 route에 속한 각 layout과 page에 설정한 option은 서로 호환되어야 합니다.
    • 'only-cache'와 'force-cache'가 모두 지정되면 'force-cache'가 우선합니다. 'only-no-store'와 'force-no-store'가 모두 지정되면 'force-no-store'가 우선합니다. force option은 route 전체의 동작을 바꾸므로, 'force-*'를 가진 segment 하나만 있어도 'only-*'로 인한 error가 발생하지 않습니다.
    • 'only-*'와 'force-*' option의 목적은 route 전체가 완전한 static이거나 완전한 dynamic임을 보장하는 것입니다. 즉:
      • 하나의 route 안에서 'only-cache'와 'only-no-store'를 함께 쓰는 것은 허용되지 않습니다.
      • 하나의 route 안에서 'force-cache'와 'force-no-store'를 함께 쓰는 것은 허용되지 않습니다.
    • child가 'auto'나 '*-cache'를 지정하면 parent는 'default-no-store'를 지정할 수 없습니다. 같은 fetch가 서로 다르게 동작할 수 있기 때문입니다.
  • 일반적으로 공유되는 parent layout은 'auto'로 두고, child segment가 달라지는 지점에서 option을 customize하는 것을 권장합니다.

Time-based revalidation시간 기반 revalidation

fetch의 next.revalidate option을 사용하면 지정한 시간(초)이 지난 뒤 데이터를 revalidate합니다:

Use the next.revalidate option on fetch to revalidate data after a specified number of seconds:

TSJSapp/page.tsx
export default async function Page() {
  const data = await fetch('https://...', { next: { revalidate: 3600 } })
}
export default async function Page() {
  const data = await fetch('https://...', { next: { revalidate: 3600 } })
}

fetch가 아닌 함수의 경우 unstable_cache가 configuration에서 revalidate option을 받습니다(위 예시 참고).

For non-fetch functions, unstable_cache accepts a revalidate option in its configuration (see example above).

Route segment config revalidate

layout이나 page의 기본 revalidation 시간을 설정합니다. 이 option은 개별 fetch request에 설정된 revalidate 값을 override하지 않습니다.

Set the default revalidation time for a layout or page. This option does not override the revalidate value set by individual fetch requests.

TSJSlayout.tsx | page.tsx | route.ts
export const revalidate = false
// false | 0 | number
export const revalidate = false
// false | 0 | number
  • false (default): cache option을 'force-cache'로 설정했거나 Request-time API가 사용되기 전에 발견된 모든 fetch request를 cache하는 기본 heuristic입니다. 의미상 revalidate: Infinity와 같으며, 사실상 resource를 무기한 cache해야 한다는 뜻입니다. 그래도 개별 fetch request는 cache: 'no-store'나 revalidate: 0을 사용해 cache되지 않게 하고 route를 dynamic하게 render되도록 만들 수 있습니다. 또는 revalidate를 route 기본값보다 작은 양수로 설정해 route의 revalidation 빈도를 높일 수도 있습니다.
  • 0: Request-time API나 cache되지 않은 data fetch가 발견되지 않더라도 layout이나 page가 항상 dynamic하게 render되도록 보장합니다. 이 option은 cache option을 설정하지 않은 fetch request의 기본값을 'no-store'로 바꾸지만, 'force-cache'를 opt-in했거나 양수 revalidate를 사용하는 fetch request는 그대로 둡니다.
  • number: (초 단위) layout이나 page의 기본 revalidation 빈도를 n초로 설정합니다.
  • false (default): The default heuristic to cache any fetch requests that set their cache option to 'force-cache' or are discovered before a Request-time API is used. Semantically equivalent to revalidate: Infinity which effectively means the resource should be cached indefinitely. It is still possible for individual fetch requests to use cache: 'no-store' or revalidate: 0 to avoid being cached and make the route dynamically rendered. Or set revalidate to a positive number lower than the route default to increase the revalidation frequency of a route.
  • 0: Ensure a layout or page is always dynamically rendered even if no Request-time APIs or uncached data fetches are discovered. This option changes the default of fetch requests that do not set a cache option to 'no-store' but leaves fetch requests that opt into 'force-cache' or use a positive revalidate as is.
  • number: (in seconds) Set the default revalidation frequency of a layout or page to n seconds.
Good to know
  • revalidate 값은 정적으로 분석 가능해야 합니다. 예를 들어 revalidate = 600은 유효하지만 revalidate = 60 * 10은 유효하지 않습니다.
  • deprecated된 runtime = 'edge'를 사용할 때는 revalidate 값을 사용할 수 없습니다.
  • Development 환경에서 Page는 항상 on-demand로 render되며 절대 cache되지 않습니다. 덕분에 revalidation 기간이 지나기를 기다리지 않고 변경 사항을 바로 확인할 수 있습니다.
  • The revalidate value needs to be statically analyzable. For example revalidate = 600 is valid, but revalidate = 60 * 10 is not.
  • The revalidate value is not available when using the deprecated runtime = 'edge'.
  • In Development, Pages are always rendered on-demand and are never cached. This allows you to see changes immediately without waiting for a revalidation period to pass.

Revalidation frequencyRevalidation 빈도

  • 하나의 route에 속한 각 layout과 page 중 가장 낮은 revalidate 값이 route _전체_의 revalidation 빈도를 결정합니다. 이렇게 해서 child page가 parent layout만큼 자주 revalidate되도록 보장합니다.
  • 개별 fetch request는 route의 기본 revalidate보다 낮은 revalidate를 설정해 route 전체의 revalidation 빈도를 높일 수 있습니다. 이를 통해 특정 기준에 따라 일부 route만 더 잦은 revalidation을 dynamic하게 opt-in할 수 있습니다.
  • The lowest revalidate across each layout and page of a single route will determine the revalidation frequency of the entire route. This ensures that child pages are revalidated as frequently as their parent layouts.
  • Individual fetch requests can set a lower revalidate than the route's default revalidate to increase the revalidation frequency of the entire route. This allows you to dynamically opt-in to more frequent revalidation for certain routes based on some criteria.

On-demand revalidation

이벤트가 발생한 뒤 cache된 데이터를 revalidate하려면 Server Action이나 Route Handler에서 revalidateTag 또는 revalidatePath를 사용하세요.

To revalidate cached data after an event, use revalidateTag or revalidatePath in a Server Action or Route Handler.

Tagging cached datacache된 데이터에 tag 붙이기

fetch request에 next.tags로 tag를 붙이면 on-demand cache invalidation을 사용할 수 있습니다:

Tag fetch requests with next.tags to enable on-demand cache invalidation:

TSJSapp/lib/data.ts
export async function getUserById(id: string) {
  const data = await fetch(`https://...`, {
    next: { tags: ['user'] },
  })
}
export async function getUserById(id) {
  const data = await fetch(`https://...`, {
    next: { tags: ['user'] },
  })
}

fetch가 아닌 함수의 경우 unstable_cache도 tags option을 받습니다(위 예시 참고).

For non-fetch functions, unstable_cache also accepts a tags option (see example above).

revalidateTag

revalidateTag를 사용해 tag 기준으로 cache된 데이터를 invalidate합니다:

Invalidate cached data by tag using revalidateTag:

TSJSapp/lib/actions.ts
import { revalidateTag } from 'next/cache'

export async function updateUser(id: string) {
  // Mutate data
  revalidateTag('user', 'max')
}
import { revalidateTag } from 'next/cache'

export async function updateUser(id) {
  // Mutate data
  revalidateTag('user', 'max')
}

revalidatePath

revalidatePath를 사용해 특정 route path의 cache된 데이터를 모두 invalidate합니다:

Invalidate all cached data for a specific route path using revalidatePath:

TSJSapp/lib/actions.ts
import { revalidatePath } from 'next/cache'

export async function updateUser(id: string) {
  // Mutate data
  revalidatePath('/profile')
}
import { revalidatePath } from 'next/cache'

export async function updateUser(id) {
  // Mutate data
  revalidatePath('/profile')
}

Deduplicating requestsRequest 중복 제거

fetch(자동으로 memoize됨)를 사용하지 않고 ORM이나 database를 직접 사용한다면, data access를 React cache 함수로 감싸 한 번의 render pass 안에서 request 중복을 제거할 수 있습니다:

If you are not using fetch (which is automatically memoized), and instead using an ORM or database directly, you can wrap your data access with the React cache function to deduplicate requests within a single render pass:

TSJSapp/lib/data.ts
import { cache } from 'react'
import { db, posts, eq } from '@/lib/db'

export const getPost = cache(async (id: string) => {
  const post = await db.query.posts.findFirst({
    where: eq(posts.id, parseInt(id)),
  })
})
import { cache } from 'react'
import { db, posts, eq } from '@/lib/db'

export const getPost = cache(async (id) => {
  const post = await db.query.posts.findFirst({
    where: eq(posts.id, parseInt(id)),
  })
})

Preloading data데이터 preload하기

blocking request보다 먼저 미리 호출하는 utility 함수를 만들어 데이터를 preload할 수 있습니다. 이렇게 하면 data fetching을 일찍 시작할 수 있어서, component가 render될 때쯤에는 데이터가 이미 준비되어 있습니다.

You can preload data by creating a utility function that you eagerly call above blocking requests. This lets you initiate data fetching early, so the data is already available by the time the component renders.

server-only package와 React의 cache를 결합해 재사용 가능한 preload utility를 만드세요:

Combine the server-only package with React's cache to create a reusable preload utility:

TSJSutils/get-item.ts
import { cache } from 'react'
import 'server-only'

export const getItem = cache(async (id: string) => {
  // ...
})

export const preload = (id: string) => {
  void getItem(id)
}
import { cache } from 'react'
import 'server-only'

export const getItem = cache(async (id) => {
  // ...
})

export const preload = (id) => {
  void getItem(id)
}

그런 다음 blocking 작업보다 먼저 preload()를 호출해 데이터 로딩이 바로 시작되게 합니다:

Then call preload() before any blocking work so the data starts loading immediately:

TSJSapp/item/[id]/page.tsx
import { getItem, preload, checkIsAvailable } from '@/lib/data'

export default async function Page({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  // Start loading item data
  preload(id)
  // Perform another asynchronous task
  const isAvailable = await checkIsAvailable()

  return isAvailable ? <Item id={id} /> : null
}

async function Item({ id }: { id: string }) {
  const result = await getItem(id)
  // ...
}
import { getItem, preload, checkIsAvailable } from '@/lib/data'

export default async function Page({ params }) {
  const { id } = await params
  // Start loading item data
  preload(id)
  // Perform another asynchronous task
  const isAvailable = await checkIsAvailable()

  return isAvailable ? <Item id={id} /> : null
}

async function Item({ id }) {
  const result = await getItem(id)
  // ...
}
