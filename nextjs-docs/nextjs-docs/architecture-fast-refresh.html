Fast RefreshFast Refresh

Fast refresh는 Next.js에 통합된 React 기능으로, 파일 변경 사항을 저장하면 임시 client-side state를 유지한 채 브라우저 page를 live reload할 수 있게 해 줍니다. 9.4 이상 버전의 모든 Next.js 애플리케이션에서 기본으로 활성화되어 있습니다. Fast Refresh가 활성화되어 있으면 대부분의 수정 사항이 1초 안에 화면에 반영됩니다.

Fast refresh is a React feature integrated into Next.js that allows you to live reload the browser page while maintaining temporary client-side state when you save changes to a file. It's enabled by default in all Next.js applications on 9.4 or newer. With Fast Refresh enabled, most edits should be visible within a second.

How It Works동작 방식

  • React component만 export하는 파일을 수정하면, Fast Refresh는 그 파일의 코드만 업데이트하고 component를 re-render합니다. style, rendering logic, event handler, effect 등 그 파일의 무엇이든 수정할 수 있습니다.
  • React component가 아닌 export가 있는 파일을 수정하면, Fast Refresh는 그 파일과 그 파일을 import하는 다른 파일들을 모두 다시 실행합니다. 따라서 Button.js와 Modal.js가 모두 theme.js를 import한다면, theme.js를 수정하면 두 component가 모두 업데이트됩니다.
  • 마지막으로, React tree 밖의 파일이 import하는 파일을 수정하면, Fast Refresh는 full reload로 fallback합니다. React component를 render하면서 React가 아닌 component가 import하는 값도 export하는 파일이 있을 수 있습니다. 예를 들어 component가 상수도 export하고, React가 아닌 utility 파일이 그 상수를 import하는 경우입니다. 이런 경우에는 상수를 별도 파일로 옮기고 두 파일 모두에서 import하는 것을 고려하세요. 그러면 Fast Refresh가 다시 동작합니다. 다른 경우도 대개 비슷한 방법으로 해결할 수 있습니다.
  • If you edit a file that only exports React component(s), Fast Refresh will update the code only for that file, and re-render your component. You can edit anything in that file, including styles, rendering logic, event handlers, or effects.
  • If you edit a file with exports that aren't React components, Fast Refresh will re-run both that file, and the other files importing it. So if both Button.js and Modal.js import theme.js, editing theme.js will update both components.
  • Finally, if you edit a file that's imported by files outside of the React tree, Fast Refresh will fall back to doing a full reload. You might have a file which renders a React component but also exports a value that is imported by a non-React component. For example, maybe your component also exports a constant, and a non-React utility file imports it. In that case, consider migrating the constant to a separate file and importing it into both files. This will re-enable Fast Refresh to work. Other cases can usually be solved in a similar way.

Error ResilienceError 복원력

Syntax ErrorsSyntax error

development 중에 syntax error를 냈다면, 고친 뒤 파일을 다시 저장하면 됩니다. error는 자동으로 사라지므로 앱을 reload할 필요가 없습니다. component state도 잃지 않습니다.

If you make a syntax error during development, you can fix it and save the file again. The error will disappear automatically, so you won't need to reload the app. You will not lose component state.

Runtime ErrorsRuntime error

component 안에서 runtime error로 이어지는 실수를 하면, 상황에 맞는 overlay가 나타납니다. error를 고치면 앱을 reload하지 않고도 overlay가 자동으로 사라집니다.

If you make a mistake that leads to a runtime error inside your component, you'll be greeted with a contextual overlay. Fixing the error will automatically dismiss the overlay, without reloading the app.

error가 rendering 중에 발생하지 않았다면 component state는 유지됩니다. error가 rendering 중에 발생했다면, React는 업데이트된 코드를 사용해 애플리케이션을 remount합니다.

Component state will be retained if the error did not occur during rendering. If the error did occur during rendering, React will remount your application using the updated code.

앱에 error boundary가 있다면(production에서 우아한 실패 처리를 위해 좋은 방법입니다), rendering error 이후 다음 수정 시 rendering을 다시 시도합니다. 즉, error boundary가 있으면 매번 root 앱 state로 초기화되는 것을 막을 수 있습니다. 하지만 error boundary를 너무 세분화해서는 안 된다는 점을 기억하세요. error boundary는 production에서 React가 사용하므로, 항상 의도적으로 설계해야 합니다.

If you have error boundaries in your app (which is a good idea for graceful failures in production), they will retry rendering on the next edit after a rendering error. This means having an error boundary can prevent you from always getting reset to the root app state. However, keep in mind that error boundaries shouldn't be too granular. They are used by React in production, and should always be designed intentionally.

Limitations제약 사항

Fast Refresh는 수정 중인 component의 local React state를 보존하려고 하지만, 그렇게 하는 것이 안전한 경우에만 보존합니다. 파일을 수정할 때마다 local state가 초기화되는 몇 가지 이유는 다음과 같습니다:

Fast Refresh tries to preserve local React state in the component you're editing, but only if it's safe to do so. Here's a few reasons why you might see local state being reset on every edit to a file:

  • class component에서는 local state가 보존되지 않습니다(function component와 Hooks만 state를 보존합니다).
  • 수정 중인 파일에 React component 외에 다른 export가 있을 수 있습니다.
  • 때때로 파일이 HOC(WrappedComponent) 같은 higher-order component 호출 결과를 export할 수 있습니다. 반환된 component가 class라면 그 state는 초기화됩니다.
  • export default () => <div />; 같은 익명 arrow function은 Fast Refresh가 local component state를 보존하지 못하게 합니다. 대규모 codebase에서는 name-default-component codemod를 사용할 수 있습니다.
  • Local state is not preserved for class components (only function components and Hooks preserve state).
  • The file you're editing might have other exports in addition to a React component.
  • Sometimes, a file would export the result of calling a higher-order component like HOC(WrappedComponent). If the returned component is a class, its state will be reset.
  • Anonymous arrow functions like export default () => <div />; cause Fast Refresh to not preserve local component state. For large codebases you can use our name-default-component codemod.

codebase의 더 많은 부분이 function component와 Hooks로 옮겨갈수록, 더 많은 경우에 state가 보존될 것으로 기대할 수 있습니다.

As more of your codebase moves to function components and Hooks, you can expect state to be preserved in more cases.

Tips팁

  • Fast Refresh는 기본적으로 function component(및 Hooks)의 React local state를 보존합니다.
  • 때로는 state를 강제로 초기화하고 component를 remount하고 싶을 수 있습니다. 예를 들어 mount 시에만 일어나는 animation을 조정하고 있을 때 유용합니다. 이렇게 하려면 수정 중인 파일 어디에든 // @refresh reset을 추가하면 됩니다. 이 directive는 해당 파일에만 적용되며, 수정할 때마다 그 파일에 정의된 component를 remount하도록 Fast Refresh에 지시합니다.
  • development 중에 수정하는 component에 console.log나 debugger;를 넣을 수 있습니다.
  • import는 대소문자를 구분한다는 점을 기억하세요. import가 실제 파일 이름과 일치하지 않으면 fast refresh와 full refresh 모두 실패할 수 있습니다. 예를 들어 './header'와 './Header'의 차이입니다.
  • Fast Refresh preserves React local state in function components (and Hooks) by default.
  • Sometimes you might want to force the state to be reset, and a component to be remounted. For example, this can be handy if you're tweaking an animation that only happens on mount. To do this, you can add // @refresh reset anywhere in the file you're editing. This directive is local to the file, and instructs Fast Refresh to remount components defined in that file on every edit.
  • You can put console.log or debugger; into the components you edit during development.
  • Remember that imports are case sensitive. Both fast and full refresh can fail, when your import doesn't match the actual filename. For example, './header' vs './Header'.

Fast Refresh and HooksFast Refresh와 Hooks

가능한 경우 Fast Refresh는 수정 사이에 component의 state를 보존하려고 시도합니다. 특히 useState와 useRef는 argument나 Hook 호출 순서를 바꾸지 않는 한 이전 값을 보존합니다.

When possible, Fast Refresh attempts to preserve the state of your component between edits. In particular, useState and useRef preserve their previous values as long as you don't change their arguments or the order of the Hook calls.

useEffect, useMemo, useCallback처럼 dependency가 있는 Hook은 Fast Refresh 중에 항상 업데이트됩니다. Fast Refresh가 일어나는 동안에는 dependency 목록이 무시됩니다.

Hooks with dependencies—such as useEffect, useMemo, and useCallback—will always update during Fast Refresh. Their list of dependencies will be ignored while Fast Refresh is happening.

예를 들어 useMemo(() => x * 2, [x])를 useMemo(() => x * 10, [x])로 수정하면, x(dependency)가 바뀌지 않았더라도 다시 실행됩니다. React가 그렇게 하지 않는다면 수정 사항이 화면에 반영되지 않을 것입니다!

For example, when you edit useMemo(() => x * 2, [x]) to useMemo(() => x * 10, [x]), it will re-run even though x (the dependency) has not changed. If React didn't do that, your edit wouldn't reflect on the screen!

때로는 이로 인해 예상치 못한 결과가 생길 수 있습니다. 예를 들어 dependency 배열이 비어 있는 useEffect라도 Fast Refresh 중에 한 번은 다시 실행됩니다.

Sometimes, this can lead to unexpected results. For example, even a useEffect with an empty array of dependencies would still re-run once during Fast Refresh.

하지만 가끔 useEffect가 다시 실행되어도 문제없는 코드를 작성하는 것은 Fast Refresh가 없더라도 좋은 습관입니다. 나중에 새 dependency를 추가하기도 쉬워지며, 활성화를 강력히 권장하는 React Strict Mode에서도 이를 강제합니다.

However, writing code resilient to occasional re-running of useEffect is a good practice even without Fast Refresh. It will make it easier for you to introduce new dependencies to it later on and it's enforced by React Strict Mode, which we highly recommend enabling.
