How to fetch client-side data with SWRSWR로 client-side 데이터 fetch하기

SWR을 사용해 Client Component에서 데이터를 fetch하고, Server Component에서 초기 데이터를 제공하며, browser mutation과 cache된 server 데이터를 조율하세요. 패턴을 고르려면 Client-side data fetching을 참고하세요.

Use SWR to fetch data in Client Components, provide initial data from Server Components, and coordinate browser mutations with cached server data. See Client-side data fetching to choose a pattern.

Fetch data on the clientclient에서 데이터 fetch하기

초기 화면이 hydration 이후의 browser request를 기다려도 된다면 SWR은 전적으로 browser에서 fetch할 수 있습니다. loading UI가 나타날 위치에 따라 inline 또는 Suspense loading state를 선택하세요. 이 예시들에서 query는 빈 값으로 시작해 hydration 이후 client state에 따라 업데이트됩니다.

SWR can fetch entirely in the browser when the initial view can wait for a browser request after hydration. Choose an inline or Suspense loading state based on where the loading UI should appear. In these examples, query starts empty and updates from client state after hydration.

component가 자체 loading state와 error state를 render해야 한다면 useSWR을 사용하세요. 조건부 key를 쓰면 상호작용으로 입력이 주어질 때까지 request가 지연됩니다:

Use useSWR when the component should render its own loading and error states. A conditional key delays the request until the interaction provides an input:

TSapp/product-autocomplete.tsx
'use client'

import useSWR from 'swr'

type Product = { id: string; name: string }

async function fetcher(url: string): Promise<Product[]> {
  const response = await fetch(url)
  if (!response.ok) throw new Error('Failed to fetch products')
  return response.json()
}

export function ProductAutocomplete({ query }: { query: string }) {
  const {
    data = [],
    error,
    isLoading,
  } = useSWR(
    query ? `/api/products?query=${encodeURIComponent(query)}` : null,
    fetcher
  )

  if (!query) return null
  if (error) return <p>Failed to load products.</p>
  if (isLoading) return <p>Loading products...</p>

  return (
    <ul>
      {data.map((product) => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  )
}

Use Suspense for client dataclient 데이터에 Suspense 사용하기

가장 가까운 Suspense boundary가 loading UI를 정의해야 한다면 suspense: true를 사용하세요. 결과가 로드되는 동안에도 사용할 수 있도록 interactive shell은 boundary 바깥에 두세요:

Use suspense: true when the nearest Suspense boundary should define the loading UI. Keep the interactive shell outside the boundary so it remains available while the results load:

TSapp/product-autocomplete.tsx
'use client'

import { Suspense } from 'react'
import useSWR from 'swr'

type Product = { id: string; name: string }

async function fetcher(url: string): Promise<Product[]> {
  const response = await fetch(url)
  if (!response.ok) throw new Error('Failed to fetch products')
  return response.json()
}

export function ProductAutocomplete({ query }: { query: string }) {
  if (!query) return null

  return (
    <Suspense fallback={<p>Loading products...</p>}>
      <ProductResults query={query} />
    </Suspense>
  )
}

function ProductResults({ query }: { query: string }) {
  const { data } = useSWR(
    `/api/products?query=${encodeURIComponent(query)}`,
    fetcher,
    { suspense: true }
  )

  return (
    <ul>
      {data.map((product) => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  )
}

조건 없는 key를 사용하면 SWR은 Suspense가 resolve된 뒤 data를 정의합니다. request error는 가장 가까운 error boundary에서 처리하세요.

With an unconditional key, SWR defines data after Suspense resolves. Handle request errors with the nearest error boundary.

isLoading 값은 request가 실행 중이고 표시할 로드된 데이터가 없을 때 true입니다. isValidating 값은 background revalidation을 포함해 request가 실행 중일 때마다 true입니다.

The isLoading value is true when a request is running and there is no loaded data to display. The isValidating value is true whenever a request is running, including background revalidation.

suspense: true를 사용하면 데이터가 없는 초기 상태는 Suspense가 처리합니다. 같은 key에 대한 이후의 revalidation에서는 Suspense fallback을 다시 보여 주지 않고 현재 데이터를 계속 render합니다. background refresh feedback을 제공하려면 isValidating을 사용하세요. SWR loading state에 대해 더 알아보세요.

With suspense: true, Suspense handles the initial no-data state. Later revalidation for the same key keeps the current data rendered instead of showing the Suspense fallback again. Use isValidating to provide background refresh feedback. Learn more about SWR loading states.

Good to know

독립적인 Suspense read는 형제 component에서 render되면 병렬로 시작될 수 있습니다. 한 component 안의 여러 Suspense read는 순차적으로 실행됩니다. network waterfall과 SWR Suspense에 대해 더 알아보세요.

Independent Suspense reads can start in parallel when they render in sibling components. Multiple Suspense reads in one component run sequentially. Learn more about network waterfalls and SWR Suspense.

Provide initial data from a Server ComponentServer Component에서 초기 데이터 제공하기

initial render에 데이터가 필요하고 SWR이 이후에도 browser에서 계속 관리해야 한다면 server가 제공하는 데이터 패턴을 사용하세요. SWR 2.3.0과 React 19에서는 client가 이어받기 전에 Server Component가 fallback 데이터를 제공할 수 있습니다.

Use the server-provided data pattern when the initial render needs the data and SWR should continue managing it in the browser. With SWR 2.3.0 and React 19, a Server Component can provide fallback data before the client takes over.

<SWRConfig>의 범위를 데이터를 소유한 route segment로 한정하세요. 이 provider는 fallback을 consumer 가까이에 두고, feature 데이터가 공유 layout에 추가되는 것을 피합니다:

Scope <SWRConfig> to the route segment that owns the data. The provider keeps the fallback close to its consumer and avoids adding feature data to a shared layout:

TSJSapp/products/[id]/page.tsx
import { Suspense } from 'react'
import { SWRConfig } from 'swr'
import { getProduct } from './data' // some server-side function
import { productCache } from './product-cache'
import { ProductView } from './product-view'

export default function Page({ params }: PageProps<'/products/[id]'>) {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      {params.then(({ id }) => (
        <ProductData id={id} />
      ))}
    </Suspense>
  )
}

function ProductData({ id }: { id: string }) {
  return (
    <SWRConfig
      value={{
        fallback: {
          // Not awaited: only components that read this key suspend
          [productCache.key(id)]: getProduct(id),
        },
      }}
    >
      <ProductView id={id} />
    </SWRConfig>
  )
}
import { Suspense } from 'react'
import { SWRConfig } from 'swr'
import { getProduct } from './data' // some server-side function
import { productCache } from './product-cache'
import { ProductView } from './product-view'

export default function Page({ params }) {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      {params.then(({ id }) => (
        <ProductData id={id} />
      ))}
    </Suspense>
  )
}

function ProductData({ id }) {
  return (
    <SWRConfig
      value={{
        fallback: {
          // Not awaited: only components that read this key suspend
          [productCache.key(id)]: getProduct(id),
        },
      }}
    >
      <ProductView id={id} />
    </SWRConfig>
  )
}

fallback과 Client Component는 같은 SWR key를 사용해야 합니다. 두 호출 위치가 같은 identity를 공유하도록 key를 한 번만 정의하세요:

The fallback and Client Component must use the same SWR key. Define the key once so both call sites share the same identity:

TSJSapp/products/[id]/product-cache.ts
export const productCache = {
  key: (id: string) => `/api/products/${id}`,
}
export const productCache = {
  key: (id) => `/api/products/${id}`,
}

page 예시에서 params.then()이 반환하는 Promise는 route parameter가 resolve될 때까지 fallback이 계속 보이게 합니다. 그다음 ProductData는 SWR fallback을 위해 await하지 않은 별도의 getProduct(id) Promise를 만듭니다. React는 그 Promise를 React Server Component payload로 전달하고, 일치하는 key를 읽는 component는 데이터가 resolve될 때까지 suspend됩니다.

In the page example, the Promise returned by params.then() keeps the fallback visible until the route parameters resolve. ProductData then creates a separate, unawaited getProduct(id) Promise for the SWR fallback. React passes that Promise through the React Server Component payload, and the component reading the matching key suspends until the data resolves.

Client Component는 같은 key로 useSWR을 사용해 데이터를 읽습니다:

The Client Component reads the data with useSWR using the same key:

TSJSapp/products/[id]/product-view.tsx
'use client'

import useSWR from 'swr'
import { productCache } from './product-cache'

type Product = { id: string; name: string }

async function fetcher(url: string): Promise<Product> {
  const response = await fetch(url)
  if (!response.ok) throw new Error('Failed to fetch product')
  return response.json()
}

export function ProductView({ id }: { id: string }) {
  const { data } = useSWR(productCache.key(id), fetcher, { suspense: true })

  return <h1>{data.name}</h1>
}

import useSWR from 'swr'
import { productCache } from './product-cache'

  if (!response.ok) throw new Error('Failed to fetch product')
  return response.json()

Good to know

fallback key와 useSWR key는 정확히 일치해야 합니다. 둘이 어긋나면 SWR은 fallback 값을 무시하고 client에서 fetch합니다.

The fallback key and the useSWR key must match exactly. If they drift, SWR ignores the fallback value and fetches on the client.

fallback은 hook의 초기 값을 제공합니다. 기본적으로 SWR은 fallback 데이터를 stale로 취급하고 hydration 이후 browser revalidation을 시작합니다.

The fallback provides the hook's initial value. By default, SWR treats fallback data as stale and starts a browser revalidation after hydration.

SWR은 fallback 데이터에 대해 시간 기반 freshness window를 제공하지 않습니다. revalidateIfStale: false를 설정하면 cache된 데이터가 있는 상태로 hook이 mount될 때 revalidation을 건너뜁니다. 이 설정은 TanStack Query의 staleTime과 달리 모든 mount에 적용됩니다.

SWR does not provide a time-based freshness window for fallback data. Setting revalidateIfStale: false skips revalidation when the hook mounts with cached data. This setting applies to every mount, unlike TanStack Query's staleTime.

focus, reconnect, polling, mutate는 여전히 key를 revalidate할 수 있습니다. 일정한 주기로 refresh하려면 refreshInterval을 설정하세요.

Focus, reconnect, polling, and mutate can still revalidate the key. To refresh on a schedule, set refreshInterval.

SWR key는 GET method를 가진 Route Handler를 가리킵니다. Route Handler는 fallback을 제공하는 것과 같은 getProduct 함수를 호출할 수 있고, browser는 revalidation과 polling에 그 URL을 사용합니다.

The SWR key points to a Route Handler with a GET method. The Route Handler can call the same getProduct function that provides the fallback, while the browser uses the URL for revalidation and polling.

Cache server-provided data with Cache ComponentsCache Components로 server가 제공하는 데이터 cache하기

이 패턴을 사용하기 전에 next.config.ts에서 cacheComponents를 활성화하세요. 그러면 SWR fallback으로 쓰이는 server 데이터를 cache할 수 있습니다. use cache를 추가하고, cacheLife profile을 고르고, mutation이 invalidate할 수 있도록 cacheTag를 적용하세요:

Enable cacheComponents in next.config.ts before using this pattern. You can then cache the server data used as the SWR fallback. Add use cache, choose a cacheLife profile, and apply cacheTag so mutations can invalidate it:

TSJSapp/products/[id]/data.ts
import { cacheLife, cacheTag } from 'next/cache'

export async function getProduct(id: string) {
  'use cache'
  cacheLife('max')
  cacheTag(`product:${id}`)

  const product = await db.product.findUnique({ where: { id } })
  if (!product) throw new Error('Product not found')
  return product
}
import { cacheLife, cacheTag } from 'next/cache'

export async function getProduct(id) {
  'use cache'
  cacheLife('max')
  cacheTag(`product:${id}`)

  const product = await db.product.findUnique({ where: { id } })
  if (!product) throw new Error('Product not found')
  return product
}

이 예시는 쓰기 작업이 product tag를 invalidate하므로 cacheLife('max')를 사용합니다. cache profile 안에서 stale은 Next.js client cache가 prefetch된 payload를 얼마나 오래 재사용할 수 있는지를 제어하고, revalidate와 expire는 server cache를 제어합니다. server 값이 시간에 따라 refresh되어야 한다면 더 짧은 profile을 선택하세요.

This example uses cacheLife('max') because writes invalidate the product tag. Within the cache profile, stale controls how long the Next.js client cache can reuse a prefetched payload, while revalidate and expire control the server cache. Choose a shorter profile when the server value should refresh with time.

SWR은 별도의 browser cache를 소유하므로, SWR의 revalidation option을 cacheLife와 맞출 필요는 없습니다.

SWR owns a separate browser cache, so its revalidation options do not need to match cacheLife.

같은 mutation이 browser cache를 업데이트하면서 cache된 server 데이터도 invalidate한다면, 두 identity를 하나의 공유 contract에 정의할 수 있습니다:

When the same mutation updates the browser cache and invalidates cached server data, you may define both identities in one shared contract:

app/products/[id]/product-cache.ts
 export const productCache = {
   key: (id: string) => `/api/products/${id}`,
+  tag: (id: string) => `product:${id}`,
 }
app/products/[id]/product-cache.js
 export const productCache = {
   key: (id) => `/api/products/${id}`,
+  tag: (id) => `product:${id}`,
 }

그러면 server 함수는 cacheTag(productCache.tag(id))를 호출할 수 있습니다. 두 cache layer가 모두 재사용할 수 있도록 이 contract에는 server 전용 import와 client 전용 import를 넣지 마세요.

The server function can then call cacheTag(productCache.tag(id)). Keep this contract free of server-only and client-only imports so both cache layers can reuse it.

Coordinate server and client caches after mutationsmutation 이후 server와 client cache 조율하기

fallback은 초기 값을 제공합니다. hydration 이후에는 SWR이 browser cache와 revalidation을 관리합니다. 재사용되는 데이터의 경우 SWR key와 server tag를 같은 cache contract에 두세요:

The fallback provides the initial value. After hydration, SWR manages the browser cache and revalidation. For reused data, keep the SWR key and server tag in the same cache contract:

TSJSapp/activity/activity-cache.ts
export const activityCache = {
  key: '/api/activity/unread',
  tag: (userId: string) => `activity:${userId}`,
}
export const activityCache = {
  key: '/api/activity/unread',
  tag: (userId) => `activity:${userId}`,
}

fallback, Client Component의 read, mutation에 같은 key를 사용하세요. SWR에서는 쓰기 작업을 mutate에 전달하고 optimisticData를 제공하세요. SWR은 optimistic 값을 즉시 보여 주고, 쓰기가 실패하면 rollback합니다. 이 예시에서는 최종 값을 알고 있으므로 action이 성공한 뒤에도 optimistic 값을 유지합니다:

Use the same key for the fallback, the Client Component read, and the mutation. With SWR, pass the write to mutate and provide optimisticData. SWR shows the optimistic value immediately and rolls it back if the write fails. This example keeps the optimistic value after the action succeeds because the final value is known:

TSJSapp/activity/mark-read-button.tsx
'use client'

import { useSWRConfig } from 'swr'
import { markActivityReadAction } from './actions'
import { activityCache } from './activity-cache'

export function MarkReadButton() {
  const { mutate } = useSWRConfig()

  function markRead() {
    return mutate(
      activityCache.key,
      async () => {
        await markActivityReadAction()
        return { count: 0 }
      },
      {
        optimisticData: { count: 0 },
        revalidate: false,
        rollbackOnError: true,
        throwOnError: false,
      }
    )
  }

  return <button onClick={markRead}>Mark read</button>
}

Server Action은 database에 쓰고 updateTag로 tag가 붙은 server 데이터를 만료시킵니다. tag가 일치하도록 cache된 server query에 cacheTag로 tag를 붙이세요:

The Server Action writes to the database and expires the tagged server data with updateTag. Tag the cached server query with cacheTag so the tag matches:

TSJSapp/activity/actions.ts
'use server'

import { updateTag } from 'next/cache'
import {
  getCurrentUserId,
  markActivityRead as markActivityReadInDatabase,
} from './data'
import { activityCache } from './activity-cache'

export async function markActivityReadAction() {
  const userId = await getCurrentUserId()
  await markActivityReadInDatabase(userId)
  updateTag(activityCache.tag(userId))
}
'use server'

import { updateTag } from 'next/cache'
import {
  getCurrentUserId,
  markActivityRead as markActivityReadInDatabase,
} from './data'
import { activityCache } from './activity-cache'

export async function markActivityReadAction() {
  const userId = await getCurrentUserId()
  await markActivityReadInDatabase(userId)
  updateTag(activityCache.tag(userId))
}

optimistic SWR 값은 현재 화면을 업데이트합니다. updateTag는 다음 cache된 server read가 최신 activity를 반환하도록 보장합니다.

The optimistic SWR value updates the current screen. updateTag ensures the next cached server read returns fresh activity.

Good to know

Server Action이 쓰기 결과를 즉시 반영해야 하는 cache된 read를 변경할 때 updateTag를 호출하세요. cache되지 않은 read에는 업데이트할 server tag가 없습니다. 다른 invalidation 동작은 Client-side data fetching을 참고하세요.

Call updateTag when a Server Action changes a cached read that must reflect the write immediately. An uncached read does not have a server tag to update. See Client-side data fetching for other invalidation behaviors.
