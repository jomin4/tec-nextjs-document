How to prevent flash before hydrationhydration 전 깜빡임 방지하기

사용자 preference, 브라우저 설정, client-side storage는 server rendering 중에는 사용할 수 없습니다. server는 적절한 기본값을 내보내지만, client 전용 state(locale, time zone, theme, 저장된 interaction)에 의존하는 UI는 사용자가 보기 전에 업데이트되어야 합니다.

User preferences, browser settings, and client-side storage aren't available during server rendering. The server emits a reasonable default, but any UI that depends on client-only state (locale, time zone, theme, persisted interactions) needs to be updated before the user sees it.

이 문제에 대한 흔한 접근 방식은 다음과 같습니다:

Some common approaches to this problem:

  • client 값으로 re-render하는 Client Component는 hydration error를 일으킵니다.
  • useEffect로 미루면 error는 피하지만 눈에 보이는 깜빡임이 생깁니다.
  • server에서만 rendering하면 client별 formatting을 완전히 포기해야 합니다.
  • A Client Component that re-renders with client values causes a hydration error.
  • Deferring to useEffect avoids the error but introduces a visible flash.
  • Rendering only on the server means giving up on client-specific formatting entirely.

브라우저가 HTML을 parse하는 동안 동기적으로 실행되는 inline script를 사용하면, first paint 전에 DOM을 업데이트할 수 있습니다. 이 가이드에서는 날짜, theme, 저장된 UI state를 다룹니다.

Using an inline script that runs synchronously as the browser parses the HTML, you can update the DOM before the first paint. This guide covers dates, themes, and persisted UI state.

  • An accordion that persists its open section to localStorage using a lazy useState initializer

Dates and formatting날짜와 formatting

2026-06-15T18:00:00Z 같은 UTC timestamp는 고정된 시점을 나타내지만, 이를 화면에 어떻게 format할지는 사용자의 locale과 time zone에 따라 달라집니다. server에서 toLocaleDateString()과 Intl.DateTimeFormat은 server의 설정을 사용하며, 이는 사용자의 설정과 다를 수 있습니다.

A UTC timestamp like 2026-06-15T18:00:00Z represents a fixed point in time, but how it is formatted for display depends on the user's locale and time zone. toLocaleDateString() and Intl.DateTimeFormat on the server use the server's settings, which may not match the user's.

The problem문제

자연스러운 접근은 날짜를 format하는 Client Component입니다:

A natural approach is a Client Component that formats the date:

TSJSapp/components/event-date.tsx

export function EventDate({ date }: { date: string }) {
  return <p>{new Date(date).toLocaleDateString()}</p>
}

SSR 중에는 toLocaleDateString()이 Node.js에서 실행되어 server의 locale로 format합니다(예: 6/15/2026). hydration 시 React는 브라우저에서 component를 다시 실행하고 사용자의 locale로 결과를 만듭니다(예: 2026/6/15). React는 불일치를 감지해 hydration error를 throw하고, 사용자는 깜빡임을 보게 됩니다.

During SSR, toLocaleDateString() runs in Node.js and formats using the server's locale (e.g. 6/15/2026). On hydration, React re-executes the component in the browser and produces the user's locale (e.g. 2026/6/15). React detects the mismatch, throws a hydration error, and the user sees a flash.

useEffect로 hydration 후에 날짜를 업데이트하는 우회 방법도 있지만, 사용자는 여전히 server에서 format된 날짜를 먼저 보게 됩니다. Server Component는 error를 완전히 피하지만, 날짜가 영구적으로 server의 locale로 표시됩니다.

You could work around this with useEffect to update the date after hydration, but the user still sees the server-formatted date first. A Server Component avoids the error entirely, but the date is permanently in the server's locale.

Good to know

컴퓨터의 locale이 브라우저의 locale과 같으면 로컬 개발 중에 이 문제를 놓치기 쉽습니다. 불일치를 일찍 발견하려면 TZ와 LANG을 브라우저와 다르게 설정해서 dev server를 실행하세요(예: TZ=UTC LANG=ja_JP.UTF-8 next dev). 대부분의 server가 UTC로 동작하므로 TZ=UTC가 좋은 기본값입니다.

This issue is easy to miss in local development if your machine's locale matches your browser's. Run your dev server with TZ and LANG set differently from your browser to catch mismatches early (e.g. TZ=UTC LANG=ja_JP.UTF-8 next dev). TZ=UTC is a good default since most servers run in UTC.

Fixing it with an inline scriptinline script로 해결하기

  1. server가 자신의 locale로 날짜를 <p> 안에 render합니다.
  2. element 뒤에 (dangerouslySetInnerHTML을 통해) <script>를 둡니다. 브라우저는 HTML parsing 중 first paint 전에 이를 동기적으로 실행합니다.
  3. inline script가 React hydrate 전에 텍스트를 바꾸므로, element에 suppressHydrationWarning을 추가합니다. 아래 Understanding suppressHydrationWarning을 참고하세요.
  1. The server renders the date with its locale into a <p>.
  2. Place a <script> (via dangerouslySetInnerHTML) after the element. The browser runs it synchronously during HTML parsing, before the first paint.
  3. Add suppressHydrationWarning to the element, since the inline script changes the text before React hydrates. See Understanding suppressHydrationWarning below.
TSJSapp/events/page.tsx
import { getEvent } from '@/app/lib/events'

export default async function Page() {
  const event = await getEvent('nextjs-conf')

  return (
    <section>
      <h1>{event.name}</h1>
      <p id="event-date" suppressHydrationWarning>
        {new Date(event.date).toLocaleDateString()}
      </p>
      <script
        dangerouslySetInnerHTML={{
          __html: `document.getElementById("event-date").textContent=new Date("${event.date}").toLocaleDateString()`,
        }}
      />
    </section>
  )
}

Understanding suppressHydrationWarningsuppressHydrationWarning 이해하기

React가 hydrate하다가 텍스트 불일치를 발견하면:

When React hydrates and finds a text mismatch:

  • suppressHydrationWarning이 없을 때: React는 이를 hydration error로 취급하고, 가장 가까운 error boundary 또는 Suspense boundary부터 client-rendering으로 복구합니다. 이때 깜빡임이 생기고, React가 DOM을 다시 만들 때 script가 다시 실행되지 않기 때문에 그 boundary 안의 다른 component에 적용된 inline script 수정 내용이 사라집니다.
  • suppressHydrationWarning이 있을 때: React는 DOM에 있는 내용을 그대로 유지하고 그 element에 대한 client 결과물을 버립니다. DOM이 우선합니다.
  • Without suppressHydrationWarning: React treats it as a hydration error and recovers by client-rendering from the nearest error or Suspense boundary. This causes a flash, and inline script corrections on other components within that boundary are lost because the scripts don't re-execute when React rebuilds the DOM.
  • With suppressHydrationWarning: React keeps whatever is in the DOM and discards the client's output for that element. The DOM wins.

inline script는 React가 hydrate하기 전에 올바른 값을 DOM에 넣습니다. Server Component의 경우에도 React는 hydration 중 DOM을 RSC payload와 비교하며, inline script가 텍스트를 바꿔 놓은 상태입니다. suppressHydrationWarning은 React에게 payload 대신 DOM을 받아들이라고 알려 줍니다.

The inline script puts the correct value in the DOM before React hydrates. Even for Server Components, React compares the DOM against the RSC payload during hydration, and the inline script has changed the text. suppressHydrationWarning tells React to accept the DOM rather than the payload.

Extracting a reusable component재사용 가능한 component로 추출하기

DOM 업데이트로 삽입된 script는 브라우저에서 실행되지 않습니다. client-side navigation에서는 React가 RSC payload로 component를 render하므로 script가 실행되지 않습니다. component를 Client Component로 만들면 이 문제가 해결됩니다. soft navigation에서는 toLocaleDateString()이 브라우저에서 직접 실행되고, hard navigation은 inline script가 처리합니다. useId는 각 instance마다 안정적인 고유 ID를 생성합니다.

Scripts inserted via DOM updates don't execute in the browser. On client-side navigations, React renders the component from the RSC payload and the script won't run. Making the component a Client Component solves this: toLocaleDateString() runs directly in the browser on soft navigations, while the inline script handles hard navigations. useId generates a stable unique ID for each instance.

React는 개발 중 rendering 결과에 <script> tag가 생기면 경고도 표시합니다. 이를 피하려면 server에서는 type="text/javascript", client에서는 type="text/plain"을 설정하는 helper로 script를 감싸세요. type 불일치는 suppressHydrationWarning이 처리합니다.

React also warns in development when rendering produces <script> tags. To avoid this, wrap the script in a helper that sets type="text/javascript" on the server and type="text/plain" on the client. suppressHydrationWarning handles the type mismatch.

TSJSapp/components/inline-script.tsx
export function InlineScript({ html }: { html: string }) {
  return (
    <script
      type={typeof window === 'undefined' ? 'text/javascript' : 'text/plain'}
      suppressHydrationWarning
      dangerouslySetInnerHTML={{ __html: html }}
    />
  )
}

Good to know
  • 표시되는 텍스트와 관계없이 검색 엔진과 screen reader가 ISO 문자열을 parse할 수 있도록 dateTime attribute가 있는 <time> element를 사용하세요.
  • dangerouslySetInnerHTML을 사용한 inline script는 'unsafe-inline'을 허용하지 않는 엄격한 Content Security Policy에 의해 차단됩니다. 앱에서 CSP를 사용한다면 nonce를 추가해야 합니다.
  • Use a <time> element with a dateTime attribute so search engines and screen readers can parse the ISO string regardless of the displayed text.
  • Inline scripts with dangerouslySetInnerHTML are blocked by strict Content Security Policies that don't allow 'unsafe-inline'. If your app uses a CSP, you'll need to add a nonce.

ThemesTheme

page가 기본 theme(예: light)으로 server-render되더라도, 사용자는 localStorage에 저장된 preference를 가지고 있을 수 있습니다. 같은 inline script 기법이 여기서도 통합니다. 브라우저가 paint하기 전에 값을 읽어 <html>에 data-theme attribute를 설정하세요.

Your page may be server-rendered with a default theme (e.g. light), but the user has a saved preference in localStorage. The same inline script technique works: read the value and set a data-theme attribute on <html> before the browser paints.

TSJSapp/layout.tsx
export default function RootLayout({ children }: LayoutProps<'/'>) {
  return (
    <html lang="en" data-theme="light" suppressHydrationWarning>
      <head>
        <script
          dangerouslySetInnerHTML={{
            __html: `(function(){try{var t=localStorage.getItem("theme");if(t)document.documentElement.setAttribute("data-theme",t)}catch(e){}})()`,
          }}
        />
      </head>
      <body>{children}</body>
    </html>
  )
}

script는 <head>에서 실행되므로 어떤 콘텐츠가 paint되기 전에 올바른 theme이 적용됩니다. try/catch는 localStorage를 사용할 수 없는 경우를 처리합니다.

The script runs in <head>, so the correct theme is applied before any content is painted. The try/catch handles cases where localStorage is unavailable.

Storing the theme in a cookietheme을 cookie에 저장하기

localStorage와 달리 cookie는 모든 request와 함께 전송되므로, server가 cookies()로 이를 읽을 수 있습니다. 하지만 root layout에서 이를 읽으면 앱 전체가 static prerendering에서 제외됩니다(그리고 Cache Components 환경에서는 layout 아래의 모든 segment가 blocking되도록 강제됩니다). 일반적인 기본값으로 page를 static prerender된 상태로 유지하면서도 깜빡임을 피하려면, 대신 inline script에서 cookie를 읽으세요:

Unlike localStorage, a cookie is sent with every request, so the server can read it with cookies(). But reading it in the root layout opts the entire app out of static prerendering (and under Cache Components, forces blocking every segment under the layout). To keep the page statically prerendered with a generic default and still avoid the flash, read the cookie in the inline script instead:

TSJSapp/layout.tsx
export default function RootLayout({ children }: LayoutProps<'/'>) {
  return (
    <html lang="en" data-theme="light" suppressHydrationWarning>
      <head>
        <script
          dangerouslySetInnerHTML={{
            __html: `(function(){try{var m=document.cookie.match(/(?:^|; )theme=([^;]*)/);if(m)document.documentElement.setAttribute("data-theme",decodeURIComponent(m[1]))}catch(e){}})()`,
          }}
        />
      </head>
      <body>{children}</body>
    </html>
  )
}
export default function RootLayout({ children }) {
  return (
    <html lang="en" data-theme="light" suppressHydrationWarning>
      <head>

          }}
        />
      </head>
      <body>{children}</body>
    </html>
  )
}

theme을 전환하려면 <html>에 attribute를 설정하고 선택 값을 cookie에 저장하세요:

To switch themes, set the attribute on <html> and persist the choice to the cookie:

const theme = 'dark'
document.documentElement.setAttribute('data-theme', theme)
document.cookie = `theme=${encodeURIComponent(theme)}; path=/; max-age=31536000; SameSite=Lax`

Syncing with React stateReact state와 동기화하기

Client Component가 interactive state(예: accordion의 어느 섹션이 열려 있는지)를 관리할 때, React의 initial state는 inline script가 설정한 DOM과 일치해야 합니다. script와 같은 소스에서 값을 읽는 lazy state initializer를 사용하세요.

When a Client Component manages interactive state (like which accordion section is open), React's initial state must match the DOM that the inline script set. Use a lazy state initializer that reads from the same source as the script.

TSJSapp/components/accordion.tsx
'use client'

import { useState, useCallback } from 'react'
import { InlineScript } from './inline-script'

const STORAGE_KEY = 'open-section'

const sections = [
  {
    id: 'setup',
    title: 'Setup',
    content: 'Install dependencies and create your project.',
  },
  {
    id: 'usage',
    title: 'Usage',
    content: 'Import the component and pass your data.',
  },
  {
    id: 'deploy',
    title: 'Deploy',
    content: 'Push to your Git provider and deploy.',
  },
]

const DEFAULT_ID = sections[0].id
const SECTION_IDS = sections.map((s) => s.id)

export function Accordion() {
  const [openId, setOpenId] = useState(() => {
    if (typeof window === 'undefined') return DEFAULT_ID
    return localStorage.getItem(STORAGE_KEY) ?? DEFAULT_ID
  })

  const handleToggle = useCallback(
    (id: string) => (e: React.ToggleEvent<HTMLDetailsElement>) => {
      if (e.newState === 'open') {
        setOpenId(id)
        localStorage.setItem(STORAGE_KEY, id)
      }
    },
    []
  )

  return (
    <div>
      {sections.map((section) => (
        <details
          key={section.id}
          name="accordion"
          id={`section-${section.id}`}
          open={openId === section.id}
          onToggle={handleToggle(section.id)}
        >
          <summary>{section.title}</summary>
          <p>{section.content}</p>
        </details>
      ))}
      <InlineScript
        html={`{var id=localStorage.getItem("${STORAGE_KEY}")??"${DEFAULT_ID}";${JSON.stringify(SECTION_IDS)}.forEach(function(s){var el=document.getElementById("section-"+s);if(el){if(s===id)el.setAttribute("open","");else el.removeAttribute("open")}})}`}
      />
    </div>
  )
}

        html={`{var id=localStorage.getItem("${STORAGE_KEY}")??"${DEFAULT_ID}";${JSON.stringify(SECTION_IDS)}.forEach(function(s){var el=document.getElementById("section-"+s);if(el){if(s===id)el.setAttribute("open","");else el.removeAttribute("open")}})}`}
      />
    </div>
  )
}

inline script와 lazy useState initializer는 둘 다 localStorage에서 값을 읽습니다. 둘은 항상 일치하므로 React의 initial state가 DOM과 맞아떨어집니다.

The inline script and the lazy useState initializer both read from localStorage. They always agree, so React's initial state matches the DOM.

Re-applying attributes in development개발 환경에서 attribute 다시 적용하기

inline script는 parsing 중에 attribute를 설정하며, production build에는 이것만으로 충분합니다. 하지만 개발 중에는 React의 Strict Mode가 bug를 드러내기 위해 component를 한 번 더 remount하는데, 이때 <html>, <head>, <body>를 JSX에서 관리하는 attribute만 남도록 reset하면서 script가 설정한 attribute를 지워 버립니다. 그러면 page가 그 attribute 없이 render되어, 값의 source of truth를 무시하게 됩니다.

The inline script sets the attribute during parsing, which is all a production build needs. In development, though, React's Strict Mode remounts components once to surface bugs, and on that remount it resets <html>, <head>, and <body> to only the attributes it manages from JSX, clearing the one the script set. The page then renders without the attribute, ignoring the value's source of truth.

이를 해결하는 한 가지 방법은 inline script가 전혀 없을 때 했을 방식을 그대로 하는 것입니다. theme을 소유하는 component에서, paint 전에 실행되는 useLayoutEffect 안에서 client에 저장된 값을 읽어 적용하세요:

One way to fix this is to do what you would do without the inline script at all. Read the stored value on the client and apply it, in the component that owns the theme, in a useLayoutEffect that runs before paint:

TSapp/components/theme-toggle.tsx
'use client'

import { useLayoutEffect } from 'react'

export function ThemeToggle() {
  // Re-apply after React clears it on the dev remount. This is a no-op in production.
  useLayoutEffect(() => {
    const theme = localStorage.getItem('theme')
    if (theme) document.documentElement.setAttribute('data-theme', theme)
  }, [])

  function toggle() {
    const next =
      (localStorage.getItem('theme') ?? 'light') === 'dark' ? 'light' : 'dark'
    localStorage.setItem('theme', next)
    document.documentElement.setAttribute('data-theme', next)
  }

  return <button onClick={toggle}>Toggle theme</button>
}

Why not useEffect?왜 useEffect가 아닐까?

useEffect는 hydration과 paint 이후에 실행됩니다. 사용자는 server 값을 먼저 본 뒤에 수정된 값을 보게 됩니다. effect 안에서 state를 설정하면 re-render도 일어나는데, 이는 상위 Suspense boundary를 다시 활성화할 수 있습니다.

useEffect runs after hydration and paint. The user sees the server value first, then the correction. Setting state in an effect also triggers a re-render, which can reactivate parent Suspense boundaries.

useLayoutEffect는 paint 전, 하지만 hydration 후에 실행됩니다. hydration과 paint 사이의 깜빡임은 막지만, HTML이 도착한 시점과 React가 hydrate하는 시점 사이의 깜빡임은 막지 못합니다. 느린 연결에서는 React가 load되기 전에 브라우저가 server HTML을 paint합니다. inline script는 React가 관여하기 전, HTML parsing 중에 실행됩니다.

useLayoutEffect runs before paint but after hydration. It prevents the flash between hydration and paint, but not the flash between the HTML arriving and React hydrating. On slow connections, the browser paints the server HTML before React has loaded. The inline script runs during HTML parsing, before React is involved.

Why not read from headers or cookies at request time?왜 request 시점에 header나 cookie를 읽지 않을까?

await headers()로 Accept-Language를 읽으면 server가 request별로 format할 수 있습니다. Cache Components를 사용하면 날짜만 Suspense fallback으로 감싸 page의 나머지는 static으로 유지할 수 있습니다. 하지만 즉시 콘텐츠를 보여 주는 대신 fallback을 보여 줘야 하고, Accept-Language에는 time zone 정보가 포함되지 않습니다.

Reading Accept-Language with await headers() lets the server format per-request. With Cache Components, you can wrap just the date in a Suspense fallback so the rest of the page stays static. But you'd need to show a fallback instead of immediate content, and Accept-Language doesn't include time zone information.
