How to implement Incremental Static Regeneration (ISR)Incremental Static Regeneration (ISR) 구현하기

예제
  • Next.js Commerce
  • On-Demand ISR
  • Next.js Forms
Good to know

이 가이드는 Cache Components를 사용하지 않는 ISR을 다룹니다. cacheComponents를 사용 중이라면 대신 ISR with Cache Components를 참고하세요.

This guide covers ISR without Cache Components. If you are using cacheComponents, see ISR with Cache Components instead.

Incremental Static Regeneration (ISR)을 사용하면 다음을 할 수 있습니다:

Incremental Static Regeneration (ISR) enables you to:

  • 전체 사이트를 다시 build하지 않고 static 콘텐츠 업데이트
  • 대부분의 request에 prerender된 static page를 제공해 server 부하 감소
  • 페이지에 적절한 cache-control header가 자동으로 추가되도록 보장
  • 긴 next build 시간 없이 대량의 콘텐츠 페이지 처리
  • Update static content without rebuilding the entire site
  • Reduce server load by serving prerendered, static pages for most requests
  • Ensure proper cache-control headers are automatically added to pages
  • Handle large amounts of content pages without long next build times

다음은 최소한의 예제입니다:

Here's a minimal example:

TSJSapp/blog/[id]/page.tsx
interface Post {
  id: string
  title: string
  content: string
}

// Next.js will invalidate the cache when a
// request comes in, at most once every 60 seconds.
export const revalidate = 60

export async function generateStaticParams() {
  const posts: Post[] = await fetch('https://api.vercel.app/blog').then((res) =>
    res.json()
  )
  return posts.map((post) => ({
    id: String(post.id),
  }))
}

export default async function Page({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const post: Post = await fetch(`https://api.vercel.app/blog/${id}`).then(
    (res) => res.json()
  )
  return (
    <main>
      <h1>{post.title}</h1>
      <p>{post.content}</p>
    </main>
  )
}
// Next.js will invalidate the cache when a
// request comes in, at most once every 60 seconds.
export const revalidate = 60

export async function generateStaticParams() {
  const posts = await fetch('https://api.vercel.app/blog').then((res) =>
    res.json()
  )
  return posts.map((post) => ({
    id: String(post.id),
  }))
}

export default async function Page({ params }) {
  const { id } = await params
  const post = await fetch(`https://api.vercel.app/blog/${id}`).then((res) =>
    res.json()
  )
  return (
    <main>
      <h1>{post.title}</h1>
      <p>{post.content}</p>
    </main>
  )
}

이 예제의 동작 방식은 다음과 같습니다:

Here's how this example works:

  1. generateStaticParams가 prerender할 post 목록을 반환해 dynamic route에 ISR을 활성화합니다
  2. next build 중에 각 post마다 페이지가 prerender됩니다
  3. 이 페이지들(예: /blog/1)에 대한 모든 request는 cache되어 즉시 응답됩니다
  4. 60초가 지난 후에도 다음 request는 여전히 cache된(이제는 stale한) 페이지를 반환합니다
  5. cache가 무효화되고 background에서 페이지의 새 버전 생성이 시작됩니다
  6. 생성이 성공하면 다음 request는 업데이트된 페이지를 반환하고, 이후 request를 위해 이를 cache합니다
  7. /blog/26이 request되고 해당 post가 존재하면 페이지가 on-demand로 생성됩니다. 이 동작은 다른 dynamicParams 값을 사용해 바꿀 수 있습니다. 하지만 post가 존재하지 않으면 404가 반환됩니다.
  1. generateStaticParams enables ISR for the dynamic route by returning the list of posts to prerender
  2. During next build, a page is prerendered for each post
  3. All requests made to these pages (e.g. /blog/1) are cached and instantaneous
  4. After 60 seconds has passed, the next request will still return the cached (now stale) page
  5. The cache is invalidated and a new version of the page begins generating in the background
  6. Once generated successfully, the next request will return the updated page and cache it for subsequent requests
  7. If /blog/26 is requested, and it exists, the page will be generated on-demand. This behavior can be changed by using a different dynamicParams value. However, if the post does not exist, then 404 is returned.

Examples예제

Time-based revalidation시간 기반 revalidation

이 예제는 /blog에서 blog post 목록을 fetch해 표시합니다. 한 시간이 지나도 다음 방문자는 빠른 응답을 위해 여전히 cache된(stale한) 버전의 페이지를 즉시 받습니다. 동시에 Next.js는 background에서 새 버전의 재생성을 시작합니다. 새 버전이 성공적으로 생성되면 cache된 버전을 대체하고, 이후 방문자는 업데이트된 콘텐츠를 받게 됩니다.

This fetches and displays a list of blog posts on /blog. After an hour has passed, the next visitor will still receive the cached (stale) version of the page immediately for a fast response. Simultaneously, Next.js triggers regeneration of a fresh version in the background. Once the new version is successfully generated, it replaces the cached version, and subsequent visitors will receive the updated content.

TSJSapp/blog/page.tsx
interface Post {
  id: string
  title: string
  content: string
}

export const revalidate = 3600 // invalidate every hour

export default async function Page() {
  const data = await fetch('https://api.vercel.app/blog')
  const posts: Post[] = await data.json()
  return (
    <main>
      <h1>Blog Posts</h1>
      <ul>
        {posts.map((post) => (
          <li key={post.id}>{post.title}</li>
        ))}
      </ul>
    </main>
  )
}
export const revalidate = 3600 // invalidate every hour

export default async function Page() {
  const data = await fetch('https://api.vercel.app/blog')
  const posts = await data.json()
  return (
    <main>
      <h1>Blog Posts</h1>
      <ul>
        {posts.map((post) => (
          <li key={post.id}>{post.title}</li>
        ))}
      </ul>
    </main>
  )
}

revalidation 시간은 길게 설정하는 것을 권장합니다. 예를 들어 1초 대신 1시간으로 설정하세요. 더 정밀한 제어가 필요하다면 on-demand revalidation 사용을 고려하세요. 실시간 데이터가 필요하다면 dynamic rendering으로 전환하는 것을 고려하세요.

We recommend setting a high revalidation time. For instance, 1 hour instead of 1 second. If you need more precision, consider using on-demand revalidation. If you need real-time data, consider switching to dynamic rendering.

On-demand revalidation with revalidatePathrevalidatePath를 사용한 on-demand revalidation

더 정밀한 revalidation 방법으로, revalidatePath 함수를 사용해 cache된 페이지를 on-demand로 무효화하세요.

For a more precise method of revalidation, invalidate cached pages on-demand with the revalidatePath function.

예를 들어 이 Server Action은 새 post를 추가한 뒤 호출됩니다. Server Component에서 fetch를 쓰든 database에 연결하든 데이터를 어떻게 가져오는지와 관계없이, 이 호출은 route 전체의 cache를 무효화합니다. 해당 route에 대한 다음 request가 재생성을 trigger하고 새 데이터를 제공하며, 이 데이터는 이후 request를 위해 cache됩니다.

For example, this Server Action would get called after adding a new post. Regardless of how you retrieve your data in your Server Component, either using fetch or connecting to a database, this will invalidate the cache for the entire route. The next request to that route will trigger regeneration and serve fresh data, which will then be cached for subsequent requests.

Note

revalidatePath는 cache entry를 무효화하지만, 재생성은 다음 request에서 일어납니다. 다음 request를 기다리지 않고 cache entry를 즉시 적극적으로(eagerly) 재생성하고 싶다면 Pages router의 res.revalidate method를 사용할 수 있습니다. App Router에서도 eager 재생성 기능을 제공하는 새 method를 추가하는 작업이 진행 중입니다.

revalidatePath invalidates the cache entries but regeneration happens on the next request. If you want to eagerly regenerate the cache entry immediately instead of waiting for the next request, you can use the Pages router res.revalidate method. We're working on adding new methods to provide eager regeneration capabilities for the App Router.

TSJSapp/actions.ts
'use server'

import { revalidatePath } from 'next/cache'

export async function createPost() {
  // Invalidate the cache for the /posts route
  revalidatePath('/posts')
}
'use server'

import { revalidatePath } from 'next/cache'

export async function createPost() {
  // Invalidate the cache for the /posts route
  revalidatePath('/posts')
}

On-demand revalidation with revalidateTagrevalidateTag를 사용한 on-demand revalidation

대부분의 경우에는 path 전체를 revalidate하는 편이 좋습니다. 더 세밀한 제어가 필요하다면 revalidateTag 함수를 사용할 수 있습니다. 예를 들어 개별 fetch 호출에 tag를 붙일 수 있습니다:

For most use cases, prefer revalidating entire paths. If you need more granular control, you can use the revalidateTag function. For example, you can tag individual fetch calls:

TSJSapp/blog/page.tsx
export default async function Page() {
  const data = await fetch('https://api.vercel.app/blog', {
    next: { tags: ['posts'] },
  })
  const posts = await data.json()
  // ...
}
export default async function Page() {
  const data = await fetch('https://api.vercel.app/blog', {
    next: { tags: ['posts'] },
  })
  const posts = await data.json()
  // ...
}

ORM을 사용하거나 database에 연결한다면 unstable_cache를 사용할 수 있습니다:

If you are using an ORM or connecting to a database, you can use unstable_cache:

TSJSapp/blog/page.tsx
import { unstable_cache } from 'next/cache'
import { db, posts } from '@/lib/db'

const getCachedPosts = unstable_cache(
  async () => {
    return await db.select().from(posts)
  },
  ['posts'],
  { revalidate: 3600, tags: ['posts'] }
)

export default async function Page() {
  const posts = getCachedPosts()
  // ...
}
import { unstable_cache } from 'next/cache'
import { db, posts } from '@/lib/db'

const getCachedPosts = unstable_cache(
  async () => {
    return await db.select().from(posts)
  },
  ['posts'],
  { revalidate: 3600, tags: ['posts'] }
)

export default async function Page() {
  const posts = getCachedPosts()
  // ...
}

그런 다음 Server Actions나 Route Handler에서 revalidateTag를 사용할 수 있습니다:

You can then use revalidateTag in a Server Actions or Route Handler:

TSJSapp/actions.ts
'use server'

import { revalidateTag } from 'next/cache'

export async function createPost() {
  // Invalidate all data tagged with 'posts'
  revalidateTag('posts', 'max')
}
'use server'

import { revalidateTag } from 'next/cache'

export async function createPost() {
  // Invalidate all data tagged with 'posts'
  revalidateTag('posts', 'max')
}

Handling uncaught exceptions처리되지 않은 exception 다루기

데이터를 revalidate하는 중에 error가 발생하면, 마지막으로 성공적으로 생성된 데이터가 계속 cache에서 제공됩니다. 그다음 request에서 Next.js는 데이터 revalidate를 다시 시도합니다. error handling에 대해 더 알아보기.

If an error is thrown while attempting to revalidate data, the last successfully generated data will continue to be served from the cache. On the next subsequent request, Next.js will retry revalidating the data. Learn more about error handling.

cache된 페이지와 데이터를 영구 저장소(durable storage)에 보관하거나, Next.js 애플리케이션의 여러 container 또는 instance 사이에서 cache를 공유하고 싶다면 Next.js cache 위치를 설정할 수 있습니다. 더 알아보기.

You can configure the Next.js cache location if you want to persist cached pages and data to durable storage, or share the cache across multiple containers or instances of your Next.js application. Learn more.

Verifying correct production behaviorproduction 동작이 올바른지 검증하기

production에서 페이지가 올바르게 cache되고 revalidate되는지 검증하려면, next build를 실행한 다음 next start로 production Next.js server를 실행해 로컬에서 테스트할 수 있습니다.

To verify your pages are cached and revalidated correctly in production, you can test locally by running next build and then next start to run the production Next.js server.

이렇게 하면 production 환경에서 동작하는 것과 똑같이 ISR 동작을 테스트할 수 있습니다. 더 자세히 디버깅하려면 .env 파일에 다음 environment variable을 추가하세요:

This will allow you to test ISR behavior as it would work in a production environment. For further debugging, add the following environment variable to your .env file:

>_.env
NEXT_PRIVATE_DEBUG_CACHE=1

이렇게 하면 Next.js server console에 ISR cache hit과 miss가 log로 출력됩니다. 출력을 살펴보면 next build 중에 어떤 페이지가 생성되는지, 그리고 path가 on-demand로 접근될 때 페이지가 어떻게 업데이트되는지 확인할 수 있습니다.

This will make the Next.js server console log ISR cache hits and misses. You can inspect the output to see which pages are generated during next build, as well as how pages are updated as paths are accessed on-demand.

Caveats주의 사항

  • ISR은 Node.js runtime(기본값)을 사용할 때만 지원됩니다.
  • Static Export를 만들 때는 ISR이 지원되지 않습니다.
  • prerender된 route에 fetch request가 여러 개 있고 각각의 revalidate 주기가 다르다면, ISR에는 가장 짧은 시간이 사용됩니다. 하지만 각 revalidate 주기는 cache에서 여전히 존중됩니다.
  • route에서 사용하는 fetch request 중 하나라도 revalidate 시간이 0이거나 명시적인 no-store가 있다면, 해당 route는 dynamic하게 render됩니다.
  • on-demand ISR request에는 Proxy가 실행되지 않으므로, Proxy의 path rewrite나 logic이 적용되지 않습니다. 정확한 path를 revalidate하고 있는지 확인하세요. 예를 들어 rewrite된 /post-1이 아니라 /post/1을 revalidate해야 합니다.
  • 여러 instance를 실행할 때 기본 file-system cache는 instance마다 따로 존재합니다. on-demand revalidation은 호출을 받은 instance만 무효화합니다. instance 간에 조율하려면 공유 custom cache handler를 사용하세요. 전체 아키텍처는 How Revalidation Works를 참고하세요.
  • background 재생성(stale-while-revalidate)은 이를 trigger한 request를 받은 instance에서 실행됩니다. request당 과금하는 플랫폼에서는 이 background 작업이 추가 compute로 계산됩니다.
  • x-nextjs-cache response header로 cache 동작을 관찰할 수 있습니다. 값은 HIT(cache에서 제공), STALE(cache에서 제공하면서 background에서 revalidate 중), MISS(cache에 없어서 새로 render), REVALIDATED(on-demand revalidation으로 재생성) 중 하나입니다.
  • ISR is only supported when using the Node.js runtime (default).
  • ISR is not supported when creating a Static Export.
  • If you have multiple fetch requests in a prerendered route, and each has a different revalidate frequency, the lowest time will be used for ISR. However, those revalidate frequencies will still be respected by the cache.
  • If any of the fetch requests used on a route have a revalidate time of 0, or an explicit no-store, the route will be dynamically rendered.
  • Proxy won't be executed for on-demand ISR requests, meaning any path rewrites or logic in Proxy will not be applied. Ensure you are revalidating the exact path. For example, /post/1 instead of a rewritten /post-1.
  • When running multiple instances, the default file-system cache is per-instance. On-demand revalidation only invalidates the instance that receives the call. Use a shared custom cache handler to coordinate across instances. See How Revalidation Works for the full architecture.
  • Background regeneration (stale-while-revalidate) runs on the instance that receives the triggering request. On platforms with per-request billing, this background work counts as additional compute.
  • You can use the x-nextjs-cache response header to observe cache behavior. Values are HIT (served from cache), STALE (served from cache, revalidating in background), MISS (not in cache, rendered fresh), or REVALIDATED (regenerated via on-demand revalidation).
