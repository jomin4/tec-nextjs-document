Caching캐싱

이 페이지는 next.config.ts 파일에서 cacheComponents: true를 설정해 활성화하는 Cache Components 기반의 caching을 다룹니다. Cache Components를 사용하지 않는다면 Caching and Revalidating (Previous Model) 가이드를 참고하세요.

This page covers caching with Cache Components, enabled by setting cacheComponents: true in your next.config.ts file. If you're not using Cache Components, see the Caching and Revalidating (Previous Model) guide.

caching은 data fetching과 기타 연산의 결과를 저장해 두어, 이후 같은 데이터에 대한 request가 들어왔을 때 작업을 다시 하지 않고 더 빠르게 제공하는 기법입니다.

Caching is a technique for storing the result of data fetching and other computations so that future requests for the same data can be served faster, without doing the work again.

Enabling Cache ComponentsCache Components 활성화하기

권장 create-next-app 기본값으로 만든 새 App Router 앱에는 Cache Components와 Partial Prefetching이 이미 활성화되어 있습니다.

New App Router apps created with the recommended create-next-app defaults already have Cache Components and Partial Prefetching enabled.

기존 앱이나 직접 만든 앱에서 활성화하려면 Next config 파일에 cacheComponents와 partialPrefetching option을 추가하세요:

To enable it in an existing or manually created app, add the cacheComponents and partialPrefetching options to your Next config file:

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
}

export default nextConfig
/** @type {import('next').NextConfig} */
const nextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
}

module.exports = nextConfig

partialPrefetching은 명시적으로 설정하세요. Cache Components의 첫 release에는 Partial Prefetching이 포함되지 않았기 때문에, 설정하지 않고 두면 warning이 log에 출력됩니다. Partial Prefetching 이전에 Cache Components를 도입한 앱을 migrate하는 동안에만 false로 설정하세요. 다음 major release에서는 두 기능이 모든 곳에서 활성화되고 이 option들은 제거될 예정입니다.

Set partialPrefetching explicitly. Leaving it unset logs a warning, because the first release of Cache Components did not include Partial Prefetching. Set it to false only while migrating an app that adopted Cache Components before Partial Prefetching. Both features will be enabled everywhere in the next major release, and the options will be removed.

Good to know

Cache Components가 활성화되면 GET Route Handler도 page와 같은 prerendering 모델을 따릅니다. 자세한 내용은 Route Handlers with Cache Components를 참고하세요.

When Cache Components is enabled, GET Route Handlers follow the same prerendering model as pages. See Route Handlers with Cache Components for details.

Usage사용법

use cache directive는 async 함수와 component의 반환값을 cache합니다. 두 가지 수준에서 적용할 수 있습니다:

The use cache directive caches the return value of async functions and components. You can apply it at two levels:

  • Data-level: 데이터를 fetch하거나 계산하는 함수를 cache합니다(예: getProducts(), getUser(id))
  • UI-level: component나 page 전체를 cache합니다(예: async function BlogPosts())
  • Data-level: Cache a function that fetches or computes data (e.g., getProducts(), getUser(id))
  • UI-level: Cache an entire component or page (e.g., async function BlogPosts())

cache directive는 결과에 lifetime(수명)을 부여하며, Next.js는 이를 시간 기반 revalidation과 rendering 최적화에 사용합니다. mutation 이후의 on-demand revalidation은 Revalidating을 참고하세요. cache된 결과가 어떻게 static shell의 일부가 되고 prefetch에 포함될 수 있는지는 Prerendering을 참고하세요.

A cache directive gives a result a lifetime, which Next.js uses for time-based revalidation and rendering optimizations. For on-demand revalidation after a mutation, see Revalidating. See Prerendering for how cached results become part of the static shell and may be included in a prefetch.

Good to know

모든 cache directive에 cacheLife를 함께 지정하는 것을 권장합니다. 지정하지 않으면 암묵적으로 default profile이 적용됩니다.

We recommend pairing every cache directive with a cacheLife. Without one, the implicit default profile applies.

인자(argument)와 상위 scope에서 capture된 값은 자동으로 cache key의 일부가 됩니다. 즉, 입력이 다르면 별도의 cache entry가 만들어집니다. entry에 무엇이 저장되는지는 cache output을, 무엇을 cache할 수 있고 인자가 어떻게 동작하는지는 serialization 요구 사항과 제약을 참고하세요.

Arguments and any values captured from parent scopes automatically become part of the cache key, which means different inputs will produce separate cache entries. See cache output for what an entry holds, and serialization requirements and constraints for details on what can be cached and how arguments work.

Data-level caching

데이터를 fetch하는 비동기 함수를 cache하려면 함수 본문 맨 위에 use cache directive를 추가하세요:

To cache an asynchronous function that fetches data, add the use cache directive at the top of the function body:

TSapp/lib/data.ts
import { cacheLife } from 'next/cache'

export async function getUsers() {
  'use cache'
  cacheLife('hours')
  return db.query('SELECT * FROM users')
}

Data-level caching은 같은 데이터를 여러 component에서 사용하거나, 데이터를 UI와 독립적으로 cache하고 싶을 때 유용합니다.

Data-level caching is useful when the same data is used across multiple components, or when you want to cache the data independently from the UI.

UI-level caching

component, page, layout 전체를 cache하려면 component나 page 본문 맨 위에 use cache directive를 추가하세요:

To cache an entire component, page, or layout, add the use cache directive at the top of the component or page body:

TSapp/page.tsx
import { cacheLife } from 'next/cache'

export default async function Page() {
  'use cache'
  cacheLife('hours')

  const users = await db.query('SELECT * FROM users')

  return (
    <ul>
      {users.map((user) => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  )
}

파일 맨 위에 "use cache"를 추가하면 그 파일에서 export되는 모든 함수가 cache됩니다.

If you add "use cache" at the top of a file, all exported functions in the file will be cached.

Streaming uncached datacache되지 않은 데이터 streaming하기

API, database 또는 기타 async 작업 같은 비동기 source에서 데이터를 fetch하고 매 request마다 최신 데이터가 필요한 component에는 "use cache"를 사용하지 마세요.

For components that fetch data from an asynchronous source such as an API, a database, or any other async operation, and require fresh data on every request, do not use "use cache".

대신 component를 <Suspense>로 감싸고 fallback UI를 제공하세요. async 작업이 request 시점에 실행되는 동안 fallback은 prerender된 shell과 함께 전달됩니다.

Instead, wrap the component in <Suspense> and provide a fallback UI. The fallback ships with the prerendered shell while the async work runs at request time.

TSpage.tsx
import { Suspense } from 'react'

async function LatestPosts() {
  const data = await fetch('https://api.example.com/posts')
  const posts = await data.json()
  return (
    <ul>
      {posts.map((post) => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  )
}

export default function Page() {
  return (
    <>
      <h1>My Blog</h1>
      <Suspense fallback={<p>Loading posts...</p>}>
        <LatestPosts />
      </Suspense>
    </>
  )
}

예를 들어 <p>Loading posts...</p>는 static shell에 포함되고, post들은 request 시점에 stream되어 들어옵니다.

For example, <p>Loading posts...</p> is included in the static shell, and the posts stream in at request time.

cache되지 않은 read를 <Suspense> boundary로 감싸지 않으면, dev overlay가 다음 해결책과 함께 blocking-route insight를 표시합니다:

Without a <Suspense> boundary around the uncached read, the dev overlay surfaces the blocking-route insight with this fix:

<Suspense>는 async 작업이 완료되는 동안 fallback UI를 제공하지만, 그 자체로 component를 dynamic rendering으로 전환(opt into)하지는 않습니다. component가 동기 작업만 수행한다면 <Suspense>로 감쌌는지와 관계없이 prerendering 중에 완료됩니다.

<Suspense> provides a fallback UI while async work completes, but it does not itself opt a component into dynamic rendering. If a component only performs synchronous work, it will complete during prerendering regardless of whether it is wrapped in <Suspense>.

Working with runtime APIsruntime API 다루기

runtime API는 사용자가 request를 보낼 때만 알 수 있는 정보를 필요로 합니다. 여기에는 다음이 포함됩니다:

Runtime APIs require information that is only available when a user makes a request. These include:

  • cookies - 사용자의 cookie 데이터
  • headers - request header
  • searchParams - URL query parameter
  • params - dynamic route parameter. build 시점에 특정 값을 prerender하려면 generateStaticParams를 사용하고, 알 수 없는 param이 background에서 resolve되는 동안 App Shell을 제공하려면 ISR with Cache Components를 사용하세요.
  • cookies - User's cookie data
  • headers - Request headers
  • searchParams - URL query parameters
  • params - Dynamic route parameters. Use generateStaticParams to prerender specific values at build time, or ISR with Cache Components to serve an App Shell while unknown params resolve in the background.

runtime API에 접근하는 component는 <Suspense>로 감싸야 합니다:

Components that access runtime APIs should be wrapped in <Suspense>:

TSpage.tsx
import { cookies } from 'next/headers'
import { Suspense } from 'react'

async function UserGreeting() {
  const cookieStore = await cookies()
  const theme = cookieStore.get('theme')?.value || 'light'
  return <p>Your theme: {theme}</p>
}

export default function Page() {
  return (
    <>
      <h1>Dashboard</h1>
      <Suspense fallback={<p>Loading...</p>}>
        <UserGreeting />
      </Suspense>
    </>
  )
}

<Suspense> 없이 runtime API에 접근하면 dev overlay에 같은 blocking-route insight가 같은 해결책과 함께 표시됩니다:

A runtime API access without <Suspense> surfaces the same blocking-route insight in the dev overlay, with the same fix:

runtime에 의존하는 데이터도 Cache Components와 함께 제공되는 또 다른 variant인 "use cache: private"로 cache lifetime을 부여할 수 있습니다. 이 directive는 cookie, header, searchParams를 직접 읽는 함수에 lifetime을 부여하므로, 그 결과가 prefetch에 포함될 수 있습니다.

Runtime-dependent data can still be given a cache lifetime with "use cache: private", another variant that ships with Cache Components. It gives a lifetime to a function that reads cookies, headers, or searchParams directly, so it can be included in a prefetch.

다음 섹션에서는 use cache: private의 대안으로, runtime 값을 추출해 공유되는 cache 함수에 전달하는 방법을 보여 줍니다.

The following section shows an alternative to use cache: private: extracting a runtime value and passing it to a shared cached function.

Passing runtime values to cached functionsruntime 값을 cache 함수에 전달하기

runtime API에서 값을 추출해 cache 함수의 인자로 전달할 수 있습니다:

You can extract values from runtime APIs and pass them as arguments to cached functions:

TSapp/profile/page.tsx
import { cookies } from 'next/headers'
import { Suspense } from 'react'

export default function Page() {
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <ProfileContent />
    </Suspense>
  )
}

// Component (not cached) reads runtime data
async function ProfileContent() {
  const session = (await cookies()).get('session')?.value
  return <CachedContent sessionId={session} />
}

// Cached component receives extracted value as a prop
async function CachedContent({ sessionId }: { sessionId: string }) {
  'use cache'
  // sessionId becomes part of the cache key
  const data = await fetchUserData(sessionId)
  return <div>{data}</div>
}

request 시점에 일치하는 cache entry가 없으면 <CachedContent />가 실행되고, 같은 sessionId를 가진 이후 request를 위해 결과를 저장합니다.

At request time, <CachedContent /> executes if no matching cache entry is found, and stores the result for future requests with the same sessionId.

Good to know

<CachedContent />는 request 데이터 뒤에 놓여 있으므로 prerender된 static shell에 추가되지 않습니다. runtime에는 기본적으로 in-memory에 cache되는데, 이는 serverless request 간에 유지되지 않으므로 매 request마다 다시 평가될 수 있습니다. 지속적이고 공유되는 caching이 필요하다면 'use cache: remote'를 사용하세요.

Because <CachedContent /> is gated behind request data, it isn't added to the prerendered static shell. At runtime it's cached in-memory by default, which doesn't persist across serverless requests, so it may re-evaluate on each request. Reach for 'use cache: remote' for durable, shared caching.

이 패턴을 사용하면 prefetching이 client transition 중에 사용자의 실제 session으로 <CachedContent />를 prerender해, 클릭하기 전에 결과를 준비해 둘 수 있습니다. server-side entry가 request 사이에 거의 살아남지 못하더라도 이 방식은 동작합니다. 여러분이 부여한 lifetime 덕분에 결과가 prefetch에 포함되고, client는 그 결과를 cacheLife의 stale 기간 동안 fresh한 것으로 취급하기 때문입니다.

With this pattern, prefetching can prerender <CachedContent /> with the user's actual session during a client transition and have the result ready before the click. This works even when server-side entries rarely survive between requests, because the lifetime you assign is what lets the result join the prefetch, where the client treats it as fresh for its cacheLife stale window.

Static, cached, and streamingStatic, cached, streaming

다음은 static 콘텐츠, cache된 dynamic 콘텐츠, streaming되는 dynamic 콘텐츠가 한 page에서 함께 동작하는 전체 예제입니다:

Here's a complete example showing static content, cached dynamic content, and streaming dynamic content working together on a single page:

TSapp/blog/page.tsx
import { Suspense } from 'react'
import { cookies } from 'next/headers'
import { cacheLife, cacheTag } from 'next/cache'
import Link from 'next/link'

export default function BlogPage() {
  return (
    <>
      {/* Static content - prerendered automatically */}
      <header>
        <h1>Our Blog</h1>
        <nav>
          <Link href="/">Home</Link> | <Link href="/about">About</Link>
        </nav>
      </header>

      {/* Cached dynamic content - included in the static shell */}
      <BlogPosts />

      {/* Runtime dynamic content - streams at request time */}
      <Suspense fallback={<p>Loading your preferences...</p>}>
        <UserPreferences />
      </Suspense>
    </>
  )
}

type Post = { id: string; title: string; author: string; date: string }

// Everyone sees the same blog posts (revalidated every hour)
async function BlogPosts() {
  'use cache'
  cacheLife('hours')
  cacheTag('posts')

  const res = await fetch('https://api.vercel.app/blog')
  const posts: Post[] = await res.json()

  return (
    <section>
      <h2>Latest Posts</h2>
      <ul>
        {posts.map((post) => (
          <li key={post.id}>
            <h3>{post.title}</h3>
            <p>
              By {post.author} on {post.date}
            </p>
          </li>
        ))}
      </ul>
    </section>
  )
}

// UI that depends on a value stored in cookies
async function UserPreferences() {
  const theme = (await cookies()).get('theme')?.value || 'light'
  const favoriteCategory = (await cookies()).get('category')?.value

  return (
    <aside>
      <p>Your theme: {theme}</p>
      {favoriteCategory && <p>Favorite category: {favoriteCategory}</p>}
    </aside>
  )
}

prerendering 중에 header(static)와 blog post(use cache로 cache됨)는 사용자 preference용 fallback UI와 함께 static shell의 일부가 됩니다. cookie에 저장된 UI preference는 request 시점에 stream되어 들어옵니다.

During prerendering, the header (static) and blog posts (cached with use cache) become part of the static shell, along with the fallback UI for user preferences. The UI preferences stored in cookies stream in at request time.

여기서 cookies()를 읽어도, 이전 rendering 모델처럼 route 전체가 dynamic rendering으로 전환되지는 않습니다. Suspense boundary가 runtime 접근이 stream되는 곳에 fallback UI를 제공하고, static 콘텐츠와 cache된 콘텐츠는 여전히 initial HTML에 담겨 전달됩니다.

Reading cookies() here doesn't opt-in the whole route into dynamic rendering, the way the previous rendering model did. The Suspense boundary provides fallback UI where the runtime access streams, while static and cached content still ship in the initial HTML.

<Suspense>가 async 접근을 감싸 가두는 것처럼, error boundary는 실패를 가둡니다. rendering 중에 error가 날 수 있는 subtree를 error boundary로 감싸세요. component 수준 boundary에는 catchError를, route 수준 boundary에는 error.js file convention을 사용하세요.

Just as <Suspense> contains async access, an error boundary contains failures: wrap them around a subtree that might error during rendering. Use catchError for component-level boundaries, or the error.js file convention for route-level boundaries.

개발하면서, generateMetadata와 generateViewport 안에서 cache되지 않은 fetch나 runtime 데이터 접근을 하면 page에서와 같은 insight와 error가 표시되어 의도한 rendering으로 안내한다는 점을 기억하세요. 알려진 param 값과 알 수 없는 param 값을 모두 다루는 incremental static regeneration은 ISR with Cache Components를 참고하세요.

As you build, consider that inside generateMetadata and generateViewport, uncached fetches or runtime data access surface the same insights and errors as in your page, guiding you to the rendering you intend. For incremental static regeneration with both known and unknown param values, see ISR with Cache Components.

Random values and timestamps무작위 값과 timestamp

Math.random(), Date.now(), crypto.randomUUID() 같은 작업은 실행할 때마다 다른 값을 만듭니다. Cache Components에서는 이런 작업을 명시적으로 처리해야 합니다.

Operations like Math.random(), Date.now(), or crypto.randomUUID() produce different values each time they execute. Cache Components requires you to explicitly handle these.

Good to know

performance.now()는 telemetry용이므로 Next.js는 이를 보호해야 할 값으로 취급하지 않습니다. 시간 측정에 사용하고, 결과는 render하지 말고 logger나 metrics로 전달하세요.

performance.now() is meant for telemetry, so Next.js doesn't treat it as a value to guard. Use it for timing and pass the result to your logger or metrics rather than rendering it.

request마다 고유한 값을 생성하려면 이런 작업 전에 connection()을 호출해 request 시점으로 미루고, component를 <Suspense>로 감싸세요:

To generate unique values per request, defer to request time by calling connection() before these operations, and wrap the component in <Suspense>:

TSpage.tsx
import { connection } from 'next/server'
import { Suspense } from 'react'

async function UniqueContent() {
  await connection()
  const uuid = crypto.randomUUID()
  return <p>Request ID: {uuid}</p>
}

export default function Page() {
  return (
    <Suspense fallback={<p>Loading...</p>}>
      <UniqueContent />
    </Suspense>
  )
}

또는 결과를 cache해서 revalidation 전까지 모든 사용자가 같은 값을 보게 할 수도 있습니다:

Alternatively, you can cache the result so all users see the same value until revalidation:

TSpage.tsx
export default async function Page() {
  'use cache'
  const buildId = crypto.randomUUID()
  return <p>Build ID: {buildId}</p>
}

Predictable values예측 가능한 값

render할 때마다 달라질 수 있는 무작위 값이나 timestamp와 달리, module import, 동기 I/O, 순수 연산은 실행할 때마다 같은 결과를 냅니다. 이런 작업만 사용하는 component는 자동으로 prerender되며, 그 출력은 build 시점에 static HTML의 일부가 됩니다.

Unlike random values and timestamps, which can vary between renders, module imports, synchronous I/O, and pure computations produce the same result every time they run. Components using only these operations are prerendered automatically, and their output becomes part of the static HTML at build time.

TSpage.tsx
import fs from 'node:fs'

export default async function Page() {
  const constants = await import('./constants.json')
  const content = fs.readFileSync('./config.json', 'utf-8')
  const items = JSON.parse(content).items ?? []

  return (
    <div>
      <h1>{constants.appName}</h1>
      <ul>
        {items.map((item) => (
          <li key={item.id}>{item.value}</li>
        ))}
      </ul>
    </div>
  )
}
Good to know

여기에는 better-sqlite3나 Node.js 내장 node:sqlite처럼 동기 API를 가진 embedded database에 대한 query도 포함됩니다. 동기 source에서 request마다 데이터를 가져와야 한다면 query 전에 connection()을 호출하세요.

This includes queries to embedded databases with synchronous APIs, such as better-sqlite3 or Node.js's built-in node:sqlite. If you need per-request data from a synchronous source, call connection() before the query.

일부 비동기 API는 font나 configuration 파일처럼 들어오는 request에 의존하지 않는 로컬 리소스를 읽습니다. 이런 리소스가 모든 request에서 같을 것으로 예상된다면, rendering 중이 아니라 module scope에서 한 번만 읽으세요

Some asynchronous APIs read local resources that don't depend on the incoming request, such as fonts or configuration files. When those resources are expected to be the same for every request, read them once at module scope instead of during rendering

대신 데이터를 rendering 중에 계산하고 request 간에 재사용해야 한다면, read를 use cache로 감싸세요. 데이터가 들어오는 request에 의존하거나 시간이 지나면서 바뀔 것으로 예상된다면, request 시점 rendering 중에 읽으세요.

If the data should instead be computed during rendering and reused across requests, wrap the read in use cache. If the data depends on the incoming request or is expected to change over time, read it during request-time rendering.

TSpage.tsx
import { readFile } from 'node:fs/promises'

const content = await readFile('./config.json', 'utf-8')
const items = JSON.parse(content).items ?? []

export default function Page() {
  return (
    <ul>
      {items.map((item) => (
        <li key={item.id}>{item.value}</li>
      ))}
    </ul>
  )
}

이 예제에서 configuration 파일은 모든 request에서 같을 것으로 예상되므로 module scope에서 한 번만 읽습니다. component 안에서 await readFile()을 호출하면 cache되지 않은 데이터로 취급되어, use cache 안에서 접근하거나 <Suspense> boundary 뒤에 두어야 합니다. 이 파일은 request에 의존하지 않고 바뀔 것으로 예상되지도 않으므로 module scope가 가장 간단한 선택입니다.

In this example, the configuration file is expected to be the same for every request, so it is read once at module scope. Calling await readFile() inside the component would be treated as uncached data that must be either accessed within use cache or behind a <Suspense> boundary. Since this file does not depend on the request and is not expected to change, module scope is the simplest option.

Prerendering

build 시점에 Next.js는 route의 component tree를 render합니다. 각 component가 처리되는 방식은 사용하는 API에 따라 다릅니다:

At build time, Next.js renders your route's component tree. How each component is handled depends on the APIs it uses:

  • use cache: lifetime이 너무 짧지 않다면 결과가 cache되어 static shell에 포함됩니다
  • <Suspense>: 콘텐츠가 request 시점에 stream되는 동안 fallback UI가 static shell에 포함됩니다
  • Predictable values: module import, fs.readFileSync, 순수 연산은 prerender 중에 완료되어 자동으로 static shell에 포함됩니다
  • Random values and timestamps: request마다 고유한 값을 얻으려면 connection() + <Suspense>를, 모든 사용자가 하나의 값을 공유하게 하려면 use cache를 사용하세요
  • use cache: the result is cached and included in the static shell, as long as its lifetime isn't too short
  • <Suspense>: fallback UI is included in the static shell while the content streams at request time
  • Predictable values: module imports, fs.readFileSync, and pure computations complete during prerender and are included in the static shell automatically
  • Random values and timestamps: use connection() + <Suspense> to get a unique value per request, or use cache to share one across users

이렇게 하면 초기 page 로드를 위한 HTML과 client-side navigation을 위한 serialize된 RSC Payload로 구성된 static shell이 생성됩니다. 덕분에 사용자가 URL로 직접 이동하든 다른 page에서 transition하든 브라우저는 완전히 render된 콘텐츠를 즉시 받습니다. 이 rendering 방식을 Partial Prerendering (PPR) 이라고 하며, Cache Components의 기본 동작입니다.

This generates a static shell consisting of HTML for initial page loads and a serialized RSC Payload for client-side navigation, ensuring the browser receives fully rendered content instantly whether users navigate directly to the URL or transition from another page. This rendering approach is called Partial Prerendering (PPR), the default behavior with Cache Components.

생성된 모든 static shell은 upstream server를 거치지 않고 CDN에서 바로 제공할 수 있습니다. 그래서 직접 navigation이 instant해집니다.

Every produced static shell can be served directly from a CDN, without going through to the upstream server. This makes direct navigations instant.

route의 static shell에 무엇이 들어가는지는 build 시점에 무엇을 알 수 있는지에 따라 달라집니다. route의 dynamic params를 알고 있다면 shell에는 그 구체적인 콘텐츠가 담기고, 나머지 cache되지 않은 데이터나 runtime 데이터는 여전히 <Suspense> fallback 뒤에서 stream됩니다. param을 알 수 없다면 재사용 가능하고 URL과 무관한 버전이 App Shell입니다. App Shell은 param에 특화된 부분을 fallback 뒤에 남겨 둔 같은 static shell입니다. Incremental Static Regeneration은 첫 방문 이후 구체적인 버전을 채워 넣습니다.

What ends up in a route's static shell depends on what's known at build time. When a route's dynamic params are known, the shell contains that concrete content, and any remaining uncached or runtime data still streams behind its <Suspense> fallback. When the params aren't known, the reusable, URL-independent version is the App Shell: the same static shell with the param-specific parts left behind their fallbacks. Incremental Static Regeneration fills in the concrete versions after the first visit.

Next.js에서는 prerendering 중에 완료될 수 없는 component를 명시적으로 처리해야 합니다. Next.js는 dev overlay와 dev server console에 validation insight를 표시하는데, 여기에는 route 이름과 해결책(접근을 cache하기, <Suspense> boundary 안으로 옮기기, route를 opt out하기)이 안내됩니다. 이 validation 덕분에 모든 route가 static shell을 생성하므로 직접 navigation이 계속 instant하게 유지됩니다.

Next.js requires you to explicitly handle components that can't complete during prerendering. It surfaces a validation insight in the dev overlay and dev server console that names the route and points at fixes (cache the access, move it into a <Suspense> boundary, or opt the route out). This validation keeps every route producing a static shell, so direct navigations stay instant.

Maximizing the static shellstatic shell 최대화하기

async 작업이 tree 깊숙이 있을수록 page의 더 많은 부분을 prerender할 수 있습니다. 이것이 Cache Components가 보상해 주는 구조적 패턴입니다. 모든 곳에 적용할 만한 일반적인 practice이며, 이어서 설명할 instant navigation과 prefetching의 기반이 됩니다. 이 원칙은 모든 runtime API와 data fetch 같은 async 작업에 적용됩니다.

The deeper your async work sits in the tree, the more of the page can be prerendered. This is the structural pattern Cache Components rewards: a general practice worth applying everywhere, and the foundation for the instant navigation and prefetching that follow. It applies to all runtime APIs and async operations like data fetches.

최상위에서 params를 destructure하는 layout을 생각해 봅시다:

Consider a layout that destructures params at the top level:

TSapp/shop/[slug]/layout.tsx
export default async function Layout({
  children,
  params,
}: LayoutProps<'/shop/[slug]'>) {
  const { slug } = await params

  return (
    <div>
      <Sidebar />
      <h1>{slug}</h1>
      {children}
    </div>
  )
}

이 param이 dynamic이라면(generateStaticParams로 제공되지 않는다면) runtime 데이터이므로 layout을 prerender할 수 없습니다.

If this param is dynamic (not provided by generateStaticParams), it is runtime data and the layout cannot be prerendered.

하지만 parameter 값을 tree의 더 아래쪽에서 읽을 수 있는 경우가 많습니다. layout 수준에서 await하는 대신 params promise를 아래로 전달하고 그곳에서 await하세요:

However, it is often possible to read the parameter value further down the tree. Instead of awaiting at the layout level, pass the params promise down and await there:

TSapp/shop/[slug]/layout.tsx
import { Suspense } from 'react'

// Not async: this layout never awaits params
export default function Layout({
  children,
  params,
}: LayoutProps<'/shop/[slug]'>) {
  return (
    <div>
      <Sidebar />
      <Suspense fallback={<h1>Loading...</h1>}>
        {/* await happens inside the boundary, so the shell still renders */}
        {params.then(({ slug }) => (
          <SlugHeading slug={slug} />
        ))}
      </Suspense>
      {children}
    </div>
  )
}

function SlugHeading({ slug }: { slug: string }) {
  return <h1>{slug}</h1>
}

이제 <Sidebar />, {children}, Suspense fallback이 모두 static shell의 일부가 됩니다. SlugHeading만 request 시점에 stream되어 들어옵니다. params promise 전체를 전달하고 child component에서 await할 수도 있습니다.

Now <Sidebar />, {children}, and the Suspense fallback are all part of the static shell. Only SlugHeading streams in at request time. You can also pass the entire params promise and await it in the child component.

같은 원칙이 cookies(), headers(), searchParams, data fetch에도 적용됩니다. 관련 패턴은 Reusing data with React.cache를 참고하세요.

The same principle applies to cookies(), headers(), searchParams, and data fetches. See Reusing data with React.cache for a related pattern.

Instant navigation

Cache Components는 16.0.0에서 route에 직접 방문했을 때 static shell이 생성되는지 검증하는 기능과 함께 출시되었습니다. client navigation은 다릅니다. 직접 방문을 감싸는 <Suspense> boundary가 transition 중의 render에는 포함되지 않을 수 있습니다. framework가 개입해 주면 이런 구조를 올바르게 잡기가 더 쉽습니다. 이제 Cache Components는 이런 navigation도 검증하여, route로의 navigation을 instant하게 만들도록 안내하는 insight와 error를 제공합니다. 예를 들어 데이터를 <Suspense>로 감싸거나, use cache로 cache하거나, 접근이 일어나는 위치를 옮기는 식입니다.

Cache Components shipped in 16.0.0 with verification that direct visits to a route produce a static shell. Client navigations are different: a <Suspense> boundary that covers a direct visit may not be part of the render during a transition. Getting that structure right is easier when the framework steps in. Cache Components now validates these navigations too, giving you insights and errors that guide you to make navigations to your route instant. For example, wrap data in <Suspense>, cache it with use cache, or move where the access happens.

Prefetching

Partial Prefetching이 활성화되면 router는 기본적으로 각 route의 App Shell을 prefetch합니다. App Shell에는 static 콘텐츠와 cookies(), headers()에서 파생된 session 데이터가 포함됩니다. searchParams나 dynamic params처럼 link의 URL data에 의존하는 cache된 콘텐츠까지 prefetch하려면 해당 link에 prefetch={true}를 설정하세요.

With Partial Prefetching enabled, the router prefetches each route's App Shell by default. The App Shell includes static content and session data derived from cookies() and headers(). To also prefetch cached content that depends on a link's URL data, such as searchParams or dynamic params, set prefetch={true} on that link.

Partial Prefetching route를 가리키는 <Link prefetch={true}>를 사용하면, Next.js는 prefetch 시점에 이번에는 목적지 URL이 resolve된 상태로 그 route의 component tree를 다시 render합니다. 같은 규칙이 적용되지만, 이제 searchParams와 params가 scope 안에 있으므로 tree의 더 많은 부분이 resolve됩니다:

With <Link prefetch={true}> pointing at a Partial Prefetching route, Next.js renders that route's component tree again at prefetch time, this time with the destination URL resolved. The same rules apply, but more of the tree resolves now that its searchParams and params are in scope:

  • runtime API에서 추출한 값(인자로 전달된 값)으로 호출된 use cache는 link별 prefetch에 포함됩니다
  • use cache: private는 server에서 실행되어 runtime 데이터를 직접 읽고, 그 결과를 link별 prefetch의 일부로 브라우저에 cache합니다
  • cache되지 않은 콘텐츠가 request 시점에 stream되는 동안 <Suspense> fallback은 prefetch된 UI에 남아 있습니다
  • use cache called with values extracted from runtime APIs (passed as arguments) joins the per-link prefetch
  • use cache: private executes on the server, reads runtime data directly, and caches the result in the browser as part of the per-link prefetch
  • <Suspense> fallbacks stay in the prefetched UI while uncached content streams at request time

이 link별 prefetch에는 목적지 URL을 알게 된 후 resolve되는 cache된 콘텐츠가 포함됩니다. prefetch 가능한 link마다 server 호출 한 번의 비용이 듭니다.

This per-link prefetch includes cached content that resolves after the destination URL is known. It costs a server invocation per prefetchable link.

예를 들어 URL에서 searchParams를 읽는 검색 page를 생각해 봅시다:

For example, take a search page that reads searchParams from the URL:

TSapp/search/page.tsx
import { Suspense } from 'react'

export default function SearchPage(props: PageProps<'/search'>) {
  return (
    <Suspense fallback={<p>Loading results...</p>}>
      <Results searchParams={props.searchParams} />
    </Suspense>
  )
}

async function Results({
  searchParams,
}: Pick<PageProps<'/search'>, 'searchParams'>) {
  const { q } = await searchParams
  const results = await search(q)
  return (
    <ul>
      {results.map((result) => (
        <li key={result.id}>{result.title}</li>
      ))}
    </ul>
  )
}

async function search(query: string | string[] | undefined) {
  'use cache'
  return db.search(query)
}

직접 방문하면 <Results>는 fallback 뒤에서 stream되어 들어옵니다.

On a direct visit, <Results> streams in behind the fallback.

/search?q=shoes로 가는 <Link>가 prefetch되면, framework는 link의 URL에서 searchParams를 resolve하므로 cache된 search 결과가 클릭 전에 runtime prerender에 포함됩니다. 그런 다음 브라우저는 stale 시간이 지나거나 searchParams가 바뀔 때까지 이 결과를 재사용합니다.

When a <Link> to /search?q=shoes is prefetched, the framework resolves searchParams from the link's URL, so the cached search result is included in the runtime prerender before the click. The browser then reuses it until its stale time passes or the searchParams change.

Where cached content is storedcache된 콘텐츠가 저장되는 곳

cache 함수의 출력은 build 시점이나 runtime에 RSC payload 형태로 serialize됩니다. 다른 모든 것은 이 payload를 바탕으로 동작합니다. Next.js는 이를 HTML로 render하거나, server 또는 remote store에 보관하거나, 브라우저로 보내며, cacheLife는 각 사본이 얼마나 오래 fresh하게 유지되는지 정합니다:

A cached function's output is serialized into an RSC payload, at build time or at runtime. This payload is what everything else works from. Next.js renders it into HTML, keeps it in a server or remote store, or sends it to the browser, and cacheLife sets how long each copy stays fresh:

  • Prerendered HTML. payload는 HTML로 render되어, self-hosting 시에는 디스크에, 그렇지 않으면 CDN 뒤에 있는 플랫폼의 durable storage에 저장됩니다. 이 HTML은 build 시점에는 static shell이고, ISR upgrade 이후에는 구체적인 page이며, 언제 다시 build될지는 revalidate와 expire가 제어합니다.
  • Shared store. 기본적으로 결과는 instance별 in-memory store에 남으며, serverless 환경에서는 일시적(ephemeral)입니다. use cache: remote는 이를 instance 간에 공유되는 durable한 cache handler로 옮깁니다. 이는 network roundtrip이 추가되므로 high hit rate(높은 적중률)일 때만 이득이 됩니다.
  • Browser. payload는 client navigation이나 prefetch를 위해 전송되는 RSC에 포함되며, 브라우저는 이를 stale 기간 동안 fresh하게 유지합니다. use cache: private 결과는 오직 여기에만 존재합니다.
  • Prerendered HTML. The payload is rendered to HTML and stored on disk when self-hosting, or in your platform's durable storage behind a CDN. That HTML is the static shell at build time and the concrete page after an ISR upgrade, with revalidate and expire controlling when it's rebuilt.
  • Shared store. By default the result stays in a per-instance, in-memory store that is ephemeral on serverless. use cache: remote moves it to a durable cache handler shared across instances, a network roundtrip that pays off only at a high hit rate.
  • Browser. The payload is included in the RSC sent for a client navigation or prefetch, where the browser keeps it fresh for its stale window. use cache: private results live only here.
Good to know

cookies()나 headers()를 읽는 App Shell은 session별로 달라지므로, 공유 server cache가 아니라 client에서 session별로 cache됩니다.

An App Shell that reads cookies() or headers() is session-specific, cached per session on the client rather than in the shared server cache.

이 모든 store는 단일 deployment 범위로 한정됩니다. 새로 deploy하면 처음부터 다시 시작하고, 새 prerender가 build되며, use cache entry는 durable한 remote entry조차 이어지지 않습니다. cache key에 build id가 포함되기 때문입니다. 환경별 동작은 Runtime caching considerations를, server cache 설정은 Self-hosting을 참고하세요.

All of these stores are scoped to a single deployment. A new deploy starts fresh, new prerenders are built, and use cache entries don't carry over, even durable remote ones, because the cache key includes the build id. See Runtime caching considerations for per-environment behavior and Self-hosting for configuring the server cache.

Incremental Static Regeneration

dynamic param segment가 있는 route에서 generateStaticParams는 나열한 URL을 build 시점에 prerender합니다. 그 밖의 URL에는 App Shell이 즉시 제공되고, 이후 background에서 이제 알게 된 param으로 upgrade되어 다음 방문자를 위해 cache됩니다.

In a route with dynamic param segments, generateStaticParams prerenders the URLs you list at build time. Any other URL is served the App Shell instantly, then upgraded in the background with its now-known params and cached for the next visitor.

Bots and crawlersBot과 crawler

Partial Prerendering을 사용하면 page의 나머지 부분은 static shell로 prerender하면서 metadata는 dynamic하게 둘 수 있습니다. shell이 즉시 제공되고 metadata는 그 뒤에 stream되어 들어옵니다. 일부 bot과 crawler는 이를 처리하지 못하며, document의 <head> tag 안에 metadata가 포함되어 있어야 합니다. Next.js는 user agent로 이들을 감지해 static shell을 건너뛰고 request 시점에 page를 dynamic하게 render합니다.

With Partial Prerendering, metadata can be dynamic while the rest of the page is prerendered into a static shell. The shell is served immediately and the metadata streams in after. Some bots and crawlers cannot handle this, and need to see the metadata included in the <head> tag of the document. Next.js detects them by their user agent, skips the static shell, and renders the page dynamically at request time.

build 시점 prerender 중에 사용할 수 있었던 data source는 request 시점에도 사용할 수 있어야 합니다. 그렇지 않으면 render가 throw할 수 있고, 이런 bot은 500 error를 받게 됩니다. 어떤 user agent가 해당되는지와 목록을 바꾸는 방법은 Streaming 가이드의 Bots and crawlers를 참고하세요.

Data sources available during the build-time prerender have to be available at request time too. Otherwise the render may throw, and these bots receive a 500 error. See Bots and crawlers in the Streaming guide for which user agents this covers and how to change the list.
