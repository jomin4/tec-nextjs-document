Linking and NavigatingLink와 Navigation

Next.js에서 route는 기본적으로 server에서 render됩니다. 이 때문에 새 route를 보여 주려면 client가 server response를 기다려야 하는 경우가 많습니다. Next.js에는 prefetching, streaming, client-side transition이 내장되어 있어 navigation이 빠르고 반응성 있게 유지됩니다.

In Next.js, routes are rendered on the server by default. This often means the client has to wait for a server response before a new route can be shown. Next.js comes with built-in prefetching, streaming, and client-side transitions ensuring navigation stays fast and responsive.

이 가이드에서는 Next.js에서 navigation이 어떻게 동작하는지, 그리고 dynamic route와 느린 network 환경에서 navigation을 어떻게 최적화할 수 있는지 설명합니다.

This guide explains how navigation works in Next.js and how you can optimize it for dynamic routes and slow networks.

How navigation worksnavigation 동작 방식

Next.js에서 navigation이 어떻게 동작하는지 이해하려면 다음 개념에 익숙해지는 것이 도움이 됩니다:

To understand how navigation works in Next.js, it helps to be familiar with the following concepts:

  • Streaming

Server Rendering

Next.js에서 Layout과 Page는 기본적으로 React Server Component입니다. 최초 navigation과 이후 navigation에서 Server Component Payload는 client로 전송되기 전에 server에서 생성됩니다.

In Next.js, Layouts and Pages are React Server Components by default. On initial and subsequent navigations, the Server Component Payload is generated on the server before being sent to the client.

server rendering은 언제 일어나느냐에 따라 두 가지 유형으로 나뉩니다:

There are two types of server rendering, based on when it happens:

  • Prerendering은 build 시점 또는 revalidation 중에 일어나며, 그 결과는 cache됩니다.
  • Dynamic Rendering은 client request에 응답해 request 시점에 일어납니다.
  • Prerendering happens at build time or during revalidation and the result is cached.
  • Dynamic Rendering happens at request time in response to a client request.

server rendering의 trade-off는 새 route를 보여 주기 전에 client가 server의 응답을 기다려야 한다는 점입니다. Next.js는 사용자가 방문할 가능성이 높은 route를 prefetching하고 client-side transition을 수행해서 이 지연을 해결합니다.

The trade-off of server rendering is that the client must wait for the server to respond before the new route can be shown. Next.js addresses this delay by prefetching routes the user is likely to visit and performing client-side transitions.

Good to know

최초 방문 시에는 HTML도 생성됩니다.

HTML is also generated for the initial visit.

Prefetching

Prefetching은 사용자가 route로 이동하기 전에 background에서 그 route를 미리 load하는 과정입니다. 사용자가 link를 클릭할 때쯤이면 다음 route를 render할 데이터가 이미 client 쪽에 준비되어 있기 때문에, 애플리케이션의 route 간 navigation이 즉각적으로 느껴집니다.

Prefetching is the process of loading a route in the background before the user navigates to it. This makes navigation between routes in your application feel instant, because by the time a user clicks on a link, the data to render the next route is already available client side.

Next.js는 <Link> component로 연결된 route가 사용자의 viewport에 들어오면 자동으로 prefetch합니다.

Next.js automatically prefetches routes linked with the <Link> component when they enter the user's viewport.

TSJSapp/layout.tsx
import Link from 'next/link'

export default function Layout({ children }: { children: React.ReactNode }) {
  return (
    <html>
      <body>
        <nav>
          {/* Prefetched when the link is hovered or enters the viewport */}
          <Link href="/blog">Blog</Link>
          {/* No prefetching */}
          <a href="/contact">Contact</a>
        </nav>
        {children}
      </body>
    </html>
  )
}
import Link from 'next/link'

export default function Layout({ children }) {
  return (
    <html>
      <body>
        <nav>
          {/* Prefetched when the link is hovered or enters the viewport */}
          <Link href="/blog">Blog</Link>
          {/* No prefetching */}
          <a href="/contact">Contact</a>
        </nav>
        {children}
      </body>
    </html>
  )
}

route를 얼마나 prefetch하는지는 그 route가 static인지 dynamic인지에 따라 달라집니다:

How much of the route is prefetched depends on whether it's static or dynamic:

  • Static Route: route 전체가 prefetch됩니다.
  • Dynamic Route: prefetching을 건너뛰거나, loading.tsx가 있으면 route가 부분적으로 prefetch됩니다.
  • Static Route: the full route is prefetched.
  • Dynamic Route: prefetching is skipped, or the route is partially prefetched if loading.tsx is present.

dynamic route의 prefetching을 건너뛰거나 부분적으로만 수행함으로써, Next.js는 사용자가 결코 방문하지 않을 수도 있는 route에 대해 server에서 불필요한 작업을 하지 않습니다. 하지만 navigation 전에 server response를 기다리면 사용자는 앱이 응답하지 않는다는 인상을 받을 수 있습니다.

By skipping or partially prefetching dynamic routes, Next.js avoids unnecessary work on the server for routes the users may never visit. However, waiting for a server response before navigation can give the users the impression that the app is not responding.

Good to know

link별로 prefetching을 제어하는 방법과 Partial Prefetching을 도입했을 때 동작이 어떻게 바뀌는지 등 전체 동작은 Prefetching 가이드를 참고하세요. link의 prefetch에 URL에 의존하는 콘텐츠를 포함하려면 Optimizing prefetching을 참고하세요.

See the Prefetching guide for the full behavior, including how to control prefetching per link and how it changes when you adopt Partial Prefetching. To include URL-dependent content in a link's prefetch, see Optimizing prefetching.

dynamic route로의 navigation 경험을 개선하려면 streaming을 사용할 수 있습니다.

To improve the navigation experience to dynamic routes, you can use streaming.

Streaming

Streaming을 사용하면 server가 route 전체가 render될 때까지 기다리지 않고, dynamic route의 각 부분이 준비되는 즉시 client로 보낼 수 있습니다. 즉, page의 일부가 아직 load 중이더라도 사용자는 무언가를 더 빨리 볼 수 있습니다. Next.js에서 streaming이 어떻게 동작하는지 자세히 알아보려면 Streaming 가이드를 참고하세요.

Streaming allows the server to send parts of a dynamic route to the client as soon as they're ready, rather than waiting for the entire route to be rendered. This means users see something sooner, even if parts of the page are still loading. See the Streaming guide for a deep dive into how streaming works in Next.js.

dynamic route의 경우, 이는 route를 부분적으로 prefetch할 수 있다는 뜻입니다. 즉, 공유 layout과 loading skeleton을 미리 request할 수 있습니다.

For dynamic routes, it means they can be partially prefetched. That is, shared layouts and loading skeletons can be requested ahead of time.

streaming을 사용하려면 route 폴더에 loading.tsx를 만드세요:

내부적으로 Next.js는 page.tsx의 내용을 <Suspense> boundary로 자동으로 감쌉니다. route가 load되는 동안에는 prefetch된 fallback UI가 표시되고, 준비가 끝나면 실제 콘텐츠로 교체됩니다.

Behind the scenes, Next.js will automatically wrap the page.tsx contents in a <Suspense> boundary. The prefetched fallback UI will be shown while the route is loading, and swapped for the actual content once ready.

You can also use <Suspense> to create loading UI for nested components.

loading.tsx의 장점:

Benefits of loading.tsx:

  • 사용자에게 즉각적인 navigation과 시각적 feedback을 제공합니다.
  • 공유 layout은 interactive한 상태로 유지되며, navigation을 중간에 취소할 수 있습니다(interruptible).
  • Core Web Vitals 개선: TTFB, FCP, TTI.
  • Immediate navigation and visual feedback for the user.
  • Shared layouts remain interactive and navigation is interruptible.
  • Improved Core Web Vitals: TTFB, FCP, and TTI.

navigation 경험을 더 개선하기 위해 Next.js는 <Link> component로 client-side transition을 수행합니다.

To further improve the navigation experience, Next.js performs a client-side transition with the <Link> component.

Client-side transitionsClient-side transition

전통적으로 server에서 render되는 page로 navigation하면 page 전체가 load됩니다. 이로 인해 state가 지워지고, scroll 위치가 초기화되며, interactivity가 막힙니다.

Traditionally, navigation to a server-rendered page triggers a full page load. This clears state, resets scroll position, and blocks interactivity.

Next.js는 <Link> component를 사용한 client-side transition으로 이를 피합니다. page를 다시 load하는 대신 다음과 같이 콘텐츠를 dynamic하게 업데이트합니다:

Next.js avoids this with client-side transitions using the <Link> component. Instead of reloading the page, it updates the content dynamically by:

  • 공유 layout과 UI는 그대로 유지합니다.
  • 현재 page를 prefetch된 loading state로, 또는 준비되어 있다면 새 page로 교체합니다.
  • Keeping any shared layouts and UI.
  • Replacing the current page with the prefetched loading state or a new page if available.

Client-side transition 덕분에 server에서 render되는 앱도 client에서 render되는 앱처럼 느껴집니다. 그리고 prefetching, streaming과 함께 사용하면 dynamic route에서도 빠른 transition이 가능합니다.

Client-side transitions make server-rendered apps feel like client-rendered apps. And when paired with prefetching and streaming, they enable fast transitions, even for dynamic routes.

Next.js는 client-side transition 중에 page 맨 위로 scroll하는 것도 처리합니다. navigation 후 콘텐츠가 sticky 또는 fixed header 뒤로 가려진다면 CSS scroll-padding-top으로 해결할 수 있습니다.

Next.js also handles scrolling to the top of the page during client-side transitions. If content scrolls behind a sticky or fixed header after navigation, you can fix this with CSS scroll-padding-top.

What can make transitions slow?transition이 느려지는 원인

이러한 Next.js 최적화 덕분에 navigation은 빠르고 반응성이 좋습니다. 하지만 특정 조건에서는 transition이 여전히 느리게 느껴질 수 있습니다. 흔한 원인과 사용자 경험을 개선하는 방법은 다음과 같습니다:

These Next.js optimizations make navigation fast and responsive. However, under certain conditions, transitions can still feel slow. Here are some common causes and how to improve the user experience:

dynamic route로 navigation할 때 client는 결과를 보여 주기 전에 server response를 기다려야 합니다. 이 때문에 사용자는 앱이 응답하지 않는다는 인상을 받을 수 있습니다.

When navigating to a dynamic route, the client must wait for the server response before showing the result. This can give the users the impression that the app is not responding.

Slow networks느린 network

느리거나 불안정한 network에서는 사용자가 link를 클릭하기 전에 prefetching이 끝나지 않을 수 있습니다. 이는 static route와 dynamic route 모두에 영향을 줄 수 있습니다. 이런 경우 loading.js fallback이 아직 prefetch되지 않았기 때문에 즉시 나타나지 않을 수 있습니다.

On slow or unstable networks, prefetching may not finish before the user clicks a link. This can affect both static and dynamic routes. In these cases, the loading.js fallback may not appear immediately because it hasn't been prefetched yet.

체감 성능을 개선하려면 useLinkStatus hook을 사용해 transition이 진행되는 동안 즉각적인 feedback을 보여 줄 수 있습니다.

To improve perceived performance, you can use the useLinkStatus hook to show immediate feedback while the transition is in progress.

TSJSapp/ui/loading-indicator.tsx
'use client'

import { useLinkStatus } from 'next/link'

export default function LoadingIndicator() {
  const { pending } = useLinkStatus()
  return (
    <span aria-hidden className={`link-hint ${pending ? 'is-pending' : ''}`} />
  )
}

Disabling prefetchingprefetching 비활성화

<Link> component의 prefetch prop을 false로 설정하면 prefetching을 사용하지 않을 수 있습니다. 이는 link가 많은 큰 목록(예: infinite scroll table)을 render할 때 불필요한 resource 사용을 피하는 데 유용합니다.

You can opt out of prefetching by setting the prefetch prop to false on the <Link> component. This is useful to avoid unnecessary usage of resources when rendering large lists of links (e.g. an infinite scroll table).

<Link prefetch={false} href="/blog">
  Blog
</Link>

하지만 prefetching을 비활성화하면 trade-off가 따릅니다:

However, disabling prefetching comes with trade-offs:

  • Static route는 사용자가 link를 클릭할 때만 fetch됩니다.
  • Dynamic route는 client가 navigation하기 전에 먼저 server에서 render되어야 합니다.
  • Static routes will only be fetched when the user clicks the link.
  • Dynamic routes will need to be rendered on the server first before the client can navigate to it.

prefetch를 완전히 끄지 않으면서 resource 사용을 줄이려면 hover 시에만 prefetch할 수 있습니다. 이렇게 하면 viewport 안의 모든 link가 아니라 사용자가 방문할 가능성이 높은 route로 prefetching이 제한됩니다.

To reduce resource usage without fully disabling prefetch, you can prefetch only on hover. This limits prefetching to routes the user is more likely to visit, rather than all links in the viewport.

TSJSapp/ui/hover-prefetch-link.tsx
'use client'

import Link from 'next/link'
import { useState } from 'react'

function HoverPrefetchLink({
  href,
  children,
}: {
  href: string
  children: React.ReactNode
}) {
  const [active, setActive] = useState(false)

  return (
    <Link
      href={href}
      prefetch={active ? null : false}
      onMouseEnter={() => setActive(true)}
    >
      {children}
    </Link>
  )
}

Hydration not completedHydration이 완료되지 않은 경우

<Link>는 Client Component이므로 route를 prefetch하려면 먼저 hydrate되어야 합니다. 최초 방문 시 JavaScript bundle이 크면 hydration이 지연되어 prefetching이 바로 시작되지 못할 수 있습니다.

<Link> is a Client Component and must be hydrated before it can prefetch routes. On the initial visit, large JavaScript bundles can delay hydration, preventing prefetching from starting right away.

React는 Selective Hydration으로 이를 완화하며, 다음 방법으로 더 개선할 수 있습니다:

React mitigates this with Selective Hydration and you can further improve this by:

  • @next/bundle-analyzer plugin으로 큰 dependency를 찾아 제거해 bundle 크기를 줄입니다.
  • 가능한 경우 logic을 client에서 server로 옮깁니다. 가이드는 Server and Client Components 문서를 참고하세요.
  • Using the @next/bundle-analyzer plugin to identify and reduce bundle size by removing large dependencies.
  • Moving logic from the client to the server where possible. See the Server and Client Components docs for guidance.

Native History API

Next.js에서는 native window.history.pushState와 window.history.replaceState method를 사용해 page를 다시 load하지 않고 브라우저의 history stack을 업데이트할 수 있습니다.

Next.js allows you to use the native window.history.pushState and window.history.replaceState methods to update the browser's history stack without reloading the page.

pushState와 replaceState 호출은 Next.js Router와 통합되어 있어 usePathname, useSearchParams와 동기화할 수 있습니다.

pushState and replaceState calls integrate into the Next.js Router, allowing you to sync with usePathname and useSearchParams.

window.history.pushState

브라우저의 history stack에 새 항목을 추가할 때 사용합니다. 사용자는 이전 state로 뒤로 이동할 수 있습니다. 예를 들어 상품 목록을 정렬하는 경우입니다:

Use it to add a new entry to the browser's history stack. The user can navigate back to the previous state. For example, to sort a list of products:

TSJS
'use client'

import { useSearchParams } from 'next/navigation'

export default function SortProducts() {
  const searchParams = useSearchParams()

  function updateSorting(sortOrder: string) {
    const params = new URLSearchParams(searchParams.toString())
    params.set('sort', sortOrder)
    window.history.pushState(null, '', `?${params.toString()}`)
  }

  return (
    <>
      <button onClick={() => updateSorting('asc')}>Sort Ascending</button>
      <button onClick={() => updateSorting('desc')}>Sort Descending</button>
    </>
  )
}

window.history.replaceState

브라우저 history stack의 현재 항목을 교체할 때 사용합니다. 사용자는 이전 state로 뒤로 이동할 수 없습니다. 예를 들어 애플리케이션의 locale을 전환하는 경우입니다:

Use it to replace the current entry on the browser's history stack. The user is not able to navigate back to the previous state. For example, to switch the application's locale:

TSJS
'use client'

import { usePathname } from 'next/navigation'

export function LocaleSwitcher() {
  const pathname = usePathname()

  function switchLocale(locale: string) {
    // e.g. '/en/about' or '/fr/contact'
    const newPath = `/${locale}${pathname}`
    window.history.replaceState(null, '', newPath)
  }

  return (
    <>
      <button onClick={() => switchLocale('en')}>English</button>
      <button onClick={() => switchLocale('fr')}>French</button>
    </>
  )
}
'use client'

import { usePathname } from 'next/navigation'

export function LocaleSwitcher() {
  const pathname = usePathname()

  function switchLocale(locale) {
    // e.g. '/en/about' or '/fr/contact'
    const newPath = `/${locale}${pathname}`
    window.history.replaceState(null, '', newPath)
  }

  return (
    <>
      <button onClick={() => switchLocale('en')}>English</button>
      <button onClick={() => switchLocale('fr')}>French</button>
    </>
  )
}
