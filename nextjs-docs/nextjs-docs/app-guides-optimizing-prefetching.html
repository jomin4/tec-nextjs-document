Optimizing prefetchingprefetching 최적화

Prefetching은 사용자가 route로 이동하기 전에 그 route의 JavaScript, CSS, RSC payload를 미리 다운로드해서, router가 round trip을 기다리지 않고 다음 route를 render할 수 있게 해 줍니다. App Router가 기본적으로 무엇을 prefetch하는지는 Prefetching 가이드에서 다룹니다.

Prefetching downloads a route's JavaScript, CSS, and RSC payload before the user navigates to it, so the router can render the next route without waiting for a round trip. The Prefetching guide covers what the App Router prefetches by default.

Cache Components와 Partial Prefetching을 사용하면, Next.js는 client navigation 전과 도중에 server-rendered output을 단계적으로 load합니다. 다음은 route의 navigation stage입니다:

With Cache Components and Partial Prefetching, Next.js loads server-rendered output in stages, before and during a client navigation. These are the route's navigation stages:

  1. 기본 <Link>는 route의 App Shell을 load합니다. App Shell에는 route의 static output과, cookies()나 headers()를 읽는 route라면 그 session별 UI가 들어 있습니다. 같은 route로 가는 link들은 이를 공유합니다.
  2. <Link prefetch={true}> 또는 router.prefetch(href, { kind: 'full' })는 공유 shell에 포함될 수 없는, link의 URL data(searchParams, params 등)에 의존하는 static 또는 cached 콘텐츠도 함께 load합니다.
  3. 사용자가 link를 따라가면, navigation이 route의 나머지 부분을 render합니다.
  1. A default <Link> loads the route's App Shell. It holds the route's static output and, for routes that read cookies() or headers(), its session-specific UI. Links to the same route share it.
  2. A <Link prefetch={true}>, or router.prefetch(href, { kind: 'full' }), also loads static or cached content that depends on the link's URL data, such as searchParams and params, which the shared shell cannot include.
  3. When the user follows the link, the navigation renders the rest of the route.

prefetch()와 navigation()을 사용해 비용이 큰 작업을 이후 단계로 옮기세요. route 전체에서 특정 단계가 static으로 유지되도록 강제하려면 Keeping pages static을 참고하세요.

Use prefetch() and navigation() to move expensive work to a later stage. To require that a stage stays static across a route, see Keeping pages static.

route가 아직 instant navigation에 맞게 구성되어 있지 않다면, Instant navigation 가이드부터 시작해 caching 구조를 검증하세요.

If the route is not yet structured for instant navigation, start with the Instant navigation guide to validate its caching structure.

Resolve URL data at prefetch timeprefetch 시점에 URL data resolve하기

<Link prefetch={true}>를 설정하면 navigation 전에 해당 link의 URL data를 resolve합니다. 목적지는 Partial Prefetching을 사용해야 하며, 이는 partialPrefetching으로 전역에서 활성화하거나 prefetch = 'partial'로 segment별로 활성화할 수 있습니다.

Set <Link prefetch={true}> to resolve URL data for that link before navigation. The destination must use Partial Prefetching, enabled globally with partialPrefetching or per segment with prefetch = 'partial'.

custom link에서는 router.prefetch(href, { kind: 'full' })를 호출해 같은 link별 단계를 요청하세요. kind option 없이 router.prefetch(href)를 호출하면 App Shell만 요청합니다.

For a custom link, call router.prefetch(href, { kind: 'full' }) to request the same per-link stage. Calling router.prefetch(href) without the kind option requests only the App Shell.

/에 있는 사용자는 /search?q=react와 /search?q=next로 가는 link를 보게 되며, 각 link는 prefetch={true}로 opt-in합니다:

A user on / sees links to /search?q=react and /search?q=next, each opting in with prefetch={true}:

TSapp/page.tsx
import Link from 'next/link'

export default function Home() {
  return (
    <nav>
      <Link href="/search?q=react" prefetch={true}>
        React
      </Link>
      <Link href="/search?q=next" prefetch={true}>
        Next.js
      </Link>
    </nav>
  )
}

'auto'는 prefetch를 생략하거나 undefined를 전달하는 것과 같습니다. 조건식에서는 기본 App Shell prefetch를 유지해야 하는 link에 'auto'를 반환하세요:

'auto' is equivalent to omitting prefetch or passing undefined. In a conditional expression, return 'auto' for links that should keep the default App Shell prefetch:

TSapp/page.tsx
<Link href={href} prefetch={isFeatured ? true : 'auto'} />

prefetch={false}는 link의 prefetching을 비활성화하려는 경우에만 사용하세요.

Use prefetch={false} only when you want to disable prefetching for a link.

/search page는 static heading과, query에 기반한 <Results> 목록을 render합니다. search() 함수는 query별로 결과를 cache해서 이후 request가 재사용할 수 있게 합니다.

The /search page renders a static heading and a <Results> list based on the query. The search() function caches results by query so later requests can reuse them.

TSapp/search/page.tsx
import { Suspense } from 'react'

export default function SearchPage({ searchParams }: PageProps<'/search'>) {
  return (
    <>
      <h1>Search</h1>
      <Suspense fallback={<ResultsSkeleton />}>
        <Results searchParams={searchParams} />
      </Suspense>
    </>
  )
}

async function Results({
  searchParams,
}: {
  searchParams: PageProps<'/search'>['searchParams']
}) {
  const { q } = await searchParams
  return <ResultList items={await search(q)} />
}

async function search(q: string) {
  'use cache'
  return db.search(q)
}

prefetch={true}가 없으면, App Shell은 <h1>을 render하고 <Results> fallback을 보여 줍니다. query는 클릭 후에 resolve되고 결과가 stream되어 들어옵니다.

Without prefetch={true}, the App Shell renders <h1> and shows the <Results> fallback. The query resolves after the click and streams the results in.

link에 prefetch={true}가 있으면, router는 클릭 전에 <Results>를 resolve하는 link별 prefetch를 요청합니다. q 값은 prefetch 시점에 이미 알 수 있는 link의 URL에서 오고, cache된 search(q) 호출이 결과를 제공합니다. 사용자가 클릭하면 fallback을 보여 주지 않고 결과가 즉시 render됩니다.

With prefetch={true} on the link, the router requests a per-link prefetch that resolves <Results> before the click. The q value comes from the link's URL, which is known at prefetch time, and the cached search(q) call provides the result. When the user clicks, the results render immediately without showing the fallback.

Next.js는 uncached read에 도달할 때까지 static 및 cached 콘텐츠를 prefetch에 포함합니다. 그 이후에는 감싸고 있는 <Suspense> boundary의 fallback을 포함합니다. 이 boundary는 instant navigation에 맞게 route를 구성하는 과정에서 이미 마련되어 있습니다.

Next.js includes static and cached content in the prefetch until it reaches an uncached read. It then includes the fallback from the surrounding <Suspense> boundary. That boundary is already in place from structuring the route for instant navigation.

link별 prefetch를 생성하려면 prefetch 가능한 link마다 server invocation이 한 번씩 발생하므로, link별 opt-in 방식입니다. 모든 콘텐츠가 statically renderable한 page에서는 Next.js가 대신 static cache에서 prefetch를 제공합니다. non-static data에 접근하는 page는, 그 접근이 navigation으로 미뤄지지(deferred) 않는 한 prefetch마다 생성됩니다.

Generating the per-link prefetch costs a server invocation per prefetchable link, so it is opt-in per link. On pages where all the content is statically renderable, Next.js serves the prefetch from the static cache instead. A page that accesses non-static data is generated per prefetch, unless that access is deferred to the navigation.

Good to know

cold cache(첫 방문 또는 만료 이후) 상태에서는 server가 여전히 cache할 결과를 계산해야 합니다. 사용자는 그 첫 navigation에서 loading spinner를 볼 수 있습니다. cache가 warm 상태인 동안에는 이후 navigation이 즉시 이루어집니다.

A cold cache (first visit, or after expiration) means the server still has to compute the cached result. Users may see a loading spinner on that first navigation. Subsequent navigations are instant as long as the cache is warm.

searchParams와 마찬가지로, params도 값이 generateStaticParams로 미리 정의되어 있더라도 <Suspense> boundary가 필요합니다. statically known param이라도 여전히 하나의 URL에 속하기 때문입니다. prefetch={true}를 사용한 link별 prefetch는 generateStaticParams가 다루지 않는 값을 resolve합니다.

Like searchParams, params needs a <Suspense> boundary, even when the values are predefined by generateStaticParams. A statically known param still belongs to one URL. A per-link prefetch with prefetch={true} resolves the values generateStaticParams does not cover.

Include session data in the shellshell에 session data 포함하기

prefetch={true}는 URL data를 resolve합니다. session data는 별도로 처리됩니다. "use cache: private"를 통한 경우를 포함해 cookies()나 headers()를 읽는 route는 session data가 포함된 App Shell을 받으며, 이 shell은 client에서 session별로 cache되어 link별 prefetch 없이도 navigation 시 준비되어 있습니다.

prefetch={true} resolves URL data. Session data is handled separately. A route that reads cookies() or headers(), including through "use cache: private", gets an App Shell that includes its session data, cached per session on the client and ready on navigation without a per-link prefetch.

session data에 기반한 lookup에는, search(q)가 URL에 대해 그랬던 것처럼 cache lifetime이 필요합니다. cookie를 읽은 다음 그 값에 기반해 콘텐츠를 lookup하는 dashboard nav를 예로 들어 보겠습니다:

A lookup based on session data needs a cache lifetime, the same way search(q) did for the URL. Take a dashboard nav that reads a cookie, then looks up content based on it:

TSapp/dashboard/layout.tsx
import { Suspense } from 'react'

export default function DashboardLayout({
  children,
}: LayoutProps<'/dashboard'>) {
  return (
    <div>
      <Suspense fallback={<nav>Loading...</nav>}>
        <UserNav />
      </Suspense>
      <main>{children}</main>
    </div>
  )
}

App Shell render는 session data를 읽을 수 있습니다. 하지만 "use cache"는 cache된 함수 안에서 cookies()를 호출할 수 없으므로, 다음 패턴 중 하나를 사용하세요:

The App Shell render can read session data. However, "use cache" cannot call cookies() inside the cached function, so use one of these patterns:

  • lookup 결과가 여러 session에 걸쳐 공유될 때는 Extract and pass.
  • 하나의 session에 묶여 있을 때는 "use cache: private".
  • Extract and pass when the lookup result is shared across many sessions.
  • "use cache: private" when it is tied to one.

Extract and pass추출해서 전달하기

cache된 함수 바깥에서 cookie를 읽고, 그 값을 argument로 전달하세요. cookies() 호출은 cache scope 바깥에 머무르고, argument가 boundary를 넘어가며, cache된 함수는 deterministic한 signature를 갖게 됩니다. cache entry는 그 argument를 key로 하며, 같은 값을 공유하는 session들은 같은 entry를 공유합니다.

Read the cookie outside the cached function and pass the value in as an argument. The cookies() call stays outside the cache scope, the argument crosses the boundary, and the cached function has a deterministic signature. The cache entry is keyed on that argument, and sessions that share the value share the entry.

TSapp/dashboard/user-nav.tsx
import { cookies } from 'next/headers'

async function UserNav() {
  const team = (await cookies()).get('team')?.value
  const topics = await getTopics(team)
  return (
    <nav>
      {topics.map((topic) => (
        <a key={topic.id} href={topic.href}>
          {topic.label}
        </a>
      ))}
    </nav>
  )
}

async function getTopics(team: string | undefined) {
  'use cache'
  return db.topics.forTeam(team)
}

직접 방문했을 때는 lookup이 resolve될 때까지 <UserNav>가 fallback을 보여 줍니다. navigation 시에는 App Shell이 이미 이를 resolve해 두었는데, team cookie가 shell이 읽을 수 있는 session data이기 때문입니다. 같은 team의 session들이 cache entry를 공유하므로, 기반 data로 가는 traffic은 session 수가 아니라 team 수에 비례해 늘어납니다.

On a direct visit, <UserNav> shows its fallback until the lookup resolves. On navigation, the App Shell has already resolved it, because the team cookie is session data the shell can read. Because sessions on the same team share the cache entry, traffic to the underlying data scales with team count, not session count.

caching directive가 없는 것은 여전히 navigation 후에 stream되어 들어옵니다. shell에는 page 전체가 아니라 navigation 전에 미리 준비할 수 있는 것만 들어 있습니다. shell은 caching 구조가 허용하는 범위까지만 진행됩니다.

Anything without a caching directive still streams in after navigation. A shell holds only what can be prepared ahead of the navigation, not the whole page. It advances only as far as the caching structure allows.

"use cache: private"

lookup이 단일 session에 묶여 있을 때는 "use cache: private"를 사용하세요. 이 directive는 cookie, header 또는 기타 runtime data를 직접 읽는 함수에 cache lifetime을 부여합니다. 결과는 브라우저에만, 해당 session 범위로 cache됩니다.

When the lookup is tied to a single session, use "use cache: private". It assigns a cache lifetime to a function that reads cookies, headers, or other runtime data directly. Results are cached in the browser only, scoped to that session.

TSapp/dashboard/user-nav.tsx
import { cookies } from 'next/headers'

async function UserNav() {
  const user = await getUser()
  return <nav>{user.name}</nav>
}

async function getUser() {
  'use cache: private'
  const session = (await cookies()).get('session')?.value
  return db.users.findBySession(session)
}

여기서 cookies()는 cache된 함수 안에 있는데, 이는 "use cache: private"에서만 동작합니다. 호출 위치에서 runtime data를 추출할 수 없을 때도 같은 패턴을 사용하세요. 예를 들어 인증 helper가 Date.now()를 token의 만료 시간과 비교하거나, session helper가 자체 코드 안에서 cookie를 읽는 경우가 있습니다.

Here cookies() lives inside the cached function, which only works under "use cache: private". Use the same pattern when runtime data cannot be extracted at the call site. For example, an authentication helper may compare Date.now() with a token's expiration, or a session helper may read cookies within its own code.

scope 안의 모든 것은 같은 lifetime을 공유합니다. "use cache: private"는 runtime data에 접근하는 곳에 최대한 가깝게 두세요.

Everything inside the scope shares the same lifetime. Colocate "use cache: private" as close to the runtime data access as possible.

Defer work to a later stage작업을 이후 단계로 미루기

App Shell은 route로 들어가는 link들이 공유합니다. link별 prefetch는 화면에 보이는 <Link prefetch={true}>나 수동 router.prefetch(href, { kind: 'full' }) 호출에 대해 실행되고, navigation은 사용자가 클릭할 때 실행됩니다. 사용자가 끝내 따라가지 않는 link를 위해 비용이 큰 작업을 생성하는 것은 가치가 없을 수 있습니다.

The App Shell is shared by the links into a route. A per-link prefetch runs for a visible <Link prefetch={true}> or a manual router.prefetch(href, { kind: 'full' }) call, and the navigation runs when the user clicks. Expensive work may not be worth generating for links the user never follows.

uncached 작업은 이미 prefetch에서 제외됩니다. cache 가능한 작업에 대해서는 next/cache가 각 호출 아래의 코드를 미루는 함수를 export합니다:

Uncached work is already left out of prefetches. For cacheable work, next/cache exports functions that defer the code below each call:

  • prefetch()는 link별 prefetch 또는 navigation까지 코드를 미룹니다.
  • navigation()은 navigation까지 코드를 미룹니다.
  • prefetch() defers the code until a per-link prefetch or navigation.
  • navigation() defers the code until navigation.

다음 diagram에서 회색 점선 테두리는 Suspense fallback을, 파란색은 render된 이후의 deferred 작업을 나타냅니다:

In the following diagram, a gray dashed outline marks the Suspense fallback, while blue marks the deferred work once it renders:

두 함수 모두 runtime rendering 중에만 적용되므로, 완전히 static한 route는 바뀌지 않습니다. 각 호출은 그것을 await하는 component와 그 component의 하위 요소들을 미룹니다. 이전 단계에서는 가장 가까운 <Suspense> fallback이 render되고, 해당 단계가 실행되면 deferred subtree가 이를 대체합니다. connection()과 달리 두 함수 모두 subtree를 request-dependent하게 만들지 않으므로, 그 안의 함수는 여전히 use cache를 사용할 수 있습니다. How navigation() differs from connection()을 참고하세요.

Both functions apply only during runtime rendering, so they do not change a fully static route. Each call defers the component that awaits it and that component's descendants. Earlier stages render the nearest <Suspense> fallback, which the deferred subtree replaces when its stage runs. Unlike connection(), neither function makes the subtree request-dependent, so functions within it can still use use cache. See How navigation() differs from connection().

Keep expensive session data out of the App Shell비용이 큰 session data를 App Shell에서 제외하기

다시 dashboard를 예로 들어 보겠습니다. session을 key로 하는 ranking은 비용이 크고, dashboard로 들어가는 모든 기본 <Link>가 shell을 위해 이를 생성하게 됩니다. ranking 위에서 prefetch()를 await해서 <Link prefetch={true}>만 클릭 전에 이를 resolve하도록 하세요:

Take the dashboard again. A ranking keyed on the session is expensive, and every default <Link> into the dashboard would generate it for the shell. Await prefetch() above the ranking so that only a <Link prefetch={true}> resolves it before the click:

TSapp/dashboard/recommendations.tsx
import { cookies } from 'next/headers'
import { prefetch } from 'next/cache'

async function Recommendations() {
  const session = (await cookies()).get('session')?.value
  await prefetch()
  const items = await rank(session)
  return <List items={items} />
}

async function rank(session?: string) {
  'use cache: private'
  return db.recommendations.rank({ session })
}

session은 prefetch() 위에서 읽히므로 여전히 shell에서 resolve됩니다. App Shell은 ranking을 생성하지 않습니다. 기본 <Link>는 <Suspense> fallback을 포함하고, navigation 중에 ranking이 이를 대체합니다. <Link prefetch={true}>는 클릭 전에 ranking을 resolve합니다. 두 경우 모두 rank는 자신의 cache lifetime을 유지합니다.

The session is read above prefetch(), so it still resolves in the shell. The App Shell does not generate the ranking. A default <Link> includes the <Suspense> fallback, which the ranking replaces during navigation. A <Link prefetch={true}> resolves the ranking before the click. rank keeps its cache lifetime in both cases.

두 함수 모두 cache된 scope 안에서는 await할 수 없으므로, 여기서 rank처럼 directive는 그 아래에서 호출되는 함수에 둡니다.

Neither function can be awaited inside a cached scope, so the directive goes on a function called below it, as rank does here.

Wait for the navigationnavigation 기다리기

화면에 보이는 각 thread가 <Link prefetch={true}>를 사용하는 inbox를 생각해 보세요. prefetch에는 thread 제목이 포함되어야 하지만, 사용자가 열기도 전에 모든 메시지 본문을 가져오는 것은 낭비입니다.

Consider an inbox where each visible thread uses <Link prefetch={true}>. The prefetch should include the thread subject, but fetching every message body before the user opens it would waste work.

최신 메시지를 별도의 <Suspense> boundary 안에서 render하고, load하기 전에 navigation()을 await하세요:

Render the latest message in its own <Suspense> boundary and await navigation() before loading it:

TSapp/inbox/[threadId]/thread.tsx
import { Suspense } from 'react'
import { navigation } from 'next/cache'
import { getLatestMessage, getThreadSummary } from '@/lib/mail'

export async function Thread({ threadId }: { threadId: string }) {
  const thread = await getThreadSummary(threadId)

  return (
    <article>
      <h1>{thread.subject}</h1>
      <Suspense fallback={<p>Loading message...</p>}>
        <LatestMessage threadId={threadId} />
      </Suspense>
    </article>
  )
}

async function LatestMessage({ threadId }: { threadId: string }) {
  await navigation()
  const message = await getLatestMessage(threadId)
  return <p>{message.body}</p>
}

두 query 모두 cache된 상태로 유지됩니다:

Both queries remain cached:

TSlib/mail.ts
import { db } from '@/lib/db'

export async function getThreadSummary(threadId: string) {
  'use cache'
  return db.thread.findUniqueOrThrow({
    select: { subject: true },
    where: { id: threadId },
  })
}

export async function getLatestMessage(threadId: string) {
  'use cache'
  return db.message.findFirstOrThrow({
    orderBy: { sentAt: 'desc' },
    select: { body: true },
    where: { threadId },
  })
}

link별 prefetch에는 cache된 제목과 메시지 fallback이 포함됩니다. cache된 메시지 본문은 사용자가 thread를 열 때 load되고, 이후 방문에서도 계속 사용할 수 있습니다.

The per-link prefetch includes the cached subject and the message fallback. The cached message body loads when the user opens the thread, then remains available for later visits.

subtree를 uncached로 두어도 prefetch에서는 제외되지만, navigation에서도 cache lifetime을 잃게 됩니다. use cache 콘텐츠의 경우 stale time을 5분 이상으로 두면 client-side router가 첫 navigation 이후 이를 재사용할 수 있습니다. 그보다 짧으면 navigation마다 다시 가져옵니다.

Leaving the subtree uncached would also keep it out of prefetches, but it would lose its cache lifetime on navigation too. For use cache content, a stale time of five minutes or more lets the client-side router reuse it after the first navigation. Below that, each navigation fetches it again.

Keep the prefetch staticprefetch를 static으로 유지하기

cookies(), headers(), params, searchParams의 모든 read가 navigation() 아래에 있으면, runtime prefetch는 build와 같은 output을 만들어 냅니다. 따라서 Next.js는 static output에서 prefetch를 제공할 수 있습니다. CDN이 그 output을 cache할 수 있으므로, route로 들어가는 link에 server compute가 필요하지 않습니다.

When every read of cookies(), headers(), params, and searchParams sits below navigation(), a runtime prefetch would produce the same output as the build. Next.js can therefore serve the prefetch from static output. A CDN can cache that output, so a link into the route requires no server compute.

dashboard는 <UserNav>가 shell에서 team cookie를 읽기 때문에 이런 형태를 취할 수 없습니다. static header가 있는 feed는 가능합니다:

The dashboard cannot take this shape, because <UserNav> reads the team cookie in the shell. A feed with a static header can:

TSapp/feed/page.tsx
import { Suspense } from 'react'
import { cookies } from 'next/headers'
import { navigation } from 'next/cache'

export default function Page() {
  return (
    <>
      <FeedHeader /> {/* static, and so is the whole prefetch */}
      <Suspense fallback={<p>Loading stories...</p>}>
        <Stories />
      </Suspense>
    </>
  )
}

async function Stories() {
  await navigation()
  const topic = (await cookies()).get('topic')?.value ?? 'all'
  return <StoryList items={await getStories(topic)} />
}

navigation() 아래에서 cookie를 읽어도 link별 prefetch가 request마다 render되지는 않습니다. 그 read는 어차피 prefetch 중에 resolve되지 않았을 것이기 때문입니다. prefetch()와 App Shell에도 같은 원리가 적용됩니다. 모든 cookies()와 headers() read가 prefetch() 아래에 있으면, shell은 static output에서 제공됩니다. params나 searchParams를 읽는다고 runtime shell이 필요해지지는 않습니다. URL data는 공유 shell에서 제외되지만, navigation() 아래에 있지 않으면 link별 prefetch를 runtime에 render하게 만들 수 있습니다.

Reading the cookie below navigation() does not make the per-link prefetch render per request, because that read would not have resolved during the prefetch anyway. The same holds for prefetch() and the App Shell. When every cookies() and headers() read sits below prefetch(), the shell is served from static output. Reading params or searchParams does not require a runtime shell. URL data is excluded from the shared shell, but it can make a per-link prefetch render at runtime unless it sits below navigation().

각 호출은 하나의 subtree를 미룹니다. route 전체에 static output을 강제해서 이후 변경으로 request-time rendering이 다시 들어오지 않게 하려면 ensureStatic을 설정하세요. Keeping pages static 가이드에서 각 수준을 단계별로 설명합니다.

Each call defers one subtree. To require static output for the whole route, so a later change cannot reintroduce request-time rendering, set ensureStatic. The Keeping pages static guide walks through each level.

Test prefetched and deferred contentprefetch된 콘텐츠와 deferred 콘텐츠 test하기

Instant navigation 가이드에서 @next/playwright를 설치하고 설정하는 방법을 설명합니다. client navigation에서는 instant()를 사용해 목적지의 prefetch된 UI를 검사하세요.

The Instant navigation guide explains how to install and configure @next/playwright. For a client navigation, use instant() to inspect the destination's prefetched UI.

Partial Prefetching을 도입할 때는, 기능을 활성화하기 전에 이 test를 실행하고 이후에 같은 assertion을 다시 실행하세요. 이렇게 하면 구현이 App Shell이나 link별 prefetch로 옮겨 가는 동안에도 legacy full prefetch에서 선택된 UI가 유지됩니다.

When adopting Partial Prefetching, run this test before enabling the feature and rerun the same assertions afterward. This preserves the UI selected from the legacy full prefetch while its implementation moves to the App Shell or a per-link prefetch.

callback 안에서 link를 클릭하고, 목적지 URL을 기다린 뒤, 어떤 콘텐츠가 사용 가능한지 assert하세요. callback이 navigation을 해제한 후에는 deferred 콘텐츠가 결국 render되는지 assert하세요:

Inside the callback, click the link, wait for the destination URL, and assert which content is available. After the callback releases the navigation, assert that deferred content eventually renders:

TSe2e/product-navigation.test.ts
import { expect, test } from '@playwright/test'
import { instant } from '@next/playwright'

test('prefetches the product summary but not reviews', async ({ page }) => {
  await page.goto('/products')

  await instant(page, async () => {
    await page.click('a[href="/products/baseball-cap"]')
    await page.waitForURL((url) => url.pathname === '/products/baseball-cap')

    await expect(
      page.getByRole('heading', { name: 'Baseball Cap' })
    ).toBeVisible()
    await expect(page.getByTestId('product-summary')).toBeVisible()
    await expect(page.getByTestId('reviews')).toHaveCount(0)
  })

  await expect(page.getByTestId('reviews')).toBeVisible()
})

instant() callback이 실행되는 동안 dynamic 콘텐츠는 일시 정지됩니다. 이 예제에서 상품 요약은 prefetch된 UI의 일부이고, 리뷰는 navigation을 기다립니다. 마지막 assertion은 일시 정지가 해제된 후 리뷰가 render되는지 확인합니다.

While the instant() callback is running, dynamic content is paused. In this example, the product summary is part of the prefetched UI, while reviews wait for navigation. The final assertion confirms that the reviews render after the pause is released.

development에서는 <Suspense> 바깥의 prefetch() 또는 navigation() 호출이 Instant Insight를 표시합니다. 완전히 prerender된 route는 영향을 받지 않지만, 이 insight는 route가 나중에 runtime rendering을 필요로 하게 될 경우 해당 호출이 fallback 없이 콘텐츠를 미루게 된다는 점을 알려 줍니다. generateMetadata()와 generateViewport() 안의 호출에는 별도의 insight가 있습니다.

In development, a prefetch() or navigation() call outside <Suspense> surfaces an Instant Insight. A fully prerendered route is unaffected, but the insight identifies that the call would defer content without a fallback if the route later requires runtime rendering. Calls in generateMetadata() and generateViewport() have separate insights.

Trade-offs트레이드오프

다음과 같은 route에서 prefetch={true}를 사용하세요:

Use prefetch={true} on routes where:

  • component tree의 일부가 URL data, 즉 전체 URL, searchParams, 또는 generateStaticParams로 resolve되지 않는 params에 의존하는 경우
  • tree의 그 부분에 알려진 cache lifetime이 있는 경우("use cache" 또는 "use cache: private"로 표현할 수 있음)
  • traffic이 link별 server invocation을 감수할 만한 경우
  • Part of the component tree depends on URL data: the full URL, searchParams, or params not resolved by generateStaticParams
  • That part of the tree has a known cache lifetime (it can be expressed with "use cache" or "use cache: private")
  • The traffic justifies the per-link server invocation

cache된 data를 prefetch해도 freshness 동작은 바뀌지 않습니다. mutation으로 data가 업데이트될 수 있다면 cache된 결과에 tag를 붙이고 invalidate하세요.

Prefetching cached data does not change its freshness behavior. If a mutation can update the data, tag and invalidate the cached result.

prefetch가 App Shell보다 나은 UI를 만들 수 없다면 사용하지 마세요. 화면에 보이는 각 <Link prefetch={true}>는 server를 깨울 수 있고, 그 비용은 클릭 전에 page의 더 많은 부분이 준비될 때만 의미가 있습니다:

Skip it when the prefetch can't produce a better UI than the App Shell. Each visible <Link prefetch={true}> can wake a server, and that cost only pays off if more of the page is ready before the click:

  • route가 URL data에 거의 또는 전혀 의존하지 않는 경우. App Shell만으로도 이미 navigation이 즉시 이루어집니다.
  • 의존하는 콘텐츠가 request마다 fresh해야 하는 경우. prerender가 같은 <Suspense> fallback에서 멈추므로, 어느 쪽이든 사용자는 같은 UI를 보게 됩니다.
  • route로의 navigation이 드문 경우. click-through와 관계없이 화면에 보이는 link마다 비용을 지불하게 됩니다.
  • The route has little or no URL-data dependency. The App Shell already makes the navigation instant.
  • The dependent content has to be fresh on every request. The prerender stops at the same <Suspense> fallback, so the user sees the same UI either way.
  • The route is rarely navigated to. You pay per visible link, regardless of click-through.

link별 prefetch는 best-effort입니다. 클릭 전에 완료된 navigation에서만 도움이 됩니다. 느린 연결, link가 많은 feed, 또는 직접 방문에서는 사용자가 이동할 때 준비되어 있지 않을 수 있으며, 그러면 navigation은 App Shell로 fallback합니다.

A per-link prefetch is best-effort. It only helps the navigations where it completes before the click. On a slow connection, on a feed of many links, or on a direct visit, it may not be ready when the user navigates, and the navigation falls back to the App Shell.

card grid처럼 한 route로 가는 link가 한꺼번에 많이 보일 때는, 각 <Link prefetch={true}>가 viewport에 들어오면서 해당 link의 콘텐츠를 prefetch하므로 grid가 card마다 server request를 한 번씩 보내게 됩니다. 대신 사용자의 의도(intent)에 따라 prefetch하세요. hover-triggered prefetch는 사용자가 클릭할 가능성이 높은 link만 가져옵니다. 기본 <Link>(prefetch={true} 없음)는 App Shell만 load하므로 이런 비용이 들지 않습니다.

When many links to a route are visible at once, such as a grid of cards, each <Link prefetch={true}> prefetches that link's content as it enters the viewport, so the grid makes one such server request per card. Prefetch on intent instead. A hover-triggered prefetch fetches only the links the user is likely to click. The default <Link> (without prefetch={true}) loads only the App Shell, so it doesn't carry this cost.

작업을 미루면 끝내 사용되지 않을 수도 있는 prefetch를 위해 콘텐츠를 생성하는 일을 피할 수 있습니다. 그 대가로, deferred 콘텐츠가 render되는 동안 navigation에서 가장 가까운 <Suspense> fallback이 보일 수 있습니다.

Deferring work avoids generating content for prefetches that may never be used. The tradeoff is that a navigation may show the nearest <Suspense> fallback while the deferred content renders.
