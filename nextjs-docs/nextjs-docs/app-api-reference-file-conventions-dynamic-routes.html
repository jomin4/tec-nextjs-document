Dynamic Route SegmentsDynamic Route Segment

URL path는 path segment들의 연속입니다. App Router에서 segment는 static(정확히 일치해야 하는 literal 값)일 수도 있고 dynamic(URL에서 값을 capture하는 placeholder)일 수도 있습니다. segment의 값을 미리 알 수 없을 때는 Dynamic Segment를 정의해 dynamic data로부터 route를 만드세요. Next.js는 capture한 값을 path params prop으로 page에 전달하며, 이 값은 request 시점에 채워지거나 build 시점에 prerender됩니다.

A URL path is a sequence of path segments. In the App Router, a segment may be static (a literal value matched exactly) or dynamic (a placeholder that captures a value from the URL). When you don't know a segment's value ahead of time, define a Dynamic Segment to create routes from dynamic data. Next.js passes the captured values to your page via the path params prop, either filled in at request time or prerendered at build time.

Good to know

Dynamic Segment는 흔히 path param, route param, URL param이라고도 부릅니다.

Dynamic Segments are often referred to as path params, route params, or URL params.

Convention규칙

Dynamic Segment는 폴더 이름을 대괄호로 감싸서 만들 수 있습니다: [folderName]. 예를 들어 블로그에는 app/blog/[slug]/page.js 같은 route가 있을 수 있으며, 여기서 [slug]는 블로그 글을 위한 Dynamic Segment입니다.

A Dynamic Segment can be created by wrapping a folder's name in square brackets: [folderName]. For example, a blog could include the following route app/blog/[slug]/page.js where [slug] is the Dynamic Segment for blog posts.

TSJSapp/blog/[slug]/page.tsx
export default async function Page({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params
  return <div>My Post: {slug}</div>
}
export default async function Page({ params }) {
  const { slug } = await params
  return <div>My Post: {slug}</div>
}

Dynamic Segment는 layout, page, route, generateMetadata 함수에 params prop으로 전달됩니다.

Dynamic Segments are passed as the params prop to layout, page, route, and generateMetadata functions.

Route예시 URLparams
app/blog/[slug]/page.js/blog/a{ slug: 'a' }
app/blog/[slug]/page.js/blog/b{ slug: 'b' }
app/blog/[slug]/page.js/blog/c{ slug: 'c' }
RouteExample URLparams
app/blog/[slug]/page.js/blog/a{ slug: 'a' }
app/blog/[slug]/page.js/blog/b{ slug: 'b' }
app/blog/[slug]/page.js/blog/c{ slug: 'c' }

root layout보다 앞에 나오는 dynamic segment는 root parameter이며, next/root-params를 사용해 어떤 Server Component에서든 추가로 읽을 수 있습니다.

Dynamic segments that appear before the root layout are root parameters, which can additionally be read from any Server Component with next/root-params.

In Client ComponentsClient Component에서

Client Component인 page에서는 use API를 사용해 props로 받은 dynamic segment에 접근할 수 있습니다.

In a Client Component page, dynamic segments from props can be accessed using the use API.

TSJSapp/blog/[slug]/page.tsx
'use client'
import { use } from 'react'

export default function BlogPostPage({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = use(params)

  return (
    <div>
      <p>{slug}</p>
    </div>
  )
}
'use client'
import { use } from 'react'

export default function BlogPostPage({ params }) {
  const { slug } = use(params)

  return (
    <div>
      <p>{slug}</p>
    </div>
  )
}

또는 Client Component에서 useParams hook을 사용하면 Client Component tree 어디에서든 params에 접근할 수 있습니다.

Alternatively Client Components can use the useParams hook to access the params anywhere in the Client Component tree.

Catch-all SegmentsCatch-all Segment

대괄호 안에 줄임표를 넣어 [...folderName]으로 만들면 Dynamic Segment를 확장해 이후의 segment를 모두 catch-all 할 수 있습니다.

Dynamic Segments can be extended to catch-all subsequent segments by adding an ellipsis inside the brackets [...folderName].

예를 들어 app/shop/[...slug]/page.js는 /shop/clothes뿐 아니라 /shop/clothes/tops, /shop/clothes/tops/t-shirts 등에도 match됩니다.

For example, app/shop/[...slug]/page.js will match /shop/clothes, but also /shop/clothes/tops, /shop/clothes/tops/t-shirts, and so on.

Route예시 URLparams
app/shop/[...slug]/page.js/shop/a{ slug: ['a'] }
app/shop/[...slug]/page.js/shop/a/b{ slug: ['a', 'b'] }
app/shop/[...slug]/page.js/shop/a/b/c{ slug: ['a', 'b', 'c'] }
RouteExample URLparams
app/shop/[...slug]/page.js/shop/a{ slug: ['a'] }
app/shop/[...slug]/page.js/shop/a/b{ slug: ['a', 'b'] }
app/shop/[...slug]/page.js/shop/a/b/c{ slug: ['a', 'b', 'c'] }

Optional Catch-all SegmentsOptional Catch-all Segment

parameter를 이중 대괄호로 감싸 [[...folderName]]으로 만들면 Catch-all Segment를 optional(선택적)로 만들 수 있습니다.

Catch-all Segments can be made optional by including the parameter in double square brackets: [[...folderName]].

예를 들어 app/shop/[[...slug]]/page.js는 /shop/clothes, /shop/clothes/tops, /shop/clothes/tops/t-shirts에 더해 /shop에도 역시 match됩니다.

For example, app/shop/[[...slug]]/page.js will also match /shop, in addition to /shop/clothes, /shop/clothes/tops, /shop/clothes/tops/t-shirts.

catch-all segment와 optional catch-all segment의 차이는, optional의 경우 parameter가 없는 route(위 예시의 /shop)도 match된다는 점입니다.

The difference between catch-all and optional catch-all segments is that with optional, the route without the parameter is also matched (/shop in the example above).

Route예시 URLparams
app/shop/[[...slug]]/page.js/shop{ slug: undefined }
app/shop/[[...slug]]/page.js/shop/a{ slug: ['a'] }
app/shop/[[...slug]]/page.js/shop/a/b{ slug: ['a', 'b'] }
app/shop/[[...slug]]/page.js/shop/a/b/c{ slug: ['a', 'b', 'c'] }
RouteExample URLparams
app/shop/[[...slug]]/page.js/shop{ slug: undefined }
app/shop/[[...slug]]/page.js/shop/a{ slug: ['a'] }
app/shop/[[...slug]]/page.js/shop/a/b{ slug: ['a', 'b'] }
app/shop/[[...slug]]/page.js/shop/a/b/c{ slug: ['a', 'b', 'c'] }

TypeScript

TypeScript를 사용할 때는 설정한 route segment에 따라 params에 type을 추가할 수 있습니다. page, layout, route에서 각각 PageProps<'/route'>, LayoutProps<'/route'>, RouteContext<'/route'>를 사용해 params의 type을 지정하세요.

When using TypeScript, you can add types for params depending on your configured route segment — use PageProps<'/route'>, LayoutProps<'/route'>, or RouteContext<'/route'> to type params in page, layout, and route respectively.

route params 값은 runtime이 되기 전까지 알 수 없기 때문에 string, string[], 또는 undefined(optional catch-all segment의 경우)로 type이 지정됩니다. 사용자는 주소창에 어떤 URL이든 입력할 수 있으며, 이렇게 넓은 type은 애플리케이션 코드가 가능한 모든 경우를 처리하도록 돕습니다.

Route params values are typed as string, string[], or undefined (for optional catch-all segments), because their values aren't known until runtime. Users can enter any URL into the address bar, and these broad types help ensure that your application code handles all these possible cases.

Routeparams Type 정의
app/blog/[slug]/page.js{ slug: string }
app/shop/[...slug]/page.js{ slug: string[] }
app/shop/[[...slug]]/page.js{ slug?: string[] }
app/[categoryId]/[itemId]/page.js{ categoryId: string, itemId: string }
Routeparams Type Definition
app/blog/[slug]/page.js{ slug: string }
app/shop/[...slug]/page.js{ slug: string[] }
app/shop/[[...slug]]/page.js{ slug?: string[] }
app/[categoryId]/[itemId]/page.js{ categoryId: string, itemId: string }

알려진 언어 코드 집합을 갖는 [locale] param처럼 params가 정해진 개수의 유효한 값만 가질 수 있는 route를 작업하고 있다면, runtime validation을 사용해 사용자가 입력할 수 있는 잘못된 param을 처리하고, 나머지 애플리케이션은 알려진 집합에서 나온 더 좁은 type으로 동작하게 할 수 있습니다.

If you're working on a route where params can only have a fixed number of valid values, such as a [locale] param with a known set of language codes, you can use runtime validation to handle any invalid params a user may enter, and let the rest of your application work with the narrower type from your known set.

TS/app/[locale]/page.tsx
import { notFound } from 'next/navigation'
import type { Locale } from '@i18n/types'
import { isValidLocale } from '@i18n/utils'

function assertValidLocale(value: string): asserts value is Locale {
  if (!isValidLocale(value)) notFound()
}

export default async function Page(props: PageProps<'/[locale]'>) {
  const { locale } = await props.params // locale is typed as string
  assertValidLocale(locale)
  // locale is now typed as Locale
}

Behavior동작

  • params prop은 promise입니다. 값에 접근하려면 async/await 또는 React의 use 함수를 사용해야 합니다.
    • 버전 14 이하에서는 params가 synchronous prop이었습니다. 하위 호환성을 위해 Next.js 15에서도 여전히 synchronous하게 접근할 수 있지만, 이 동작은 앞으로 deprecated될 예정입니다.
  • Since the params prop is a promise. You must use async/await or React's use function to access the values.
    • In version 14 and earlier, params was a synchronous prop. To help with backwards compatibility, you can still access it synchronously in Next.js 15, but this behavior will be deprecated in the future.

With Cache ComponentsCache Components와 함께 사용하기

dynamic route segment와 함께 Cache Components를 사용할 때, params를 처리하는 방법은 generateStaticParams를 사용하는지 여부에 따라 달라집니다.

When using Cache Components with dynamic route segments, how you handle params depends on whether you use generateStaticParams.

generateStaticParams가 없으면 prerendering 중에는 param 값을 알 수 없으므로 params는 runtime data가 됩니다. fallback UI를 제공하려면 param 접근을 <Suspense> boundary로 감싸야 합니다.

Without generateStaticParams, param values are unknown during prerendering, making params runtime data. You must wrap param access in <Suspense> boundaries to provide fallback UI.

generateStaticParams를 사용하면 build 시점에 사용할 수 있는 sample param 값을 제공하게 됩니다. build 과정에서 dynamic content와 다른 runtime API가 올바르게 처리되는지 검증한 뒤, sample에 대한 static HTML 파일을 생성합니다. runtime param으로 render된 page는 첫 request가 성공한 뒤 디스크에 저장됩니다.

With generateStaticParams, you provide sample param values that can be used at build time. The build process validates that dynamic content and other runtime APIs are correctly handled, then generates static HTML files for the samples. Pages rendered with runtime params are saved to disk after a successful first request.

아래 섹션에서 두 가지 pattern을 모두 보여 줍니다.

The sections below demonstrate both patterns.

Without generateStaticParamsgenerateStaticParams 없이

모든 params는 runtime data입니다. param 접근은 Suspense fallback UI로 감싸야 합니다. Next.js는 build 시점에 static shell을 생성하고, content는 request마다 load됩니다.

All params are runtime data. Param access must be wrapped by Suspense fallback UI. Next.js generates a static shell at build time, and content loads on each request.

Good to know
  • page 수준의 fallback UI에는 loading.tsx를 사용할 수도 있습니다.
  • layout에서는 top level에서 params를 await하지 마세요. 그렇게 하면 layout이 prerender되지 못합니다. 대신 params promise를 그것이 필요한 component로 넘겨 그곳에서 await하세요. 예시는 Maximizing the static shell을 참고하세요.
  • You can also use loading.tsx for page-level fallback UI.
  • In layouts, avoid awaiting params at the top level. Doing so prevents the layout from being prerendered. Instead, pass the params promise down to the component that needs it and await there. See Maximizing the static shell for examples.
TSapp/blog/[slug]/page.tsx
import { Suspense } from 'react'

export default function Page({ params }: PageProps<'/blog/[slug]'>) {
  return (
    <div>
      <h1>Blog Post</h1>
      <Suspense fallback={<div>Loading...</div>}>
        {params.then(({ slug }) => (
          <Content slug={slug} />
        ))}
      </Suspense>
    </div>
  )
}

async function Content({ slug }: { slug: string }) {
  const res = await fetch(`https://api.vercel.app/blog/${slug}`)
  const post = await res.json()

  return (
    <article>
      <h2>{post.title}</h2>
      <p>{post.content}</p>
    </article>
  )
}

With generateStaticParamsgenerateStaticParams와 함께

params를 미리 제공해 build 시점에 page를 prerender하세요. 필요에 따라 모든 route를 prerender하거나 일부만 prerender할 수 있습니다.

Provide params ahead of time to prerender pages at build time. You can prerender all routes or a subset depending on your needs.

build 과정에서 route는 각 sample param으로 실행되어 HTML 결과를 수집합니다. dynamic content나 runtime data에 잘못 접근하면 build가 실패합니다.

During the build process, the route is executed with each sample param to collect the HTML result. If dynamic content or runtime data are accessed incorrectly, the build will fail.

TSapp/blog/[slug]/page.tsx
import { Suspense } from 'react'

export async function generateStaticParams() {
  return [{ slug: '1' }, { slug: '2' }, { slug: '3' }]
}

export default async function Page({ params }: PageProps<'/blog/[slug]'>) {
  const { slug } = await params

  return (
    <div>
      <h1>Blog Post</h1>
      <Content slug={slug} />
    </div>
  )
}

async function Content({ slug }: { slug: string }) {
  const post = await getPost(slug)
  return (
    <article>
      <h2>{post.title}</h2>
      <p>{post.content}</p>
    </article>
  )
}

async function getPost(slug: string) {
  'use cache'
  const res = await fetch(`https://api.vercel.app/blog/${slug}`)
  return res.json()
}

build 시점 validation은 sample params로 실행되는 code path만 다룹니다. route에 sample에 없는 특정 param 값에서 runtime API에 접근하는 조건부 로직이 있다면, 그 분기는 build 시점에 검증되지 않습니다:

Build-time validation only covers code paths that execute with the sample params. If your route has conditional logic that accesses runtime APIs for certain param values not in your samples, those branches won't be validated at build time:

TSapp/blog/[slug]/page.tsx
import { cookies } from 'next/headers'

export async function generateStaticParams() {
  return [{ slug: 'public-post' }, { slug: 'hello-world' }]
}

export default async function Page({ params }: PageProps<'/blog/[slug]'>) {
  const { slug } = await params

  if (slug.startsWith('private-')) {
    // This branch is never executed at build time
    // Runtime requests for 'private-*' slugs will error
    return <PrivatePost slug={slug} />
  }

  return <PublicPost slug={slug} />
}

async function PrivatePost({ slug }: { slug: string }) {
  const token = (await cookies()).get('token')
  // ... fetch and render private post using token for auth
}

generateStaticParams가 반환하지 않은 runtime param의 경우, validation은 첫 request 때 이루어집니다. 위 예시에서 private-로 시작하는 slug에 대한 request는 PrivatePost가 Suspense boundary 없이 cookies()에 접근하기 때문에 실패합니다. 조건부 분기에 해당하지 않는 다른 runtime param은 정상적으로 render되며, 이후 request를 위해 디스크에 저장됩니다.

For runtime params not returned by generateStaticParams, validation occurs during the first request. In the example above, requests for slugs starting with private- will fail because PrivatePost accesses cookies() without a Suspense boundary. Other runtime params that don't hit the conditional branch will render successfully and be saved to disk for subsequent requests.

이를 해결하려면 PrivatePost를 Suspense로 감싸세요:

To fix this, wrap PrivatePost with Suspense:

TSapp/blog/[slug]/page.tsx
import { Suspense } from 'react'
import { cookies } from 'next/headers'

export async function generateStaticParams() {
  return [{ slug: 'public-post' }, { slug: 'hello-world' }]
}

export default async function Page({ params }: PageProps<'/blog/[slug]'>) {
  const { slug } = await params

  if (slug.startsWith('private-')) {
    return (
      <Suspense fallback={<div>Loading...</div>}>
        <PrivatePost slug={slug} />
      </Suspense>
    )
  }

  return <PublicPost slug={slug} />
}

async function PrivatePost({ slug }: { slug: string }) {
  const token = (await cookies()).get('token')
  // ... fetch and render private post using token for auth
}

Examples예시

With generateStaticParamsgenerateStaticParams와 함께

generateStaticParams 함수를 사용하면 request 시점에 on-demand로 생성하는 대신 build 시점에 route를 statically generate할 수 있습니다.

The generateStaticParams function can be used to statically generate routes at build time instead of on-demand at request time.

TSJSapp/blog/[slug]/page.tsx
export async function generateStaticParams() {
  const posts = await fetch('https://.../posts').then((res) => res.json())

  return posts.map((post) => ({
    slug: post.slug,
  }))
}
export async function generateStaticParams() {
  const posts = await fetch('https://.../posts').then((res) => res.json())

  return posts.map((post) => ({
    slug: post.slug,
  }))
}

generateStaticParams 함수 안에서 fetch를 사용하면 request가 자동으로 deduplicate됩니다. 이렇게 하면 Layout, Page, 그리고 다른 generateStaticParams 함수에서 같은 data에 대해 여러 번 network call을 하지 않게 되어 build 시간이 빨라집니다.

When using fetch inside the generateStaticParams function, the requests are automatically deduplicated. This avoids multiple network calls for the same data Layouts, Pages, and other generateStaticParams functions, speeding up build time.

Dynamic GET Route Handlers with generateStaticParamsgenerateStaticParams를 사용한 Dynamic GET Route Handler

generateStaticParams는 dynamic Route Handler와도 함께 동작해 build 시점에 API response를 statically generate할 수 있습니다:

generateStaticParams also works with dynamic Route Handlers to statically generate API responses at build time:

TSJSapp/api/posts/[id]/route.ts
export async function generateStaticParams() {
  const posts: { id: number }[] = await fetch(
    'https://api.vercel.app/blog'
  ).then((res) => res.json())

  return posts.map((post) => ({
    id: `${post.id}`,
  }))
}

export async function GET(
  request: Request,
  { params }: RouteContext<'/api/posts/[id]'>
) {
  const { id } = await params
  const res = await fetch(`https://api.vercel.app/blog/${id}`)

  if (!res.ok) {
    return Response.json({ error: 'Post not found' }, { status: 404 })
  }

  const post = await res.json()
  return Response.json(post)
}
export async function generateStaticParams() {
  const posts = await fetch('https://api.vercel.app/blog').then((res) =>
    res.json()
  )

  return posts.map((post) => ({
    id: `${post.id}`,
  }))
}

export async function GET(request, { params }) {
  const { id } = await params
  const res = await fetch(`https://api.vercel.app/blog/${id}`)

  if (!res.ok) {
    return Response.json({ error: 'Post not found' }, { status: 404 })
  }

  const post = await res.json()
  return Response.json(post)
}

이 예시에서는 generateStaticParams가 반환한 모든 블로그 글 ID에 대한 route handler가 build 시점에 statically generate됩니다. 다른 ID에 대한 request는 request 시점에 dynamic하게 처리됩니다.

In this example, route handlers for all blog post IDs returned by generateStaticParams will be statically generated at build time. Requests to other IDs will be handled dynamically at request time.
