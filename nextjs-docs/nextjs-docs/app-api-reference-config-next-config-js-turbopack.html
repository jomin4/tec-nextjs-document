turbopackturbopack

turbopack option을 사용하면 Turbopack을 customize해서 다양한 파일을 transform하고 module이 resolve되는 방식을 바꿀 수 있습니다.

The turbopack option lets you customize Turbopack to transform different files and change how modules are resolved.

Good to know

turbopack option은 Next.js 13.0.0부터 15.2.x 버전까지 experimental.turbo라는 이름이었습니다. 이 option은 여전히 alias로 동작하지만, 새 configuration에서는 top-level turbopack option을 사용해야 합니다.

이전 버전의 Next.js를 사용하고 있다면 npx @next/codemod@latest next-experimental-turbo-to-turbopack .를 실행해 configuration을 자동으로 migrate하세요.

The turbopack option was previously named experimental.turbo in Next.js versions 13.0.0 to 15.2.x, an option which still works as an alias, but new configuration should use the top-level turbopack option.

If you are using an older version of Next.js, run npx @next/codemod@latest next-experimental-turbo-to-turbopack . to automatically migrate your configuration.

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  turbopack: {
    // ...
  },
}

export default nextConfig
/** @type {import('next').NextConfig} */
const nextConfig = {
  turbopack: {
    // ...
  },
}

module.exports = nextConfig
Good to know
  • Next.js용 Turbopack은 built-in 기능에 loader나 loader configuration이 필요하지 않습니다. Turbopack은 CSS와 최신 JavaScript compile을 기본으로 지원하므로, @babel/preset-env를 사용하고 있다면 css-loader, postcss-loader, babel-loader가 필요 없습니다.
  • Turbopack for Next.js does not require loaders or loader configuration for built-in functionality. Turbopack has built-in support for CSS and compiling modern JavaScript, so there's no need for css-loader, postcss-loader, or babel-loader if you're using @babel/preset-env.

Turbopack은 webpack loader를 실행하기 위해 loader-runner library를 사용하며, 이 library는 표준 loader API의 대부분을 제공합니다. 하지만 일부 기능은 지원되지 않습니다:

Turbopack uses the loader-runner library to execute webpack loaders, which provides most of the standard loader API. However, some features are not supported:

Module loading:

Module loading:

  • importModule - 지원 안 함
  • loadModule - 지원 안 함
  • importModule - No support
  • loadModule - No support

File system and output:

File system and output:

  • fs - 부분 지원: 현재 fs.readFile만 구현되어 있습니다.
  • emitFile - 지원 안 함
  • fs - Partial support: only fs.readFile is currently implemented.
  • emitFile - No support

Utilities:

Utilities:

  • utils - 지원 안 함
  • utils - No support

이 기능들 중 하나에 결정적으로 의존하는 loader가 있다면 issue를 등록해 주세요.

If you have a loader that is critically dependent upon one of these features please file an issue.

Examples예시

Root directory

Turbopack은 module을 resolve할 때 root directory를 사용합니다. 프로젝트 root 밖에 있는 파일은 resolve되지 않습니다.

Turbopack uses the root directory to resolve modules. Files outside of the project root are not resolved.

프로젝트 root 밖의 파일을 resolve하지 않는 이유는 cache validation을 개선하고, filesystem watching overhead를 줄이고, 필요한 resolving 단계 수를 줄이기 위해서입니다.

Files are not resolved outside of the project root is to improve cache validation, reduce filesystem watching overhead, and reduce the number of resolving steps needed.

Next.js는 프로젝트의 root directory를 자동으로 감지합니다. 다음 파일 중 하나를 찾는 방식으로 감지합니다:

Next.js automatically detects the root directory of your project. It does so by looking for one of these files:

  • pnpm-lock.yaml
  • package-lock.json
  • yarn.lock
  • bun.lock
  • bun.lockb
  • pnpm-lock.yaml
  • package-lock.json
  • yarn.lock
  • bun.lock
  • bun.lockb

프로젝트 구조가 다르다면, 예를 들어 workspace를 사용하지 않는다면 root option을 직접 설정할 수 있습니다:

If you have a different project structure, for example if you don't use workspaces, you can manually set the root option:

JSnext.config.js
const path = require('path')
module.exports = {
  turbopack: {
    root: path.join(__dirname, '..'),
  },
}

프로젝트 root 밖에 있는 linked dependency(예: npm link)의 파일을 resolve하려면, turbopack.root를 프로젝트와 linked dependency 모두의 상위 directory로 설정하거나 additional root를 설정해야 합니다.

To resolve files from linked dependencies outside the project root (e.g. npm link), you must either configure the turbopack.root to the parent directory of both the project and the linked dependencies or configure an additional root.

monorepo에서 작업할 때 이 option으로 root를 설정하세요. root directory를 너무 넓게(예: home directory까지) 확장하지 마세요. Turbopack은 root 안의 모든 파일을 watch할 수 있으므로, root directory를 너무 넓게 설정하면 심각한 performance 문제가 생길 수 있습니다.

Use this option to configure the root when working in a monorepo. Do not extend the root directory too broadly (e.g. to your home directory). Turbopack may watch all files inside of roots, and configuring too broad of a root directory can cause significant performance problems.

Additional roots (experimental)Additional root (experimental)

experimental.turbopackAdditionalRoots를 사용하면 Turbopack이 target이 turbopack.root 밖에 있는 symbolic link를 따라갈 수 있습니다.

experimental.turbopackAdditionalRoots allows Turbopack to follow symbolic links whose targets are outside turbopack.root.

이는 프로젝트 밖에 있는 linked package(예: npm link나 global virtual store)에 유용합니다.

It is useful for linked packages that live outside the project (e.g. npm link or a global virtual store).

additional root는 symlink 경계에서만 넘어갈 수 있습니다. root를 벗어나는 직접적인 relative import는 지원되지 않습니다.

Additional roots can only be crossed at symlink boundaries. Direct relative imports that escape a root are unsupported.

JSnext.config.js
const path = require('path')

module.exports = {
  experimental: {
    turbopackAdditionalRoots: {
      linkedPackages: { path: path.join(__dirname, '../packages') },
    },
  },
}

각 key는 하나의 root를 식별합니다. path는 절대 경로이거나 Next.js를 실행하는 directory 기준의 상대 경로일 수 있습니다.

Each key identifies one root. path can be absolute or relative to the directory where you run Next.js.

Good to know
  • next dev 또는 next build가 시작되기 전에 symbolic link와 그 target이 모두 build 머신에 존재해야 합니다.
  • deployment 도구와 CI 시스템은 repository를 별도의 build 머신으로 복사할 수 있습니다. 이런 도구는 additional root를 모를 수 있고, 필요한 파일을 복사하지 못할 수 있습니다.
  • Windows에서는 build 시 symbolic link를 만들려면 Developer Mode나 상승된 권한이 필요합니다. output artifact를 만들 때 symbolic link 생성이 필요할 수 있습니다. symlink 생성이 허용되지 않는 경우 Turbopack이 directory junction으로 fallback할 수 있는 경우도 있지만, junction은 절대 경로를 사용하므로 결과 output을 다른 위치로 옮기지 못할 수 있습니다.
  • The symbolic link and its target must both be available on the build machine before next dev or next build starts.
  • Deployment tools and CI systems may copy your repository to a separate build machine. These tools may be unaware of the additional roots, and they may fail to copy required files.
  • On Windows, builds require Developer Mode or elevated permissions to create symbolic links. Creating output artifacts may require creating symbolic links. In some cases, Turbopack can fall back to directory junctions when symlink creation is not permitted, but these junctions use absolute paths, so the resulting output may not be relocatable.

next build나 next dev가 시작될 때 root path를 찾지 못하면 warning이 표시됩니다. 단, ignoreIfMissing이 true로 설정되어 있으면 표시되지 않습니다(기본값은 false).

If a root path is not found when next build or next dev starts, a warning will be issued, unless ignoreIfMissing is set to true (defaults to false).

Windows를 포함한 다양한 platform에서 configuration의 이식성을 보장하려면 root 이름이 다음 요구 사항을 모두 충족해야 합니다:

To ensure portability of your configuration across a variety of platforms, including Windows, a root name must meet all of these requirements:

  • 1~40자로 이루어집니다.
  • 각 문자는 ASCII 문자(a-z 또는 A-Z), 숫자(0-9), underscore(_), hyphen(-) 중 하나여야 합니다.
  • Windows device 이름이 아닙니다.
  • ASCII 대소문자를 구분하지 않고 비교했을 때 앞선 이름과 중복되지 않습니다.
  • It contains 1 to 40 characters.
  • Each character must be an ASCII letter (a-z or A-Z), a digit (0-9), an underscore (_), or a hyphen (-).
  • It is not a Windows device name.
  • It does not duplicate an earlier name under ASCII case-insensitive comparison.

파일 참조가 모호해지지 않도록 additional root는 turbopack.root나 서로 겹칠 수 없습니다. 즉, additional root는 turbopack.root 안에 있거나 그것을 포함할 수 없습니다. 예를 들어 foo/와 foo/bar/를 모두 additional root로 설정하면 warning이 발생하고, 겹치는 additional root는 무시됩니다.

To avoid ambiguous references to files, additional roots may not overlap turbopack.root or one another. This means an additional root cannot be inside turbopack.root or contain it. For example, configuring both foo/ and foo/bar/ as additional roots would produce a warning, and the overlapping additional root will be ignored.

additional root는 Next.js의 trace format을 바꿉니다.

Additional roots change Next.js's trace format.

output: "standalone"을 사용하면 이 additional root에 저장된 bundle되지 않은 파일은 output directory 안의, root에 설정한 이름을 가진 하위 directory로 복사됩니다.

When using output: "standalone", unbundled files stored in these additional roots will be copied to a subdirectory of the output directory containing the configured name of the root.

Configuring webpack loaderswebpack loader 설정하기

built-in 기능을 넘어서는 loader 지원이 필요하다면, 많은 webpack loader가 이미 Turbopack에서 동작합니다. 현재는 몇 가지 제한이 있습니다:

If you need loader support beyond what's built in, many webpack loaders already work with Turbopack. There are currently some limitations:

  • webpack loader API의 핵심 일부만 구현되어 있습니다. 현재 일부 인기 loader를 지원하기에 충분한 수준이며, 앞으로 API 지원을 확대할 예정입니다.
  • JavaScript 코드를 반환하는 loader만 지원됩니다. stylesheet나 이미지 같은 파일을 transform하는 loader는 현재 지원되지 않습니다.
  • webpack loader에 전달하는 option은 일반 JavaScript primitive, 객체, 배열이어야 합니다. 예를 들어 require()로 가져온 plugin module을 option 값으로 전달할 수는 없습니다.
  • Only a core subset of the webpack loader API is implemented. Currently, there is enough coverage for some popular loaders, and we'll expand our API support in the future.
  • Only loaders that return JavaScript code are supported. Loaders that transform files like stylesheets or images are not currently supported.
  • Options passed to webpack loaders must be plain JavaScript primitives, objects, and arrays. For example, it's not possible to pass require() plugin modules as option values.

loader를 설정하려면 next.config.js에 설치한 loader 이름과 option을 추가하고, 파일 확장자를 loader 목록에 mapping하세요. rule은 순서대로 평가됩니다.

To configure loaders, add the names of the loaders you've installed and any options in next.config.js, mapping file extensions to a list of loaders. Rules are evaluated in order.

아래는 @svgr/webpack loader를 사용하는 예시입니다. 이 loader를 사용하면 .svg 파일을 import해서 React component로 rendering할 수 있습니다.

Here is an example below using the @svgr/webpack loader, which enables importing .svg files and rendering them as React components.

JSnext.config.js
module.exports = {
  turbopack: {
    rules: {
      '*.svg': {
        loaders: ['@svgr/webpack'],
        as: '*.js',
      },
    },
  },
}
Good to know

rules 객체에 사용하는 glob은 파일 이름을 기준으로 match됩니다. 단, glob에 / 문자가 들어 있으면 프로젝트 기준 전체 파일 경로를 기준으로 match됩니다. Windows 파일 경로는 unix 스타일 / 경로 구분자를 사용하도록 normalize됩니다.

Turbopack은 Rust globset library를 수정한 버전을 사용합니다.

Globs used in the rules object match based on file name, unless the glob contains a / character, which will cause it to match based on the full project-relative file path. Windows file paths are normalized to use unix-style / path separators.

Turbopack uses a modified version of the Rust globset library.

configuration option이 필요한 loader라면 문자열 대신 객체 형식을 사용할 수 있습니다:

For loaders that require configuration options, you can use an object format instead of a string:

JSnext.config.js
module.exports = {
  turbopack: {
    rules: {
      '*.svg': {
        loaders: [
          {
            loader: '@svgr/webpack',
            options: {
              icon: true,
            },
          },
        ],
        as: '*.js',
      },
    },
  },
}
Good to know

Next.js 13.4.4 이전에는 turbopack.rules의 이름이 turbo.loaders였고, *.mdx 대신 .mdx 같은 파일 확장자만 받았습니다.

Prior to Next.js version 13.4.4, turbopack.rules was named turbo.loaders and only accepted file extensions like .mdx instead of *.mdx.

Advanced webpack loader conditions고급 webpack loader condition

고급 condition 문법을 사용해 loader가 실행되는 위치를 더 제한할 수 있습니다:

You can further restrict where a loader runs using the advanced condition syntax:

JSnext.config.js
module.exports = {
  turbopack: {
    rules: {
      // '*' will match all file paths, but we restrict where our
      // rule runs with a condition.
      '*': {
        condition: {
          all: [
            // 'foreign' is a built-in condition.
            { not: 'foreign' },
            // 'path' can be a RegExp or a glob string. A RegExp matches
            // anywhere in the full project-relative file path.
            { path: /^img\/[0-9]{3}\// },
            {
              any: [
                { path: '*.svg' },
                // 'query' matches anywhere in the full query string,
                // which can be empty, or start with `?`.
                { query: /[?&]svgr(?=&|$)/ },
                // 'content' is always a RegExp, and can match
                // anywhere in the file.
                { content: /\<svg\W/ },
              ],
            },
          ],
        },
        loaders: ['@svgr/webpack'],
        as: '*.js',
      },
    },
  },
}
  • 지원되는 boolean operator는 {all: [...]}, {any: [...]}, {not: ...}입니다.
  • 지원되는 customizable operator는 {path: string | RegExp}, {content: RegExp}, {query: string | RegExp}, {contentType: string | RegExp}입니다. 같은 객체에 여러 operator를 지정하면 암묵적인 and로 동작합니다.
    • path는 프로젝트 기준 파일 경로와 match됩니다. 문자열은 glob pattern으로 취급되며, RegExp를 사용하면 경로의 일부와 match할 수 있습니다.
    • content는 파일 내용의 어느 부분과든 match됩니다.
    • query는 import의 query string(예: import './file?foo'의 ?foo)과 match됩니다. 문자열은 정확히 일치해야 하며, RegExp를 사용하면 query string의 일부와 match할 수 있습니다.
    • contentType은 resource의 MIME content type(예: data:text/plain,... 같은 data URL에서 온 값)과 match됩니다. 문자열은 glob pattern(예: text/*, image/*)으로 취급되며, RegExp를 사용하면 content type의 일부와 match할 수 있습니다.
  • Supported boolean operators are {all: [...]}, {any: [...]} and {not: ...}.
  • Supported customizable operators are {path: string | RegExp}, {content: RegExp}, {query: string | RegExp}, and {contentType: string | RegExp}. If multiple operators are specified in the same object, it acts as an implicit and.
    • path matches against the project-relative file path. A string is treated as a glob pattern, while a RegExp can be used to match the path partially.
    • content matches anywhere in the file content.
    • query matches the import's query string (e.g., ?foo in import './file?foo'). A string must match exactly, while a RegExp can be used to match the query string partially.
    • contentType matches the MIME content type of the resource (e.g., from data URLs like data:text/plain,...). A string is treated as a glob pattern (e.g., text/*, image/*), while a RegExp can be used to match the content type partially.

또한 여러 built-in condition이 지원됩니다:

In addition, a number of built-in conditions are supported:

  • browser: client에서 실행될 코드와 match됩니다. server 코드는 {not: 'browser'}로 match할 수 있습니다.
  • foreign: node_modules에 있는 코드와 일부 Next.js 내부 코드와 match됩니다. 보통 loader를 {not: 'foreign'}으로 제한하는 것이 좋습니다. 이렇게 하면 loader가 호출되는 파일 수가 줄어 performance가 개선될 수 있습니다.
  • development: next dev를 사용할 때 match됩니다.
  • production: next build를 사용할 때 match됩니다.
  • node: 기본 Node.js runtime에서 실행될 코드와 match됩니다.
  • edge-light: Edge runtime(deprecated)에서 실행될 코드와 match됩니다.
  • browser: Matches code that will execute on the client. Server code can be matched using {not: 'browser'}.
  • foreign: Matches code in node_modules, as well as some Next.js internals. Usually you'll want to restrict loaders to {not: 'foreign'}. This can improve performance by reducing the number of files the loader is invoked on.
  • development: Matches when using next dev.
  • production: Matches when using next build.
  • node: Matches code that will run on the default Node.js runtime.
  • edge-light: Matches code that will run on the Edge runtime (deprecated).

rule은 객체이거나 객체의 배열일 수 있습니다. 배열은 서로 겹치지 않는 condition을 표현할 때 유용한 경우가 많습니다:

Rules can be an object or an array of objects. An array is often useful for modeling disjoint conditions:

JSnext.config.js
module.exports = {
  turbopack: {
    rules: {
      '*.svg': [
        {
          condition: 'browser',
          loaders: ['@svgr/webpack'],
          as: '*.js',
        },
        {
          condition: { not: 'browser' },
          loaders: [require.resolve('./custom-svg-loader.js')],
          as: '*.js',
        },
      ],
    },
  },
}
Good to know

match되는 모든 rule이 순서대로 실행됩니다.

All matching rules are executed in order.

Module typesModule type

loader를 사용하지 않고 module type을 직접 설정할 수 있습니다. webpack의 type option과 비슷하게, 파일이 처리되는 방식을 바꿀 때 유용합니다.

You can set the module type directly without using a loader. This is useful for changing how files are processed, similar to webpack's type option.

JSnext.config.js
module.exports = {
  turbopack: {
    rules: {
      '*.svg': {
        type: 'asset',
      },
    },
  },
}

type: 'asset'을 사용하면 파일을 import했을 때 그 URL이 반환됩니다:

When using type: 'asset', importing the file returns its URL:

TSapp/page.tsx
import svgUrl from './icon.svg'

export default function Page() {
  return <img src={svgUrl} alt="Icon" />
}

type option은 loaders와 함께 사용할 수 있습니다. loader가 먼저 실행되고, 그 결과가 지정한 type에 따라 처리됩니다.

The type option can be combined with loaders - loaders run first, then the result is processed according to the specified type.

Inline loader configuration with import attributesimport attribute를 이용한 inline loader 설정

with 절(import attribute)을 사용해 개별 import에 Turbopack loader를 적용할 수 있습니다. 이 설정은 turbopack.rules로 전역 지정하는 대신 import마다 지정합니다.

You can apply a Turbopack loader to an individual import using the with clause (import attributes). This is specified per-import rather than globally via turbopack.rules.

해당 type의 모든 파일에 영향을 주지 않고 특정 import에만 loader를 적용하고 싶을 때 유용합니다.

This is useful when you want to apply a loader to a specific import without affecting all files of that type.

TSapp/page.tsx
// Apply a raw loader to import a .txt file as a JavaScript module
import rawText from '../data.txt' with { turbopackLoader: 'raw-loader', turbopackAs: '*.js' }

export default function Page() {
  return <p>{rawText}</p>
}

다음 import attribute가 지원됩니다:

The following import attributes are supported:

AttributeDescription
turbopackLoader적용할 loader입니다(예: 'raw-loader').
turbopackLoaderOptionsloader option의 JSON 문자열입니다(예: '{"search":"X","replace":"Y"}').
turbopackAsoutput의 rename pattern입니다(turbopack.rules[].as와 동일). 예를 들어 '*.js'는 loader output을 JavaScript로 취급합니다.
turbopackModuleTypeoutput의 module type을 설정합니다(turbopack.rules[].type과 동일).
AttributeDescription
turbopackLoaderThe loader to apply (e.g. 'raw-loader').
turbopackLoaderOptionsJSON string of loader options (e.g. '{"search":"X","replace":"Y"}').
turbopackAsRename pattern for the output (same as turbopack.rules[].as). For example, '*.js' treats the loader output as JavaScript.
turbopackModuleTypeSet the module type for the output (same as turbopack.rules[].type).

option이 있는 loader는 turbopackLoaderOptions로 JSON-encode된 문자열을 전달합니다:

Loaders with options pass a JSON-encoded string via turbopackLoaderOptions:

TSapp/page.tsx
import value from '../data.js' with { turbopackLoader: 'string-replace-loader', turbopackLoaderOptions: '{"search":"PLACEHOLDER","replace":"replaced value"}' }
Good to know

turbopackLoader를 사용하는 import attribute는 Turbopack 전용이며 webpack에서는 지원되지 않습니다. 이 기능을 사용하려면 import 문에서 (assert가 아니라) with keyword를 사용해야 합니다.

Import attributes with turbopackLoader are Turbopack-specific and are not supported by webpack. This feature requires the with keyword (not assert) in your import statements.

Resolving aliasesAlias resolve하기

webpack의 resolve.alias configuration과 비슷하게, alias를 통해 module resolution을 수정하도록 Turbopack을 설정할 수 있습니다.

Turbopack can be configured to modify module resolution through aliases, similar to webpack's resolve.alias configuration.

resolve alias를 설정하려면 next.config.js에서 import pattern을 새 destination에 mapping하세요:

To configure resolve aliases, map imported patterns to their new destination in next.config.js:

JSnext.config.js
module.exports = {
  turbopack: {
    resolveAlias: {
      underscore: 'lodash',
      mocha: { browser: 'mocha/browser-entry.js' },
    },
  },
}

이 설정은 underscore package의 import를 lodash package로 alias합니다. 즉, import underscore from 'underscore'는 underscore 대신 lodash module을 load합니다.

This aliases imports of the underscore package to the lodash package. In other words, import underscore from 'underscore' will load the lodash module instead of underscore.

Turbopack은 Node.js의 conditional exports와 비슷하게, 이 field를 통한 conditional aliasing도 지원합니다. 현재는 browser condition만 지원됩니다. 위 예시에서는 Turbopack이 브라우저 환경을 target으로 할 때 mocha module의 import가 mocha/browser-entry.js로 alias됩니다.

Turbopack also supports conditional aliasing through this field, similar to Node.js' conditional exports. At the moment only the browser condition is supported. In the case above, imports of the mocha module will be aliased to mocha/browser-entry.js when Turbopack targets browser environments.

Resolving custom extensionsCustom 확장자 resolve하기

webpack의 resolve.extensions configuration과 비슷하게, custom 확장자를 가진 module을 resolve하도록 Turbopack을 설정할 수 있습니다.

Turbopack can be configured to resolve modules with custom extensions, similar to webpack's resolve.extensions configuration.

resolve 확장자를 설정하려면 next.config.js에서 resolveExtensions field를 사용하세요:

To configure resolve extensions, use the resolveExtensions field in next.config.js:

JSnext.config.js
module.exports = {
  turbopack: {
    resolveExtensions: [
      '.mdx',
      '.tsx',
      '.ts',
      '.jsx',
      '.js',
      '.mjs',
      '.node',
      '.json',
    ],
  },
}

이 설정은 기본 resolve 확장자를 지정한 목록으로 덮어쓰므로, 여전히 필요한 확장자를 모두 포함하세요. 기본값은 .tsx, .ts, .jsx, .js, .mjs, .json이며, server-side resolution에서는 native module을 위해 .node가 추가됩니다. client에서 .node를 나열해도 문제가 없으므로 하나의 목록으로 양쪽을 모두 처리할 수 있습니다.

This overwrites the default resolve extensions with the provided list, so include every extension you still need. The defaults are .tsx, .ts, .jsx, .js, .mjs, and .json, and server-side resolution adds .node for native modules. Listing .node on the client is harmless, so a single list can cover both.

Good to know

이 설정은 직접 작성한 source 파일에 적용됩니다. node_modules 안에서 resolve되는 import는 자체 확장자 목록을 유지하며 이 option의 영향을 받지 않습니다.

This applies to your own source files. Imports resolved inside node_modules keep their own extension list and are not affected by this option.

앱을 webpack에서 Turbopack으로 migrate하는 방법에 대한 자세한 정보와 가이드는 webpack 호환성에 관한 Turbopack 문서를 참고하세요.

For more information and guidance for how to migrate your app to Turbopack from webpack, see Turbopack's documentation on webpack compatibility.

Debug IDsDebug ID

JavaScript bundle과 source map에서 debug ID를 생성하도록 Turbopack을 설정할 수 있습니다.

Turbopack can be configured to generate debug IDs in JavaScript bundles and source maps.

debug ID를 설정하려면 next.config.js에서 debugIds field를 사용하세요:

To configure debug IDs, use the debugIds field in next.config.js:

JSnext.config.js
module.exports = {
  turbopack: {
    debugIds: true,
  },
}

이 option은 호환성을 보장하기 위해 JavaScript bundle에 debug ID용 polyfill을 자동으로 추가합니다. debug ID는 globalThis._debugIds global 변수에서 사용할 수 있습니다.

The option automatically adds a polyfill for debug IDs to the JavaScript bundle to ensure compatibility. The debug IDs are available in the globalThis._debugIds global variable.
