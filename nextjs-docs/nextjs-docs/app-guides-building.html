Building your application애플리케이션 build하기

next build를 실행하면 production용으로 애플리케이션을 compile하고, 해당되는 route를 prerender하며, 각 route가 어떻게 제공되는지 보여 주는 route table을 출력합니다.

Running next build compiles your application for production, prerenders eligible routes, and prints a route table showing how each route is served.

What next build doesnext build가 하는 일

next build를 실행하면 build는 다음 단계를 거칩니다:

When you run next build, the build moves through these phases:

  1. Setup. environment variable(.env 파일)을 로드하고, next.config를 검증하며, build ID를 생성합니다.
  2. Route discovery. app/과 pages/ directory에서 route를 스캔하고, proxy와 instrumentation 같은 root 수준 convention 파일을 감지합니다. TypeScript route definition을 생성합니다.
  3. Compilation. Turbopack(또는 webpack)으로 client, server, edge 코드를 bundle합니다. TypeScript와 JSX를 transpile하고, 사용하지 않는 코드를 tree-shake하며, CSS와 font를 최적화합니다.
  4. Static analysis. 각 route를 prerendering 대상과 on-demand rendering 대상으로 분류합니다. generateStaticParams output을 수집합니다. Cache Components를 사용하면 prerender를 막는 error가 있는지 확인합니다.
  5. Prerendering. static page와 PPR shell을 HTML로 prerender합니다. client-side navigation을 위한 RSC payload를 생성합니다.
  6. Output. build 결과를 .next/에 씁니다. output: 'standalone'이면 runtime에 필요한 파일만 bundle합니다. output: 'export'이면 완전한 static site를 생성합니다. route table을 출력합니다.
  1. Setup. Loads environment variables (.env files), validates your next.config, and generates a build ID.
  2. Route discovery. Scans the app/ and pages/ directories for routes, and detects root-level convention files like proxy and instrumentation. Generates TypeScript route definitions.
  3. Compilation. Bundles client, server, and edge code with Turbopack (or webpack). Transpiles TypeScript and JSX, tree-shakes unused code, and optimizes CSS and fonts.
  4. Static analysis. Classifies each route for prerendering versus on-demand rendering. Collects generateStaticParams output. With Cache Components, checks for prerender-blocking errors.
  5. Prerendering. Prerenders static pages and PPR shells to HTML. Generates RSC payloads for client-side navigation.
  6. Output. Writes the build to .next/. For output: 'standalone', bundles only the files needed at runtime. For output: 'export', generates a full static site. Prints the route table.

typescript.ignoreBuildErrors가 활성화되어 있지 않으면 build는 TypeScript를 검사합니다.

The build checks TypeScript unless typescript.ignoreBuildErrors is enabled.

next dev는 실행 중인 development server의 state와 incremental compilation cache를 .next/dev에 저장합니다. .next를 삭제하거나 옮기면 그 state가 사라지므로 development server가 이를 다시 만들어야 합니다. 격리된 production build를 실행하려면 별도의 distDir을 설정하세요.

next dev stores the running development server's state and incremental compilation caches in .next/dev. Deleting or moving .next discards that state, so the development server has to recreate it. To run an isolated production build, configure a separate distDir.

build가 성공하면 Next.js는 각 route 옆에 기호가 붙은 route table을 출력합니다.

After a successful build, Next.js prints a route table with a symbol next to each route.

기호는 Cache Components 활성화 여부에 따라 달라집니다.

The symbols differ depending on whether Cache Components is enabled.

Without Cache ComponentsCache Components 없이

Cache Components가 없으면 App Router page와 Pages Router route는 다음 rendering 분류를 사용합니다:

Without Cache Components, App Router pages and Pages Router routes use these rendering classifications:

SymbolNameBehavior
○StaticNext.js가 route 전체를 HTML로 prerender합니다.
●SSGNext.js가 generateStaticParams 또는 getStaticProps에서 나온 path를 HTML로 prerender합니다.
ƒDynamicNext.js가 route를 on demand로 render합니다.
SymbolNameBehavior
○StaticNext.js prerenders the entire route as HTML.
●SSGNext.js prerenders paths from generateStaticParams or getStaticProps as HTML.
ƒDynamicNext.js renders the route on demand.

With Cache ComponentsCache Components 사용 시

Cache Components를 사용하면 Partial Prerendering이 App Router page의 유일한 rendering model이 됩니다. 이런 page에서 기호는 build가 얼마나 많은 HTML을 만들어 냈는지를 나타냅니다:

With Cache Components, Partial Prerendering is the only rendering model for App Router pages. For these pages, the symbols describe how much HTML the build produced:

SymbolNameBehavior
○StaticNext.js가 route 전체를 HTML로 prerender합니다.
◐Partial PrerenderNext.js가 static HTML shell을 prerender하고 나머지 콘텐츠는 on demand로 render합니다.
ƒDynamicNext.js가 route를 on demand로 render합니다.
SymbolNameBehavior
○StaticNext.js prerenders the entire route as HTML.
◐Partial PrerenderNext.js prerenders a static HTML shell and renders the remaining content on demand.
ƒDynamicNext.js renders the route on demand.

Cache Components page에서 ƒ는 build가 비어 있는 HTML prerender를 허용했다는 뜻입니다. Next.js는 request가 올 때 route를 render합니다. dynamic route는 generateStaticParams가 반환하지 않은 pathname을 위한 fallback을 포함할 수도 있습니다.

For a Cache Components page, ƒ means the build accepted an empty HTML prerender. Next.js renders the route on request. A dynamic route can also include a fallback for pathnames not returned by generateStaticParams.

Other route entries그 밖의 route 항목

request에 의존하는 Route Handler(API endpoint), Proxy(Middleware), 그리고 icon, opengraph-image, twitter-image 같은 dynamic metadata route는 ƒ를 사용합니다. 이 항목들은 on demand로 render되며 PPR을 사용하지 않습니다.

Request-dependent Route Handlers (API endpoints), Proxy (Middleware), and dynamic metadata routes such as icon, opengraph-image, and twitter-image use ƒ. These entries render on demand and do not use PPR.

Prerender validationPrerender 검증

Cache Components를 사용하면 next build는 각 App Router page가 static shell을 만들어 낼 수 있는지 검증합니다. <Suspense> 밖에서 params, cookies(), headers() 같은 request 시점 값을 사용하면 runtime data error가 발생합니다. cache되지 않은 데이터는 uncached data error를 발생시킵니다. 각 error에는 해당 데이터 source에 적용되는 해결 방법으로 가는 링크가 있습니다.

With Cache Components, next build validates that each App Router page can produce a static shell. Request-time values such as params, cookies(), and headers() outside of <Suspense> produce a runtime data error. Uncached data produces an uncached data error. Each error links to the fixes that apply to that data source.

Debug prerender errorsprerender error 디버깅

production build는 기본적으로 server 코드를 minify하고 server source map을 생략합니다. 더 자세한 stack trace와 code frame을 보려면 --debug-prerender를 사용하세요:

Production builds minify server code and omit server source maps by default. Use --debug-prerender for more detailed stack traces and code frames:

>_Terminal
next build --debug-prerender

이 option은 server minification을 끄고, server source map을 활성화하며, route 하나가 실패해도 나머지 build가 멈추지 않도록 합니다.

The option disables server minification, enables server source maps, and prevents one failed route from stopping the rest of the build.

Warning

--debug-prerender로 만든 build는 deploy하지 마세요. 이런 build에는 debugging option이 포함되어 있고 production용으로 최적화되어 있지 않습니다.

Do not deploy builds produced with --debug-prerender. These builds include debugging options and are not optimized for production.

Build specific routes특정 route만 build하기

큰 애플리케이션을 디버깅할 때는 --debug-build-paths를 사용해 선택한 route만 compile하고 prerender하세요. 이 option은 쉼표로 구분된 path와 glob pattern을 받습니다. pattern 앞에 !를 붙이면 제외됩니다. --debug-prerender와 함께 사용할 수도 있습니다.

Use --debug-build-paths to compile and prerender selected routes while debugging a large application. The option accepts comma-separated paths and glob patterns. Prefix a pattern with ! to exclude it. You can also combine it with --debug-prerender.

route table에는 match되는 route만 나타납니다. App Router route를 선택하면 Next.js는 기본 제공 /_not-found route도 함께 포함합니다.

Only matching routes appear in the route table. When you select an App Router route, Next.js also includes the built-in /_not-found route.

error는 request 시점 작업을 stream할 수 있는지, cache할 수 있는지, 아니면 route를 반드시 block해야 하는지에 따라 세 가지 option을 제시합니다. 첫 번째 방법은 fallback UI를 stream하는 것입니다.

The error offers three options based on whether the request-time work can stream, be cached, or must block the route. The first approach streams fallback UI.

A streaming product pagestreaming 상품 page

request 시점 데이터가 로드되는 동안 보여 줄 만한 UI가 route에 있다면 error의 [stream] option을 선택하세요. Next.js는 그 fallback을 prerender한 다음, params와 상품 데이터가 resolve되면 상품 page로 교체합니다. 이 route에서는 loading.js 파일이 fallback을 제공합니다:

Choose the error's [stream] option when the route has useful UI to show while request-time data loads. Next.js prerenders that fallback, then replaces it with the product page after the params and product data resolve. In this route, a loading.js file provides the fallback:

TSJSapp/products/[id]/loading.tsx
export default function Loading() {
  return <div>Loading...</div>
}
export default function Loading() {
  return <div>Loading...</div>
}

loading.js는 page를 <Suspense> boundary로 감싸고 loading component를 fallback으로 사용합니다. Next.js는 이 fallback을 상품 route의 static shell로 prerender합니다. page는 request 시점에 params를 읽고 상품을 fetch한 다음, fallback을 완성된 콘텐츠로 교체합니다.

loading.js wraps the page in a <Suspense> boundary and uses the loading component as its fallback. Next.js prerenders this fallback as the product route's static shell. The page reads the params and fetches the product at request time, then replaces the fallback with the completed content.

더 세밀한 streaming을 원한다면, request 시점 데이터가 필요한 component에만 명시적인 <Suspense> boundary를 추가하세요. 그러면 page의 더 많은 부분이 static shell에 남을 수 있습니다. Streaming을 참고하세요.

For more granular streaming, add an explicit <Suspense> boundary around only the component that needs request-time data. More of the page can then stay in the static shell. See Streaming.

Good to know

generateStaticParams는 선택 사항입니다. build 시점에 알려진 pathname 집합이 있고 prerender할 가치가 있을 때 사용하세요. Cache Components에서는 최소 하나의 param을 반환해야 합니다. 빈 배열을 반환하면 build error가 발생합니다.

generateStaticParams is optional. Use it when a set of pathnames is known at build time and worth prerendering. With Cache Components, it must return at least one param. An empty array causes a build error.

Cached product datacache된 상품 데이터

상품 조회를 방문자마다 실행하는 대신 여러 request에 걸쳐 재사용할 수 있다면 error의 [cache] option을 선택하세요. caching을 사용하면 Next.js가 알려진 상품을 prerender할 때 상품 데이터를 포함할 수 있어서, 해당 path에 대해 완전한 HTML을 만들어 냅니다. 조회 함수에 use cache를 추가하세요:

Choose the error's [cache] option when the product lookup can be reused across requests instead of running for every visitor. Caching lets Next.js include the product data when it prerenders a known product, producing complete HTML for those paths. Add use cache to the lookup:

TSJSapp/products/[id]/page.tsx
export async function generateStaticParams() {
  const res = await fetch('https://api.example.com/products')
  const products = await res.json()
  return products.slice(0, 12).map((product) => ({ id: product.id }))
}

async function getProduct(id: string) {
  'use cache'
  const res = await fetch(`https://api.example.com/products/${id}`)
  return res.json()
}

export default async function Page(props: PageProps<'/products/[id]'>) {
  const { id } = await props.params
  const product = await getProduct(id)
  return <div>{product.name}</div>
}

/products/[id] fallback은 generateStaticParams가 반환하지 않은 상품 ID를 나타냅니다. build가 모든 상품 ID를 알지 못하므로 ◐로 남습니다. 목록에 없는 상품에 처음 방문하면, Partial Prefetching이 loading.js fallback을 즉시 제공하고 그동안 Next.js가 해당 ID의 page를 render해 ISR cache에 저장합니다. 이후 방문에서는 fallback 대신 완성된 page를 받습니다. 전체 upgrade 흐름은 ISR with Cache Components를 참고하세요.

The /products/[id] fallback represents product IDs not returned by generateStaticParams. It stays ◐ because the build does not know every product ID. On the first visit to an unlisted product, Partial Prefetching serves the loading.js fallback immediately while Next.js renders the page for that ID and stores it in the ISR cache. Later visits receive the completed page instead of the fallback. See ISR with Cache Components for the complete upgrade flow.

cache된 함수나 component를 포함하는 route에는 Revalidate와 Expire 열도 표시될 수 있습니다. route는 자신이 포함한 모든 cache 중에서 가장 짧은 revalidate와 expire를 표시합니다. 명시적인 cacheLife 호출이 없으면 cache는 default profile을 사용합니다. 같은 cache된 데이터를 render하는 /products 목록 page는 다음과 같은 output을 만듭니다:

Routes that contain cached functions or components can also show Revalidate and Expire columns. A route reports the shortest revalidate and expire across all the caches it contains. Caches use the default profile when there is no explicit cacheLife call. A /products listing page that renders the same cached data produces this output:

request 시점 작업을 기다리는 것이 route에 맞는 동작이라면 error의 [block] option을 선택하세요. route가 response하기 전에 완성된 결과가 필요할 수도 있고, Cache Components를 점진적으로 도입하는 동안 어려운 refactor를 미루고 싶을 수도 있습니다.

Choose the error's [block] option when waiting for request-time work is the correct behavior for the route. The route may need the completed result before it responds, or you may want to defer a difficult refactor while adopting Cache Components incrementally.

이 상품 route가 당분간 blocking 상태로 남아야 한다고 가정해 봅시다. generateStaticParams는 유지하고, loading 파일과 use cache directive를 제거한 다음, instant = false를 설정하세요:

Suppose this product route needs to remain blocking for now. Keep generateStaticParams, remove the loading file and the use cache directive, then set instant = false:

TSJSapp/products/[id]/page.tsx
import { notFound } from 'next/navigation'

export const instant = false

export async function generateStaticParams() {
  const res = await fetch('https://api.example.com/products')
  const products = await res.json()
  return products.slice(0, 12).map((product) => ({ id: product.id }))
}

export default async function Page(props: PageProps<'/products/[id]'>) {
  const { id } = await props.params
  const res = await fetch(`https://api.example.com/products/${id}`)
  if (!res.ok) {
    notFound()
  }
  const product = await res.json()
  return <div>{product.name}</div>
}
import { notFound } from 'next/navigation'

export const instant = false

export async function generateStaticParams() {
  const res = await fetch('https://api.example.com/products')
  const products = await res.json()
  return products.slice(0, 12).map((product) => ({ id: product.id }))
}

export default async function Page({ params }) {
  const { id } = await params
  const res = await fetch(`https://api.example.com/products/${id}`)
  if (!res.ok) {
    notFound()
  }
  const product = await res.json()
  return <div>{product.name}</div>
}

loading boundary가 제거되었으므로, page가 params와 상품 조회를 await하는 동안 render할 수 있는 fallback이 없습니다. use cache를 제거했으므로 조회도 request마다 실행됩니다. server는 상품 page나 404를 반환하기 전에 둘 다 기다립니다. client navigation 중에는 이 작업이 끝날 때까지 목적지에서 보여 줄 fallback이 없습니다.

With the loading boundary removed, no fallback can render while the page awaits params and the product lookup. Removing use cache means the lookup also runs for each request. The server waits for both before returning the product page or a 404. During a client navigation, the destination has no fallback to show until this work completes.

instant = false는 이 route에 대한 instant-navigation validation을 비활성화하며, 여기에는 static shell이 비어 있지 않은지 확인하는 check도 포함됩니다. rendering model을 바꾸거나 prerendering을 막지는 않습니다.

instant = false disables instant-navigation validation for this route, including the check that its static shell is non-empty. It does not change the rendering model or prevent prerendering.

들여쓰기된 /products/[id] 행은 generateStaticParams가 반환하지 않은 ID를 위한 fallback입니다. 들여쓰기된 다른 행은 생성된 상품 path입니다. 상품 조회는 생성된 path가 HTML을 만들기 전에 이를 block하고, fallback은 params가 먼저 block합니다. 모든 prerender가 비어 있으므로 ƒ를 사용합니다. 공유 layout이 children을 <Suspense>로 감싸고 있다면, Next.js는 그 fallback을 static shell로 보존하고 대신 ◐를 사용합니다.

The indented /products/[id] row is the fallback for IDs not returned by generateStaticParams. The other indented rows are the generated product paths. The product lookup blocks the generated paths before they produce HTML, while params blocks the fallback first. Every prerender is empty and uses ƒ. When a shared layout wraps children in <Suspense>, Next.js preserves its fallback as the static shell and uses ◐ instead.

Math.random(), new Date(), crypto.randomUUID() 같은 동기 값은 여전히 prerender error를 발생시킵니다.

Synchronous values such as Math.random(), new Date(), and crypto.randomUUID() still produce prerender errors.
