Using a CDN with Next.jsNext.js에서 CDN 사용하기

Next.js는 CDN이 edge에서 response를 cache하는 데 사용할 수 있는 표준 Cache-Control header를 설정합니다. 이 페이지에서는 현재 동작하는 것, CDN caching이 까다로운 부분, 그리고 custom header 의존성을 없애는 방향을 다룹니다.

Next.js sets standard Cache-Control headers that CDNs can use to cache responses at the edge. This page covers what works today, where CDN caching is challenging, and the direction toward eliminating custom-header dependencies.

What Works Today현재 동작하는 것

Cache-Control headersCache-Control header

Next.js는 각 route의 rendering 전략에 따라 Cache-Control header를 설정합니다:

Next.js sets Cache-Control headers based on the rendering strategy of each route:

  • Static page (revalidation 없음): s-maxage=31536000 (1년)
  • ISR page (시간 기반 revalidation): s-maxage={revalidate}, stale-while-revalidate={expire - revalidate}. 기본 expire는 1년이므로 기본적으로 response header에 stale-while-revalidate가 포함됩니다. cacheLife로 customize할 수 있습니다.
  • Dynamic page (caching 없음): private, no-cache, no-store, max-age=0, must-revalidate
  • Static pages (no revalidation): s-maxage=31536000 (one year)
  • ISR pages (time-based revalidation): s-maxage={revalidate}, stale-while-revalidate={expire - revalidate}. The default expire is one year, so stale-while-revalidate is included in the response header by default. You can customize this with cacheLife.
  • Dynamic pages (no caching): private, no-cache, no-store, max-age=0, must-revalidate

s-maxage와 stale-while-revalidate를 따르는 CDN은 static page와 ISR page를 edge에서 cache할 수 있습니다. 하지만 CDN 수준의 caching만으로는 on-demand revalidation(revalidateTag() / revalidatePath())을 지원하지 않습니다. 이 호출들은 Next.js server cache를 invalidate하지만, CDN은 s-maxage TTL이 만료될 때까지 cache된 사본을 계속 제공합니다. on-demand revalidation을 CDN까지 전파하려면 revalidation 호출과 함께 CDN purge를 trigger하세요. 일반적인 패턴은 revalidateTag()/revalidatePath()를 호출해 Next.js server cache를 invalidate한 다음, 영향을 받는 key(HTML과 RSC variant 모두 포함)에 대해 CDN purge API를 호출하는 것입니다.

CDNs that respect s-maxage and stale-while-revalidate can cache static and ISR pages at the edge. However, CDN-level caching alone does not support on-demand revalidation (revalidateTag() / revalidatePath()): those calls invalidate the Next.js server cache, but the CDN will continue serving its cached copy until the s-maxage TTL expires. To propagate on-demand revalidation to the CDN, trigger CDN purges alongside your revalidation call. A common pattern is: call revalidateTag()/revalidatePath() to invalidate the Next.js server cache, then call your CDN purge API for the affected keys (including both HTML and RSC variants).

Static assetsStatic asset

/_next/static/에서 제공되는 static asset(JavaScript, CSS, 이미지, font)은 파일 이름에 content hash가 들어 있고, 1년짜리 max-age와 immutable directive를 가집니다: public, max-age=31536000, immutable

Static assets (JavaScript, CSS, images, fonts) served from /_next/static/ include content hashes in their filenames and have a 1 year max-age and immutable directive: public, max-age=31536000, immutable

assetPrefix를 사용하면 다른 domain이나 CDN origin에서 static asset을 제공할 수 있습니다.

You can use assetPrefix to serve static assets from a different domain or CDN origin.

Static prefetches (PPR-enabled routes)Static prefetch (PPR이 활성화된 route)

route에 Partial Prerendering이 활성화되어 있고 next-router-prefetch header가 설정되어 있으면(static prefetch임을 나타냄), response는 결정적(deterministic)입니다. 즉, client의 router state와 관계없이 같은 prerender된 콘텐츠를 반환합니다. 이런 request에서는 next-router-state-tree header를 parse하지 않으므로 response에 영향을 주지 않습니다.

When a route has Partial Prerendering enabled and the next-router-prefetch header is set (indicating a static prefetch), the response is deterministic: it returns the same prerendered content regardless of the client's router state. The next-router-state-tree header is not parsed for these requests, so it does not affect the response.

PPR이 활성화된 route에서 CDN은 다음 조건을 만족하면 static prefetch response를 cache할 수 있습니다:

For PPR-enabled routes, a CDN can cache static prefetch responses if it:

  1. cache key에 _rsc search parameter를 포함합니다(prefetch variant와 HTML response를 구분하기 위해).
  2. Next.js가 response에 설정한 Cache-Control header를 따릅니다.
  1. Includes the _rsc search parameter in the cache key (to distinguish prefetch variants from HTML responses).
  2. Respects the Cache-Control headers Next.js sets on the response.
Good to know

PPR이 없는 route에서는 prefetch request 중에 어떤 segment를 포함할지 결정하기 위해 next-router-state-tree header를 읽는데, 이 header가 현재 router state를 전달하므로 cache vary가 늘어납니다. Cache Components가 활성화되어 있으면 segment 수준 prefetch는 이미 pathname 기반 route(예: /page.segments/_tree.segment.rsc)를 사용하며, CDN은 표준 pathname 기반 cache key로 이를 cache할 수 있습니다.

For routes without PPR, the next-router-state-tree header is read during prefetch requests to determine which segments to include, which increases cache vary as it passes the current router state. When Cache Components is enabled, segment-level prefetches already use pathname-based routes (for example, /page.segments/_tree.segment.rsc), and CDNs can cache these with standard pathname-based cache keys.

Where CDN Caching Is ChallengingCDN caching이 까다로운 부분

App Router response는 여러 custom request header에 따라 달라질 수 있습니다. Next.js는 response에 Vary header를 설정해 CDN에 이를 알립니다:

App Router responses can vary based on several custom request headers. Next.js sets a Vary header on responses to signal this to CDNs:

  • rsc — request가 HTML 대신 React Server Components(RSC) payload를 반환해야 하는지 여부
  • next-router-state-tree — client의 현재 router state로, dynamic navigation 중 대상 segment 업데이트에 사용됨
  • next-router-prefetch — prefetch request인지 여부
  • next-router-segment-prefetch — prefetch되는 특정 segment
  • next-url — interception route를 사용하는 route에만 추가되며, intercept되는 URL을 전달함
  • rsc — whether the request should return a React Server Components (RSC) payload instead of HTML
  • next-router-state-tree — the client's current router state, used for targeted segment updates during dynamic navigations
  • next-router-prefetch — whether this is a prefetch request
  • next-router-segment-prefetch — the specific segment being prefetched
  • next-url — added only for routes that use interception routes, carries the URL being intercepted
Good to know

proxy.js(이전 이름 Middleware)는 CDN cache보다 먼저 실행되어야 auth, redirect, rewrite의 source of truth로 남을 수 있습니다. deployment에서 proxy.js가 CDN 뒤에 위치한다면, proxy.js의 결정에 의존하는 route는 caching을 우회하도록 cache layer를 설정하세요.

proxy.js (previously Middleware) should run before the CDN cache so it remains the source of truth for auth, redirects, and rewrites. If your deployment places proxy.js behind the CDN, configure the cache layer to bypass caching for routes that depend on proxy.js decisions.

많은 CDN은 추가 설정 없이는 Vary를 지원하지 않습니다. Next.js는 이 문제를 _rsc search parameter로 해결합니다. 이 값은 관련 request header 값들의 hash로, cache-key 역할을 해서 서로 다른 response variant가 서로 다른 cache key를 갖도록 보장합니다. 덕분에 Vary를 무시하는 CDN에서도 올바른 response가 보장됩니다.

Many CDNs don't support Vary without additional configuration. Next.js addresses this with the _rsc search parameter: a hash of the relevant request header values that acts as a cache-key, ensuring different response variants get different cache keys. This ensures correct responses even on CDNs that ignore Vary.

Handling Headers at the CDNCDN에서 header 처리하기

What you can safely ignore안전하게 무시할 수 있는 것

다음 header는 특정 경우에 생략해도 protocol error가 발생하지 않습니다. server는 여전히 parse 가능한 response를 반환하지만, response가 더 커지거나 특정 navigation에 덜 최적화될 수 있습니다:

These headers can be omitted in specific cases without causing protocol errors. The server still returns a parseable response, but it may be larger or less targeted to the specific navigation:

next-router-state-tree: prefetch가 아닌 RSC request에서 생략하면, server는 대상 segment 업데이트 대신 전체 payload를 반환합니다.

next-router-state-tree: when omitted on non-prefetch RSC requests, the server returns a full payload instead of a targeted segment update.

next-router-segment-prefetch: prefetch request에서 생략하면, server는 segment별 payload 대신 더 넓은 범위의 prefetch payload로 fallback합니다.

next-router-segment-prefetch: when omitted on prefetch requests, the server falls back to a broader prefetch payload instead of a segment-specific one.

next-url: interception route에서 referring page에 따라 response를 다르게 하기 위해 사용됩니다. 생략하면 server가 어떤 원래 path와 match해야 할지 알 수 없으므로 interception route가 지원되지 않습니다. next-url이 생략되면 일반 navigation에 대한 response가 반환되어, 사용자는 intercept된 대상 page 대신 대상 page를 보게 됩니다.

next-url: used for interception routes to vary the response based on the referring page. If omitted, interception routes are not supported as the server doesn't know what original path to match against. The response returned is for regular navigation when next-url is omitted: the user sees the target page instead of the intercepted target page.

What you must preserve반드시 유지해야 하는 것

rsc header는 반드시 client에서 server로 전달되어야 합니다. 이 header는 server에 HTML 대신 RSC payload를 반환하라고 알려 줍니다. CDN이 이 header를 제거하면, client-side router가 RSC 데이터를 기대하는데 server가 HTML을 반환하게 되어 client-side navigation이 깨지고 대신 브라우저 navigation이 발생합니다. Vary header와 _rsc parameter는 바로 CDN이 RSC request에 cache된 HTML response를 제공하는 것(또는 그 반대)을 막기 위해 존재합니다.

The rsc header must be forwarded from the client to the server. This header tells the server to return an RSC payload instead of HTML. If a CDN strips it, the server returns HTML when the client-side router expects RSC data, which breaks client-side navigation, causing browser navigations instead. The Vary header and _rsc parameter exist specifically to prevent CDNs from serving a cached HTML response to an RSC request (or vice versa).

next-router-prefetch가 있으면 prefetch header와 _rsc search parameter를 모두 유지하세요. prefetch 흐름에서 _rsc는 필수 cache-busting 구분자이므로 반드시 있어야 하는 값으로 취급해야 합니다.

When next-router-prefetch is present, preserve both the prefetch header and the _rsc search parameter. For prefetch flows, _rsc is a required cache-busting discriminator and should be treated as mandatory.

_rsc search parameter는 반드시 cache key에 포함되어야 합니다. 이 값은 response variant(HTML vs. RSC, 서로 다른 prefetch 유형)를 구분합니다. 일부 CDN은 기본적으로 cache key에서 query parameter를 제거하므로, CDN이 그렇게 하지 않도록 확인하세요. 기본적으로 RSC request가 올바른 _rsc 값 없이 도착하면, server는 올바른 hash가 붙은 URL로 307 redirect 응답을 보냅니다. 이 동작은 experimental.validateRSCRequestHeaders를 false로 설정해 끌 수 있습니다. CDN은 이 redirect를 따라가야 합니다. upstream에서 hash를 계산하는 플랫폼은 추가 round trip을 피하기 위해 request를 전달하기 전에 올바른 _rsc를 포함하도록 rewrite할 수 있습니다.

The _rsc search parameter must be included in the cache key. It distinguishes response variants (HTML vs. RSC, different prefetch types). Ensure your CDN does not strip query parameters from cache keys, as some CDNs do this by default. By default, when an RSC request arrives without the correct _rsc value, the server responds with a 307 redirect to the URL with the correct hash. This behavior can be disabled by setting experimental.validateRSCRequestHeaders to false. CDNs should follow this redirect. Platforms that compute the hash upstream can rewrite requests to include the correct _rsc before forwarding to avoid an extra round trip.

Good to know

현재는 static prefetch 중에도 next-url이 _rsc hash에 포함됩니다. 따라서 현재 방식에서는 cache miss가 발생할 위험 없이 이 header를 안전하게 무시할 수 없습니다. 아래에서 설명하는 pathname 기반 방향이 이 공백을 해결합니다.

Today, next-url is included in the _rsc hash even during static prefetches. This means you cannot safely ignore it under the current scheme without potentially getting cache misses. The pathname-based direction described below resolves this gap.

Direction: Pathname-Based Cache Keying방향: Pathname 기반 Cache Keying

Next.js 팀은 cache에 영향을 주는 모든 입력을 URL pathname으로 옮기는 작업을 진행하고 있습니다. 이렇게 하면 custom header에 대한 Vary가 필요 없어지고 _rsc search parameter도 제거됩니다. 이는 위에서 설명한 CDN caching 문제를 해결합니다.

The Next.js team is working on moving all cache-affecting inputs into the URL pathname, eliminating the need for Vary on custom headers and removing the _rsc search parameter. This resolves the CDN caching challenges described above.

How it works동작 방식

이 접근 방식은 output: 'export'와 segment prefetch가 이미 사용하고 있는 routing 방식을 확장합니다. pathname의 파일 확장자가 response 유형을 식별합니다:

The approach extends the routing scheme that output: 'export' and segment prefetches already use today. File extensions in the pathname identify the response type:

  • Full page RSC: /my/page.rsc는 page 전체에 대한 RSC payload를 반환합니다
  • Segment RSC: /my/page.segments/path/to/segment.segment.rsc는 특정 segment에 대한 RSC payload를 반환합니다
  • Full page RSC: /my/page.rsc returns the RSC payload for the entire page
  • Segment RSC: /my/page.segments/path/to/segment.segment.rsc returns the RSC payload for a specific segment

이 모델에서는:

Under this model:

  • pathname이 cache key를 결정합니다. pathname에 있는 모든 것이 어떤 response variant가 반환될지에 영향을 줍니다.
  • search parameter는 안전하게 버릴 수 있으며, 반환되는 response에 영향을 주지 않습니다.
  • 표준 HTTP cache header(Cache-Control, max-age 등)는 평소처럼 적용됩니다.
  • CDN에서 Vary 지원이 필요 없습니다.
  • The pathname determines the cache key. Anything in the pathname affects which response variant is returned.
  • Search parameters can be safely dropped without affecting returned responses.
  • Standard HTTP cache headers (Cache-Control, max-age, etc.) are respected as usual.
  • No Vary support needed from the CDN.

CDN은 pathname을 cache key로 사용하고, search parameter를 무시하며, 표준 Cache-Control header를 따르는 방식으로 Next.js response를 cache하게 됩니다. Vary를 이해하거나, custom header를 검사하거나, edge logic을 작성할 필요가 없습니다.

A CDN would cache Next.js responses by using the pathname as the cache key, ignoring search parameters, and respecting standard Cache-Control headers. No need to understand Vary, inspect custom headers, or program edge logic.

What changes for interception routesInterception route에서 달라지는 점

현재 방식에서는 next-url이 _rsc hash에 반영되므로, 이를 버리면 cache miss가 발생합니다. pathname 기반 방식에서는 interception variability가 (pathname이 아닌) search parameter에 encode됩니다:

Under the current scheme, next-url contributes to the _rsc hash, so dropping it causes cache misses. Under the pathname-based scheme, interception variability would be encoded in a search parameter (not the pathname):

  • CDN이 search param을 유지하면 interception이 올바르게 동작합니다.
  • CDN이 search param을 버리면 interception이 지원되지 않습니다. 이 경우 intercept되지 않은 page로 자연스럽게 degrade되며, client-side navigation은 깨지지 않습니다.
  • If a CDN preserves search params, interception works correctly.
  • If a CDN drops search params, interception is not supported. It would gracefully degrade to the non-intercepted page, client-side navigations won't break.

따라서 interception route 지원은 필수 요구 사항이 아니라 CDN이 opt-in하는 기능이 됩니다.

This makes interception route support an opt-in CDN capability rather than a requirement.

Current status현재 상태

이 방향은 codebase에서 이미 동작하고 있는 패턴(segment prefetch path, output: 'export' mode)을 확장한 것입니다. 현재 활발하게 설계 중입니다.

This direction extends patterns that are already operational in the codebase (segment prefetch paths, output: 'export' mode). It is in active design.
