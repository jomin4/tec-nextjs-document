Optimizing the static shellstatic shell 최적화

Cache Components는 request-time 콘텐츠가 stream되어 들어오는 동안 static shell을 prerender할 수 있습니다. shell은 page를 하나의 넓은 fallback으로 대체하는 대신, route의 layout, navigation, heading, 그리고 범위가 좁은 loading state를 계속 보이게 할 수 있습니다.

Cache Components can prerender a static shell while request-time content streams in. The shell can keep the route's layout, navigation, headings, and focused loading states visible instead of replacing the page with one broad fallback.

Cache Components 이전에 작성된 앱은 layout이나 page의 상단 근처에서 request data를 await하는 경우가 많습니다. Cache Components를 활성화하면 이런 route는 이미 작은 static shell을 가지고 있을 수 있는데, 때로는 넓은 loading state 하나로만 이루어져 있기도 합니다.

Apps written before Cache Components often await request data near the top of a layout or page. With Cache Components enabled, those routes may already have a small static shell, sometimes made up of one broad loading state.

이 가이드에서는 각 data read를 그것이 필요한 UI까지 추적하고, 재사용 가능한 작업을 cache하고, request-time 작업을 범위가 좁은 <Suspense> boundary 뒤로 옮겨서 shell을 확장하는 방법을 배웁니다. 이런 패턴을 사용하면 중요한 콘텐츠를 일찍 보여 주고, page의 나머지가 stream되어 들어오는 동안 공간을 확보해 둘 수 있습니다.

In this guide, you'll learn how to expand the shell by tracing each data read to the UI that needs it, caching reusable work, and moving request-time work behind focused <Suspense> boundaries. These patterns keep important content available early and reserve space as the rest of the page streams in.

Good to know

이 가이드는 아래에서 설명하는 static shell과 instant navigation 검증을 가능하게 하는 Cache Components에 초점을 맞춥니다. data 접근을 그것이 필요한 UI 가까이로 옮기기, 범위가 좁은 <Suspense> boundary로 streaming하기, waterfall 피하기, 안정적인 loading state 설계하기 같은 기본 패턴 중 상당수는 다른 App Router 애플리케이션에서도 유용합니다. cache directive와 검증 workflow는 Cache Components가 필요합니다.

This guide focuses on Cache Components, which enable the static shell and instant navigation validation described below. Many of the underlying patterns, such as moving data access closer to the UI that needs it, streaming with focused <Suspense> boundaries, avoiding waterfalls, and designing stable loading states, are also useful in other App Router applications. The cache directives and validation workflow require Cache Components.

cacheComponents를 활성화하고 먼저 route의 blocking validation error를 해결하세요. migration workflow는 Migrating to Cache Components를 참고하세요.

Enable cacheComponents and resolve the route's blocking validation errors first. For the migration workflow, see Migrating to Cache Components.

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
}

export default nextConfig

client navigation을 위해 Partial Prefetching도 함께 활성화하는 것을 고려해 보세요. Partial Prefetching을 활성화하면 <Link prefetch={true}>가 클릭 전에 cache된 URL별 콘텐츠를 포함할 수 있어서, navigation 시 더 많은 UI를 즉시 보여 줄 수 있습니다. 어떤 콘텐츠를 prefetch할지 고르려면 Optimizing prefetching을 참고하세요.

For client navigations, consider enabling Partial Prefetching as well. With Partial Prefetching enabled, <Link prefetch={true}> can include cached URL-specific content before the click, making more UI available immediately on navigation. The following patterns can make more useful UI available in the static shell:

Keep static UI in the shellstatic UI를 shell에 유지하기

<Suspense> boundary는 자식이 suspend될 때 그 fallback이 UI의 어느 부분을 대체할지 결정합니다. static UI가 boundary 안에 있어도 문제는 없습니다. 하지만 같은 boundary에 느리거나 request-time인 작업도 들어 있다면, 그 fallback이 static UI까지 일시적으로 대체합니다.

A <Suspense> boundary controls which part of the UI its fallback replaces when a child suspends. Static UI can sit inside a boundary without a problem. However, if the same boundary also contains slow or request-time work, that fallback temporarily replaces the static UI too.

TSapp/products/page.tsx
// Before: one loading state replaces the whole page
<Suspense fallback={<ProductsSkeleton />}>
  <h1>Products</h1>
  <p>Browse the latest products.</p>
  <LiveInventory />
</Suspense>

heading, navigation, cache된 콘텐츠 및 기타 안정적인 UI를 계속 보이게 하려면, 굳이 포함될 필요가 없는 loading state 바깥으로 이들을 꺼내세요. 그다음 boundary를 suspend될 수 있는 더 작은 영역으로 내리세요:

To keep headings, navigation, cached content, and other stable UI visible, take them out of any loading state they do not need to be part of. Then move the boundary down to the smaller region that can suspend:

TSapp/products/page.tsx
// After: only inventory uses the loading state
<main>
  <h1>Products</h1>
  <p>Browse the latest products.</p>
  <Suspense fallback={<InventorySkeleton />}>
    <LiveInventory />
  </Suspense>
</main>

주요 heading이나 다른 Largest Contentful Paint 후보가 재사용 가능한 data에 의존한다면, 그 data를 cache해서 완성된 콘텐츠가 shell에서 render될 수 있게 하세요. data가 request를 기다려야 한다면, loading state의 범위를 좁게 유지해서 page의 나머지를 붙잡지 않게 하세요.

When the primary heading or other Largest Contentful Paint candidate depends on reusable data, cache that data so the completed content can render in the shell. If the data must wait for the request, keep its loading state focused so it does not hold back the rest of the page.

Stream request-time workrequest-time 작업 stream하기

어떤 data는 request가 도착하기 전까지 알 수 없거나, request마다 다시 계산해야 하거나, prerendering하기에는 cache lifetime이 너무 짧습니다. layout이나 page가 상단 근처에서 이런 작업을 await하면 page 전체의 rendering을 막을 수 있습니다. 결과가 필요한 영역을 분리하고 그 영역만 suspend되도록 해서 page의 나머지가 먼저 render될 수 있게 하세요.

Some data cannot be known until a request arrives, must be recomputed for every request, or has a cache lifetime too short for prerendering. If a layout or page awaits that work near the top, it can block the whole page from rendering. Split out the region that needs the result and let only that region suspend so the rest of the page can render first.

Push data access downdata 접근을 아래로 내리기

request-time data는 그것을 사용하는 논리적인 UI 영역에서 resolve하세요. 이는 data를 await하는 Server Component일 수도 있고, server에서 전달된 promise를 unwrap하는 Client Component일 수도 있습니다.

Resolve request-time data in the logical UI region that uses it. This can be a Server Component that awaits the data or a Client Component that unwraps a promise passed from the server.

data 접근을 Server Component로 옮기세요. page가 request-time data를 직접 resolve하면, 그 작업이 끝날 때까지 heading과 다른 독립적인 UI를 render할 수 없습니다:

Move data access into a Server Component. When the page resolves request-time data itself, its heading and other independent UI cannot render until that work finishes:

TSapp/products/[slug]/page.tsx
// Before: request-time work blocks the page
export default async function ProductPage({
  params,
}: PageProps<'/products/[slug]'>) {
  const { slug } = await params
  const product = await db.products.findBySlug(slug)

  return (
    <main>
      <h1>Product</h1>
      <ProductDetails product={product} />
    </main>
  )
}

params, searchParams 또는 다른 request-time data read를 관련 UI 영역을 나타내는 Server Component로 옮기세요. 그 component를 <Suspense> 뒤에 두어 작업이 resolve되는 동안 형제 요소들이 render될 수 있게 하세요:

Move params, searchParams, or another request-time data read into the Server Component that represents the relevant UI region. Place that component behind <Suspense> so its siblings can render while the work resolves:

TSapp/products/[slug]/page.tsx
// After: only the product region waits
import { Suspense } from 'react'

export default function ProductPage({ params }: PageProps<'/products/[slug]'>) {
  return (
    <main>
      <h1>Product</h1>
      <Suspense fallback={<ProductSkeleton />}>
        <Product params={params} />
      </Suspense>
    </main>
  )
}

async function Product({
  params,
}: Pick<PageProps<'/products/[slug]'>, 'params'>) {
  const { slug } = await params
  const product = await db.products.findBySlug(slug)
  return <ProductDetails product={product} />
}

heading과 product fallback은 request-time product query가 끝나기 전에 render될 수 있습니다. cookies()와 headers() 같은 Request API도 범위가 좁은 component로 옮길 수 있습니다:

The heading and product fallback can render before the request-time product query finishes. Request APIs such as cookies() and headers() can also be moved into a focused component:

TSapp/dashboard/layout.tsx
import { Suspense } from 'react'
import { cookies } from 'next/headers'

export default function DashboardLayout({ children }) {
  return (
    <DashboardShell>
      <Suspense fallback={<UserMenuSkeleton />}>
        <UserMenu />
      </Suspense>
      {children}
    </DashboardShell>
  )
}

async function UserMenu() {
  const cookieStore = await cookies()
  const menuStyle = cookieStore.get('menu-style')?.value ?? 'compact'

  return <DashboardMenu menuStyle={menuStyle} />
}

layout은 UserMenu가 들어오는 request를 읽기 전에 DashboardShell을 반환할 수 있습니다.

The layout can return DashboardShell before UserMenu reads the incoming request.

promise를 inline으로 resolve하세요. 작은 영역이라면 promise를 await하기 위해서만 component를 하나 더 만들 필요는 없습니다. boundary 안에서 .then()으로 params, searchParams 또는 다른 promise를 inline으로 resolve하세요:

Resolve a promise inline. For a small region, you do not need to create another component only to await a promise. Resolve params, searchParams, or another promise inline with .then() inside the boundary:

TSapp/products/page.tsx
<Suspense fallback={<ProductTabsSkeleton />}>
  {searchParams.then(({ tab = 'details' }) => (
    <ProductTabs activeTab={tab} />
  ))}
</Suspense>

promise를 Client Component에 전달하세요. interactive한 Client Component가 server에서 가져온 data를 필요로 할 수 있습니다. 그 data를 부모에서 await하면 부모의 안정적인 UI도 붙잡히게 됩니다:

Pass a promise to a Client Component. An interactive Client Component may need data fetched on the server. Awaiting that data in its parent would also hold back the parent's stable UI:

TSapp/dashboard/page.tsx
// Before: the page waits for the chart data
export default async function DashboardPage() {
  const activity = await getActivity()

  return (
    <main>
      <h1>Dashboard</h1>
      <ActivityChart data={activity} />
    </main>
  )
}

request를 await하지 않고 시작한 다음, <Suspense> 뒤에 있는 Client Component에 promise를 전달하세요:

Start the request without awaiting it, then pass the promise to the Client Component behind <Suspense>:

TSapp/dashboard/page.tsx
// After: the heading can render while the chart waits
import { Suspense } from 'react'
import { getActivity } from '@/app/lib/data'
import { ActivityChart } from './activity-chart'

export default function DashboardPage() {
  const activityPromise = getActivity()

  return (
    <Suspense fallback={<ActivityChartSkeleton />}>
      <ActivityChart dataPromise={activityPromise} />
    </Suspense>
  )
}

Client Component는 React의 use()로 promise를 unwrap합니다:

The Client Component unwraps the promise with React's use():

TSapp/dashboard/activity-chart.tsx
'use client'

import { use } from 'react'

type Activity = { date: string; value: number }

export function ActivityChart({
  dataPromise,
}: {
  dataPromise: Promise<Activity[]>
}) {
  const activity = use(dataPromise)

  return <Chart data={activity} />
}

URL data의 경우, Client Component는 promise를 전달받는 대신 useParams()나 useSearchParams()를 호출할 수 있는 경우가 많습니다. router가 이미 URL을 알고 있기 때문에, 두 hook 모두 client navigation 중에 synchronous하게 resolve됩니다.

For URL data, a Client Component can often call useParams() or useSearchParams() instead of receiving a promise. Both hooks resolve synchronously during a client navigation because the router already has the URL.

request-time 작업을 그것을 사용하는 UI 가까이에서 resolve하는 더 많은 예제는 Push dynamic access down을 참고하세요.

See Push dynamic access down for more examples of resolving request-time work closer to the UI that uses it.

Design loading statesloading state 설계하기

이 refactor 이전에는 route가 segment 전체에 대해 하나의 loading.tsx 파일에 의존했을 수 있습니다. page가 하나의 단위로 load되는 동안에는 그것으로 충분한 경우가 많습니다. data 접근을 아래로 내려서 완성된 UI를 더 많이 드러낼수록, 범위가 좁은 <Suspense> boundary를 사용하고 그 loading state를 더 신중하게 선택하세요. loading.tsx 파일은 바깥쪽 fallback으로 남겨 두거나, route에 더 이상 필요하지 않으면 제거할 수 있습니다.

Before this refactor, a route might rely on one loading.tsx file for the whole segment. That is often enough while the page loads as one unit. As you push data access down to reveal more completed UI, use focused <Suspense> boundaries and choose their loading states more deliberately. The loading.tsx file can remain as an outer fallback, or be removed when the route no longer needs it.

독립적인 영역은 따로 드러내세요. 완성된 각 영역의 크기를 예측할 수 있고 각자 따로 나타날 수 있다면 형제 boundary를 사용하세요. 각 fallback은 완성된 영역에 필요한 공간을 확보해야 합니다:

Reveal independent regions separately. Use sibling boundaries when each completed region has predictable dimensions and can appear on its own. Each fallback should reserve the space its completed region needs:

TSapp/account/page.tsx
<Suspense fallback={<AccountHeaderSkeleton />}>
  <AccountHeader />
</Suspense>
<Suspense fallback={<ActivitySkeleton />}>
  <Activity />
</Suspense>

관련된 영역은 단계적으로 드러내세요. 그룹이 먼저 함께 나타난 다음 더 자세한 내용을 드러내야 할 때, 또는 높이가 가변적인 영역을 단독으로 드러내면 그 아래 콘텐츠가 밀려날 수 있을 때는 boundary를 중첩하세요:

Reveal related regions in stages. Nest boundaries when the group should first appear together and then reveal more detail, or when revealing a variable-height region by itself could shift the content below it:

TSapp/account/page.tsx
<Suspense fallback={<AccountSkeleton />}>
  <AccountHeader />
  <Suspense fallback={<ActivitySkeleton />}>
    <Activity />
  </Suspense>
</Suspense>

React는 같은 render 중에 독립적으로 도달 가능한 작업을 여전히 시작할 수 있습니다. 중첩은 드러나는 순서를 바꿀 뿐, 독립적인 request를 순차적으로 만들지는 않습니다.

React can still start independently reachable work during the same render. Nesting changes the reveal order. It does not make independent requests sequential.

길이가 가변적인 콘텐츠라면, 예측 가능한 접힌 상태를 Show more나 Load more control과 함께 render해서 아래 콘텐츠가 나중에 밀려나지 않고 나타나게 하는 방법도 있습니다.

For variable-length content, another option is to render a predictable collapsed state with a Show more or Load more control so content below can appear without shifting later.

route가 parallel slot을 사용한다면, 각 slot은 자체 loading state로 stream될 수 있습니다. Loading and Error UI with Parallel Routes를 참고하세요.

When a route uses parallel slots, each slot can stream with its own loading state. See Loading and Error UI with Parallel Routes.

loading UI와 완성된 UI에 같은 layout을 사용하세요. component와 responsive layout이 바뀌면서 fallback이 완성된 UI와 점점 어긋날 수 있습니다. layout을 담당하는 container는 boundary 바깥에 두세요. 이 예제에서는 skeleton card와 완성된 product card가 모두 같은 responsive grid를 사용합니다:

Use the same layout for loading and completed UI. Fallbacks can drift away from the completed UI as components and responsive layouts change. Keep the container that owns the layout outside the boundary. In this example, the skeleton cards and completed product cards both use the same responsive grid:

TSapp/products/page.tsx
<ProductGrid>
  <Suspense fallback={<ProductCardSkeletons />}>
    <ProductCards />
  </Suspense>
</ProductGrid>
Good to know

UI를 refactor하거나 업데이트하다 보면 skeleton이 더 이상 완성된 component의 크기나 responsive layout과 맞지 않을 수 있습니다. skeleton을 component 옆에 두거나 같은 파일에서 export하면, 그 component를 <Suspense>로 감싸야 할 때마다 업데이트하고 재사용하기가 더 쉽습니다.

As you refactor or update the UI, a skeleton might no longer match the completed component's size or responsive layout. Keeping the skeleton next to the component, or exporting it from the same file, makes it easier to update and reuse whenever that component needs to be wrapped in <Suspense>.

빈 fallback은 null을 반환하는 authorization gate처럼 resolve된 component도 시각적으로 차지하는 공간이 없을 때만 사용하세요. 그렇지 않다면 완성된 UI를 위한 공간을 확보하는 fallback을 제공하세요.

Use an empty fallback only when the resolved component also has no visual footprint, such as an authorization gate that returns null. Otherwise, provide a fallback that reserves space for the completed UI.

관련 data-fetching 패턴. 작업을 stream되는 영역들로 나눈 후에는, 다음 패턴으로 request 자체가 필요 이상으로 늦게 시작되는 것을 막을 수 있습니다:

Related data-fetching patterns. After splitting work into streamed regions, these patterns can prevent the requests themselves from starting later than necessary:

  • 여러 독립적인 request가 한 영역에 있어야 한다면, parallel data fetching으로 함께 시작하세요.
  • React가 render 후반에 data dependency에 도달한다면, preloading으로 더 일찍 시작하세요.
  • When multiple independent requests must stay in one region, use parallel data fetching to start them together.
  • When React reaches a data dependency later in the render, use preloading to start it sooner.

Cache reusable work재사용 가능한 작업 cache하기

page를 막을 수 있는 작업을 분리한 다음에는, 그 결과를 정말로 request마다 다시 계산해야 하는지 생각해 보세요. 재사용할 수 있다면 함수나 component를 cache해서 완성된 UI가 static shell에서 render될 수 있게 하세요. data가 얼마나 fresh해야 하는지에 따라 결과에 lifetime을 지정하세요:

After isolating work that would block the page, consider whether the result actually needs to be recomputed for every request. When it can be reused, cache the function or component so its completed UI can render in the static shell. Give the result a lifetime based on how fresh the data needs to be:

// Before: the query runs for every request

Instead, move the cookies() and headers() reads into an authentication gate behind <Suspense>. The layout can then render the settings frame without waiting for authentication:

TSapp/[team]/settings/layout.tsx
// After: only the authorization gate waits for the request
import { Suspense } from 'react'
import { cookies, headers } from 'next/headers'
import { redirect } from 'next/navigation'

export default function SettingsLayout({ children }) {
  return (
    <SettingsShell>
      <Suspense fallback={null}>
        <AuthGate />
      </Suspense>
      {children}
    </SettingsShell>
  )
}

async function AuthGate() {
  const [cookieStore, requestHeaders] = await Promise.all([
    cookies(),
    headers(),
  ])
  const user = await getCurrentUser({ cookieStore, requestHeaders })

  if (!user) redirect('/login')

  return null
}

request 값이 필요한 component는 AuthGate뿐이므로, 그 read는 AuthGate가 담당합니다. 이 boundary 덕분에 settings frame과 page가 shell에 남을 수 있습니다. 승인된 gate도 null을 반환하므로, 이 boundary에는 빈 fallback이 적합합니다.

AuthGate is the only component that needs the request values, so it owns those reads. Its boundary lets the settings frame and page stay in the shell. An empty fallback fits this boundary because an authorized gate also returns null.

Good to know

unauthorized()나 forbidden() 같은 authorization interrupt가 streaming이 시작된 후에 실행되면, 해당 UI는 render할 수 있지만 response status는 200으로 남습니다. HTTP 401 또는 403 status가 중요하다면, streaming이 시작되기 전에 접근 권한을 확인하세요. Status codes를 참고하세요.

If an authorization interrupt such as unauthorized() or forbidden() runs after streaming starts, it can render its UI, but the response status remains 200. If the HTTP 401 or 403 status matters, check access before streaming begins. See Status codes.

layout redirect만으로는 database query나 Server Action이 보호되지 않습니다. authorization 검사는 page에서 사용하는 data access 함수 안에 두고, authentication이 완료되기 전의 shell에는 안전한 UI만 포함하세요. 전체 패턴은 Authentication with Cache Components를 참고하세요.

A layout redirect does not protect a database query or Server Action by itself. Keep authorization checks in the data access functions used by the page, and include only safe UI in the shell before authentication completes. See Authentication with Cache Components for the complete pattern.

During a client navigation, SettingsTabs can read the URL synchronously. Other server content that depends on the destination's params or searchParams is not part of the shared shell. If that work is cacheable, a per-link prefetch can resolve it before the click instead of streaming it afterward.
