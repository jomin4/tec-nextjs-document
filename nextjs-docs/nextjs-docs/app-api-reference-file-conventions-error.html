error.jserror.js

error 파일을 사용하면 예상치 못한 runtime error를 처리하고 fallback UI를 표시할 수 있습니다.

An error file allows you to handle unexpected runtime errors and display fallback UI.

TSJSapp/dashboard/error.tsx
'use client' // Error boundaries must be Client Components

import { useEffect } from 'react'

export default function Error({
  error,
  retry,
}: {
  error: unknown
  retry: () => void
}) {
  useEffect(() => {
    // Log the error to an error reporting service
    console.error(error)
  }, [error])

  return (
    <div>
      <h2>Something went wrong!</h2>
      <button
        onClick={
          // Attempt to recover by re-fetching and re-rendering the segment
          () => retry()
        }
      >
        Try again
      </button>
    </div>
  )
}

error.js는 route segment와 그 안에 중첩된 children을 React Error Boundary로 감쌉니다. boundary 안에서 error가 throw되면 error component가 fallback UI로 표시됩니다.

error.js wraps a route segment and its nested children in a React Error Boundary. When an error throws within the boundary, the error component shows as the fallback UI.

Good to know
  • React DevTools를 사용하면 error boundary를 toggle해서 error 상태를 테스트할 수 있습니다.
  • error가 상위 error boundary로 bubble up되게 하려면 error component를 render할 때 throw하면 됩니다.
  • error.js처럼 route segment에 묶이지 않는 component 수준의 error 복구에는 catchError 함수를 사용하세요.
  • The React DevTools allow you to toggle error boundaries to test error states.
  • If you want errors to bubble up to the parent error boundary, you can throw when rendering the error component.
  • For component-level error recovery that aren't tied to route segments like error.js, use the catchError function.

component hierarchy에서 error.js는 loading.js, not-found.js, page.js, 그리고 중첩된 layout.js 파일을 React error boundary로 감쌉니다. 같은 segment에서 그 위에 있는 layout.js나 template.js는 감싸지 않습니다. root layout의 error를 처리하려면 global-error.js를 사용하세요.

In the component hierarchy, error.js wraps loading.js, not-found.js, page.js, and nested layout.js files in a React error boundary. It does not wrap the layout.js or template.js above it in the same segment. To handle errors in the root layout, use global-error.js.

Reference레퍼런스

Props

error

throw된 값으로, error.js Client Component로 전달됩니다. Server Component에서 발생한 error는 Error instance로 전달되지만, Client Component에서 throw된 값은 그대로 전달되므로 Error가 아닐 수도 있습니다. message나 digest 같은 property를 읽기 전에 instanceof Error 등으로 type을 좁히세요.

The value that was thrown, forwarded to the error.js Client Component. Errors from Server Components arrive as an Error instance, while a value thrown in a Client Component is passed as-is and may not be an Error. Narrow it, for example with instanceof Error, before reading properties like message or digest.

Good to know

development 중에는 client로 전달되는 Error 객체가 serialize되며, 디버깅을 쉽게 하도록 원래 error의 message를 포함합니다. 하지만 error에 포함될 수 있는 민감한 정보가 client로 유출되지 않도록 production에서는 이 동작이 다릅니다.

During development, the Error object forwarded to the client will be serialized and include the message of the original error for easier debugging. However, this behavior is different in production to avoid leaking potentially sensitive details included in the error to the client.

error.message

  • Client Component에서 전달된 error는 원래의 Error message를 보여 줍니다.
  • Server Component에서 전달된 error는 identifier가 포함된 일반적인 message를 보여 줍니다. 민감한 정보 유출을 막기 위해서입니다. error.digest에 있는 identifier를 사용해 해당하는 server-side log를 찾을 수 있습니다.
  • Errors forwarded from Client Components show the original Error message.
  • Errors forwarded from Server Components show a generic message with an identifier. This is to prevent leaking sensitive details. You can use the identifier, under error.digest, to match the corresponding server-side logs.

error.digest

throw된 error에 대해 자동으로 생성된 hash입니다. server-side log에서 해당 error를 찾는 데 사용할 수 있습니다.

An automatically generated hash of the error thrown. It can be used to match the corresponding error in server-side logs.

retry

error의 원인은 때로 일시적일 수 있습니다. 이런 경우 다시 시도하면 문제가 해결될 수도 있습니다.

The cause of an error can sometimes be temporary. In these cases, trying again might resolve the issue.

error component는 retry() 함수를 사용해 사용자가 error에서 복구를 시도하도록 유도할 수 있습니다. 이 함수를 실행하면 error boundary의 children을 다시 fetch하고 다시 render하려고 시도합니다. 성공하면 fallback error component가 re-render 결과로 대체됩니다.

An error component can use the retry() function to prompt the user to attempt to recover from the error. When executed, the function will try to re-fetch and re-render the error boundary's children. If successful, the fallback error component is replaced with the result of the re-render.

TSJSapp/dashboard/error.tsx
'use client' // Error boundaries must be Client Components

export default function Error({
  error,
  retry,
}: {
  error: unknown
  retry: () => void
}) {
  return (
    <div>
      <h2>Something went wrong!</h2>
      <button onClick={() => retry()}>Try again</button>
    </div>
  )
}

reset

대부분의 경우에는 retry()를 대신 사용해야 합니다. 하지만 content를 다시 fetch하지 않고 error 상태를 지운 뒤 error boundary의 children을 다시 render해야 할 특별한 이유가 있다면 reset() 함수를 사용할 수 있습니다.

In most cases, you should use retry() instead. However, if you have a specific reason to clear the error state and re-render the error boundary's children without re-fetching the contents, you can use the reset() function.

Examples예시

Global Error

흔하지는 않지만, internationalization을 활용하는 경우에도 root app directory에 위치한 global-error.jsx를 사용해 root layout이나 template의 error를 처리할 수 있습니다. Global error UI는 자체 <html>과 <body> tag, 그리고 error page에 필요한 global style, font 등 기타 dependency를 직접 정의해야 합니다. 이 파일이 활성화되면 root layout이나 template을 대체합니다.

While less common, you can handle errors in the root layout or template using global-error.jsx, located in the root app directory, even when leveraging internationalization. Global error UI must define its own <html> and <body> tags, global styles, fonts, or other dependencies that your error page requires. This file replaces the root layout or template when active.

Good to know

global-error와 기본 제공 500 page는 자체 document를 render하며 global style을 포함하지 않으므로, 앱 수준의 theme toggle(class나 data-theme attribute)이 적용되지 않습니다. 기본 UI는 OS color scheme을 따릅니다. 앱의 theme에 맞추려면 직접 만든 global-error component 안에서 theme을 적용하세요.

global-error and the built-in 500 page render their own document and do not include your global styles, so an app-level theme toggle (a class or data-theme attribute) won't reach them. The default UI follows the OS color scheme; to match your app's theme, apply it inside your own global-error component.

Good to know

Error boundary는 반드시 Client Component여야 하므로, global-error.jsx에서는 metadata와 generateMetadata export가 지원되지 않습니다. 대안으로 React <title> component를 사용할 수 있습니다.

Error boundaries must be Client Components, which means that metadata and generateMetadata exports are not supported in global-error.jsx. As an alternative, you can use the React <title> component.

'use client' // Error boundaries must be Client Components

export default function GlobalError({
  error,
  retry,
}: {
  error: unknown
  retry: () => void
}) {
  return (
    // global-error must include html and body tags
    <html>
      <body>
        <h2>Something went wrong!</h2>
        <button onClick={() => retry()}>Try again</button>
      </body>
    </html>
  )
}

Graceful error recovery with a custom error boundarycustom error boundary로 graceful하게 error 복구하기

client에서 rendering이 실패했을 때, 마지막으로 알려진 server render UI를 보여 주면 더 나은 사용자 경험을 제공할 수 있습니다.

When rendering fails on the client, it can be useful to show the last known server rendered UI for a better user experience.

GracefullyDegradingErrorBoundary는 error가 발생하기 전에 현재 HTML을 capture해 보존하는 custom error boundary의 예시입니다. rendering error가 발생하면 capture한 HTML을 다시 render하고, 사용자에게 알리는 고정 notification bar를 표시합니다.

The GracefullyDegradingErrorBoundary is an example of a custom error boundary that captures and preserves the current HTML before an error occurs. If a rendering error happens, it re-renders the captured HTML and displays a persistent notification bar to inform the user.

TSJSapp/dashboard/error.tsx
'use client'

import React, { Component, ErrorInfo, ReactNode } from 'react'

interface ErrorBoundaryProps {
  children: ReactNode
  onError?: (error: Error, errorInfo: ErrorInfo) => void
}

interface ErrorBoundaryState {
  hasError: boolean
}

export class GracefullyDegradingErrorBoundary extends Component<
  ErrorBoundaryProps,
  ErrorBoundaryState
> {
  private contentRef: React.RefObject<HTMLDivElement | null>

  constructor(props: ErrorBoundaryProps) {
    super(props)
    this.state = { hasError: false }
    this.contentRef = React.createRef()
  }

  static getDerivedStateFromError(_: Error): ErrorBoundaryState {
    return { hasError: true }
  }

  componentDidCatch(error: Error, errorInfo: ErrorInfo) {
    if (this.props.onError) {
      this.props.onError(error, errorInfo)
    }
  }

  render() {
    if (this.state.hasError) {
      // Render the current HTML content without hydration
      return (
        <>
          <div
            ref={this.contentRef}
            suppressHydrationWarning
            dangerouslySetInnerHTML={{
              __html: this.contentRef.current?.innerHTML || '',
            }}
          />
          <div className="fixed bottom-0 left-0 right-0 bg-red-600 text-white py-4 px-6 text-center">
            <p className="font-semibold">
              An error occurred during page rendering
            </p>
          </div>
        </>
      )
    }

    return <div ref={this.contentRef}>{this.props.children}</div>
  }
}

export default GracefullyDegradingErrorBoundary
