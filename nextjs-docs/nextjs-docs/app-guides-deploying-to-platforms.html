Deploying Next.js to different platforms다양한 플랫폼에 Next.js deploy하기

Next.js는 component 수준에서 static과 dynamic content를 하나의 스펙트럼으로 다룹니다. 이 모델의 기능마다 필요한 플랫폼 capability가 다릅니다. 이 페이지는 플랫폼이 무엇을 지원해야 하는지, 그리고 deployment를 어떻게 설정해야 하는지 이해하는 데 도움을 줍니다.

Next.js treats static and dynamic content as a spectrum at the component level. Different features in this model require different platform capabilities. This page helps you understand what your platform needs to support and how to configure your deployment.

Minimum Requirements최소 요구 사항

Next.js를 실행하려면 플랫폼에 Node.js server만 있으면 됩니다. 그게 전부입니다.

To run Next.js, your platform needs a Node.js server. That's it.

하나의 next start process가 Server Components, ISR, PPR, Cache Components, Server Actions, Proxy, after() 등 모든 Next.js 기능을 올바르게 처리합니다. PPR과 Server Components 같은 기능이 content를 점진적으로 전달하려면 streaming 지원이 필요합니다(streaming이 없으면 response가 buffer되어 한꺼번에 전송되는데, 여전히 동작은 하지만 streaming의 performance 이점은 잃게 됩니다). 추가 인프라(CDN caching, edge compute, shared cache)는 주로 performance와 multi-instance 일관성을 개선합니다. multi-instance deployment에서는 shared cache와 tag 조정이 instance 간 stale 데이터의 불일치를 줄여 줍니다. 유일한 추가 dependency는 Image Optimization에 필요한 sharp package입니다.

A single next start process handles every Next.js feature correctly: Server Components, ISR, PPR, Cache Components, Server Actions, Proxy, and after(). Streaming support is needed for features like PPR and Server Components to deliver content progressively (without it, responses are buffered and sent as a whole, which still works but loses the streaming performance benefit). Additional infrastructure (CDN caching, edge compute, shared cache) primarily improves performance and multi-instance consistency. In multi-instance deployments, shared cache and tag coordination reduce stale divergence between instances. The only additional dependency is the sharp package, which is required for Image Optimization.

Functional Fidelity vs. Performance Fidelity기능 충실도 vs. 성능 충실도

플랫폼의 Next.js 지원을 평가할 때는 두 가지 수준을 구분하면 도움이 됩니다:

When evaluating platform support for Next.js, it helps to distinguish between two levels:

Functional fidelity는 모든 Next.js 기능이 올바르게 동작한다는 뜻입니다. adapter test suite가 그 계약입니다: 플랫폼의 adapter가 test를 통과하면 Next.js를 지원하는 것입니다. 이는 이진적입니다: 통과하거나 통과하지 못하거나 둘 중 하나입니다.

Functional fidelity means every Next.js feature works correctly. The adapter test suite is the contract: if a platform's adapter passes the tests, it supports Next.js. This is binary: it passes or it doesn't.

Performance fidelity는 기능이 최적의 performance 특성을 달성한다는 뜻입니다. 예를 들어 PPR의 static shell이 origin latency가 아닌 CDN latency로 제공되는 것, 또는 ISR이 stale content를 즉시 제공하면서 1초 미만으로 revalidation을 전파하는 것이 있습니다. Performance fidelity는 스펙트럼이며, 각 플랫폼이 자신의 아키텍처에 따라 서로 다르게 달성하게 됩니다.

Performance fidelity means features achieve their optimal performance characteristics. Examples include PPR's static shell served at CDN latency rather than origin latency, or ISR serving stale content instantly with sub-second revalidation propagation. Performance fidelity is a spectrum that every platform will achieve differently based on their architecture.

functional fidelity를 달성한 플랫폼은 Next.js의 완전히 지원되는 deployment target입니다. Performance fidelity는 플랫폼들이 차별화하는 지점이며, 시간이 지나면서 점진적으로 개선됩니다.

A platform that achieves functional fidelity is a fully supported deployment target for Next.js. Performance fidelity is how platforms differentiate, and it improves incrementally over time.

아래 기능 matrix는 이런 관점으로 보세요: "Streaming Required"와 "Shared Cache Recommended"는 functional fidelity에 필요한 것을 설명합니다. "Edge Stitching"은 performance fidelity 최적화입니다.

Use the feature matrix below through this lens: "Streaming Required" and "Shared Cache Recommended" describe what is needed for functional fidelity. "Edge Stitching" is a performance fidelity optimization.

기능마다 필요한 인프라 capability가 다릅니다. "Edge Stitching" 열은 정확성 요구 사항이 아니라 performance 최적화입니다. 모든 기능은 단일 origin server에서도 올바르게 동작합니다.

Different features require different infrastructure capabilities. The "Edge Stitching" column is a performance optimization, not a correctness requirement. All features work correctly from a single origin server.

Streaming Required는 플랫폼이 chunked transfer encoding 또는 HTTP/2 streaming을 지원해야 하며, client에 보내기 전에 response를 buffer해서는 안 된다는 뜻입니다.

Streaming Required means the platform must support chunked transfer encoding or HTTP/2 streaming and must not buffer the response before sending it to the client.

Shared Cache Recommended는 여러 server instance가 조정을 위해 shared cache backend를 사용하면 이점이 있다는 뜻입니다. ISR과 server response caching에는 cacheHandler를 사용하세요. 'use cache' entry에는 cacheHandlers를 사용하세요. shared cache가 없으면 각 instance가 자체 cache를 독립적으로 유지합니다 — 기능은 각 instance에서 여전히 올바르게 동작하지만, revalidation 이벤트가 instance 간에 전파되지 않습니다.

Shared Cache Recommended means multiple server instances benefit from shared cache backends to coordinate. For ISR and server response caching, use cacheHandler. For 'use cache' entries, use cacheHandlers. Without shared cache, each instance maintains its own cache independently — features still work correctly on each instance, but revalidation events don't propagate across instances.

Adapters

Next.js는 플랫폼이 자신의 인프라에 맞게 Next.js 애플리케이션의 build와 deploy 방식을 customize할 수 있는 Deployment Adapter API를 제공합니다. adapter는 build time에 실행되며, 표준 Next.js build로부터 플랫폼 특화 output을 생성합니다. 누구나 특별한 접근 권한 없이 public API를 사용해 adapter를 만들 수 있습니다.

Next.js provides a Deployment Adapter API that lets platforms customize how Next.js applications are built and deployed for their infrastructure. Adapters run at build time and produce platform-specific output from the standard Next.js build. Anyone can build an adapter using the public API with no special access required.

adapter API와 Next.js caching interface가 합쳐져 플랫폼 integration의 전체 영역을 이룹니다. adapter는 build-time output을 처리하고, cacheHandler와 cacheHandlers는 서로 다른 runtime caching 경로를 담당합니다. cacheHandler(단수)는 ISR, route handler, patch된 fetch/unstable_cache, image optimization 같은 server cache 경로를 담당합니다. cacheHandlers(복수)는 'use cache' directive backend를 설정합니다.

The adapter API plus Next.js caching interfaces form the complete platform integration surface. The adapter handles build-time output, while cacheHandler and cacheHandlers cover different runtime caching paths. cacheHandler (singular) covers server cache paths like ISR, route handlers, patched fetch/unstable_cache, and image optimization. cacheHandlers (plural) configures 'use cache' directive backends.

Verified Adapters검증된 Adapter

verified adapter는 다음 두 가지 요구 사항을 충족하는 adapter입니다:

A verified adapter is one that meets two requirements:

  1. Open source. community와 Next.js 팀이 검사하고, 기여하고, 검증할 수 있도록 adapter source 코드가 공개되어 있습니다.
  2. Runs the compatibility test suite. 플랫폼이 자신의 adapter에 대해 전체 Next.js compatibility test suite를 실행할 수 있는 방법을 제공합니다. 이를 통해 어떤 기능이 동작하고, 어떤 기능이 진행 중이며, 어디에 공백이 남아 있는지 볼 수 있습니다.
  1. Open source. The adapter source code is publicly available so the community and the Next.js team can inspect, contribute to, and verify it.
  2. Runs the compatibility test suite. The platform provides a way to run the full Next.js compatibility test suite against their adapter. This gives visibility into which features work, which are in progress, and where gaps remain.

verified adapter는 Next.js GitHub organization 아래에서 호스팅되고, Next.js 문서에 지원되는 deployment target으로 등재되며, 각 플랫폼 팀이 유지보수합니다. 비공개 framework hook이나 integration 경로는 없습니다: Vercel의 adapter도 다른 모든 adapter와 같은 public API를 사용합니다.

Verified adapters are hosted under the Next.js GitHub organization, listed as supported deployment targets in the Next.js documentation, and maintained by their respective platform teams. There are no private framework hooks or integration paths: Vercel's adapter uses the same public API as every other adapter.

verified adapter와 Ecosystem Working Group을 통해 verified 상태를 목표로 하는 플랫폼에 대해 Next.js 팀은 다음을 약속합니다:

For verified adapters and platforms working toward verified status through the Ecosystem Working Group, the Next.js team commits to:

  • Coordinated testing. 주요 release 전에 플랫폼 팀과 함께 compatibility test suite를 실행해 문제를 일찍 드러냅니다.
  • Early access. adapter 작성자는 RFC와 release candidate 기간 동안 API 변경 사항에 먼저 접근할 수 있습니다.
  • Direct support. adapter 계약을 업데이트해야 할 때는 adapter 팀과 직접 협력합니다.
  • Coordinated testing. Before major releases, we work with platform teams to run the compatibility test suite and surface issues early.
  • Early access. Adapter authors receive early access to API changes during RFCs and release candidates.
  • Direct support. When the adapter contract needs updating, we work directly with adapter teams.
Good to know

플랫폼은 같은 public API와 test suite를 기반으로 closed-source adapter를 만들 수 있습니다. 하지만 Next.js 팀은 검사할 수 없는 것을 검증할 수 없으므로, closed-source adapter는 verified로 등재되지 않습니다.

Platforms can build closed-source adapters on the same public API and test suite. However, closed-source adapters will not be listed as verified, since the Next.js team cannot verify what it cannot inspect.

A Note on Infrastructure Requirements인프라 요구 사항에 대한 참고

Next.js의 rendering 모델은 static/dynamic 경계를 route 수준이 아닌 component 수준에 둡니다. 경계가 더 세밀할수록 개발자에게는 더 많은 유연성을 주지만, 그 대가로 hosting 플랫폼에 대한 요구 사항이 넓어집니다. 이는 의도적인 trade-off입니다: 이 페이지의 인프라 요구 사항은 rendering 모델이 제공하는 것 때문에 존재합니다.

Next.js's rendering model places the static/dynamic boundary at the component level rather than the route level. Finer-grained boundaries provide more flexibility for developers at the cost of broader requirements for hosting platforms. This is a deliberate trade-off: the infrastructure requirements on this page exist because of what the rendering model delivers.
