How to upgrade to version 16버전 16으로 업그레이드하기

Use a coding agent (recommended)coding agent 사용하기 (권장)

앱 directory에서 최신 upgrade CLI를 실행하세요:

Run the latest upgrade CLI from your app's directory:

>_Terminal
npx next@canary upgrade --agent=latest

CLI는 agent를 위해 Next.js 16 migration guide와 codemod command를 준비한 다음, agent에게 변경 사항을 적용하고 앱을 검증하도록 요청합니다. 자세한 내용은 Upgrade with a coding agent를 참고하세요.

The CLI prepares the Next.js 16 migration guides and codemod command for the agent, then asks it to apply the changes and verify the app. See Upgrade with a coding agent for details.

Or upgrade manually또는 수동으로 업그레이드하기

수동 upgrade는 몇 가지 단계를 순서대로 따릅니다:

Upgrading manually follows a few steps, in order:

  1. 지금 coding agent를 사용하고 있거나, 앞으로의 agent 작업이 버전에 맞는 문서를 기반으로 하길 원한다면 AI agent 문서를 설정하세요.
  2. upgrade codemod를 실행하세요.
  3. codemod를 실행하고 싶지 않다면 package를 수동으로 설치하세요.
  4. 아래의 breaking change를 차례로 살펴보고, 관련 check를 실행하고, 남은 문제를 고치세요.
  1. Set up AI agent docs if you use a coding agent now or want future agent work grounded in version-matched docs.
  2. Run the upgrade codemod.
  3. If you prefer not to run the codemod, install packages manually.
  4. Continue through the breaking changes below, run the relevant checks, and fix any remaining issues.

Set up AI agent docsAI agent 문서 설정하기

upgrade하기 전에 AGENTS.md가 버전에 맞는 Next.js 문서를 가리키도록 해서 coding agent가 나머지 단계를 도울 수 있게 하세요:

Before upgrading, point AGENTS.md at version-matched Next.js docs so a coding agent can help with the remaining steps:

>_Terminal
npx @next/codemod@canary agents-md

upgrade한 뒤에는 AGENTS.md가 node_modules/next/dist/docs/에 있는, 설치된 버전에 포함된 문서를 가리키는지 확인하세요. Next.js 16.2 이상에서는 next dev가 coding agent를 감지하면 이 block을 최신 상태로 유지합니다. setup이 문서를 .next-docs/에 다운로드했다면, 더 이상 그 directory를 참조하는 곳이 없을 때 제거하세요. 관리되는 block과 setup에 대한 자세한 내용은 Version-matched documentation을 참고하세요.

After upgrading, check that AGENTS.md points at the docs bundled with the installed version in node_modules/next/dist/docs/. On Next.js 16.2 and later, next dev keeps this block up to date when it detects a coding agent. If the setup downloaded docs into .next-docs/, remove that directory once nothing references it. See Version-matched documentation for the managed block and setup details.

Using the codemodcodemod 사용하기

Next.js 버전 16으로 업데이트하려면 upgrade codemod를 사용할 수 있습니다:

To update to Next.js version 16, you can use the upgrade codemod:

pnpm dlx @next/codemod@canary upgrade latest
npx @next/codemod@canary upgrade latest
yarn dlx @next/codemod@canary upgrade latest
bunx @next/codemod@canary upgrade latest

codemod는 다음을 할 수 있습니다:

The codemod is able to:

  • 새 turbopack configuration을 사용하도록 next.config.js 업데이트
  • next lint에서 ESLint CLI로 migrate
  • deprecated된 middleware convention에서 proxy로 migrate
  • 안정화된 API에서 unstable_ prefix 제거
  • page와 layout에서 experimental_ppr Route Segment Config 제거
  • Update next.config.js to use the new turbopack configuration
  • Migrate from next lint to the ESLint CLI
  • Migrate from deprecated middleware convention to proxy
  • Remove unstable_ prefix from stabilized APIs
  • Remove experimental_ppr Route Segment Config from pages and layouts

upgrade codemod가 모든 migration codemod를 실행하지는 않습니다. 앱이 Next.js 15 호환 기간의 동기 params, searchParams, cookies(), headers(), draftMode() 접근을 아직 사용하고 있다면 async Request API codemod도 실행하세요:

The upgrade codemod does not run every migration codemod. If your app still uses synchronous params, searchParams, cookies(), headers(), or draftMode() access from the Next.js 15 compatibility period, also run the async Request APIs codemod:

>_Terminal
npx @next/codemod@canary next-async-request-api .

Install packages manuallypackage 수동 설치하기

직접 하고 싶다면 최신 Next.js와 React 버전을 설치하세요:

If you prefer to do it manually, install the latest Next.js and React versions:

pnpm add next@latest react@latest react-dom@latest
npm install next@latest react@latest react-dom@latest
yarn add next@latest react@latest react-dom@latest
bun add next@latest react@latest react-dom@latest

TypeScript를 사용한다면 @types/react와 @types/react-dom도 최신 버전으로 upgrade하세요.

If you are using TypeScript, ensure you also upgrade @types/react and @types/react-dom to their latest versions.

Turbopack by default기본 Turbopack

Next.js 16부터 Turbopack은 stable이 되었고 next dev와 next build에서 기본으로 사용됩니다

Starting with Next.js 16, Turbopack is stable and used by default with next dev and next build

이전에는 --turbopack 또는 --turbo로 Turbopack을 활성화해야 했습니다.

Previously you had to enable Turbopack using --turbopack, or --turbo.

package.json
{
  "scripts": {
    "dev": "next dev --turbopack",
    "build": "next build --turbopack",
    "start": "next start"
  }
}

이제는 그럴 필요가 없습니다. package.json script를 업데이트할 수 있습니다:

This is no longer necessary. You can update your package.json scripts:

package.json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start"
  }
}

프로젝트에 custom webpack configuration이 있는데 next build(이제 기본으로 Turbopack 사용)를 실행하면, 잘못된 설정 문제를 막기 위해 build가 실패합니다.

If your project has a custom webpack configuration and you run next build (which now uses Turbopack by default), the build will fail to prevent misconfiguration issues.

이 문제는 몇 가지 방법으로 해결할 수 있습니다:

You have a few different ways to address this:

  • 그래도 Turbopack 사용: next build --turbopack으로 실행해 Turbopack으로 build하고 webpack config는 무시합니다.
  • Turbopack으로 완전히 전환: webpack config를 Turbopack 호환 option으로 migrate합니다.
  • Webpack 계속 사용: --webpack flag로 Turbopack을 opt out하고 Webpack으로 build합니다.
  • Use Turbopack anyway: Run with next build --turbopack to build using Turbopack and ignore your webpack config.
  • Switch to Turbopack fully: Migrate your webpack config to Turbopack-compatible options.
  • Keep using Webpack: Use the --webpack flag to opt out of Turbopack and build with Webpack.
Good to know

webpack configuration이 발견되어 build가 실패하는데 직접 정의한 적이 없다면, plugin이 webpack option을 추가하고 있을 가능성이 높습니다

If you see failing builds because a webpack configuration was found, but you don't define one yourself, it is likely that a plugin is adding a webpack option

Opting out of TurbopackTurbopack opt out하기

Webpack을 계속 사용해야 한다면 --webpack flag로 opt out할 수 있습니다. 예를 들어 development에서는 Turbopack을, production build에서는 Webpack을 사용하려면 다음과 같이 합니다:

If you need to continue using Webpack, you can opt out with the --webpack flag. For example, to use Turbopack in development but Webpack for production builds:

package.json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build --webpack",
    "start": "next start"
  }
}

development와 production 모두에 Turbopack 사용을 권장합니다. Turbopack으로 전환할 수 없다면 이 thread에 comment를 남겨 주세요.

We recommend using Turbopack for development and production. Submit a comment to this thread, if you are unable to switch to Turbopack.

Resolve alias fallback

일부 프로젝트에서는 client-side 코드가 Node.js native module을 포함한 파일을 import할 수 있습니다. 이 경우 Module not found: Can't resolve 'fs' 유형의 error가 발생합니다.

In some projects, client-side code may import files containing Node.js native modules. This will cause Module not found: Can't resolve 'fs' type of errors.

이런 일이 생기면 client-side bundle이 이 Node.js native module을 참조하지 않도록 코드를 refactor해야 합니다.

When this happens, you should refactor your code so that your client-side bundles do not reference these Node.js native modules.

하지만 경우에 따라서는 이것이 불가능할 수도 있습니다. Webpack에서는 보통 resolve.fallback option을 사용해 error를 숨겼습니다. Turbopack은 turbopack.resolveAlias를 사용하는 비슷한 option을 제공합니다. 이 경우 브라우저용으로 fs가 요청되면 빈 module을 load하도록 Turbopack에 알려 주세요.

However, in some cases, this might not be possible. In Webpack the resolve.fallback option was typically used to silence the error. Turbopack offers a similar option, using turbopack.resolveAlias. In this case, tell Turbopack to load an empty module when fs is requested for the browser.

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  turbopack: {
    resolveAlias: {
      fs: {
        browser: './empty.ts', // We recommend to fix code imports before using this method
      },
    },
  },
}

export default nextConfig

client 코드가 Node.js native module을 사용하는 module에서 절대 import하지 않도록 module을 refactor하는 것이 더 바람직합니다.

It is preferable to refactor your modules so that client code doesn't ever import from modules using Node.js native modules.

Sass node_modules importsSass node_modules import

Turbopack은 node_modules에서 Sass 파일을 import하는 것을 완전히 지원합니다. 단, Webpack은 legacy tilde(~) prefix를 허용했지만 Turbopack은 이 문법을 지원하지 않는다는 점에 유의하세요.

Turbopack fully supports importing Sass files from node_modules. Note that while Webpack allowed the legacy tilde (~) prefix, Turbopack does not support this syntax.

Webpack에서는:

In Webpack:

styles/globals.scss
@import '~bootstrap/dist/css/bootstrap.min.css';

Turbopack에서는:

In Turbopack:

styles/globals.scss
@import 'bootstrap/dist/css/bootstrap.min.css';

import를 바꿀 수 없다면 turbopack.resolveAlias를 사용할 수 있습니다. 예를 들면 다음과 같습니다:

If changing the imports is not possible, you can use turbopack.resolveAlias. For example:

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  turbopack: {
    resolveAlias: {
      '~*': '*',
    },
  },
}

export default nextConfig

Turbopack File System Caching

Turbopack은 실행 사이에 compiler artifact를 disk에 저장해서, 재시작 시 compile 시간을 크게 줄여 줍니다. Filesystem caching은 experimental.turbopackFileSystemCacheForDev와 experimental.turbopackFileSystemCacheForBuild를 통해 next dev와 next build 모두에서 기본으로 활성화되어 있습니다. 둘 중 하나를 설정하거나 끄려면 Turbopack FileSystem Caching을 참고하세요.

Turbopack stores compiler artifacts on disk between runs, for significantly faster compile times across restarts. Filesystem caching is enabled by default for both next dev and next build, through experimental.turbopackFileSystemCacheForDev and experimental.turbopackFileSystemCacheForBuild. See Turbopack FileSystem Caching to configure or disable either one.

React Compiler SupportReact Compiler 지원

React Compiler의 1.0 release에 이어 Next.js 16에서 React Compiler built-in 지원이 stable이 되었습니다. React Compiler는 component를 자동으로 memoize해서, 코드를 직접 하나도 바꾸지 않고도 불필요한 re-render를 줄여 줍니다.

Built-in support for the React Compiler is now stable in Next.js 16 following the React Compiler's 1.0 release. The React Compiler automatically memoizes components, reducing unnecessary re-renders with zero manual code changes.

reactCompiler configuration option이 experimental에서 stable로 승격되었습니다. 다양한 애플리케이션 유형에 걸친 build 성능 데이터를 계속 수집하고 있기 때문에 기본으로 활성화되어 있지는 않습니다.

The reactCompiler configuration option has been promoted from experimental to stable. It is not enabled by default as we continue gathering build performance data across different application types.

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  reactCompiler: true,
}

export default nextConfig
/** @type {import('next').NextConfig} */
const nextConfig = {
  reactCompiler: true,
}

module.exports = nextConfig

최신 버전의 React Compiler plugin을 설치하세요:

Install the latest version of the React Compiler plugin:

pnpm add -D babel-plugin-react-compiler
npm install -D babel-plugin-react-compiler
yarn add -D babel-plugin-react-compiler
bun add -D babel-plugin-react-compiler
Good to know

React Compiler는 Babel에 의존하기 때문에, 이 option을 활성화하면 development와 build 중 compile 시간이 늘어날 수 있습니다.

Expect compile times in development and during builds to be higher when enabling this option as the React Compiler relies on Babel.

middleware to proxymiddleware에서 proxy로

middleware 파일 이름은 deprecated되었고, network boundary와 routing 중심이라는 점을 명확히 하기 위해 proxy로 이름이 바뀌었습니다.

The middleware filename is deprecated, and has been renamed to proxy to clarify network boundary and routing focus.

proxy에서는 edge runtime이 지원되지 않습니다. proxy의 runtime은 nodejs이며 설정으로 바꿀 수 없습니다. edge runtime을 계속 사용하려면 middleware를 계속 사용하세요. edge runtime에 대한 추가 안내는 이후 minor release에서 제공할 예정입니다.

The edge runtime is NOT supported in proxy. The proxy runtime is nodejs, and it cannot be configured. If you want to continue using the edge runtime, keep using middleware. We will follow up on a minor release with further edge runtime instructions.

>_Terminal
# Rename your middleware file
mv middleware.ts proxy.ts
# or
mv middleware.js proxy.js

named export middleware도 deprecated되었습니다. 함수 이름을 proxy로 바꾸세요.

The named export middleware is also deprecated. Rename your function to proxy.

TSJSproxy.ts
export function proxy(request: Request) {}
export function proxy(request) {}

default export를 사용하더라도 함수 이름을 proxy로 바꾸는 것을 권장합니다.

We recommend changing the function name to proxy, even if you are using a default export.

middleware라는 이름이 들어간 configuration flag도 이름이 바뀌었습니다. 예를 들어 skipMiddlewareUrlNormalize는 이제 skipProxyUrlNormalize입니다

Configuration flags that contained the middleware name are also renamed. For example, skipMiddlewareUrlNormalize is now skipProxyUrlNormalize

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  skipProxyUrlNormalize: true,
}

export default nextConfig
/** @type {import('next').NextConfig} */
const nextConfig = {
  skipProxyUrlNormalize: true,
}

module.exports = nextConfig

버전 16 codemod로 이 flag들도 업데이트할 수 있습니다.

The version 16 codemod is able to update these flags too.

next/image changesnext/image 변경 사항

Local Images with Query Strings (Breaking change)query string이 있는 local image (Breaking change)

query string이 있는 local image source는 이제 enumeration attack을 막기 위해 images.localPatterns.search configuration이 필요합니다.

Local image sources with query strings now require images.localPatterns.search configuration to prevent enumeration attacks.

TSapp/page.tsx
import Image from 'next/image'

export default function Page() {
  return <Image src="/assets/photo?v=1" alt="Photo" width="100" height="100" />
}

local image에 query string을 사용해야 한다면 configuration에 pattern을 추가하세요:

If you need to use query strings with local images, add the pattern to your configuration:

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  images: {
    localPatterns: [
      {
        pathname: '/assets/**',
        search: '?v=1',
      },
    ],
  },
}

export default nextConfig
/** @type {import('next').NextConfig} */
const nextConfig = {
  images: {
    localPatterns: [
      {
        pathname: '/assets/**',
        search: '?v=1',
      },
    ],
  },
}

module.exports = nextConfig

minimumCacheTTL Default (Breaking change)minimumCacheTTL 기본값 (Breaking change)

images.minimumCacheTTL의 기본값이 60 seconds에서 4 hours(14400초)로 바뀌었습니다. 이를 통해 cache-control header가 없는 image의 revalidation 비용이 줄어듭니다.

The default value for images.minimumCacheTTL has changed from 60 seconds to 4 hours (14400 seconds). This reduces revalidation cost for images without cache-control headers.

일부 Next.js 사용자의 경우 image revalidation이 자주 발생했는데, 대개 upstream source image에 cache-control header가 빠져 있었기 때문입니다. 이로 인해 60초마다 revalidation이 일어나 CPU 사용량과 비용이 늘어났습니다.

For some Next.js users, image revalidation was happening frequently, often because the upstream source images missed a cache-control header. This caused revalidation to happen every 60 seconds, which increased CPU usage and cost.

대부분의 image는 자주 바뀌지 않기 때문에 이렇게 짧은 간격은 바람직하지 않습니다. 기본값을 4시간으로 설정하면 기본적으로 더 오래 유지되는 cache를 제공하면서도, 필요하면 image가 하루에 몇 번은 업데이트될 수 있습니다.

Since most images do not change often, this short interval is not ideal. Setting the default to 4 hours offers a more durable cache by default, while still allowing images to update a few times per day if needed.

이전 동작이 필요하다면 minimumCacheTTL을 더 낮은 값으로, 예를 들어 다시 60초로 바꾸세요:

If you need the previous behavior, change minimumCacheTTL to a lower value, for example back to 60 seconds:

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  images: {
    minimumCacheTTL: 60,
  },
}

export default nextConfig
/** @type {import('next').NextConfig} */
const nextConfig = {
  images: {
    minimumCacheTTL: 60,
  },
}

module.exports = nextConfig

imageSizes Default (Breaking change)imageSizes 기본값 (Breaking change)

기본 images.imageSizes array에서 16 값이 제거되었습니다.

The value 16 has been removed from the default images.imageSizes array.

request analytics를 살펴본 결과, 16 pixel 너비의 image를 제공하는 프로젝트는 극히 드물었습니다. 이 설정을 제거하면 next/image가 브라우저에 보내는 srcset attribute의 크기가 줄어듭니다.

We have looked at request analytics and found out that very few projects ever serve 16 pixels width images. Removing this setting reduces the size of the srcset attribute shipped to the browser by next/image.

16px image를 지원해야 한다면:

If you need to support 16px images:

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  images: {
    imageSizes: [16, 32, 48, 64, 96, 128, 256, 384],
  },
}

export default nextConfig
/** @type {import('next').NextConfig} */
const nextConfig = {
  images: {
    imageSizes: [16, 32, 48, 64, 96, 128, 256, 384],
  },
}

module.exports = nextConfig

개발자들이 잘 사용하지 않아서라기보다는, devicePixelRatio: 2가 retina display에서 흐릿함을 막기 위해 실제로는 32px image를 가져오기 때문에 16 pixel 너비의 image가 덜 흔해졌다고 판단합니다.

Rather than lack of developer usage, we believe 16 pixels width images have become less common, because devicePixelRatio: 2 actually fetches a 32px image to prevent blurriness in retina displays.

qualities Default (Breaking change)qualities 기본값 (Breaking change)

images.qualities의 기본값이 모든 quality를 허용하던 것에서 [75]만 허용하도록 바뀌었습니다.

Scroll Behavior Override

이전 버전의 Next.js에서는 CSS로 <html> element에 전역으로 scroll-behavior: smooth를 설정해 두었다면, SPA route 전환 중에 Next.js가 다음과 같이 이 설정을 override했습니다:

In previous versions of Next.js, if you had set scroll-behavior: smooth globally on your <html> element via CSS, Next.js would override this during SPA route transitions, as follows:

  1. 일시적으로 scroll-behavior를 auto로 설정
  2. navigation 수행(즉시 맨 위로 scroll됨)
  3. 원래 scroll-behavior 값 복원
  1. Temporarily set scroll-behavior to auto
  2. Perform the navigation (causing instant scroll to top)
  3. Restore your original scroll-behavior value

이렇게 하면 page 안의 navigation에 smooth scrolling을 활성화해 두었더라도 page navigation은 항상 빠르고 즉각적으로 느껴졌습니다. 하지만 이 조작은 특히 매 navigation이 시작될 때 비용이 클 수 있었습니다.

This ensured that page navigation always felt snappy and instant, even when you had smooth scrolling enabled for in-page navigation. However, this manipulation could be expensive, especially at the start of every navigation.

Next.js 16에서는 이 동작이 바뀌었습니다. 기본적으로 Next.js는 navigation 중에 scroll-behavior 설정을 더 이상 override하지 않습니다.

In Next.js 16, this behavior has changed. By default, Next.js will no longer override your scroll-behavior setting during navigation.

Next.js가 이 override를 수행하길 원한다면 (이전 기본 동작) <html> element에 data-scroll-behavior="smooth" attribute를 추가하세요:

If you want Next.js to perform this override (the previous default behavior), add the data-scroll-behavior="smooth" attribute to your <html> element:

TSpages/_document.tsx
import { Html, Head, Main, NextScript } from 'next/document'

export default function Document() {
  return (
    <Html lang="en" data-scroll-behavior="smooth">
      <Head />
      <body>
        <Main />
        <NextScript />
      </body>
    </Html>
  )
}

Performance Improvements성능 개선

next dev와 next start command의 성능이 크게 최적화되었고, 더 명확한 형식, 더 나은 error message, 개선된 performance metric으로 terminal output도 좋아졌습니다.

Significant performance optimizations for next dev and next start commands, along with improved terminal output with clearer formatting, better error messages, and improved performance metrics.

Next.js 16은 next build output에서 size와 First Load JS metric을 제거합니다. React Server Components를 사용하는 server-driven architecture에서는 이 값들이 부정확하다는 것을 확인했습니다. Turbopack과 Webpack 구현 모두 문제가 있었고, Client Component payload를 계산하는 방식도 서로 달랐습니다.

Next.js 16 removes the size and First Load JS metrics from the next build output. We found these to be inaccurate in server-driven architectures using React Server Components. Both our Turbopack and Webpack implementations had issues, and disagreed on how to account for Client Components payload.

실제 route 성능을 측정하는 가장 효과적인 방법은 Core Web Vitals와 다운로드된 resource 크기에 초점을 맞춘 Chrome Lighthouse나 Vercel Analytics 같은 도구를 사용하는 것입니다.

The most effective way to measure actual route performance is through tools such as Chrome Lighthouse or Vercel Analytics, which focus on Core Web Vitals and downloaded resource sizes.

Next.js 16은 next lint를 제거하지만, ESLint CLI로 migrate하는 데 ESLint upgrade가 필요한 것은 아닙니다. eslint-config-next@16은 ESLint 9 이상이 필요하고, eslint-config-next@16.4.0 이상은 ESLint 10을 지원합니다. 기존 lint configuration이 eslint-config-next@16을 사용하지 않는다면 호환되는 기존 ESLint 버전을 그대로 유지할 수 있습니다.

If your existing lint configuration does not use eslint-config-next@16, you can keep its compatible ESLint version.

  • [ ] 설치 때문에 upgrade가 중단되었다면, 고친 lint stack을 유지하고 lint codemod를 건너뛰도록 --skip-eslint-upgrade와 함께 똑같은 target으로 다시 시도하세요. Next.js가 이미 target과 일치한다면 dependency를 설치하고 중단된 migration을 개별적으로 완료하세요. next lint script를 유지된 configuration과 호환되는 ESLint CLI command로 교체하세요. 설치와 lint가 통과하는지 확인하세요.
  • [ ] If an ESLint upgrade causes peer dependency conflicts, restore the previous compatible versions of eslint, eslint-config-next, and @next/eslint-plugin-next (if present), along with the previous lint configuration.

If Next.js already matches the target, install dependencies and complete interrupted migrations individually.   • [ ] Development and build scripts agree with the effective bundler configuration, including plugins, loaders, aliases, and affected Sass imports.
  • [ ] Middleware and proxy changes preserve the required runtime and routing behavior. Edge middleware is not blindly renamed to proxy.
