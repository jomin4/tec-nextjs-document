TypeScriptTypeScript

Next.js는 TypeScript를 기본으로 내장하고 있어서, create-next-app으로 새 프로젝트를 만들면 필요한 package를 자동으로 설치하고 적절한 설정을 구성합니다.

Next.js comes with built-in TypeScript, automatically installing the necessary packages and configuring the proper settings when you create a new project with create-next-app.

기존 프로젝트에 TypeScript를 추가하려면 파일 이름을 .ts / .tsx로 바꾸세요. next dev와 next build를 실행하면 필요한 dependency가 자동으로 설치되고, 권장 config option이 들어간 tsconfig.json 파일이 추가됩니다.

To add TypeScript to an existing project, rename a file to .ts / .tsx. Run next dev and next build to automatically install the necessary dependencies and add a tsconfig.json file with the recommended config options.

Good to know

이미 jsconfig.json 파일이 있다면, 기존 jsconfig.json의 paths compiler option을 새 tsconfig.json 파일로 복사한 뒤 기존 jsconfig.json 파일을 삭제하세요.

If you already have a jsconfig.json file, copy the paths compiler option from the old jsconfig.json into the new tsconfig.json file, and delete the old jsconfig.json file.

Using TypeScript 7TypeScript 7 사용하기

TypeScript 7은 현재 JavaScript compiler API를 제공하지 않습니다. next build 중에 TypeScript 7을 사용하려면 프로젝트에 설치하세요:

TypeScript 7 does not currently provide the JavaScript compiler API. To use TypeScript 7 during next build, install it in your project:

pnpm add -D typescript@^7
npm install -D typescript@^7
yarn add -D typescript@^7
bun add -D typescript@^7

Next.js는 기본적으로 프로젝트 로컬 tsc CLI를 사용하므로 추가 설정이 필요 없습니다. 대신 JavaScript compiler API를 사용하려면 experimental.useTypeScriptCli를 false로 설정하세요.

Next.js uses the project-local tsc CLI by default, so no additional configuration is required. To use the JavaScript compiler API instead, set experimental.useTypeScriptCli to false.

Good to know
  • CLI type checking은 native tsc diagnostic을 출력합니다. Next.js 전용 code frame을 적용하거나 route, page, layout, route handler에 대한 error를 재작성하지 않습니다.
  • CLI는 tsconfig 파일이 선택한 프로젝트 전체를 check합니다. 해당 configuration에 포함되어 있다면 test 파일과 .next/dev/types도 대상이 됩니다. next build --debug-build-paths는 type check 대상 파일을 좁히지 않으며, 이 option과 함께 사용하면 warning이 출력됩니다.
  • typescript.tsconfigPath는 계속해서 tsc에 전달할 configuration을 선택합니다. typescript.ignoreBuildErrors는 CLI checker를 포함한 type-checking 단계를 건너뜁니다.
  • experimental.useTypeScriptCli는 experimental이며 동작이 바뀔 수 있습니다.
  • CLI type checking prints the native tsc diagnostics. It does not apply Next.js-specific code frames or rewrite errors for routes, pages, layouts, or route handlers.
  • The CLI checks the complete project selected by your tsconfig file. This includes test files and .next/dev/types when they are included by that configuration. next build --debug-build-paths does not narrow the files that are type checked and produces a warning when used with this option.
  • typescript.tsconfigPath continues to select the configuration passed to tsc. typescript.ignoreBuildErrors skips the type-checking step, including the CLI checker.
  • experimental.useTypeScriptCli is experimental and its behavior may change.

next-env.d.ts

Next.js는 프로젝트 root에 next-env.d.ts 파일을 생성합니다. 이 파일은 Next.js type 정의를 참조하여, TypeScript가 코드가 아닌 import(이미지, stylesheet 등)와 Next.js 전용 type을 인식할 수 있게 합니다.

Next.js generates a next-env.d.ts file in your project root. This file references Next.js type definitions, allowing TypeScript to recognize non-code imports (images, stylesheets, etc.) and Next.js-specific types.

next dev, next build, next typegen을 실행하면 이 파일이 다시 생성됩니다.

Running next dev, next build, or next typegen regenerates this file.

Good to know
  • next-env.d.ts는 Next.js가 관리합니다. 내용은 구현 세부 사항이며 시간이 지나면서 바뀔 수 있습니다. .gitignore에 추가하세요. 프로젝트에서 이미 이 파일을 추적하고 있다면 Git에서 제거하세요. 이 파일을 직접 수정하지 마세요.
  • 이 파일은 tsconfig.json의 include 배열에 포함되어 있어야 합니다(create-next-app이 자동으로 처리합니다).
  • next-env.d.ts is managed by Next.js. Its contents are an implementation detail and may change over time. Add it to .gitignore. If your project already tracks the file, remove it from Git. Do not edit this file manually.
  • The file must be in your tsconfig.json include array (create-next-app does this automatically).

Type Checking Next.js Configuration FilesNext.js configuration 파일 type checking

next.config.ts를 사용하면 Next.js configuration에서 TypeScript를 사용하고 type을 import할 수 있습니다.

You can use TypeScript and import types in your Next.js configuration by using next.config.ts.

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  /* config options here */
}

export default nextConfig

next.config.ts의 module resolution은 현재 CommonJS로 제한됩니다. 다만 Node.js v22.10.0 이상에서 Node.js native TypeScript resolver를 사용하면 ECMAScript Modules(ESM) 문법을 사용할 수 있습니다.

Module resolution in next.config.ts is currently limited to CommonJS. However, ECMAScript Modules (ESM) syntax is available when using Node.js native TypeScript resolver for Node.js v22.10.0 and higher.

next.config.js 파일을 사용할 때는 아래와 같이 JSDoc을 사용해 IDE에서 어느 정도 type checking을 할 수 있습니다:

When using the next.config.js file, you can add some type checking in your IDE using JSDoc as below:

JSnext.config.js
// @ts-check

/** @type {import('next').NextConfig} */
const nextConfig = {
  /* config options here */
}

module.exports = nextConfig

Using Node.js Native TypeScript Resolver for next.config.tsnext.config.ts에 Node.js native TypeScript resolver 사용하기

Note

Node.js v22.10.0+에서, 그리고 해당 기능이 활성화된 경우에만 사용할 수 있습니다. Next.js가 이 기능을 활성화하지는 않습니다.

Available on Node.js v22.10.0+ and only when the feature is enabled. Next.js does not enable it.

Next.js는 버전 v22.10.0 시점에 추가된 process.features.typescript를 통해 Node.js native TypeScript resolver를 감지합니다. 이것이 있으면 next.config.ts에서 top‑level await와 dynamic import()를 포함한 native ESM을 사용할 수 있습니다. 이 방식은 Node resolver의 기능과 제약을 그대로 이어받습니다.

Next.js detects the Node.js native TypeScript resolver via process.features.typescript, added in v22.10.0. When present, next.config.ts can use native ESM, including top‑level await and dynamic import(). This mechanism inherits the capabilities and limitations of Node's resolver.

Node.js 버전 v22.18.0+ 이상에서는 process.features.typescript가 기본적으로 활성화되어 있습니다. 버전 v22.10.0 부터 22.17.x 사이에서는 NODE_OPTIONS=--experimental-transform-types로 opt in하세요:

In Node.js versions v22.18.0+, process.features.typescript is enabled by default. For versions between v22.10.0 and 22.17.x, opt in with NODE_OPTIONS=--experimental-transform-types:

>_Terminal
NODE_OPTIONS=--experimental-transform-types next <command>

For CommonJS Projects (Default)CommonJS 프로젝트 (기본값)

next.config.ts는 CommonJS 프로젝트에서도 native ESM 문법을 지원하지만, Node.js는 기본적으로 여전히 next.config.ts를 CommonJS 파일로 간주하므로 module 문법이 감지되면 파일을 ESM으로 다시 parse하게 됩니다. 따라서 CommonJS 프로젝트에서는 ESM module임을 명시적으로 나타내기 위해 next.config.mts 파일을 사용하는 것을 권장합니다:

Although next.config.ts supports native ESM syntax in CommonJS projects, Node.js will still assume next.config.ts is a CommonJS file by default, resulting in Node.js reparsing the file as ESM when module syntax is detected. Therefore, we recommend using the next.config.mts file for CommonJS projects to explicitly indicate it's an ESM module:

TSnext.config.mts
import type { NextConfig } from 'next'

// Top-level await and dynamic import are supported
const flags = await import('./flags.js').then((m) => m.default ?? m)

const nextConfig: NextConfig = {
  /* config options here */
  typedRoutes: Boolean(flags?.typedRoutes),
}

export default nextConfig

For ESM ProjectsESM 프로젝트

package.json에서 "type"이 "module"로 설정되어 있으면 프로젝트는 ESM을 사용합니다. 이 설정에 대한 자세한 내용은 Node.js 문서를 참고하세요. 이 경우 next.config.ts를 ESM 문법으로 바로 작성할 수 있습니다.

When "type" is set to "module" in package.json, your project uses ESM. Learn more about this setting in the Node.js docs. In this case, you can write next.config.ts directly with ESM syntax.

Good to know

package.json에서 "type": "module"을 사용하면 프로젝트의 모든 .js와 .ts 파일이 기본적으로 ESM module로 취급됩니다. 필요하다면 CommonJS 문법을 사용하는 파일의 확장자를 .cjs 또는 .cts로 바꿔야 할 수 있습니다.

When using "type": "module" in your package.json, all .js and .ts files in your project are treated as ESM modules by default. You may need to rename files with CommonJS syntax to .cjs or .cts extensions if needed.

Statically Typed LinksStatically typed link

Next.js는 next/link를 사용할 때 오타나 기타 error를 방지하도록 link에 static type을 지정할 수 있어서, page 간 이동 시 type safety를 높여 줍니다.

Next.js can statically type links to prevent typos and other errors when using next/link, improving type safety when navigating between pages.

Pages Router와 App Router 모두에서 next/link의 href prop에 적용됩니다. App Router에서는 push, replace, prefetch 같은 next/navigation method에도 type이 지정됩니다. Pages Router의 next/router method에는 type이 지정되지 않습니다.

Works in both the Pages and App Router for the href prop in next/link. In the App Router, it also types next/navigation methods like push, replace, and prefetch. It does not type next/router methods in Pages Router.

literal href 문자열은 검증되며, literal이 아닌 href는 as Route로 cast해야 할 수 있습니다.

Literal href strings are validated, while non-literal hrefs may require a cast with as Route.

이 기능을 사용하려면(opt-in) typedRoutes를 활성화해야 하고, 프로젝트에서 TypeScript를 사용해야 합니다.

To opt-into this feature, typedRoutes needs to be enabled and the project needs to be using TypeScript.

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  typedRoutes: true,
}

export default nextConfig

Next.js는 애플리케이션에 존재하는 모든 route에 대한 정보를 담은 link 정의를 .next/types에 생성하며, TypeScript는 이를 이용해 editor에서 잘못된 link에 대한 피드백을 제공할 수 있습니다.

Next.js will generate a link definition in .next/types that contains information about all existing routes in your application, which TypeScript can then use to provide feedback in your editor about invalid links.

Good to know

create-next-app 없이 프로젝트를 설정했다면, tsconfig.json의 include 배열에 .next/types/**/*.ts를 추가해 생성된 Next.js type이 포함되도록 하세요:

If you set up your project without create-next-app, ensure the generated Next.js types are included by adding .next/types/**/*.ts to the include array in your tsconfig.json:

tsconfig.json
{
  "include": [
    "next-env.d.ts",
    ".next/types/**/*.ts",
    "**/*.ts",
    "**/*.tsx"
  ],
  "exclude": ["node_modules"]
}

현재는 dynamic segment를 포함한 모든 string literal을 지원합니다. literal이 아닌 문자열은 as Route로 직접 cast해야 합니다. 아래 예제는 next/link와 next/navigation 사용법을 모두 보여 줍니다:

Currently, support includes any string literal, including dynamic segments. For non-literal strings, you need to manually cast with as Route. The example below shows both next/link and next/navigation usage:

TSapp/example-client.tsx
'use client'

import type { Route } from 'next'
import Link from 'next/link'
import { useRouter } from 'next/navigation'

export default function Example() {
  const router = useRouter()
  const slug = 'nextjs'

  return (
    <>
      {/* Link: literal and dynamic */}
      <Link href="/about" />
      <Link href={`/blog/${slug}`} />
      <Link href={('/blog/' + slug) as Route} />
      {/* TypeScript error if href is not a valid route */}
      <Link href="/aboot" />

      {/* Router: literal and dynamic strings are validated */}
      <button onClick={() => router.push('/about')}>Push About</button>
      <button onClick={() => router.replace(`/blog/${slug}`)}>
        Replace Blog
      </button>
      <button onClick={() => router.prefetch('/contact')}>
        Prefetch Contact
      </button>

      {/* For non-literal strings, cast to Route */}
      <button onClick={() => router.push(('/blog/' + slug) as Route)}>
        Push Non-literal Blog
      </button>
    </>
  )
}

proxy에서 정의한 redirect route에도 똑같이 적용됩니다:

The same applies for redirecting routes defined by proxy:

TSproxy.ts
import { NextRequest, NextResponse } from 'next/server'

export function proxy(request: NextRequest) {
  if (request.nextUrl.pathname === '/proxy-redirect') {
    return NextResponse.redirect(new URL('/', request.url))
  }

  return NextResponse.next()
}
TSapp/some/page.tsx
import type { Route } from 'next'
import Link from 'next/link'

export default function Page() {
  return <Link href={'/proxy-redirect' as Route}>Link Text</Link>
}

next/link를 감싸는 custom component에서 href를 받으려면 generic을 사용하세요:

To accept href in a custom component wrapping next/link, use a generic:

import type { Route } from 'next'
import Link from 'next/link'

function Card<T extends string>({ href }: { href: Route<T> | URL }) {
  return (
    <Link href={href}>
      <div>My Card</div>
    </Link>
  )
}

간단한 데이터 구조에 type을 지정하고 순회하며 link를 render할 수도 있습니다:

You can also type a simple data structure and iterate to render links:

import type { Route } from 'next'

  label: string

]

그런 다음 item들을 map해서 Link를 render합니다:

Then, map over the items to render Links:

TScomponents/nav.tsx
import Link from 'next/link'
import { navItems } from './nav-items'

export function Nav() {
  return (
    <nav>
      {navItems.map((item) => (
        <Link key={item.href} href={item.href}>
          {item.label}
        </Link>
      ))}
    </nav>
  )
}

How does it work?

next typegen, next dev, next build를 실행하면 Next.js는 .next 안에 애플리케이션의 모든 기존 route 정보(Link의 href type으로 쓸 수 있는 모든 유효한 route)를 담은 숨겨진 .d.ts 파일을 생성합니다. 이 .d.ts 파일은 tsconfig.json에 포함되며, TypeScript compiler가 이 .d.ts를 확인해 editor에서 잘못된 link에 대한 피드백을 제공합니다.

How does it work?

When running, next typegen, next dev or next build, Next.js generates a hidden .d.ts file inside .next that contains information about all existing routes in your application (all valid routes as the href type of Link). This .d.ts file is included in tsconfig.json and the TypeScript compiler will check that .d.ts and provide feedback in your editor about invalid links.

Type IntelliSense for Environment VariablesEnvironment variable을 위한 type IntelliSense

development 중 Next.js는 editor의 IntelliSense를 위해, load된 environment variable 정보를 담은 .d.ts 파일을 .next/types에 생성합니다. 같은 environment variable key가 여러 파일에 정의되어 있으면 Environment Variable Load Order에 따라 중복이 제거됩니다.

During development, Next.js generates a .d.ts file in .next/types that contains information about the loaded environment variables for your editor's IntelliSense. If the same environment variable key is defined in multiple files, it is deduplicated according to the Environment Variable Load Order.

이 기능을 사용하려면(opt-in) experimental.typedEnv를 활성화해야 하고, 프로젝트에서 TypeScript를 사용해야 합니다.

To opt-into this feature, experimental.typedEnv needs to be enabled and the project needs to be using TypeScript.

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    typedEnv: true,
  },
}

export default nextConfig
Good to know

type은 development runtime에 load된 environment variable을 기준으로 생성되며, 기본적으로 .env.production* 파일의 variable은 제외됩니다. production 전용 variable을 포함하려면 NODE_ENV=production으로 next dev를 실행하세요.

Types are generated based on the environment variables loaded at development runtime, which excludes variables from .env.production* files by default. To include production-specific variables, run next dev with NODE_ENV=production.

Custom tsconfig pathCustom tsconfig 경로

경우에 따라 build나 tooling에 다른 TypeScript configuration을 사용하고 싶을 수 있습니다. 그렇게 하려면 next.config.ts에서 typescript.tsconfigPath를 설정해 Next.js가 다른 tsconfig 파일을 가리키도록 하세요.

In some cases, you might want to use a different TypeScript configuration for builds or tooling. To do that, set typescript.tsconfigPath in next.config.ts to point Next.js to another tsconfig file.

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  typescript: {
    tsconfigPath: 'tsconfig.build.json',
  },
}

export default nextConfig

예를 들어 production build에서는 다른 config로 전환할 수 있습니다:

For example, switch to a different config for production builds:

TSnext.config.ts
import type { NextConfig } from 'next'

const isProd = process.env.NODE_ENV === 'production'

const nextConfig: NextConfig = {
  typescript: {
    tsconfigPath: isProd ? 'tsconfig.build.json' : 'tsconfig.json',
  },
}

export default nextConfig
build용으로 별도의 tsconfig를 사용하는 이유

monorepo처럼 build가 프로젝트 기준에 맞지 않는 공유 dependency까지 검증하는 상황이나, 로컬에서는 더 엄격한 TypeScript 설정으로 migrate하면서(IDE에서는 여전히 잘못된 사용을 강조 표시하길 원하면서) CI에서는 check를 완화해 계속 배포하고 싶은 경우에 check를 완화해야 할 수 있습니다.

예를 들어 프로젝트는 useUnknownInCatchVariables를 사용하지만 일부 monorepo dependency가 여전히 any를 가정하는 경우:

tsconfig.build.json
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "useUnknownInCatchVariables": false
  }
}

이렇게 하면 tsconfig.json으로 editor는 엄격하게 유지하면서 production build는 완화된 설정을 사용할 수 있습니다.

Good to know
  • IDE는 보통 diagnostic과 IntelliSense를 위해 tsconfig.json을 읽으므로, production build가 대체 config를 사용하더라도 IDE warning은 계속 볼 수 있습니다. editor에서도 동일하게 맞추고 싶다면 중요한 option을 똑같이 반영하세요.
  • development에서는 tsconfig.json의 변경만 감시됩니다. typescript.tsconfigPath로 지정한 다른 이름의 파일을 수정했다면, 변경 사항을 적용하기 위해 dev server를 재시작하세요.
  • 설정한 파일은 next dev, next build, next typegen에서 사용됩니다.
  • IDEs typically read tsconfig.json for diagnostics and IntelliSense, so you can still see IDE warnings while production builds use the alternate config. Mirror critical options if you want parity in the editor.
  • In development, only tsconfig.json is watched for changes. If you edit a different file name via typescript.tsconfigPath, restart the dev server to apply changes.
  • The configured file is used in next dev, next build, and next typegen.

Disabling TypeScript errors in productionproduction에서 TypeScript error 비활성화하기

프로젝트에 TypeScript error가 있으면 Next.js는 production build(next build)를 실패시킵니다.

Next.js fails your production build (next build) when TypeScript errors are present in your project.

애플리케이션에 error가 있더라도 Next.js가 위험을 감수하고 production 코드를 만들어 내길 원한다면, 내장 type checking 단계를 비활성화할 수 있습니다.

If you'd like Next.js to dangerously produce production code even when your application has errors, you can disable the built-in type checking step.

비활성화한다면 build 또는 deploy 과정에서 반드시 type check를 실행하세요. 그렇지 않으면 매우 위험할 수 있습니다.

If disabled, be sure you are running type checks as part of your build or deploy process, otherwise this can be very dangerous.

next.config.ts를 열고 typescript config에서 ignoreBuildErrors option을 활성화하세요:

Open next.config.ts and enable the ignoreBuildErrors option in the typescript config:

TSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  typescript: {
    // !! WARN !!
    // Dangerously allow production builds to successfully complete even if
    // your project has type errors.
    // !! WARN !!
    ignoreBuildErrors: true,
  },
}

export default nextConfig
Good to know

build하기 전에 직접 tsc --noEmit을 실행해 TypeScript error를 확인할 수 있습니다. deploy 전에 TypeScript error를 확인하고 싶은 CI/CD pipeline에서 유용합니다.

You can run tsc --noEmit to check for TypeScript errors yourself before building. This is useful for CI/CD pipelines where you'd like to check for TypeScript errors before deploying.

Custom type declarationsCustom type 선언

custom type을 선언해야 할 때 next-env.d.ts를 수정하고 싶어질 수 있습니다. 하지만 이 파일은 자동으로 생성되므로 변경 사항은 덮어써집니다. 대신 새 파일(예: new-types.d.ts)을 만들고 tsconfig.json에서 참조해야 합니다:

When you need to declare custom types, you might be tempted to modify next-env.d.ts. However, this file is automatically generated, so any changes you make will be overwritten. Instead, you should create a new file, let's call it new-types.d.ts, and reference it in your tsconfig.json:

tsconfig.json
{
  "compilerOptions": {
    "skipLibCheck": true
    //...truncated...
  },
  "include": [
    "new-types.d.ts",
    "next-env.d.ts",
    ".next/types/**/*.ts",
    "**/*.ts",
    "**/*.tsx"
  ],
  "exclude": ["node_modules"]
}
