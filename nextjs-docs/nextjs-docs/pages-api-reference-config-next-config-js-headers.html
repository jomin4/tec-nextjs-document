headersheaders

header를 사용하면 특정 path로 들어오는 request에 대한 response에 custom HTTP header를 설정할 수 있습니다.

Headers allow you to set custom HTTP headers on the response to an incoming request on a given path.

custom HTTP header를 설정하려면 next.config.js에서 headers key를 사용하면 됩니다:

To set custom HTTP headers you can use the headers key in next.config.js:

JSnext.config.js
module.exports = {
  headers() {
    return [
      {
        source: '/about',
        headers: [
          {
            key: 'x-custom-header',
            value: 'my custom header value',
          },
          {
            key: 'x-another-custom-header',
            value: 'my other custom header value',
          },
        ],
      },
    ]
  },
}

headers는 동기 함수 또는 async 함수로 정의할 수 있습니다. 이 함수는 source와 headers property를 가진 object의 배열을 반환하거나, 그 배열로 resolve되어야 합니다:

headers can be defined as a synchronous or async function. It should return, or resolve to, an array of objects with source and headers properties:

  • source는 들어오는 request path pattern입니다.
  • headers는 key와 value property를 가진 response header object의 배열입니다.
  • basePath: false 또는 undefined - false이면 matching할 때 basePath가 포함되지 않습니다. external rewrite에만 사용할 수 있습니다.
  • locale: false 또는 undefined - matching할 때 locale을 포함하지 않을지 여부입니다.
  • has는 type, key, value property를 가진 has object의 배열입니다.
  • missing은 type, key, value property를 가진 missing object의 배열입니다.
  • source is the incoming request path pattern.
  • headers is an array of response header objects, with key and value properties.
  • basePath: false or undefined - if false the basePath won't be included when matching, can be used for external rewrites only.
  • locale: false or undefined - whether the locale should not be included when matching.
  • has is an array of has objects with the type, key and value properties.
  • missing is an array of missing objects with the type, key and value properties.

header는 page와 /public 파일을 포함하는 filesystem보다 먼저 검사됩니다.

Headers are checked before the filesystem which includes pages and /public files.

Header Overriding Behaviorheader override 동작

두 header가 같은 path에 match되고 같은 header key를 설정하면, 마지막 header key가 첫 번째 것을 override합니다. 아래 header를 사용하면 마지막으로 설정된 header 값이 world이므로 path /hello의 header x-hello는 world가 됩니다.

If two headers match the same path and set the same header key, the last header key will override the first. Using the below headers, the path /hello will result in the header x-hello being world due to the last header value set being world.

JSnext.config.js
module.exports = {
  headers() {
    return [
      {
        source: '/:path*',
        headers: [
          {
            key: 'x-hello',
            value: 'there',
          },
        ],
      },
      {
        source: '/hello',
        headers: [
          {
            key: 'x-hello',
            value: 'world',
          },
        ],
      },
    ]
  },
}

Path Matching

path match를 사용할 수 있습니다. 예를 들어 /blog/:slug는 /blog/first-post에 match됩니다(nested path는 제외):

Path matches are allowed, for example /blog/:slug will match /blog/first-post (no nested paths):

JSnext.config.js
module.exports = {
  headers() {
    return [
      {
        source: '/blog/:slug',
        headers: [
          {
            key: 'x-slug',
            value: ':slug', // Matched parameters can be used in the value
          },
          {
            key: 'x-slug-:slug', // Matched parameters can be used in the key
            value: 'my other custom header value',
          },
        ],
      },
    ]
  },
}

pattern /blog/:slug는 /blog/first-post와 /blog/post-1에는 match되지만 /blog/a/b 같은 nested path에는 match되지 않습니다. pattern은 시작 부분에 고정(anchored)되므로 /blog/:slug는 /archive/blog/first-post에 match되지 않습니다.

The pattern /blog/:slug matches /blog/first-post and /blog/post-1 but not a nested path like /blog/a/b. Patterns are anchored to the start, /blog/:slug will not match /archive/blog/first-post.

parameter에 modifier를 사용할 수 있습니다: *(0개 이상), +(1개 이상), ?(0개 또는 1개). 예를 들어 /blog/:slug*는 /blog, /blog/a, /blog/a/b/c에 match됩니다.

You can use modifiers on parameters: * (zero or more), + (one or more), ? (zero or one). For example, /blog/:slug* matches /blog, /blog/a, and /blog/a/b/c.

자세한 내용은 path-to-regexp 문서를 참고하세요.

Read more details on path-to-regexp documentation.

Wildcard Path Matching

wildcard path를 match하려면 parameter 뒤에 *를 사용하면 됩니다. 예를 들어 /blog/:slug*는 /blog/a/b/c/d/hello-world에 match됩니다:

To match a wildcard path you can use * after a parameter, for example /blog/:slug* will match /blog/a/b/c/d/hello-world:

JSnext.config.js
module.exports = {
  headers() {
    return [
      {
        source: '/blog/:slug*',
        headers: [
          {
            key: 'x-slug',
            value: ':slug*', // Matched parameters can be used in the value
          },
          {
            key: 'x-slug-:slug*', // Matched parameters can be used in the key
            value: 'my other custom header value',
          },
        ],
      },
    ]
  },
}

Regex Path Matching

regex path를 match하려면 parameter 뒤에 regex를 괄호로 감싸면 됩니다. 예를 들어 /blog/:slug(\\d{1,})는 /blog/123에는 match되지만 /blog/abc에는 match되지 않습니다:

To match a regex path you can wrap the regex in parenthesis after a parameter, for example /blog/:slug(\\d{1,}) will match /blog/123 but not /blog/abc:

JSnext.config.js
module.exports = {
  headers() {
    return [
      {
        source: '/blog/:post(\\d{1,})',
        headers: [
          {
            key: 'x-post',
            value: ':post',
          },
        ],
      },
    ]
  },
}

다음 문자 (, ), {, }, :, *, +, ?는 regex path matching에 사용되므로, source에서 특수 의미가 아닌 값으로 쓸 때는 앞에 \\를 붙여 escape해야 합니다:

The following characters (, ), {, }, :, *, +, ? are used for regex path matching, so when used in the source as non-special values they must be escaped by adding \\ before them:

JSnext.config.js
module.exports = {
  headers() {
    return [
      {
        // this will match `/english(default)/something` being requested
        source: '/english\\(default\\)/:slug',
        headers: [
          {
            key: 'x-header',
            value: 'value',
          },
        ],
      },
    ]
  },
}

Header, Cookie, and Query Matchingheader, cookie, query matching

header, cookie, query 값이 has 필드와 match되거나 missing 필드와 match되지 않을 때만 header를 적용하려면 이 필드들을 사용할 수 있습니다. header가 적용되려면 source와 모든 has 항목이 match되어야 하고, 모든 missing 항목은 match되지 않아야 합니다.

To only apply a header when header, cookie, or query values also match the has field or don't match the missing field can be used. Both the source and all has items must match and all missing items must not match for the header to be applied.

has와 missing 항목은 다음 필드를 가질 수 있습니다:

has and missing items can have the following fields:

  • type: String - header, cookie, host, query 중 하나여야 합니다.
  • key: String - 선택한 type에서 match할 key입니다.
  • value: String 또는 undefined - 확인할 값입니다. undefined이면 어떤 값이든 match됩니다. regex 형태의 문자열을 사용해 값의 특정 부분을 capture할 수 있습니다. 예를 들어 first-second에 대해 값 first-(?<paramName>.*)를 사용하면 destination에서 :paramName으로 second를 사용할 수 있습니다.
  • type: String - must be either header, cookie, host, or query.
  • key: String - the key from the selected type to match against.
  • value: String or undefined - the value to check for, if undefined any value will match. A regex like string can be used to capture a specific part of the value, e.g. if the value first-(?<paramName>.*) is used for first-second then second will be usable in the destination with :paramName.
JSnext.config.js
module.exports = {
  headers() {
    return [
      // if the header `x-add-header` is present,
      // the `x-another-header` header will be applied
      {
        source: '/:path*',
        has: [
          {
            type: 'header',
            key: 'x-add-header',
          },
        ],
        headers: [
          {
            key: 'x-another-header',
            value: 'hello',
          },
        ],
      },
      // if the header `x-no-header` is not present,
      // the `x-another-header` header will be applied
      {
        source: '/:path*',
        missing: [
          {
            type: 'header',
            key: 'x-no-header',
          },
        ],
        headers: [
          {
            key: 'x-another-header',
            value: 'hello',
          },
        ],
      },
      // if the source, query, and cookie are matched,
      // the `x-authorized` header will be applied
      {
        source: '/specific/:path*',
        has: [
          {
            type: 'query',
            key: 'page',
            // the page value will not be available in the
            // header key/values since value is provided and
            // doesn't use a named capture group e.g. (?<page>home)
            value: 'home',
          },
          {
            type: 'cookie',
            key: 'authorized',
            value: 'true',
          },
        ],
        headers: [
          {
            key: 'x-authorized',
            value: ':authorized',
          },
        ],
      },
      // if the header `x-authorized` is present and
      // contains a matching value, the `x-another-header` will be applied
      {
        source: '/:path*',
        has: [
          {
            type: 'header',
            key: 'x-authorized',
            value: '(?<authorized>yes|true)',
          },
        ],
        headers: [
          {
            key: 'x-another-header',
            value: ':authorized',
          },
        ],
      },
      // if the host is `example.com`,
      // this header will be applied
      {
        source: '/:path*',
        has: [
          {
            type: 'host',
            value: 'example.com',
          },
        ],
        headers: [
          {
            key: 'x-another-header',
            value: ':authorized',
          },
        ],
      },
    ]
  },
}

Headers with basePath supportbasePath 지원과 header

header와 함께 basePath 지원을 활용하면, header에 basePath: false를 추가하지 않는 한 각 source 앞에 basePath가 자동으로 붙습니다:

When leveraging basePath support with headers each source is automatically prefixed with the basePath unless you add basePath: false to the header:

JSnext.config.js
module.exports = {
  basePath: '/docs',

  headers() {
    return [
      {
        source: '/with-basePath', // becomes /docs/with-basePath
        headers: [
          {
            key: 'x-hello',
            value: 'world',
          },
        ],
      },
      {
        source: '/without-basePath', // is not modified since basePath: false is set
        headers: [
          {
            key: 'x-hello',
            value: 'world',
          },
        ],
        basePath: false,
      },
    ]
  },
}

Headers with i18n supporti18n 지원과 header

header와 함께 i18n 지원을 활용하면, header에 locale: false를 추가하지 않는 한 설정된 locales를 처리하도록 각 source 앞에 자동으로 prefix가 붙습니다. locale: false를 사용하면 올바르게 match되도록 source 앞에 locale을 직접 붙여야 합니다.

When leveraging i18n support with headers each source is automatically prefixed to handle the configured locales unless you add locale: false to the header. If locale: false is used you must prefix the source with a locale for it to be matched correctly.

JSnext.config.js
module.exports = {
  i18n: {
    locales: ['en', 'fr', 'de'],
    defaultLocale: 'en',
  },

  headers() {
    return [
      {
        source: '/with-locale', // automatically handles all locales
        headers: [
          {
            key: 'x-hello',
            value: 'world',
          },
        ],
      },
      {
        // does not handle locales automatically since locale: false is set
        source: '/nl/with-locale-manual',
        locale: false,
        headers: [
          {
            key: 'x-hello',
            value: 'world',
          },
        ],
      },
      {
        // this matches '/' since `en` is the defaultLocale
        source: '/en',
        locale: false,
        headers: [
          {
            key: 'x-hello',
            value: 'world',
          },
        ],
      },
      {
        // this gets converted to /(en|fr|de)/(.*) so will not match the top-level
        // `/` or `/fr` routes like /:path* would
        source: '/(.*)',
        headers: [
          {
            key: 'x-hello',
            value: 'world',
          },
        ],
      },
    ]
  },
}

Cache-Control

Next.js는 진짜로 변하지 않는(immutable) asset에 public, max-age=31536000, immutable 값의 Cache-Control header를 설정합니다. 이 값은 override할 수 없습니다. 이런 immutable 파일은 파일 이름에 SHA-hash가 포함되어 있어 무기한 안전하게 cache될 수 있습니다. 예를 들어 Static Image Import가 있습니다. 이런 asset에 대해서는 next.config.js에서 Cache-Control header를 설정할 수 없습니다.

Next.js sets the Cache-Control header of public, max-age=31536000, immutable for truly immutable assets. It cannot be overridden. These immutable files contain a SHA-hash in the file name, so they can be safely cached indefinitely. For example, Static Image Imports. You cannot set Cache-Control headers in next.config.js for these assets.

하지만 다른 response나 data에 대해서는 Cache-Control header를 설정할 수 있습니다.

However, you can set Cache-Control headers for other responses or data.

statically generated page의 cache를 revalidate해야 한다면, page의 getStaticProps 함수에서 revalidate prop을 설정하면 됩니다.

If you need to revalidate the cache of a page that has been statically generated, you can do so by setting the revalidate prop in the page's getStaticProps function.

API Route의 response를 cache하려면 res.setHeader를 사용할 수 있습니다:

To cache the response from an API Route, you can use res.setHeader:

TSJSpages/api/hello.ts
import type { NextApiRequest, NextApiResponse } from 'next'

type ResponseData = {
  message: string
}

export default function handler(
  req: NextApiRequest,
  res: NextApiResponse<ResponseData>
) {
  res.setHeader('Cache-Control', 's-maxage=86400')
  res.status(200).json({ message: 'Hello from Next.js!' })
}
export default function handler(req, res) {
  res.setHeader('Cache-Control', 's-maxage=86400')
  res.status(200).json({ message: 'Hello from Next.js!' })
}

getServerSideProps 안에서 caching header(Cache-Control)를 사용해 dynamic response를 cache할 수도 있습니다. 예를 들어 stale-while-revalidate를 사용할 수 있습니다.

You can also use caching headers (Cache-Control) inside getServerSideProps to cache dynamic responses. For example, using stale-while-revalidate.

TSJSpages/index.tsx
import { GetStaticProps, GetStaticPaths, GetServerSideProps } from 'next'

// This value is considered fresh for ten seconds (s-maxage=10).
// If a request is repeated within the next 10 seconds, the previously
// cached value will still be fresh. If the request is repeated before 59 seconds,
// the cached value will be stale but still render (stale-while-revalidate=59).
//
// In the background, a revalidation request will be made to populate the cache
// with a fresh value. If you refresh the page, you will see the new value.
export const getServerSideProps = (async (context) => {
  context.res.setHeader(
    'Cache-Control',
    'public, s-maxage=10, stale-while-revalidate=59'
  )

  return {
    props: {},
  }
}) satisfies GetServerSideProps
// This value is considered fresh for ten seconds (s-maxage=10).
// If a request is repeated within the next 10 seconds, the previously
// cached value will still be fresh. If the request is repeated before 59 seconds,
// the cached value will be stale but still render (stale-while-revalidate=59).
//
// In the background, a revalidation request will be made to populate the cache
// with a fresh value. If you refresh the page, you will see the new value.
export async function getServerSideProps({ req, res }) {
  res.setHeader(
    'Cache-Control',
    'public, s-maxage=10, stale-while-revalidate=59'
  )

  return {
    props: {},
  }
}

Options옵션

CORS

Cross-Origin Resource Sharing (CORS)는 어떤 사이트가 리소스에 접근할 수 있는지 제어하는 보안 기능입니다. Access-Control-Allow-Origin header를 설정해 특정 origin이 API Endpoints에 접근하도록 허용할 수 있습니다.

Cross-Origin Resource Sharing (CORS) is a security feature that allows you to control which sites can access your resources. You can set the Access-Control-Allow-Origin header to allow a specific origin to access your API Endpoints.

headers() {
    return [
      {
        source: "/api/:path*",
        headers: [
          {
            key: "Access-Control-Allow-Origin",
            value: "*", // Set your origin
          },
          {
            key: "Access-Control-Allow-Methods",
            value: "GET, POST, PUT, DELETE, OPTIONS",
          },
          {
            key: "Access-Control-Allow-Headers",
            value: "Content-Type, Authorization",
          },
        ],
      },
    ];
  },

X-DNS-Prefetch-Control

이 header는 DNS prefetching을 제어해, 브라우저가 외부 링크, 이미지, CSS, JavaScript 등에 대해 domain name resolution을 미리 수행할 수 있게 합니다. 이 prefetching은 background에서 수행되므로, 참조된 항목이 필요해질 즈음에는 DNS가 이미 resolve되어 있을 가능성이 높습니다. 이렇게 하면 사용자가 링크를 클릭할 때의 latency가 줄어듭니다.

This header controls DNS prefetching, allowing browsers to proactively perform domain name resolution on external links, images, CSS, JavaScript, and more. This prefetching is performed in the background, so the DNS is more likely to be resolved by the time the referenced items are needed. This reduces latency when the user clicks a link.

{
  key: 'X-DNS-Prefetch-Control',
  value: 'on'
}

Strict-Transport-Security

이 header는 브라우저에게 HTTP 대신 HTTPS로만 접근해야 한다고 알립니다. 아래 configuration을 사용하면 현재와 미래의 모든 subdomain이 2년의 max-age 동안 HTTPS를 사용합니다. 이렇게 하면 HTTP로만 serve될 수 있는 page나 subdomain에 대한 접근이 차단됩니다.

This header informs browsers it should only be accessed using HTTPS, instead of using HTTP. Using the configuration below, all present and future subdomains will use HTTPS for a max-age of 2 years. This blocks access to pages or subdomains that can only be served over HTTP.

{
  key: 'Strict-Transport-Security',
  value: 'max-age=63072000; includeSubDomains; preload'
}

X-Frame-Options

이 header는 사이트가 iframe 안에 표시되는 것을 허용할지 여부를 나타냅니다. 이를 통해 clickjacking 공격을 방지할 수 있습니다.

This header indicates whether the site should be allowed to be displayed within an iframe. This can prevent against clickjacking attacks.

이 header는 CSP의 frame-ancestors option으로 대체되었습니다. 이 option은 최신 브라우저에서 더 잘 지원됩니다(설정 방법은 Content Security Policy를 참고하세요).

This header has been superseded by CSP's frame-ancestors option, which has better support in modern browsers (see Content Security Policy for configuration details).

{
  key: 'X-Frame-Options',
  value: 'SAMEORIGIN'
}

Permissions-Policy

이 header를 사용하면 브라우저에서 어떤 기능과 API를 사용할 수 있는지 제어할 수 있습니다. 이전 이름은 Feature-Policy였습니다.

This header allows you to control which features and APIs can be used in the browser. It was previously named Feature-Policy.

{
  key: 'Permissions-Policy',
  value: 'camera=(), microphone=(), geolocation=(), browsing-topics=()'
}

X-Content-Type-Options

이 header는 Content-Type header가 명시적으로 설정되지 않았을 때 브라우저가 콘텐츠의 type을 추측하지 못하게 합니다. 이를 통해 사용자가 파일을 업로드하고 공유할 수 있는 웹사이트에서 XSS exploit을 방지할 수 있습니다.

This header prevents the browser from attempting to guess the type of content if the Content-Type header is not explicitly set. This can prevent XSS exploits for websites that allow users to upload and share files.

예를 들어 사용자가 이미지를 다운로드하려 하는데, 그 이미지가 실행 파일처럼 다른 Content-Type으로 처리되면 악의적일 수 있습니다. 이 header는 브라우저 extension 다운로드에도 적용됩니다. 이 header의 유일한 유효 값은 nosniff입니다.

For example, a user trying to download an image, but having it treated as a different Content-Type like an executable, which could be malicious. This header also applies to downloading browser extensions. The only valid value for this header is nosniff.

{
  key: 'X-Content-Type-Options',
  value: 'nosniff'
}

Referrer-Policy

이 header는 현재 웹사이트(origin)에서 다른 곳으로 이동할 때 브라우저가 얼마나 많은 정보를 포함할지 제어합니다.

This header controls how much information the browser includes when navigating from the current website (origin) to another.

{
  key: 'Referrer-Policy',
  value: 'origin-when-cross-origin'
}
