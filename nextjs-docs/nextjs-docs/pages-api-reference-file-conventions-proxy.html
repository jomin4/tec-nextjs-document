Proxyproxy.js

Note

middleware file convention은 deprecated되었으며 proxy로 이름이 바뀌었습니다. 자세한 내용은 Migration to Proxy를 참고하세요.

The middleware file convention is deprecated and has been renamed to proxy. See Migration to Proxy for more details.

proxy.js|ts 파일은 Proxy를 작성해 request가 완료되기 전에 서버에서 코드를 실행하는 데 사용합니다. 그런 다음 들어오는 request를 기반으로 rewrite, redirect, request 또는 response header 수정, 직접 응답하기 등의 방식으로 response를 변경할 수 있습니다.

The proxy.js|ts file is used to write Proxy and run code on the server before a request is completed. Then, based on the incoming request, you can modify the response by rewriting, redirecting, modifying the request or response headers, or responding directly.

Proxy는 route가 rendering되기 전에 실행됩니다. 인증(authentication), 로깅, redirect 처리 같은 custom server-side 로직을 구현할 때 특히 유용합니다.

Proxy executes before routes are rendered. It's particularly useful for implementing custom server-side logic like authentication, logging, or handling redirects.

Good to know

Proxy는 rendering 코드와 별도로 호출되도록 설계되었고, 최적화된 경우 빠른 redirect/rewrite 처리를 위해 CDN에 deploy되므로, 공유 module이나 global에 의존하려고 해서는 안 됩니다.

Proxy에서 애플리케이션으로 정보를 전달하려면 headers, cookies, rewrites, redirects 또는 URL을 사용하세요.

Proxy is meant to be invoked separately of your render code and in optimized cases deployed to your CDN for fast redirect/rewrite handling, you should not attempt relying on shared modules or globals.

To pass information from Proxy to your application, use headers, cookies, rewrites, redirects, or the URL.

프로젝트 루트(해당하는 경우 src 안)에 proxy.ts(또는 .js) 파일을 만들어 pages나 app과 같은 레벨에 위치하도록 하세요.

Create a proxy.ts (or .js) file in the project root, or inside src if applicable, so that it is located at the same level as pages or app.

pageExtensions를 예를 들어 .page.ts나 .page.js로 customize했다면, 파일 이름도 그에 맞게 proxy.page.ts 또는 proxy.page.js로 지정하세요.

If you’ve customized pageExtensions, for example to .page.ts or .page.js, name your file proxy.page.ts or proxy.page.js accordingly.

TSJSproxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

// This function can be marked `async` if using `await` inside
export function proxy(request: NextRequest) {
  return NextResponse.redirect(new URL('/home', request.url))
}

export const config = {
  matcher: '/about/:path*',
}

Exports

Proxy functionProxy 함수

파일은 default export 또는 proxy라는 이름의 named export로 단 하나의 함수를 export해야 합니다. 같은 파일에서 여러 proxy를 export하는 것은 지원되지 않습니다.

The file must export a single function, either as a default export or named proxy. Note that multiple proxy from the same file are not supported.

JSproxy.js
// Example of default export
export default function proxy(request) {
  // Proxy logic
}

Config object (optional)Config 객체 (선택)

선택적으로 Proxy 함수와 함께 config 객체를 export할 수 있습니다. 이 객체에는 Proxy가 적용될 경로를 지정하는 matcher가 포함됩니다.

Optionally, a config object can be exported alongside the Proxy function. This object includes the matcher to specify paths where the Proxy applies.

Matcher

matcher option을 사용하면 Proxy가 실행될 특정 경로를 target으로 지정할 수 있습니다.

The matcher option allows you to target specific paths for the Proxy to run on.

matcher가 없으면 Proxy는 static 파일(_next/static), 이미지 최적화(_next/image), public/ 폴더의 asset을 포함한 모든 request에서 실행됩니다. 이 경로들을 제외하려면 negative match pattern 사용을 고려하세요. 그렇지 않으면 인증 로직이나 redirect가 의도치 않게 CSS, JS, 이미지 로딩을 막을 수 있습니다.

Without a matcher, Proxy runs on every request, including static files (_next/static), image optimizations (_next/image), and assets in the public/ folder. Consider using a negative match pattern to exclude these paths, otherwise auth logic or redirects can unintentionally block CSS, JS, or images from loading.

경로는 여러 방식으로 지정할 수 있습니다:

You can specify paths in several ways:

  • 단일 경로: '/about'처럼 문자열을 직접 사용해 경로를 정의합니다.
  • 여러 경로: matcher: ['/about', '/contact']처럼 배열로 여러 경로를 나열하면 /about과 /contact 모두에 Proxy가 적용됩니다.
  • For a single path: Directly use a string to define the path, like '/about'.
  • For multiple paths: Use an array to list multiple paths, such as matcher: ['/about', '/contact'], which applies the Proxy to both /about and /contact.
JSproxy.js
export const config = {
  matcher: ['/about/:path*', '/dashboard/:path*'],
}

또한 matcher option은 정규 표현식(regular expression)을 사용한 복잡한 경로 지정도 지원합니다. 예를 들어 정규 표현식 matcher로 특정 경로를 제외할 수 있습니다:

Additionally, the matcher option supports complex path specifications using regular expressions. For example, you can exclude certain paths with a regular expression matcher:

JSproxy.js
export const config = {
  matcher: [
    // Exclude API routes, static files, image optimizations, and .png files
    '/((?!api|_next/static|_next/image|.*\\.png$).*)',
  ],
}

이를 통해 포함하거나 제외할 경로를 정밀하게 제어할 수 있습니다.

This enables precise control over which paths to include or exclude.

matcher option은 다음 key를 가진 객체의 배열도 받습니다:

The matcher option accepts an array of objects with the following keys:

  • source: request 경로를 매칭하는 데 사용하는 경로 또는 패턴입니다. 직접 경로 매칭을 위한 문자열이거나 더 복잡한 매칭을 위한 패턴일 수 있습니다.
  • locale (선택): false로 설정하면 경로 매칭에서 locale 기반 routing을 무시하는 boolean입니다.
  • has (선택): header, query parameter, cookie 같은 특정 request 요소의 존재 여부에 따른 조건을 지정합니다.
  • missing (선택): header나 cookie가 없는 경우처럼 특정 request 요소가 없는 조건에 초점을 맞춥니다.
  • source: The path or pattern used to match the request paths. It can be a string for direct path matching or a pattern for more complex matching.
  • locale (optional): A boolean that, when set to false, ignores locale-based routing in path matching.
  • has (optional): Specifies conditions based on the presence of specific request elements such as headers, query parameters, or cookies.
  • missing (optional): Focuses on conditions where certain request elements are absent, like missing headers or cookies.
JSproxy.js
export const config = {
  matcher: [
    {
      source: '/api/:path*',
      locale: false,
      has: [
        { type: 'header', key: 'Authorization', value: 'Bearer Token' },
        { type: 'query', key: 'userId', value: '123' },
      ],
      missing: [{ type: 'cookie', key: 'session', value: 'active' }],
    },
  ],
}

source 경로 패턴은:

The source path patterns:

  1. 반드시 /로 시작해야 합니다
  2. named parameter를 포함할 수 있습니다: /about/:path는 /about/a, /about/b와 매칭되지만 /about/a/c와는 매칭되지 않습니다
  3. named parameter(:로 시작)에 modifier를 붙일 수 있습니다: *는 0개 이상 이므로 /about/:path*는 /about/a/b/c와 매칭됩니다. ?는 0개 또는 1개, +는 1개 이상 입니다
  4. 괄호로 감싼 정규 표현식을 사용할 수 있습니다: /about/(.*)는 /about/:path*와 같습니다
  5. 경로의 시작 부분에 고정(anchor)됩니다: /about은 /about, /about/team과 매칭되지만 /blog/about과는 매칭되지 않습니다
  1. MUST start with /
  2. Can include named parameters: /about/:path matches /about/a and /about/b but not /about/a/c
  3. Can have modifiers on named parameters (starting with :): /about/:path* matches /about/a/b/c because * is zero or more. ? is zero or one and + one or more
  4. Can use regular expression enclosed in parenthesis: /about/(.*) is the same as /about/:path*
  5. Are anchored to the start of the path: /about matches /about and /about/team but not /blog/about

자세한 내용은 path-to-regexp 문서를 참고하세요.

Read more details on path-to-regexp documentation.

Good to know
  • matcher 값은 build 시점에 정적으로 분석될 수 있도록 상수여야 합니다. 변수 같은 동적 값은 무시됩니다.
  • 하위 호환성을 위해 Next.js는 항상 /public을 /public/index로 간주합니다. 따라서 /public/:path matcher는 매칭됩니다.
  • The matcher values need to be constants so they can be statically analyzed at build-time. Dynamic values such as variables will be ignored.
  • For backward compatibility, Next.js always considers /public as /public/index. Therefore, a matcher of /public/:path will match.

Params

Next.js는 Proxy 함수를 request와 event 두 개의 인자로 이 순서대로 호출합니다. 사용하는 것만 선언하세요.

Next.js calls the Proxy function with two arguments, request and event, in that order. Declare only the ones you use.

request

첫 번째 parameter는 들어오는 HTTP request를 나타내는 NextRequest의 instance입니다.

The first parameter is an instance of NextRequest, which represents the incoming HTTP request.

TSJSproxy.ts
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  // Proxy logic goes here
}
export function proxy(request) {
  // Proxy logic goes here
}

event

두 번째 parameter는 NextFetchEvent의 instance입니다. 이 객체는 waitUntil(promise)라는 단 하나의 method를 제공하며, promise가 settle될 때까지 Proxy 호출을 유지하므로 로깅이나 analytics 같은 background 작업이 response가 전송된 뒤에도 완료될 수 있습니다. 전체 예시는 waitUntil and NextFetchEvent를 참고하세요.

The second parameter is an instance of NextFetchEvent. It exposes a single method, waitUntil(promise), which keeps the Proxy invocation alive until the promise settles, so background work like logging or analytics can finish after the response is sent. See waitUntil and NextFetchEvent for a full example.

TSJSproxy.ts
import type { NextFetchEvent, NextRequest } from 'next/server'

export function proxy(request: NextRequest, event: NextFetchEvent) {
  event.waitUntil(
    fetch('https://example.com/log', {
      method: 'POST',
      body: JSON.stringify({ pathname: request.nextUrl.pathname }),
    })
  )
}
export function proxy(request, event) {
  event.waitUntil(
    fetch('https://example.com/log', {
      method: 'POST',
      body: JSON.stringify({ pathname: request.nextUrl.pathname }),
    })
  )
}

NextProxy type

간결한 표현을 선호한다면 NextProxy type을 사용할 수 있습니다. 이 type은 request(NextRequest)와 event(NextFetchEvent) 모두의 parameter type을 자동으로 추론합니다:

If you prefer a shorthand, you can use the NextProxy type. It infers the parameter types for both request (NextRequest) and event (NextFetchEvent) automatically:

TSproxy.ts
import type { NextProxy } from 'next/server'

export const proxy: NextProxy = (request, event) => {
  event.waitUntil(Promise.resolve())
  return Response.json({ pathname: request.nextUrl.pathname })
}
Good to know
  • NextRequest는 Next.js Proxy에서 들어오는 HTTP request를 나타내는 type이고, NextResponse는 HTTP response를 조작하고 돌려보내는 데 사용하는 class입니다.
  • NextRequest is a type that represents incoming HTTP requests in Next.js Proxy, whereas NextResponse is a class used to manipulate and send back HTTP responses.

NextResponse

NextResponse API로 다음을 할 수 있습니다:

The NextResponse API allows you to:

  • 들어오는 request를 다른 URL로 redirect
  • 주어진 URL을 표시하도록 response를 rewrite
  • API Routes, getServerSideProps, rewrite destination을 위한 request header 설정
  • response cookie 설정
  • response header 설정
  • redirect the incoming request to a different URL
  • rewrite the response by displaying a given URL
  • Set request headers for API Routes, getServerSideProps, and rewrite destinations
  • Set response cookies
  • Set response headers

Proxy에서 response를 생성하려면 다음을 할 수 있습니다:

To produce a response from Proxy, you can:

  1. response를 생성하는 route(Page 또는 Edge API Route)로 rewrite
  2. NextResponse를 직접 return. Producing a Response를 참고하세요
  1. rewrite to a route (Page or Edge API Route) that produces a response

Execution order실행 순서

Proxy는 프로젝트의 모든 route에 대해 호출됩니다. 따라서 matchers를 사용해 특정 route를 정확히 target하거나 제외하는 것이 매우 중요합니다. 실행 순서는 다음과 같습니다:

Proxy will be invoked for every route in your project. Given this, it's crucial to use matchers to precisely target or exclude specific routes. The following is the execution order:

  1. next.config.js의 headers
  2. next.config.js의 redirects
  3. Proxy (rewrites, redirects 등)
  4. next.config.js의 beforeFiles (rewrites)
  5. Filesystem route (public/, _next/static/, pages/, app/ 등)
  6. next.config.js의 afterFiles (rewrites)
  7. Dynamic Routes (/blog/[slug])
  8. next.config.js의 fallback (rewrites)
  1. headers from next.config.js
  2. redirects from next.config.js
  3. Proxy (rewrites, redirects, etc.)
  4. beforeFiles (rewrites) from next.config.js
  5. Filesystem routes (public/, _next/static/, pages/, app/, etc.)
  6. afterFiles (rewrites) from next.config.js
  7. Dynamic Routes (/blog/[slug])
  8. fallback (rewrites) from next.config.js
Good to know

Server Functions는 이 체인에서 별도의 route가 아닙니다. Server Function은 사용되는 route로의 POST request로 처리되므로, 어떤 경로를 제외하는 Proxy matcher는 그 경로의 Server Function 호출도 건너뜁니다.

matcher 변경이나 Server Function을 다른 route로 옮기는 리팩터링으로 인해 Proxy 적용 범위가 조용히 사라질 수 있습니다. Proxy에만 의존하지 말고 항상 각 Server Function 내부에서 authentication과 authorization을 검증하세요. 권장 패턴은 Data Security guide를 참고하세요.

Server Functions are not separate routes in this chain. They are handled as POST requests to the route where they are used, so a Proxy matcher that excludes a path will also skip Server Function calls on that path.

A matcher change or a refactor that moves a Server Function to a different route can silently remove Proxy coverage. Always verify authentication and authorization inside each Server Function rather than relying on Proxy alone. See the Data Security guide for recommended patterns.

Runtime

Proxy는 기본적으로 Node.js runtime을 사용합니다. runtime config option은 Proxy 파일에서 사용할 수 없습니다. Proxy에서 runtime config option을 설정하면 error가 발생합니다.

Proxy defaults to using the Node.js runtime. The runtime config option is not available in Proxy files. Setting the runtime config option in Proxy will throw an error.

Advanced Proxy flags고급 Proxy flag

Next.js v13.1에서 고급 use case를 처리하기 위해 proxy용 flag 두 개, skipProxyUrlNormalize(이전 이름 skipMiddlewareUrlNormalize)와 skipTrailingSlashRedirect가 도입되었습니다.

In v13.1 of Next.js two additional flags were introduced for proxy, skipProxyUrlNormalize (formerly skipMiddlewareUrlNormalize) and skipTrailingSlashRedirect to handle advanced use cases.

skipTrailingSlashRedirect는 trailing slash를 추가하거나 제거하는 Next.js redirect를 비활성화합니다. 이를 통해 proxy 내부에서 custom 처리를 하여 일부 경로에서는 trailing slash를 유지하고 다른 경로에서는 유지하지 않을 수 있어, 점진적인 migration을 더 쉽게 만들 수 있습니다.

skipTrailingSlashRedirect disables Next.js redirects for adding or removing trailing slashes. This allows custom handling inside proxy to maintain the trailing slash for some paths but not others, which can make incremental migrations easier.

JSnext.config.js
module.exports = {
  skipTrailingSlashRedirect: true,
}
JSproxy.js
const legacyPrefixes = ['/docs', '/blog']

export default async function proxy(req) {
  const { pathname } = req.nextUrl

  if (legacyPrefixes.some((prefix) => pathname.startsWith(prefix))) {
    return NextResponse.next()
  }

  // apply trailing slash handling
  if (
    !pathname.endsWith('/') &&
    !pathname.match(/((?!\.well-known(?:\/.*)?)(?:[^/]+\/)*[^/]+\.\w+)/)
  ) {
    return NextResponse.redirect(
      new URL(`${req.nextUrl.pathname}/`, req.nextUrl)
    )
  }
}

skipProxyUrlNormalize는 Next.js의 URL 정규화(normalization)를 비활성화하여 직접 방문과 client 전환(client-transition)을 동일하게 처리할 수 있게 합니다. 일부 고급 사례에서 이 option은 원래 URL을 사용해 완전한 제어권을 제공합니다.

skipProxyUrlNormalize allows for disabling the URL normalization in Next.js to make handling direct visits and client-transitions the same. In some advanced cases, this option provides full control by using the original URL.

JSnext.config.js
module.exports = {
  skipProxyUrlNormalize: true,
}
JSproxy.js
export default async function proxy(req) {
  const { pathname } = req.nextUrl

  // GET /_next/data/build-id/hello.json

  console.log(pathname)
  // with the flag this now /_next/data/build-id/hello.json
  // without the flag this would be normalized to /hello
}

Using CookiesCookie 사용하기

Cookie는 일반 header입니다. Request에서는 Cookie header에, Response에서는 Set-Cookie header에 저장됩니다. Next.js는 NextRequest와 NextResponse의 cookies extension을 통해 이 cookie에 편리하게 접근하고 조작하는 방법을 제공합니다.

Cookies are regular headers. On a Request, they are stored in the Cookie header. On a Response they are in the Set-Cookie header. Next.js provides a convenient way to access and manipulate these cookies through the cookies extension on NextRequest and NextResponse.

  1. 들어오는 request의 경우 cookies는 get, getAll, set, delete method를 제공합니다. has로 cookie 존재 여부를 확인하거나 clear로 모든 cookie를 제거할 수 있습니다.
  2. 나가는 response의 경우 cookies는 get, getAll, set, delete method를 제공합니다.
  1. For incoming requests, cookies comes with the following methods: get, getAll, set, and delete cookies. You can check for the existence of a cookie with has or remove all cookies with clear.
  2. For outgoing responses, cookies have the following methods get, getAll, set, and delete.
TSJSproxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  // Assume a "Cookie:nextjs=fast" header to be present on the incoming request
  // Getting cookies from the request using the `RequestCookies` API
  let cookie = request.cookies.get('nextjs')
  console.log(cookie) // => { name: 'nextjs', value: 'fast', Path: '/' }
  const allCookies = request.cookies.getAll()
  console.log(allCookies) // => [{ name: 'nextjs', value: 'fast' }]

  request.cookies.has('nextjs') // => true
  request.cookies.delete('nextjs')
  request.cookies.has('nextjs') // => false

  // Setting cookies on the response using the `ResponseCookies` API
  const response = NextResponse.next()
  response.cookies.set('vercel', 'fast')
  response.cookies.set({
    name: 'vercel',
    value: 'fast',
    path: '/',
  })
  cookie = response.cookies.get('vercel')
  console.log(cookie) // => { name: 'vercel', value: 'fast', Path: '/' }
  // The outgoing response will have a `Set-Cookie:vercel=fast;path=/` header.

  return response
}

Setting HeadersHeader 설정하기

NextResponse API를 사용해 request header와 response header를 설정할 수 있습니다(request header 설정은 Next.js v13.0.0부터 가능).

You can set request and response headers using the NextResponse API (setting request headers is available since Next.js v13.0.0).

TSJSproxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  // Clone the request headers and set a new header `x-hello-from-proxy1`
  const requestHeaders = new Headers(request.headers)
  requestHeaders.set('x-hello-from-proxy1', 'hello')

  // You can also set request headers in NextResponse.next
  const response = NextResponse.next({
    request: {
      // New request headers
      headers: requestHeaders,
    },
  })

  // Set a new response header `x-hello-from-proxy2`
  response.headers.set('x-hello-from-proxy2', 'hello')
  return response
}
import { NextResponse } from 'next/server'

export function proxy(request) {
  // Clone the request headers and set a new header `x-hello-from-proxy1`
  const requestHeaders = new Headers(request.headers)
  requestHeaders.set('x-hello-from-proxy1', 'hello')

  // You can also set request headers in NextResponse.next
  const response = NextResponse.next({
    request: {
      // New request headers
      headers: requestHeaders,
    },
  })

  // Set a new response header `x-hello-from-proxy2`
  response.headers.set('x-hello-from-proxy2', 'hello')
  return response
}

이 snippet에서는 다음을 사용한다는 점에 유의하세요:

Note that the snippet uses:

  • requestHeaders를 upstream에서 사용할 수 있게 하는 NextResponse.next({ request: { headers: requestHeaders } })
  • requestHeaders를 client가 사용할 수 있게 하는 NextResponse.next({ headers: requestHeaders })는 사용하지 않음
  • NextResponse.next({ request: { headers: requestHeaders } }) to make requestHeaders available upstream
  • NOT NextResponse.next({ headers: requestHeaders }) which makes requestHeaders available to clients

자세한 내용은 NextResponse headers in Proxy를 참고하세요.

Learn more in NextResponse headers in Proxy.

Good to know

backend web server 설정에 따라 431 Request Header Fields Too Large error가 발생할 수 있으므로 큰 header를 설정하지 마세요.

Avoid setting large headers as it might cause 431 Request Header Fields Too Large error depending on your backend web server configuration.

RSC requests and rewritesRSC request와 rewrite

RSC request 중에 Next.js는 Proxy의 request instance에서 내부 Flight header를 제거합니다. 예를 들어 rsc, next-router-state-tree, next-router-prefetch 같은 header는 request.headers를 통해 노출되지 않습니다. 이는 RSC request와 HTML request가 서로 일치해야 하므로, RSC request를 HTML request와 다르게 실수로 처리하는 것을 방지하기 위함입니다.

During RSC requests, Next.js strips internal Flight headers from the request instance in Proxy. For example, headers like rsc, next-router-state-tree, and next-router-prefetch are not exposed through request.headers. This is to prevent accidentally handling an RSC request differently than the HTML request as both need to align.

NextResponse.rewrite()를 사용하면 Next.js가 필요한 RSC rewrite header를 upstream으로 자동 전파합니다.

When you use NextResponse.rewrite(), Next.js automatically propagates the required RSC rewrite headers upstream.

NextResponse.rewrite() 대신 fetch()로 custom rewrite 로직을 구현하면, RSC header를 직접 전달(forward)하지 않는 한 RSC header가 누락되는 문제를 겪을 수 있습니다.

If you implement custom rewrite logic with fetch() instead of NextResponse.rewrite(), you can run into missing RSC headers unless you forward them manually.

custom fetch rewrite 구성에서는 next.config.js에서 skipProxyUrlNormalize를 활성화하여 rewrite 로직이 제공된 request 객체로부터 필요한 URL 형태와 RSC header를 받을 수 있게 할 수도 있습니다:

For custom fetch rewrite setups, you can also enable skipProxyUrlNormalize in next.config.js so your rewrite logic can receive the necessary URL shape and RSC headers from the provided request object:

JSnext.config.js
module.exports = {
  skipProxyUrlNormalize: true,
}

CORS

Proxy에서 CORS header를 설정해 simple request와 preflighted request를 포함한 cross-origin request를 허용할 수 있습니다.

You can set CORS headers in Proxy to allow cross-origin requests, including simple and preflighted requests.

TSJSproxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

const allowedOrigins = ['https://acme.com', 'https://my-app.org']

const corsOptions = {
  'Access-Control-Allow-Methods': 'GET, POST, PUT, DELETE, OPTIONS',
  'Access-Control-Allow-Headers': 'Content-Type, Authorization',
}

export function proxy(request: NextRequest) {
  // Check the origin from the request
  const origin = request.headers.get('origin') ?? ''
  const isAllowedOrigin = allowedOrigins.includes(origin)

  // Handle preflighted requests
  const isPreflight = request.method === 'OPTIONS'

  if (isPreflight) {
    const preflightHeaders = {
      ...(isAllowedOrigin && { 'Access-Control-Allow-Origin': origin }),
      ...corsOptions,
    }
    return NextResponse.json({}, { headers: preflightHeaders })
  }

  // Handle simple requests
  const response = NextResponse.next()

  if (isAllowedOrigin) {
    response.headers.set('Access-Control-Allow-Origin', origin)
  }

  Object.entries(corsOptions).forEach(([key, value]) => {
    response.headers.set(key, value)
  })

  return response
}

export const config = {
  matcher: '/api/:path*',
}

Producing a responseResponse 생성하기

Response 또는 NextResponse instance를 return하여 Proxy에서 직접 응답할 수 있습니다. (이 기능은 Next.js v13.1.0부터 사용할 수 있습니다)

You can respond from Proxy directly by returning a Response or NextResponse instance. (This is available since Next.js v13.1.0)

TSJSproxy.ts
import type { NextRequest } from 'next/server'
import { isAuthenticated } from '@lib/auth'

// Limit the proxy to paths starting with `/api/`
export const config = {
  matcher: '/api/:function*',
}

export function proxy(request: NextRequest) {
  // Call our authentication function to check the request
  if (!isAuthenticated(request)) {
    // Respond with JSON indicating an error message
    return Response.json(
      { success: false, message: 'authentication failed' },
      { status: 401 }
    )
  }
}

Negative matching

matcher config는 완전한 정규 표현식을 지원하므로 negative lookahead나 문자 매칭 같은 매칭이 가능합니다. 특정 경로를 제외한 모든 경로와 매칭하는 negative lookahead 예시는 다음과 같습니다:

The matcher config allows full regex so matching like negative lookaheads or character matching is supported. An example of a negative lookahead to match all except specific paths can be seen here:

JSproxy.js
export const config = {
  matcher: [
    /*
     * Match all request paths except for the ones starting with:
     * - api (API routes)
     * - _next/static (static files)
     * - _next/image (image optimization files)
     * - favicon.ico, sitemap.xml, robots.txt (metadata files)
     */
    '/((?!api|_next/static|_next/image|favicon.ico|sitemap.xml|robots.txt).*)',
  ],
}

missing 또는 has 배열, 혹은 둘의 조합을 사용해 특정 request에 대해 Proxy를 우회할 수도 있습니다:

You can also bypass Proxy for certain requests by using the missing or has arrays, or a combination of both:

JSproxy.js
export const config = {
  matcher: [
    /*
     * Match all request paths except for the ones starting with:
     * - api (API routes)
     * - _next/static (static files)
     * - _next/image (image optimization files)
     * - favicon.ico, sitemap.xml, robots.txt (metadata files)
     */
    {
      source:
        '/((?!api|_next/static|_next/image|favicon.ico|sitemap.xml|robots.txt).*)',
      missing: [
        { type: 'header', key: 'next-router-prefetch' },
        { type: 'header', key: 'purpose', value: 'prefetch' },
      ],
    },

    {
      source:
        '/((?!api|_next/static|_next/image|favicon.ico|sitemap.xml|robots.txt).*)',
      has: [
        { type: 'header', key: 'next-router-prefetch' },
        { type: 'header', key: 'purpose', value: 'prefetch' },
      ],
    },

    {
      source:
        '/((?!api|_next/static|_next/image|favicon.ico|sitemap.xml|robots.txt).*)',
      has: [{ type: 'header', key: 'x-present' }],
      missing: [{ type: 'header', key: 'x-missing', value: 'prefetch' }],
    },
  ],
}
Good to know

negative matcher 패턴에서 _next/data를 제외하더라도 _next/data route에 대해서는 proxy가 여전히 호출됩니다. 이는 page는 보호했지만 대응하는 data route 보호를 잊어버리는 실수로 인한 보안 문제를 방지하기 위한 의도된 동작입니다.

Even when _next/data is excluded in a negative matcher pattern, proxy will still be invoked for _next/data routes. This is intentional behavior to prevent accidental security issues where you might protect a page but forget to protect the corresponding data route.

JSproxy.js
export const config = {
  matcher:
    '/((?!api|_next/data|_next/static|_next/image|favicon.ico|sitemap.xml|robots.txt).*)',
}

// Proxy will still run for /_next/data/* routes despite being excluded

waitUntil and NextFetchEvent

NextFetchEvent 객체는 native FetchEvent 객체를 확장하며 waitUntil() method를 포함합니다.

The NextFetchEvent object extends the native FetchEvent object, and includes the waitUntil() method.

waitUntil() method는 promise를 인자로 받아 promise가 settle될 때까지 Proxy의 수명을 연장합니다. background에서 작업을 수행할 때 유용합니다.

The waitUntil() method takes a promise as an argument, and extends the lifetime of the Proxy until the promise settles. This is useful for performing work in the background.

TSproxy.ts
import { NextResponse } from 'next/server'
import type { NextFetchEvent, NextRequest } from 'next/server'

export function proxy(req: NextRequest, event: NextFetchEvent) {
  event.waitUntil(
    fetch('https://my-analytics-platform.com', {
      method: 'POST',
      body: JSON.stringify({ pathname: req.nextUrl.pathname }),
    })
  )

  return NextResponse.next()
}

Unit testing (experimental)Unit testing (실험적)

Next.js 15.1부터 next/experimental/testing/server package에는 proxy 파일의 unit test를 돕는 유틸리티가 포함되어 있습니다. proxy를 unit test하면 코드가 production에 도달하기 전에 proxy가 원하는 경로에서만 실행되고 custom routing 로직이 의도대로 동작하는지 확인하는 데 도움이 됩니다.

Starting in Next.js 15.1, the next/experimental/testing/server package contains utilities to help unit test proxy files. Unit testing proxy can help ensure that it's only run on desired paths and that custom routing logic works as intended before code reaches production.

unstable_doesMiddlewareMatch 함수는 주어진 URL, header, cookie에 대해 proxy가 실행될지 assert하는 데 사용할 수 있습니다.

The unstable_doesMiddlewareMatch function can be used to assert whether proxy will run for the provided URL, headers, and cookies.

import { unstable_doesMiddlewareMatch } from 'next/experimental/testing/server'

expect(
  unstable_doesMiddlewareMatch({
    config,
    nextConfig,
    url: '/test',
  })
).toEqual(false)

proxy 함수 전체도 테스트할 수 있습니다.

The entire proxy function can also be tested.

import { isRewrite, getRewrittenUrl } from 'next/experimental/testing/server'

const request = new NextRequest('https://nextjs.org/docs')
const response = await proxy(request)
expect(isRewrite(response)).toEqual(true)
expect(getRewrittenUrl(response)).toEqual('https://other-domain.com/docs')
// getRedirectUrl could also be used if the response were a redirect

Migration to ProxyProxy로 migration

Why the Change변경 이유

middleware의 이름을 바꾼 이유는 "middleware"라는 용어가 Express.js middleware와 혼동되어 그 목적이 잘못 해석되는 경우가 많기 때문입니다. 또한 Middleware는 매우 강력해서 사용을 부추길 수 있지만, 이 기능은 최후의 수단으로 사용하는 것이 권장됩니다.

The reason behind the renaming of middleware is that the term "middleware" can often be confused with Express.js middleware, leading to a misinterpretation of its purpose. Also, Middleware is highly capable, so it may encourage the usage; however, this feature is recommended to be used as a last resort.

Next.js는 개발자가 Middleware 없이도 목표를 달성할 수 있도록 더 나은 사용성(ergonomics)을 갖춘 더 좋은 API를 제공하는 방향으로 나아가고 있습니다. 이것이 middleware의 이름을 바꾼 이유입니다.

Next.js is moving forward to provide better APIs with better ergonomics so that developers can achieve their goals without Middleware. This is the reason behind the renaming of middleware.

Why "Proxy"왜 "Proxy"인가

Proxy라는 이름은 Middleware가 할 수 있는 일을 명확히 보여 줍니다. "proxy"라는 용어는 앱 앞단의 네트워크 경계를 의미하며, 이 기능이 바로 그렇게 동작합니다. 이 기능은 애플리케이션의 main runtime 바깥에서 실행될 수 있고 request가 앱에 도달하기 전에 처리할 수 있습니다. 이러한 특성은 "proxy"라는 용어와 더 잘 맞으며 기능의 목적을 더 명확하게 해 줍니다.

The name Proxy clarifies what Middleware is capable of. The term "proxy" implies a network boundary in front of the app, which is how this feature behaves. It can run outside of your application’s main runtime and handle requests before they reach your app. These characteristics align better with the term "proxy" and provide a clearer purpose for the feature.

How to MigrateMigration 방법

다른 방법이 없는 경우가 아니라면 Middleware에 의존하지 않기를 권장합니다. 저희의 목표는 사용자가 Middleware 없이도 목표를 달성할 수 있도록 더 나은 사용성을 갖춘 API를 제공하는 것입니다.

We recommend users avoid relying on Middleware unless no other options exist. Our goal is to give them APIs with better ergonomics so they can achieve their goals without Middleware.

"middleware"라는 용어는 사용자에게 Express.js middleware와 혼동을 주어 오용을 부추길 수 있습니다. 방향성을 명확히 하기 위해 file convention의 이름을 "proxy"로 바꿉니다. 이는 저희가 Middleware에서 벗어나 과도하게 많은 기능을 분리하고 Proxy의 목적을 명확히 하고 있음을 보여 줍니다.

The term “middleware” often confuses users with Express.js middleware, which can encourage misuse. To clarify our direction, we are renaming the file convention to “proxy.” This highlights that we are moving away from Middleware, breaking down its overloaded features, and making the Proxy clear in its purpose.

Next.js는 middleware.ts에서 proxy.ts로 migration하는 codemod를 제공합니다. 다음 명령어를 실행해 migration할 수 있습니다:

Next.js provides a codemod to migrate from middleware.ts to proxy.ts. You can run the following command to migrate:

npx @next/codemod@canary middleware-to-proxy .

codemod는 파일 이름과 함수 이름을 middleware에서 proxy로 바꿉니다.

The codemod will rename the file and the function name from middleware to proxy.

// middleware.ts -> proxy.ts

- export function middleware() {
+ export function proxy() {
