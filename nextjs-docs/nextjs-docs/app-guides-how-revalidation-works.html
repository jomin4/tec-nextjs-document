How revalidation works in Next.jsNext.js에서 revalidation이 동작하는 방식

Caching 페이지에서는 use cache, cacheTag, cacheLife 사용법을 다룹니다. 이 페이지는 custom cache handler를 구현하거나 revalidation 동작을 debug하기 위해 시스템을 이해해야 하는 플랫폼 엔지니어와 고급 사용자를 위해 revalidation이 내부적으로 어떻게 동작하는지 설명합니다.

The Caching page covers how to use use cache, cacheTag, and cacheLife. This page explains how revalidation works internally, for platform engineers and advanced users who need to understand the system to implement custom cache handlers or debug revalidation behavior.

The Revalidation ModelRevalidation 모델

Next.js의 대부분의 route는 on demand로 revalidate할 수 있습니다. 여기에는 App Router route와 ISR/prerender cache entry를 생성하는 Pages Router route가 포함됩니다. 자동으로 static 최적화된(순수 static output) Pages Router route는 on demand로 revalidate되지 않습니다. 다시 deploy하지 않고 cache된 content를 업데이트하는 능력은 Next.js rendering 모델의 핵심 부분입니다.

Most routes in Next.js can be revalidated on demand. This includes App Router routes and Pages Router routes that produce ISR/prerender cache entries. Pages Router routes that are automatically statically optimized (pure static output) are not revalidated on demand. The ability to update cached content without redeploying is a core part of Next.js's rendering model.

revalidation에는 두 가지 유형이 있습니다:

There are two types of revalidation:

  • Time-based revalidation은 stale-while-revalidate 패턴을 사용합니다. cache된 content는 즉시 제공되고, content의 나이가 cacheLife 또는 revalidate 기간을 넘으면 background 재생성이 트리거됩니다. 새 content가 준비될 때까지 stale content가 계속 제공됩니다.
  • On-demand revalidation은 revalidateTag()나 revalidatePath()를 호출해 cache된 content를 명시적으로 무효화합니다. 해당 content에 대한 다음 request가 새 render를 트리거합니다.
  • Time-based revalidation uses a stale-while-revalidate pattern. The cached content is served immediately, and a background regeneration is triggered when the content's age exceeds the cacheLife or revalidate duration. The stale content continues to be served until the fresh content is ready.
  • On-demand revalidation explicitly invalidates cached content by calling revalidateTag() or revalidatePath(). The next request to that content triggers a fresh render.
Good to know

Pages Router의 on-demand ISR API(예: res.revalidate()와 x-prerender-revalidate 흐름)는 여전히 지원되며, server cache handler(cacheHandler, 단수)를 사용합니다. cacheHandlers option(복수)은 'use cache' directive용입니다.

Pages Router on-demand ISR APIs (for example res.revalidate() and the x-prerender-revalidate flow) are still supported and use the server cache handler (cacheHandler, singular). The cacheHandlers option (plural) is for 'use cache' directives.

What Gets Revalidated무엇이 revalidate되는가

route가 revalidate되면 Next.js는 같은 React component tree로부터 HTML response와 RSC payload(React Server Components payload)를 둘 다 다시 생성합니다. 두 결과물은 같은 cache entry에 함께 저장됩니다.

When a route is revalidated, Next.js regenerates both the HTML response and the RSC payload (React Server Components payload) from the same React component tree. Both artifacts are stored together in the same cache entry.

RSC payload는 client-side navigation에 사용되기 때문에 이 일관성이 중요합니다. 브라우저 navigation과 client-side navigation은 같은 content를 가져야 합니다.

This consistency matters because the RSC payload is used for client-side navigations. Browser navigations and client-side navigations should hold the same content.

What happens if they get out of sync둘이 어긋나면 어떻게 되는가

플랫폼의 cache가 한 render의 HTML과 다른 render의 RSC payload를 제공하면, 사용자는 client-side navigation 중에 stale하거나 일치하지 않는 content를 볼 수 있습니다. 주된 완화책은 HTML과 RSC response를 같은 TTL과 무효화 정책으로 함께 cache하고, Next.js가 설정하는 Vary header를 존중하는 것입니다. 자세한 내용은 CDN Caching을 참고하세요.

If a platform's cache serves HTML from one render and an RSC payload from a different render, users may see stale or mismatched content during client-side navigation. The primary mitigation is to cache HTML and RSC responses together with the same TTL and invalidation policy, and to respect the Vary header that Next.js sets. See CDN Caching for details.

별개지만 관련된 문제로 cross-deployment skew가 있습니다: rolling deployment 중에 deploy A로 build된 client가 deploy B를 실행하는 server로부터 response를 받을 수 있습니다. deploymentId가 이를 완화합니다: client가 server에서 다른 deployment ID를 감지하면 일관된 content를 가져오기 위해 hard navigation을 트리거합니다.

A separate but related problem is cross-deployment skew: during rolling deployments, a client built with deploy A may receive responses from a server running deploy B. deploymentId mitigates this: when the client detects a different deployment ID from the server, it triggers a hard navigation to fetch consistent content.

Tag System ArchitectureTag System 아키텍처

Next.js는 어떤 cache된 content를 무효화해야 하는지 추적하기 위해 tag 기반 시스템을 사용합니다. tag에는 두 가지 유형이 있습니다:

Next.js uses a tag-based system to track which cached content needs to be invalidated. There are two types of tags:

Explicit tagsExplicit tag

explicit tag는 개발자가 use cache 함수 안에서 cacheTag()를 사용하거나, fetch 호출에 next: { tags: [...] }를 지정해 설정합니다. revalidateTag('my-tag', 'max')가 호출되면 해당 tag를 가진 모든 cache entry가 무효화됩니다.

Explicit tags are set by the developer using cacheTag() inside a use cache function, or via next: { tags: [...] } on a fetch call. When revalidateTag('my-tag', 'max') is called, all cache entries with that tag are invalidated.

Soft tagsSoft tag

soft tag는 Next.js가 route 경로를 기반으로 자동 생성하며, _N_T_ 접두사가 붙습니다. 예를 들어 route /blog/hello는 _N_T_/layout, _N_T_/blog/layout, _N_T_/blog/hello/layout, _N_T_/blog/hello 같은 soft tag를 생성합니다. 경로의 각 segment가 layout tag를 하나씩 받고, 여기에 leaf route 자체의 tag가 더해집니다.

Soft tags are automatically generated by Next.js based on the route path, prefixed with _N_T_. For example, the route /blog/hello generates soft tags like _N_T_/layout, _N_T_/blog/layout, _N_T_/blog/hello/layout, and _N_T_/blog/hello. Each segment in the path gets a layout tag, plus the leaf route itself.

soft tag 덕분에 revalidatePath()가 같은 tag 기반 시스템을 통해 동작할 수 있습니다. revalidatePath('/blog/hello')가 호출되면, 해당 경로의 leaf route tag와 상위 layout soft tag(예: _N_T_/layout, _N_T_/blog/layout, _N_T_/blog/hello/layout, _N_T_/blog/hello)에 연결된 cache entry를 무효화합니다.

Soft tags enable revalidatePath() to work through the same tag-based system. When revalidatePath('/blog/hello') is called, it invalidates cache entries associated with that path's leaf route tag and its ancestor layout soft tags (for example _N_T_/layout, _N_T_/blog/layout, _N_T_/blog/hello/layout, and _N_T_/blog/hello).

cache handler API에서 soft tag는 get() method에 softTags parameter로 전달됩니다. handler는 cache entry의 timestamp 이후에 무효화된 soft tag가 있는지 확인해야 합니다. getExpiration() method는 전달된 모든 tag 중 가장 최근의 revalidation timestamp를 반환하고, 아무것도 revalidate되지 않았다면 0을 반환합니다. 또한 Infinity를 반환해서 soft tag를 대신 get()에 전달해 그곳에서 만료 여부를 확인하라는 신호를 보낼 수도 있습니다. 반환된 timestamp가 entry 자체의 timestamp보다 최신이라면 handler는 해당 entry를 stale로 취급해야 합니다. 전체 semantics는 cache handler API reference를 참고하세요.

In the cache handler API, soft tags are passed to the get() method as the softTags parameter. Your handler should check whether any soft tag has been invalidated after the cache entry's timestamp. The getExpiration() method returns the most recent revalidation timestamp across all provided tags, or 0 if none have been revalidated. It can also return Infinity to signal that the soft tags should instead be passed to get() and checked for expiration there. Your handler should treat an entry as stale if the returned timestamp is newer than the entry's own timestamp. See the cache handler API reference for the full semantics.

Multi-Instance ConsiderationsMulti-Instance 고려 사항

load balancer 뒤에서 여러 Next.js instance를 실행하는 경우, revalidation 이벤트는 기본적으로 local입니다. instance A에서 revalidateTag()를 호출하면 그 instance의 cache만 무효화됩니다. 다른 instance들은 무효화 사실을 알게 될 때까지 stale content를 계속 제공합니다.

When running multiple Next.js instances behind a load balancer, revalidation events are local by default. Calling revalidateTag() on instance A only invalidates the cache on that instance. Other instances continue serving the stale content until they learn about the invalidation.

cache handler API는 분산 조정을 위한 두 가지 hook을 제공합니다:

The cache handler API provides two hooks for distributed coordination:

  • updateTags(): revalidateTag()가 호출될 때 호출됩니다. handler는 다른 instance가 발견할 수 있도록 무효화 이벤트를 공유 저장소(예: Redis나 database)에 기록해야 합니다.
  • refreshTags(): 주기적으로 호출되지만, 새 request를 시작하기 전에는 항상 호출됩니다. handler는 공유 저장소에서 최근 무효화 이벤트를 확인하고 그에 따라 local tag 상태를 업데이트해야 합니다.
  • updateTags() is called when revalidateTag() is invoked. Your handler should write the invalidation event to shared storage (for example, Redis or a database) so other instances can discover it.
  • refreshTags() is called periodically, but always before starting a new request. Your handler should check shared storage for recent invalidation events and update its local tag state accordingly.

구현 세부 사항과 Redis 예제는 Custom Cache Handlers를 참고하세요.

For implementation details and a Redis example, see Custom Cache Handlers.

Implementation Patterns for Platforms플랫폼을 위한 구현 패턴

Single instance단일 instance

기본 file-system cache가 일관성을 자동으로 처리합니다. cache 쓰기는 local filesystem에서 atomic하게 이루어지고, tag 상태는 memory에 유지됩니다. 추가 설정은 필요 없습니다.

The default file-system cache handles consistency automatically. Cache writes are atomic on the local filesystem, and tag state is maintained in memory. No additional configuration is needed.

Multi-instance with shared cacheShared cache를 사용하는 multi-instance

조정이 없으면 각 instance는 자신의 local cache만 사용해 독립적으로 content를 제공하고 revalidation을 처리합니다. 어떤 instance가 request를 처리하느냐에 따라 사용자마다 다른 content를 볼 수 있으며, on-demand revalidation은 호출을 받은 instance에서만 효과가 있습니다.

Without coordination, each instance independently serves content and handles revalidation using only its local cache. Different users may see different content depending on which instance serves their request, and on-demand revalidation only takes effect on the instance that received the call.

이 기간을 줄이고 revalidation이 instance 간에 전파되도록 하려면:

To reduce this window and ensure revalidation propagates across instances:

  1. tag 무효화 timestamp를 공유 서비스(Redis, DynamoDB, 또는 간단한 HTTP API)에 저장합니다.
  2. 공유 서비스에 기록하도록 updateTags()를 구현합니다.
  3. 공유 서비스에서 읽도록 refreshTags()를 구현합니다. handler는 refreshTags()에서 발생하는 error를 반드시 catch해야 합니다: error가 throw되면 그 exception이 request 실패로 전파됩니다. error를 catch하면 마지막으로 알려진 local tag 상태로 request를 계속 처리할 수 있으며, 연결이 복구될 때까지 stale content를 제공할 수 있습니다.
  4. cache entry(HTML + RSC payload)를 공유 저장소에 저장합니다. atomic 쓰기는 불일치 기간을 더 줄여 주지만, 정확성을 위해 필수는 아닙니다.
  1. Store tag invalidation timestamps in a shared service (Redis, DynamoDB, or a simple HTTP API).
  2. Implement updateTags() to write to the shared service.
  3. Implement refreshTags() to read from the shared service. Your handler must catch errors in refreshTags(): if it throws, the exception propagates as a request failure. Catching the error allows requests to continue with the last known local tag state, serving potentially stale content until connectivity is restored.
  4. Store cache entries (HTML + RSC payload) in shared storage. Atomic writes reduce the mismatch window further but are not required for correctness.

CDN integration

CDN이 Next.js response를 cache한다면, Next.js가 설정하는 Vary header와 Cache-Control directive를 존중해야 합니다. HTML과 RSC payload response를 서로 다른 TTL로 따로 cache하지 마세요. 자세한 내용은 CDN Caching을 참고하세요.

If a CDN caches Next.js responses, it should respect the Vary header and the Cache-Control directives that Next.js sets. Do not cache HTML and RSC payload responses separately with different TTLs. See CDN Caching for details.

Graceful Degradation점진적 성능 저하(Graceful Degradation)

revalidation 시스템은 엄격한 일관성보다 가용성을 우선합니다. 인프라 보장을 완전히 충족할 수 없을 때도 content는 항상 제공됩니다:

The revalidation system prioritizes availability over strict consistency. Content is always served, even when infrastructure guarantees cannot be fully met:

  • Cache write 실패: 쓰기는 비동기로 이루어지므로 response는 여전히 사용자에게 제공됩니다. cache entry는 손실되고, 다음 request가 새 render를 트리거합니다.
  • Cache read 실패: handler는 내부 error를 catch하고 undefined(cache miss 신호)를 반환해야 합니다. 그러면 route가 server에서 새로 render됩니다. throw된 error는 cache miss로 취급되지 않고 render error로 전파되므로, miss를 알리려면 항상 undefined를 반환하세요.
  • HTML/RSC cache 불일치: CDN이 HTML과 RSC response를 서로 다른 TTL이나 무효화 타이밍으로 cache하면, 사용자는 client-side navigation 중에 일치하지 않는 content를 볼 수 있습니다. 이를 피하려면 둘을 함께 cache하고 Vary header를 존중하세요.
  • Cross-deployment skew: rolling deployment 중에는 build ID 변경이 일관된 content를 가져오는 hard navigation을 트리거하도록 deploymentId를 설정하세요.
  • Cache write failure: the response is still served to the user because writes are asynchronous. The cache entry is lost, and the next request triggers a fresh render.
  • Cache read failure: your handler should catch internal errors and return undefined (the cache miss signal). The route is then server-rendered fresh. A thrown error is not treated as a cache miss; it propagates as a render error, so always return undefined to signal a miss.
  • HTML/RSC cache inconsistency: if a CDN caches HTML and RSC responses with different TTLs or invalidation timing, users may see mismatched content during client-side navigation. Cache them together and respect the Vary header to avoid this.
  • Cross-deployment skew: during rolling deployments, configure deploymentId so that a build ID change triggers a hard navigation to fetch consistent content.

cache 실패는 애플리케이션이 망가지는 것이 아니라 performance 저하(stale content, 추가 render)로 이어집니다.

Cache failures result in degraded performance (stale content, extra renders), not broken applications.
