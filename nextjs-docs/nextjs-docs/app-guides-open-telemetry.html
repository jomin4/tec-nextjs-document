How to set up instrumentation with OpenTelemetryOpenTelemetry로 instrumentation 설정하기

observability는 Next.js 앱의 동작과 performance를 이해하고 최적화하는 데 매우 중요합니다.

Observability is crucial for understanding and optimizing the behavior and performance of your Next.js app.

애플리케이션이 복잡해질수록 발생할 수 있는 문제를 찾아내고 진단하기가 점점 더 어려워집니다. logging과 metrics 같은 observability 도구를 활용하면 개발자는 애플리케이션의 동작에 대한 insight를 얻고 최적화할 부분을 찾을 수 있습니다. observability가 있으면 개발자는 문제가 커지기 전에 선제적으로 대응하고 더 나은 사용자 경험을 제공할 수 있습니다. 따라서 performance를 개선하고, resource를 최적화하고, 사용자 경험을 향상시키기 위해 Next.js 애플리케이션에서 observability를 사용하는 것을 적극 권장합니다.

As applications become more complex, it becomes increasingly difficult to identify and diagnose issues that may arise. By leveraging observability tools, such as logging and metrics, developers can gain insights into their application's behavior and identify areas for optimization. With observability, developers can proactively address issues before they become major problems and provide a better user experience. Therefore, it is highly recommended to use observability in your Next.js applications to improve performance, optimize resources, and enhance user experience.

앱을 instrument할 때는 OpenTelemetry 사용을 권장합니다. OpenTelemetry는 platform에 구애받지 않는(platform-agnostic) 방식으로 앱을 instrument하므로, 코드를 바꾸지 않고도 observability provider를 변경할 수 있습니다. OpenTelemetry와 그 동작 방식에 대한 자세한 내용은 공식 OpenTelemetry 문서를 읽어 보세요.

We recommend using OpenTelemetry for instrumenting your apps. It's a platform-agnostic way to instrument apps that allows you to change your observability provider without changing your code. Read Official OpenTelemetry docs for more information about OpenTelemetry and how it works.

이 문서 전반에서는 Span, Trace, Exporter 같은 용어를 사용하며, 이 용어들은 모두 OpenTelemetry Observability Primer에서 찾아볼 수 있습니다.

This documentation uses terms like Span, Trace or Exporter throughout this doc, all of which can be found in the OpenTelemetry Observability Primer.

Next.js는 OpenTelemetry instrumentation을 별도 설정 없이(out of the box) 지원합니다. 즉, Next.js 자체는 이미 instrument되어 있습니다.

Next.js supports OpenTelemetry instrumentation out of the box, which means that we already instrumented Next.js itself.

Getting Started시작하기

OpenTelemetry는 확장성이 좋지만, 제대로 설정하려면 꽤 장황해질 수 있습니다. 그래서 빠르게 시작할 수 있도록 돕는 @vercel/otel package를 준비했습니다.

OpenTelemetry is extensible but setting it up properly can be quite verbose. That's why we prepared a package @vercel/otel that helps you get started quickly.

Using @vercel/otel@vercel/otel 사용하기

시작하려면 다음 package를 설치하세요:

To get started, install the following packages:

pnpm add @vercel/otel @opentelemetry/sdk-logs @opentelemetry/api-logs @opentelemetry/instrumentation
npm install @vercel/otel @opentelemetry/sdk-logs @opentelemetry/api-logs @opentelemetry/instrumentation
yarn add @vercel/otel @opentelemetry/sdk-logs @opentelemetry/api-logs @opentelemetry/instrumentation
bun add @vercel/otel @opentelemetry/sdk-logs @opentelemetry/api-logs @opentelemetry/instrumentation

다음으로 프로젝트의 root directory(또는 src 폴더를 사용한다면 그 안)에 custom instrumentation.ts(또는 .js) 파일을 만드세요:

Next, create a custom instrumentation.ts (or .js) file in the root directory of the project (or inside src folder if using one):

TSJSyour-project/instrumentation.ts
import { registerOTel } from '@vercel/otel'

export function register() {
  registerOTel({ serviceName: 'next-app' })
}
import { registerOTel } from '@vercel/otel'

export function register() {
  registerOTel({ serviceName: 'next-app' })
}

추가 configuration option은 @vercel/otel 문서를 참고하세요.

See the @vercel/otel documentation for additional configuration options.

Good to know
  • instrumentation 파일은 app이나 pages directory 안이 아니라 프로젝트 root에 있어야 합니다. src 폴더를 사용한다면 pages, app과 나란히 src 안에 파일을 두세요.
  • pageExtensions config option으로 suffix를 추가한다면, instrumentation 파일 이름도 그에 맞게 바꿔야 합니다.
  • 바로 사용할 수 있는 기본 with-opentelemetry 예시를 만들어 두었습니다.
  • The instrumentation file should be in the root of your project and not inside the app or pages directory. If you're using the src folder, then place the file inside src alongside pages and app.
  • If you use the pageExtensions config option to add a suffix, you will also need to update the instrumentation filename to match.
  • We have created a basic with-opentelemetry example that you can use.

Manual OpenTelemetry configurationOpenTelemetry 수동 설정

@vercel/otel package는 많은 configuration option을 제공하며 대부분의 일반적인 use case를 충족할 것입니다. 하지만 필요에 맞지 않는다면 OpenTelemetry를 수동으로 설정할 수 있습니다.

The @vercel/otel package provides many configuration options and should serve most of common use cases. But if it doesn't suit your needs, you can configure OpenTelemetry manually.

먼저 OpenTelemetry package를 설치해야 합니다:

Firstly you need to install OpenTelemetry packages:

pnpm add @opentelemetry/sdk-node @opentelemetry/resources @opentelemetry/semantic-conventions @opentelemetry/sdk-trace-node @opentelemetry/exporter-trace-otlp-http
npm install @opentelemetry/sdk-node @opentelemetry/resources @opentelemetry/semantic-conventions @opentelemetry/sdk-trace-node @opentelemetry/exporter-trace-otlp-http
yarn add @opentelemetry/sdk-node @opentelemetry/resources @opentelemetry/semantic-conventions @opentelemetry/sdk-trace-node @opentelemetry/exporter-trace-otlp-http
bun add @opentelemetry/sdk-node @opentelemetry/resources @opentelemetry/semantic-conventions @opentelemetry/sdk-trace-node @opentelemetry/exporter-trace-otlp-http

이제 instrumentation.ts에서 NodeSDK를 초기화할 수 있습니다. @vercel/otel과 달리 NodeSDK는 edge runtime과 호환되지 않으므로, process.env.NEXT_RUNTIME === 'nodejs'일 때만 import하도록 해야 합니다. node를 사용할 때만 조건부로 import하는 새 파일 instrumentation.node.ts를 만드는 것을 권장합니다:

Now you can initialize NodeSDK in your instrumentation.ts. Unlike @vercel/otel, NodeSDK is not compatible with edge runtime, so you need to make sure that you are importing them only when process.env.NEXT_RUNTIME === 'nodejs'. We recommend creating a new file instrumentation.node.ts which you conditionally import only when using node:

TSJSinstrumentation.ts
export async function register() {
  if (process.env.NEXT_RUNTIME === 'nodejs') {
    await import('./instrumentation.node.ts')
  }
}
export async function register() {
  if (process.env.NEXT_RUNTIME === 'nodejs') {
    await import('./instrumentation.node.js')
  }
}
TSJSinstrumentation.node.ts
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http'
import { resourceFromAttributes } from '@opentelemetry/resources'
import { NodeSDK } from '@opentelemetry/sdk-node'
import { SimpleSpanProcessor } from '@opentelemetry/sdk-trace-node'
import { ATTR_SERVICE_NAME } from '@opentelemetry/semantic-conventions'

const sdk = new NodeSDK({
  resource: resourceFromAttributes({
    [ATTR_SERVICE_NAME]: 'next-app',
  }),
  spanProcessor: new SimpleSpanProcessor(new OTLPTraceExporter()),
})
sdk.start()
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http'
import { resourceFromAttributes } from '@opentelemetry/resources'
import { NodeSDK } from '@opentelemetry/sdk-node'
import { SimpleSpanProcessor } from '@opentelemetry/sdk-trace-node'
import { ATTR_SERVICE_NAME } from '@opentelemetry/semantic-conventions'

const sdk = new NodeSDK({
  resource: resourceFromAttributes({
    [ATTR_SERVICE_NAME]: 'next-app',
  }),
  spanProcessor: new SimpleSpanProcessor(new OTLPTraceExporter()),
})
sdk.start()

이렇게 하는 것은 @vercel/otel을 사용하는 것과 동일하지만, @vercel/otel이 노출하지 않는 일부 기능을 수정하고 확장할 수 있습니다. edge runtime 지원이 필요하다면 @vercel/otel을 사용해야 합니다.

Doing this is equivalent to using @vercel/otel, but it's possible to modify and extend some features that are not exposed by the @vercel/otel. If edge runtime support is necessary, you will have to use @vercel/otel.

Testing your instrumentationInstrumentation 테스트하기

OpenTelemetry trace를 로컬에서 테스트하려면 호환되는 backend가 있는 OpenTelemetry collector가 필요합니다. OpenTelemetry dev environment 사용을 권장합니다.

You need an OpenTelemetry collector with a compatible backend to test OpenTelemetry traces locally. We recommend using our OpenTelemetry dev environment.

모든 것이 잘 동작한다면 GET /requested/pathname이라는 label이 붙은 root server span을 볼 수 있을 것입니다. 해당 trace의 다른 모든 span은 그 아래에 중첩됩니다.

If everything works well you should be able to see the root server span labeled as GET /requested/pathname. All other spans from that particular trace will be nested under it.

Next.js는 기본으로 내보내는 것보다 더 많은 span을 trace합니다. 더 많은 span을 보려면 NEXT_OTEL_VERBOSE=1을 설정해야 합니다.

Next.js traces more spans than are emitted by default. To see more spans, you must set NEXT_OTEL_VERBOSE=1.

Custom ExportersCustom Exporter

OpenTelemetry Collector가 반드시 필요한 것은 아닙니다. @vercel/otel이나 OpenTelemetry 수동 설정과 함께 custom OpenTelemetry exporter를 사용할 수 있습니다.

OpenTelemetry Collector is not necessary. You can use a custom OpenTelemetry exporter with @vercel/otel or manual OpenTelemetry configuration.

Custom SpansCustom Span

OpenTelemetry API로 custom span을 추가할 수 있습니다.

You can add a custom span with OpenTelemetry APIs.

pnpm add @opentelemetry/api
npm install @opentelemetry/api
yarn add @opentelemetry/api
bun add @opentelemetry/api

다음 예시는 GitHub star 수를 fetch하고, fetch request의 결과를 추적하기 위해 custom fetchGithubStars span을 추가하는 함수를 보여 줍니다:

The following example demonstrates a function that fetches GitHub stars and adds a custom fetchGithubStars span to track the fetch request's result:

import { trace } from '@opentelemetry/api'

export async function fetchGithubStars() {
  return await trace
    .getTracer('nextjs-example')
    .startActiveSpan('fetchGithubStars', async (span) => {
      try {
        return await getValue()
      } finally {
        span.end()
      }
    })
}

register 함수는 새 environment에서 코드가 실행되기 전에 실행됩니다. 그 후 request를 처리하는 동안 만든 span은 해당 request의 trace에 추가됩니다.

The register function will execute before your code runs in a new environment. After that, spans you create while handling a request are added to that request's trace.

Good to know

instrumentation 파일이 로드되는 동안이나 register 안에서 만든 span은 자동으로 request trace에 합류하지 않습니다. tracer provider가 설치되기 전에 시작된 span(예: registerOTel이 실행되기 전 파일 최상위에서 시작된 span)은 기록되지 않으며, registerOTel(또는 사용하는 OpenTelemetry SDK)이 시작된 후 register 안에서 시작된 span은 보통 별도의 root trace가 됩니다. 작업을 request의 일부로 trace하려면, page를 render할 때나 Route Handler 또는 API Route 안처럼 request를 처리하는 동안 실행되는 코드에서 span을 만드세요.

Spans created while the instrumentation file is loaded, or inside register, don't automatically join a request trace. Spans started before the tracer provider is installed (for example, at the top level of the file before registerOTel runs) are not recorded, and spans started inside register after registerOTel (or your OpenTelemetry SDK) has started typically become separate root traces. To trace work as part of a request, create the span in code that runs while handling the request, such as when rendering a page or in a Route Handler or API Route.

Default Spans in Next.jsNext.js의 기본 Span

Next.js는 애플리케이션 performance에 대한 유용한 insight를 제공하기 위해 여러 span을 자동으로 instrument합니다.

Next.js automatically instruments several spans for you to provide useful insights into your application's performance.

span의 attribute는 OpenTelemetry semantic conventions를 따릅니다. 또한 next namespace 아래에 몇 가지 custom attribute를 추가합니다:

Attributes on spans follow OpenTelemetry semantic conventions. We also add some custom attributes under the next namespace:

  • next.span_name - span 이름을 복제합니다
  • next.span_type - 각 span type마다 고유한 식별자가 있습니다
  • next.route - request의 route pattern입니다(예: /[param]/user).
  • next.rsc (true/false) - prefetch 같은 RSC request인지 여부입니다.
  • next.page
    • app router에서 사용하는 내부 값입니다.
    • 특별한 파일(page.ts, layout.ts, loading.ts 등)로 가는 route라고 생각하면 됩니다
    • /layout은 /(groupA)/layout.ts와 /(groupB)/layout.ts를 모두 가리킬 수 있으므로, next.route와 짝을 이룰 때만 고유한 식별자로 사용할 수 있습니다
  • next.span_name - duplicates span name
  • next.span_type - each span type has a unique identifier
  • next.route - The route pattern of the request (e.g., /[param]/user).
  • next.rsc (true/false) - Whether the request is an RSC request, such as prefetch.
  • next.page
    • This is an internal value used by an app router.
    • You can think about it as a route to a special file (like page.ts, layout.ts, loading.ts and others)
    • It can be used as a unique identifier only when paired with next.route because /layout can be used to identify both /(groupA)/layout.ts and /(groupB)/layout.ts
