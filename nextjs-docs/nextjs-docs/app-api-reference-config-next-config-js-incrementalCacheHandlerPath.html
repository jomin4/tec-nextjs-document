Custom Next.js Cache HandlerCustom Next.js Cache Handler

cache된 page와 data를 durable storage에 영구 저장하거나, Next.js 애플리케이션의 여러 container 또는 instance 간에 cache를 공유하고 싶다면 Next.js cache 위치를 설정할 수 있습니다.

You can configure the Next.js cache location if you want to persist cached pages and data to durable storage, or share the cache across multiple containers or instances of your Next.js application.

Good to know

cacheHandler(단수) configuration은 ISR, route handler response, 최적화된 이미지의 저장과 revalidate 같은 server cache 작업에 Next.js가 전용으로 사용합니다. 'use cache' directive에는 사용되지 않습니다. 'use cache' directive에는 대신 cacheHandlers(복수)를 사용하세요. cacheMaxMemorySize는 둘 모두와 별개이며, 각각의 in-memory cache 크기를 정합니다.

The cacheHandler (singular) configuration is specifically used by Next.js for server cache operations such as storing and revalidating ISR, route handler responses, and optimized images. It is not used by 'use cache' directives. For 'use cache' directives, use cacheHandlers (plural) instead. cacheMaxMemorySize is separate from both, and sizes the in-memory cache for each.

JSnext.config.js
module.exports = {
  cacheHandler: require.resolve('./cache-handler.js'),
  cacheMaxMemorySize: 0, // disable default in-memory caching
}

동작하는 구현은 Redis cacheHandler 예제를, shared store 기반 handler에 필요한 사항은 Configuring Caching을 참고하세요.

See the Redis cacheHandler example for a working implementation, and Configuring Caching for what a handler backed by a shared store needs.

API ReferenceAPI 레퍼런스

cache handler는 다음 method를 구현할 수 있습니다: get, set, revalidateTag, resetRequestCache.

The cache handler can implement the following methods: get, set, revalidateTag, and resetRequestCache.

get()

ctx parameter에는 조회하는 cache entry의 type을 나타내는 kind property가 들어 있습니다. 가능한 값은 'APP_PAGE', 'APP_ROUTE', 'PAGES', 'FETCH', 'IMAGE'입니다.

The ctx parameter contains a kind property that indicates the type of cache entry being retrieved. Possible values include 'APP_PAGE', 'APP_ROUTE', 'PAGES', 'FETCH', and 'IMAGE'.

cache key는 opaque identifier입니다. entry를 읽고 쓸 때 key 전체를 그대로 유지하세요. key는 request pathname이 아닙니다.

Cache keys are opaque identifiers. Preserve the entire key when reading and writing entries; a key is not a request pathname.

response key에는 서로 다른 route가 entry를 공유하지 않도록 response 종류와 source route의 SHA-256 hash가 포함됩니다. Pages Router source는 route definition의 canonical pathname을 사용하므로, index module은 두 bundler에서 같은 identity를 가집니다. App Router source는 route group과 parallel slot을 포함한 전체 page module 이름을 사용합니다. 예를 들어 /blog/[slug]로 생성된 /blog/post의 Pages Router response는 /route-cache/PAGES/<route-hash>/$/blog/post를 사용하며, 여기서 <route-hash>는 UTF-8 source 문자열 /blog/[slug]의 64자리 16진수 SHA-256 digest입니다. 이렇게 하면 추가되는 directory 깊이가 제한되고 disk에서 Unicode source 이름이 길게 펼쳐지는 것을 피할 수 있습니다. request pathname은 그대로 읽을 수 있지만, source route는 hash로부터 복원할 수 없습니다. 이전에 key를 pathname으로 해석하던 handler는 이 namespace를 고려해야 합니다. fetch cache key는 변경되지 않았습니다.

Response keys include the response kind and a SHA-256 hash of the source route to keep different routes from sharing entries. Pages Router sources use the route definition's canonical pathname, so an index module has the same identity in both bundlers. App Router sources use the full page module name, including route groups and parallel slots. For example, a Pages Router response for /blog/post generated by /blog/[slug] uses /route-cache/PAGES/<route-hash>/$/blog/post, where <route-hash> is the 64-character hexadecimal SHA-256 digest of the UTF-8 source string /blog/[slug]. This bounds the added directory depth and avoids expanding Unicode source names on disk. The request pathname remains readable; the source route cannot be recovered from its hash. Handlers that previously interpreted keys as pathnames must account for this namespace. Fetch cache keys are unchanged.

build adapter가 없으면 prerender된 response는 기존의 server/pages와 server/app 경로에 그대로 남습니다. 그 metadata는 각 immutable build seed를 만든 정확한 scoped key, source owner, fallback 상태를 식별합니다. 내장 filesystem cache는 기존 seed를 읽기 전에 그 metadata를 검증한 다음, 원래 artifact와 그 age를 유지하면서 전체 response를 server/route-cache로 승격합니다. adapter가 설정되어 있으면 build 시점의 response artifact는 scoped server/route-cache key에 바로 기록되므로, adapter가 이를 package하기 전에 충돌하는 route가 서로를 덮어쓸 수 없습니다. static output: 'export'는 계속 일반적인 public export 파일을 출력합니다. runtime의 읽기와 쓰기는 scoped key만 사용합니다. custom cache handler는 opaque scoped key를 받으며 기존 pathname으로 조회되는 일은 없습니다. 외부 response cache는 그 key를 변경 없이 유지해야 합니다.

Without a build adapter, prerendered responses remain at their historical server/pages and server/app paths. Their metadata identifies the exact scoped key, source owner, and fallback status that produced each immutable build seed. The built-in filesystem cache verifies that metadata before reading a historical seed, then promotes the complete response to server/route-cache while retaining the original artifact and its age. When an adapter is configured, build-time response artifacts are written directly to their scoped server/route-cache keys so colliding routes cannot overwrite one another before the adapter packages them. Static output: 'export' continues to emit normal public export files. Runtime reads and writes use only scoped keys. Custom cache handlers receive the opaque scoped key and are never queried with a historical pathname; an external response cache must preserve that key unchanged.

runtime packaging은 prerender manifest에 있는 기존 source-route metadata를 보존해야 합니다. Next.js는 이 metadata를 사용해 선택된 route의 허용 parameter와 rendering mode도 검증합니다.

Runtime packaging must preserve the existing source-route metadata in the prerender manifest. Next.js also uses it to verify the allowed parameters and rendering mode of the selected route.

Next.js를 호출하기 전에 cache된 response를 읽는 integration도 entry를 선택할 때 source-route 소유 관계를 보존해야 합니다. route namespace를 제거하거나 pathname만 사용하는 cache entry로 fallback하면 이 격리가 무력화됩니다.

Integrations that read cached responses before invoking Next.js must also preserve source-route ownership when selecting entries. Removing the route namespace or falling back to pathname-only cache entries defeats that isolation.

cache된 값을 반환하며, 찾지 못하면 null을 반환합니다.

Returns the cached value or null if not found.

resetRequestCache()

이 method는 다음 request 전에 단일 request를 위한 임시 in-memory cache를 초기화합니다.

This method resets the temporary in-memory cache for a single request before the next request.

void를 반환합니다.

Returns void.

Good to know:

Good to know:

  • revalidatePath는 cache tag 위에 얹힌 편의 layer입니다. revalidatePath를 호출하면 revalidateTag 함수가 호출되며, 그 안에서 path를 기준으로 cache key에 tag를 붙일지 선택할 수 있습니다.
  • revalidatePath is a convenience layer on top of cache tags. Calling revalidatePath will call your revalidateTag function, which you can then choose if you want to tag cache keys based on the path.

Image Optimization Caching

cacheHandler는 next/image로 최적화된 이미지를 cache하는 데도 사용할 수 있습니다. 이를 활성화하려면 next.config.js에서 images.customCacheHandler를 true로 설정하세요:

The cacheHandler can also be used for caching optimized images from next/image. To enable this, set images.customCacheHandler to true in your next.config.js:

JSnext.config.js
module.exports = {
  cacheHandler: require.resolve('./cache-handler.js'),
  images: {
    customCacheHandler: true,
  },
}
Good to know

이 opt-in flag는 다음 major 버전에서 기본 동작이 됩니다. 지금 설정해 두면 cache handler가 image optimization entry를 처리하도록 미리 준비할 수 있습니다.

This opt-in flag will become the default behavior in the next major version. Setting it now allows you to prepare your cache handler for image optimization entries.

kind property를 사용해 cache entry type을 구분하고, 필요하면 이미지를 따로 처리할 수 있습니다. 예를 들어 eviction policy를 구현하거나 이미지를 다른 위치에 저장할 수 있습니다.

You can use the kind property to differentiate between cache entry types and handle images separately if needed, for example to implement an eviction policy or store images in a different location.

image cache entry를 처리할 때 kind는 'IMAGE'이고, data에는 buffer, etag, extension, revalidate property가 포함됩니다.

When handling image cache entries, the kind will be 'IMAGE' and the data will include buffer, etag, extension, and revalidate properties.
