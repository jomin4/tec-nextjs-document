usePathnameusePathname

usePathname은 현재 URL의 pathname을 읽을 수 있게 해 주는 Client Component hook입니다.

usePathname is a Client Component hook that lets you read the current URL's pathname.

TSJSapp/example-client-component.tsx
'use client'

import { usePathname } from 'next/navigation'

export default function ExampleClientComponent() {
  const pathname = usePathname()
  return <p>Current pathname: {pathname}</p>
}
'use client'

import { usePathname } from 'next/navigation'

export default function ExampleClientComponent() {
  const pathname = usePathname()
  return <p>Current pathname: {pathname}</p>
}

usePathname은 의도적으로 Client Component에서만 사용하도록 되어 있습니다. Client Component는 de-optimization(최적화 저하)이 아니라는 점을 알아 두는 것이 중요합니다. Client Component는 Server Components architecture의 필수적인 부분입니다.

usePathname intentionally requires using a Client Component. It's important to note Client Components are not a de-optimization. They are an integral part of the Server Components architecture.

예를 들어 usePathname을 사용하는 Client Component는 initial page load 때 HTML로 render됩니다. 새 route로 이동할 때 이 component를 다시 fetch할 필요가 없습니다. 대신 component는 (client JavaScript bundle에 포함되어) 한 번만 다운로드되고, 현재 state에 따라 re-render됩니다.

For example, a Client Component with usePathname will be rendered into HTML on the initial page load. When navigating to a new route, this component does not need to be re-fetched. Instead, the component is downloaded once (in the client JavaScript bundle), and re-renders based on the current state.

Good to know
  • Server Component에서 현재 URL을 읽는 것은 지원되지 않습니다. 이는 page navigation 간에 layout state가 유지되도록 하기 위한 의도적인 설계입니다.
  • page가 statically prerender되고 있고 앱에 next.config의 rewrites나 Proxy 파일이 있다면, usePathname()으로 pathname을 읽을 때 hydration mismatch error가 발생할 수 있습니다. initial 값은 server에서 오며 routing 이후 실제 브라우저 pathname과 일치하지 않을 수 있기 때문입니다. 이 문제를 완화하는 방법은 예시를 참고하세요.
  • Reading the current URL from a Server Component is not supported. This design is intentional to support layout state being preserved across page navigations.
  • If your page is being statically prerendered and your app has rewrites in next.config or a Proxy file, reading the pathname with usePathname() can result in hydration mismatch errors, because the initial value comes from the server and may not match the actual browser pathname after routing. See our example for a way to mitigate this issue.
Pages Router와의 호환성

usePathname을 사용하는 component를 Pages Router의 route에서 import한다면, router가 아직 초기화되지 않은 경우 usePathname이 null을 반환할 수 있다는 점에 유의하세요. 이는 Pages Router의 fallback routes나 Automatic Static Optimization 중과 같은 경우에 발생할 수 있습니다.

routing system 간의 호환성을 높이기 위해, 프로젝트에 app directory와 pages directory가 모두 있으면 Next.js가 usePathname의 return type을 자동으로 조정합니다.

Behavior동작

Cache Components

cacheComponents가 활성화되어 있으면 usePathname에 Suspense boundary가 필요할 수 있습니다. 이는 prerendering 중에 pathname을 resolve할 수 있는지에 따라 달라집니다.

When cacheComponents is enabled, usePathname may require a Suspense boundary. This depends on whether the pathname can be resolved during prerendering.

  • Static route와 generateStaticParams가 있는 route: dynamic param을 포함한 모든 route segment를 build 시점에 알 수 있습니다. prerendering 중에 pathname을 resolve할 수 있으므로 usePathname은 server에서 resolve되며 Suspense boundary가 필요하지 않습니다.
  • generateStaticParams로 다루지 않는 dynamic param이 있는 route: 이 param은 request 시점까지 알 수 없는 fallback param입니다. prerendering 중에 pathname을 resolve할 수 없으므로 usePathname은 suspend됩니다. prerendering 중에 fallback이 render될 수 있도록 component(또는 상위 component)를 Suspense boundary로 감싸세요. 그렇지 않으면 build가 실패합니다.
  • Static routes and routes with generateStaticParams: every route segment, including dynamic params, is known at build time. The pathname can be resolved during prerendering, so usePathname resolves on the server and no Suspense boundary is required.
  • Routes with dynamic params not covered by generateStaticParams: the param is a fallback param that is not known until request time. The pathname cannot be resolved during prerendering, so usePathname suspends. Wrap the component (or a parent) in a Suspense boundary so its fallback can be rendered during prerendering; otherwise, the build fails.

이는 usePathname을 호출하는 component 자체가 static인 경우에도 적용됩니다. 예를 들어 layout에서 render되는 active link가 있는 sidebar는, 그 아래에 있는 page 중 알 수 없는 dynamic param을 가진 page에서 suspend됩니다. layout의 나머지 부분을 prerender된 상태로 유지하려면 usePathname을 호출하는 component(또는 상위 component)를 fallback이 있는 Suspense boundary로 감싸세요.

This applies even when the component that calls usePathname is itself static. For example, a sidebar with active links rendered in a layout suspends on any page below it that has an unknown dynamic param. To keep the rest of the layout prerendered, wrap the component that calls usePathname (or a parent) in a Suspense boundary with a fallback.

전체 해결 방법과 trade-off는 Next.js encountered URL data in a Client Component outside of Suspense를 참고하세요.

See Next.js encountered URL data in a Client Component outside of Suspense for full fix options and trade-offs.

Avoid hydration mismatch with rewritesrewrites 사용 시 hydration mismatch 피하기

page가 prerender되면 HTML은 그 page의 경로에 대해 생성됩니다. 예를 들어 app/blog/[slug]/page.tsx의 경우 /blog/hello 같은 경로입니다. next.config의 rewrite나 Proxy가 그 page를 다른 URL에서 제공하면, 브라우저는 자신이 요청한 URL을 유지하고, usePathname()은 client에서 rewrite 대상이 아니라 그 브라우저 URL을 읽습니다.

When a page is prerendered, the HTML is generated for its path, such as /blog/hello for app/blog/[slug]/page.tsx. If a rewrite in next.config or Proxy serves that page at a different URL, the browser keeps the URL it requested, and usePathname() reads that browser URL on the client rather than the rewrite destination.

hydration mismatch를 피하려면 client pathname에 의존하는 부분이 작고 고립된 일부만 되도록 UI를 설계하세요. server에서는 안정적인 fallback을 render하고, mount 이후에 그 부분을 업데이트하세요. 읽기를 지연시키면 실제 pathname이 나타나기 전에 잠깐 fallback이 보입니다. 눈에 보이는 깜빡임을 없애는 기법은 Preventing flash before hydration을 참고하세요.

To avoid hydration mismatches, design the UI so that only a small, isolated part depends on the client pathname. Render a stable fallback on the server and update that part after mount. The deferred read shows a brief moment of the fallback before the real pathname appears; see Preventing flash before hydration for techniques that eliminate the visible flicker.

TSJSapp/example-client-component.tsx
'use client'

import { useEffect, useState } from 'react'
import { usePathname } from 'next/navigation'

export default function PathnameBadge() {
  const pathname = usePathname()
  const [clientPathname, setClientPathname] = useState('')

  useEffect(() => {
    setClientPathname(pathname)
  }, [pathname])

  return (
    <p>
      Current pathname: <span>{clientPathname}</span>
    </p>
  )
}
