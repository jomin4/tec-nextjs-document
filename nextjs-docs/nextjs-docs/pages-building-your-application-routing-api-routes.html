Good to know

App Router를 사용한다면 API Route 대신 Server Components나 Route Handlers를 사용할 수 있습니다.

If you are using the App Router, you can use Server Components or Route Handlers instead of API Routes.

API route는 Next.js로 public API를 만드는 방법을 제공합니다.

API routes provide a solution to build a public API with Next.js.

pages/api 폴더 안의 모든 파일은 /api/*에 mapping되며, page가 아니라 API endpoint로 취급됩니다. 이 파일들은 server-side 전용 bundle이므로 client-side bundle 크기를 늘리지 않습니다.

Any file inside the folder pages/api is mapped to /api/* and will be treated as an API endpoint instead of a page. They are server-side only bundles and won't increase your client-side bundle size.

예를 들어 다음 API route는 status code 200과 함께 JSON response를 반환합니다:

For example, the following API route returns a JSON response with a status code of 200:

TSJSpages/api/hello.ts
import type { NextApiRequest, NextApiResponse } from 'next'

type ResponseData = {
  message: string
}

export default function handler(
  req: NextApiRequest,
  res: NextApiResponse<ResponseData>
) {
  res.status(200).json({ message: 'Hello from Next.js!' })
}
export default function handler(req, res) {
  res.status(200).json({ message: 'Hello from Next.js!' })
}
Good to know
  • API Route는 CORS header를 지정하지 않습니다. 즉, 기본적으로 same-origin 전용입니다. request handler를 CORS request helper로 감싸 이 동작을 customize할 수 있습니다.
  • API Route는 static export와 함께 사용할 수 없습니다. 하지만 App Router의 Route Handlers는 사용할 수 있습니다.
  • API Route는 next.config.js의 pageExtensions configuration의 영향을 받습니다.
  • API Routes do not specify CORS headers, meaning they are same-origin only by default. You can customize such behavior by wrapping the request handler with the CORS request helpers.
  • API Routes can't be used with static exports. However, Route Handlers in the App Router can.
  • API Routes will be affected by pageExtensions configuration in next.config.js.

Parameters

export default function handler(req: NextApiRequest, res: NextApiResponse) {
  // ...
}
  • req: http.IncomingMessage의 instance
  • res: http.ServerResponse의 instance
  • req: An instance of http.IncomingMessage
  • res: An instance of http.ServerResponse

HTTP MethodsHTTP Method

API route에서 서로 다른 HTTP method를 처리하려면 request handler에서 다음과 같이 req.method를 사용할 수 있습니다:

To handle different HTTP methods in an API route, you can use req.method in your request handler, like so:

TSJSpages/api/hello.ts
import type { NextApiRequest, NextApiResponse } from 'next'

export default function handler(req: NextApiRequest, res: NextApiResponse) {
  if (req.method === 'POST') {
    // Process a POST request
  } else {
    // Handle any other HTTP method
  }
}
export default function handler(req, res) {
  if (req.method === 'POST') {
    // Process a POST request
  } else {
    // Handle any other HTTP method
  }
}

Request HelpersRequest Helper

API Route는 들어오는 request(req)를 parse하는 기본 제공 request helper를 제공합니다:

API Routes provide built-in request helpers which parse the incoming request (req):

  • req.cookies - request가 보낸 cookie를 담은 object입니다. 기본값은 {}
  • req.query - query string을 담은 object입니다. 기본값은 {}
  • req.body - content-type에 따라 parse된 body를 담은 object이며, body가 전송되지 않았다면 null
  • req.cookies - An object containing the cookies sent by the request. Defaults to {}
  • req.query - An object containing the query string. Defaults to {}
  • req.body - An object containing the body parsed by content-type, or null if no body was sent

Custom config

모든 API Route는 config object를 export해 기본 configuration을 바꿀 수 있습니다. 기본 configuration은 다음과 같습니다:

Every API Route can export a config object to change the default configuration, which is the following:

export const config = {
  api: {
    bodyParser: {
      sizeLimit: '1mb',
    },
  },
  // Specifies the maximum allowed duration for this function to execute (in seconds)
  maxDuration: 5,
}

bodyParser는 자동으로 활성화됩니다. body를 Stream으로 사용하거나 raw-body로 사용하고 싶다면 이를 false로 설정할 수 있습니다.

bodyParser is automatically enabled. If you want to consume the body as a Stream or with raw-body, you can set this to false.

자동 bodyParser를 비활성화하는 사용 사례 중 하나는 GitHub에서 오는 것과 같은 webhook request의 raw body를 검증하는 것입니다.

One use case for disabling the automatic bodyParser is to allow you to verify the raw body of a webhook request, for example from GitHub.

export const config = {
  api: {
    bodyParser: false,
  },
}

bodyParser.sizeLimit은 parse된 body에 허용되는 최대 크기이며, 다음처럼 bytes가 지원하는 모든 형식으로 지정할 수 있습니다:

bodyParser.sizeLimit is the maximum size allowed for the parsed body, in any format supported by bytes, like so:

export const config = {
  api: {
    bodyParser: {
      sizeLimit: '500kb',
    },
  },
}

externalResolver는 이 route가 express_나 _connect 같은 외부 resolver에 의해 처리되고 있음을 server에 알리는 명시적 flag입니다. 이 option을 활성화하면 해결되지 않은(unresolved) request에 대한 경고가 표시되지 않습니다.

externalResolver is an explicit flag that tells the server that this route is being handled by an external resolver like express or connect. Enabling this option disables warnings for unresolved requests.

export const config = {
  api: {
    externalResolver: true,
  },
}

responseLimit은 자동으로 활성화되며, API Route의 response body가 4MB를 넘으면 경고합니다.

responseLimit is automatically enabled, warning when an API Routes' response body is over 4MB.

serverless 환경에서 Next.js를 사용하지 않고, CDN이나 전용 media host를 사용하지 않을 때의 performance 영향을 이해하고 있다면 이 limit을 false로 설정할 수 있습니다.

If you are not using Next.js in a serverless environment, and understand the performance implications of not using a CDN or dedicated media host, you can set this limit to false.

export const config = {
  api: {
    responseLimit: false,
  },
}

responseLimit에는 byte 수나 bytes가 지원하는 문자열 형식(예: 1000, '500kb', '3mb')도 지정할 수 있습니다. 이 값은 경고가 표시되기 전까지의 최대 response 크기가 됩니다. 기본값은 4MB입니다. (위 참고)

responseLimit can also take the number of bytes or any string format supported by bytes, for example 1000, '500kb' or '3mb'. This value will be the maximum response size before a warning is displayed. Default is 4MB. (see above)

export const config = {
  api: {
    responseLimit: '8mb',
  },
}

Response HelpersResponse Helper

Server Response object(흔히 res로 줄여 씀)에는 개발자 경험을 개선하고 새 API endpoint를 만드는 속도를 높여 주는 Express.js 스타일의 helper method가 포함되어 있습니다.

The Server Response object, (often abbreviated as res) includes a set of Express.js-like helper methods to improve the developer experience and increase the speed of creating new API endpoints.

포함된 helper는 다음과 같습니다:

The included helpers are:

  • res.status(code) - status code를 설정하는 함수입니다. code는 유효한 HTTP status code여야 합니다
  • res.json(body) - JSON response를 보냅니다. body는 serializable object여야 합니다
  • res.send(body) - HTTP response를 보냅니다. body는 string, object, Buffer 중 하나일 수 있습니다
  • res.redirect([status,] path) - 지정한 path나 URL로 redirect합니다. status는 유효한 HTTP status code여야 합니다. 지정하지 않으면 status의 기본값은 "307" "Temporary redirect"입니다.
  • res.revalidate(urlPath) - getStaticProps를 사용해 page를 on-demand로 revalidate합니다. urlPath는 string이어야 합니다.
  • res.status(code) - A function to set the status code. code must be a valid HTTP status code
  • res.json(body) - Sends a JSON response. body must be a serializable object
  • res.send(body) - Sends the HTTP response. body can be a string, an object or a Buffer
  • res.redirect([status,] path) - Redirects to a specified path or URL. status must be a valid HTTP status code. If not specified, status defaults to "307" "Temporary redirect".
  • res.revalidate(urlPath) - Revalidate a page on demand using getStaticProps. urlPath must be a string.

Setting the status code of a responseresponse의 status code 설정하기

client에 response를 돌려보낼 때 response의 status code를 설정할 수 있습니다.

When sending a response back to the client, you can set the status code of the response.

다음 예시는 response의 status code를 200(OK)으로 설정하고, 값이 Hello from Next.js!인 message property를 JSON response로 반환합니다:

The following example sets the status code of the response to 200 (OK) and returns a message property with the value of Hello from Next.js! as a JSON response:

TSJSpages/api/hello.ts
import type { NextApiRequest, NextApiResponse } from 'next'

type ResponseData = {
  message: string
}

export default function handler(
  req: NextApiRequest,
  res: NextApiResponse<ResponseData>
) {
  res.status(200).json({ message: 'Hello from Next.js!' })
}
export default function handler(req, res) {
  res.status(200).json({ message: 'Hello from Next.js!' })
}

Sending a JSON responseJSON response 보내기

client에 response를 돌려보낼 때 JSON response를 보낼 수 있으며, 이는 serializable object여야 합니다. 실제 애플리케이션에서는 요청한 endpoint의 결과에 따라 client에게 request의 상태를 알려 주고 싶을 수 있습니다.

When sending a response back to the client you can send a JSON response, this must be a serializable object. In a real world application you might want to let the client know the status of the request depending on the result of the requested endpoint.

다음 예시는 status code 200(OK)과 async 작업의 결과를 담은 JSON response를 보냅니다. 발생할 수 있는 error를 처리하기 위해 try catch block 안에 들어 있으며, 적절한 status code와 catch한 error message를 client에 돌려보냅니다:

The following example sends a JSON response with the status code 200 (OK) and the result of the async operation. It's contained in a try catch block to handle any errors that may occur, with the appropriate status code and error message caught and sent back to the client:

TSJSpages/api/hello.ts
import type { NextApiRequest, NextApiResponse } from 'next'

export default async function handler(
  req: NextApiRequest,
  res: NextApiResponse
) {
  try {
    const result = await someAsyncOperation()
    res.status(200).json({ result })
  } catch (err) {
    res.status(500).json({ error: 'failed to load data' })
  }
}
export default async function handler(req, res) {
  try {
    const result = await someAsyncOperation()
    res.status(200).json({ result })
  } catch (err) {
    res.status(500).json({ error: 'failed to load data' })
  }
}

Sending an HTTP responseHTTP response 보내기

HTTP response를 보내는 방법은 JSON response를 보낼 때와 같습니다. 유일한 차이점은 response body가 string, object, Buffer 중 하나일 수 있다는 것입니다.

Sending an HTTP response works the same way as when sending a JSON response. The only difference is that the response body can be a string, an object or a Buffer.

다음 예시는 status code 200(OK)과 async 작업의 결과를 담은 HTTP response를 보냅니다.

The following example sends an HTTP response with the status code 200 (OK) and the result of the async operation.

TSJSpages/api/hello.ts
import type { NextApiRequest, NextApiResponse } from 'next'

export default async function handler(
  req: NextApiRequest,
  res: NextApiResponse
) {
  try {
    const result = await someAsyncOperation()
    res.status(200).send({ result })
  } catch (err) {
    res.status(500).send({ error: 'failed to fetch data' })
  }
}

  try {

Redirects to a specified path or URL지정한 path나 URL로 redirect하기

form을 예로 들면, client가 form을 제출한 뒤 지정한 path나 URL로 redirect하고 싶을 수 있습니다.

Taking a form as an example, you may want to redirect your client to a specified path or URL once they have submitted the form.

다음 예시는 form이 성공적으로 제출되면 client를 / path로 redirect합니다:

The following example redirects the client to the / path if the form is successfully submitted:

TSJSpages/api/hello.ts
import type { NextApiRequest, NextApiResponse } from 'next'

export default async function handler(
  req: NextApiRequest,
  res: NextApiResponse
) {
  const { name, message } = req.body

  try {
    await handleFormInputAsync({ name, message })
    res.redirect(307, '/')
  } catch (err) {
    res.status(500).send({ error: 'Failed to fetch data' })
  }
}
export default async function handler(req, res) {
  const { name, message } = req.body

    await handleFormInputAsync({ name, message })

Adding TypeScript typesTypeScript type 추가하기

next에서 NextApiRequest와 NextApiResponse type을 import하면 API Route를 더 type-safe하게 만들 수 있으며, 이와 함께 response data에도 type을 지정할 수 있습니다:

You can make your API Routes more type-safe by importing the NextApiRequest and NextApiResponse types from next, in addition to those, you can also type your response data:

import type { NextApiRequest, NextApiResponse } from 'next'

type ResponseData = {
  message: string
}

export default function handler(
  req: NextApiRequest,
  res: NextApiResponse<ResponseData>
) {
  res.status(200).json({ message: 'Hello from Next.js!' })
}
Good to know

client가 어떤 payload든 포함할 수 있으므로 NextApiRequest의 body는 any입니다. body를 사용하기 전에 runtime에서 body의 type/형태를 검증해야 합니다.

The body of NextApiRequest is any because the client may include any payload. You should validate the type/shape of the body at runtime before using it.

Dynamic API RoutesDynamic API Route

API Route는 dynamic route를 지원하며, pages/에서 사용하는 것과 같은 파일 이름 규칙을 따릅니다.

API Routes support dynamic routes, and follow the same file naming rules used for pages/.

TSJSpages/api/post/[pid].ts
import type { NextApiRequest, NextApiResponse } from 'next'

export default function handler(req: NextApiRequest, res: NextApiResponse) {
  const { pid } = req.query
  res.end(`Post: ${pid}`)
}
export default function handler(req, res) {
  const { pid } = req.query
  res.end(`Post: ${pid}`)
}

이제 /api/post/abc로 request를 보내면 Post: abc라는 텍스트로 응답합니다.

Now, a request to /api/post/abc will respond with the text: Post: abc.

Catch all API routesCatch all API route

대괄호 안에 점 세 개(...)를 추가하면 API Route를 확장해 모든 path를 catch할 수 있습니다. 예를 들면 다음과 같습니다:

API Routes can be extended to catch all paths by adding three dots (...) inside the brackets. For example:

  • pages/api/post/[...slug].js는 /api/post/a뿐 아니라 /api/post/a/b, /api/post/a/b/c 등에도 match됩니다.
  • pages/api/post/[...slug].js matches /api/post/a, but also /api/post/a/b, /api/post/a/b/c and so on.
Good to know

[...param]처럼 slug 외의 다른 이름도 사용할 수 있습니다

You can use names other than slug, such as: [...param]

match된 parameter는 query parameter(예시에서는 slug)로 page에 전달되며, 항상 array입니다. 따라서 path /api/post/a는 다음 query object를 갖습니다:

Matched parameters will be sent as a query parameter (slug in the example) to the page, and it will always be an array, so, the path /api/post/a will have the following query object:

{ "slug": ["a"] }

그리고 /api/post/a/b나 그 밖에 match되는 path의 경우, 다음처럼 새 parameter가 array에 추가됩니다:

And in the case of /api/post/a/b, and any other matching path, new parameters will be added to the array, like so:

{ "slug": ["a", "b"] }

예를 들면 다음과 같습니다:

For example:

TSJSpages/api/post/[...slug].ts
import type { NextApiRequest, NextApiResponse } from 'next'

export default function handler(req: NextApiRequest, res: NextApiResponse) {
  const { slug } = req.query
  res.end(`Post: ${slug.join(', ')}`)
}
export default function handler(req, res) {
  const { slug } = req.query
  res.end(`Post: ${slug.join(', ')}`)
}

이제 /api/post/a/b/c로 request를 보내면 Post: a, b, c라는 텍스트로 응답합니다.

Now, a request to /api/post/a/b/c will respond with the text: Post: a, b, c.

Optional catch all API routesOptional catch all API route

parameter를 이중 대괄호([[...slug]])로 감싸면 catch all route를 optional로 만들 수 있습니다.

Catch all routes can be made optional by including the parameter in double brackets ([[...slug]]).

예를 들어 pages/api/post/[[...slug]].js는 /api/post, /api/post/a, /api/post/a/b 등에 match됩니다.

For example, pages/api/post/[[...slug]].js will match /api/post, /api/post/a, /api/post/a/b, and so on.

catch all route와 optional catch all route의 주요 차이점은, optional의 경우 parameter가 없는 route(위 예시의 /api/post)도 match된다는 것입니다.

The main difference between catch all and optional catch all routes is that with optional, the route without the parameter is also matched (/api/post in the example above).

query object는 다음과 같습니다:

The query objects are as follows:

{ } // GET `/api/post` (empty object)
{ "slug": ["a"] } // `GET /api/post/a` (single-element array)
{ "slug": ["a", "b"] } // `GET /api/post/a/b` (multi-element array)

Caveats주의 사항

  • 미리 정의된 API route가 dynamic API route보다 우선하고, dynamic API route가 catch all API route보다 우선합니다. 다음 예시를 살펴보세요:
    • pages/api/post/create.js - /api/post/create에 match됩니다
    • pages/api/post/[pid].js - /api/post/1, /api/post/abc 등에 match됩니다. 하지만 /api/post/create에는 match되지 않습니다
    • pages/api/post/[...slug].js - /api/post/1/2, /api/post/a/b/c 등에 match됩니다. 하지만 /api/post/create, /api/post/abc에는 match되지 않습니다
  • Predefined API routes take precedence over dynamic API routes, and dynamic API routes over catch all API routes. Take a look at the following examples:
    • pages/api/post/create.js - Will match /api/post/create
    • pages/api/post/[pid].js - Will match /api/post/1, /api/post/abc, etc. But not /api/post/create
    • pages/api/post/[...slug].js - Will match /api/post/1/2, /api/post/a/b/c, etc. But not /api/post/create, /api/post/abc

Streaming responsesStreaming response

Pages Router도 API Route에서 streaming response를 지원하지만, Next.js 14+를 사용한다면 App Router를 점진적으로 도입하고 Route Handlers를 사용하는 것을 권장합니다.

While the Pages Router does support streaming responses with API Routes, we recommend incrementally adopting the App Router and using Route Handlers if you are on Next.js 14+.

다음은 writeHead로 API Route에서 response를 stream하는 방법입니다:

Here's how you can stream a response from an API Route with writeHead:

TSJSpages/api/hello.ts
import { NextApiRequest, NextApiResponse } from 'next'

export default async function handler(
  req: NextApiRequest,
  res: NextApiResponse
) {
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-store',
  })
  let i = 0
  while (i < 10) {
    res.write(`data: ${i}\n\n`)
    i++
    await new Promise((resolve) => setTimeout(resolve, 1000))
  }
  res.end()
}
export default async function handler(req, res) {
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-store',
  })
  let i = 0
  while (i < 10) {
    res.write(`data: ${i}\n\n`)
    i++
    await new Promise((resolve) => setTimeout(resolve, 1000))
  }
  res.end()
}
