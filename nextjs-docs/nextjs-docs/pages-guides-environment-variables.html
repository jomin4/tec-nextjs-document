How to use environment variables in Next.jsNext.js에서 environment variable 사용하기

Next.js는 environment variable을 기본으로(built-in) 지원하며, 이를 통해 다음을 할 수 있습니다:

Next.js comes with built-in support for environment variables, which allows you to do the following:

  • .env로 environment variable 불러오기
  • NEXT_PUBLIC_ 접두사를 붙여 브라우저용 environment variable bundle하기
  • Use .env to load environment variables
  • Bundle environment variables for the browser by prefixing with NEXT_PUBLIC_
Warning

기본 create-next-app template은 모든 .env 파일이 .gitignore에 추가되도록 보장합니다. 이 파일들을 repository에 commit하고 싶은 경우는 거의 없을 것입니다.

The default create-next-app template ensures all .env files are added to your .gitignore. You almost never want to commit these files to your repository.

Loading Environment VariablesEnvironment Variable 불러오기

Next.js는 .env* 파일의 environment variable을 process.env로 불러오는 기능을 기본으로 지원합니다.

Next.js has built-in support for loading environment variables from .env* files into process.env.

>_.env
DB_HOST=localhost
DB_USER=myuser
DB_PASS=mypassword

이렇게 하면 process.env.DB_HOST, process.env.DB_USER, process.env.DB_PASS가 Node.js 환경에 자동으로 로드되어 Next.js data fetching method와 API routes에서 사용할 수 있습니다.

This loads process.env.DB_HOST, process.env.DB_USER, and process.env.DB_PASS into the Node.js environment automatically allowing you to use them in Next.js data fetching methods and API routes.

예를 들어 getStaticProps를 사용하면:

For example, using getStaticProps:

JSpages/index.js
export async function getStaticProps() {
  const db = await myDB.connect({
    host: process.env.DB_HOST,
    username: process.env.DB_USER,
    password: process.env.DB_PASS,
  })
  // ...
}

Loading Environment Variables with @next/env@next/env로 Environment Variable 불러오기

ORM이나 test runner의 root config 파일처럼 Next.js runtime 밖에서 environment variable을 불러와야 한다면 @next/env package를 사용할 수 있습니다.

If you need to load environment variables outside of the Next.js runtime, such as in a root config file for an ORM or test runner, you can use the @next/env package.

이 package는 Next.js가 내부적으로 .env* 파일에서 environment variable을 불러올 때 사용합니다.

This package is used internally by Next.js to load environment variables from .env* files.

사용하려면 package를 설치하고 loadEnvConfig 함수로 environment variable을 불러오세요:

To use it, install the package and use the loadEnvConfig function to load the environment variables:

pnpm add @next/env
npm install @next/env
yarn add @next/env
bun add @next/env
TSJSenvConfig.ts
import { loadEnvConfig } from '@next/env'

const projectDir = process.cwd()
loadEnvConfig(projectDir)
import { loadEnvConfig } from '@next/env'

const projectDir = process.cwd()
loadEnvConfig(projectDir)

그런 다음 필요한 곳에서 configuration을 import할 수 있습니다. 예를 들면 다음과 같습니다:

Then, you can import the configuration where needed. For example:

TSJSorm.config.ts
import './envConfig.ts'

export default defineConfig({
  dbCredentials: {
    connectionString: process.env.DATABASE_URL!,
  },
})
import './envConfig.js'

export default defineConfig({
  dbCredentials: {
    connectionString: process.env.DATABASE_URL,
  },
})

Referencing Other Variables다른 변수 참조하기

Next.js는 .env* 파일 안에서 $VARIABLE처럼 $를 사용해 다른 변수를 참조하는 변수를 자동으로 확장합니다. 이를 통해 다른 secret을 참조할 수 있습니다. 예를 들면 다음과 같습니다:

Next.js will automatically expand variables that use $ to reference other variables e.g. $VARIABLE inside of your .env* files. This allows you to reference other secrets. For example:

>_.env
TWITTER_USER=nextjs
TWITTER_URL=https://x.com/$TWITTER_USER

위 예제에서 process.env.TWITTER_URL은 https://x.com/nextjs로 설정됩니다.

In the above example, process.env.TWITTER_URL would be set to https://x.com/nextjs.

Good to know

실제 값에 $가 들어간 변수를 사용해야 한다면 \$처럼 escape해야 합니다.

If you need to use variable with a $ in the actual value, it needs to be escaped e.g. \$.

Bundling Environment Variables for the Browser브라우저용 Environment Variable bundle하기

NEXT_PUBLIC_이 아닌 environment variable은 Node.js 환경에서만 사용할 수 있습니다. 즉, 브라우저에서는 접근할 수 없습니다(client는 다른 *환경*에서 실행됩니다).

Non-NEXT_PUBLIC_ environment variables are only available in the Node.js environment, meaning they aren't accessible to the browser (the client runs in a different environment).

environment variable의 값을 브라우저에서 접근할 수 있게 하기 위해, Next.js는 build time에 client로 전달되는 js bundle에 값을 "inline"하여 process.env.[variable]에 대한 모든 참조를 하드코딩된 값으로 대체할 수 있습니다. 이렇게 하도록 지시하려면 변수에 NEXT_PUBLIC_ 접두사만 붙이면 됩니다. 예를 들면 다음과 같습니다:

In order to make the value of an environment variable accessible in the browser, Next.js can "inline" a value, at build time, into the js bundle that is delivered to the client, replacing all references to process.env.[variable] with a hard-coded value. To tell it to do this, you just have to prefix the variable with NEXT_PUBLIC_. For example:

>_.env
NEXT_PUBLIC_ANALYTICS_ID=abcdefghijk

이렇게 하면 Next.js는 Node.js 환경에서 process.env.NEXT_PUBLIC_ANALYTICS_ID에 대한 모든 참조를 next build를 실행한 환경의 값으로 대체하므로, 코드 어디에서나 사용할 수 있습니다. 이 값은 브라우저로 전송되는 모든 JavaScript에 inline됩니다.

This will tell Next.js to replace all references to process.env.NEXT_PUBLIC_ANALYTICS_ID in the Node.js environment with the value from the environment in which you run next build, allowing you to use it anywhere in your code. It will be inlined into any JavaScript sent to the browser.

Note

build된 이후에는 앱이 이 environment variable의 변경에 더 이상 반응하지 않습니다. 예를 들어 Heroku pipeline을 사용해 한 환경에서 build된 slug를 다른 환경으로 승격(promote)하거나, 하나의 Docker image를 build해서 여러 환경에 deploy하는 경우, 모든 NEXT_PUBLIC_ 변수는 build time에 평가된 값으로 고정됩니다. 따라서 이 값들은 프로젝트를 build할 때 적절히 설정되어 있어야 합니다. runtime 환경 값에 접근해야 한다면 이를 client에 제공하는 자체 API를 설정해야 합니다(필요할 때 또는 초기화 중에).

After being built, your app will no longer respond to changes to these environment variables. For instance, if you use a Heroku pipeline to promote slugs built in one environment to another environment, or if you build and deploy a single Docker image to multiple environments, all NEXT_PUBLIC_ variables will be frozen with the value evaluated at build time, so these values need to be set appropriately when the project is built. If you need access to runtime environment values, you'll have to set up your own API to provide them to the client (either on demand or during initialization).

JSpages/index.js
import setupAnalyticsService from '../lib/my-analytics-service'

// 'NEXT_PUBLIC_ANALYTICS_ID' can be used here as it's prefixed by 'NEXT_PUBLIC_'.
// It will be transformed at build time to `setupAnalyticsService('abcdefghijk')`.
setupAnalyticsService(process.env.NEXT_PUBLIC_ANALYTICS_ID)

function HomePage() {
  return <h1>Hello World</h1>
}

export default HomePage

다음과 같은 dynamic lookup은 inline되지 *않는다*는 점에 유의하세요:

Note that dynamic lookups will not be inlined, such as:

// This will NOT be inlined, because it uses a variable
const varName = 'NEXT_PUBLIC_ANALYTICS_ID'
setupAnalyticsService(process.env[varName])

// This will NOT be inlined, because it uses a variable
const env = process.env
setupAnalyticsService(env.NEXT_PUBLIC_ANALYTICS_ID)

Runtime Environment VariablesRuntime Environment Variable

Next.js는 build time과 runtime environment variable을 모두 지원할 수 있습니다.

Next.js can support both build time and runtime environment variables.

기본적으로 environment variable은 server에서만 사용할 수 있습니다. environment variable을 브라우저에 노출하려면 NEXT_PUBLIC_ 접두사를 붙여야 합니다. 하지만 이런 public environment variable은 next build 중에 JavaScript bundle에 inline됩니다.

By default, environment variables are only available on the server. To expose an environment variable to the browser, it must be prefixed with NEXT_PUBLIC_. However, these public environment variables will be inlined into the JavaScript bundle during next build.

runtime environment variable을 읽으려면 getServerSideProps를 사용하거나 App Router를 점진적으로 도입하는 것을 권장합니다.

To read runtime environment variables, we recommend using getServerSideProps or incrementally adopting the App Router.

이를 통해 서로 다른 값을 가진 여러 환경으로 승격될 수 있는 단일 Docker image를 사용할 수 있습니다.

This allows you to use a singular Docker image that can be promoted through multiple environments with different values.

Good to know:

Good to know:

  • register 함수를 사용해 server 시작 시 코드를 실행할 수 있습니다.
  • You can run code on server startup using the register function.

Test Environment VariablesTest Environment Variable

development와 production 환경 외에 세 번째 옵션인 test도 있습니다. development나 production 환경의 기본값을 설정하는 것과 같은 방식으로, testing 환경에 대해서도 .env.test 파일로 기본값을 설정할 수 있습니다(앞의 두 가지만큼 흔하지는 않습니다). Next.js는 testing 환경에서 .env.development나 .env.production의 environment variable을 불러오지 않습니다.

Apart from development and production environments, there is a 3rd option available: test. In the same way you can set defaults for development or production environments, you can do the same with a .env.test file for the testing environment (though this one is not as common as the previous two). Next.js will not load environment variables from .env.development or .env.production in the testing environment.

이 옵션은 테스트 목적으로만 특정 environment variable을 설정해야 하는 jest나 cypress 같은 도구로 테스트를 실행할 때 유용합니다. NODE_ENV가 test로 설정되면 test 기본값이 로드되지만, 보통은 테스트 도구가 알아서 처리해 주므로 직접 설정할 필요는 없습니다.

This one is useful when running tests with tools like jest or cypress where you need to set specific environment vars only for testing purposes. Test default values will be loaded if NODE_ENV is set to test, though you usually don't need to do this manually as testing tools will address it for you.

test 환경과 development·production 환경 사이에는 염두에 두어야 할 작은 차이가 있습니다: 테스트는 모두에게 같은 결과를 내야 하므로 .env.local은 로드되지 않습니다. 이런 방식으로 (기본 설정을 덮어쓰기 위한) .env.local을 무시함으로써, 모든 테스트 실행이 실행마다 같은 env 기본값을 사용하게 됩니다.

There is a small difference between test environment, and both development and production that you need to bear in mind: .env.local won't be loaded, as you expect tests to produce the same results for everyone. This way every test execution will use the same env defaults across different executions by ignoring your .env.local (which is intended to override the default set).

Good to know

Default Environment Variables와 마찬가지로 .env.test 파일은 repository에 포함해야 하지만, .env.test.local은 포함하면 안 됩니다. .env*.local은 .gitignore로 무시되도록 의도된 파일이기 때문입니다.

similar to Default Environment Variables, .env.test file should be included in your repository, but .env.test.local shouldn't, as .env*.local are intended to be ignored through .gitignore.

unit test를 실행하는 동안 @next/env package의 loadEnvConfig 함수를 활용하면 Next.js와 같은 방식으로 environment variable을 불러올 수 있습니다.

While running unit tests you can make sure to load your environment variables the same way Next.js does by leveraging the loadEnvConfig function from the @next/env package.

// The below can be used in a Jest global setup file or similar for your testing set-up
import { loadEnvConfig } from '@next/env'

export default async () => {
  const projectDir = process.cwd()
  loadEnvConfig(projectDir)
}

Environment Variable Load OrderEnvironment Variable 로드 순서

environment variable은 다음 위치에서 순서대로 찾으며, 변수를 찾으면 멈춥니다.

Environment variables are looked up in the following places, in order, stopping once the variable is found.

  1. process.env
  2. .env.$(NODE_ENV).local
  3. .env.local (NODE_ENV가 test일 때는 확인하지 않습니다.)
  4. .env.$(NODE_ENV)
  5. .env
  1. process.env
  2. .env.$(NODE_ENV).local
  3. .env.local (Not checked when NODE_ENV is test.)
  4. .env.$(NODE_ENV)
  5. .env

예를 들어 NODE_ENV가 development이고 .env.development.local과 .env 양쪽에 변수를 정의했다면 .env.development.local의 값이 사용됩니다.

For example, if NODE_ENV is development and you define a variable in both .env.development.local and .env, the value in .env.development.local will be used.

Good to know

NODE_ENV에 허용되는 값은 production, development, test입니다.

The allowed values for NODE_ENV are production, development and test.

Good to know

  • /src directory를 사용하는 경우에도 .env.* 파일은 프로젝트 root에 두어야 합니다.
  • environment variable NODE_ENV가 할당되지 않은 경우, Next.js는 next dev 명령을 실행할 때 자동으로 development를, 그 외 모든 명령에는 production을 할당합니다.
  • If you are using a /src directory, .env.* files should remain in the root of your project.
  • If the environment variable NODE_ENV is unassigned, Next.js automatically assigns development when running the next dev command, or production for all other commands.
