Image (Legacy)legacyImage (Legacy)

Next.js 13부터 next/image component는 성능과 개발자 경험(developer experience)을 모두 개선하기 위해 새로 작성되었습니다. 하위 호환되는 upgrade 방법을 제공하기 위해, 기존 next/image는 next/legacy/image로 이름이 바뀌었습니다.

Starting with Next.js 13, the next/image component was rewritten to improve both the performance and developer experience. In order to provide a backwards compatible upgrade solution, the old next/image was renamed to next/legacy/image.

Warning

next/legacy/image는 deprecated되었으며 Next.js의 향후 버전에서 제거될 예정입니다. 대신 next/image를 사용하세요.

next/legacy/image is deprecated and will be removed in a future version of Next.js. Please use next/image instead.

Comparison비교

next/legacy/image와 비교해 새 next/image component에는 다음과 같은 변경 사항이 있습니다:

Compared to next/legacy/image, the new next/image component has the following changes:

  • native computed aspect ratio를 사용하기 위해 <img>를 감싸던 <span> wrapper를 제거했습니다
  • 표준 style prop 지원을 추가했습니다
    • style이나 className을 사용하도록 layout prop을 제거했습니다
    • style이나 className을 사용하도록 objectFit prop을 제거했습니다
    • style이나 className을 사용하도록 objectPosition prop을 제거했습니다
  • native lazy loading을 사용하기 위해 IntersectionObserver 구현을 제거했습니다
    • native에 대응하는 기능이 없으므로 lazyBoundary prop을 제거했습니다
    • native에 대응하는 기능이 없으므로 lazyRoot prop을 제거했습니다
  • loader prop을 사용하도록 loader config를 제거했습니다
  • alt prop을 선택 사항에서 필수로 변경했습니다
  • onLoadingComplete callback이 <img> element에 대한 reference를 받도록 변경했습니다
  • Removes <span> wrapper around <img> in favor of native computed aspect ratio
  • Adds support for canonical style prop
    • Removes layout prop in favor of style or className
    • Removes objectFit prop in favor of style or className
    • Removes objectPosition prop in favor of style or className
  • Removes IntersectionObserver implementation in favor of native lazy loading
    • Removes lazyBoundary prop since there is no native equivalent
    • Removes lazyRoot prop since there is no native equivalent
  • Removes loader config in favor of loader prop
  • Changed alt prop from optional to required
  • Changed onLoadingComplete callback to receive reference to <img> element

Required Props필수 Props

<Image /> component에는 다음 property가 필요합니다.

The <Image /> component requires the following properties.

src

다음 중 하나여야 합니다:

Must be one of the following:

  • static하게 import된 이미지 파일
  • path 문자열. loader prop이나 loader configuration에 따라 절대 외부 URL이나 내부 path가 될 수 있습니다.
  • A statically imported image file
  • A path string. This can be either an absolute external URL, or an internal path depending on the loader prop or loader configuration.

기본 loader를 사용할 때는 원본 이미지에 대해 다음 사항도 고려하세요:

When using the default loader, also consider the following for source images:

  • src가 외부 URL이면 remotePatterns도 설정해야 합니다
  • src가 animated이거나 알려진 형식(JPEG, PNG, WebP, AVIF, GIF, TIFF)이 아니면 이미지가 있는 그대로 제공됩니다
  • src가 SVG 형식이면 unoptimized나 dangerouslyAllowSVG가 활성화되지 않는 한 차단됩니다
  • When src is an external URL, you must also configure remotePatterns
  • When src is animated or not a known format (JPEG, PNG, WebP, AVIF, GIF, TIFF) the image will be served as-is
  • When src is SVG format, it will be blocked unless unoptimized or dangerouslyAllowSVG is enabled

width

width property는 layout과 sizes property에 따라 render되는 너비 또는 원본 너비를 pixel 단위로 나타낼 수 있습니다.

The width property can represent either the rendered width or original width in pixels, depending on the layout and sizes properties.

layout="intrinsic"이나 layout="fixed"를 사용하면 width property는 render되는 너비를 pixel 단위로 나타내므로, 이미지가 얼마나 크게 보이는지에 영향을 줍니다.

When using layout="intrinsic" or layout="fixed" the width property represents the rendered width in pixels, so it will affect how large the image appears.

layout="responsive", layout="fill"을 사용하면 width property는 원본 너비를 pixel 단위로 나타내므로, aspect ratio에만 영향을 줍니다.

When using layout="responsive", layout="fill", the width property represents the original width in pixels, so it will only affect the aspect ratio.

width property는 static하게 import된 이미지나 layout="fill"을 사용하는 이미지를 제외하고는 필수입니다.

The width property is required, except for statically imported images, or those with layout="fill".

height

height property는 layout과 sizes property에 따라 render되는 높이 또는 원본 높이를 pixel 단위로 나타낼 수 있습니다.

The height property can represent either the rendered height or original height in pixels, depending on the layout and sizes properties.

layout="intrinsic"이나 layout="fixed"를 사용하면 height property는 render되는 높이를 pixel 단위로 나타내므로, 이미지가 얼마나 크게 보이는지에 영향을 줍니다.

When using layout="intrinsic" or layout="fixed" the height property represents the rendered height in pixels, so it will affect how large the image appears.

layout="responsive", layout="fill"을 사용하면 height property는 원본 높이를 pixel 단위로 나타내므로, aspect ratio에만 영향을 줍니다.

When using layout="responsive", layout="fill", the height property represents the original height in pixels, so it will only affect the aspect ratio.

height property는 static하게 import된 이미지나 layout="fill"을 사용하는 이미지를 제외하고는 필수입니다.

The height property is required, except for statically imported images, or those with layout="fill".

<Image /> component는 필수 property 외에도 여러 추가 property를 받습니다. 이 섹션에서는 Image component에서 가장 자주 쓰이는 property를 설명합니다. 덜 쓰이는 property에 대한 자세한 내용은 Advanced Props 섹션에서 확인하세요.

The <Image /> component accepts a number of additional properties beyond those which are required. This section describes the most commonly-used properties of the Image component. Find details about more rarely-used properties in the Advanced Props section.

loader

URL을 resolve하는 데 사용하는 custom 함수입니다. Image component에 loader를 prop으로 설정하면 next.config.js의 images 섹션에 정의된 기본 loader를 override합니다.

A custom function used to resolve URLs. Setting the loader as a prop on the Image component overrides the default loader defined in the images section of next.config.js.

loader는 다음 parameter를 받아 이미지의 URL 문자열을 반환하는 함수입니다:

A loader is a function returning a URL string for the image, given the following parameters:

  • src
  • width
  • quality
  • src
  • width
  • quality

다음은 custom loader를 사용하는 예제입니다:

Here is an example of using a custom loader:

import Image from 'next/legacy/image'

const myLoader = ({ src, width, quality }) => {
  return `https://example.com/${src}?w=${width}&q=${quality || 75}`
}

const MyImage = (props) => {
  return (
    <Image
      loader={myLoader}
      src="me.png"
      alt="Picture of the author"
      width={500}
      height={500}
    />
  )
}

sizes

breakpoint별로 이미지가 얼마나 넓게 표시될지에 대한 정보를 제공하는 문자열입니다. sizes 값은 layout="responsive"나 layout="fill"을 사용하는 이미지의 성능에 큰 영향을 줍니다. layout="intrinsic"이나 layout="fixed"를 사용하는 이미지에서는 무시됩니다.

A string that provides information about how wide the image will be at different breakpoints. The value of sizes will greatly affect performance for images using layout="responsive" or layout="fill". It will be ignored for images using layout="intrinsic" or layout="fixed".

sizes property는 이미지 성능과 관련해 두 가지 중요한 역할을 합니다:

The sizes property serves two important purposes related to image performance:

첫째, 브라우저는 sizes 값을 사용해 next/legacy/image가 자동 생성한 source set에서 어떤 크기의 이미지를 다운로드할지 결정합니다. 브라우저가 선택하는 시점에는 아직 page에서의 이미지 크기를 알지 못하므로, viewport와 같거나 더 큰 이미지를 선택합니다. sizes property를 사용하면 이미지가 실제로는 전체 화면보다 작다는 것을 브라우저에 알려 줄 수 있습니다. sizes 값을 지정하지 않으면 기본값 100vw(전체 화면 너비)가 사용됩니다.

First, the value of sizes is used by the browser to determine which size of the image to download, from next/legacy/image's automatically-generated source set. When the browser chooses, it does not yet know the size of the image on the page, so it selects an image that is the same size or larger than the viewport. The sizes property allows you to tell the browser that the image will actually be smaller than full screen. If you don't specify a sizes value, a default value of 100vw (full screen width) is used.

둘째, sizes 값은 parse되어 자동 생성된 source set의 값을 줄이는 데 사용됩니다. sizes property에 viewport 너비의 비율을 나타내는 50vw 같은 크기가 포함되어 있으면, source set에서 결코 필요하지 않을 만큼 작은 값은 제외됩니다.

Second, the sizes value is parsed and used to trim the values in the automatically-created source set. If the sizes property includes sizes such as 50vw, which represent a percentage of the viewport width, then the source set is trimmed to not include any values which are too small to ever be necessary.

예를 들어 styling 때문에 이미지가 모바일 기기에서는 전체 너비, 태블릿에서는 2열 layout, 데스크톱 화면에서는 3열 layout으로 표시된다는 것을 안다면, 다음과 같은 sizes property를 포함해야 합니다:

For example, if you know your styling will cause an image to be full-width on mobile devices, in a 2-column layout on tablets, and a 3-column layout on desktop displays, you should include a sizes property such as the following:

import Image from 'next/legacy/image'
const Example = () => (
  <div className="grid-element">
    <Image
      src="/example.png"
      layout="fill"
      sizes="(max-width: 768px) 100vw,
              (max-width: 1200px) 50vw,
              33vw"
    />
  </div>
)

이 예제의 sizes는 성능 지표에 극적인 효과를 줄 수 있습니다. 33vw sizes가 없다면 server에서 선택되는 이미지는 필요한 것보다 3배 넓습니다. 파일 크기는 너비의 제곱에 비례하므로, sizes가 없으면 사용자는 필요한 것보다 9배 큰 이미지를 다운로드하게 됩니다.

This example sizes could have a dramatic effect on performance metrics. Without the 33vw sizes, the image selected from the server would be 3 times as wide as it needs to be. Because file size is proportional to the square of the width, without sizes the user would download an image that's 9 times larger than necessary.

quality

최적화된 이미지의 품질로, 1에서 100 사이의 정수이며 100이 가장 좋은 품질입니다. 기본값은 75입니다.

The quality of the optimized image, an integer between 1 and 100 where 100 is the best quality. Defaults to 75.

priority

true이면 이미지는 높은 우선순위로 간주되어 preload됩니다. priority를 사용하는 이미지는 lazy loading이 자동으로 비활성화됩니다.

When true, the image will be considered high priority and preload. Lazy loading is automatically disabled for images using priority.

Largest Contentful Paint (LCP) element로 감지되는 모든 이미지에 priority property를 사용해야 합니다. viewport 크기에 따라 서로 다른 이미지가 LCP element가 될 수 있으므로, priority 이미지를 여러 개 두는 것이 적절할 수도 있습니다.

You should use the priority property on any image detected as the Largest Contentful Paint (LCP) element. It may be appropriate to have multiple priority images, as different images may be the LCP element for different viewport sizes.

이미지가 above the fold(스크롤 없이 보이는 영역)에 보일 때만 사용해야 합니다. 기본값은 false입니다.

Should only be used when the image is visible above the fold. Defaults to false.

placeholder

이미지가 로드되는 동안 사용할 placeholder입니다. 가능한 값은 blur 또는 empty입니다. 기본값은 empty입니다.

A placeholder to use while the image is loading. Possible values are blur or empty. Defaults to empty.

blur이면 blurDataURL property가 placeholder로 사용됩니다. src가 static import로 가져온 object이고 import된 이미지가 .jpg, .png, .webp, .avif라면 blurDataURL이 자동으로 채워집니다.

When blur, the blurDataURL property will be used as the placeholder. If src is an object from a static import and the imported image is .jpg, .png, .webp, or .avif, then blurDataURL will be automatically populated.

dynamic 이미지의 경우 blurDataURL property를 직접 제공해야 합니다. Plaiceholder 같은 솔루션이 base64 생성에 도움이 될 수 있습니다.

For dynamic images, you must provide the blurDataURL property. Solutions such as Plaiceholder can help with base64 generation.

empty이면 이미지가 로드되는 동안 placeholder 없이 빈 공간만 표시됩니다.

When empty, there will be no placeholder while the image is loading, only empty space.

Advanced Props고급 Props

경우에 따라 더 고급 사용법이 필요할 수 있습니다. <Image /> component는 선택적으로 다음 고급 property를 받습니다.

In some cases, you may need more advanced usage. The <Image /> component optionally accepts the following advanced properties.

style

내부 image element에 CSS style을 전달할 수 있습니다.

Allows passing CSS styles to the underlying image element.

모든 layout mode는 image element에 자체 style을 적용하며, 이 자동 style이 style prop보다 우선한다는 점에 유의하세요.

Note that all layout modes apply their own styles to the image element, and these automatic styles take precedence over the style prop.

또한 필수인 width와 height props가 styling과 상호작용할 수 있다는 점도 기억하세요. styling으로 이미지의 width를 수정한다면 height="auto" style도 함께 설정해야 하며, 그렇지 않으면 이미지가 왜곡됩니다.

Also keep in mind that the required width and height props can interact with your styling. If you use styling to modify an image's width, you must set the height="auto" style as well, or your image will be distorted.

objectFit

layout="fill"을 사용할 때 이미지가 parent container에 어떻게 맞춰질지 정의합니다.

Defines how the image will fit into its parent container when using layout="fill".

이 값은 src 이미지의 object-fit CSS property로 전달됩니다.

This value is passed to the object-fit CSS property for the src image.

objectPosition

layout="fill"을 사용할 때 이미지가 parent element 안에서 어떻게 배치될지 정의합니다.

Defines how the image is positioned within its parent element when using layout="fill".

이 값은 이미지에 적용되는 object-position CSS property로 전달됩니다.

This value is passed to the object-position CSS property applied to the image.

onLoadingComplete

이미지가 완전히 로드되고 placeholder가 제거되면 호출되는 callback 함수입니다.

A callback function that is invoked once the image is completely loaded and the placeholder has been removed.

onLoadingComplete 함수는 다음 property를 가진 object 하나를 parameter로 받습니다:

The onLoadingComplete function accepts one parameter, an object with the following properties:

  • naturalWidth
  • naturalHeight
  • naturalWidth
  • naturalHeight

loading

이미지의 loading 동작입니다. 기본값은 lazy입니다.

The loading behavior of the image. Defaults to lazy.

lazy이면 이미지가 viewport로부터 계산된 거리에 도달할 때까지 이미지 로드를 미룹니다.

When lazy, defer loading the image until it reaches a calculated distance from the viewport.

eager이면 이미지를 즉시 로드합니다.

When eager, load the image immediately.

blurDataURL

src 이미지가 성공적으로 로드되기 전에 placeholder 이미지로 사용할 Data URL입니다. placeholder="blur"와 함께 사용할 때만 효과가 있습니다.

A Data URL to be used as a placeholder image before the src image successfully loads. Only takes effect when combined with placeholder="blur".

base64로 encode된 이미지여야 합니다. 이미지가 확대되고 blur 처리되므로 아주 작은 이미지(10px 이하)를 권장합니다. 더 큰 이미지를 placeholder로 포함하면 애플리케이션 성능이 저하될 수 있습니다.

Must be a base64-encoded image. It will be enlarged and blurred, so a very small image (10px or less) is recommended. Including larger images as placeholders may harm your application performance.

lazyBoundary

viewport와 이미지의 교차(intersection)를 감지해 lazy loading을 trigger하는 데 사용되는 bounding box 역할을 하는 문자열입니다(margin property와 비슷한 문법). 기본값은 "200px"입니다.

A string (with similar syntax to the margin property) that acts as the bounding box used to detect the intersection of the viewport with the image and trigger lazy loading. Defaults to "200px".

이미지가 root document가 아닌 scroll 가능한 parent element 안에 중첩되어 있다면 lazyRoot prop도 지정해야 합니다.

If the image is nested in a scrollable parent element other than the root document, you will also need to assign the lazyRoot prop.

Remote Patterns

악의적인 사용자로부터 애플리케이션을 보호하기 위해, 외부 이미지를 사용하려면 configuration이 필요합니다. 이를 통해 여러분의 계정에 속한 외부 이미지만 Next.js Image Optimization API에서 제공되도록 보장합니다. 이러한 외부 이미지는 아래와 같이 next.config.js 파일의 remotePatterns property로 설정할 수 있습니다:

To protect your application from malicious users, configuration is required in order to use external images. This ensures that only external images from your account can be served from the Next.js Image Optimization API. These external images can be configured with the remotePatterns property in your next.config.js file, as shown below:

JSnext.config.js
module.exports = {
  images: {
    remotePatterns: [
      {
        protocol: 'https',
        hostname: 'example.com',
        port: '',
        pathname: '/account123/**',
        search: '',
      },
    ],
  },
}
Good to know

위 예제는 next/legacy/image의 src property가 반드시 https://example.com/account123/로 시작하고 query string이 없도록 보장합니다. 그 외의 protocol, hostname, port 또는 일치하지 않는 path는 400 Bad Request로 응답합니다.

The example above will ensure the src property of next/legacy/image must start with https://example.com/account123/ and must not have a query string. Any other protocol, hostname, port, or unmatched path will respond with 400 Bad Request.

다음은 next.config.js 파일에서 hostname에 wildcard pattern을 사용한 remotePatterns property 예제입니다:

Below is an example of the remotePatterns property in the next.config.js file using a wildcard pattern in the hostname:

JSnext.config.js
module.exports = {
  images: {
    remotePatterns: [
      {
        protocol: 'https',
        hostname: '**.example.com',
        port: '',
        search: '',
      },
    ],
  },
}
Good to know

위 예제는 next/legacy/image의 src property가 반드시 https://img1.example.com, https://me.avatar.example.com 또는 임의 개수의 subdomain으로 시작하도록 보장합니다. port나 query string은 가질 수 없습니다. 그 외의 protocol이나 일치하지 않는 hostname은 400 Bad Request로 응답합니다.

The example above will ensure the src property of next/legacy/image must start with https://img1.example.com or https://me.avatar.example.com or any number of subdomains. It cannot have a port or query string. Any other protocol or unmatched hostname will respond with 400 Bad Request.

wildcard pattern은 pathname과 hostname 모두에 사용할 수 있으며, 다음 문법을 따릅니다:

Wildcard patterns can be used for both pathname and hostname and have the following syntax:

  • *는 하나의 path segment 또는 subdomain과 일치합니다
  • **는 끝부분의 여러 path segment 또는 시작 부분의 여러 subdomain과 일치합니다
  • * match a single path segment or subdomain
  • ** match any number of path segments at the end or subdomains at the beginning

** 문법은 pattern 중간에서는 동작하지 않습니다.

The ** syntax does not work in the middle of the pattern.

Good to know

protocol, port, pathname, search를 생략하면 wildcard **가 암묵적으로 적용됩니다. 이렇게 하면 악의적인 사용자가 의도하지 않은 url을 최적화하게 될 수 있으므로 권장하지 않습니다.

When omitting protocol, port, pathname, or search then the wildcard ** is implied. This is not recommended because it may allow malicious actors to optimize urls you did not intend.

다음은 next.config.js 파일에서 search를 사용한 remotePatterns property 예제입니다:

Below is an example of the remotePatterns property in the next.config.js file using search:

JSnext.config.js
module.exports = {
  images: {
    remotePatterns: [
      {
        protocol: 'https',
        hostname: 'assets.example.com',
        search: '?v=1727111025337',
      },
    ],
  },
}
Good to know

위 예제는 next/legacy/image의 src property가 반드시 https://assets.example.com으로 시작하고 정확히 ?v=1727111025337 query string을 갖도록 보장합니다. 그 외의 protocol이나 query string은 400 Bad Request로 응답합니다.

The example above will ensure the src property of next/legacy/image must start with https://assets.example.com and must have the exact query string ?v=1727111025337. Any other protocol or query string will respond with 400 Bad Request.

next.config.js 파일의 images.imageSizes property로 이미지 너비 목록을 지정할 수 있습니다. 이 너비들은 device sizes 배열과 합쳐져, 이미지 srcset을 생성하는 데 사용되는 전체 크기 배열을 구성합니다.

Acceptable Formats

기본 Image Optimization API는 최적의 output 형식을 결정하기 위해 request의 Accept header를 통해 브라우저가 지원하는 이미지 형식을 자동으로 감지합니다.

The default Image Optimization API will automatically detect the browser's supported image formats via the request's Accept header in order to determine the best output format.

Accept header가 설정된 형식 중 둘 이상과 일치하면 배열에서 처음 일치하는 형식이 사용됩니다. 따라서 배열 순서가 중요합니다. 일치하는 형식이 없으면(또는 원본 이미지가 animated이면) Image Optimization API는 원본 이미지의 형식으로 fallback합니다.

If the Accept header matches more than one of the configured formats, the first match in the array is used. Therefore, the array order matters. If there is no match (or the source image is animated), the Image Optimization API will fallback to the original image's format.

configuration을 제공하지 않으면 아래 기본값이 사용됩니다.

If no configuration is provided, the default below is used.

JSnext.config.js
module.exports = {
  images: {
    formats: ['image/webp'],
  },
}

AVIF 지원을 활성화할 수 있으며, 브라우저가 AVIF를 지원하지 않으면 src 이미지의 원본 형식으로 fallback합니다:

You can enable AVIF support, which will fallback to the original format of the src image if the browser does not support AVIF:

JSnext.config.js
module.exports = {
  images: {
    formats: ['image/avif'],
  },
}

AVIF와 WebP 형식을 함께 활성화할 수도 있습니다. AVIF를 지원하는 브라우저에서는 AVIF가 우선 사용되고, WebP가 fallback으로 사용됩니다:

You can also enable both AVIF and WebP formats together. AVIF will be preferred for browsers that support it, with WebP as a fallback:

JSnext.config.js
module.exports = {
  images: {
    formats: ['image/avif', 'image/webp'],
  },
}
Good to know
  • 대부분의 use case에서는 여전히 WebP 사용을 권장합니다.
  • AVIF는 일반적으로 encode하는 데 50% 더 오래 걸리지만, WebP보다 20% 더 작게 압축됩니다. 즉, 이미지가 처음 요청될 때는 보통 더 느리고, 이후 cache된 request는 더 빠릅니다.
  • 여러 형식을 사용하면 Next.js는 각 형식을 별도로 cache합니다. 서로 다른 브라우저 지원을 위해 AVIF와 WebP 버전의 이미지가 모두 저장되므로, 단일 형식을 사용할 때보다 저장 공간이 더 필요합니다.
  • Next.js 앞에 Proxy/CDN을 두고 self-host한다면, Proxy가 Accept header를 전달하도록 설정해야 합니다.
  • We still recommend using WebP for most use cases.
  • AVIF generally takes 50% longer to encode but it compresses 20% smaller compared to WebP. This means that the first time an image is requested, it will typically be slower and then subsequent requests that are cached will be faster.
  • When using multiple formats, Next.js will cache each format separately. This means increased storage requirements compared to using a single format, as both AVIF and WebP versions of images will be stored for different browser support.
  • If you self-host with a Proxy/CDN in front of Next.js, you must configure the Proxy to forward the Accept header.

Caching BehaviorCaching 동작

다음은 기본 loader의 caching 알고리즘을 설명합니다. 다른 모든 loader에 대해서는 cloud provider의 문서를 참고하세요.

The following describes the caching algorithm for the default loader. For all other loaders, please refer to your cloud provider's documentation.

이미지는 request 시점에 dynamic하게 최적화되어 <distDir>/cache/images directory에 저장됩니다. 최적화된 이미지 파일은 만료될 때까지 이후 request에 제공됩니다. cache되어 있지만 만료된 파일과 일치하는 request가 들어오면, 만료된 이미지가 즉시 stale 상태로 제공됩니다. 그런 다음 이미지가 background에서 다시 최적화되고(revalidation이라고도 함) 새 만료 날짜와 함께 cache에 저장됩니다.

Images are optimized dynamically upon request and stored in the <distDir>/cache/images directory. The optimized image file will be served for subsequent requests until the expiration is reached. When a request is made that matches a cached but expired file, the expired image is served stale immediately. Then the image is optimized again in the background (also called revalidation) and saved to the cache with the new expiration date.

이미지의 cache 상태는 x-nextjs-cache(Vercel에 deploy한 경우 x-vercel-cache) response header 값을 읽어 확인할 수 있습니다. 가능한 값은 다음과 같습니다:

The cache status of an image can be determined by reading the value of the x-nextjs-cache (x-vercel-cache when deployed on Vercel) response header. The possible values are the following:

  • MISS - path가 cache에 없음 (첫 방문 시 최대 한 번 발생)
  • STALE - path가 cache에 있지만 revalidate 시간을 초과해서 background에서 업데이트됨
  • HIT - path가 cache에 있고 revalidate 시간을 초과하지 않음
  • MISS - the path is not in the cache (occurs at most once, on the first visit)
  • STALE - the path is in the cache but exceeded the revalidate time so it will be updated in the background
  • HIT - the path is in the cache and has not exceeded the revalidate time

만료(정확히는 Max Age)는 minimumCacheTTL configuration과 upstream 이미지의 Cache-Control header 중 더 큰 값으로 정의됩니다. 구체적으로는 Cache-Control header의 max-age 값이 사용됩니다. s-maxage와 max-age가 모두 있으면 s-maxage가 우선합니다. max-age는 CDN과 브라우저를 포함한 모든 downstream client에도 그대로 전달됩니다.

The expiration (or rather Max Age) is defined by either the minimumCacheTTL configuration or the upstream image Cache-Control header, whichever is larger. Specifically, the max-age value of the Cache-Control header is used. If both s-maxage and max-age are found, then s-maxage is preferred. The max-age is also passed-through to any downstream clients including CDNs and browsers.

  • upstream 이미지에 Cache-Control header가 없거나 값이 매우 낮으면 minimumCacheTTL을 설정해 cache 기간을 늘릴 수 있습니다.
  • deviceSizes와 imageSizes를 설정해 생성될 수 있는 이미지의 총 개수를 줄일 수 있습니다.
  • formats를 설정해 여러 형식 대신 단일 이미지 형식만 사용하도록 할 수 있습니다.
  • You can configure minimumCacheTTL to increase the cache duration when the upstream image does not include Cache-Control header or the value is very low.
  • You can configure deviceSizes and imageSizes to reduce the total number of possible generated images.
  • You can configure formats to disable multiple formats in favor of a single image format.

Minimum Cache TTL

cache된 최적화 이미지의 TTL(Time to Live)을 초 단위로 설정할 수 있습니다. 많은 경우 Static Image Import를 사용하는 것이 더 좋습니다. Static Image Import는 파일 내용을 자동으로 hash하고, 수명이 긴 immutable Cache-Control header로 이미지를 cache합니다.

You can configure the Time to Live (TTL) in seconds for cached optimized images. In many cases, it's better to use a Static Image Import which will automatically hash the file contents and cache the image with a long-lived immutable Cache-Control header.

configuration을 제공하지 않으면 아래 기본값이 사용됩니다.

If no configuration is provided, the default below is used.

JSnext.config.js
module.exports = {
  images: {
    minimumCacheTTL: 14400, // 4 hours
  },
}

TTL을 늘려 revalidation 횟수를 줄이고 비용을 낮출 수 있습니다:

You can increase the TTL to reduce the number of revalidations and potentially lower cost:

JSnext.config.js
module.exports = {
  images: {
    minimumCacheTTL: 2678400, // 31 days
  },
}

최적화된 이미지의 만료(정확히는 Max Age)는 minimumCacheTTL과 upstream 이미지의 Cache-Control header 중 더 큰 값으로 정의됩니다.

The expiration (or rather Max Age) of the optimized image is defined by either the minimumCacheTTL or the upstream image Cache-Control header, whichever is larger.

이미지별로 caching 동작을 바꿔야 한다면, headers를 설정해 upstream 이미지(/_next/image 자체가 아니라 예: /some-asset.jpg)에 Cache-Control header를 지정할 수 있습니다.

If you need to change the caching behavior per image, you can configure headers to set the Cache-Control header on the upstream image (e.g. /some-asset.jpg, not /_next/image itself).

현재는 cache를 무효화하는 방법이 없으므로 minimumCacheTTL을 낮게 유지하는 것이 좋습니다. 그렇지 않으면 src prop을 직접 바꾸거나 <distDir>/cache/images를 삭제해야 할 수 있습니다.

There is no mechanism to invalidate the cache at this time, so its best to keep minimumCacheTTL low. Otherwise you may need to manually change the src prop or delete <distDir>/cache/images.

Disable Static Imports

기본 동작에서는 import icon from './icon.png'처럼 static 파일을 import한 다음 src property에 전달할 수 있습니다.

The default behavior allows you to import static files such as import icon from './icon.png' and then pass that to the src property.

경우에 따라 import가 다르게 동작하기를 기대하는 다른 plugin과 충돌한다면 이 기능을 비활성화하고 싶을 수 있습니다.

In some cases, you may wish to disable this feature if it conflicts with other plugins that expect the import to behave differently.

next.config.js에서 static image import를 비활성화할 수 있습니다:

You can disable static image imports inside your next.config.js:

JSnext.config.js
module.exports = {
  images: {
    disableStaticImages: true,
  },
}

Dangerously Allow SVG

기본 loader는 몇 가지 이유로 SVG 이미지를 최적화하지 않습니다. 첫째, SVG는 vector 형식이므로 손실 없이 크기를 조정할 수 있습니다. 둘째, SVG는 HTML/CSS와 같은 기능을 많이 가지고 있어서, 적절한 Content Security Policy (CSP) header 없이는 취약점이 생길 수 있습니다.

The default loader does not optimize SVG images for a few reasons. First, SVG is a vector format meaning it can be resized losslessly. Second, SVG has many of the same features as HTML/CSS, which can lead to vulnerabilities without proper Content Security Policy (CSP) headers.

따라서 src prop이 SVG라는 것을 알고 있다면 unoptimized prop을 사용하는 것을 권장합니다. src가 ".svg"로 끝나면 이는 자동으로 적용됩니다.

Therefore, we recommended using the unoptimized prop when the src prop is known to be SVG. This happens automatically when src ends with ".svg".

하지만 기본 Image Optimization API로 SVG 이미지를 제공해야 한다면, next.config.js에서 dangerouslyAllowSVG를 설정할 수 있습니다:

However, if you need to serve SVG images with the default Image Optimization API, you can set dangerouslyAllowSVG inside your next.config.js:

JSnext.config.js
module.exports = {
  images: {
    dangerouslyAllowSVG: true,
    contentDispositionType: 'attachment',
    contentSecurityPolicy: "default-src 'self'; script-src 'none'; sandbox;",
  },
}

또한 브라우저가 이미지를 다운로드하도록 강제하는 contentDispositionType과, 이미지에 포함된 script가 실행되지 않도록 막는 contentSecurityPolicy도 함께 설정할 것을 강력히 권장합니다.

In addition, it is strongly recommended to also set contentDispositionType to force the browser to download the image, as well as contentSecurityPolicy to prevent scripts embedded in the image from executing.

contentDispositionType

기본 loader는 API가 임의의 원격 이미지를 제공할 수 있으므로, 추가 보호를 위해 Content-Disposition header를 attachment로 설정합니다.

The default loader sets the Content-Disposition header to attachment for added protection since the API can serve arbitrary remote images.

기본값은 attachment이며, 직접 방문했을 때 브라우저가 이미지를 다운로드하도록 강제합니다. 이는 dangerouslyAllowSVG가 true일 때 특히 중요합니다.

The default value is attachment which forces the browser to download the image when visiting directly. This is particularly important when dangerouslyAllowSVG is true.

선택적으로 inline을 설정하면 직접 방문했을 때 다운로드 없이 브라우저가 이미지를 render하도록 할 수 있습니다.

You can optionally configure inline to allow the browser to render the image when visiting directly, without downloading it.

JSnext.config.js
module.exports = {
  images: {
    contentDispositionType: 'inline',
  },
}

Animated Images

기본 loader는 animated 이미지에 대해 Image Optimization을 자동으로 우회하고 이미지를 있는 그대로 제공합니다.

The default loader will automatically bypass Image Optimization for animated images and serve the image as-is.

animated 파일 자동 감지는 best-effort 방식이며 GIF, APNG, WebP를 지원합니다. 특정 animated 이미지에 대해 명시적으로 Image Optimization을 우회하고 싶다면 unoptimized prop을 사용하세요.

Auto-detection for animated files is best-effort and supports GIF, APNG, and WebP. If you want to explicitly bypass Image Optimization for a given animated image, use the unoptimized prop.
