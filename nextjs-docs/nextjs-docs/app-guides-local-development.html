How to optimize your local development environment로컬 개발 환경 최적화하기

Next.js는 뛰어난 개발자 경험을 제공하도록 설계되었습니다. 애플리케이션이 커지면 로컬 개발 중에 compile 시간이 느려지는 것을 느낄 수 있습니다. 이 가이드는 흔한 compile-time 성능 문제를 찾아내고 고치는 데 도움을 줍니다.

Next.js is designed to provide a great developer experience. As your application grows, you might notice slower compilation times during local development. This guide will help you identify and fix common compile-time performance issues.

Local dev vs. production로컬 개발 vs. production

next dev를 사용한 개발 과정은 next build, next start와 다릅니다.

The development process with next dev is different than next build and next start.

next dev는 애플리케이션의 route를 열거나 navigate할 때 그 route를 compile합니다. 덕분에 애플리케이션의 모든 route가 compile되기를 기다리지 않고 dev server를 시작할 수 있어서, 더 빠르고 memory도 적게 사용합니다. production build를 실행하면 파일 minify, content hash 생성 같은 다른 최적화가 적용되는데, 이는 로컬 개발에는 필요하지 않습니다.

next dev compiles routes in your application as you open or navigate to them. This enables you to start the dev server without waiting for every route in your application to compile, which is both faster and uses less memory. Running a production build applies other optimizations, like minifying files and creating content hashes, which are not needed for local development.

System configuration시스템 설정

1. Check your computer's antivirus1. 컴퓨터의 백신 프로그램 확인하기

백신(antivirus) 소프트웨어는 파일 접근 속도를 늦출 수 있습니다. Windows 컴퓨터에서 더 흔하긴 하지만, 백신 도구가 설치된 어떤 시스템에서든 문제가 될 수 있습니다.

Antivirus software can slow down file access. While this is more common on Windows machines, this can be an issue for any system with an antivirus tool installed.

Windows에서는 프로젝트를 Microsoft Defender Antivirus 제외 목록에 추가할 수 있습니다.

On Windows, you can add your project to the Microsoft Defender Antivirus exclusion list.

  1. "Windows Security" 애플리케이션을 열고 "Virus & threat protection" → "Manage settings" → "Add or remove exclusions" 순서로 선택합니다.
  2. "Folder" 제외 항목을 추가합니다. 프로젝트 폴더를 선택하세요.
  1. Open the "Windows Security" application and then select "Virus & threat protection" → "Manage settings" → "Add or remove exclusions".
  2. Add a "Folder" exclusion. Select your project folder.

또는 Dev Drive를 활성화해 사용할 수 있는데, Dev Drive는 Microsoft Defender의 "performance mode"를 사용합니다.

Alternatively, you can enable and use a Dev Drive, which uses Microsoft Defender's "performance mode".

macOS에서는 terminal 안에서 Gatekeeper를 비활성화할 수 있습니다.

On macOS, you can disable Gatekeeper inside of your terminal.

  1. terminal에서 sudo spctl developer-mode enable-terminal을 실행합니다.
  2. "System Settings" 앱을 열고 "Privacy & Security" → "Developer Tools" 순서로 선택합니다.
  3. 사용 중인 terminal이 목록에 있고 활성화되어 있는지 확인합니다. iTerm이나 Ghostty 같은 third-party terminal을 사용한다면 그것을 목록에 추가하세요.
  4. terminal을 다시 시작합니다.
  1. Run sudo spctl developer-mode enable-terminal in your terminal.
  2. Open the "System Settings" app and then select "Privacy & Security" → "Developer Tools".
  3. Ensure your terminal is listed and enabled. If you're using a third-party terminal like iTerm or Ghostty, add that to the list.
  4. Restart your terminal.

본인이나 회사가 시스템에 다른 백신 솔루션을 설정해 두었다면, 해당 제품의 관련 설정을 확인해야 합니다.

If you or your employer have configured any other Antivirus solutions on your system, you should inspect the relevant settings for those products.

2. Avoid common Docker pitfalls2. 흔한 Docker 함정 피하기

Mac이나 Windows에서 개발에 Docker를 사용한다면, Docker 없이 Next.js를 실행할 때보다 성능이 크게 느려질 수 있습니다.

If you're using Docker for development on Mac or Windows, you may experience significantly slower performance compared to running Next.js without Docker.

production 환경이나 Docker가 Linux에서 native로 실행될 때는 프로젝트 파일이 Docker Desktop의 host-to-VM 파일 공유 계층을 거치지 않으므로 일반적으로 문제가 되지 않습니다.

This generally isn't an issue in production or when Docker runs natively on Linux, because project files don't cross Docker Desktop's host-to-VM file-sharing layer.

프로젝트 파일이 macOS나 Windows host에 저장되어 있고 Docker Desktop 같은 도구를 통해 container에 mount되면, host-to-VM 파일 공유 계층이 filesystem event 전달을 지연시키거나 전달하지 못할 수 있습니다. 이 때문에 Fast Refresh가 몇 초, 심지어 몇 분씩 걸릴 수 있는 반면, 같은 애플리케이션도 Docker 없이 host에서 개발하면 업데이트가 빠르게 반영됩니다.

When project files are stored on the macOS or Windows host and mounted into a container through Docker Desktop or similar tools, the host-to-VM file-sharing layer can delay or fail to propagate filesystem events. This can cause Fast Refresh to take seconds or even minutes, while the same application shows updates quickly when developed on the host without Docker.

최상의 개발 경험을 위해서는:

For the best development experience:

  • 개발 중에는 Docker 없이 Next.js를 실행하세요(npm run dev 또는 pnpm dev).
  • Docker는 production deploy와 production build 테스트용으로 남겨 두세요.
  • 개발에 꼭 Docker를 써야 한다면 Linux 머신이나 수동으로 설정한 virtual machine에서 Docker를 native로 실행하는 것을 고려하세요. 수동으로 설정한 virtual machine을 사용한다면 source code를 VM 안으로 옮기고 host에서 공유하지 마세요.
  • Docker Desktop을 사용한다면 synchronized file shares 사용을 검토해 보세요. synchronized file share도 host에서 Next.js를 직접 실행하는 것에 비하면 여전히 latency가 추가되지만, polling에 의존하지 않고도 file-watching 안정성을 높일 수 있습니다.
  • Fast Refresh 문제를 우회하려고 next.config.js에서 watchOptions.pollIntervalMs를 사용하는 것은 피하세요. 최후의 수단으로만 사용하세요. polling은 상당한 latency를 추가하고 CPU와 I/O 사용량을 크게 늘릴 수 있습니다.
  • Run Next.js without Docker (npm run dev or pnpm dev) during development.
  • Reserve Docker for production deployments and testing production builds.
  • If you must use Docker for development, consider running Docker natively on a Linux machine or a manually configured virtual machine. If using a manually configured virtual machine, move the source code into the VM and do not share it from the host.
  • If you're using Docker Desktop, evaluate using synchronized file shares. Synchronized file shares still add latency compared to running Next.js directly on the host, but can improve file-watching reliability without resorting to polling.
  • Avoid using watchOptions.pollIntervalMs in next.config.js to work around Fast Refresh issues. Only use it as a last resort. Polling adds significant latency and can drastically increase CPU and I/O usage.

production에서의 사용은 Docker deploy에 대해 더 알아보기를 참고하세요.

Learn more about Docker deployment for production use.

3. (Windows) Use Dev Drive or WSL 23. (Windows) Dev Drive 또는 WSL 2 사용하기

Windows 11의 Dev Drive 기능은 일반적인 개발 workflow의 성능을 높이기 위해 대체 filesystem을 사용합니다. Microsoft에 설정 방법을 설명하는 가이드가 있습니다.

Windows 11's Dev Drive feature uses an alternative filesystem to improve performance for common development workflows. Microsoft has a guide explaining how to configure it.

또는 Windows는 Windows Subsystem for Linux를 사용해 Linux virtual machine을 쉽게 설정하는 방법을 제공합니다. WSL 2를 사용하면 더 나은 성능을 얻을 수 있습니다.

Alternatively, Windows provides an easy way to set up a Linux virtual machine using Windows Subsystem for Linux. You may see better performance by using WSL 2.

WSL 2를 사용할 때는 프로젝트 directory를 Windows drive(예: C:\ 또는 /mnt/c)가 아니라 virtual machine의 filesystem 안(예: /home/$USER/project)에 저장하세요. 그렇지 않으면 성능이 더 나빠지고, 개발 중에 파일 업데이트가 제대로 반영되지 않을 수 있습니다.

When using WSL 2, store your project directory inside the virtual machine's filesystem (e.g. /home/$USER/project) and not on a Windows drive (e.g. C:\ or /mnt/c). If you do not do this, you will experience worse performance and file updates may not be reflected properly in development.

Improving application development performance애플리케이션 개발 성능 개선하기

1. Update Next.js and use Turbopack1. Next.js 업데이트하고 Turbopack 사용하기

최신 버전의 Next.js를 사용하고 있는지 확인하세요. 새 버전에는 성능 개선이 포함되는 경우가 많습니다.

Make sure you're using the latest version of Next.js. Each new version often includes performance improvements.

이제 Turbopack이 Next.js 개발의 기본 bundler이며, webpack보다 성능이 크게 향상되었습니다.

Turbopack is now the default bundler for Next.js development and provides significant performance improvements over webpack.

pnpm add next@latest
pnpm dev  # Turbopack is used by default
npm install next@latest
npm run dev  # Turbopack is used by default
yarn add next@latest
yarn dev  # Turbopack is used by default
bun add next@latest
bun dev  # Turbopack is used by default

Turbopack 대신 Webpack을 사용해야 한다면 opt-in할 수 있습니다:

If you need to use Webpack instead of Turbopack, you can opt-in:

pnpm dev --webpack
npm run dev -- --webpack
yarn dev --webpack
bun run dev --webpack

Turbopack에 대해 더 알아보기. 자세한 내용은 upgrade 가이드와 codemod를 참고하세요.

Learn more about Turbopack. See our upgrade guides and codemods for more information.

2. Check your imports2. import 확인하기

코드를 import하는 방식은 compile 및 bundling 시간에 큰 영향을 줄 수 있습니다. package bundling 최적화에 대해 더 알아보고, Dependency Cruiser나 Madge 같은 도구를 살펴보세요.

The way you import code can greatly affect compilation and bundling time. Learn more about optimizing package bundling and explore tools like Dependency Cruiser or Madge.

Icon librariesIcon library

@material-ui/icons, @phosphor-icons/react, react-icons 같은 library는 몇 개만 사용하더라도 수천 개의 icon을 import할 수 있습니다. 필요한 icon만 import하도록 해 보세요:

Libraries like @material-ui/icons, @phosphor-icons/react, or react-icons can import thousands of icons, even if you only use a few. Try to import only the icons you need:

// Instead of this:
import { TriangleIcon } from '@phosphor-icons/react'

// Do this:
import { TriangleIcon } from '@phosphor-icons/react/dist/csr/Triangle'

어떤 import 패턴을 써야 하는지는 사용 중인 icon library의 문서에서 찾을 수 있는 경우가 많습니다. 이 예제는 @phosphor-icons/react의 권장 사항을 따릅니다.

You can often find what import pattern to use in the documentation for the icon library you're using. This example follows @phosphor-icons/react recommendation.

react-icons 같은 library에는 여러 가지 icon set이 들어 있습니다. 하나의 set을 골라 그 set만 계속 사용하세요.

Libraries like react-icons includes many different icon sets. Choose one set and stick with that set.

예를 들어 애플리케이션이 react-icons를 사용하면서 다음을 모두 import한다고 해 봅시다:

For example, if your application uses react-icons and imports all of these:

  • pi (Phosphor Icons)
  • md (Material Design Icons)
  • tb (tabler-icons)
  • cg (cssgg)
  • pi (Phosphor Icons)
  • md (Material Design Icons)
  • tb (tabler-icons)
  • cg (cssgg)

각각에서 import를 하나씩만 사용하더라도, 합치면 compiler가 처리해야 하는 module이 수만 개가 됩니다.

Combined they will be tens of thousands of modules that the compiler has to handle, even if you only use a single import from each.

Barrel filesBarrel 파일

"Barrel file"은 다른 파일의 여러 항목을 export하는 파일입니다. compiler가 import를 통해 module scope에 side-effect가 있는지 알아내기 위해 이 파일을 parse해야 하므로 build가 느려질 수 있습니다.

"Barrel files" are files that export many items from other files. They can slow down builds because the compiler has to parse them to find if there are side-effects in the module scope by using the import.

가능하면 특정 파일에서 직접 import하세요. barrel file과 Next.js의 built-in 최적화에 대해 더 알아보세요.

Try to import directly from specific files when possible. Learn more about barrel files and the built-in optimizations in Next.js.

Optimize package importspackage import 최적화하기

Next.js는 특정 package의 import를 자동으로 최적화할 수 있습니다. barrel file을 사용하는 package를 쓰고 있다면 next.config.js에 추가하세요:

Next.js can automatically optimize imports for certain packages. If you are using packages that utilize barrel files, add them to your next.config.js:

module.exports = {
  experimental: {
    optimizePackageImports: ['package-name'],
  },
}

Turbopack은 import를 자동으로 분석하고 최적화합니다. 이 configuration이 필요하지 않습니다.

Turbopack automatically analyzes imports and optimizes them. It does not require this configuration.

3. Check your Tailwind CSS setup3. Tailwind CSS setup 확인하기

Tailwind CSS를 사용한다면 올바르게 설정되어 있는지 확인하세요.

If you're using Tailwind CSS, make sure it's set up correctly.

흔한 실수는 content 배열을 node_modules나 scan하면 안 되는 다른 큰 파일 directory가 포함되도록 설정하는 것입니다.

A common mistake is configuring your content array in a way which includes node_modules or other large directories of files that should not be scanned.

Tailwind CSS 3.4.8 이상 버전은 build를 느리게 할 수 있는 설정에 대해 경고해 줍니다.

Tailwind CSS version 3.4.8 or newer will warn you about settings that might slow down your build.

  1. tailwind.config.js에서 scan할 파일을 구체적으로 지정하세요:

    module.exports = {
  content: [
    './src/**/*.{js,ts,jsx,tsx}', // Good
    // This might be too broad
    // It will match `packages/**/node_modules` too
    // '../../packages/**/*.{js,ts,jsx,tsx}',
  ],
}

  2. 불필요한 파일을 scan하지 마세요:

    module.exports = {
  content: [
    // Better - only scans the 'src' folder
    '../../packages/ui/src/**/*.{js,ts,jsx,tsx}',
  ],
}

  1. In your tailwind.config.js, be specific about which files to scan:

    module.exports = {
  content: [
    './src/**/*.{js,ts,jsx,tsx}', // Good
    // This might be too broad
    // It will match `packages/**/node_modules` too
    // '../../packages/**/*.{js,ts,jsx,tsx}',
  ],
}

  2. Avoid scanning unnecessary files:

    module.exports = {
  content: [
    // Better - only scans the 'src' folder
    '../../packages/ui/src/**/*.{js,ts,jsx,tsx}',
  ],
}

4. Check custom webpack settings4. custom webpack 설정 확인하기

custom webpack 설정을 추가했다면 그것이 compile을 느리게 하고 있을 수 있습니다.

If you've added custom webpack settings, they might be slowing down compilation.

로컬 개발에 정말 필요한지 생각해 보세요. 특정 도구를 production build에만 포함하도록 선택할 수도 있고, 대신 기본 bundler인 Turbopack을 사용하면서 loader를 설정하는 방법을 살펴볼 수도 있습니다.

Consider if you really need them for local development. You can optionally only include certain tools for production builds, or explore using the default Turbopack bundler and configuring loaders instead.

앱이 매우 크다면 더 많은 memory가 필요할 수 있습니다.

If your app is very large, it might need more memory.

6. Server Components and data fetching6. Server Component와 data fetching

Server Component를 변경하면 새 변경 사항을 보여 주기 위해 로컬에서 페이지 전체가 다시 render되며, 여기에는 component의 새 데이터를 fetch하는 것도 포함됩니다.

Changes to Server Components cause the entire page to re-render locally in order to show the new changes, which includes fetching new data for the component.

experimental serverComponentsHmrCache option을 사용하면 로컬 개발에서 Hot Module Replacement(HMR) refresh 사이에 Server Component의 fetch response를 cache할 수 있습니다. 그 결과 response가 더 빨라지고 과금되는 API 호출 비용이 줄어듭니다.

The experimental serverComponentsHmrCache option allows you to cache fetch responses in Server Components across Hot Module Replacement (HMR) refreshes in local development. This results in faster responses and reduced costs for billed API calls.

experimental option에 대해 더 알아보기.

Learn more about the experimental option.

Tools for finding problems문제를 찾는 도구

Detailed fetch logging상세 fetch logging

개발 중에 무슨 일이 일어나고 있는지 더 자세한 정보를 보려면 next.config.js 파일에서 logging.fetches option을 사용하세요:

Use the logging.fetches option in your next.config.js file, to see more detailed information about what's happening during development:

module.exports = {
  logging: {
    fetches: {
      fullUrl: true,
    },
  },
}

Turbopack tracing

Turbopack tracing은 로컬 개발 중 애플리케이션의 성능을 이해하는 데 도움을 주는 도구입니다. 각 module을 compile하는 데 걸린 시간과 module 간의 관계에 대한 상세한 정보를 제공합니다.

Turbopack tracing is a tool that helps you understand the performance of your application during local development. It provides detailed information about the time taken for each module to compile and how they are related.

  1. 최신 버전의 Next.js가 설치되어 있는지 확인합니다.

  2. Turbopack trace 파일을 생성합니다:

    pnpm dev --internal-trace
    npm run dev -- --internal-trace
    yarn dev --internal-trace
    bun dev --internal-trace
  3. 애플리케이션을 돌아다니거나 파일을 수정해 문제를 재현합니다.
  4. Next.js development server를 중지합니다.
  5. .next-profiles 폴더에 trace-turbopack.bin이라는 파일이 생깁니다.

  6. npx next internal trace [path-to-file]로 이 파일을 해석할 수 있습니다:

    npx next internal trace .next-profiles/trace-turbopack.bin

    trace를 사용할 수 없는 버전에서는 이 command의 이름이 turbo-trace-server였습니다:

    npx next internal turbo-trace-server .next-profiles/trace-turbopack.bin
  7. trace server가 실행되면 https://trace.nextjs.org/ 에서 trace를 볼 수 있습니다.
  8. 기본적으로 trace viewer는 시간을 집계(aggregate)해서 보여 줍니다. 개별 시간을 보려면 viewer 오른쪽 위에서 "Aggregated in order"를 "Spans in order"로 바꾸면 됩니다.
  1. Make sure you have the latest version of Next.js installed.

  2. Generate a Turbopack trace file:

    pnpm dev --internal-trace
    npm run dev -- --internal-trace
    yarn dev --internal-trace
    bun dev --internal-trace
  3. Navigate around your application or make edits to files to reproduce the problem.
  4. Stop the Next.js development server.
  5. A file called trace-turbopack.bin will be available in the .next-profiles folder.

  6. You can interpret the file using npx next internal trace [path-to-file]:

    npx next internal trace .next-profiles/trace-turbopack.bin

    On versions where trace is not available, the command was named turbo-trace-server:

    npx next internal turbo-trace-server .next-profiles/trace-turbopack.bin
  7. Once the trace server is running you can view the trace at https://trace.nextjs.org/.
  8. By default the trace viewer will aggregate timings, in order to see each individual time you can switch from "Aggregated in order" to "Spans in order" at the top right of the viewer.
Good to know

trace 파일은 프로젝트 root의 .next-profiles directory에 생성됩니다.

The trace file is placed in the .next-profiles directory at the project root.
