How to implement authentication in Next.jsNext.js에서 인증 구현하기

authentication을 이해하는 것은 애플리케이션의 데이터를 보호하는 데 매우 중요합니다. 이 페이지에서는 auth를 구현할 때 어떤 React와 Next.js 기능을 사용해야 하는지 안내합니다.

Understanding authentication is crucial for protecting your application's data. This page will guide you through what React and Next.js features to use to implement auth.

시작하기 전에 이 과정을 세 가지 개념으로 나눠 보면 도움이 됩니다:

Before starting, it helps to break down the process into three concepts:

  1. Authentication: 사용자가 자신이 주장하는 그 사람이 맞는지 확인합니다. 사용자는 username과 password처럼 자신이 가진 무언가로 신원을 증명해야 합니다.
  2. Session Management: 여러 request에 걸쳐 사용자의 auth state를 추적합니다.
  3. Authorization: 사용자가 어떤 route와 데이터에 접근할 수 있는지 결정합니다.
  1. Authentication: Verifies if the user is who they say they are. It requires the user to prove their identity with something they have, such as a username and password.
  2. Session Management: Tracks the user's auth state across requests.
  3. Authorization: Decides what routes and data the user can access.

이 페이지의 예제는 학습 목적으로 기본적인 username/password auth를 단계별로 살펴봅니다. 직접 custom auth solution을 구현할 수도 있지만, 보안을 높이고 단순하게 만들기 위해 authentication library 사용을 권장합니다. 이런 library는 authentication, session management, authorization을 위한 기본 solution뿐 아니라 social login, multi-factor authentication, role-based access control 같은 추가 기능도 제공합니다. 목록은 Auth Libraries 섹션에서 확인할 수 있습니다.

The examples on this page walk through basic username and password auth for educational purposes. While you can implement a custom auth solution, for increased security and simplicity, we recommend using an authentication library. These offer built-in solutions for authentication, session management, and authorization, as well as additional features such as social logins, multi-factor authentication, and role-based access control. You can find a list in the Auth Libraries section.

You can use the <form> element with React's Server Actions and useActionState to capture user credentials, validate form fields, and call your Authentication Provider's API or database.

Server Action은 항상 server에서 실행되므로 authentication 로직을 처리하기에 안전한 환경을 제공합니다.

Since Server Actions always execute on the server, they provide a secure environment for handling authentication logic.

2. Validate form fields on the server2. server에서 form field 검증하기

Server Action을 사용해 server에서 form field를 검증하세요. authentication provider가 form validation을 제공하지 않는다면 Zod, Valibot, Yup 같은 schema validation library를 사용할 수 있습니다.

Use the Server Action to validate the form fields on the server. If your authentication provider doesn't provide form validation, you can use a schema validation library like Zod, Valibot or Yup.

Zod를 예로 들면, 적절한 error message와 함께 form schema를 정의할 수 있습니다:

Using Zod as an example, you can define a form schema with appropriate error messages:

TSJSapp/lib/definitions.ts
import * as z from 'zod'

export const SignupFormSchema = z.object({
  name: z
    .string()
    .min(2, { error: 'Name must be at least 2 characters long.' })
    .trim(),
  email: z.email({ error: 'Please enter a valid email.' }).trim(),
  password: z
    .string()
    .min(8, { error: 'Be at least 8 characters long' })
    .regex(/[a-zA-Z]/, { error: 'Contain at least one letter.' })
    .regex(/[0-9]/, { error: 'Contain at least one number.' })
    .regex(/[^a-zA-Z0-9]/, {
      error: 'Contain at least one special character.',
    })
    .trim(),
})

authentication provider의 API나 database를 불필요하게 호출하지 않도록, form field 중 하나라도 정의된 schema와 맞지 않으면 Server Action에서 일찍 return할 수 있습니다.

To prevent unnecessary calls to your authentication provider's API or database, you can return early in the Server Action if any form fields do not match the defined schema.

TSJSapp/actions/auth.ts
import { SignupFormSchema, FormState } from '@/app/lib/definitions'

export async function signup(state: FormState, formData: FormData) {
  // Validate form fields
  const validatedFields = SignupFormSchema.safeParse({
    name: formData.get('name'),
    email: formData.get('email'),
    password: formData.get('password'),
  })

  // If any form fields are invalid, return early
  if (!validatedFields.success) {
    return {
      errors: validatedFields.error.flatten().fieldErrors,
    }
  }

  // Call the provider or db to create a user...
}

Back in your <SignupForm />, you can use React's useActionState hook to display validation errors while the form is submitting:

'use client'

import { signup } from '@/app/actions/auth'
import { useActionState } from 'react'

export default function SignupForm() {
  const [state, action, pending] = useActionState(signup, undefined)

  return (

      <div>

        <input id="name" name="name" placeholder="Name" />

        <label htmlFor="email">Email</label>

          </ul>
        </div>

Session Management세션 관리

session management는 사용자의 인증된 state가 여러 request에 걸쳐 유지되도록 보장합니다. 여기에는 session 또는 token의 생성, 저장, 갱신, 삭제가 포함됩니다.

Session management ensures that the user's authenticated state is preserved across requests. It involves creating, storing, refreshing, and deleting sessions or tokens.

session에는 두 가지 유형이 있습니다:

There are two types of sessions:

  1. Stateless: session 데이터(또는 token)가 브라우저의 cookie에 저장됩니다. cookie는 request마다 함께 전송되어 server에서 session을 검증할 수 있습니다. 이 방법은 더 단순하지만, 올바르게 구현하지 않으면 보안이 약해질 수 있습니다.
  2. Database: session 데이터가 database에 저장되고, 사용자의 브라우저는 암호화된 session ID만 받습니다. 이 방법은 더 안전하지만, 복잡할 수 있고 server 리소스를 더 많이 사용합니다.
  1. Stateless: Session data (or a token) is stored in the browser's cookies. The cookie is sent with each request, allowing the session to be verified on the server. This method is simpler, but can be less secure if not implemented correctly.
  2. Database: Session data is stored in a database, with the user's browser only receiving the encrypted session ID. This method is more secure, but can be complex and use more server resources.
Good to know

두 방법 중 하나를 쓰거나 둘 다 쓸 수 있지만, iron-session이나 Jose 같은 session management library 사용을 권장합니다.

While you can use either method, or both, we recommend using a session management library such as iron-session or Jose.

Stateless Sessions

stateless session을 만들고 관리하려면 몇 가지 단계를 따라야 합니다:

To create and manage stateless sessions, there are a few steps you need to follow:

  1. session에 서명하는 데 사용할 secret key를 생성하고 environment variable로 저장합니다.
  2. session management library를 사용해 session 데이터를 암호화/복호화하는 로직을 작성합니다.
  3. Next.js cookies API로 cookie를 관리합니다.
  1. Generate a secret key, which will be used to sign your session, and store it as an environment variable.
  2. Write logic to encrypt/decrypt session data using a session management library.
  3. Manage cookies using the Next.js cookies API.

위 내용 외에도, 사용자가 애플리케이션에 다시 돌아왔을 때 session을 update(또는 refresh)하고, 사용자가 로그아웃할 때 session을 삭제하는 기능을 추가하는 것을 고려하세요.

In addition to the above, consider adding functionality to update (or refresh) the session when the user returns to the application, and delete the session when the user logs out.

1. Generating a secret key1. secret key 생성하기

session에 서명할 secret key를 생성하는 방법은 몇 가지가 있습니다. 예를 들어 terminal에서 openssl command를 사용할 수 있습니다:

There are a few ways you can generate secret key to sign your session. For example, you may choose to use the openssl command in your terminal:

>_terminal

이 command는 32자 random string을 생성하며, 이를 secret key로 사용해 environment variable 파일에 저장할 수 있습니다:

This command generates a 32-character random string that you can use as your secret key and store in your environment variables file:

>_.env
SESSION_SECRET=your_secret_key

그러면 session management 로직에서 이 key를 참조할 수 있습니다:

You can then reference this key in your session management logic:

JSapp/lib/session.js
const secretKey = process.env.SESSION_SECRET

2. Encrypting and decrypting sessions2. session 암호화와 복호화

다음으로, 선호하는 session management library를 사용해 session을 암호화하고 복호화할 수 있습니다. 이전 예제에 이어서, session management 로직이 server에서만 실행되도록 Jose와 React의 server-only package를 사용하겠습니다.

Next, you can use your preferred session management library to encrypt and decrypt sessions. Continuing from the previous example, we'll use Jose and React's server-only package to ensure that your session management logic is only executed on the server.

TSJSapp/lib/session.ts
import 'server-only'
import { SignJWT, jwtVerify } from 'jose'
import { SessionPayload } from '@/app/lib/definitions'

const secretKey = process.env.SESSION_SECRET
const encodedKey = new TextEncoder().encode(secretKey)

export async function encrypt(payload: SessionPayload) {
  return new SignJWT(payload)
    .setProtectedHeader({ alg: 'HS256' })
    .setIssuedAt()
    .setExpirationTime('7d')
    .sign(encodedKey)
}

export async function decrypt(session: string | undefined = '') {
  try {
    const { payload } = await jwtVerify(session, encodedKey, {
      algorithms: ['HS256'],
    })
    return payload
  } catch (error) {
    console.log('Failed to verify session')
  }
}

Tips
  • payload에는 사용자 ID, role 등 이후 request에서 사용할 최소한의 고유한 사용자 데이터만 들어 있어야 합니다. 전화번호, email 주소, 신용카드 정보 같은 개인 식별 정보나 password 같은 민감한 데이터는 포함하지 않아야 합니다.
  • The payload should contain the minimum, unique user data that'll be used in subsequent requests, such as the user's ID, role, etc. It should not contain personally identifiable information like phone number, email address, credit card information, etc, or sensitive data like passwords.

3. Setting cookies (recommended options)3. cookie 설정하기 (권장 option)

session을 cookie에 저장하려면 Next.js cookies API를 사용하세요. cookie는 server에서 설정해야 하며, 다음 권장 option을 포함해야 합니다:

To store the session in a cookie, use the Next.js cookies API. The cookie should be set on the server, and include the recommended options:

  • HttpOnly: client-side JavaScript가 cookie에 접근하지 못하게 합니다.
  • Secure: https로 cookie를 전송합니다.
  • SameSite: cookie를 cross-site request와 함께 보낼 수 있는지 지정합니다.
  • Max-Age or Expires: 일정 기간이 지나면 cookie를 삭제합니다.
  • Path: cookie의 URL path를 정의합니다.
  • HttpOnly: Prevents client-side JavaScript from accessing the cookie.
  • Secure: Use https to send the cookie.
  • SameSite: Specify whether the cookie can be sent with cross-site requests.
  • Max-Age or Expires: Delete the cookie after a certain period.
  • Path: Define the URL path for the cookie.

Database Sessions

database session을 만들고 관리하려면 다음 단계를 따라야 합니다:

To create and manage database sessions, you'll need to follow these steps:

  1. database에 session과 데이터를 저장할 table을 만듭니다(또는 Auth Library가 이를 처리하는지 확인합니다).
  2. session을 insert, update, delete하는 기능을 구현합니다
  3. session ID를 사용자의 브라우저에 저장하기 전에 암호화하고, database와 cookie가 동기화된 상태를 유지하도록 합니다(선택 사항이지만 Proxy에서 optimistic auth check를 하려면 권장됩니다).
  1. Create a table in your database to store session and data (or check if your Auth Library handles this).
  2. Implement functionality to insert, update, and delete sessions
  3. Encrypt the session ID before storing it in the user's browser, and ensure the database and cookie stay in sync (this is optional, but recommended for optimistic auth checks in Proxy).

예를 들면 다음과 같습니다:

For example:

TSJSapp/lib/session.ts
import { cookies } from 'next/headers'
import { db } from '@/app/lib/db'
import { encrypt } from '@/app/lib/session'

export async function createSession(id: number) {
  const expiresAt = new Date(Date.now() + 7 * 24 * 60 * 60 * 1000)

  // 1. Create a session in the database
  const data = await db
    .insert(sessions)
    .values({
      userId: id,
      expiresAt,
    })
    // Return the session ID
    .returning({ id: sessions.id })

  const sessionId = data[0].id

  // 2. Encrypt the session ID
  const session = await encrypt({ sessionId, expiresAt })

  // 3. Store the session in cookies for optimistic auth checks
  const cookieStore = await cookies()
  cookieStore.set('session', session, {
    httpOnly: true,
    secure: true,
    expires: expiresAt,
    sameSite: 'lax',
    path: '/',
  })
}

  • 사용자가 마지막으로 로그인한 시각이나 활성 기기 수를 추적하거나, 사용자가 모든 기기에서 로그아웃할 수 있게 하는 등 더 고급 use case에서는 database session을 선택할 수 있습니다.
  • For faster access, you may consider adding server caching for the lifetime of the session. You can also keep the session data in your primary database, and combine data requests to reduce the number of queries.
  • You may opt to use database sessions for more advanced use cases, such as keeping track of the last time a user logged in, or number of active devices, or give users the ability to log out of all devices.

After implementing session management, you'll need to add authorization logic to control what users can access and do within your application. Continue to the Authorization section to learn more.

Authorization

사용자가 인증되고 session이 생성되면, authorization을 구현해 사용자가 애플리케이션 안에서 무엇에 접근하고 무엇을 할 수 있는지 제어할 수 있습니다.

Once a user is authenticated and a session is created, you can implement authorization to control what the user can access and do within your application.

authorization check에는 크게 두 가지 유형이 있습니다:

There are two main types of authorization checks:

  1. Optimistic: cookie에 저장된 session 데이터를 사용해 사용자가 route에 접근하거나 action을 수행할 권한이 있는지 확인합니다. 이런 check는 UI element를 보여 주거나 숨기는 것, 또는 권한이나 role에 따라 사용자를 redirect하는 것 같은 빠른 작업에 유용합니다.
  2. Secure: database에 저장된 session 데이터를 사용해 사용자가 route에 접근하거나 action을 수행할 권한이 있는지 확인합니다. 이런 check는 더 안전하며, 민감한 데이터나 action에 접근해야 하는 작업에 사용합니다.
  1. Optimistic: Checks if the user is authorized to access a route or perform an action using the session data stored in the cookie. These checks are useful for quick operations, such as showing/hiding UI elements or redirecting users based on permissions or roles.
  2. Secure: Checks if the user is authorized to access a route or perform an action using the session data stored in the database. These checks are more secure and are used for operations that require access to sensitive data or actions.

두 경우 모두 다음을 권장합니다:

For both cases, we recommend:

  • authorization 로직을 한곳에 모으기 위해 Data Access Layer 만들기
  • 필요한 데이터만 반환하도록 Data Transfer Objects (DTO) 사용하기
  • 선택적으로 Proxy를 사용해 optimistic check 수행하기.
  • Creating a Data Access Layer to centralize your authorization logic
  • Using Data Transfer Objects (DTO) to only return the necessary data
  • Optionally use Proxy to perform optimistic checks.

Optimistic checks with Proxy (Optional)Proxy로 optimistic check 하기 (선택)

Proxy를 사용해 권한에 따라 사용자를 redirect하고 싶은 경우가 있습니다:

There are some cases where you may want to use Proxy and redirect users based on permissions:

  • optimistic check를 수행하려는 경우. Proxy는 모든 route에서 실행되므로, redirect 로직을 한곳에 모으고 권한이 없는 사용자를 미리 걸러 내기에 좋은 방법입니다.
  • 사용자 간에 데이터를 공유하는 static route(예: paywall 뒤의 콘텐츠)를 보호하려는 경우.
  • To perform optimistic checks. Since Proxy runs on every route, it's a good way to centralize redirect logic and pre-filter unauthorized users.
  • To protect static routes that share data between users (e.g. content behind a paywall).

하지만 Proxy는 prefetch된 route를 포함한 모든 route에서 실행되므로, 성능 문제를 막으려면 cookie에서 session만 읽고(optimistic check) database check는 피하는 것이 중요합니다.

However, since Proxy runs on every route, including prefetched routes, it's important to only read the session from the cookie (optimistic checks), and avoid database checks to prevent performance issues.

예를 들면 다음과 같습니다:

For example:

TSJSproxy.ts
import { NextRequest, NextResponse } from 'next/server'
import { decrypt } from '@/app/lib/session'
import { cookies } from 'next/headers'

// 1. Specify protected and public routes
const protectedRoutes = ['/dashboard']
const publicRoutes = ['/login', '/signup', '/']

export default async function proxy(req: NextRequest) {
  // 2. Check if the current route is protected or public
  const path = req.nextUrl.pathname
  const isProtectedRoute = protectedRoutes.includes(path)
  const isPublicRoute = publicRoutes.includes(path)

  // 3. Decrypt the session from the cookie
  const cookie = (await cookies()).get('session')?.value
  const session = await decrypt(cookie)

  // 4. Redirect to /login if the user is not authenticated
  if (isProtectedRoute && !session?.userId) {
    return NextResponse.redirect(new URL('/login', req.nextUrl))
  }

  // 5. Redirect to /dashboard if the user is authenticated
  if (
    isPublicRoute &&
    session?.userId &&
    !req.nextUrl.pathname.startsWith('/dashboard')
  ) {
    return NextResponse.redirect(new URL('/dashboard', req.nextUrl))
  }

  return NextResponse.next()
}

// Routes Proxy should not run on
export const config = {
  matcher: ['/((?!api|_next/static|_next/image|.*\\.png$).*)'],
}

Proxy는 초기 check에 유용할 수 있지만, 데이터를 보호하는 유일한 방어선이 되어서는 안 됩니다. 대부분의 security check는 데이터 source에 최대한 가까운 곳에서 수행해야 합니다. 자세한 내용은 Data Access Layer를 참고하세요.

While Proxy can be useful for initial checks, it should not be your only line of defense in protecting your data. The majority of security checks should be performed as close as possible to your data source, see Data Access Layer for more information.

Tips
  • Proxy에서는 req.cookies.get('session')?.value로도 cookie를 읽을 수 있습니다.
  • Proxy는 Node.js runtime을 사용하므로, 사용하는 Auth library와 session management library가 호환되는지 확인하세요.
  • Proxy의 matcher property를 사용해 Proxy가 실행될 route를 지정할 수 있습니다. 다만 auth의 경우에는 Proxy가 모든 route에서 실행되도록 하는 것을 권장합니다.
  • In Proxy, you can also read cookies using req.cookies.get('session')?.value.
  • Proxy uses the Node.js runtime, check if your Auth library and session management library are compatible.
  • You can use the matcher property in the Proxy to specify which routes Proxy should run on. Although, for auth, it's recommended Proxy runs on all routes.

Creating a Data Access Layer (DAL)Data Access Layer (DAL) 만들기

데이터 request와 authorization 로직을 한곳에 모으기 위해 DAL을 만드는 것을 권장합니다.

We recommend creating a DAL to centralize your data requests and authorization logic.

DAL에는 사용자가 애플리케이션과 상호작용할 때 사용자의 session을 검증하는 함수가 포함되어야 합니다. 최소한 이 함수는 session이 유효한지 확인한 다음, redirect하거나 이후 request에 필요한 사용자 정보를 반환해야 합니다.

The DAL should include a function that verifies the user's session as they interact with your application. At the very least, the function should check if the session is valid, then redirect or return the user information needed to make further requests.

예를 들어 verifySession() 함수를 포함하는 DAL용 파일을 따로 만드세요. 그런 다음 React의 cache API를 사용해 React render pass 동안 함수의 반환값을 memoize하세요:

For example, create a separate file for your DAL that includes a verifySession() function. Then use React's cache API to memoize the return value of the function during a React render pass:

TSJSapp/lib/dal.ts
import 'server-only'

import { cache } from 'react'
import { cookies } from 'next/headers'
import { redirect } from 'next/navigation'
import { decrypt } from '@/app/lib/session'

export const verifySession = cache(async () => {
  const cookie = (await cookies()).get('session')?.value
  const session = await decrypt(cookie)

  if (!session?.userId) {
    redirect('/login')
  }

  return { isAuth: true, userId: session.userId }
})

You can then invoke the verifySession() function in your data requests, Server Actions, and Route Handlers:

Good to know

React의 cache는 하나의 React render pass 안에서 중복을 제거합니다. Server Action과 Route Handler는 render pass의 일부가 아니므로, 이 wrapper는 아무 효과가 없고 호출할 때마다 함수가 실행됩니다.

React's cache deduplicates within a React render pass. Server Actions and Route Handlers are not part of a render pass, so the wrapper does nothing and every call runs the function.

TSJSapp/lib/dal.ts
export const getUser = cache(async () => {
  const session = await verifySession()
  if (!session) return null

  try {
    const data = await db.query.users.findMany({
      where: eq(users.id, session.userId),
      // Explicitly return the columns you need rather than the whole user object
      columns: {
        id: true,
        name: true,
        email: true,
      },
    })

    const user = data[0]

    return user
  } catch (error) {
    console.log('Failed to fetch user')
    return null
  }
})

  • secure check를 위해 session ID를 database와 비교해 session이 유효한지 확인할 수 있습니다. render pass 동안 database에 불필요한 중복 request가 가지 않도록 React의 cache 함수를 사용하세요.
  • 관련된 데이터 request를 어떤 method보다 먼저 verifySession()을 실행하는 JavaScript class로 묶고 싶을 수도 있습니다.
  • A DAL can be used to protect data fetched at request time. However, for static routes that share data between users, data will be fetched at build time and not at request time. Use Proxy to protect static routes.
  • For secure checks, you can check if the session is valid by comparing the session ID with your database. Use React's cache function to avoid unnecessary duplicate requests to the database during a render pass.
  • You may wish to consolidate related data requests in a JavaScript class that runs verifySession() before any methods.

Using Data Transfer Objects (DTO)Data Transfer Objects (DTO) 사용하기

데이터를 가져올 때는 object 전체가 아니라 애플리케이션에서 사용할 필요한 데이터만 반환하는 것을 권장합니다. 예를 들어 사용자 데이터를 fetch한다면, password나 전화번호 등이 들어 있을 수 있는 user object 전체 대신 사용자의 ID와 이름만 반환할 수 있습니다.

When retrieving data, it's recommended you return only the necessary data that will be used in your application, and not entire objects. For example, if you're fetching user data, you might only return the user's ID and name, rather than the entire user object which could contain passwords, phone numbers, etc.

하지만 반환되는 데이터 구조를 제어할 수 없거나, 팀에서 object 전체가 client로 전달되는 것을 피하고 싶다면, client에 노출해도 안전한 field를 지정하는 것 같은 전략을 사용할 수 있습니다.

However, if you have no control over the returned data structure, or are working in a team where you want to avoid whole objects being passed to the client, you can use strategies such as specifying what fields are safe to be exposed to the client.

TSJSapp/lib/dto.ts
import 'server-only'
import { getUser } from '@/app/lib/dal'

function canSeeUsername(viewer: User) {
  return true
}

function canSeePhoneNumber(viewer: User, team: string) {
  return viewer.isAdmin || team === viewer.team
}

export async function getProfileDTO(slug: string) {
  const data = await db.query.users.findMany({
    where: eq(users.slug, slug),
    // Return specific columns here
  })
  const user = data[0]

  const currentUser = await getUser(user.id)

  // Or return only what's specific to the query here
  return {
    username: canSeeUsername(currentUser) ? user.username : null,
    phonenumber: canSeePhoneNumber(currentUser, user.team)
      ? user.phonenumber
      : null,
  }
}

데이터 request와 authorization 로직을 DAL에 모으고 DTO를 사용하면 모든 데이터 request가 안전하고 일관되게 처리되도록 보장할 수 있어서, 애플리케이션이 커져도 유지 보수, 감사(audit), debug가 쉬워집니다.

By centralizing your data requests and authorization logic in a DAL and using DTOs, you can ensure that all data requests are secure and consistent, making it easier to maintain, audit, and debug as your application scales.

Good to know
  • DTO를 정의하는 방법은 toJSON()을 사용하는 것부터 위 예제처럼 개별 함수를 쓰는 것, JS class를 쓰는 것까지 여러 가지가 있습니다. 이는 React나 Next.js 기능이 아니라 JavaScript 패턴이므로, 애플리케이션에 가장 적합한 패턴을 찾기 위해 조사해 보는 것을 권장합니다.

  • There are a couple of different ways you can define a DTO, from using toJSON(), to individual functions like the example above, or JS classes. Since these are JavaScript patterns and not a React or Next.js feature, we recommend doing some research to find the best pattern for your application.

Server Components

Server Component에서의 auth check는 role-based access에 유용합니다. 예를 들어 사용자의 role에 따라 component를 조건부로 render할 수 있습니다:

Auth check in Server Components are useful for role-based access. For example, to conditionally render components based on the user's role:

TSJSapp/dashboard/page.tsx
import { verifySession } from '@/app/lib/dal'

export default async function Dashboard() {
  const session = await verifySession()
  const userRole = session?.role // Assuming 'role' is part of the session object

  if (userRole === 'admin') {
    return <AdminDashboard />
  } else if (userRole === 'user') {
    return <UserDashboard />
  } else {
    redirect('/login')
  }
}

이 예제에서는 DAL의 verifySession() 함수를 사용해 'admin', 'user', 권한 없음 role을 확인합니다. 이 패턴은 각 사용자가 자신의 role에 맞는 component하고만 상호작용하도록 보장합니다.

In the example, we use the verifySession() function from our DAL to check for 'admin', 'user', and unauthorized roles. This pattern ensures that each user interacts only with components appropriate to their role.

Layouts and auth checksLayout과 auth check

Partial Rendering 때문에 Layout에서 check를 할 때는 주의해야 합니다. layout은 navigation 시 다시 render되지 않으므로, route가 바뀔 때마다 사용자 session이 확인되지 않습니다.

Due to Partial Rendering, be cautious when doing checks in Layouts as these don't re-render on navigation, meaning the user session won't be checked on every route change.

또한 layout은 route의 나머지 부분이 render될지 여부를 제어하지 않습니다. route segment와 parallel route slot은 router가 render하므로, layout이 이를 숨기거나 바꿔치기해도 실행되는 것이나 RSC Payload에 나타나는 것을 막지 못합니다.

A layout also does not control whether the rest of the route renders. Route segments and parallel route slots are rendered by the router, so a layout that hides or swaps them does not stop them from running or from appearing in the RSC Payload.

대신 데이터 source나 조건부로 render될 component 가까이에서 check를 해야 합니다.

Instead, you should do the checks close to your data source or the component that'll be conditionally rendered.

예를 들어 사용자 데이터를 fetch해서 nav에 사용자 이미지를 표시하는 공유 layout을 생각해 보세요. layout에서 auth check를 하는 대신, layout에서는 사용자 데이터(getUser())를 fetch하고 auth check는 DAL에서 해야 합니다.

For example, consider a shared layout that fetches the user data and displays the user image in a nav. Instead of doing the auth check in the layout, you should fetch the user data (getUser()) in the layout and do the auth check in your DAL.

이렇게 하면 애플리케이션 어디에서 getUser()가 호출되든 auth check가 수행되도록 보장되고, 개발자가 사용자에게 데이터 접근 권한이 있는지 확인하는 것을 잊는 일을 막을 수 있습니다.

This guarantees that wherever getUser() is called within your application, the auth check is performed, and prevents developers from forgetting to check that the user is authorized to access the data.

Auth and streamingAuth와 streaming

session과 사용자 데이터는 route 전반에 반복되는 shell UI(header, nav)에 자주 나타납니다. layout에서 cookies(), headers(), 또는 DAL에 대해 최상위 await를 하면 해당 segment의 첫 streaming chunk가 늦어지고, {children}이 그 작업 뒤에 묶이게 됩니다.

Session and user data often appear in shell UI (header, nav) that repeats across routes. A top-level await on cookies(), headers(), or the DAL in a layout delays the first streamed chunk for that segment and holds {children} behind that work.

shell의 일부(예: user menu)만 session 데이터가 필요하다면, await를 중첩된 Server Component로 옮기고 <Suspense>로 감싸서 page의 나머지 부분이 먼저 stream되도록 하세요. 이 패턴은 Push dynamic access down을 참고하세요.

If only part of the shell needs session data (for example, a user menu), move the await into a nested Server Component and wrap it in <Suspense> so the rest of the page streams first. See Push dynamic access down for the pattern.

Client Component는 DAL을 import할 수 없습니다. 부모 Server Component에서 verifySession(), getUser() 같은 함수를 실행한 다음, 데이터를 props나 context provider를 통해 client 자식에게 전달하세요. 이 패턴은 Using React's use within a Context Provider를 참고하고, 민감한 session field가 client에 도달하지 않도록 React의 taintUniqueValue API를 사용하세요.

Client Components can't import the DAL. Run verifySession(), getUser(), or similar in a parent Server Component, then pass data to client children as props or through a context provider. For that pattern, see Using React's use within a Context Provider, and use React's taintUniqueValue API to keep sensitive session fields from reaching the client.

예를 들어 dashboard page에서 사용자 session을 검증하고 사용자 데이터를 fetch할 수 있습니다:

Auth checks in leaf componentsleaf component에서의 auth check

사용자 권한에 따라 UI element를 조건부로 render하는 leaf component에서도 auth check를 수행할 수 있습니다. 예를 들어 admin 전용 action을 표시하는 component는 다음과 같습니다:

You can also perform auth checks in leaf components that conditionally render UI elements based on user permissions. For example, a component that displays admin-only actions:

TSJSapp/ui/admin-actions.tsx
import { verifySession } from '@/app/lib/dal'

export default async function AdminActions() {
  const session = await verifySession()
  const userRole = session?.role

  if (userRole !== 'admin') {
    return null
  }

  return (
    <div>
      <button>Delete User</button>
      <button>Edit Settings</button>
    </div>
  )
}
import { verifySession } from '@/app/lib/dal'

export default async function AdminActions() {
  const session = await verifySession()
  const userRole = session?.role

  if (userRole !== 'admin') {
    return null
  }

  return (
    <div>
      <button>Delete User</button>
      <button>Edit Settings</button>
    </div>
  )
}

이 패턴을 사용하면 각 component에서 render 시점에 auth check가 이루어지도록 보장하면서, 사용자 권한에 따라 UI element를 보여 주거나 숨길 수 있습니다.

This pattern allows you to show or hide UI elements based on user permissions while ensuring the auth check happens at render time in each component.

Good to know
  • SPA에서 흔한 패턴은 사용자가 권한이 없으면 layout이나 최상위 component에서 return null을 하는 것입니다. Next.js 애플리케이션에는 여러 entry point가 있어서 이 방법으로는 중첩된 route segment와 Server Action에 대한 접근을 막을 수 없으므로, 이 패턴은 권장하지 않습니다.
  • 이런 component에서 호출하는 Server Action도 반드시 자체 authorization check를 수행하도록 하세요. client 쪽 UI 제한만으로는 보안에 충분하지 않습니다.
  • A common pattern in SPAs is to return null in a layout or a top-level component if a user is not authorized. This pattern is not recommended since Next.js applications have multiple entry points, which will not prevent nested route segments and Server Actions from being accessed.
  • Ensure that any Server Actions called from these components also perform their own authorization checks, as client-side UI restrictions alone are not sufficient for security.

Server Actions

Server Action은 외부에 공개된 API endpoint와 같은 수준의 보안 고려 사항으로 다루고, 사용자가 mutation을 수행할 권한이 있는지 확인하세요.

Treat Server Actions with the same security considerations as public-facing API endpoints, and verify if the user is allowed to perform a mutation.

아래 예제에서는 action 진행을 허용하기 전에 사용자의 role을 확인합니다:

In the example below, we check the user's role before allowing the action to proceed:

TSJSapp/lib/actions.ts
'use server'
import { verifySession } from '@/app/lib/dal'

export async function serverAction(formData: FormData) {
  const session = await verifySession()
  const userRole = session?.role

  // Return early if user is not authorized to perform the action
  if (userRole !== 'admin') {
    return null
  }

  // Proceed with the action for authorized users
}

Route Handlers

Route Handler는 외부에 공개된 API endpoint와 같은 수준의 보안 고려 사항으로 다루고, 사용자가 Route Handler에 접근할 권한이 있는지 확인하세요.

Treat Route Handlers with the same security considerations as public-facing API endpoints, and verify if the user is allowed to access the Route Handler.

예를 들면 다음과 같습니다:

For example:

TSJSapp/api/route.ts
import { verifySession } from '@/app/lib/dal'

export async function GET() {
  // User authentication and role verification
  const session = await verifySession()

  // Check if the user is authenticated
  if (!session) {
    // User is not authenticated
    return new Response(null, { status: 401 })
  }

  // Check if the user has the 'admin' role
  if (session?.role !== 'admin') {
    // User is authenticated but does not have the right permissions
    return new Response(null, { status: 403 })
  }

  // Continue for authorized users
}

The example above demonstrates a Route Handler with a two-tier security check. It first checks for an active session, and then verifies if the logged-in user is an 'admin'.
