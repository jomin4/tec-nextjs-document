turbopackChunkingexperimentalturbopackChunking

experimental.turbopackChunking을 사용하면 Turbopack의 production JavaScript chunker를 설정할 수 있습니다. 이 option들로 chunker가 사용자 행동에 대해 세우는 가정을 바꾸고, chunker가 사용하는 raw size threshold를 조정하고, experimental component chunk 기능을 활성화할 수 있습니다.

experimental.turbopackChunking lets you configure Turbopack's production JavaScript chunker. These options allow you to change the assumptions the chunker makes about user behavior, tweak the raw size thresholds it uses, and enable the experimental component chunks feature.

기본적으로 Turbopack의 chunking은 다음과 같이 설정되어 있습니다:

By default, Turbopack's chunking is configured as follows:

TSJSnext.config.ts
import type { NextConfig } from 'next'

const nextConfig = {
  experimental: {
    turbopackChunking: {
      minChunkSize: 50000,
      maxChunkCountPerGroup: 40,
      maxMergeChunkSize: 200000,
      minComponentChunkSize: 20000,
      generateComponentChunks: false,
    },
  },
} satisfies NextConfig

export default nextConfig
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    turbopackChunking: {
      minChunkSize: 50000,
      maxChunkCountPerGroup: 40,
      maxMergeChunkSize: 200000,
      minComponentChunkSize: 20000,
      generateComponentChunks: false,
    },
  },
}

module.exports = nextConfig

Size ThresholdsSize threshold

다음 option들은 Turbopack이 chunk를 얼마나 적극적으로 merge하는지, 그리고 chunk가 얼마나 커질 수 있는지를 제어합니다. 크기는 압축·minify되지 않은 코드의 byte 단위입니다(압축·minify된 output 크기의 대략 5배).

The following options control how aggressively Turbopack merges chunks and how large a chunk is allowed to grow. Sizes are in bytes of uncompressed, unminified code (roughly 5x the size of the compressed, minified output).

  • minChunkSize (기본값 50000): Turbopack은 작은 chunk를 더 큰 chunk로 merge해서 이 크기보다 작은 chunk가 둘 이상 만들어지는 것을 피합니다. 이 값을 높이면 더 적고 더 큰 chunk가 만들어지고, 낮추면 더 작고 더 많은 chunk가 만들어집니다.
  • maxChunkCountPerGroup (기본값 40): Turbopack은 chunk group(예: route나 dynamic import)당 이 개수보다 많은 chunk를 emit하지 않습니다. 이 값을 낮추면 merge가 더 적극적으로 일어나 page당 network request가 줄어듭니다. 높이면 chunk가 더 작아지고 navigation 시 cache hit 가능성이 높아집니다.
  • maxMergeChunkSize (기본값 200000): Turbopack은 이 크기보다 큰 chunk를 다른 chunk와 절대 merge하지 않습니다. 이렇게 하면 큰 chunk의 코드가 여러 개의 큰 output chunk에 중복되지 않습니다.
  • minChunkSize (default 50000): Turbopack will avoid creating more than one chunk smaller than this size by merging small chunks into larger ones. Raising this number will produce fewer, larger chunks. Meanwhile, lowering it will produce more chunks that are smaller.
  • maxChunkCountPerGroup (default 40): Turbopack will not emit more than this many chunks per chunk group (eg. a route or a dynamic import). Lowering this number will lead to more aggressive merging and less network requests per-page. Raising it will produce smaller chunks and increase the likelihood of cache hits when navigating.
  • maxMergeChunkSize (default 200000): Turbopack never merges a chunk larger than this size with other chunks. This keeps the code in large chunks from being duplicated across multiple large output chunks.

chunk를 merge할 때의 trade-off는 navigation performance를 희생해서 초기 page load performance를 개선하는 것입니다. network request가 하나 늘어날 때마다 비용이 크지만, 작은 chunk일수록 여러 page에서 재사용될 가능성이 높기 때문입니다.

When merging chunks, the trade-off being made is an improvement to performance on initial page loads at the cost of navigation performance. This is because each additional network request being made is costly, however, smaller chunks are more likely to be re-usable across pages.

Component ChunksComponent chunk

component chunk 생성은 재사용성을 희생하지 않으면서 merge된 chunk의 초기 page load 이점을 얻는 것을 목표로 하는 experimental 기능입니다. 이 기능을 사용하면 runtime이 merge된 chunk를 하나의 파일로 load할지, 아니면 아직 갖고 있지 않은 component chunk만 load할지를 동적으로 선택할 수 있습니다. 또한 merge된 chunk의 일부로 이미 load된 chunk는 다시 다운로드되지 않습니다.

Producing component chunks is an experimental feature that aims to give you the initial page load benefits of merged chunks without sacrificing reusability. This feature lets the runtime dynamically choose whether to load a merged chunk as a single file, or to load only the component chunks it doesn't already have. Additionally, chunks that were already loaded as part of a merged chunk will not be re-downloaded.

이렇게 하면 navigation 시 브라우저가 이미 가진 JavaScript를 다시 다운로드하지 않게 됩니다.

This avoids re-downloading JavaScript the browser already has when navigating.

  • generateComponentChunks (기본값 false): 활성화하면 merge된 각 production chunk가 자신을 구성하는 component chunk도 함께 emit하므로, 브라우저 runtime이 개별 component chunk를 fetch할 수 있습니다.
  • minComponentChunkSize (기본값 20000): 아주 작은 chunk가 많이 만들어지는 것을 피하기 위해, 이 크기보다 작은 component chunk는 단독으로 emit되지 않고 하나의 component로 합쳐집니다.
  • generateComponentChunks (default false): when enabled, each merged production chunk also emits its constituent component chunks alongside it, so the browser runtime can fetch individual component chunks.
  • minComponentChunkSize (default 20000): component chunks smaller than this size are folded into a single component instead of being emitted on their own, to avoid producing many tiny chunks.

HeuristicsHeuristic

이 option들은 두 chunk를 merge할 가치가 있는지 따질 때 chunker가 세우는 가정을 바꿉니다.

These change the assumptions the chunker makes when weighing whether merging two chunks is worth it.

  • clusters (RegExp 배열의 배열, 예: [[/^\/dashboard/, /^\/settings/]]): 흔히 함께 방문되는 route의 그룹으로, route pathname과 match됩니다. Turbopack은 navigation이 cluster 안에 머무를 가능성이 높다고 가정하므로, cluster의 route들이 공유하는 chunk를 더 적극적으로 merge합니다.
  • firstPageLoadPriority (0과 1 사이의 숫자): 단일 page load에서 chunk를 merge하는 이점에 얼마나 큰 가중치를 둘지입니다. 값이 높을수록 더 적극적으로 merge합니다. 더 나은 값이 없다면 사이트의 bounce rate가 좋은 근사치입니다.
  • priorityRoutes (RegExp 배열): 방문자가 처음 도착하는 page인 경우가 많은 route입니다(예: homepage). 이 route들의 client-side bundle은 단일 route request 비용을 줄이기 위해 더 적극적으로 merge되며, 그 대가로 다른 page로 navigation할 때 request가 늘어납니다.
  • priorityBoost (기본값 1.5): priorityRoutes route의 single-request 확률에 곱하는 배수입니다. 값이 높을수록 해당 route의 bundle을 더 적극적으로 merge합니다.
  • requestCost (기본값 200000): 추가 request 하나의 예상 비용으로, 압축·minify되지 않은 코드의 byte 단위입니다. 값이 클수록 더 적고 더 큰 chunk, 그리고 전체적으로 더 적은 request 쪽으로 치우칩니다.
  • clusters (an array of arrays of RegExp, e.g. [[/^\/dashboard/, /^\/settings/]]): groups of routes that are commonly visited together, matched against the route pathname. Turbopack assumes navigations are likely to stay within a cluster, so chunks shared by a cluster's routes are merged more eagerly.
  • firstPageLoadPriority (a number between 0 and 1): how heavily to weight the benefit of merging chunks for a single page load. Higher values merge more eagerly. If you don't have a better value, your site's bounce rate is a good approximation.
  • priorityRoutes (an array of RegExp): routes that are often the first page a visitor lands on (e.g. the homepage). Their client-side bundles are merged more eagerly to reduce the single-route request cost, at the cost of extra requests when navigating to other pages.
  • priorityBoost (default 1.5): a multiplier on the single-request probability of priorityRoutes routes. Higher values merge those routes' bundles more aggressively.
  • requestCost (default 200000): the estimated cost of an additional request, in bytes of uncompressed, unminified code. Larger values bias toward fewer, larger chunks and fewer requests overall.
